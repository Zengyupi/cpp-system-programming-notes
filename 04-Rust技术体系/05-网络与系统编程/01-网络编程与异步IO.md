## 1. std::net 同步网络模型

### 1.1 TcpListener 与 TcpStream

Rust 标准库的 `std::net` 提供了同步网络 API，与 C++ 的 BSD socket 封装（如 `boost::asio` 同步模式或裸 socket）对应。核心类型包括 `TcpListener`（服务端监听）、`TcpStream`（TCP 连接）、`UdpSocket`（UDP 套接字）。

```rust
use std::io::{Read, Write};
use std::net::{TcpListener, TcpStream};
use std::thread;

fn handle_client(mut stream: TcpStream) {
    let mut buffer = [0u8; 1024];
    loop {
        match stream.read(&mut buffer) {
            Ok(0) => {
                // 对端关闭连接
                println!("客户端断开: {:?}", stream.peer_addr());
                break;
            }
            Ok(n) => {
                // 回显：将收到的数据原样发回
                if stream.write_all(&buffer[..n]).is_err() {
                    break;
                }
            }
            Err(e) => {
                eprintln!("读取错误: {}", e);
                break;
            }
        }
    }
}

fn main() -> std::io::Result<()> {
    let listener = TcpListener::bind("127.0.0.1:8080")?;
    println!("同步回声服务器监听 127.0.0.1:8080");

    for stream in listener.incoming() {
        match stream {
            Ok(stream) => {
                // 每个连接一个线程（与 C++ thread-per-connection 模型相同）
                thread::spawn(move || handle_client(stream));
            }
            Err(e) => eprintln!("接受连接失败: {}", e),
        }
    }
    Ok(())
}
```

`TcpListener::incoming()` 返回一个迭代器，每次调用 `accept()` 阻塞等待新连接。`TcpStream` 实现了 `Read` 和 `Write` trait，可以像文件一样读写。这个同步模型的局限与 C++ 同步 socket 相同：每个连接需要一个线程，高并发下线程切换开销大，且 `read()`/`write()` 会阻塞当前线程。

### 1.2 UdpSocket 与多线程模型

UDP 是无连接协议，`UdpSocket` 同时用于发送和接收：

```rust
use std::net::UdpSocket;

fn main() -> std::io::Result<()> {
    // 绑定到本地端口
    let socket = UdpSocket::bind("127.0.0.1:9090")?;
    println!("UDP 服务器监听 127.0.0.1:9090");

    let mut buffer = [0u8; 1024];
    loop {
        // recv_from 返回数据长度和对端地址
        let (len, src) = socket.recv_from(&mut buffer)?;
        println!("收到 {} 字节来自 {}", len, src);

        // send_to 向指定地址发送
        socket.send_to(&buffer[..len], src)?;
    }
}
```

UDP 服务器通常不需要多线程（单个 socket 可以处理所有客户端），但如果处理逻辑耗时较长，可以将数据包投递到线程池处理。C++ 对照：`std::net` 的 API 设计与 Python 的 `socket` 模块更接近，比 C++ 裸 socket 的 `bind`/`listen`/`accept`/`recv`/`send` 序列更简洁，但功能等价。

## 2. Tokio 异步运行时与网络

### 2.1 Tokio 架构与 Reactor 对应

Tokio 是 Rust 生态最主流的异步运行时，其架构本质上是一个 Reactor 模型的实现（可交叉参考《../../01-C++技术体系/03-网络编程/02-IO多路复用与Reactor模型.md》中 C++ Reactor 的详细讨论）。Tokio 的核心组件：

| 组件 | 作用 | Reactor 模型对应 |
|------|------|-----------------|
| 运行时（Runtime） | 事件循环 + 线程池 | Reactor 主循环 + 工作线程池 |
| I/O Driver | 封装 epoll/kqueue/IOCP | 事件分离器（epoll_wait） |
| Timer | 定时器轮 | 定时事件处理器 |
| `tokio::net` | 异步网络 API | 异步事件处理器 |
| `tokio::task` | 任务调度（spawn） | 事件分发到工作线程 |

Tokio 的多线程运行时默认使用 `worker_threads = num_cpus` 个工作线程，每个线程运行一个事件循环。任务（`tokio::spawn` 创建的 future）在工作线程间调度，IO 事件由 I/O Driver 统一监听后分发到对应任务。这与 C++ 中 `one loop per thread + thread pool` 的模式（muduo、boost::asio）完全对应。

```toml
# Cargo.toml
[dependencies]
tokio = { version = "1", features = ["full"] }
```

### 2.2 tokio::net::TcpListener 异步接收

```rust
use tokio::io::{AsyncReadExt, AsyncWriteExt};
use tokio::net::TcpListener;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let listener = TcpListener::bind("127.0.0.1:8080").await?;
    println!("异步回声服务器监听 127.0.0.1:8080");

    loop {
        // accept 是异步的，不阻塞线程
        let (stream, addr) = listener.accept().await?;
        println!("新连接: {}", addr);

        // 每个连接 spawn 一个异步任务（轻量，不是线程）
        tokio::spawn(async move {
            if let Err(e) = handle_client(stream).await {
                eprintln!("连接 {} 错误: {}", addr, e);
            }
        });
    }
}

async fn handle_client(mut stream: tokio::net::TcpStream) -> Result<(), Box<dyn std::error::Error>> {
    let mut buffer = vec![0u8; 1024];
    loop {
        // read 是异步的，无数据时让出线程
        let n = stream.read(&mut buffer).await?;
        if n == 0 {
            break; // 对端关闭
        }
        stream.write_all(&buffer[..n]).await?;
    }
    Ok(())
}
```

关键差异：`tokio::spawn` 创建的是**异步任务**（类似协程），不是线程。一个工作线程可以同时管理数万个异步任务，任务在 `.await` 点自动让出线程。这与 C++ 中 `boost::asio::spawn` 栈ful协程或 C++20 coroutine 的原理相同，但 Tokio 的任务调度器是内置的，无需手动配置 `io_context`。

## 3. bytes::Bytes 零拷贝缓冲

### 3.1 Bytes/BytesMut 与引用计数

`bytes` crate 提供了高效的字节缓冲区类型，核心设计是**引用计数 + 切片共享**，避免数据拷贝。`Bytes` 是不可变字节视图，`BytesMut` 是可变字节缓冲区。以 crates.io 最新稳定版为准。

```toml
# Cargo.toml
[dependencies]
bytes = "1"
```

```rust
use bytes::{Bytes, BytesMut, Buf, BufMut};

fn main() {
    // BytesMut：可变缓冲区，类似 Vec<u8> 但支持零拷贝切片
    let mut buf = BytesMut::with_capacity(1024);
    buf.put_u8(0x01);
    buf.put_u32(42);
    buf.put_slice(b"hello");

    // 从 BytesMut 冻结为 Bytes（不可变，可廉价 clone）
    let bytes: Bytes = buf.freeze();

    // clone 是零拷贝的：只增加引用计数，不复制数据
    let slice1 = bytes.clone();
    let slice2 = bytes.slice(4..8); // 切片也是零拷贝

    println!("slice1 len={}, slice2 len={}", slice1.len(), slice2.len());

    // Bytes 可以像 &[u8] 一样访问
    assert_eq!(&bytes[5..10], b"hello");

    // 从 Vec<u8> 转换（零拷贝，夺取所有权）
    let vec = vec![1u8, 2, 3, 4];
    let from_vec = Bytes::from(vec);

    // 从 &'static [u8] 转换（零拷贝，无引用计数开销）
    let from_static = Bytes::from_static(b"static data");
}
```

`Bytes` 的核心优势：`clone()` 是 `O(1)` 的（只增加原子引用计数），切片 `slice()` 也是 `O(1)` 的（创建指向同一内存的新视图）。这在网络编程中极其重要——从 socket 读取数据后，可以将数据切片分发给多个处理任务，无需拷贝。C++ 中对应的是 `std::shared_ptr<std::vector<uint8_t>>` + 自定义切片，但 `Bytes` 的 API 更简洁，且与 `Buf`/`BufMut` trait 生态集成。

### 3.2 Buf/BufMut trait 与零拷贝操作

`Buf` 和 `BufMut` 是 bytes crate 定义的 trait，抽象了"可读字节流"和"可写字节流"。它们的核心价值是支持**分散/聚集 IO**（scatter/gather）——一个 `Buf` 可以由多个不连续的内存片段组成，读取时自动跨片段拼接，无需先拷贝到连续内存。

```rust
use bytes::{Bytes, BytesMut, Buf, BufMut};

fn demo_buf_traits() {
    // Buf：读取操作
    let mut buf = Bytes::from_static(b"\x00\x00\x00\x2ahello world");
    let len = buf.get_u32(); // 读取 4 字节大端整数，自动前进游标
    assert_eq!(len, 42);
    let remaining = buf.remaining(); // 剩余字节数
    let chunk: &[u8] = buf.chunk();  // 当前连续片段（可能只是一部分）

    // BufMut：写入操作
    let mut writer = BytesMut::with_capacity(64);
    writer.put_u8(1);
    writer.put_u16(8080);
    writer.put_f32(3.14);
    writer.put_slice(b"payload");

    // 链式 Buf：多个片段组合，零拷贝
    let header = Bytes::from_static(b"HEAD");
    let body = Bytes::from(vec![0xAB; 100]);
    let mut chained = header.chain(body);
    let total = chained.remaining(); // 4 + 100 = 104，无需拼接
}
```

`Buf::chain()` 是网络编程中的关键操作——协议头和协议体通常在不同的内存区域，`chain()` 可以将它们组合成一个逻辑上连续的 `Buf`，写入 socket 时由 `writev`（分散写）一次性发出，避免了先拼接再发送的拷贝。C++ 中对应的是 `iovec` 数组 + `writev`，但需要手动管理数组，`Buf` trait 将其抽象化。

## 4. 粘包分包与编解码

### 4.1 长度前缀协议编解码

TCP 是面向流的协议，没有消息边界。应用层必须自己处理粘包（多个消息合并在一个 TCP 段中）和分包（一个消息被拆到多个 TCP 段中）。最常用的方案是**长度前缀**：每个消息前固定长度的字段表示消息体长度。

```rust
use bytes::{Bytes, BytesMut, Buf, BufMut};
use std::io;

/// 长度前缀编解码器：4 字节大端长度 + 消息体
pub struct LengthDelimitedCodec;

impl LengthDelimitedCodec {
    /// 从缓冲区中解码一个消息
    /// 返回 Ok(Some(msg)) 表示成功解码一个消息
    /// 返回 Ok(None) 表示缓冲区数据不足，需要等待更多数据
    pub fn decode(buf: &mut BytesMut) -> io::Result<Option<Bytes>> {
        if buf.len() < 4 {
            return Ok(None); // 连长度字段都不完整
        }

        // 读取长度（不消耗缓冲区，先检查）
        let length = u32::from_be_bytes([buf[0], buf[1], buf[2], buf[3]]) as usize;

        if buf.len() < 4 + length {
            // 消息体不完整，预留空间并等待更多数据
            buf.reserve(4 + length - buf.len());
            return Ok(None);
        }

        // 消耗长度字段
        buf.advance(4);
        // 分割出消息体（零拷贝，从 buf 中分离）
        let message = buf.split_to(length).freeze();
        Ok(Some(message))
    }

    /// 编码一个消息到缓冲区
    pub fn encode(message: &[u8], buf: &mut BytesMut) {
        buf.reserve(4 + message.len());
        buf.put_u32(message.len() as u32);
        buf.put_slice(message);
    }
}
```

使用模式：从 socket 读取数据追加到 `BytesMut`，然后循环调用 `decode` 直到返回 `None`。这与 C++ 中"读缓冲区 + 循环解析"的模式完全一致，但 `BytesMut::split_to()` 的零拷贝特性避免了消息体的内存拷贝。

### 4.2 分隔符协议与 framed codec

对于基于分隔符的协议（如行协议 `\n`、HTTP header 的 `\r\n\r\n`），可以使用 `tokio_util::codec` 框架提供的 `Framed` 适配器，它将 `AsyncRead + AsyncWrite` 自动转换为 `Stream + Sink`，内部处理缓冲区管理和编解码调用。

```toml
# Cargo.toml
[dependencies]
tokio-util = { version = "0.7", features = ["codec"] }
futures = "0.3"
```

```rust
use tokio_util::codec::{Decoder, Encoder, LinesCodec};
use tokio::net::TcpStream;
use futures::{SinkExt, StreamExt};
use bytes::BytesMut;

/// 自定义行编解码器：以 \n 分隔，自动去除 \r
pub struct LineCodec;

impl Decoder for LineCodec {
    type Item = String;
    type Error = std::io::Error;

    fn decode(&mut self, src: &mut BytesMut) -> Result<Option<Self::Item>, Self::Error> {
        // 查找换行符
        if let Some(pos) = src.windows(1).position(|w| w == b"\n") {
            let mut line = src.split_to(pos + 1);
            line.truncate(pos); // 去掉 \n
            // 去掉可能的 \r
            if line.last() == Some(&b'\r') {
                line.truncate(line.len() - 1);
            }
            Ok(Some(String::from_utf8_lossy(&line).to_string()))
        } else {
            Ok(None) // 没有完整行
        }
    }
}

impl Encoder<String> for LineCodec {
    type Error = std::io::Error;

    fn encode(&mut self, item: String, dst: &mut BytesMut) -> Result<(), Self::Error> {
        dst.extend_from_slice(item.as_bytes());
        dst.extend_from_slice(b"\n");
        Ok(())
    }
}

// 使用 Framed 自动管理读写
async fn echo_with_framed(stream: TcpStream) -> Result<(), Box<dyn std::error::Error>> {
    let mut framed = tokio_util::codec::Framed::new(stream, LineCodec);

    while let Some(result) = framed.next().await {
        match result {
            Ok(line) => {
                println!("收到: {}", line);
                framed.send(line).await?; // 回显
            }
            Err(e) => {
                eprintln!("解码错误: {}", e);
                break;
            }
        }
    }
    Ok(())
}
```

`Framed` 内部维护一个读缓冲区和一个写缓冲区，自动处理：从 socket 读取数据 → 调用 `Decoder::decode` → 输出 `Stream` 消息；从 `Sink` 接收消息 → 调用 `Encoder::encode` → 写入 socket。开发者只需实现 `Decoder`/`Encoder` trait，无需手动管理缓冲区。C++ 中对应的是 `boost::asio::read_until` + 手动缓冲区管理，或自研的 codec 框架，Rust 的 `tokio-util` 提供了标准化的抽象。

## 5. 回声服务器完整实现

### 5.1 异步回声服务器架构

整合以上所有组件，实现一个支持长度前缀协议、零拷贝缓冲、优雅关闭的生产级回声服务器：

```toml
# Cargo.toml
[package]
name = "echo-server"
version = "0.1.0"
edition = "2021"

[dependencies]
tokio = { version = "1", features = ["full"] }
bytes = "1"
tokio-util = { version = "0.7", features = ["codec"] }
futures = "0.3"
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }
```

```rust
// src/main.rs
use bytes::{Bytes, BytesMut, Buf, BufMut};
use futures::{SinkExt, StreamExt};
use std::sync::Arc;
use std::time::Duration;
use tokio::io::{AsyncReadExt, AsyncWriteExt};
use tokio::net::{TcpListener, TcpStream};
use tokio::sync::{broadcast, Semaphore};
use tokio_util::codec::{Decoder, Encoder, Framed};

/// 长度前缀编解码器
struct LengthCodec;

impl Decoder for LengthCodec {
    type Item = Bytes;
    type Error = std::io::Error;

    fn decode(&mut self, src: &mut BytesMut) -> Result<Option<Self::Item>, Self::Error> {
        if src.len() < 4 {
            return Ok(None);
        }
        let len = u32::from_be_bytes([src[0], src[1], src[2], src[3]]) as usize;
        if src.len() < 4 + len {
            src.reserve(4 + len - src.len());
            return Ok(None);
        }
        src.advance(4);
        Ok(Some(src.split_to(len).freeze()))
    }
}

impl Encoder<Bytes> for LengthCodec {
    type Error = std::io::Error;

    fn encode(&mut self, item: Bytes, dst: &mut BytesMut) -> Result<(), Self::Error> {
        dst.reserve(4 + item.len());
        dst.put_u32(item.len() as u32);
        dst.put_slice(&item);
        Ok(())
    }
}

/// 连接配置
struct ServerConfig {
    max_connections: usize,
    read_timeout: Duration,
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    tracing_subscriber::fmt::init();

    let config = Arc::new(ServerConfig {
        max_connections: 10000,
        read_timeout: Duration::from_secs(30),
    });

    let listener = TcpListener::bind("0.0.0.0:8080").await?;
    tracing::info!("回声服务器启动: 0.0.0.0:8080");

    // 信号量限制最大并发连接数
    let semaphore = Arc::new(Semaphore::new(config.max_connections));

    // 广播通道用于优雅关闭通知
    let (shutdown_tx, _) = broadcast::channel::<()>(1);

    // Ctrl+C 信号处理
    let shutdown_tx_clone = shutdown_tx.clone();
    tokio::spawn(async move {
        tokio::signal::ctrl_c().await.expect("监听 Ctrl+C 失败");
        tracing::info!("收到关闭信号");
        let _ = shutdown_tx_clone.send(());
    });

    let mut shutdown_rx = shutdown_tx.subscribe();

    loop {
        tokio::select! {
            result = listener.accept() => {
                match result {
                    Ok((stream, addr)) => {
                        let permit = semaphore.clone().acquire_owned().await?;
                        let config = config.clone();
                        let mut conn_shutdown = shutdown_tx.subscribe();

                        tokio::spawn(async move {
                            tracing::info!(%addr, "新连接");
                            handle_connection(stream, config, &mut conn_shutdown).await;
                            drop(permit); // 释放连接名额
                            tracing::info!(%addr, "连接关闭");
                        });
                    }
                    Err(e) => tracing::error!(%e, "接受连接失败"),
                }
            }
            _ = shutdown_rx.recv() => {
                tracing::info!("停止接受新连接");
                break;
            }
        }
    }

    // 等待已有连接完成（简化版，实际应跟踪所有连接句柄）
    tokio::time::sleep(Duration::from_secs(3)).await;
    tracing::info!("服务器已关闭");
    Ok(())
}

async fn handle_connection(
    stream: TcpStream,
    config: Arc<ServerConfig>,
    shutdown: &mut broadcast::Receiver<()>,
) {
    let mut framed = Framed::new(stream, LengthCodec);

    loop {
        tokio::select! {
            msg = framed.next() => {
                match msg {
                    Some(Ok(data)) => {
                        tracing::debug!(len = data.len(), "收到消息");
                        // 回显：Bytes 的 clone 是零拷贝的
                        if framed.send(data.clone()).await.is_err() {
                            break;
                        }
                    }
                    Some(Err(e)) => {
                        tracing::error!(%e, "编解码错误");
                        break;
                    }
                    None => break, // 连接关闭
                }
            }
            _ = shutdown.recv() => {
                tracing::info!("收到关闭通知，断开连接");
                break;
            }
        }
    }
}
```

### 5.2 优雅关闭与连接管理

上述实现中的优雅关闭机制：

1. **广播通道**：`broadcast::channel` 向所有连接发送关闭通知，每个连接的 `select!` 中监听该通道。
2. **信号量**：`Semaphore` 限制最大并发连接数，`acquire_owned()` 返回的 `OwnedSemaphorePermit` 在连接结束时自动释放。
3. **`tokio::select!`**：同时监听"新消息"和"关闭信号"，任一就绪即处理。这是异步 Rust 中管理多个事件源的核心模式，等价于 C++ Reactor 中同时注册多个事件处理器。

C++ 对照：C++ 中实现同样的功能需要 `epoll` 监听 `listenfd` 和 `signalfd`，用 `std::shared_ptr` 管理连接生命周期，用 `std::atomic<bool>` 标志位通知关闭。Rust 的 `tokio::select!` + `broadcast` + `Semaphore` 将这些机制标准化，代码量远少于 C++ 手写实现（可参考《../../01-C++技术体系/03-网络编程/02-IO多路复用与Reactor模型.md》中 C++ Reactor 的代码量对比）。

## 6. 与 C++ Reactor 模型对照

Rust Tokio 与 C++ Reactor 模型（muduo、boost::asio、libevent）的核心对应关系：

| Reactor 概念 | C++ 实现 | Rust Tokio 实现 |
|-------------|----------|-----------------|
| 事件分离器 | `epoll_wait` / `kqueue` | `tokio::runtime::Runtime` 内部 I/O Driver |
| 事件循环 | `while(true) { epoll_wait; dispatch; }` | `#[tokio::main]` 启动的运行时循环 |
| 事件处理器 | `Channel::handleRead()` | `async fn` 中的 `.await` 点 |
| 事件注册 | `epoll_ctl(EPOLL_CTL_ADD)` | `TcpListener::bind()` 后自动注册 |
| 工作线程池 | `EventLoopThreadPool` | `Runtime::new().worker_threads(N)` |
| 任务分发 | `runInLoop()` / `queueInLoop()` | `tokio::spawn()` |
| 定时器 | `TimerQueue` + 时间轮 | `tokio::time::sleep()` / `interval()` |
| 异步 IO | `boost::asio::async_read()` | `AsyncReadExt::read()` |
| 连接管理 | `TcpConnection` 生命周期管理 | `tokio::spawn` 任务 + `select!` 监听关闭 |
| 缓冲区 | `Buffer` (readIndex/writeIndex) | `BytesMut` ( Bytes 的游标管理) |
| 编解码 | `Codec` 自定义 | `tokio_util::codec::Decoder/Encoder` |

核心差异：C++ Reactor 是**基于回调**的——注册事件时传入回调函数，事件触发时调用回调。Rust async 是**基于协程**的——用同步风格写异步代码，`.await` 点自动挂起和恢复。回调模式的问题是"回调地狱"（嵌套层级深、错误处理分散），协程模式的代码结构与同步代码一致，可读性更好。C++20 引入了 coroutine，但生态成熟度远不如 Tokio。

## 7. 常见坑与本节小结

### 常见坑

1. **在 async 函数中调用阻塞 IO**：`std::fs::File::read`、`std::thread::sleep` 等阻塞调用会阻塞整个工作线程，导致其他任务无法调度。必须使用 `tokio::fs`、`tokio::time::sleep` 等异步版本，或用 `tokio::task::spawn_blocking` 包裹阻塞操作。
2. **`BytesMut` 缓冲区无限增长**：如果对端发送恶意数据（长度字段声明极大但不发送数据），`decode` 中的 `reserve()` 会分配大量内存。必须设置最大消息长度限制，超过则断开连接。
3. **忘记处理 `write_all` 的返回值**：异步写可能因对端关闭而失败，忽略错误会导致"写成功"的假象。必须检查 `write_all().await` 的 `Result`。
4. **`Framed` 的 `next()` 返回 `None` 后继续使用**：`Stream` 结束后 `Framed` 内部的 stream 已关闭，继续 `send` 会失败。应在 `None` 时 break 退出循环。
5. **`tokio::select!` 中分支有先后顺序**：`select!` 随机选择就绪的分支（公平调度），不是按书写顺序。如果需要优先级，使用 `tokio::select!` 的 `biased;` 模式。
6. **`std::net` 与 `tokio::net` 混用**：`std::net::TcpStream` 是阻塞的，不能在 async 上下文中直接使用。需要用 `tokio::net::TcpStream::from_std()` 转换，或直接用 `tokio::net` 的 API。
7. **`Bytes::clone()` 不是深拷贝但持有内存**：`clone()` 只增加引用计数，但只要有一个 `Bytes` 视图存活，整个原始内存就不会释放。长时间持有大 `Bytes` 的小切片会导致内存无法回收（类似 C++ `shared_ptr` 的别名构造问题）。需要时用 `copy_to_bytes` 做深拷贝分离。

### 本节小结

Rust 网络编程的技术栈以 Tokio 为核心，形成了完整的异步 IO 生态。`std::net` 提供同步 API（与 C++ 裸 socket 等价），Tokio 的 `tokio::net` 提供异步版本，其架构是 Reactor 模型的 Rust 实现（可交叉参考《../../01-C++技术体系/03-网络编程/02-IO多路复用与Reactor模型.md》）。`bytes::Bytes`/`BytesMut` 通过引用计数实现零拷贝缓冲，`clone()` 和 `slice()` 都是 `O(1)`，是高性能网络编程的基础。粘包分包通过长度前缀或分隔符编解码处理，`tokio_util::codec::Framed` 将 `AsyncRead+AsyncWrite` 自动转换为 `Stream+Sink`，标准化了缓冲区管理和编解码调用。完整的回声服务器整合了 `Framed`、`select!`、`broadcast`、`Semaphore` 等组件，实现了连接管理、限流、优雅关闭。与 C++ Reactor 模型相比，Rust 的 async/await 协程模式避免了回调地狱，代码可读性和可维护性显著优于 C++ 回调模式，且零拷贝缓冲和标准化 codec 框架减少了样板代码。
