## 1. 裸机引导与目标三元组

### 1.1 no_std + no_main 内核环境

编写操作系统内核是 Rust `no_std` 应用的终极场景。内核环境没有操作系统，没有 libc，没有堆分配器（至少初始阶段没有），需要自己处理一切：引导、内存管理、中断、设备驱动。

一个最小的 x86_64 内核入口：

```rust
// src/main.rs
#![no_std]
#![no_main]

use core::panic::PanicInfo;

/// 内核入口：被引导加载器（如 bootloader、GRUB、Limine）调用
/// 名称和调用约定由引导协议决定
#[no_mangle]
pub extern "C" fn _start() -> ! {
    // 内核初始化：清 BSS、设置栈、初始化硬件
    // ...

    // 内核主循环
    loop {
        // HLT 指令：停止 CPU 直到下一个中断，节省电力
        unsafe { core::arch::asm!("hlt") };
    }
}

#[panic_handler]
fn panic(_info: &PanicInfo) -> ! {
    // 内核 panic：通常输出错误信息到 VGA 或串口，然后死循环
    loop {
        unsafe { core::arch::asm!("hlt") };
    }
}
```

与嵌入式 `no_std` 的区别：
- 目标平台不同：嵌入式通常是 `thumbv7em-none-eabihf`（Cortex-M），内核是 `x86_64-unknown-none` 或自定义目标
- 引导方式不同：嵌入式由复位向量直接进入，x86 内核需要引导加载器（GRUB、Limine、bootloader crate）处理实模式到长模式的切换
- 内存管理不同：嵌入式通常物理地址直接映射，x86 内核需要设置分页（paging）
- 中断模型不同：Cortex-M 用 NVIC，x86 用 IDT（中断描述符表）+ APIC

### 1.2 自定义目标与编译配置

x86_64 裸机目标需要自定义 target specification JSON，因为 `x86_64-unknown-none` 不包含内核特定的配置（如重定位模型、栈保护）：

```json
// x86_64-os.json
{
  "llvm-target": "x86_64-unknown-none",
  "data-layout": "e-m:e-p270:32:32-p271:32:32-p272:64:64-i64:64-i128:128-f80:128-n8:16:32:64-S128",
  "arch": "x86_64",
  "target-endian": "little",
  "target-pointer-width": "64",
  "target-c-int-width": "32",
  "os": "none",
  "executables": true,
  "linker-flavor": "ld.lld",
  "linker": "rust-lld",
  "panic-strategy": "abort",
  "disable-redzone": true,
  "features": "-mmx,-sse,-sse2,+soft-float",
  "code-model": "kernel",
  "relocation-model": "static"
}
```

关键配置说明：
- `disable-redzone: true`：禁用红区（red zone），中断处理时不会破坏栈上的临时数据
- `features: "-mmx,-sse,-sse2,+soft-float"`：禁用 SIMD 指令（内核中保存/恢复 SIMD 寄存器开销大），使用软浮点
- `code-model: "kernel"`：内核代码模型，符号地址在 2GB 范围内，使用更高效的寻址
- `relocation-model: "static"`：静态重定位，不依赖动态链接器

```toml
# .cargo/config.toml
[build]
target = "x86_64-os.json"

[unstable]
build-std = ["core", "alloc", "compiler_builtins"]
build-std-features = ["compiler-builtins-mem"]
```

`build-std` 是 nightly 功能，用于为自定义目标编译 `core` 和 `alloc`。因为自定义目标没有预编译的标准库，必须从源码编译。

C 对照：C 内核开发（如 Linux 内核）使用特殊的编译标志（`-ffreestanding`、`-mno-red-zone`、`-mcmodel=kernel`、`-mgeneral-regs-only`）和自定义链接脚本。Rust 的 target JSON 将这些配置标准化，且 `build-std` 自动编译 `core`，无需像 C 那样手动维护 freestanding 头文件。

## 2. 最小内核实现

### 2.1 VGA 文本模式输出

x86_64 内核最基础的输出是 VGA 文本模式——内存映射的文本缓冲区位于物理地址 `0xb8000`，每个字符占 2 字节（1 字节 ASCII + 1 字节颜色属性），80 列 × 25 行。

```rust
use core::fmt;
use volatile::Volatile;
use lazy_static::lazy_static;
use spin::Mutex;

/// VGA 颜色
#[allow(dead_code)]
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[repr(u8)]
pub enum Color {
    Black = 0, Blue = 1, Green = 2, Cyan = 3,
    Red = 4, Magenta = 5, Brown = 6, LightGray = 7,
    DarkGray = 8, LightBlue = 9, LightGreen = 10, LightCyan = 11,
    LightRed = 12, Pink = 13, Yellow = 14, White = 15,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[repr(transparent)]
struct ColorCode(u8);

impl ColorCode {
    fn new(foreground: Color, background: Color) -> ColorCode {
        ColorCode((background as u8) << 4 | (foreground as u8))
    }
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[repr(C)]
struct ScreenChar {
    ascii_character: u8,
    color_code: ColorCode,
}

const BUFFER_HEIGHT: usize = 25;
const BUFFER_WIDTH: usize = 80;

#[repr(transparent)]
struct Buffer {
    chars: [[Volatile<ScreenChar>; BUFFER_WIDTH]; BUFFER_HEIGHT],
}

pub struct Writer {
    column_position: usize,
    color_code: ColorCode,
    buffer: &'static mut Buffer,
}

impl Writer {
    pub fn write_byte(&mut self, byte: u8) {
        match byte {
            b'\n' => self.new_line(),
            byte => {
                if self.column_position >= BUFFER_WIDTH {
                    self.new_line();
                }
                let row = BUFFER_HEIGHT - 1;
                let col = self.column_position;
                let color_code = self.color_code;
                self.buffer.chars[row][col].write(ScreenChar {
                    ascii_character: byte,
                    color_code,
                });
                self.column_position += 1;
            }
        }
    }

    fn new_line(&mut self) {
        // 所有行上移一行，第一行被丢弃
        for row in 1..BUFFER_HEIGHT {
            for col in 0..BUFFER_WIDTH {
                let character = self.buffer.chars[row][col].read();
                self.buffer.chars[row - 1][col].write(character);
            }
        }
        self.clear_row(BUFFER_HEIGHT - 1);
        self.column_position = 0;
    }

    fn clear_row(&mut self, row: usize) {
        let blank = ScreenChar {
            ascii_character: b' ',
            color_code: self.color_code,
        };
        for col in 0..BUFFER_WIDTH {
            self.buffer.chars[row][col].write(blank);
        }
    }
}

impl fmt::Write for Writer {
    fn write_str(&mut self, s: &str) -> fmt::Result {
        for byte in s.bytes() {
            self.write_byte(byte);
        }
        Ok(())
    }
}

lazy_static! {
    pub static ref WRITER: Mutex<Writer> = Mutex::new(Writer {
        column_position: 0,
        color_code: ColorCode::new(Color::Yellow, Color::Black),
        buffer: unsafe { &mut *(0xb8000 as *mut Buffer) },
    });
}

// 提供 println! 宏
#[macro_export]
macro_rules! print {
    ($($arg:tt)*) => ($crate::vga_buffer::_print(format_args!($($arg)*)));
}

#[macro_export]
macro_rules! println {
    () => ($crate::print!("\n"));
    ($($arg:tt)*) => ($crate::print!("{}\n", format_args!($($arg)*)));
}

#[doc(hidden)]
pub fn _print(args: fmt::Arguments) {
    use core::fmt::Write;
    WRITER.lock().write_fmt(args).unwrap();
}
```

关键点：
- `Volatile<T>`：VGA 缓冲区是内存映射 IO（MMIO），编译器不能优化掉对它的读写（因为外部硬件可能异步修改）。`volatile`  crate 提供了 `Volatile` 类型，`read()`/`write()` 方法生成 volatile 加载/存储指令。
- `lazy_static` + `spin::Mutex`：静态变量需要延迟初始化（因为 `0xb8000 as *mut Buffer` 不是 const fn），且需要互斥保护（多核或中断中可能并发访问）。`spin::Mutex` 是自旋锁，不需要操作系统支持。
- `#[repr(C)]`：确保 `ScreenChar` 的内存布局与 C 一致（ASCII 字节在前，颜色字节在后），与 VGA 硬件期望的布局匹配。

C 对照：C 内核中 VGA 输出通常是直接操作 `(uint16_t*)0xb8000` 指针，容易出现编译器优化掉写入（需要 `volatile` 关键字）、并发竞争（需要关中断或锁）等问题。Rust 的 `Volatile` 类型、`spin::Mutex`、`lazy_static` 将这些关注点模块化，类型系统确保了 MMIO 访问的正确性。

### 2.2 中断与异常处理

x86_64 的中断通过 IDT（Interrupt Descriptor Table）管理。异常（如页错误、除零）和硬件中断（如定时器、键盘）都通过 IDT 分发到处理函数。`x86_64` crate 提供了 IDT 的类型安全抽象：

```toml
# Cargo.toml
[dependencies]
x86_64 = "0.15"
pic8259 = "0.11"  # 8259 可编程中断控制器
```

```rust
use x86_64::structures::idt::{InterruptDescriptorTable, InterruptStackFrame};
use lazy_static::lazy_static;
use pic8259::ChainedPics;
use spin;

/// 8259 PIC 中断向量偏移（32 以上，避免与 CPU 异常冲突）
pub const PIC_1_OFFSET: u8 = 32;
pub const PIC_2_OFFSET: u8 = 32 + 8;

pub static PICS: spin::Mutex<ChainedPics> =
    spin::Mutex::new(unsafe { ChainedPics::new(PIC_1_OFFSET, PIC_2_OFFSET) });

#[derive(Debug, Clone, Copy)]
#[repr(u8)]
pub enum InterruptIndex {
    Timer = PIC_1_OFFSET,
    Keyboard,
}

lazy_static! {
    static ref IDT: InterruptDescriptorTable = {
        let mut idt = InterruptDescriptorTable::new();
        // CPU 异常处理
        idt.breakpoint.set_handler_fn(breakpoint_handler);
        idt.double_fault.set_handler_fn(double_fault_handler);
        // 硬件中断处理
        idt[InterruptIndex::Timer as usize].set_handler_fn(timer_interrupt_handler);
        idt[InterruptIndex::Keyboard as usize].set_handler_fn(keyboard_interrupt_handler);
        idt
    };
}

pub fn init_idt() {
    IDT.load();
}

extern "x86-interrupt" fn breakpoint_handler(stack_frame: InterruptStackFrame) {
    println!("EXCEPTION: BREAKPOINT\n{:#?}", stack_frame);
}

extern "x86-interrupt" fn double_fault_handler(
    stack_frame: InterruptStackFrame,
    _error_code: u64,
) -> ! {
    panic!("EXCEPTION: DOUBLE FAULT\n{:#?}", stack_frame);
}

extern "x86-interrupt" fn timer_interrupt_handler(_stack_frame: InterruptStackFrame) {
    // 定时器中断：可以做任务调度、时间计数
    unsafe {
        PICS.lock()
            .notify_end_of_interrupt(InterruptIndex::Timer as u8);
    }
}

extern "x86-interrupt" fn keyboard_interrupt_handler(_stack_frame: InterruptStackFrame) {
    use x86_64::instructions::port::Port;
    let mut port = Port::new(0x60);
    let scancode: u8 = unsafe { port.read() };
    println!("键盘扫描码: {:#x}", scancode);
    unsafe {
        PICS.lock()
            .notify_end_of_interrupt(InterruptIndex::Keyboard as u8);
    }
}
```

`extern "x86-interrupt"` 调用约定确保中断处理函数使用正确的寄存器保存/恢复规则（与普通函数不同，中断处理时 CPU 自动压入错误码和栈帧）。`x86_64` crate 的 `InterruptDescriptorTable` 类型安全地管理 IDT 条目，避免了 C 中手动构造 IDT 描述符（设置段选择子、权限、偏移地址高低位）的易错操作。

### 2.3 分页与内存管理概念

x86_64 使用四级页表（PML4 → PDPT → PD → PT）将虚拟地址映射到物理地址。内核启动时需要建立自己的页表，将内核代码映射到高地址（如 `0xffff_ffff_8000_0000`），并将物理内存映射到虚拟地址空间以便管理。

```rust
use x86_64::{
    structures::paging::{
        PageTable, OffsetPageTable, Page, PhysFrame, Mapper, Size4KiB, FrameAllocator,
    },
    VirtAddr, PhysAddr,
};

/// 简单的帧分配器：从可用物理内存区域分配 4KiB 帧
pub struct BootInfoFrameAllocator {
    memory_map: &'static [MemoryRegion],
    next: usize,
}

impl BootInfoFrameAllocator {
    pub unsafe fn init(memory_map: &'static [MemoryRegion]) -> Self {
        BootInfoFrameAllocator { memory_map, next: 0 }
    }

    fn usable_frames(&self) -> impl Iterator<Item = PhysFrame> {
        let regions = self.memory_map.iter();
        let usable_regions = regions.filter(|r| r.kind == MemoryRegionKind::Usable);
        let addr_ranges = usable_regions.map(|r| r.range.start_addr()..r.range.end_addr());
        let frame_addresses = addr_ranges.flat_map(|r| r.step_by(4096));
        frame_addresses.map(|addr| PhysFrame::containing_address(PhysAddr::new(addr)))
    }
}

unsafe impl FrameAllocator<Size4KiB> for BootInfoFrameAllocator {
    fn allocate_frame(&mut self) -> Option<PhysFrame> {
        let frame = self.usable_frames().nth(self.next);
        self.next += 1;
        frame
    }
}

/// 初始化页表：将物理内存偏移映射到虚拟地址
pub fn init(physical_memory_offset: VirtAddr) -> OffsetPageTable<'static> {
    let level_4_table = active_level_4_table(physical_memory_offset);
    unsafe { OffsetPageTable::new(level_4_table, physical_memory_offset) }
}

fn active_level_4_table(physical_memory_offset: VirtAddr) -> &'static mut PageTable {
    use x86_64::registers::control::Cr3;
    let (level_4_table_frame, _) = Cr3::read();
    let phys = level_4_table_frame.start_address();
    let virt = physical_memory_offset + phys.as_u64();
    let page_table_ptr: *mut PageTable = virt.as_mut_ptr();
    unsafe { &mut *page_table_ptr }
}
```

分页是操作系统最核心的机制之一，完整实现（包括堆分配器、slab 分配器、写时复制、内存映射文件）需要数千行代码。上述示例展示了最基础的帧分配和页表访问，`x86_64` crate 提供了类型安全的页表操作，避免了 C 中手动操作页表条目的位域（present、read/write、user/supervisor、physical address 等）的易错性。

C 对照：Linux 内核的内存管理（`mm/` 目录）是最复杂的子系统之一，包含伙伴系统、slab/slub 分配器、反向映射、透明巨页等。Rust 编写内核在内存安全上有优势（页表操作的类型安全、分配器的边界检查），但目前 Rust for Linux 的内存管理子系统仍在使用 C 实现，Rust 只能通过封装调用。

## 3. 驱动开发

### 3.1 MMIO 与类型安全访问

驱动开发的核心是与硬件通信，主要方式有两种：MMIO（内存映射 IO，通过读写特定内存地址与设备交互）和 Port IO（通过 `in`/`out` 指令访问 IO 端口）。Rust 通过 `volatile`  crate 和 `x86_64` 的 `Port` 类型提供类型安全的访问。Linux 驱动开发的基础概念可参考《../../01-C++技术体系/09-嵌入式开发/05-嵌入式Linux系统与驱动开发.md》，Rust 在底层驱动中提供了更安全的类型抽象。

```rust
use volatile::Volatile;
use core::marker::PhantomData;

/// MMIO 寄存器块：代表一个设备的寄存器集合
#[repr(C)]
pub struct UartRegs {
    pub data: Volatile<u32>,        // 数据寄存器（偏移 0x00）
    pub interrupt_enable: Volatile<u32>, // 中断使能（偏移 0x04）
    pub fifo_control: Volatile<u32>,    // FIFO 控制（偏移 0x08）
    pub line_control: Volatile<u32>,    // 行控制（偏移 0x0C）
    pub modem_control: Volatile<u32>,   // Modem 控制（偏移 0x10）
    pub line_status: Volatile<u32>,     // 行状态（偏移 0x14）
}

/// UART 驱动
pub struct UartDriver {
    regs: *mut UartRegs,
    _marker: PhantomData<&'static mut UartRegs>,
}

impl UartDriver {
    /// 以 MMIO 基地址创建驱动
    pub unsafe fn new(base: usize) -> Self {
        UartDriver {
            regs: base as *mut UartRegs,
            _marker: PhantomData,
        }
    }

    /// 初始化 UART：设置波特率、数据位、停止位
    pub fn init(&self) {
        let regs = unsafe { &*self.regs };
        // 启用 DLAB（分频寄存器访问）
        regs.line_control.write(0x80);
        // 设置分频锁存器（115200 波特率，假设 18.432 MHz 时钟）
        regs.data.write(1);    // 低字节
        regs.interrupt_enable.write(0); // 高字节
        // 8 数据位、1 停止位、无校验
        regs.line_control.write(0x03);
        // 启用 FIFO
        regs.fifo_control.write(0x01);
    }

    /// 发送一个字节
    pub fn send(&self, byte: u8) {
        let regs = unsafe { &*self.regs };
        // 等待发送 FIFO 为空（line_status 第 5 位）
        while regs.line_status.read() & 0x20 == 0 {}
        regs.data.write(byte as u32);
    }

    /// 接收一个字节（阻塞）
    pub fn receive(&self) -> u8 {
        let regs = unsafe { &*self.regs };
        // 等待数据就绪（line_status 第 0 位）
        while regs.line_status.read() & 0x01 == 0 {}
        regs.data.read() as u8
    }
}
```

`#[repr(C)]` 确保结构体字段按声明顺序排列，与硬件寄存器的偏移一致。`Volatile<u32>` 确保每次读写都生成 volatile 指令，不会被编译器优化掉。`PhantomData` 标记驱动持有对寄存器的可变引用，帮助编译器进行生命周期和线程安全分析。

C 对照：C 驱动中 MMIO 访问通常是 `#define UART_DATA (*(volatile uint32_t*)0x10000000)`，然后直接读写。这种方式缺乏类型安全——寄存器偏移错误、读写宽度错误（用 8 位访问 32 位寄存器）都不会编译报错。Rust 的 `#[repr(C)]` 结构体 + `Volatile<T>` 将寄存器映射类型化，偏移错误会导致访问错误的字段（但至少字段名有意义），宽度错误会编译失败。

### 3.2 中断驱动的设备驱动

中断驱动的驱动需要：注册中断处理函数、在中断中读取设备数据、通过环形缓冲区或事件机制将数据传递给内核其他部分。Rust 的 `heapless` crate 提供了 `no_std` 环境下的环形缓冲区：

```toml
# Cargo.toml
[dependencies]
heapless = "0.8"
```

```rust
use heapless::spsc::Queue;
use spin::Mutex;
use core::task::{Context, Poll, Waker};

/// 中断安全的 UART 接收驱动
pub struct InterruptDrivenUart {
    regs: *mut UartRegs,
    rx_queue: Mutex<Queue<u8, 256>>,  // 接收环形缓冲区
    waker: Mutex<Option<Waker>>,       // 异步等待者
}

impl InterruptDrivenUart {
    pub const fn new(base: usize) -> Self {
        InterruptDrivenUart {
            regs: base as *mut UartRegs,
            rx_queue: Mutex::new(Queue::new()),
            waker: Mutex::new(None),
        }
    }

    /// 启用接收中断
    pub fn enable_rx_interrupt(&self) {
        let regs = unsafe { &*self.regs };
        regs.interrupt_enable.write(0x01); // 启用接收数据中断
    }

    /// 中断处理函数：在 UART 中断中调用
    pub fn handle_interrupt(&self) {
        let regs = unsafe { &*self.regs };
        // 读取所有可用数据
        while regs.line_status.read() & 0x01 != 0 {
            let byte = regs.data.read() as u8;
            let mut queue = self.rx_queue.lock();
            if queue.enqueue(byte).is_err() {
                // 缓冲区满，丢弃字节（或记录溢出）
                break;
            }
        }
        // 唤醒等待者
        if let Some(waker) = self.waker.lock().take() {
            waker.wake();
        }
    }

    /// 异步读取一个字节
    pub async fn read_byte(&self) -> u8 {
        core::future::poll_fn(|cx| {
            let mut queue = self.rx_queue.lock();
            if let Some(byte) = queue.dequeue() {
                Poll::Ready(byte)
            } else {
                // 注册 waker，中断到来时唤醒
                *self.waker.lock() = Some(cx.waker().clone());
                Poll::Pending
            }
        }).await
    }
}
```

这个驱动实现了异步读取：`read_byte()` 返回一个 future，当缓冲区为空时注册 `Waker` 并返回 `Pending`，中断到来时数据入队并唤醒 future。这是 Rust 异步运行时在 `no_std` 环境中的应用——不需要完整的 Tokio，只需要 `core::task` 的 `Waker` 机制。

C 对照：C 驱动中中断和主循环的通信通常通过全局环形缓冲区 + 等待队列（wait queue），需要手动管理 `wake_up()` 和 `wait_event()`。Rust 的 `Waker` 机制将异步等待标准化，`poll_fn` 抽象了 poll 循环，代码结构更清晰。且 `heapless::spsc::Queue` 是无锁的单生产者单消费者队列，中断和主循环之间不需要锁（上述示例用 `Mutex` 是为了简化，实际可以用 `split()` 分离生产者和消费者）。

## 4. Linux 系统调用对照

### 4.1 libc 与直接系统调用

在用户态 Linux 编程中，Rust 标准库的 `std::os::unix` 模块提供了对 POSIX API 的封装。对于标准库未覆盖的系统调用，可以使用 `libc` crate（C libc 的 Rust 绑定）或直接通过 `syscall` 指令发起系统调用。

```toml
# Cargo.toml
[dependencies]
libc = "0.2"
```

```rust
use std::io;

/// 使用标准库的 Unix 扩展
fn std_lib_example() -> io::Result<()> {
    use std::os::unix::io::AsRawFd;
    use std::fs::File;
    use std::os::unix::fs::OpenOptionsExt;

    let file = std::fs::OpenOptions::new()
        .read(true)
        .custom_flags(libc::O_NONBLOCK) // 自定义 open 标志
        .open("/dev/null")?;

    let fd = file.as_raw_fd();
    println!("文件描述符: {}", fd);
    Ok(())
}

/// 使用 libc crate 直接调用 POSIX API
fn libc_example() {
    unsafe {
        // getpid
        let pid = libc::getpid();
        println!("PID: {}", pid);

        // write 系统调用
        let msg = b"Hello via libc write\n";
        libc::write(libc::STDOUT_FILENO, msg.as_ptr() as *const _, msg.len());

        // mmap 匿名映射
        let addr = libc::mmap(
            std::ptr::null_mut(),
            4096,
            libc::PROT_READ | libc::PROT_WRITE,
            libc::MAP_PRIVATE | libc::MAP_ANONYMOUS,
            -1,
            0,
        );
        if addr == libc::MAP_FAILED {
            eprintln!("mmap 失败");
        } else {
            // 使用映射内存
            *(addr as *mut u8) = 42;
            libc::munmap(addr, 4096);
        }
    }
}
```

`libc` crate 提供了所有 POSIX 类型和函数的 Rust 绑定，调用时需要 `unsafe`（因为这些是外部 C 函数，Rust 无法保证其安全性）。对于常见操作（文件、网络、线程），优先使用 `std` 封装；对于标准库未覆盖的系统调用（如 `mmap`、`epoll`、`signalfd`），使用 `libc` crate。

### 4.2 syscall 与 errno 处理

对于 `libc` 未覆盖的新系统调用（如 `io_uring` 的 `io_uring_setup`），可以直接使用 `syscall` 函数：

```rust
/// 直接发起系统调用
fn direct_syscall_example() {
    unsafe {
        // syscall 号：x86_64 上 getpid = 39
        let pid = libc::syscall(39);
        println!("直接 syscall getpid: {}", pid);

        // 带参数的系统调用：write(1, msg, len)
        let msg = b"Direct syscall write\n";
        let ret = libc::syscall(
            1, // write 系统调用号
            1, // stdout fd
            msg.as_ptr(),
            msg.len(),
        );
        if ret < 0 {
            // 系统调用错误：返回值是 -errno
            let errno = -ret;
            eprintln!("write 失败，errno: {}", errno);
        }
    }
}

/// 安全的系统调用包装：处理 errno
fn syscall_write(fd: i32, data: &[u8]) -> Result<usize, i32> {
    let ret = unsafe {
        libc::syscall(1, fd, data.as_ptr(), data.len())
    };
    if ret < 0 {
        Err(-ret as i32)
    } else {
        Ok(ret as usize)
    }
}
```

系统调用的错误处理约定：返回值为负数时，其绝对值是 errno 号。Rust 的 `std::io::Error` 可以从 errno 构造：`std::io::Error::from_raw_os_error(errno)`。

C 对照：C 中系统调用通过 `syscall()` 函数或直接内联汇编，错误通过 `errno` 全局变量获取（注意线程局部）。Rust 的 `libc::syscall` 返回值直接包含错误码（负数），不需要读取 `errno` 变量，避免了 C 中 `errno` 被后续调用覆盖的问题。且 Rust 的 `Result` 类型强制调用方处理错误，C 中经常忽略系统调用返回值导致难以调试的 bug。

## 5. Rust for Linux 内核模块

### 5.1 项目现状与架构

Rust for Linux 是一个将 Rust 语言引入 Linux 内核的项目，由 Miguel Ojeda 领导，自 2021 年起进入 Linux 内核主线（6.1 版本首次包含 Rust 支持）。其架构设计：

| 层 | 内容 | 语言 |
|----|------|------|
| 内核核心 | 调度、内存管理、文件系统、网络栈 | C（现有，不重写） |
| Rust 绑定层 | `kernel` crate：对内核 C API 的安全封装 | Rust |
| 驱动/模块 | 使用 Rust 编写的内核模块 | Rust |
| 构建系统 | `rustc` 调用、绑定生成、文档 | Makefile/Kbuild 扩展 |

Rust for Linux 的核心原则是**不重写内核**，而是提供 Rust 绑定让新代码可以用 Rust 编写。现有的 C 代码（占内核 99% 以上）保持不变，Rust 模块通过 FFI 调用 C 函数，C 代码也可以调用导出的 Rust 函数。

`kernel` crate 提供的主要抽象：
- `kernel::module`：模块注册宏（替代 `module_init`/`module_exit`）
- `kernel::sync`：`Mutex`、`SpinLock`、`RCU` 等同步原语的安全封装
- `kernel::file`：文件操作（`File`、`Operations`）
- `kernel::miscdev`：杂项设备注册
- `kernel::io_mem`：MMIO 映射的安全封装
- `kernel::irq`：中断处理注册
- `kernel::error`：内核错误码（`Error` 类型，封装 `errno`）

### 5.2 内核模块示例与边界

一个最小的 Rust 内核模块（字符设备）：

```rust
// 注意：这是 Rust for Linux 内核模块，不是用户态程序
// 需要在内核源码树中编译，使用特殊的 rustc 配置

use kernel::prelude::*;
use kernel::{
    file::{self, File, Operations},
    io_buffer::IoBufferReader,
    miscdev,
    sync::{Mutex, Ref},
};

module! {
    type: RustCharDevice,
    name: "rust_char_device",
    author: "Rust for Linux",
    description: "A simple character device in Rust",
    license: "GPL",
}

struct RustCharDevice {
    _dev: Pin<Box<miscdev::Registration<Self>>>,
    message: Mutex<Vec<u8>>,
}

impl kernel::Module for RustCharDevice {
    fn init(_module: &'static ThisModule) -> Result<Self> {
        // 注册杂项设备
        let dev = miscdev::Registration::new_pinned(fmt!("rust_dev"), ())?;
        Ok(RustCharDevice {
            _dev: dev,
            message: Mutex::new(Vec::new()),
        })
    }
}

#[vtable]
impl Operations for RustCharDevice {
    type OpenData = ();
    type Data = Ref<RustCharDevice>;

    fn open(_context: &(), _file: &File) -> Result<Self::Data> {
        // 获取模块状态（简化）
        Err(ENOSYS) // 实际应返回 Ref
    }

    fn read(
        _data: <Self::Data as Pointer>::Target,
        _file: &File,
        _writer: &mut impl IoBufferWriter,
        _offset: u64,
    ) -> Result<usize> {
        Err(ENOSYS)
    }

    fn write(
        _data: <Self::Data as Pointer>::Target,
        _file: &File,
        _reader: &mut impl IoBufferReader,
        _offset: u64,
    ) -> Result<usize> {
        Err(ENOSYS)
    }
}
```

**当前边界与限制**：

1. **仅支持特定架构**：目前 Rust for Linux 主要支持 x86_64 和 arm64，其他架构支持有限。
2. **`alloc` 依赖**：Rust 内核模块使用 `alloc`（需要内核的 `kmalloc` 作为全局分配器），不支持完全 `no_core`。
3. **绑定覆盖不全**：`kernel` crate 只覆盖了部分内核子系统（字符设备、网络、部分文件系统），很多子系统（如块设备、USB、GPU）尚无 Rust 绑定。
4. **不稳定 API**：`kernel` crate 的 API 仍在快速演变，没有稳定版本承诺。
5. **编译工具链**：需要特定版本的 `rustc`（通常是较新的 nightly），与发行版自带的 Rust 版本可能不兼容。
6. **性能开销**：Rust 绑定层有少量抽象开销（主要在错误转换和类型包装），对性能极端敏感的路径（如网络栈快速路径）仍用 C。

C 对照：Linux 内核模块开发长期以来只能用 C（和汇编），Rust for Linux 是第一个被内核社区接受的非 C 语言。C 内核模块的常见问题（空指针、use-after-free、缓冲区溢出、并发错误）在 Rust 中由类型系统和所有权机制在编译期拦截。但目前 Rust for Linux 仍处于早期阶段，生产级驱动（尤其是复杂子系统）仍以 C 为主。

## 6. 用户态高性能：io_uring 绑定

### 6.1 io_uring 原理与 Rust 绑定

io_uring 是 Linux 5.1 引入的异步 IO 接口，通过共享内存的环形缓冲区（submission queue 和 completion queue）在用户态和内核态之间传递 IO 请求，避免了传统 `read`/`write` 系统调用的上下文切换开销。对于高并发 IO（数据库、代理、文件服务器），io_uring 可以显著提升性能。

Rust 生态的 io_uring 绑定主要有两个：
- `io-uring`：低级绑定，直接封装 io_uring 系统调用
- `tokio-uring`：基于 Tokio 运行时的高级异步封装

```toml
# Cargo.toml
[dependencies]
io-uring = "0.6"
```

```rust
use io_uring::{IoUring, opcode, types};
use std::fs::File;
use std::os::unix::io::AsRawFd;

fn io_uring_read_example() -> Result<(), Box<dyn std::error::Error>> {
    // 创建 io_uring 实例：提交队列深度 8
    let mut ring = IoUring::new(8)?;

    let file = File::open("/etc/hostname")?;
    let fd = file.as_raw_fd();

    // 准备读取缓冲区
    let mut buffer = vec![0u8; 1024];
    let buf_ptr = buffer.as_mut_ptr();

    // 构造 readv 操作（io_uring 用 readv 而非 read）
    let read_op = opcode::Read::new(types::Fd(fd), buf_ptr, buffer.len() as u32)
        .build()
        .user_data(0xCAFE); // 用户数据：用于在完成队列中识别请求

    // 提交到提交队列
    unsafe {
        ring.submission().push(&read_op)?;
    }

    // 提交并等待至少 1 个完成
    ring.submit_and_wait(1)?;

    // 从完成队列读取结果
    for cqe in ring.completion() {
        let result = cqe.result();
        let user_data = cqe.user_data();
        if result < 0 {
            eprintln!("IO 失败，errno: {}", -result);
        } else {
            println!("读取 {} 字节，user_data: {:#x}", result, user_data);
            println!("内容: {:?}", &buffer[..result as usize]);
        }
    }

    Ok(())
}
```

`io-uring` crate 的低级 API 直接对应 io_uring 的系统调用接口：`submission()` 获取提交队列，`push()` 添加请求，`submit_and_wait()` 提交并等待，`completion()` 遍历完成队列。`user_data` 字段用于将完成事件与原始请求关联（类似 epoll 的 `data` 字段）。

### 6.2 tokio-uring 异步 IO

`tokio-uring` 将 io_uring 集成到 Tokio 异步运行时，提供了 `async fn` 风格的 API，自动管理提交/完成队列和 `user_data` 关联：

```toml
# Cargo.toml
[dependencies]
tokio-uring = "0.4"
```

```rust
use tokio_uring::fs::File;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // tokio-uring 有自己的运行时入口（基于 io_uring 的 Tokio 运行时）
    tokio_uring::start(async {
        // 打开文件
        let file = File::open("/etc/hostname").await?;

        // 分配缓冲区
        let buffer = vec![0u8; 1024];

        // 异步读取：返回 (结果, 缓冲区)（缓冲区被归还，因为 io_uring 需要稳定的内存）
        let (res, buffer) = file.read_at(buffer, 0).await;
        let n = res?;

        println!("读取 {} 字节: {:?}", n, &buffer[..n]);

        Ok::<(), std::io::Error>(())
    })?;
    Ok(())
}
```

`tokio-uring` 的 `read_at` 返回 `(Result<usize>, Buffer)`——缓冲区被归还是因为 io_uring 在 IO 进行期间需要缓冲区内存保持稳定（不能被移动或释放），所以 API 设计为"借出缓冲区，完成后归还"。这与 Tokio 普通的 `AsyncReadExt::read`（传入 `&mut [u8]`）不同，因为普通 read 的缓冲区在 `.await` 期间可以被移动（Tokio 会在 poll 之间拷贝），而 io_uring 的缓冲区地址在提交后就固定了。

io_uring 支持的操作远不止文件读写：`accept`、`connect`、`send`、`recv`、`openat`、`close`、`fsync`、`splice`、`tee` 等。对于高并发网络服务器，io_uring 可以替代 epoll + 非阻塞 IO 的传统模型，减少系统调用次数和上下文切换。

C 对照：C 中使用 io_uring 需要直接操作 `io_uring_setup`/`io_uring_enter` 系统调用，手动管理 SQ/CQ 环形缓冲区的内存映射和指针，代码量大且易错。`liburing` 库提供了封装，但仍是 C 风格的 API。Rust 的 `io-uring` crate 提供了类型安全的环形缓冲区操作，`tokio-uring` 进一步将其集成到异步运行时，开发者只需写 `async/await` 代码，无需手动管理队列。这是 Rust 在高性能系统编程领域的显著优势。

## 7. 常见坑与本节小结

### 常见坑

1. **`no_std` 内核中使用 `std` 类型**：内核环境没有 `std`，`String`、`Vec`、`HashMap` 等需要 `extern crate alloc` 且提供全局分配器。忘记 `alloc` 会导致编译错误。
2. **MMIO 访问忘记 `volatile`**：对 MMIO 地址的普通读写可能被编译器优化掉（因为编译器认为内存值不会异步改变）。必须使用 `Volatile::read()`/`write()` 或 `read_volatile`/`write_volatile` 内联函数。
3. **中断处理函数中使用非中断安全的操作**：中断中不能进行堆分配、不能获取可能死锁的锁、不能执行耗时操作。中断中应使用固定大小缓冲区、无锁队列、自旋锁（`spin::Mutex`）。
4. **x86_64 内核忘记禁用红区**：红区是栈指针下方 128 字节的区域，中断处理时 CPU 不会自动跳过红区，可能破坏栈上数据。内核必须在 target JSON 中设置 `disable-redzone: true`。
5. **Rust for Linux 模块使用了不稳定的 `kernel` crate API**：`kernel` crate 的 API 仍在演变，升级内核版本后模块可能编译失败。需要锁定内核版本并关注 API 变更。
6. **io_uring 缓冲区在 IO 完成前被移动或释放**：io_uring 提交后缓冲区地址固定，在完成事件到达前不能移动或释放缓冲区。`tokio-uring` 的 API 通过"借出-归还"模式强制这一点，低级 `io-uring` 需要手动保证。
7. **直接系统调用的参数类型错误**：`libc::syscall` 的参数是 `c_long`，传入错误类型（如 `usize` 在 32 位平台上宽度不同）会导致系统调用参数错误。使用 `libc` 提供的类型而非 Rust 原生类型。
8. **内核 panic 没有输出**：`no_std` 环境的 `panic_handler` 默认可能只是死循环，没有输出。需要实现 VGA 或串口输出，在 panic 时打印错误信息和栈回溯（`x86_64` crate 的 `StackFrame`）。

### 本节小结

Rust 在操作系统与底层开发领域展现了从用户态到内核态的完整技术能力。裸机内核开发以 `no_std` + `no_main` 为基础，通过自定义 target JSON 配置内核特定的编译选项（禁用红区、禁用 SIMD、内核代码模型），`build-std` 从源码编译 `core`/`alloc`。最小内核实现涵盖 VGA 文本输出（`Volatile` MMIO 访问）、IDT 中断处理（`x86_64` crate 类型安全抽象）、分页与帧分配（四级页表、物理内存管理）。驱动开发通过 `#[repr(C)]` 寄存器结构体 + `Volatile<T>` 实现类型安全的 MMIO 访问，中断驱动使用 `heapless` 无锁队列和 `Waker` 机制实现异步数据传递。Linux 用户态系统调用通过 `libc` crate 或直接 `syscall` 访问，`Result` 类型强制错误处理。Rust for Linux 项目自 6.1 版本进入内核主线，提供 `kernel` crate 安全封装，但目前绑定覆盖不全、API 不稳定，适用于新驱动开发而非核心子系统重写。用户态高性能 IO 通过 `io-uring`/`tokio-uring` 绑定 io_uring，减少系统调用开销，`tokio-uring` 的异步 API 自动管理环形缓冲区。与 C 系统编程相比，Rust 的类型安全、所有权、`Volatile` 抽象消除了底层开发中最常见的错误类别，同时保留了 C 的性能和底层控制能力。
