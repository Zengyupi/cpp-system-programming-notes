## 1. 共享状态vs通道通信

### 1.1 共享状态范式

共享状态范式通过锁保护共享数据，多个线程/任务读写同一份数据：

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // 共享状态：计数器
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            // 所有线程共享同一个计数器，通过锁保护
            let mut count = counter.lock().unwrap();
            *count += 1;
        }));
    }

    for h in handles {
        h.join().unwrap();
    }

    println!("计数器: {}", *counter.lock().unwrap()); // 10
}
```

共享状态的特点：
- 数据集中存储，所有参与者直接访问
- 需要锁/原子操作保证一致性
- 读写冲突时需要等待
- 适合：数据需要被多方读写、状态复杂、需要强一致性

### 1.2 通道通信范式

通道通信范式通过消息传递交换数据，不共享状态：

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    // 通道：多生产者单消费者
    let (tx, rx) = mpsc::channel();

    // 生产者线程：发送消息
    for i in 0..5 {
        let tx = tx.clone();
        thread::spawn(move || {
            tx.send(i * 2).unwrap();
        });
    }
    drop(tx);

    // 消费者线程：接收并处理消息
    let handle = thread::spawn(move || {
        let mut sum = 0;
        while let Ok(msg) = rx.recv() {
            sum += msg;
        }
        sum
    });

    println!("总和: {}", handle.join().unwrap()); // 0+2+4+6+8 = 20
}
```

异步版本（Tokio mpsc）：

```rust
use tokio::sync::mpsc;

#[tokio::main]
async fn main() {
    let (tx, mut rx) = mpsc::channel(32); // 有界通道，提供背压

    // 生产者任务
    for i in 0..5 {
        let tx = tx.clone();
        tokio::spawn(async move {
            tx.send(i * 2).await.unwrap();
        });
    }
    drop(tx);

    // 消费者任务
    let mut sum = 0;
    while let Some(msg) = rx.recv().await {
        sum += msg;
    }
    println!("总和: {}", sum);
}
```

通道通信的特点：
- 数据通过消息传递，不共享状态
- 发送者和接收者解耦
- 有界通道天然提供背压
- 适合：数据流处理、事件驱动、解耦模块

### 1.3 范式选择与对比

| 维度 | 共享状态 | 通道通信 |
|------|----------|----------|
| 数据访问 | 直接读写共享数据 | 通过消息传递 |
| 同步机制 | 锁/原子操作 | 通道缓冲区 |
| 耦合度 | 高（共享数据结构） | 低（消息格式解耦） |
| 死锁风险 | 高（多锁顺序） | 低（单通道无死锁） |
| 性能 | 高（无拷贝，直接访问） | 中（消息拷贝/移动） |
| 可扩展性 | 差（锁竞争随线程数增长） | 好（通道可分片） |
| 调试难度 | 高（数据竞争难复现） | 中（消息流可追踪） |
| 典型场景 | 缓存、配置、计数器 | 流水线、事件总线、任务队列 |

Rust的设计哲学倾向于"通过通信共享内存，而不是通过共享内存通信"（Go的CSP哲学），但两种范式在Rust中都有完善的支持。实际项目中通常混合使用：配置/缓存用共享状态，数据流用通道。

## 2. CSP与Actor模型

### 2.1 CSP模型

CSP（Communicating Sequential Processes）模型中，并发实体通过通道通信，通道是一等公民：

CSP典型三阶段流水线：进程1生成数据→tx1→进程2处理（rx1收，tx2发）→进程3消费（rx2收）。核心原则：并发实体是顺序进程、进程间通过通道通信、通道有类型有界、不共享状态只传递消息。Rust的`mpsc`通道是CSP的直接实现。

### 2.2 Actor模型

Actor模型中每个Actor是独立并发实体，有私有状态，通过消息邮箱接收消息，串行处理不需要锁：

```rust
use tokio::sync::mpsc;

enum Msg { Inc, Get(tokio::sync::oneshot::Sender<u64>) }

struct Actor { count: u64, rx: mpsc::Receiver<Msg> }

impl Actor {
    async fn run(mut self) {
        while let Some(msg) = self.rx.recv().await {
            match msg {
                Msg::Inc => self.count += 1,
                Msg::Get(tx) => { let _ = tx.send(self.count); }
            }
        }
    }
}

#[derive(Clone)]
struct Handle { tx: mpsc::Sender<Msg> }

impl Handle {
    fn new() -> Self {
        let (tx, rx) = mpsc::channel(32);
        tokio::spawn(Actor { count: 0, rx }.run());
        Handle { tx }
    }
    async fn inc(&self) { self.tx.send(Msg::Inc).await.unwrap(); }
    async fn get(&self) -> u64 {
        let (tx, rx) = tokio::sync::oneshot::channel();
        self.tx.send(Msg::Get(tx)).await.unwrap();
        rx.await.unwrap()
    }
}
```

Actor核心原则：私有状态不对外暴露、异步消息通信、串行处理无需锁、可创建监督子Actor。Rust无原生Actor框架，可用`mpsc`+事件循环实现，社区有`actix`、`riker`等。

## 3. 流水线与背压

### 3.1 流水线模式

流水线将处理过程分为多个阶段，每个阶段由独立的任务/线程处理，阶段间通过通道连接：

```text
数据源 → [阶段1: 解析] → [阶段2: 转换] → [阶段3: 输出] → 汇
           通道1            通道2            通道3
```

```rust
use tokio::sync::mpsc;

#[tokio::main]
async fn main() {
    let (tx_raw, rx_raw) = mpsc::channel(10);
    let (tx_parsed, rx_parsed) = mpsc::channel(10);
    let (tx_output, mut rx_output) = mpsc::channel(10);

    // 阶段1：生成原始数据
    tokio::spawn(async move {
        for i in 0..20 {
            tx_raw.send(format!("raw_{}", i)).await.unwrap();
        }
    });

    // 阶段2：解析
    let tx_parsed_clone = tx_parsed.clone();
    tokio::spawn(async move {
        let mut rx_raw = rx_raw;
        while let Some(raw) = rx_raw.recv().await {
            let parsed = raw.replace("raw_", "parsed_");
            tx_parsed_clone.send(parsed).await.unwrap();
        }
    });

    // 阶段3：转换（大写）
    tokio::spawn(async move {
        let mut rx_parsed = rx_parsed;
        while let Some(parsed) = rx_parsed.recv().await {
            let output = parsed.to_uppercase();
            tx_output.send(output).await.unwrap();
        }
    });

    // 汇：收集结果
    while let Some(result) = rx_output.recv().await {
        println!("{}", result);
    }
}
```

流水线的优势：
- **并行**：不同阶段同时处理不同数据
- **解耦**：阶段间通过通道解耦，可独立修改
- **背压**：有界通道自动限制处理速度

### 3.2 背压机制

背压（backpressure）是当下游处理速度慢于上游时，上游自动减速的机制：

```rust
use tokio::sync::mpsc;

#[tokio::main]
async fn main() {
    // 有界通道：容量为5
    // 当通道满时，send().await会挂起，上游自动减速
    let (tx, mut rx) = mpsc::channel(5);

    // 快速生产者
    let producer = tokio::spawn(async move {
        for i in 0..100 {
            // 通道满时这里会等待，实现背压
            tx.send(i).await.unwrap();
            println!("生产: {}", i);
        }
    });

    // 慢速消费者
    let consumer = tokio::spawn(async move {
        while let Some(msg) = rx.recv().await {
            println!("消费: {}", msg);
            tokio::time::sleep(std::time::Duration::from_millis(50)).await;
        }
    });

    producer.await.unwrap();
    consumer.await.unwrap();
}
```

背压的实现方式：
1. **有界通道**：最常用，通道满时send阻塞
2. **信号量**：`tokio::sync::Semaphore`限制并发数
3. **手动流控**：消费者反馈处理速度，生产者据此调整

无界通道（`mpsc::unbounded_channel`）不提供背压，可能导致内存无限增长，应谨慎使用。

## 4. spawn_blocking桥接同步阻塞

异步运行时中执行阻塞操作会阻塞工作线程，导致其他任务无法执行。`spawn_blocking`将阻塞操作放到专门的阻塞线程池中：

```rust
use tokio::task;

#[tokio::main]
async fn main() {
    // 错误：在异步代码中直接执行阻塞操作
    // let content = std::fs::read_to_string("large_file.txt").unwrap(); // 阻塞！

    // 正确：用spawn_blocking执行阻塞操作
    let content = task::spawn_blocking(|| {
        std::fs::read_to_string("large_file.txt")
    }).await.unwrap(); // 等待阻塞线程完成

    println!("文件大小: {} 字节", content.unwrap().len());

    // CPU密集型计算也用spawn_blocking
    let result = task::spawn_blocking(|| {
        let mut sum = 0u64;
        for i in 0..1_000_000 {
            sum += i;
        }
        sum
    }).await.unwrap();

    println!("计算结果: {}", result);
}
```

`spawn_blocking`的特点：
- 使用独立的阻塞线程池（默认最大512个线程）
- 不占用异步工作线程
- 返回`JoinHandle`，可以await获取结果
- 适合：同步IO（std::fs）、CPU密集计算、调用阻塞的C库

需要用`spawn_blocking`的场景：
- `std::fs`文件操作
- 同步数据库驱动（非异步的）
- CPU密集型计算（加密、压缩、图像处理）
- 调用阻塞的C库（FFI）

不需要`spawn_blocking`的场景：
- Tokio的异步IO（`tokio::fs`、`tokio::net`）
- 异步数据库驱动（`sqlx`、`tokio-postgres`）
- 纯计算且耗时很短（微秒级）

## 5. 结构化并发与任务取消

### 5.1 结构化并发原则

结构化并发要求任务生命周期嵌套在父任务内，父任务结束前所有子任务必须结束。`JoinSet`是核心工具：

```rust
use tokio::task::JoinSet;
let mut set = JoinSet::new();
for i in 0..5 { set.spawn(async move { i * 2 }); }
while let Some(r) = set.join_next().await { println!("{}", r.unwrap()); }
// JoinSet drop时abort所有未完成任务，无"孤儿任务"
```

原则：子任务在父作用域内创建、父任务等待所有子任务完成、父取消时子任务也取消、无孤儿任务。`tokio::spawn`是detached的，需用`JoinSet`实现结构化并发。

### 5.2 任务取消与超时

`timeout(Duration, future)`实现超时，超时后Future被drop取消。`handle.abort()`立即取消任务。取消是协作式的：任务在下次await点被取消，正在执行的同步代码不会中断，被取消任务的drop会执行释放资源。`spawn`的子任务不会随父任务自动取消，需手动abort或用JoinSet。

## 6. 限流与批量合并

### 6.1 限流模式

限流（Rate Limiting）控制请求速率，保护下游服务：

```rust
use tokio::sync::Semaphore;
use std::sync::Arc;

#[tokio::main]
async fn main() {
    // 信号量限流：最多10个并发
    let semaphore = Arc::new(Semaphore::new(10));
    let mut handles = vec![];

    for i in 0..100 {
        let semaphore = Arc::clone(&semaphore);
        handles.push(tokio::spawn(async move {
            // 获取许可，超过并发数时等待
            let _permit = semaphore.acquire().await.unwrap();
            // 执行受限操作
            println!("请求{}执行", i);
            tokio::time::sleep(std::time::Duration::from_millis(10)).await;
            // permit drop时释放许可
        }));
    }

    for h in handles {
        h.await.unwrap();
    }
}
```

令牌桶限流（`governor` crate，以crates.io最新稳定版为准）：

```rust
use governor::{Quota, RateLimiter};
use std::num::NonZeroU32;

#[tokio::main]
async fn main() {
    // 每秒10个请求
    let quota = Quota::per_second(NonZeroU32::new(10).unwrap());
    let limiter = RateLimiter::direct(quota);

    for i in 0..20 {
        limiter.until_ready().await; // 等待直到有令牌
        println!("请求{}执行", i);
    }
}
```

### 6.2 批量合并模式

批量合并将多个小请求合并为一个大请求，减少IO次数。核心实现：

```rust
struct Batcher { rx: mpsc::Receiver<Request>, max_size: usize, max_delay: Duration }

impl Batcher {
    async fn run(mut self) {
        loop {
            let mut batch = vec![];
            match self.rx.recv().await { Some(r) => batch.push(r), None => break }
            let deadline = tokio::time::sleep(self.max_delay);
            tokio::pin!(deadline);
            while batch.len() < self.max_size {
                tokio::select! {
                    r = self.rx.recv() => { match r { Some(v) => batch.push(v), None => break } }
                    _ = &mut deadline => break,
                }
            }
            // 批量处理后逐个回复
            for req in batch { let _ = req.reply.send("ok".into()); }
        }
    }
}
```

关键：用`select!`同时等待新请求和超时，达到批量大小或超时后立即处理。适用于数据库写入、网络请求、日志写入等场景。

## 7. 并发陷阱

### 7.1 阻塞executor

在异步任务中执行阻塞操作会阻塞整个工作线程：

```rust
#[tokio::main]
async fn main() {
    // 危险：阻塞操作占用工作线程
    // tokio::spawn(async {
    //     std::thread::sleep(std::time::Duration::from_secs(10)); // 阻塞！
    // });

    // 正确1：用异步sleep
    tokio::spawn(async {
        tokio::time::sleep(std::time::Duration::from_secs(10)).await;
    });

    // 正确2：用spawn_blocking
    tokio::task::spawn_blocking(|| {
        std::thread::sleep(std::time::Duration::from_secs(10));
    });
}
```

阻塞executor的后果：
- 工作线程被占用，其他任务无法执行
- 如果所有工作线程都被阻塞，整个运行时"冻结"
- 延迟飙升，吞吐量下降

### 7.2 任务饥饿

任务饥饿（Starvation）是指某些任务长期得不到执行：

```rust
#[tokio::main]
async fn main() {
    // 危险：CPU密集型循环不yield
    // tokio::spawn(async {
    //     loop {
    //         // 纯计算，没有await点，其他任务无法执行
    //         compute_heavy();
    //     }
    // });

    // 正确：定期yield
    tokio::spawn(async {
        loop {
            compute_heavy();
            // 让出执行权，让其他任务有机会执行
            tokio::task::yield_now().await;
        }
    });
}

fn compute_heavy() {
    // 模拟计算
    let _ = (0..1000).sum::<u64>();
}
```

Tokio的work-stealing调度器是协作式的：任务只有在await点才会让出线程。CPU密集型循环没有await点，会长期占用线程。

解决方案：
- 用`spawn_blocking`执行CPU密集型任务
- 定期`yield_now().await`
- 将大任务拆分为小任务

### 7.3 死锁与活锁

异步死锁的常见原因：

```rust
use tokio::sync::Mutex;
use std::sync::Arc;

#[tokio::main]
async fn main() {
    // 危险：异步锁的循环等待
    let a = Arc::new(Mutex::new(0));
    let b = Arc::new(Mutex::new(0));

    // 任务1：先锁a，再锁b
    let a1 = Arc::clone(&a);
    let b1 = Arc::clone(&b);
    tokio::spawn(async move {
        let _ga = a1.lock().await;
        tokio::time::sleep(std::time::Duration::from_millis(10)).await;
        let _gb = b1.lock().await; // 可能死锁
    });

    // 任务2：先锁b，再锁a
    let a2 = Arc::clone(&a);
    let b2 = Arc::clone(&b);
    tokio::spawn(async move {
        let _gb = b2.lock().await;
        tokio::time::sleep(std::time::Duration::from_millis(10)).await;
        let _ga = a2.lock().await; // 可能死锁
    };
}
```

死锁预防：
- 固定锁的获取顺序（所有任务都先a后b）
- 尽量使用短临界区
- 用`tokio::sync::try_lock`避免无限等待
- 考虑用通道替代共享状态

活锁（Livelock）：任务不断重试但都无法进展，通常由过度的重试逻辑导致。解决：增加退避（backoff）和随机抖动（jitter）。

### 7.4 优先级反转

优先级反转：低优先级任务持有高优先级任务需要的资源，导致高优先级任务等待。Tokio的调度器没有优先级概念（所有任务平等），但在自定义调度中可能出现。

## 8. 对照C++线程池实战模式

交叉引用：C++线程池与并发实战模式详见《../../01-C++技术体系/04-并发编程/05-线程池与并发实战模式.md》。

| 模式 | Rust实现 | C++实现 |
|------|----------|---------|
| 线程池 | `tokio::spawn`（work-stealing） | 手动实现或`boost::asio::thread_pool` |
| 任务队列/背压 | 有界`mpsc::channel` | 有界队列+条件变量 |

| 任务取消 | `abort()`/`timeout` | 需手动实现（`std::stop_token` C++20） |

Rust优势：Send/Sync编译期消除数据竞争、RAII自动释放、async/await语言级统一模型、通道内置背压、`JoinSet`结构化并发。

## 9. 本节小结

- **共享状态vs通道通信**：共享状态通过锁保护数据，适合缓存/计数器；通道通信通过消息传递，适合数据流/事件驱动。Rust倾向"通过通信共享内存"，但实际项目中混合使用。
- **CSP/Actor模型**：CSP通过通道通信，通道是一等公民；Actor有私有状态和消息邮箱，串行处理消息不需要锁。Rust可用`mpsc`+事件循环实现Actor。
- **流水线与背压**：流水线将处理分为多阶段，阶段间通道连接，并行处理。有界通道天然提供背压，下游慢时上游自动减速。无界通道可能导致内存溢出。
- **spawn_blocking**：将阻塞操作（同步IO、CPU计算、阻塞C库）放到独立线程池，不占用异步工作线程。这是异步代码中调用同步代码的标准方式。
- **结构化并发**：子任务生命周期嵌套在父任务内，父任务结束前所有子任务必须结束。`JoinSet`提供结构化并发，drop时abort所有未完成任务。`tokio::spawn`是detached的，需要手动管理。
- **限流与批量合并**：`Semaphore`限制并发数，`governor`实现令牌桶限流。批量合并将多个小请求合并为大请求，用`select!`+超时实现，减少IO次数。
- **并发陷阱**：阻塞executor（用spawn_blocking）、任务饥饿（CPU密集循环加yield_now）、死锁（固定锁顺序、短临界区）、活锁（加退避抖动）。交叉引用《../../01-C++技术体系/04-并发编程/05-线程池与并发实战模式.md》。
