## 1. Mutex：锁的是数据

### 1.1 基本用法与MutexGuard

Rust的`Mutex<T>`是**包装数据**的互斥锁，而不是保护代码段的锁：

```rust
use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];
for _ in 0..10 {
    let counter = Arc::clone(&counter);
    handles.push(thread::spawn(move || {
        let mut num = counter.lock().unwrap(); // MutexGuard是RAII守卫
        *num += 1;
    })); // guard离开作用域自动drop，锁释放
}
```

`MutexGuard<T>`关键特性：RAII自动释放、Deref/DerefMut直接访问数据、不可复制、生命周期与Mutex绑定。

### 1.2 「锁数据」vs「锁代码」范式对比

| 范式 | Rust `Mutex<T>` | C++ `std::mutex` |
|------|-----------------|-------------------|
| 锁的对象 | 数据本身 | 独立的锁变量 |
| 数据访问 | 通过guard自动加锁 | 手动lock/unlock |
| 忘记解锁 | 不可能（RAII） | 可能（除非用lock_guard） |
| 未加锁访问数据 | 不可能（数据在Mutex内） | 可能（数据和锁是分离的） |
| 编译期保证 | 强（类型系统保证） | 弱（靠约定） |

C++的典型写法（数据与锁分离）：

```cpp
// C++：数据和锁是分离的，需要手动保证访问数据时持有锁
class Counter {
    std::mutex mtx;
    int count = 0; // 数据和锁是分开的
public:
    void increment() {
        std::lock_guard<std::mutex> lock(mtx); // 手动加锁
        count++; // 需要记住这里有锁保护
    }
    // 危险：可能写出忘记加锁的方法
    int get() {
        return count; // 忘记加锁！数据竞争
    }
};
```

Rust的写法（数据与锁绑定）：

```rust
use std::sync::Mutex;

struct Counter {
    count: Mutex<i32>, // 数据和锁绑定在一起
}

impl Counter {
    fn new() -> Self {
        Counter { count: Mutex::new(0) }
    }

    fn increment(&self) {
        let mut count = self.count.lock().unwrap();
        *count += 1;
    }

    fn get(&self) -> i32 {
        // 不可能忘记加锁：访问数据必须通过lock()
        *self.count.lock().unwrap()
    }
}
```

Rust的「锁数据」范式从根本上消除了"忘记加锁访问数据"这一类bug，因为数据被封装在Mutex内部，不通过lock()就无法访问。

### 1.3 死锁与中毒（poisoning）

Rust的Mutex有一个独特的特性：**中毒（poisoning）**。如果持有锁的线程panic了，Mutex会被标记为"中毒"，后续的lock()调用会返回`Err`。

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let data = Arc::new(Mutex::new(0));

    let data_clone = Arc::clone(&data);
    let handle = thread::spawn(move || {
        let mut guard = data_clone.lock().unwrap();
        *guard = 42;
        panic!("故意panic"); // 持有锁时panic，Mutex中毒
    });

    let _ = handle.join(); // 子线程panic

    // 主线程尝试获取锁
    match data.lock() {
        Ok(guard) => println!("获取成功: {}", *guard),
        Err(poisoned) => {
            // 中毒的锁仍然可以通过into_inner()获取数据
            let guard = poisoned.into_inner();
            println!("锁中毒了，但数据仍可访问: {}", *guard);
        }
    }
}
```

中毒机制的设计意图：如果持有锁的线程panic了，它可能在修改数据的中间状态崩溃，数据可能处于不一致状态。中毒提醒调用者检查数据一致性。

交叉引用：C++互斥锁与死锁的完整讨论见《../../01-C++技术体系/04-并发编程/02-互斥锁与死锁.md》。Rust的「锁数据」范式和RAII守卫显著减少了死锁的可能性，详见第8节。

## 2. RwLock读写锁

`RwLock<T>`允许多个读者同时访问，但写者排他：

```rust
use std::sync::{Arc, RwLock};
let data = Arc::new(RwLock::new(vec![1, 2, 3]));
// 读线程：data.read().unwrap()  多个读者可并发
// 写线程：data.write().unwrap() 写者排他
```

RwLock vs Mutex选择：读多写少用RwLock（多个读者并发），写多读少或读写相当用Mutex（RwLock开销更大）。RwLock也有中毒机制，与Mutex相同。

## 3. Condvar条件变量

`Condvar`（条件变量）用于线程间等待某个条件成立，通常与Mutex配合使用。

```rust
use std::sync::{Arc, Mutex, Condvar};
use std::thread;

fn main() {
    let pair = Arc::new((Mutex::new(false), Condvar::new()));
    let pair2 = Arc::clone(&pair);

    // 等待线程
    let handle = thread::spawn(move || {
        let (lock, cvar) = &*pair2;
        let mut started = lock.lock().unwrap();

        // while循环检查条件（防止虚假唤醒）
        while !*started {
            println!("等待条件...");
            started = cvar.wait(started).unwrap(); // wait会自动释放锁并阻塞
        }

        println!("条件成立，继续执行");
    });

    // 通知线程
    thread::sleep(std::time::Duration::from_millis(100));
    let (lock, cvar) = &*pair;
    let mut started = lock.lock().unwrap();
    *started = true;
    cvar.notify_one(); // 唤醒一个等待线程
    drop(started); // 释放锁

    handle.join().unwrap();
}
```

Condvar的关键模式：
1. **与Mutex配合**：条件检查在锁保护下进行
2. **while循环**：防止虚假唤醒（spurious wakeup）
3. **wait自动释放锁**：等待时释放锁，被唤醒时重新获取
4. **notify_one/notify_all**：唤醒一个或所有等待线程

生产者-消费者模式（Condvar+Mutex+VecDeque）：

```rust
let queue = Arc::new(Mutex::new(VecDeque::new()));
let cvar = Arc::new(Condvar::new());

// 生产者：lock→push→notify_one
// 消费者：lock→while空{wait}→pop_front
// wait自动释放锁并阻塞，被唤醒时重新获取锁
```

关键模式：while循环防虚假唤醒，wait自动释放/重获锁，notify_one唤醒一个等待者。

## 4. Barrier屏障

`Barrier`让多个线程在某个点同步，所有线程都到达后才继续。

```rust
use std::sync::{Arc, Barrier};
use std::thread;

fn main() {
    let n = 4;
    let barrier = Arc::new(Barrier::new(n));
    let mut handles = vec![];

    for i in 0..n {
        let barrier = Arc::clone(&barrier);
        handles.push(thread::spawn(move || {
            println!("线程{}: 第一阶段开始", i);
            thread::sleep(std::time::Duration::from_millis(i * 10));
            println!("线程{}: 第一阶段完成，等待屏障", i);

            // 等待所有线程到达
            let result = barrier.wait();
            // result.is_leader()为true的线程是"领导者"，可以做一次性工作
            if result.is_leader() {
                println!("领导者线程: 所有线程已到达屏障");
            }

            println!("线程{}: 第二阶段开始", i);
        }));
    }

    for h in handles {
        h.join().unwrap();
    }
}
```

Barrier适用于分阶段并行计算：所有线程完成第一阶段后，才开始第二阶段。

## 5. 原子操作与内存序

### 5.1 Atomic类型与常用方法

标准库提供`AtomicBool`、`AtomicI8..AtomicI64`、`AtomicUsize`、`AtomicPtr<T>`等原子类型：

```rust
use std::sync::atomic::{AtomicUsize, Ordering};

let atom = AtomicUsize::new(10);
atom.store(20, Ordering::SeqCst);        // 存储
assert_eq!(atom.load(Ordering::SeqCst), 20); // 读取
assert_eq!(atom.fetch_add(5, Ordering::SeqCst), 20); // 加5返回旧值
assert_eq!(atom.fetch_sub(3, Ordering::SeqCst), 25); // 减3

// compare_exchange：比较并交换（CAS）
assert_eq!(atom.compare_exchange(22, 100, Ordering::SeqCst, Ordering::SeqCst), Ok(22));
// compare_exchange_weak：可能虚假失败但性能更好，适合循环重试
```

多线程计数器用`Arc<AtomicUsize>` + `fetch_add`，无需锁。

### 5.2 五种Ordering详解

Rust的内存序与C++11的内存序一一对应，定义了原子操作的可见性和排序保证。

| Ordering | 含义 | 性能开销 | 典型用途 |
|----------|------|----------|----------|
| `Relaxed` | 只保证原子性，不保证排序 | 最低 | 计数器、引用计数 |
| `Acquire` | 读操作：之后的读/写不能重排到之前 | 低 | 锁的获取、加载数据 |
| `Release` | 写操作：之前的读/写不能重排到之后 | 低 | 锁的释放、存储数据 |
| `AcqRel` | Acquire+Release（用于读-改-写操作） | 中 | 无锁数据结构 |
| `SeqCst` | 全局顺序一致性 | 最高 | 最保守的保证，需要全局排序时 |

**Acquire-Release配对**：

```text
线程A（Release存储）          线程B（Acquire加载）
┌──────────────────┐         ┌──────────────────┐
│ 写入数据字段      │         │                  │
│ data = 42;       │         │                  │
├──────────────────┤         ├──────────────────┤
│ flag.store(true, │         │ if flag.load(    │
│   Release)       │         │   Acquire) {     │
└──────────────────┘         │   读取data       │
                             │   // 一定能看到42 │
                             │ }                │
                             └──────────────────┘

Acquire-Release保证：线程B的Acquire加载看到线程A的Release存储后，
线程A在Release之前的所有写入，对线程B在Acquire之后的所有读取都可见。
```

Acquire-Release配对代码示例：

```rust
// 写线程：data.store(Relaxed) → flag.store(true, Release)
// 读线程：flag.load(Acquire)看到true后 → data.load(Relaxed)一定看到42
// Release保证之前的写入不重排到之后，Acquire保证之后的读取不重排到之前
```

**Relaxed**：只保证原子性，不保证排序。适用于计数器、引用计数等不依赖其他变量顺序的场景。`Arc`的`clone()`用`fetch_add(Relaxed)`，`drop()`用`fetch_sub(Release)`。

### 5.3 对照C++memory_order

| Rust Ordering | C++ memory_order | 说明 |
|----------------|-------------------|------|
| `Relaxed` | `memory_order_relaxed` | 只保证原子性 |
| `Acquire` | `memory_order_acquire` | 读操作的获取语义 |
| `Release` | `memory_order_release` | 写操作的释放语义 |
| `AcqRel` | `memory_order_acq_rel` | 读-改-写操作 |
| `SeqCst` | `memory_order_seq_cst` | 全局顺序一致性 |

Rust和C++的内存序完全对应，因为两者都基于C++11引入的内存模型。交叉引用：C++内存模型的深入讨论见《../../01-C++技术体系/04-并发编程/04-原子操作与C++内存模型.md》，无锁编程基础见《../../01-C++技术体系/13-并发异步与组件/06-无锁编程基础.md》和《../../01-C++技术体系/13-并发异步与组件/07-原子操作与无锁组件.md》。

## 6. Arc与无锁数据结构

### 6.1 Arc引用计数

`Arc<T>`（Atomic Reference Counted）是线程安全的引用计数智能指针，`clone()`用`fetch_add(Relaxed)`增加计数，`drop()`用`fetch_sub(Release)`减少计数，计数为0时销毁数据。

```rust
use std::sync::Arc;
let data = Arc::new(vec![1, 2, 3]);
let data2 = Arc::clone(&data); // 浅拷贝，增加引用计数
// 多线程共享只读数据，需要可变时用 Arc<Mutex<T>>
```

Arc限制：只能共享不可变数据，需要内部可变性用`Arc<Mutex<T>>`或`Arc<RwLock<T>>`，循环引用用`Weak<T>`打破。

### 6.2 无锁栈实现（Treiber Stack）

Treiber Stack用CAS实现，核心算法：push读取head→设置node.next=head→CAS(head,node)；pop读取head→读取next→CAS(head,next)→返回数据。

```rust
use std::sync::atomic::{AtomicPtr, Ordering};
use std::ptr;

struct Node<T> { data: T, next: *mut Node<T> }
pub struct LockFreeStack<T> { head: AtomicPtr<Node<T>> }

impl<T> LockFreeStack<T> {
    pub fn push(&self, data: T) {
        let node = Box::into_raw(Box::new(Node { data, next: ptr::null_mut() }));
        loop {
            let head = self.head.load(Ordering::Acquire);
            unsafe { (*node).next = head; }
            if self.head.compare_exchange(head, node, Ordering::Release, Ordering::Relaxed).is_ok() { return; }
        }
    }
    pub fn pop(&self) -> Option<T> {
        loop {
            let head = self.head.load(Ordering::Acquire);
            if head.is_null() { return None; }
            unsafe {
                let next = (*head).next;
                if self.head.compare_exchange(head, next, Ordering::Release, Ordering::Relaxed).is_ok() {
                    return Some(Box::from_raw(head).data);
                }
            }
        }
    }
}
```

**ABA问题**：pop时线程A读head=H后被调度走，B pop(H)后push新节点（地址恰好也是H），A恢复后CAS成功但next可能不对。Treiber Stack中ABA不影响正确性，复杂结构需epoch回收。

### 6.3 无锁队列（Michael-Scott Queue）

Michael-Scott Queue使用头尾两个原子指针和哨兵节点，核心算法：

- **enqueue**：读取tail→读取tail.next→若next为空则CAS插入新节点→CAS推进tail
- **dequeue**：读取head/tail/next→若head==tail且next为空则队列为空→否则CAS移动head到next→返回数据

关键技巧：**帮助推进**（helping）——当发现tail落后时，当前线程帮助推进tail，减少竞争。

由于Michael-Scott Queue的完整实现涉及复杂的内存回收（裸指针+CAS+drop顺序），且手写实现容易有use-after-free风险，生产环境应直接使用`crossbeam`库的`SegQueue`（无锁队列）或`ArrayQueue`（有界无锁队列），它们经过了严格的验证和测试。

## 7. crossbeam与epoch回收

`crossbeam`（以crates.io最新稳定版为准）是Rust生态中最成熟的并发编程库，提供：
- 无锁队列（`ArrayQueue`、`SegQueue`）
- 无锁栈（`TreiberStack`）
- 无锁双端队列（`Injector`、`Worker`）
- epoch回收机制（`crossbeam-epoch`）
- 作用域线程（`crossbeam-utils::thread::scope`）

epoch回收是解决无锁数据结构中内存回收问题的标准方案：

```text
Epoch回收核心思想：
全局epoch计数器 + 每个线程局部epoch和活动标记
1. 线程pin()进入临界区，记录当前epoch
2. 线程读取指针、使用数据
3. 线程退出临界区，取消活动标记
4. 所有线程epoch前进后，旧epoch节点可安全回收
保证：没有线程正在访问待回收的节点
```

crossbeam-epoch的核心API：`epoch::pin()`进入临界区返回Guard，`guard.defer_destroy(pointer)`延迟回收节点，Guard drop时退出临界区。`Atomic<T>`替代`AtomicPtr`，`Owned<T>`替代`Box`，所有操作都接受Guard参数以保证内存安全。生产环境的无锁数据结构应直接使用crossbeam提供的`SegQueue`/`ArrayQueue`/`TreiberStack`，不需要手动实现epoch回收。

## 8. Rust如何减少死锁

对照C++的互斥锁（详见《../../01-C++技术体系/04-并发编程/02-互斥锁与死锁.md》），Rust从多个层面减少死锁：

| 死锁原因 | C++情况 | Rust情况 |
|----------|---------|----------|
| 忘记释放锁 | 可能（手动unlock） | 不可能（MutexGuard RAII自动释放） |
| 异常时未释放锁 | 可能（除非用lock_guard） | 不可能（panic时guard drop释放锁） |
| 未加锁访问数据 | 可能（数据与锁分离） | 不可能（数据封装在Mutex内） |
| 循环等待 | 可能 | 可能（但类型系统帮助减少） |
| 锁顺序不一致 | 可能 | 可能（需要约定） |

Rust减少死锁的具体机制：

1. **RAII守卫**：`MutexGuard`离开作用域自动释放，不可能忘记unlock。panic时guard也会drop，锁被释放（但Mutex会中毒）。

2. **「锁数据」范式**：数据和锁绑定在一起，不通过lock就无法访问数据。这消除了"忘记加锁"和"访问未保护数据"两类bug。

3. **不可变引用的共享性**：Rust的借用规则保证同一时间要么一个`&mut`，要么多个`&`。这意味着不需要锁的场景（只读共享）编译器自动保证安全，减少了锁的使用量。

4. **编译期数据竞争消除**：Send/Sync在编译期阻止数据竞争，减少了需要锁的场景。

5. **`std::sync::mpsc`通道**：Rust鼓励"通过通信共享内存"而不是"通过共享内存通信"，通道模式天然避免了锁和死锁。

但Rust不能完全消除死锁：
- 多个Mutex的循环等待仍然可能死锁
- 同一线程重复lock同一个Mutex（非重入锁）会死锁
- Condvar的wait/notify顺序问题

最佳实践：
- 固定锁的获取顺序
- 尽量使用短临界区
- 考虑用通道替代共享状态
- 使用`tokio::sync::Mutex`（异步场景，支持超时）

## 9. 本节小结

- **Mutex「锁的是数据」**：`Mutex<T>`把数据和锁绑定，不通过lock()无法访问数据。`MutexGuard`是RAII守卫，自动释放锁。这与C++的"数据和锁分离"形成鲜明对比，从根本上消除了"忘记加锁"类bug。
- **RwLock**：读写锁，多读者并发、写者排他。读多写少场景优于Mutex。
- **Condvar**：条件变量，与Mutex配合，wait自动释放锁，while循环防虚假唤醒。用于生产者-消费者等模式。
- **Barrier**：多线程同步点，所有线程到达后才继续。
- **原子操作**：`Atomic*`类型提供load/store/fetch_add/compare_exchange等方法。五种Ordering：Relaxed（只原子）、Acquire/Release（配对可见性）、AcqRel（读-改-写）、SeqCst（全局顺序）。与C++ memory_order完全对应。
- **Arc**：原子引用计数，多线程共享只读数据。`Arc<Mutex<T>>`是共享可变状态的标准模式。
- **无锁数据结构**：Treiber Stack用CAS实现无锁栈，Michael-Scott Queue实现无锁队列。ABA问题在简单栈中不影响正确性，复杂结构需要epoch回收。
- **crossbeam**：提供经过验证的无锁数据结构和epoch回收机制。`epoch::pin()`进入临界区，`defer_destroy`延迟回收。
- Rust通过RAII、「锁数据」范式、Send/Sync、借用规则和通道模式显著减少死锁，但多Mutex循环等待和非重入锁仍然可能死锁。
