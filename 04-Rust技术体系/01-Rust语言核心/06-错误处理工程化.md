## 1. 错误处理哲学：类型即文档

### 1.1 Rust 的错误分类

Rust 将错误分为两大类，采用完全不同的处理机制：

| 错误类型 | 机制 | 可恢复性 | 典型场景 |
|---|---|---|---|
| 可恢复错误 | `Result<T, E>` | 可恢复，调用方必须处理 | 文件不存在、网络超时、解析失败 |
| 不可恢复错误 | `panic!` | 不可恢复，终止线程/程序 | 索引越界、断言失败、逻辑 invariant 被破坏 |

这种分类的核心思想是：**错误是类型的一部分，函数签名明确告知调用方"这个函数可能失败"**。

```rust
// 函数签名即文档：返回 Result 表示可能失败
fn read_config(path: &str) -> Result<Config, std::io::Error> {
    // ...
}

// 返回 Option 表示"可能没有值"，但不是错误
fn find_user(id: u32) -> Option<User> {
    // ...
}

// 直接返回 T 表示"不会失败"（或失败时 panic）
fn square(x: i32) -> i32 {
    x * x
}
```

### 1.2 为什么不用异常

Rust 选择不使用异常机制，原因包括：

1. **零成本抽象**：异常的栈展开（stack unwinding）有运行时开销，即使没有异常发生也可能影响优化。Rust 的 `Result` 是普通枚举，没有额外开销。
2. **显式错误路径**：C++ 异常的问题在于"看不到哪些函数会抛异常"——任何函数调用都可能隐式抛出，异常安全（exception safety）需要程序员仔细分析。Rust 中 `Result` 在类型签名中显式标记，调用方必须处理（或显式 `?` 传播）。
3. **无异常安全问题**：C++ 中异常可能在构造函数、析构函数、赋值运算符中抛出，导致资源泄漏或对象状态不一致（需要 RAII 和异常安全保证）。Rust 中没有异常，`?` 只是提前返回，不会跳过析构（drop 仍然正常执行）。

> **深度对照**：C++ 异常的详细讨论可参考《../../01-C++技术体系/01-语言基础/07-异常处理与异常安全.md》。C++ 的异常安全有三个级别（基本保证、强保证、不抛保证），编写异常安全代码是 C++ 高级主题。Rust 通过消除异常机制，从根本上避免了这一类问题。

## 2. Option 组合子

`Option<T>` 提供了大量组合子方法，避免手写 `match`，使代码更简洁：

### 2.1 map / and_then / or_else

```rust
fn main() {
    let some: Option<i32> = Some(5);
    let none: Option<i32> = None;

    // map：转换内部值（如果有）
    let doubled = some.map(|x| x * 2);  // Some(10)
    let doubled_none = none.map(|x| x * 2);  // None

    // and_then（flatmap）：链式返回 Option 的操作
    let result = some.and_then(|x| if x > 0 { Some(x * 2) } else { None });
    // Some(10)

    // or_else：None 时尝试替代值
    let recovered = none.or_else(|| Some(0));  // Some(0)

    // 链式组合：解析字符串为整数并加倍
    fn parse_and_double(s: &str) -> Option<i32> {
        s.parse::<i32>().ok().and_then(|n| if n > 0 { Some(n * 2) } else { None })
    }
    println!("{:?}", parse_and_double("21"));  // Some(42)
    println!("{:?}", parse_and_double("abc")); // None
    println!("{:?}", parse_and_double("-5"));  // None
}
```

### 2.2 unwrap / unwrap_or / unwrap_or_else

```rust
fn main() {
    let some = Some(5);
    let none: Option<i32> = None;

    // unwrap：有值返回，None 时 panic（谨慎使用）
    let v = some.unwrap();  // 5
    // none.unwrap();  // panic

    // expect：unwrap 的带消息版本
    // none.expect("should have a value");  // panic with message

    // unwrap_or：提供默认值
    let v = none.unwrap_or(0);  // 0

    // unwrap_or_else：延迟计算默认值（闭包，仅 None 时执行）
    let v = none.unwrap_or_else(|| {
        // 复杂的默认值计算
        42
    });

    // unwrap_or_default：使用类型的 Default 实现
    let v: i32 = none.unwrap_or_default();  // 0
}
```

### 2.3 ok_or / ok_or_else

将 `Option` 转换为 `Result`：

```rust
fn main() {
    let some = Some(5);
    let none: Option<i32> = None;

    // ok_or：Option -> Result，有值为 Ok，无值为 Err(指定错误)
    let result: Result<i32, &str> = some.ok_or("no value");  // Ok(5)
    let err: Result<i32, &str> = none.ok_or("no value");      // Err("no value")

    // ok_or_else：延迟计算错误
    let err = none.ok_or_else(|| format!("no value at {}", std::line!()));
}
```

### 2.4 flatten / transpose

```rust
fn main() {
    // flatten：去除一层 Option 嵌套
    let nested: Option<Option<i32>> = Some(Some(5));
    let flat = nested.flatten();  // Some(5)

    // transpose：Option<Result<T,E>> <-> Result<Option<T>,E>
    let opt_result: Option<Result<i32, &str>> = Some(Ok(5));
    let result_opt: Result<Option<i32>, &str> = opt_result.transpose();  // Ok(Some(5))
}
```

## 3. Result 组合子

### 3.1 map / map_err / and_then

```rust
fn main() {
    let ok: Result<i32, &str> = Ok(5);
    let err: Result<i32, &str> = Err("something went wrong");

    // map：转换 Ok 中的值
    let doubled = ok.map(|x| x * 2);  // Ok(10)
    let doubled_err = err.map(|x| x * 2);  // Err("something went wrong")（不变）

    // map_err：转换 Err 中的值
    let with_context = err.map_err(|e| format!("ERROR: {}", e));
    // Err("ERROR: something went wrong")

    // and_then：链式返回 Result 的操作（flatmap）
    let result = ok.and_then(|x| if x > 0 { Ok(x * 2) } else { Err("negative") });
    // Ok(10)

    // or_else：Err 时尝试恢复
    let recovered = err.or_else(|_| Ok(0));  // Ok(0)
}
```

### 3.2 unwrap / expect / unwrap_or

```rust
fn main() {
    let ok: Result<i32, &str> = Ok(5);
    let err: Result<i32, &str> = Err("failed");

    // unwrap：Ok 返回值，Err 时 panic
    let v = ok.unwrap();  // 5
    // err.unwrap();  // panic

    // expect：带消息的 unwrap
    // err.expect("operation should succeed");  // panic with message

    // unwrap_or / unwrap_or_else / unwrap_or_default
    let v = err.unwrap_or(-1);  // -1
    let v = err.unwrap_or_else(|e| { eprintln!("{}", e); 0 });  // 0
}
```

### 3.3 ok / err / transpose

```rust
fn main() {
    let ok: Result<i32, &str> = Ok(5);

    // ok：Result -> Option（丢弃错误）
    let opt = ok.ok();  // Some(5)

    // err：Result -> Option（丢弃值，保留错误）
    let err_opt: Result<i32, &str> = Err("failed");
    let err = err_opt.err();  // Some("failed")

    // transpose：Result<Option<T>,E> <-> Option<Result<T,E>>
    let result_opt: Result<Option<i32>, &str> = Ok(Some(5));
    let opt_result: Option<Result<i32, &str>> = result_opt.transpose();
}
```

## 4. ? 运算符与 From 自动转换

### 4.1 ? 的工作原理

`?` 运算符是 Rust 错误处理的核心语法糖，用于传播错误：

```rust
use std::fs::File;
use std::io::Read;

// 使用 ? 传播错误
fn read_username_from_file(path: &str) -> Result<String, std::io::Error> {
    let mut file = File::open(path)?;  // 如果 Err，立即返回 Err
    let mut username = String::new();
    file.read_to_string(&mut username)?;  // 如果 Err，立即返回 Err
    Ok(username)
}

// 等价的 match 写法（冗长）
fn read_username_match(path: &str) -> Result<String, std::io::Error> {
    let mut file = match File::open(path) {
        Ok(f) => f,
        Err(e) => return Err(e),
    };
    let mut username = String::new();
    match file.read_to_string(&mut username) {
        Ok(_) => (),
        Err(e) => return Err(e),
    };
    Ok(username)
}
```

`?` 的本质是：

```rust
// expr?  等价于：
match expr {
    Ok(v) => v,
    Err(e) => return Err(From::from(e)),  // 自动转换错误类型
}
```

关键：`?` 会自动调用 `From::from(e)` 将错误类型转换为函数返回类型中的错误类型。

### 4.2 From trait 与错误转换

```rust
use std::fmt;

// 自定义错误类型
#[derive(Debug)]
enum AppError {
    Io(std::io::Error),
    Parse(std::num::ParseIntError),
    Other(String),
}

impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            AppError::Io(e) => write!(f, "IO error: {}", e),
            AppError::Parse(e) => write!(f, "Parse error: {}", e),
            AppError::Other(s) => write!(f, "{}", s),
        }
    }
}

impl std::error::Error for AppError {}

// 实现 From：自动错误转换
impl From<std::io::Error> for AppError {
    fn from(err: std::io::Error) -> Self {
        AppError::Io(err)
    }
}

impl From<std::num::ParseIntError> for AppError {
    fn from(err: std::num::ParseIntError) -> Self {
        AppError::Parse(err)
    }
}

// 使用 ? 自动转换不同错误类型
fn process_file(path: &str) -> Result<i32, AppError> {
    let content = std::fs::read_to_string(path)?;  // io::Error -> AppError
    let number: i32 = content.trim().parse()?;      // ParseIntError -> AppError
    Ok(number * 2)
}
```

> **设计要点**：为自定义错误类型实现 `From` 后，`?` 运算符会自动转换，无需手动 `map_err`。这是 Rust 错误处理的核心便利机制。C++ 中异常可以自动传播（不需要转换），但异常类型不匹配时需要 `catch` 后重新抛出，Rust 的 `From` 转换更显式、更可控。

### 4.3 try_blocks 与 try_trait

`?` 运算符目前只能在返回 `Result`/`Option` 的函数中使用。`try_blocks`（nightly）允许在块中使用 `?`：

```rust
// nightly 特性
#![feature(try_blocks)]

fn main() {
    let result: Result<i32, String> = try {
        let x: i32 = "42".parse().map_err(|e| format!("{}", e))?;
        x * 2
    };
    println!("{:?}", result);  // Ok(84)
}
```

`?` 运算符基于 `Try` trait（nightly 中为 `Try`/`FromResidual`），理论上可以为任何类型实现 `Try` 来支持 `?`，但目前稳定版只支持 `Result` 和 `Option`。

## 5. panic! 与 Result 的边界

### 5.1 什么时候用 panic

`panic!` 用于**不可恢复**的错误——程序处于无法继续运行的状态：

```rust
fn main() {
    // 1. 断言/不变量被破坏
    let v = vec![1, 2, 3];
    // v[10];  // 索引越界 → panic（不可恢复，说明逻辑有 bug）

    // 2. 示例/原型代码中简化错误处理
    let f = std::fs::File::open("config.txt").unwrap();  // 原型中可用

    // 3. 确定不会失败的场景（unwrap/expect）
    let n: i32 = "42".parse().expect("42 should parse");  // 硬编码值，确定成功

    // 4. 测试中
    // assert_eq!(result, expected);  // 断言失败 → panic
}
```

**不应该用 panic 的场景**：
- 库代码中处理外部输入（文件、网络、用户输入）——应该返回 `Result`
- 任何可以合理恢复的错误
- 生产代码中的 `.unwrap()`（除非能证明永远不会失败）

### 5.2 库 vs 应用的错误策略

| 维度 | 库 (library) | 应用 (application) |
|---|---|---|
| 错误返回 | `Result<T, E>`，自定义错误类型 | 可以用 `anyhow::Error` 聚合 |
| panic 使用 | 极少（仅 invariant 破坏） | 可以在 main 中 panic（用户友好错误） |
| 错误信息 | 结构化、可程序化处理 | 人类可读、带上下文 |
| 错误转换 | 实现 `From` 支持 `?` | 用 `anyhow!`/`bail!` 宏 |
| 关注点 | 灵活性、可组合性 | 易用性、可调试性 |

### 5.3 panic 的展开与中止

```toml
# Cargo.toml 中配置 panic 策略
[profile.release]
panic = "unwind"  # 默认：栈展开，执行 drop，可被 catch_unwind 捕获
# panic = "abort"  # 直接终止，不执行 drop，二进制更小
```

```rust
use std::panic;

fn main() {
    // catch_unwind：捕获 panic（类似 C++ 的 try/catch，但不推荐用于常规错误处理）
    let result = panic::catch_unwind(|| {
        panic!("something went wrong");
    });

    match result {
        Ok(_) => println!("no panic"),
        Err(_) => println!("caught a panic"),
    }
}
```

> **注意**：`catch_unwind` 不是用于常规错误处理的（那是 `Result` 的工作），而是用于隔离第三方代码的 panic（如 FFI 边界、插件系统），防止 panic 传播到 C 代码导致 UB。

## 6. 自定义错误类型

### 6.1 枚举错误类型

最常见的自定义错误是枚举，每个变体代表一种错误：

```rust
use std::fmt;

#[derive(Debug)]
enum ConfigError {
    IoError(std::io::Error),
    ParseError { line: usize, message: String },
    MissingField(String),
    InvalidValue { field: String, expected: String, got: String },
}

impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            ConfigError::IoError(e) => write!(f, "IO error: {}", e),
            ConfigError::ParseError { line, message } =>
                write!(f, "Parse error at line {}: {}", line, message),
            ConfigError::MissingField(field) =>
                write!(f, "Missing required field: {}", field),
            ConfigError::InvalidValue { field, expected, got } =>
                write!(f, "Invalid value for '{}': expected {}, got '{}'", field, expected, got),
        }
    }
}

impl std::error::Error for ConfigError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            ConfigError::IoError(e) => Some(e),  // 错误链：返回底层错误
            _ => None,
        }
    }
}

impl From<std::io::Error> for ConfigError {
    fn from(err: std::io::Error) -> Self {
        ConfigError::IoError(err)
    }
}
```

### 6.2 错误 trait：Error / Display / Debug

一个完整的错误类型应实现三个 trait：

| trait | 用途 | 自动派生 |
|---|---|---|
| `Debug` | 调试输出（`{:?}`） | `#[derive(Debug)]` |
| `Display` | 用户友好输出（`{}`） | 手动实现 |
| `Error` | 标准错误 trait，支持 `source()` 错误链 | 手动实现（可空实现） |

`Error` trait 的核心方法：

```rust
pub trait Error: Debug + Display {
    // 错误链：返回底层错误（可选）
    fn source(&self) -> Option<&(dyn Error + 'static)> { None }

    // 已弃用，用 Display 替代
    fn description(&self) -> &str { "" }
    fn cause(&self) -> Option<&dyn Error> { self.source() }
}
```

## 7. thiserror vs anyhow 选型

### 7.1 thiserror：库的自定义错误

`thiserror` 是一个派生宏库，自动为枚举错误类型生成 `Display`、`Error`、`From` 实现：

```toml
# Cargo.toml
[dependencies]
thiserror = "1"  # 以 crates.io 最新稳定版为准
```

```rust
use thiserror::Error;

#[derive(Error, Debug)]
enum ConfigError {
    #[error("IO error: {0}")]
    Io(#[from] std::io::Error),  // #[from] 自动生成 From 实现

    #[error("Parse error at line {line}: {message}")]
    Parse {
        line: usize,
        message: String,
    },

    #[error("Missing required field: {0}")]
    MissingField(String),

    #[error("Invalid value for '{field}': expected {expected}, got '{got}'")]
    InvalidValue {
        field: String,
        expected: String,
        got: String,
    },
}

// 使用：自动获得 Display、Error、From<std::io::Error>
fn load_config(path: &str) -> Result<(), ConfigError> {
    let content = std::fs::read_to_string(path)?;  // ? 自动转换 io::Error
    // ...
    Ok(())
}
```

`thiserror` 的关键属性：
- `#[error("...")]`：生成 `Display` 实现，支持 `{0}`、`{field}` 插值
- `#[from]`：自动生成 `From` 实现，支持 `?` 自动转换
- `#[source]`：指定 `source()` 返回的字段（错误链）

### 7.2 anyhow：应用的错误聚合

`anyhow` 提供 `anyhow::Error` 类型和 `anyhow!`/`bail!` 宏，用于应用层快速聚合错误：

```toml
# Cargo.toml
[dependencies]
anyhow = "1"  # 以 crates.io 最新稳定版为准
```

```rust
use anyhow::{anyhow, bail, Result, Context};

// 返回 anyhow::Result<T>（等价于 Result<T, anyhow::Error>）
fn run() -> Result<()> {
    // 1. ? 自动转换任何实现了 std::error::Error 的类型
    let content = std::fs::read_to_string("config.txt")
        .context("Failed to read config file")?;  // 添加上下文

    // 2. bail!：立即返回错误（类似 return Err(...)）
    if content.is_empty() {
        bail!("Config file is empty");
    }

    // 3. anyhow!：构造错误
    let port: u16 = content.trim().parse()
        .map_err(|_| anyhow!("Invalid port number: {}", content.trim()))?;

    // 4. with_context：延迟计算上下文
    let config = parse_config(&content)
        .with_context(|| format!("Failed to parse config with {} bytes", content.len()))?;

    Ok(())
}

fn main() {
    if let Err(e) = run() {
        eprintln!("Error: {:?}", e);  // Debug 输出显示完整错误链
        std::process::exit(1);
    }
}
```

`anyhow::Error` 的特点：
- 可以包装任何实现了 `std::error::Error` 的类型
- 支持错误链（`source()`）和上下文（`context()`/`with_context()`）
- `Debug` 输出显示完整错误链（带缩进）
- `Downcast`：可以尝试转换回具体错误类型

### 7.3 选型决策表

| 场景 | 推荐 | 原因 |
|---|---|---|
| 库的公共 API 返回错误 | `thiserror` | 调用方需要结构化、可匹配的错误类型 |
| 应用的 `main`/业务逻辑 | `anyhow` | 不需要匹配具体错误，只需要展示和日志 |
| 需要 `match` 错误变体 | `thiserror` | `anyhow::Error` 是类型擦除的，匹配需 downcast |
| 快速原型/脚本 | `anyhow` | 零样板，`?` 直接用 |
| 错误需要跨 FFI 边界 | 自定义（简化枚举） | `anyhow::Error` 不是 FFI-safe |
| 嵌入式 `no_std` | 自定义 | `thiserror`/`anyhow` 依赖 std |

> **常见模式**：库用 `thiserror` 定义结构化错误，应用用 `anyhow` 聚合库错误和其他错误。`anyhow::Error` 可以包装 `thiserror` 生成的错误（因为它实现了 `std::error::Error`），两者配合使用。

## 8. 错误链与上下文

错误链（error chain）记录错误的因果关系，便于调试：

```rust
use std::error::Error;
use std::fmt;

#[derive(Debug)]
enum DatabaseError {
    ConnectionFailed(String),
    QueryFailed(String),
}

impl fmt::Display for DatabaseError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            DatabaseError::ConnectionFailed(s) => write!(f, "Connection failed: {}", s),
            DatabaseError::QueryFailed(s) => write!(f, "Query failed: {}", s),
        }
    }
}

impl Error for DatabaseError {}

#[derive(Debug)]
enum UserServiceError {
    Db(DatabaseError),  // 包装底层错误
    NotFound(u32),
}

impl fmt::Display for UserServiceError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            UserServiceError::Db(_) => write!(f, "Database operation failed"),
            UserServiceError::NotFound(id) => write!(f, "User {} not found", id),
        }
    }
}

impl Error for UserServiceError {
    fn source(&self) -> Option<&(dyn Error + 'static)> {
        match self {
            UserServiceError::Db(e) => Some(e),  // 返回底层错误
            _ => None,
        }
    }
}

impl From<DatabaseError> for UserServiceError {
    fn from(e: DatabaseError) -> Self {
        UserServiceError::Db(e)
    }
}

fn print_error_chain(mut e: &dyn Error) {
    println!("Error: {}", e);
    while let Some(source) = e.source() {
        println!("  Caused by: {}", source);
        e = source;
    }
}
```

`anyhow` 的上下文机制更简洁：

```rust
use anyhow::{Context, Result};

fn load_user(id: u32) -> Result<User> {
    let data = std::fs::read_to_string(format!("users/{}.json", id))
        .with_context(|| format!("Failed to read user file for id {}", id))?;

    let user: User = serde_json::from_str(&data)
        .with_context(|| format!("Failed to parse user data for id {}", id))?;

    Ok(user)
}
// 错误链：Failed to parse user data for id 42
//   Caused by: expected `:` at line 3 column 5
```

## 9. 对照 C++：异常 / 错误码

| 维度 | Rust Result + ? | C++ 异常 | C++ 错误码 |
|---|---|---|---|
| 错误标记 | 类型签名显式（`Result<T,E>`） | 隐式（任何函数可能抛） | 类型签名显式（返回 int/枚举） |
| 错误传播 | `?` 运算符（显式但简洁） | 自动传播（隐式） | 手动 `if (err) return err;` |
| 正常路径开销 | 零（枚举判断） | 零（无异常时）/ 有（异常时） | 零（返回值判断） |
| 错误路径开销 | 零（提前返回） | 高（栈展开、异常对象） | 零（返回值） |
| 资源清理 | drop 自动执行（无异常） | RAII（异常时析构仍执行） | 手动 goto cleanup / RAII |
| 错误信息 | 结构化（枚举变体 + 字段） | 异常对象（what() 字符串） | 整数/枚举（需查表获取信息） |
| 错误链 | `source()` + `context()` | 异常嵌套（C++11 nested_exception） | 无（需手动包装） |
| 强制处理 | 编译器强制（Result 必须处理） | 不强制（可忽略异常） | 不强制（可忽略返回值） |
| 异常安全 | 无此概念（无异常） | 三个保证级别，需仔细分析 | 无此概念 |
| 跨 FFI | 需转换为 C 兼容错误码 | 不能跨 FFI（C 无异常） | 天然兼容 |

> **核心差异**：Rust 的 `Result` 结合了 C++ 错误码的"显式、零开销"和 C++ 异常的"自动传播、丰富信息"，通过 `?` 运算符和 `From` 转换实现了简洁的错误传播，同时保持了类型安全和零开销。C++23 的 `std::expected` 是向 Rust `Result` 靠拢的尝试，但生态和语言支持仍不如 Rust 成熟。

## 10. 综合示例：文件解析器

```rust
use thiserror::Error;
use std::collections::HashMap;

// 自定义错误（thiserror）
#[derive(Error, Debug)]
enum ParseError {
    #[error("IO error: {0}")]
    Io(#[from] std::io::Error),

    #[error("Parse error at line {line}: {message}")]
    Parse {
        line: usize,
        message: String,
    },

    #[error("Duplicate key: {0}")]
    DuplicateKey(String),
}

// 解析结果
#[derive(Debug)]
struct Config {
    values: HashMap<String, String>,
}

impl Config {
    // 从文件加载
    fn from_file(path: &str) -> Result<Self, ParseError> {
        let content = std::fs::read_to_string(path)?;  // Io 错误自动转换
        Self::from_str(&content)
    }

    // 从字符串解析
    fn from_str(content: &str) -> Result<Self, ParseError> {
        let mut values = HashMap::new();

        for (line_num, line) in content.lines().enumerate() {
            let line = line.trim();

            // 跳过空行和注释
            if line.is_empty() || line.starts_with('#') {
                continue;
            }

            // 解析 key=value
            let parts: Vec<&str> = line.splitn(2, '=').collect();
            if parts.len() != 2 {
                return Err(ParseError::Parse {
                    line: line_num + 1,
                    message: format!("expected 'key=value', got '{}'", line),
                });
            }

            let key = parts[0].trim().to_string();
            let value = parts[1].trim().to_string();

            if values.contains_key(&key) {
                return Err(ParseError::DuplicateKey(key));
            }

            values.insert(key, value);
        }

        Ok(Config { values })
    }

    fn get(&self, key: &str) -> Option<&String> {
        self.values.get(key)
    }
}

// 应用层：用 anyhow 聚合
use anyhow::{Context, Result};

fn run() -> Result<()> {
    let config = Config::from_file("config.txt")
        .context("Failed to load configuration")?;

    let port = config.get("port")
        .context("Missing 'port' in config")?;

    println!("Using port: {}", port);
    Ok(())
}

fn main() {
    if let Err(e) = run() {
        eprintln!("{:?}", e);  // 显示完整错误链
        std::process::exit(1);
    }
}
```

## 11. 常见坑与编译错误

### 错误 1：the `?` operator can only be used in a function that returns `Result`

```text
error[E0277]: the `?` operator can only be used in a function that returns `Result` or `Option`
```
**原因**：在返回 `()` 或其他类型的函数中使用了 `?`。**修复**：将函数返回类型改为 `Result<(), E>`，或使用 `match`/`if let` 处理。

### 错误 2：mismatched types: expected enum `Result`, found `()`

```text
error[E0308]: mismatched types
  = note: expected enum `Result<(), _>`
             found unit type `()`
```
**原因**：函数声明返回 `Result` 但函数体最后没有 `Ok(())`。**修复**：在函数末尾添加 `Ok(())`。

### 错误 3：`?` couldn't convert error type

```text
error[E0277]: `?` couldn't convert the error to `MyError`
```
**原因**：`?` 需要将底层错误转换为函数返回的错误类型，但没有实现 `From`。**修复**：为目标错误类型实现 `From<SourceError>`，或使用 `map_err` 手动转换。

### 错误 4：called `Result::unwrap()` on an `Err` value

```text
thread 'main' panicked at 'called `Result::unwrap()` on an `Err` value: ...'
```
**原因**：运行时 `unwrap()` 被调用在 `Err` 上。**修复**：用 `?` 传播错误，或用 `unwrap_or`/`match` 处理，避免生产代码中裸 `unwrap()`。

## 12. 本节小结

- **错误处理哲学**：Rust 将错误分为可恢复（`Result`）和不可恢复（`panic!`），错误是类型的一部分，函数签名即文档。不使用异常，避免了异常安全问题和隐式错误路径。
- **Option 组合子**：`map`/`and_then`/`or_else` 链式转换，`unwrap_or` 提供默认值，`ok_or` 转换为 `Result`，`flatten`/`transpose` 处理嵌套。
- **Result 组合子**：`map`/`map_err`/`and_then` 分别转换 Ok/Err 和链式操作，`ok`/`err` 转换为 `Option`。
- **? 运算符**：核心语法糖，等价于 `match` + `return Err(From::from(e))`，自动传播错误并转换类型。基于 `From` trait 实现自动错误转换。
- **panic 边界**：仅用于不可恢复错误（invariant 破坏、断言、确定成功的 unwrap）。库代码极少 panic，应用可在 main 中 panic。panic 策略可配置为 unwind 或 abort。
- **自定义错误**：枚举错误类型 + `Display` + `Error` + `From` 四件套，`source()` 支持错误链。
- **thiserror vs anyhow**：库用 `thiserror`（结构化、可匹配、派生宏零样板），应用用 `anyhow`（聚合、上下文、错误链）。两者配合使用。
- **错误链与上下文**：`source()` 记录因果关系，`context()`/`with_context()` 添加人类可读上下文，便于调试。
- **与 C++ 对照**：Rust `Result` + `?` 结合了错误码的显式零开销和异常的自动传播，编译器强制处理错误。C++23 `std::expected` 是类似尝试但生态不成熟。
