## 1. crate 与模块的层级关系

### 1.1 crate 是编译单元

crate 是 Rust 的**编译单元**，也是可见性的最外层边界。一个 crate 对应一个 `Cargo.toml` 和一个根模块（`src/lib.rs` 或 `src/main.rs`）。

```text
crate（编译单元）
└── 根模块（lib.rs / main.rs）
    ├── mod network
    │   ├── mod tcp
    │   └── mod udp
    ├── mod protocol
    │   └── mod http
    └── mod utils
```

crate 分两种：
- **binary crate**：有 `src/main.rs`，编译为可执行文件
- **library crate**：有 `src/lib.rs`，编译为库，可以被其他 crate 依赖

对照 C++：Rust 的 crate 相当于 C++的一个静态库/动态库项目，但 Rust 的 crate 有统一的构建系统（Cargo）和明确的可见性边界。C++的"库"没有语言级别的可见性概念，全靠头文件的 `public`/`private` 和约定。

### 1.2 mod 的声明与嵌套

```rust
// src/lib.rs —— crate根模块

// 声明子模块，Rust会自动查找对应的文件
mod network;
mod protocol;
mod utils;

// 内联模块：直接在当前文件中定义
mod config {
    pub struct ServerConfig {
        pub port: u16,
    }

    impl ServerConfig {
        pub fn new(port: u16) -> Self {
            ServerConfig { port }
        }
    }
}

// 公开模块：外部crate可以访问
pub mod api;

// 条件编译模块
#[cfg(feature = "tls")]
pub mod tls;
```

模块的嵌套通过文件系统或内联 `mod` 块实现，形成一棵树。每个模块有自己的可见性作用域。

## 2. 可见性：pub/pub(crate)/pub(super)/pub(in path)

### 2.1 五种可见性级别

| 可见性 | 含义 | 类比 C++ |
|--------|------|---------|
| （默认）私有 | 仅当前模块及子模块可访问 | `private` |
| `pub(super)` | 当前模块的父模块可访问 | 无直接对应 |
| `pub(crate)` | 整个 crate 内可访问 | 无直接对应（类似内部头文件） |
| `pub(in path)` | 指定路径内可访问 | 无直接对应 |
| `pub` | 所有 crate 可访问 | `public` |

```rust
mod outer {
    // 私有：仅outer及其子模块可访问
    struct Private {
        value: i32,
    }

    // pub(super)：outer的父模块（根模块）可访问
    pub(super) struct SuperVisible {
        value: i32,
    }

    // pub(crate)：整个crate可访问
    pub(crate) struct CrateVisible {
        pub value: i32,
    }

    // pub：所有crate可访问
    pub struct Public {
        pub value: i32,
    }

    mod inner {
        // 可以访问outer的私有项
        use super::Private;

        fn demo() {
            let _p = Private { value: 1 }; // OK：子模块可访问父模块私有项
        }
    }
}

// 根模块中
fn main() {
    // let _p = outer::Private { value: 1 }; // 错误：私有
    let _s = outer::SuperVisible { value: 2 }; // OK：pub(super)
    let _c = outer::CrateVisible { value: 3 }; // OK：pub(crate)
    let _p = outer::Public { value: 4 }; // OK：pub
}
```

### 2.2 字段与方法的可见性

结构体的字段可见性独立于结构体本身：

```rust
pub struct User {
    pub id: u64,           // 公开字段
    pub(crate) email: String, // crate内可见
    password_hash: String,  // 私有字段
}

impl User {
    pub fn new(id: u64, email: String, password_hash: String) -> Self {
        User { id, email, password_hash }
    }

    // 公开方法
    pub fn verify_password(&self, input: &str) -> bool {
        self.password_hash == input // 私有字段在impl块内可访问
    }

    // crate内可见的方法
    pub(crate) fn internal_id(&self) -> u64 {
        self.id
    }
}
```

枚举的变体默认与枚举本身可见性相同，不能单独设置变体可见性（但可以设置变体字段的可见性）。

## 3. 文件与模块映射规则

### 3.1 单文件模块

```text
src/
├── lib.rs          # 根模块，包含 mod network;
└── network.rs      # network模块的内容
```

```rust
// src/lib.rs
mod network; // 查找 src/network.rs

// src/network.rs
pub fn connect() -> bool {
    true
}
```

### 3.2 目录模块（mod.rs 与目录名.rs）

当模块有子模块时，使用目录结构：

```text
src/
├── lib.rs
└── network/
    ├── mod.rs      # network模块本身（2015 edition风格）
    ├── tcp.rs      # network::tcp
    └── udp.rs      # network::udp
```

```rust
// src/network/mod.rs
pub mod tcp;   // 查找 src/network/tcp.rs
pub mod udp;   // 查找 src/network/udp.rs

pub fn connect() -> bool {
    tcp::connect() || udp::connect()
}
```

### 3.3 2018 edition 后的文件映射

2018 edition 引入了更简洁的目录模块写法：用 `network.rs` 代替 `network/mod.rs`：

```text
src/
├── lib.rs
├── network.rs      # network模块本身（2018+风格）
└── network/
    ├── tcp.rs
    └── udp.rs
```

```rust
// src/network.rs
pub mod tcp;
pub mod udp;

pub fn connect() -> bool {
    tcp::connect() || udp::connect()
}
```

两种风格可以混用，但同一个项目中建议统一。2018+风格的优势是模块文件名直接对应模块名，不需要在目录中找 `mod.rs`。

对照 C++：C++没有文件与模块的映射规则，头文件和源文件的组织完全是约定。Rust 的模块系统强制了文件与命名空间的对应关系，减少了"这个类在哪个文件"的困惑。

## 4. 路径与 use 重导出

### 4.1 绝对路径与相对路径

```rust
// src/lib.rs
pub mod network {
    pub mod tcp {
        pub fn connect() -> bool { true }
    }
}

mod client {
    use crate::network::tcp; // 绝对路径：从crate根开始

    pub fn run() {
        tcp::connect();
    }
}

mod server {
    use super::network::tcp; // 相对路径：从父模块开始

    pub fn run() {
        tcp::connect();
    }
}

mod handler {
    use super::network::tcp; // 相对路径：从父模块开始

    pub fn run() {
        tcp::connect();
    }
}
```

2018 edition 后，`use` 路径默认是绝对路径（从 crate 根或外部 crate 名开始）。需要相对路径时用 `crate::`、`super::`、`self::` 开头。

### 4.2 use 与 as 重命名

```rust
// 导入并重命名
use std::collections::HashMap as Map;
use std::io::Result as IoResult;

// 嵌套导入
use std::collections::{HashMap, HashSet};

// 通配符导入（谨慎使用）
use std::prelude::v1::*;

// 自导入：把模块本身导入当前作用域
use self::network;

fn main() {
    let mut map: Map<String, i32> = Map::new();
    map.insert("key".to_string(), 42);
}
```

### 4.3 pub use 重导出

`pub use` 是库设计的核心工具：将内部模块的项重新导出，形成稳定的公共 API。

```rust
// src/lib.rs
mod internal {
    pub struct Connection {
        pub addr: String,
    }

    impl Connection {
        pub fn new(addr: &str) -> Self {
            Connection { addr: addr.to_string() }
        }
    }

    pub struct ConnectionPool {
        connections: Vec<Connection>,
    }
}

// 重导出：外部用户不需要知道internal模块的存在
pub use internal::Connection;
pub use internal::ConnectionPool;

// 也可以重命名后导出
pub use internal::Connection as Conn;
```

外部用户使用时：

```rust
use my_crate::Connection; // 直接从crate根导入，不需要my_crate::internal::Connection

fn main() {
    let conn = Connection::new("127.0.0.1:8080");
}
```

重导出的好处：
1. **隐藏内部结构**：内部模块可以自由重构，不影响外部 API
2. **扁平化 API**：用户不需要记住深层路径
3. **版本兼容**：可以同时导出新旧名称，平滑迁移

对照 C++：C++中没有 `pub use`，命名空间的重导出需要用 `namespace alias` 或 `using` 声明，但这些是头文件级别的，没有 crate 可见性的保护。C++库的内部头文件经常被用户意外直接包含，破坏封装。

## 5. workspace 多 crate 组织

### 5.1 workspace 结构与 Cargo.toml

workspace 是多个 crate 的集合，共享同一个 `Cargo.lock` 和输出目录。

```text
my_project/
├── Cargo.toml          # workspace根配置
├── Cargo.lock
├── crates/
│   ├── core/           # 核心库crate
│   ├── network/        # 网络库crate
│   └── cli/            # 命令行工具crate
└── tests/              # workspace级集成测试
```

workspace 根 `Cargo.toml`：

```toml
[workspace]
members = [
    "crates/core",
    "crates/network",
    "crates/cli",
]

# 共享依赖版本（Cargo 1.64+）
[workspace.dependencies]
serde = { version = "1", features = ["derive"] }
tokio = { version = "1", features = ["full"] }
anyhow = "1"
thiserror = "1"

# 共享元数据
[workspace.package]
version = "0.1.0"
edition = "2021"
license = "MIT"
repository = "https://github.com/user/my_project"
```

（以上 crate 版本以 crates.io 最新稳定版为准）

### 5.2 成员 crate 间的依赖

```toml
# crates/network/Cargo.toml
[package]
name = "my-project-network"
version.workspace = true
edition.workspace = true

[dependencies]
# 依赖workspace内的其他crate
my-project-core = { path = "../core" }

# 使用workspace共享依赖
serde.workspace = true
tokio.workspace = true
```

```toml
# crates/cli/Cargo.toml
[package]
name = "my-project-cli"
version.workspace = true
edition.workspace = true

[dependencies]
my-project-core = { path = "../core" }
my-project-network = { path = "../network" }
anyhow.workspace = true
clap = { version = "4", features = ["derive"] }
```

### 5.3 共享依赖与 workspace.dependencies

`workspace.dependencies` 确保所有成员 crate 使用相同版本的依赖，避免版本冲突和重复编译：

```toml
# 根Cargo.toml
[workspace.dependencies]
serde = { version = "1.0", features = ["derive"] }

# 成员Cargo.toml
[dependencies]
serde.workspace = true  # 使用workspace中定义的serde

# 也可以覆盖部分属性
serde = { workspace = true, features = ["rc"] }  # 在workspace基础上增加feature
```

## 6. feature flags 条件编译

### 6.1 定义与启用 feature

```toml
# Cargo.toml
[features]
default = ["std"]
std = []
alloc = []
# 启用tls feature时自动依赖相关crate
tls = ["dep:rustls", "dep:webpki-roots"]
# 启用json feature时启用serde的derive feature
json = ["dep:serde", "serde/derive"]
# feature之间的依赖
full = ["std", "tls", "json"]
```

```rust
// src/lib.rs

// 默认启用std时的代码
#[cfg(feature = "std")]
pub mod io {
    pub fn read_to_string(path: &str) -> std::io::Result<String> {
        std::fs::read_to_string(path)
    }
}

// no_std环境下的替代实现
#[cfg(not(feature = "std"))]
pub mod io {
    pub fn read_to_string(_path: &str) -> Result<String, &'static str> {
        Err("no_std: file IO not available")
    }
}

// 仅在启用tls时编译
#[cfg(feature = "tls")]
pub mod tls {
    pub struct TlsConfig {
        pub cert: Vec<u8>,
    }
}

// 条件编译函数
#[cfg(feature = "json")]
pub fn to_json<T: serde::Serialize>(value: &T) -> Result<String, serde_json::Error> {
    serde_json::to_string(value)
}
```

启用 feature 的方式：

```bash
# 命令行指定
cargo build --features tls,json

# 启用所有feature
cargo build --all-features

# 不使用默认feature
cargo build --no-default-features --features alloc
```

### 6.2 可选依赖与 feature 联动

```toml
[dependencies]
serde = { version = "1", optional = true }
serde_json = { version = "1", optional = true }
rustls = { version = "0.21", optional = true }

[features]
# 旧写法：feature名称与可选依赖同名
# serde = ["dep:serde"]  # 2024年前需要显式声明

# 新写法（Cargo 1.60+）：可选依赖自动创建同名feature
# 可以用dep:前缀在feature中引用可选依赖
json = ["dep:serde", "dep:serde_json", "serde/derive"]
```

### 6.3 cfg 属性与 cfg!宏

`#[cfg]` 属性在编译期条件性包含代码，`cfg!` 宏在运行时检查配置（但编译器会优化掉不可能的分支）：

```rust
// 属性形式：条件编译整个项
#[cfg(target_os = "linux")]
fn epoll_create() -> i32 {
    // Linux特定代码
    0
}

#[cfg(target_os = "windows")]
fn iocp_create() -> i32 {
    // Windows特定代码
    0
}

// cfg!宏：运行时检查，编译期优化
fn platform_name() -> &'static str {
    if cfg!(target_os = "linux") {
        "linux"
    } else if cfg!(target_os = "windows") {
        "windows"
    } else {
        "unknown"
    }
}

// 常用cfg条件
#[cfg(unix)]            // 所有Unix系统
#[cfg(windows)]         // Windows
#[cfg(target_pointer_width = "64")]
#[cfg(target_endian = "little")]
#[cfg(debug_assertions)] // debug构建
#[cfg(test)]            // 测试构建
fn demo() {}
```


## 8. 循环依赖规避

Rust 中 crate 之间**不允许循环依赖**（A 依赖 B，B 依赖 A）。模块之间可以有循环引用（通过路径引用），但 crate 级别的循环依赖会导致编译失败。

### 常见循环依赖场景与解决方案

**场景 1：core 和 net 互相依赖**

```text
core ←→ net  （循环依赖，编译失败）
```

**解决方案：提取公共类型到独立 crate**

```text
common（公共类型/trait定义）
  ↑    ↑
core  net
```

```rust
// crates/common/src/lib.rs
pub trait ConnectionHandler {
    fn on_data(&mut self, data: &[u8]);
}

pub struct Message {
    pub id: u64,
    pub payload: Vec<u8>,
}

// crates/core/src/lib.rs
use my_project_common::{ConnectionHandler, Message};

pub struct Engine {
    handler: Box<dyn ConnectionHandler>,
}

// crates/net/src/lib.rs
use my_project_common::{ConnectionHandler, Message};

pub struct TcpServer {
    handler: Box<dyn ConnectionHandler>,
}
```

**场景 2：trait 定义与实现在不同 crate 中互相引用**

**解决方案：使用 trait object 或泛型参数，将依赖方向反转**

```rust
// 不要这样：A依赖B的类型，B依赖A的trait
// crate A: pub trait Handler { fn handle(&self, event: B::Event); }
// crate B: impl A::Handler for B::Processor { ... }

// 正确：trait中使用关联类型或泛型
// crate A:
pub trait Handler {
    type Event;
    fn handle(&self, event: Self::Event);
}

// crate B:
struct Processor;
struct Event { data: Vec<u8> }

impl Handler for Processor {
    type Event = Event;
    fn handle(&self, event: Event) {
        println!("{}", event.data.len());
    }
}
```

**场景 3：功能拆分导致的循环**

**解决方案：使用 feature flags 或运行时注册**

```rust
// 通过trait注册机制避免编译期循环
// crates/core/src/lib.rs
pub struct PluginRegistry {
    plugins: Vec<Box<dyn Plugin>>,
}

pub trait Plugin {
    fn name(&self) -> &str;
}

// crates/extra/src/lib.rs
use my_project_core::{Plugin, PluginRegistry};

pub struct ExtraPlugin;
impl Plugin for ExtraPlugin {
    fn name(&self) -> &str { "extra" }
}

// 在main中注册，core不需要知道extra的存在
fn main() {
    let mut registry = PluginRegistry { plugins: vec![] };
    registry.plugins.push(Box::new(my_project_extra::ExtraPlugin));
}
```

## 9. 快速参考卡片

| 查询点 | 速答 |
| --- | --- |
| mod 声明 | `mod a;` 让 `a.rs`（或 `a/mod.rs`）参与编译；**不声明就不会被编译** |
| 可见性五级 | 默认私有 → `pub`、`pub(crate)`、`pub(super)`、`pub(in path)` |
| 可见性传导 | `pub` 项在私有模块内，外部仍不可见；可见性沿路径逐级检查 |
| 路径写法 | 2018+ 用 `crate::a::b`（绝对）或 `self::`/`super::`（相对）；`use` 引入后可直接用短名 |
| 重导出 | `pub use crate::inner::Thing;` 在 crate 根聚合公共 API |
| 文件布局 | `src/lib.rs` + `src/foo.rs` 或 `src/foo/mod.rs`（二选一）；2018 后推荐 `foo.rs` |
| workspace | 根 `Cargo.toml` 写 `[workspace] members = [...]`；共享依赖用 `[workspace.dependencies]` |
| 成员引用 | 成员 crate 写 `foo = { path = "../foo" }`；版本统一提升到 workspace |
| feature 机制 | `[features]` + `#[cfg(feature = "x")]`；可选依赖自动生成同名 feature |
| 循环依赖 | crate 间不允许；模块间允许但需 `super::` 绕行，通常说明该抽 trait |

## 10. 常见坑

### 坑 1：新增文件忘了写 `mod`

`src/utils.rs` 建好了，但 `main.rs` 里没写 `mod utils;`——该文件根本不会被编译，代码"像不存在一样"。IDE 可能不报错，`use` 时才报"unresolved module"。

### 坑 2：以为 `pub` 就一定对外可见

`pub fn` 放在私有模块 `mod inner` 中，crate 外部依然访问不到。要么模块也 `pub`，要么在 crate 根用 `pub use` 重导出。可见性是路径上每一级的与运算。

### 坑 3：`mod.rs` 与 `foo.rs` 混用

同一个模块同时存在 `foo.rs` 和 `foo/mod.rs` 会编译报错（ambiguous module）。2018 edition 起推荐 `foo.rs` + `foo/` 目录的写法，不要两套混着来。

### 坑 4：workspace 里依赖版本各写各的

每个成员各自写 `serde = "1.0"` 尚可，但一旦出现 `"1.0"` 与 `"1.0.100"` 交织、或同一 crate 的两个大版本，就会出现"两份类型不兼容"的编译错误。统一在 `[workspace.dependencies]` 声明，成员用 `serde.workspace = true` 继承。

### 坑 5：feature 不是加性的

Cargo 的 feature 应当是**纯加法**：开启 A 不应导致原本能编译的代码失败。常见反例：`#[cfg(not(feature = "a"))]` 改类型签名、feature 之间互斥。正确做法是用 `cfg` 只做"增加实现/依赖"，或用独立 feature 组合出 `cfg(all(...))`。

### 坑 6：`pub use crate::*` 污染导出面

在 crate 根通配重导出会让公共 API 变得不可控（内部重构直接破坏下游）。显式列出要导出的名字，必要时用 `pub(crate)` 收敛内部接口。

## 11. 本节小结

- **crate**是编译单元和可见性最外层边界，分 binary 和 library 两种。模块（mod）形成树状结构，嵌套通过文件系统或内联块实现。
- **可见性五级**：私有（默认）、`pub(super)`、`pub(crate)`、`pub(in path)`、`pub`。结构体字段可见性独立于结构体本身。`pub(crate)` 是内部 API 的核心工具。
- **文件映射**：单文件模块 `module.rs`，目录模块用 `module/mod.rs`（2015）或 `module.rs`+`module/`（2018+）。2018+风格更推荐。
- **路径与重导出**：`use` 默认绝对路径，`crate::`/`super::`/`self::` 表示相对路径。`pub use` 重导出是库 API 设计的核心，隐藏内部结构、扁平化 API。
- **workspace**：多 crate 共享 `Cargo.lock` 和输出目录，`workspace.dependencies` 统一依赖版本，`workspace.package` 共享元数据。成员 crate 间用 `path` 依赖。
- **feature flags**：在 `Cargo.toml` 的 `[features]` 中定义，`#[cfg(feature = "...")]` 条件编译，可选依赖自动创建 feature。`cfg!` 宏运行时检查（编译期优化）。
