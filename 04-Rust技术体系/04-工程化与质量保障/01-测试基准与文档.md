## 1. 测试体系总览与 C++ 对照

### 1.1 Rust 测试分层模型

Rust 的测试能力由语言内置属性 `#[test]` 和 `cargo test` 命令驱动，无需引入第三方框架即可完成单元测试、集成测试和文档测试。测试代码与业务代码共存于同一 crate，通过 `#[cfg(test)]` 条件编译在非测试构建中完全剥离。

测试分层从内到外依次为：

| 层级 | 位置 | 访问权限 | 运行方式 |
|------|------|----------|----------|
| 单元测试 | `src/` 内 `#[cfg(test)] mod tests` | 可访问私有项 | `cargo test` |
| 集成测试 | `tests/` 目录下独立 `.rs` | 仅能访问公开 API | `cargo test` |
| 文档测试 | `///` 注释中的代码块 | 仅能访问公开 API | `cargo test --doc` |
| 基准测试 | `benches/` 目录 + criterion | 公开 API 或内部 | `cargo bench` |

### 1.2 与 C++ 测试框架对照

C++ 生态中常见的组合是 GoogleTest（单元/集成）+ Google Benchmark（基准）+ LCOV/gcov（覆盖率）+ Doxygen（文档）。Rust 将这些能力收敛到 `cargo` 单一入口，对照表如下：

| 能力 | C++ 方案 | Rust 方案 |
|------|----------|-----------|
| 单元测试 | GoogleTest `TEST()` | `#[test]` + `assert_eq!` |
| 测试夹具 | `TEST_F()` + SetUp/TearDown | 普通函数 + RAII guard |
| 参数化测试 | `TEST_P()` | `#[test]` 循环或 `rstest` crate |
| 集成测试 | 独立可执行 target | `tests/` 目录自动识别 |
| 文档测试 | 无（Doxygen 不执行） | `cargo test --doc` 强制执行 |
| 基准测试 | Google Benchmark | `criterion` crate |
| 覆盖率 | gcov/LCOV | `cargo-tarpaulin` 或 `llvm-cov` |
| Mock | gmock | `mockall` crate |

关键差异：C++ 的测试框架是外部库，需要在 CMake 中链接；Rust 的 `#[test]` 是编译器内置属性，零依赖即可运行。文档测试是 Rust 独有的强约束——注释中的示例代码会被编译执行，从机制上杜绝了"文档与实现漂移"。

## 2. 单元测试与 `#[cfg(test)]`

### 2.1 测试模块与私有项访问

单元测试通常写在源文件末尾的 `tests` 模块中，通过 `#[cfg(test)]` 标记仅在测试构建时编译。由于测试模块是被测模块的子模块，Rust 的可见性规则允许子模块访问父模块的私有项——这与 C++ 中 `friend class` 或把测试放到同命名空间的做法等价，但更安全。

```rust
// src/calculator.rs
pub struct Calculator {
    accumulator: i64, // 私有字段
}

impl Calculator {
    pub fn new() -> Self {
        Calculator { accumulator: 0 }
    }

    pub fn add(&mut self, value: i64) {
        self.accumulator += value;
    }

    fn internal_reset(&mut self) {
        self.accumulator = 0;
    }
}

#[cfg(test)]
mod tests {
    use super::*; // 导入父模块所有项，包括私有

    #[test]
    fn test_add_accumulates() {
        let mut calc = Calculator::new();
        calc.add(5);
        calc.add(3);
        // 可以直接访问私有字段 accumulator
        assert_eq!(calc.accumulator, 8);
    }

    #[test]
    fn test_internal_reset_works() {
        let mut calc = Calculator::new();
        calc.add(10);
        calc.internal_reset(); // 可以调用私有方法
        assert_eq!(calc.accumulator, 0);
    }
}
```

C++ 对照：在 C++ 中要测试私有成员，通常需要 `FRIEND_TEST` 宏或将测试类声明为 `friend`，这会污染生产代码的头文件。Rust 的子模块可见性是语言级机制，生产代码无需任何修改。

### 2.2 断言家族

Rust 标准库提供四个核心断言宏，均位于 `std` 顶层，无需导入：

| 宏 | 用途 | 失败时输出 |
|----|------|------------|
| `assert!(cond)` | 布尔条件 | 条件表达式 + 位置 |
| `assert_eq!(a, b)` | 相等比较 | 左右值的 Debug 输出 |
| `assert_ne!(a, b)` | 不等比较 | 左右值的 Debug 输出 |
| `debug_assert!(cond)` | 仅 debug 构建检查 | 同 assert |

`assert_eq!` 和 `assert_ne!` 要求被比较类型实现 `PartialEq` 和 `Debug` trait。对于自定义结构体，派生这两个 trait 即可：

```rust
#[derive(Debug, PartialEq)]
pub struct Point {
    pub x: i32,
    pub y: i32,
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_point_equality() {
        let p1 = Point { x: 1, y: 2 };
        let p2 = Point { x: 1, y: 2 };
        assert_eq!(p1, p2); // 自动比较所有字段
    }

    #[test]
    fn test_with_custom_message() {
        let result = 42;
        assert!(result > 100, "结果 {} 不应小于等于 100", result);
    }
}
```

C++ 对照：`ASSERT_EQ` 在 GoogleTest 中需要类型支持 `operator==` 和 `operator<<`（用于打印）。Rust 通过 derive 宏自动生成，减少了样板代码。`assert_eq!` 的失败信息会同时打印左右值，与 GoogleTest 的 `Expected`/`Actual` 输出等价。

### 2.3 `should_panic` 与预期失败

当测试目标是验证"某段代码应当 panic"时（例如非法输入校验），使用 `#[should_panic]` 属性。可以通过 `expected` 参数精确匹配 panic 消息，避免测试因不相关的 panic 而误通过。

```rust
pub fn divide(a: i64, b: i64) -> f64 {
    if b == 0 {
        panic!("除数不能为零");
    }
    a as f64 / b as f64
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    #[should_panic(expected = "除数不能为零")]
    fn test_divide_by_zero_panics() {
        divide(10, 0);
    }

    #[test]
    #[should_panic] // 不指定消息，任意 panic 都通过
    fn test_any_panic_is_fine() {
        divide(1, 0);
    }
}
```

C++ 对照：GoogleTest 中使用 `ASSERT_DEATH` 或 `EXPECT_DEATH` 验证进程崩溃，但这会 fork 子进程，开销较大。Rust 的 `should_panic` 在同一进程内捕获 panic（通过 `std::panic::catch_unwind`），轻量且快速。注意：如果 crate 设置了 `panic = "abort"`，`should_panic` 将无法工作，因为进程直接终止而非展开栈。

## 3. 集成测试与 `tests/` 目录

### 3.1 集成测试的可见性边界

集成测试位于 crate 根目录下的 `tests/` 文件夹中，每个 `.rs` 文件会被编译为独立的测试可执行文件。集成测试只能通过 `use crate_name::...` 访问 crate 的公开 API，无法触及私有项——这与 C++ 中把测试放到独立 target、只链接公开头文件的做法一致。

```rust
// tests/integration_basic.rs
use my_crate::Calculator; // 只能导入公开项

#[test]
fn test_calculator_public_api() {
    let mut calc = Calculator::new();
    calc.add(10);
    // calc.accumulator; // 编译错误：私有字段不可访问
    // calc.internal_reset(); // 编译错误：私有方法不可访问
    calc.add(5); // add 返回 ()，修改内部状态
    assert_eq!(calc.value(), 15); // 用 value() 读取当前值
}
```

运行集成测试时，`cargo test` 会先编译 library crate，再为每个 `tests/*.rs` 编译独立二进制并运行。可以通过 `cargo test --test integration_basic` 只运行指定的集成测试文件。

### 3.2 共享辅助代码与 `tests/common/mod.rs`

多个集成测试文件之间共享辅助代码（如测试夹具、mock 服务器）时，不能直接在 `tests/` 下创建普通模块——每个顶层 `.rs` 都会被当作独立测试 target。正确做法是创建 `tests/common/mod.rs`，在其中定义共享函数，然后在测试文件中通过 `mod common;` 引入。

```rust
// tests/common/mod.rs
use my_crate::Calculator;

pub fn make_calculator_with_value(value: i64) -> Calculator {
    let mut calc = Calculator::new();
    calc.add(value);
    calc
}

pub fn assert_close(a: f64, b: f64, epsilon: f64) {
    assert!(
        (a - b).abs() < epsilon,
        "{} 与 {} 的差值超过 epsilon {}",
        a, b, epsilon
    );
}
```

```rust
// tests/test_with_helpers.rs
mod common; // 引入共享模块
use common::{make_calculator_with_value, assert_close};
use my_crate::divide;

#[test]
fn test_using_helper() {
    let calc = make_calculator_with_value(100);
    // ... 使用 calc 进行测试
}

#[test]
fn test_float_division() {
    assert_close(divide(1, 3), 0.3333333, 1e-6);
}
```

C++ 对照：C++ 中通常在 `tests/` 下创建 `test_helpers.h` 头文件，在各测试 `.cpp` 中 `#include`。Rust 的 `tests/common/mod.rs` 模式等价，但 Rust 的模块系统会自动忽略 `common/` 目录下的文件作为独立测试 target（因为它不是顶层 `.rs`）。

## 4. 文档测试：注释即测试

### 4.1 `///` 文档注释与代码块执行

Rust 的文档注释使用 `///`（外部文档）或 `//!`（模块/crate 级文档）。注释中用三个反引号包裹的代码块会被 `cargo test --doc` 提取、编译并执行。这意味着文档中的每个示例都是活的——一旦 API 变更导致示例无法编译，测试就会失败。

```rust
/// 将两个数字相加。
///
/// # 示例
///
/// ```
/// use my_crate::add;
/// assert_eq!(add(2, 3), 5);
/// ```
///
/// # 边界情况
///
/// 当输入为 `i64::MAX` 时溢出会 panic：
///
/// ```should_panic
/// use my_crate::add;
/// add(i64::MAX, 1);
/// ```
pub fn add(a: i64, b: i64) -> i64 {
    a + b
}
```

文档测试代码块支持多种标注：

| 标注 | 含义 |
|------|------|
| ```` ```rust ```` 或无标注 | 编译并运行 |
| ```` ```ignore ```` | 不编译（用于伪代码） |
| ```` ```no_run ```` | 编译但不运行（用于有副作用的示例） |
| ```` ```should_panic ```` | 运行并预期 panic |
| ```` ```compile_fail ```` | 预期编译失败 |
| ```` ```text ```` / ```` ```bash ```` | 非 Rust 代码，不编译 |

### 4.2 文档测试的隐藏行与 `no_run`

有时文档示例需要一些准备代码（如导入、初始化），但不希望这些代码出现在渲染后的文档中。可以在代码行前加 `# ` 前缀，该行会被编译执行但不会显示在 `cargo doc` 生成的 HTML 中。

```rust
/// 从文件读取并解析配置。
///
/// # 示例
///
/// ```
/// # use std::io::Write;
/// # // 以下准备代码在文档中隐藏
/// # let mut tmp = std::env::temp_dir();
/// # tmp.push("config_demo.toml");
/// # let mut f = std::fs::File::create(&tmp).unwrap();
/// # f.write_all(b"name = \"demo\"\n").unwrap();
/// # let path = tmp.clone();
/// // 文档中只显示这行有意义的调用
/// let config = my_crate::load_config(&path).unwrap();
/// assert_eq!(config.name, "demo");
/// # std::fs::remove_file(&tmp).unwrap();
/// ```
pub fn load_config(path: &std::path::Path) -> Result<Config, std::io::Error> {
    // ...
}
```

对于启动服务器、监听端口等有副作用的示例，使用 `no_run` 确保编译通过但不实际执行：

```rust
/// 启动一个 HTTP 服务器。
///
/// ```no_run
/// use my_crate::Server;
/// Server::bind("127.0.0.1:8080")?.run()?;
/// # Ok::<(), std::io::Error>(())
/// ```
```

C++ 对照：C++ 的 Doxygen 注释中的代码块仅用于展示，不会被编译执行。这导致大量 C++ 项目的文档示例随着 API 演进而逐渐失效。Rust 的文档测试从机制上保证了"文档即规范"，是 Rust 生态质量保障的核心差异化能力。

## 5. Mock 思路与依赖注入

### 5.1 trait 抽象作为接缝

Rust 没有继承，mock 的核心思路是通过 trait 定义依赖接口，在生产代码中注入真实实现，在测试中注入 mock 实现。这与 C++ 中通过纯虚基类 + 依赖注入实现 mock 的思路一致，但 Rust 的 trait object 或泛型约束更零成本。

```rust
// 定义数据获取 trait 作为接缝
pub trait DataSource {
    fn fetch(&self, key: &str) -> Option<String>;
}

// 业务逻辑依赖 trait，而非具体实现
pub struct UserService<D: DataSource> {
    data_source: D,
}

impl<D: DataSource> UserService<D> {
    pub fn new(data_source: D) -> Self {
        UserService { data_source }
    }

    pub fn get_user_name(&self, user_id: &str) -> String {
        self.data_source
            .fetch(user_id)
            .unwrap_or_else(|| "未知用户".to_string())
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    // 手写 mock：实现 trait，内部用 HashMap 模拟数据
    struct MockDataSource {
        data: std::collections::HashMap<String, String>,
    }

    impl DataSource for MockDataSource {
        fn fetch(&self, key: &str) -> Option<String> {
            self.data.get(key).cloned()
        }
    }

    #[test]
    fn test_get_existing_user() {
        let mut mock = MockDataSource { data: std::collections::HashMap::new() };
        mock.data.insert("user_1".to_string(), "Alice".to_string());
        let service = UserService::new(mock);
        assert_eq!(service.get_user_name("user_1"), "Alice");
    }

    #[test]
    fn test_get_missing_user_returns_default() {
        let mock = MockDataSource { data: std::collections::HashMap::new() };
        let service = UserService::new(mock);
        assert_eq!(service.get_user_name("nonexistent"), "未知用户");
    }
}
```

### 5.2 mockall 自动生成 mock

手写 mock 适用于简单场景，但当 trait 方法较多、需要验证调用次数和参数时，`mockall` crate 可以自动生成功能完整的 mock。以 crates.io 最新稳定版为准。

```toml
# Cargo.toml
[dev-dependencies]
mockall = "0.13"
```

```rust
use mockall::{automock, predicate::*};

#[automock]
pub trait DataSource {
    fn fetch(&self, key: &str) -> Option<String>;
    fn store(&mut self, key: &str, value: &str);
}

pub struct UserService<D: DataSource> {
    data_source: D,
}

impl<D: DataSource> UserService<D> {
    pub fn new(data_source: D) -> Self {
        UserService { data_source }
    }

    pub fn get_user_name(&self, user_id: &str) -> String {
        self.data_source
            .fetch(user_id)
            .unwrap_or_else(|| "未知用户".to_string())
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_mock_expectation() {
        let mut mock = MockDataSource::new();
        // 设置预期：fetch("user_1") 被调用时返回 Some("Alice")
        mock.expect_fetch()
            .with(eq("user_1"))
            .times(1)
            .returning(|_| Some("Alice".to_string()));

        let service = UserService::new(mock);
        assert_eq!(service.get_user_name("user_1"), "Alice");
        // mock drop 时自动验证 times(1) 预期
    }
}
```

C++ 对照：`mockall` 的 `expect_xxx().with().times().returning()` 链式调用与 gmock 的 `EXPECT_CALL(mock, Method(...)).Times(...).WillOnce(...)` 语法高度对应。差异在于 gmock 需要 `MOCK_METHOD` 宏在 mock 类中声明，而 `mockall` 通过 `#[automock]` 属性宏自动生成，减少了样板代码。

## 6. criterion 基准测试

### 6.1 基准函数与统计输出

Rust 官方的 `#[bench]` 属性目前仅在 nightly 可用。稳定通道的标准方案是 `criterion` crate，它提供统计严谨的基准测试，自动输出均值、中位数、标准差、p95/p99 等指标，并生成 HTML 报告和趋势图。以 crates.io 最新稳定版为准。

```toml
# Cargo.toml
[dev-dependencies]
criterion = { version = "0.5", features = ["html_reports"] }

[[bench]]
name = "my_benchmark"
harness = false
```

```rust
// benches/my_benchmark.rs
use criterion::{black_box, criterion_group, criterion_main, Criterion};

fn fibonacci(n: u64) -> u64 {
    match n {
        0 => 1,
        1 => 1,
        _ => fibonacci(n - 1) + fibonacci(n - 2),
    }
}

fn bench_fibonacci(c: &mut Criterion) {
    c.bench_function("fibonacci 20", |b| {
        b.iter(|| fibonacci(black_box(20)));
    });

    // 参数化基准：测试不同输入规模
    let mut group = c.benchmark_group("fibonacci_by_input");
    for &n in &[10u64, 20, 30] {
        group.bench_with_input(format!("n={}", n), &n, |b, &n| {
            b.iter(|| fibonacci(black_box(n)));
        });
    }
    group.finish();
}

criterion_group!(benches, bench_fibonacci);
criterion_main!(benches);
```

运行 `cargo bench` 后，criterion 会在 `target/criterion/` 下生成报告，包含：

- 每次迭代的平均耗时（ns/μs/ms 自动换算）
- 标准差与置信区间
- 与上一次基准的对比（regression/improvement 检测）
- HTML 报告含 SVG 趋势图

`black_box` 的作用是阻止编译器将已知结果优化掉，与 C++ Google Benchmark 中的 `benchmark::DoNotOptimize` 等价。

### 6.2 与 C++ Google Benchmark 对照

| 特性 | C++ Google Benchmark | Rust criterion |
|------|---------------------|----------------|
| 基准注册 | `BENCHMARK(MyFunc)` | `criterion_group!` + `criterion_main!` |
| 阻止优化 | `DoNotOptimize` | `black_box` |
| 参数化 | `->Arg(10)->Arg(20)` | `benchmark_group` + 循环 |
| 统计输出 | 均值 + 标准差 + 手动重复 | 均值/中位数/p95/p99 + 自动重复 |
| 趋势对比 | 无内置 | 自动检测 regression |
| HTML 报告 | 需额外工具 | 内置 `html_reports` feature |
| 运行命令 | 编译后直接运行二进制 | `cargo bench` |

criterion 的核心优势是统计严谨性：它会自动运行足够多次以获得 95% 置信区间，并在检测到性能回归时给出明确警告。C++ Google Benchmark 默认只运行固定次数，需要手动设置 `->Iterations()` 或 `->Repetitions()`。

## 7. tarpaulin 覆盖率统计

### 7.1 安装与基本用法

`cargo-tarpaulin` 是 Rust 生态最常用的覆盖率工具，基于 ptrace 或 LLVM  profiling instrumentation 统计测试覆盖的代码行。安装后通过 `cargo tarpaulin` 运行。

```bash
# 安装（以 crates.io 最新稳定版为准）
cargo install cargo-tarpaulin

# 基本运行：输出文本格式覆盖率
cargo tarpaulin

# 生成 HTML 报告（可在浏览器中查看逐行覆盖）
cargo tarpaulin --out Html

# 生成 LCOV 格式（可与 Codecov、Coveralls 等平台集成）
cargo tarpaulin --out Lcov

# 排除特定文件或目录
cargo tarpaulin --exclude-files "tests/*" --exclude-files "benches/*"

# 设置覆盖率阈值，低于阈值时返回非零退出码（CI 门禁）
cargo tarpaulin --fail-under 80
```

### 7.2 覆盖率报告与 CI 集成

tarpaulin 生成的 `tarpaulin-report.html` 会用绿色标记已覆盖行、红色标记未覆盖行，便于定位测试盲区。在 CI 中通常配合 LCOV 输出上传到 Codecov：

```yaml
# .github/workflows/coverage.yml（节选）
- name: Run coverage
  run: cargo tarpaulin --out Lcov --exclude-files "tests/*"
- name: Upload to Codecov
  uses: codecov/codecov-action@v4
  with:
    files: lcov.info
    fail_ci_if_error: true
```

C++ 对照：C++ 中通常用 `gcov` 收集覆盖率数据，再用 `LCOV` 生成 HTML 报告，需要在编译时加 `--coverage` 标志并在 CMake 中配置。Rust 的 tarpaulin 一键完成编译、运行、收集、报告全流程，且自动处理增量编译缓存。需要注意的是，tarpaulin 在某些平台（如 Windows MSVC）上支持有限，Windows 环境可改用 `cargo-llvm-cov`（基于 LLVM 原生覆盖率，跨平台更好）。

## 8. 常见坑与本节小结

### 常见坑

1. **集成测试无法访问私有项**：这是设计意图，不是缺陷。如果需要测试私有逻辑，将其放在单元测试中，或将逻辑提取为公开但 `#[doc(hidden)]` 的辅助函数。
2. **`should_panic` 与 `panic = "abort"` 冲突**：如果 `Cargo.toml` 中设置了 `panic = "abort"`，所有 `should_panic` 测试都会失败。需要为测试 profile 单独配置 `panic = "unwind"`。
3. **文档测试中的 `?` 运算符需要返回 `Result`**：文档测试代码块默认返回 `()`，如果使用 `?` 必须在末尾加 `# Ok::<(), ErrorType>(())` 隐藏行。
4. **criterion 基准被优化器消除**：忘记用 `black_box` 包裹输入或输出会导致基准时间接近 0ns。始终对基准函数的输入和返回值使用 `black_box`。
5. **tarpaulin 在 Windows 上不稳定**：Windows MSVC 工具链下 tarpaulin 可能无法正常工作，建议使用 WSL2 或切换到 `cargo-llvm-cov`。
6. **测试失败时需结合调试器定位**：`cargo test` 只显示失败断言，复杂逻辑错误需用 `rust-gdb` 附加到测试二进制进行单步调试，调试方法可参考《../../01-C++技术体系/07-调试与测试/01-GDB程序调试.md》。

### 本节小结

Rust 的测试体系以 `cargo test` 为统一入口，覆盖单元测试（`#[cfg(test)]` 子模块，可访问私有项）、集成测试（`tests/` 目录，仅公开 API）、文档测试（`///` 注释中的代码块强制执行）三个层级。断言宏 `assert!`/`assert_eq!`/`assert_ne!` 配合 `#[should_panic]` 覆盖正常与异常路径。Mock 通过 trait 抽象 + `mockall` 自动生成实现，与 C++ gmock 思路一致但样板更少。基准测试使用 `criterion`，提供统计严谨的自动重复与回归检测。覆盖率使用 `cargo-tarpaulin` 或 `cargo-llvm-cov`，支持 HTML/LCOV 报告与 CI 门禁。文档测试是 Rust 区别于 C++ 生态的核心差异化能力，从机制上保证了文档与实现的一致性。
