## 1. 可观测性三支柱与 Rust 生态总览

### 1.1 日志/指标/追踪的分工

可观测性（Observability）的三大支柱各有分工：

| 支柱 | 回答的问题 | 数据特征 | Rust 核心 crate |
|------|-----------|----------|-----------------|
| 日志（Logs） | 发生了什么？ | 离散事件、文本/结构化 | `log` + `env_logger` / `tracing` |
| 指标（Metrics） | 系统当前状态如何？ | 数值聚合、时间序列 | `metrics` + `prometheus` |
| 追踪（Traces） | 请求经过了哪些环节？耗时分布？ | 有向无环图、span 链路 | `tracing` + `opentelemetry` |

Rust 生态的一个显著特点是 `tracing` crate 同时覆盖了"结构化日志"和"分布式追踪"两个领域——它的 `span` 概念既是日志的上下文容器，也是追踪链路的基本单元。这与 C++ 中日志（spdlog/glog）和追踪（OpenTelemetry C++）完全分离的架构不同。

### 1.2 与 C++ 可观测手段对照

C++ 后台开发中常见的可观测组合是：spdlog（同步/异步日志）+ Prometheus C++ 客户端（指标）+ OpenTelemetry C++（追踪）。三者各自独立，需要手动关联（如在日志中打印 trace_id）。Rust 生态的对照如下（可交叉参考《../../01-C++技术体系/15-中间件与微服务/03-异步日志与Protobuf.md》中 C++ 异步日志的实现细节）：

| 能力 | C++ 方案 | Rust 方案 |
|------|----------|-----------|
| 日志门面 | 无统一门面，直接用 spdlog | `log` trait 门面，可切换后端 |
| 异步日志 | spdlog `async_logger_mt` | `tracing` + `tracing-subscriber` 非阻塞输出 |
| 结构化日志 | 手动格式化 JSON 字符串 | `tracing` 原生结构化字段 |
| 日志级别过滤 | spdlog `set_level_pattern` | `RUST_LOG` 环境变量 + 模块级过滤 |
| 指标 | prometheus-cpp | `metrics` crate 门面 |
| 追踪 | OpenTelemetry C++ | `tracing` + `opentelemetry-rust` |
| 日志与追踪关联 | 手动在日志中注入 trace_id | `tracing` span 自动携带上下文 |

核心差异：C++ 的可观测三支柱是三个独立库，需要在应用代码中手动串联；Rust 的 `tracing` 将日志和追踪统一在一个抽象下，`metrics` 提供指标门面，三者可以通过 `tracing::span!` 的字段自然关联。

## 2. log 门面与基础日志

### 2.1 log crate 门面模式

`log` crate 是 Rust 生态的日志门面（facade），它只定义日志级别和宏，不提供实际输出。应用代码通过 `log::info!` 等宏记录日志，具体输出由实现了 `log::Log` trait 的后端 crate（如 `env_logger`、`simple_logger`、`tracing_log`）决定。这种门面模式与 C++ 中 slf4j（Java）或自己封装的日志抽象层类似，但 Rust 生态已形成统一标准。

```toml
# Cargo.toml
[dependencies]
log = "0.4"
env_logger = "0.11"
```

```rust
use log::{info, warn, error, debug, trace};

fn process_request(id: u64, path: &str) {
    debug!("开始处理请求: id={}, path={}", id, path);
    info!("请求处理完成: id={}", id);
    if id % 100 == 0 {
        warn!("第 {} 个请求，可能需要关注", id);
    }
}

fn main() {
    // 初始化日志后端
    env_logger::init();

    info!("应用启动");
    process_request(1, "/api/users");
    process_request(100, "/api/orders");
    error!("模拟错误: 数据库连接超时");
}
```

`log` 宏支持五个级别，从低到高：`trace!` < `debug!` < `info!` < `warn!` < `error!`。级别过滤由后端实现，`log` 门面本身不做过滤决策。这种设计使得库 crate 可以只依赖 `log`（轻量），而应用 crate 选择具体后端。

### 2.2 env_logger 与灵活过滤

`env_logger` 是最常用的 `log` 后端，通过 `RUST_LOG` 环境变量控制日志级别和模块过滤。过滤语法支持全局级别、模块级覆盖、正则匹配：

```bash
# 全局 info 级别
RUST_LOG=info cargo run

# 全局 warn，但 my_crate::db 模块用 debug
RUST_LOG=warn,my_crate::db=debug cargo run

# 全局 info，过滤掉含 "health_check" 的日志
RUST_LOG=info/health_check cargo run

# 多个模块分别设置
RUST_LOG=my_crate=debug,hyper=info,tower=warn cargo run
```

```rust
use env_logger::Env;

fn main() {
    // 程序化配置：默认级别 info，环境变量覆盖
    env_logger::Builder::from_env(Env::default().default_filter_or("info"))
        .format_timestamp_secs()
        .format_target(false) // 不显示模块路径
        .init();

    log::info!("应用启动，日志系统就绪");
}
```

C++ 对照：spdlog 的级别过滤通常在代码中通过 `spdlog::set_level()` 全局设置，或为每个 logger 单独设置。`env_logger` 的 `RUST_LOG` 环境变量机制更灵活——无需重新编译即可调整过滤策略，且支持模块级精细控制。这与 Java 的 logback 配置文件类似，但 Rust 用环境变量而非 XML 配置。

## 3. tracing：结构化异步日志

### 3.1 span 与 event 的概念模型

`tracing` 是 Rust 异步生态的标准可观测框架，核心概念有两个：

- **Event（事件）**：离散的日志记录，等价于传统日志的一条消息。通过 `tracing::info!`、`tracing::error!` 等宏创建。
- **Span（跨度）**：一段有开始和结束的时间区间，代表一个操作的生命周期。Span 可以嵌套，形成调用链；Span 上可以附加结构化字段（key-value），在整个生命周期内有效。

```rust
use tracing::{info, info_span, error, instrument};

// 方式一：手动创建 span
fn handle_request(user_id: u64, path: &str) {
    let span = info_span!("handle_request", user_id, path);
    let _guard = span.enter(); // 进入 span，guard drop 时退出

    info!("开始处理");
    // ... 业务逻辑
    info!("处理完成");
}

// 方式二：#[instrument] 宏自动为函数创建 span
#[instrument(skip(password), fields(user_id = %user.id))]
fn login(user: &User, password: &str) -> Result<Token, AuthError> {
    info!("用户登录尝试");
    // ... 验证逻辑
    // password 被 skip，不会出现在日志中
}
```

Span 的关键价值在于**上下文传播**：当一个 event 发生时，它自动继承当前所有活跃 span 的字段。例如在 `handle_request` span 内调用 `login`，`login` 内的 `info!` 会同时携带 `user_id`、`path`（来自外层 span）和 `user.id`（来自内层 span）。这在异步代码中尤为重要——传统日志无法跨 `.await` 点保留上下文，而 tracing 的 span 与 async task 绑定，自动跟随执行流。

### 3.2 结构化字段与异步上下文传播

tracing 的字段支持多种格式化语法：

| 语法 | 含义 | 示例 |
|------|------|------|
| `field = value` | Debug 格式化 | `user_id = user.id` |
| `field = %value` | Display 格式化 | `name = %user.name` |
| `field = ?value` | Debug 格式化（显式） | `config = ?config` |
| `field = &value` | 引用，避免 move | `data = &large_data` |
| `field = tracing::field::Empty` | 延迟填充 | `status = tracing::field::Empty` |

```rust
use tracing::{info, info_span, Instrument};

async fn fetch_data(url: &str) -> Result<Response, reqwest::Error> {
    let span = info_span!("fetch_data", url, status = tracing::field::Empty);
    let _guard = span.enter();

    info!("发起 HTTP 请求");
    let response = reqwest::get(url).await?;

    // 延迟填充字段：请求完成后才知道 status
    span.record("status", &response.status().as_u16());
    info!("请求完成");

    Ok(response)
}

// 用 .instrument() 为 future 附加 span，跨 await 自动传播
async fn process_batch(urls: Vec<String>) {
    let handles: Vec<_> = urls.into_iter().map(|url| {
        let span = info_span!("batch_item", url = %url);
        fetch_data(&url).instrument(span)
    }).collect();

    for handle in handles {
        if let Err(e) = handle.await {
            tracing::error!(error = %e, "批量处理失败");
        }
    }
}
```

`.instrument(span)` 是 tracing 与 async 集成的关键：它将 span 附加到 future 上，future 每次被 poll 时自动进入 span，poll 结束时退出。这确保了即使 future 在多个 task 间迁移（如 `tokio::spawn`），span 上下文始终跟随。C++ 中要实现类似效果，需要手动在回调中传递上下文对象，或使用 OpenTelemetry 的 context propagation API，样板代码远多于 Rust。

## 4. Subscriber 与分层输出

### 4.1 tracing_subscriber 配置

`tracing` 本身只定义事件和 span 的产生，实际的收集、过滤、格式化、输出由实现了 `Subscriber` trait 的组件完成。`tracing-subscriber` crate 提供了常用的 Subscriber 实现和配置工具。

```toml
# Cargo.toml
[dependencies]
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter", "json"] }
```

```rust
use tracing_subscriber::{fmt, EnvFilter};

fn main() {
    // 基础配置：文本格式 + 环境变量过滤
    tracing_subscriber::fmt()
        .with_env_filter(EnvFilter::from_default_env()) // 读取 RUST_LOG
        .with_target(true)        // 显示模块路径
        .with_thread_ids(true)    // 显示线程 ID
        .with_file(true)          // 显示文件名
        .with_line_number(true)   // 显示行号
        .init();

    tracing::info!("tracing 系统初始化完成");
}
```

`EnvFilter` 支持与 `env_logger` 相同的 `RUST_LOG` 语法，同时还支持 span 字段过滤（如 `RUST_LOG=info[{user_id=42}]` 只记录特定用户的日志），这是 `env_logger` 不具备的能力。

### 4.2 分层 Layer 与 JSON 输出

`tracing-subscriber` 的 `Layer` trait 支持将多个输出层组合：一层输出文本到控制台，一层输出 JSON 到文件，一层发送到 OpenTelemetry。各层可以有独立的过滤策略。

```rust
use tracing_subscriber::{fmt, layer::SubscriberExt, util::SubscriberInitExt, EnvFilter};
use tracing_appender::rolling::{RollingFileAppender, Rotation};

fn main() {
    // 控制台层：人类可读文本
    let console_layer = fmt::layer()
        .with_target(true)
        .with_writer(std::io::stdout);

    // 文件层：JSON 格式，按小时滚动
    let file_appender = RollingFileAppender::new(
        Rotation::HOURLY,
        "./logs",
        "app.log",
    );
    let (non_blocking, _guard) = tracing_appender::non_blocking(file_appender);
    let file_layer = fmt::layer()
        .json()
        .with_current_span(true)
        .with_span_list(true)
        .with_writer(non_blocking);

    // 组合多层 + 全局过滤
    tracing_subscriber::registry()
        .with(EnvFilter::from_default_env())
        .with(console_layer)
        .with(file_layer)
        .init();

    tracing::info!(user_id = 42, "这条日志同时输出到控制台和 JSON 文件");
}
```

JSON 输出的每条日志包含 `timestamp`、`level`、`message`、`target`、`span`（当前活跃 span 名称和字段）、`spans`（完整 span 链）等字段，可直接被 ELK、Loki、Datadog 等日志平台解析。`tracing_appender::non_blocking` 提供异步非阻塞写入，避免日志 IO 阻塞业务线程——这与 C++ spdlog 的 `async_logger` 原理相同（可参考《../../01-C++技术体系/15-中间件与微服务/03-异步日志与Protobuf.md》），但 tracing 的非阻塞写入与 span 上下文传播天然集成。

## 5. metrics 指标体系

### 5.1 metrics crate 与宏

`metrics` crate 是 Rust 生态的指标门面，与 `log` 门面模式类似：库 crate 依赖 `metrics` 宏记录指标，应用 crate 选择具体后端（如 `metrics-exporter-prometheus`）输出。核心指标类型有三种：

| 类型 | 用途 | 宏 | C++ Prometheus 对应 |
|------|------|----|---------------------|
| Counter（计数器） | 单调递增的值 | `counter!` | `Counter` |
| Gauge（仪表盘） | 可增可减的瞬时值 | `gauge!` | `Gauge` |
| Histogram（直方图） | 观测值分布 | `histogram!` | `Histogram` |

```toml
# Cargo.toml
[dependencies]
metrics = "0.23"
metrics-exporter-prometheus = "0.15"
```

```rust
use metrics::{counter, gauge, histogram, describe_counter, describe_gauge, describe_histogram};
use std::time::Instant;

fn init_metrics() {
    // 注册 Prometheus exporter，监听 /metrics 端点
    let exporter = metrics_exporter_prometheus::PrometheusBuilder::new()
        .with_http_listener(([0, 0, 0, 0], 9090).into())
        .install()
        .expect("Failed to install Prometheus exporter");

    // 描述指标（帮助文本，出现在 /metrics 输出中）
    describe_counter!("http_requests_total", "HTTP 请求总数");
    describe_gauge!("active_connections", "当前活跃连接数");
    describe_histogram!("http_request_duration_seconds", "HTTP 请求耗时分布");
}

fn handle_http_request(method: &str, path: &str, status: u16) {
    let start = Instant::now();

    // Counter：带标签（label）
    counter!("http_requests_total",
        "method" => method.to_string(),
        "path" => path.to_string(),
        "status" => status.to_string(),
    ).increment(1);

    // Gauge：活跃连接数增减
    gauge!("active_connections").increment(1.0);
    // ... 处理请求 ...
    gauge!("active_connections").decrement(1.0);

    // Histogram：记录耗时
    let duration = start.elapsed().as_secs_f64();
    histogram!("http_request_duration_seconds",
        "method" => method.to_string(),
        "path" => path.to_string(),
    ).record(duration);
}
```

`metrics` 宏的标签（labels）通过 `"key" => value` 语法附加，与 Prometheus 的 label 概念直接对应。Counter 和 Gauge 返回的句柄可以多次调用 `increment`/`decrement`/`set`，Histogram 返回的句柄调用 `record`。

### 5.2 对接 Prometheus

`metrics-exporter-prometheus` 自动在指定端口启动 HTTP 服务，暴露 `/metrics` 端点，Prometheus 抓取后即可存储和查询。Grafana 可以通过 Prometheus 数据源创建仪表盘。

```yaml
# prometheus.yml 配置示例
scrape_configs:
  - job_name: 'rust-app'
    static_configs:
      - targets: ['localhost:9090']
    scrape_interval: 15s
```

```bash
# 手动查看指标输出
curl http://localhost:9090/metrics
```

输出格式为标准 Prometheus 文本格式：

```text
# HELP http_requests_total HTTP 请求总数
# TYPE http_requests_total counter
http_requests_total{method="GET",path="/api/users",status="200"} 153
http_requests_total{method="POST",path="/api/orders",status="201"} 42
# HELP active_connections 当前活跃连接数
# TYPE active_connections gauge
active_connections 12
# HELP http_request_duration_seconds HTTP 请求耗时分布
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{method="GET",path="/api/users",le="0.005"} 100
http_request_duration_seconds_bucket{method="GET",path="/api/users",le="0.01"} 140
http_request_duration_seconds_sum{method="GET",path="/api/users"} 0.85
http_request_duration_seconds_count{method="GET",path="/api/users"} 153
```

C++ 对照：prometheus-cpp 需要手动注册 `Registry`、创建 `Family`、管理指标对象生命周期，且线程安全需要手动注意。Rust 的 `metrics` 门面将指标注册和管理隐藏在宏背后，`metrics-exporter-prometheus` 一键启动 HTTP 端点，代码量显著少于 C++。

## 6. 错误链与上下文传播

### 6.1 thiserror 与 anyhow 分工

Rust 错误处理的两个核心 crate 分工明确：

- **`thiserror`**：用于库 crate 定义自定义错误类型。通过 derive 宏为枚举实现 `std::error::Error`，支持 `#[error("...")]` 格式化消息和 `#[from]` 自动转换。
- **`anyhow`**：用于应用 crate 的顶层错误处理。提供 `anyhow::Result<T>` 和 `anyhow::Error`，支持链式上下文（`.context()`）和向下转换。

```toml
# Cargo.toml
[dependencies]
thiserror = "1"
anyhow = "1"
```

```rust
// 库 crate：用 thiserror 定义结构化错误
use thiserror::Error;

#[derive(Error, Debug)]
pub enum DatabaseError {
    #[error("数据库连接失败: {0}")]
    ConnectionFailed(#[from] std::io::Error),

    #[error("查询超时，SQL: {sql}")]
    QueryTimeout { sql: String },

    #[error("记录不存在: id={id}")]
    NotFound { id: u64 },
}

// 应用 crate：用 anyhow 添加上下文
use anyhow::{Context, Result};

fn load_user(id: u64) -> Result<User> {
    let user = db::find_user(id)
        .with_context(|| format!("加载用户失败: id={}", id))?;
    Ok(user)
}

fn main() -> Result<()> {
    match load_user(42) {
        Ok(user) => println!("用户: {:?}", user),
        Err(e) => {
            // 打印完整错误链
            eprintln!("错误: {}", e);
            for (i, cause) in e.chain().enumerate() {
                eprintln!("  原因 {}: {}", i + 1, cause);
            }
        }
    }
    Ok(())
}
```

错误链输出示例：

```text
错误: 加载用户失败: id=42
  原因 1: 加载用户失败: id=42
  原因 2: 查询超时，SQL: SELECT * FROM users WHERE id = 42
  原因 3: Connection refused (os error 111)
```

### 6.2 错误上下文与日志关联

将错误链与 tracing span 结合，可以在日志中同时看到错误原因和请求上下文：

```rust
use tracing::{error, info_span};
use anyhow::{Context, Result};

#[tracing::instrument(skip_all, fields(user_id = %user_id))]
fn process_user_order(user_id: u64, order_id: u64) -> Result<()> {
    let user = load_user(user_id)
        .with_context(|| format!("处理订单时加载用户失败: order_id={}", order_id))?;

    let order = load_order(order_id)
        .with_context(|| format!("加载订单失败: user_id={}", user_id))?;

    // ... 业务逻辑 ...
    Ok(())
}

fn main() -> Result<()> {
    if let Err(e) = process_user_order(42, 1001) {
        // error! 宏的 %e 会显示错误消息，
        // ?e 会显示 Debug 格式（含完整链），
        // span 中的 user_id 自动附加
        error!(error = ?e, "订单处理失败");
    }
    Ok(())
}
```

输出的 JSON 日志中会包含 `user_id: 42`（来自 span）、完整错误链（来自 `?e`），以及 `target`、`timestamp` 等元数据。运维人员可以通过 `user_id` 或错误消息快速检索，通过错误链定位根因。

C++ 对照：C++ 中错误链通常通过 `std::nested_exception` 或自定义异常类的 `cause` 成员实现，但标准库没有统一的上下文附加机制。`anyhow::Context` 的 `.with_context()` 是 Rust 独有的优雅设计——它在 `?` 传播错误时自动包装上下文，无需在每个函数中手动 `try/catch` 再 rethrow。

| 查询点 | 速答 |
| --- | --- |
| tracing 三件套 | `tracing`（宏）+ `tracing-subscriber`（输出）+ 可选 `tracing-opentelemetry` |
| 事件与字段 | `info!(user_id = %id, "登录成功")`；`%` 用 Display，`?` 用 Debug |

## 8. 常见坑与本节小结

### 常见坑

1. **忘记初始化 tracing subscriber**：`tracing::info!` 等宏在没有注册 subscriber 时静默丢弃所有事件。必须在 `main` 开头调用 `tracing_subscriber::fmt().init()` 或等效配置。
2. **span guard 跨 await 导致死锁**：`let _guard = span.enter()` 返回的 guard 是 `!Send` 的，不能跨 `.await` 点持有。异步函数中应使用 `.instrument(span)` 而非手动 `enter()`。
3. **`RUST_LOG` 未设置时默认级别**：`EnvFilter::from_default_env()` 在 `RUST_LOG` 未设置时默认级别为 `error`，会丢失 `info` 日志。应使用 `EnvFilter::try_from_default_env().unwrap_or_else(|_| EnvFilter::new("info"))`。
4. **metrics 标签值高基数问题**：将 `user_id`、`request_id` 等高基数值作为 label 会导致 Prometheus 内存爆炸。label 应只用于低基数维度（method、path、status_code）。
5. **`anyhow` 在库 crate 中滥用**：`anyhow::Error` 丢失了具体错误类型信息，库 crate 的公开 API 应使用 `thiserror` 定义的具体错误枚举，`anyhow` 仅限应用顶层和测试。
6. **JSON 日志中的 span 字段为空**：如果 event 发生在 span 之外，`span` 字段为空。确保关键操作被 `#[instrument]` 或 `info_span!` 包裹。
7. **tracing 与 log 混用导致日志丢失**：依赖的库 crate 可能使用 `log` 宏，需要 `tracing-log` crate 的 `LogTracer` 将 `log` 事件桥接到 tracing subscriber。

### 本节小结

Rust 可观测性生态以 `tracing` 为核心，统一了结构化日志和分布式追踪两个领域。`log` 门面适用于简单场景，`tracing` 的 span/event 模型为异步代码提供了自动上下文传播——这是 C++ 生态需要手动串联日志和追踪才能实现的能力（可参考《../../01-C++技术体系/15-中间件与微服务/03-异步日志与Protobuf.md》中 C++ 异步日志的实现）。`tracing-subscriber` 的 Layer 机制支持控制台文本、JSON 文件、OpenTelemetry 等多输出层组合。`metrics` 门面 + `metrics-exporter-prometheus` 一键暴露 `/metrics` 端点，对接 Prometheus/Grafana。错误处理通过 `thiserror`（库定义结构化错误）+ `anyhow`（应用添加上下文链）分工，与 tracing span 结合后可在日志中同时看到请求上下文和完整错误根因。核心原则：异步项目直接用 tracing，不要混用 log；指标 label 控制低基数；库用 thiserror，应用用 anyhow。
