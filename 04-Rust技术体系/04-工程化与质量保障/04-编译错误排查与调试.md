## 1. Rust 编译错误哲学与 C++ 对照

### 1.1 编译期保证 vs 运行期崩溃

Rust 的核心设计哲学是"把错误从运行期提前到编译期"。C++ 中大量在运行时才暴露的问题（空指针解引用、悬垂引用、数据竞争、use-after-free），在 Rust 中由借用检查器、类型系统和所有权机制在编译期拦截。这意味着 Rust 开发者会面对更多编译错误，但换来的是运行期崩溃的大幅减少。

| 问题类型 | C++ 表现 | Rust 表现 |
|----------|----------|-----------|
| 悬垂引用 | 运行时段错误（偶发，难复现） | 编译期 lifetime 错误 |
| use-after-free | 运行时内存破坏（Valgrind 才能发现） | 编译期 moved value 错误 |
| 数据竞争 | 运行时偶发错误（TSan 才能发现） | 编译期 Send/Sync 错误 |
| 空指针 | 运行时段错误 | 编译期 Option 强制处理 |
| 未初始化变量 | 运行时未定义行为 | 编译期错误（必须初始化） |
| 整数溢出 | 运行时错误（Release 下静默回绕） | Debug 下 panic，Release 下回绕 |

C++ 开发者转向 Rust 时最大的心理障碍是"编译不过"的挫败感。但需要认识到：每一个编译错误都是在避免一个潜在的生产事故。C++ 中用 Valgrind（可参考《../../01-C++技术体系/07-调试与测试/02-Valgrind内存检测.md》）和 TSan 花几天才能定位的内存问题，Rust 在编译时就拒绝了。

### 1.2 错误信息结构与阅读法

Rust 编译器的错误信息结构高度标准化，每条错误包含：错误码（如 `E0382`）、错误级别（error/warning/help/note）、错误位置（文件:行:列）、错误描述、源代码标注、可能的修复建议。阅读顺序建议：

1. **先看错误描述行**：理解核心问题
2. **再看源代码标注**：`^` 指向的具体位置
3. **然后看 `help:` 和 `note:`**：编译器给出的修复方向
4. **最后看错误码**：`rustc --explain E0382` 获取详细文档

典型错误信息示例：

```text
error[E0382]: borrow of moved value: `s`
 --> src/main.rs:4:20
  |
2 |     let s = String::from("hello");
  |         - move occurs because `s` has type `String`, which does not implement the `Copy` trait
3 |     let s2 = s;
  |              - value moved here
4 |     println!("{}", s);
  |                    ^ value borrowed here after move
  |
  = note: this error originates in the macro `$crate::format_args` which comes from the expansion of `println!` (in Nightly builds, run with -Z macro-backtrace for more info)
help: consider cloning the value if the performance cost is acceptable
  |
3 |     let s2 = s.clone();
  |               ++++++++
```

C++ 对照：C++ 编译器（GCC/Clang）的错误信息在模板相关报错时极其冗长且难以定位（"template error from hell"）。Rust 的错误信息经过精心设计，每条都有明确的错误码和修复建议，且 `rustc --explain` 提供详细文档。这是 Rust 工具链相比 C++ 的显著优势。

## 2. 借用检查器高频报错逐条翻译

### 2.1 cannot borrow as mutable

**错误信息**：

```text
error[E0596]: cannot borrow `*v` as mutable, as it is behind a `&` reference
 --> src/main.rs:3:5
  |
2 | fn push_item(v: &Vec<i32>) {
  |               - help: consider changing this to be a mutable reference: `&mut Vec<i32>`
3 |     v.push(1);
  |     ^^^^^^^^^^ `v` is a `&` reference, so the data it refers to cannot be borrowed as mutable
```

**原因**：通过不可变引用 `&T` 调用了需要 `&mut self` 的方法（如 `Vec::push`）。不可变引用承诺不修改数据，而 `push` 需要修改。

**修复代码**：

```rust
// 错误：不可变引用调用修改方法
fn push_item_wrong(v: &Vec<i32>) {
    // v.push(1); // 编译错误 E0596
}

// 修复：改为可变引用
fn push_item_fixed(v: &mut Vec<i32>) {
    v.push(1);
}

// 或者使用内部可变性（Cell/RefCell），但需谨慎
use std::cell::RefCell;
fn push_item_with_cell(v: &RefCell<Vec<i32>>) {
    v.borrow_mut().push(1);
}
```

**C++ 对照**：等价于在 C++ 中对 `const vector<int>&` 调用 `push_back`，编译器会报 "passing 'const vector<int>' as 'this' argument discards qualifiers"。Rust 的错误信息更明确地指出了修复方向（改为 `&mut`）。

### 2.2 use of moved value

**错误信息**：

```text
error[E0382]: use of moved value: `s`
 --> src/main.rs:5:20
  |
3 |     let s = String::from("hello");
  |         - move occurs because `s` has type `String`, which does not implement the `Copy` trait
4 |     let s2 = s;
  |              - value moved here
5 |     println!("{}", s);
  |                    ^ value used here after move
```

**原因**：`String` 没有实现 `Copy` trait，赋值 `let s2 = s` 发生了所有权移动（move），`s` 不再有效。这是 Rust 所有权系统的核心规则。

**修复代码**：

```rust
fn main() {
    let s = String::from("hello");

    // 方案一：clone（深拷贝，有性能开销）
    let s2 = s.clone();
    println!("s={}, s2={}", s, s2);

    // 方案二：使用引用（不转移所有权）
    let s3 = &s;
    println!("s={}, s3={}", s, s3);

    // 方案三：对于实现 Copy 的类型（i32、bool 等），直接赋值即可
    let x = 42;
    let y = x; // Copy，x 仍然有效
    println!("x={}, y={}", x, y);
}
```

**C++ 对照**：C++ 中 `std::string s2 = s` 默认是拷贝构造（深拷贝），`s` 仍然有效。Rust 默认移动语义，需要显式 `.clone()` 才能深拷贝。这避免了 C++ 中意外的深拷贝性能问题，但需要开发者有意识地管理所有权。C++11 的 `std::move(s)` 等价于 Rust 的默认行为，但 C++ 中 move 后对象仍可访问（处于有效但未指定状态），Rust 中 move 后变量完全不可用——编译器强制拦截。

### 2.3 lifetime 相关报错

**错误信息（最常见：函数返回引用）**：

```text
error[E0106]: missing lifetime specifier
 --> src/main.rs:1:30
  |
1 | fn longest(x: &str, y: &str) -> &str {
  |                              ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but the signature does not say whether it is borrowed from `x` or `y`
help: consider introducing a named lifetime parameter
  |
1 | fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
  |          ++++   +++           +++           +++
```

**原因**：函数返回引用时，编译器需要知道返回值的生命周期与哪个输入参数关联。如果不标注，编译器无法确定返回值是否悬垂。

**修复代码**：

```rust
// 修复：标注生命周期，说明返回值的生命周期与 x、y 中较短的一致
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

// 结构体中包含引用时也必须标注生命周期
struct Excerpt<'a> {
    part: &'a str,
}

impl<'a> Excerpt<'a> {
    fn level(&self) -> i32 { 3 }
}

// 生命周期省略规则：满足以下条件时编译器自动推断，无需手动标注
// 1. 每个输入引用都有独立生命周期
// 2. 只有一个输入引用时，输出引用的生命周期等于它
// 3. 有 &self 或 &mut self 时，输出引用的生命周期等于 self 的
fn first_word(s: &str) -> &str { // 自动省略，等价于 fn first_word<'a>(s: &'a str) -> &'a str
    &s[..s.find(' ').unwrap_or(s.len())]
}
```

**C++ 对照**：C++ 中没有生命周期概念，返回引用完全依赖开发者自觉。`const string& longest(const string& x, const string& y)` 可以编译通过，但如果返回了局部变量的引用，运行时才会崩溃（悬垂引用）。Rust 的生命周期标注是编译期的悬垂引用防护，虽然增加了语法复杂度，但从机制上杜绝了这类 bug。

### 2.4 object safety 报错

**错误信息**：

```text
error[E0038]: the trait `MyTrait` cannot be made into an object
 --> src/main.rs:9:16
  |
9 | fn process(t: &dyn MyTrait) {
  |                ^^^^^^^^^^^^ `MyTrait` cannot be made into an object
  |
note: for a trait to be "object safe" it needs to allow building a vtable to allow the call to be resolvable dynamically; for more information visit <https://doc.rust-lang.org/reference/items/traits.html#object-safety>
 --> src/main.rs:2:8
  |
2 |     fn generic<T>(&self, x: T);
  |        ^^^^^^^ this trait cannot be made into an object...
  |
  = note: ...because method `generic` has generic type parameters
```

**原因**：`dyn Trait`（trait object）需要在运行时通过 vtable 分发方法，但泛型方法在编译期为每个类型生成单独实例，无法放入 vtable。因此包含泛型方法的 trait 不是 object safe 的，不能用作 `dyn Trait`。

**修复代码**：

```rust
// 错误：包含泛型方法的 trait 不能做 trait object
trait NotObjectSafe {
    fn generic<T>(&self, x: T); // 泛型方法 → 不是 object safe
}

// 修复方案一：将泛型参数移到 trait 级别
trait ObjectSafeGeneric<T> {
    fn process(&self, x: T);
}

// 修复方案二：使用 Box<dyn Any> 接受任意类型（运行时向下转换）
trait ObjectSafeAny {
    fn process(&self, x: Box<dyn std::any::Any>);
}

// 修复方案三：如果不需要动态分发，直接用泛型函数（静态分发）
fn process_generic<T: MyTrait>(t: &T) {
    // 编译期单态化，无 vtable 开销
}
```

**C++ 对照**：C++ 中虚函数可以是模板吗？不行——C++ 标准规定虚函数不能是模板，原因与 Rust 相同（无法为每个类型生成 vtable 条目）。但 C++ 编译器的报错信息通常是 "templates may not be 'virtual'"，不如 Rust 的错误信息详细。Rust 明确区分了"trait 可以用于泛型约束（静态分发）"和"trait 可以用于 dyn（动态分发）"两种用法，object safety 只限制后者。

## 3. trait bound 报错阅读法

### 3.1 缺失 trait 实现

**错误信息**：

```text
error[E0277]: `MyStruct` doesn't implement `Debug`
 --> src/main.rs:7:20
  |
7 |     println!("{:?}", s);
  |                    ^ `MyStruct` cannot be formatted using `{:?}`
  |
  = help: the trait `Debug` is not implemented for `MyStruct`
  = note: add `#[derive(Debug)]` to `MyStruct` or manually `impl Debug for MyStruct`
```

**原因**：`{:?}` 格式化需要类型实现 `Debug` trait，而 `MyStruct` 没有实现。Rust 不会自动为自定义类型实现任何 trait（除了编译器内置的少数），必须显式派生或手动实现。

**修复代码**：

```rust
// 修复方案一：derive 派生（最常用）
#[derive(Debug)]
struct MyStruct {
    field: i32,
}

// 修复方案二：手动实现（需要自定义格式时）
use std::fmt;
struct MyStructManual {
    field: i32,
}
impl fmt::Debug for MyStructManual {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        f.debug_struct("MyStructManual")
            .field("field", &self.field)
            .finish()
    }
}
```

**C++ 对照**：C++ 中 `std::cout << s` 需要类型实现 `operator<<`，未实现时报错 "no match for 'operator<<'"。Rust 的 `Debug` 与 C++ 的 `operator<<` 对应，但 Rust 通过 derive 宏可以自动生成，C++ 通常需要手动编写或使用第三方库（如 `fmt`）。

### 3.2 泛型约束不满足

**错误信息**：

```text
error[E0277]: the trait bound `T: Ord` is not satisfied
 --> src/main.rs:2:12
  |
2 | fn max<T>(a: T, b: T) -> T {
  |    ---      ^ required by this bound in `max`
3 |     if a > b { a } else { b }
  |           ^ the trait `Ord` is not implemented for `T`
  |
help: consider restricting type parameter `T`
  |
2 | fn max<T: std::cmp::Ord>(a: T, b: T) -> T {
  |           ++++++++++++++
```

**原因**：`>` 运算符需要类型实现 `Ord` trait，但泛型参数 `T` 没有约束。Rust 的运算符都是 trait 的语法糖，泛型函数必须显式声明所需的 trait bound。

**修复代码**：

```rust
// 修复：添加 trait bound
use std::cmp::Ord;
fn max<T: Ord>(a: T, b: T) -> T {
    if a > b { a } else { b }
}

// 多个 bound 用 + 连接
fn process<T: Clone + Debug + Send>(x: T) {
    // ...
}

// where 子句：bound 较多时更清晰
fn complex_process<T, U>(a: T, b: U)
where
    T: Clone + Debug + Send,
    U: PartialEq + Default,
{
    // ...
}
```

**C++ 对照**：C++ 模板中 `a > b` 不需要显式约束，编译器在实例化时才检查。这导致 C++ 模板报错信息极其冗长（错误出现在模板定义处，但实际原因在调用处）。Rust 的 trait bound 在函数定义处就约束了参数能力，报错信息精准指向定义处，且 C++20 的 concepts 正是在向 Rust 的 trait bound 学习。

## 4. 调试工具：rust-gdb 与 rust-lldb

### 4.1 rust-gdb 基本用法

`rust-gdb` 是 GDB 的包装脚本，自动加载 Rust 调试插件（pretty-printer），使得 Rust 类型（`String`、`Vec`、`Option`、`Result` 等）在 GDB 中以可读格式显示，而非原始内存布局。

```bash
# 编译时包含调试信息（debug profile 默认包含，release 需手动设置）
cargo build

# 启动 rust-gdb
rust-gdb target/debug/my_app

# 常用命令
(gdb) break src/main.rs:42    # 在指定行打断点
(gdb) break my_crate::module::function_name  # 在函数入口打断点
(gdb) run                       # 运行程序
(gdb) next                      # 单步跳过（不进入函数）
(gdb) step                      # 单步进入（进入函数）
(gdb) print variable_name       # 打印变量（Rust 类型自动美化）
(gdb) print vec.len()           # 调用方法（需启用）
(gdb) bt                        # 查看调用栈
(gdb) continue                  # 继续运行
(gdb) watch variable            # 数据断点（变量被修改时中断）
```

`rust-gdb` 的 pretty-printer 效果对比：

```text
# 没有 rust-gdb 插件时（原始 GDB）
(gdb) print s
$1 = {buf = {ptr = {pointer = 0x7ffff000, _marker = ...}, cap = 5, ...}, len = 5}

# 使用 rust-gdb 后
(gdb) print s
$1 = "hello"

(gdb) print v
$2 = Vec<i32>(len=3, cap=4) = {1, 2, 3}

(gdb) print opt
$3 = Some(42)
```

### 4.2 与 C++ GDB 调试对照

Rust 调试与 C++ 调试的核心差异（可参考《../../01-C++技术体系/07-调试与测试/01-GDB程序调试.md》中 C++ GDB 的详细用法）：

| 特性 | C++ GDB | Rust rust-gdb |
|------|---------|---------------|
| 字符串显示 | `std::string` 需 pretty-printer | `String`/`&str` 自动显示为文本 |
| 容器显示 | `std::vector` 需 pretty-printer | `Vec` 自动显示长度和元素 |
| 枚举显示 | `enum class` 显示枚举值 | `Option`/`Result` 显示 `Some(x)`/`Ok(x)` |
| 函数名 | C++ name mangling（`_ZN...`） | Rust name mangling（`_R...`），rust-gdb 自动 demangle |
| 断点设置 | `break Class::method` | `break crate::module::function` |
| 异步代码 | 无特殊支持 | tokio 任务需 `tokio-console` 辅助 |
| 多线程 | `thread apply all bt` | 同左，Rust 线程名通过 `std::thread::Builder::name` 设置 |

对于异步代码调试，GDB 在 `.await` 点的单步体验不够理想（future 被编译器转换为状态机）。推荐使用 `tokio-console`（tokio 生态的异步调试工具）或在关键位置加 `tracing::info!` 日志辅助定位。

macOS 用户使用 `rust-lldb`，用法与 `rust-gdb` 类似，但命令语法有差异（`b` 设断点、`p` 打印、`bt` 调用栈等基本一致）。

## 5. 编译器提示与 cargo fix

### 5.1 rustc 错误码与解释

每个 Rust 编译错误都有唯一的错误码（如 `E0382`、`E0596`、`E0277`），通过 `rustc --explain <错误码>` 可以查看详细解释、错误原因和修复示例：

```bash
# 查看错误码详细解释
rustc --explain E0382

# 输出示例（节选）：
# E0382
# -------
# A value was used after it was moved.
#
# Erroneous code example:
# ...
```

常用错误码速查表：

| 错误码 | 含义 | 常见场景 |
|--------|------|----------|
| E0382 | use of moved value | 所有权移动后继续使用 |
| E0596 | cannot borrow as mutable | 不可变引用调用修改方法 |
| E0502 | cannot borrow as mutable because also borrowed as immutable | 同时存在可变和不可变借用 |
| E0106 | missing lifetime specifier | 返回引用未标注生命周期 |
| E0038 | trait not object safe | 泛型方法的 trait 用于 dyn |
| E0277 | trait bound not satisfied | 缺失 trait 实现 |
| E0308 | mismatched types | 类型不匹配 |
| E0425 | cannot find value in scope | 未导入或未定义 |
| E0599 | no method named | 类型没有该方法（可能未导入 trait） |
| E0605 | non-primitive cast | 不合法的类型转换 |

### 5.2 cargo fix 自动修复

`cargo fix` 可以自动修复编译器警告和部分可机械修复的错误。它基于 rustc 的 `MachineApplicable` 建议，自动应用修复补丁。

```bash
# 自动修复当前 crate 的所有可修复警告
cargo fix

# 修复所有 target（包括测试、示例、bench）
cargo fix --all-targets

# 修复整个 workspace
cargo fix --workspace

# 允许修改（默认是 dry-run 模式，需要 --allow-dirty 或 --allow-staged）
cargo fix --allow-dirty

# 升级 edition 时自动修复兼容性问题
cargo fix --edition
```

`cargo fix` 能自动修复的典型问题：

- 未使用的导入（`unused_imports`）→ 自动删除
- 需使用 `dyn` 的 trait object（`bare_trait_objects`）→ 自动添加 `dyn`
- 需使用 `?` 运算符的 `try!` 宏 → 自动替换
- 过时的 API 用法 → 自动替换为新 API
- 缺失的 `#[derive]` → 部分场景自动添加

C++ 对照：C++ 中没有等价的自动修复工具。Clang-Tidy 可以提供修复建议（`-fix`），但覆盖范围远小于 `cargo fix`，且需要手动配置检查项。Rust 的 `cargo fix` 与编译器深度集成，所有 `MachineApplicable` 级别的建议都能自动应用，是 Rust 工具链的一大优势。

## 6. 编译时间优化

### 6.1 workspace 拆分与增量编译

Rust 编译慢是社区公认的痛点，主要原因是：泛型单态化（monomorphization）产生大量代码、LLVM 优化耗时、增量编译的粒度问题。优化策略从易到难：

**策略一：合理设置 profile**

```toml
# Cargo.toml
[profile.dev]
opt-level = 0        # dev 默认不优化，编译快
debug = 1            # 只限行号调试信息，比 full 快
incremental = true   # 增量编译（默认开启）

[profile.release]
opt-level = 3
lto = "thin"         # thin LTO 比 full 快，性能损失很小
codegen-units = 16   # 并行编译单元（release 默认 1，设为 16 加快编译）
```

**策略二：workspace 拆分**

将大 crate 拆分为多个小 crate，每个 crate 独立编译。修改一个 crate 时只需重编译它和依赖它的 crate，未修改的 crate 复用缓存。

```toml
# 根 Cargo.toml
[workspace]
members = [
    "crates/core",       # 核心逻辑，最稳定
    "crates/network",    # 网络层
    "crates/storage",    # 存储层
    "crates/api",        # API 层，最常修改
    "apps/server",       # 最终二进制
]
```

拆分原则：将稳定的、不常修改的代码放到独立 crate（如 `core`），将频繁修改的代码放到依赖链末端（如 `api`）。这样修改 `api` 时只需重编译 `api` 和 `server`，`core`/`network`/`storage` 都复用缓存。

### 6.2 cranelift 与 sccache

**策略三：cranelift 后端（nightly）**

Rust 编译器默认使用 LLVM 作为后端，LLVM 优化耗时较长。Cranelift 是一个更快的代码生成后端，虽然生成的代码运行效率低于 LLVM，但编译速度显著提升。目前仅在 nightly 可用：

```bash
# 安装 cranelift 后端
rustup component add rustc-codegen-cranelift-preview --toolchain nightly

# 使用 cranelift 编译
cargo +nightly build -Zcodegen-backend=cranelift
```

对于日常开发调试（不关心运行性能），cranelift 可以将编译时间减少 30%-50%。

**策略四：sccache 分布式缓存**

`sccache` 是 Mozilla 开发的编译缓存工具，支持将编译结果缓存到本地磁盘、S3、Redis 等，跨机器共享缓存。CI 环境中效果显著：

```bash
# 安装
cargo install sccache

# 设置环境变量
export RUSTC_WRAPPER=sccache

# 配置缓存后端（本地磁盘）
export SCCACHE_DIR=/path/to/cache

# 配置 S3 后端（团队共享）
export SCCACHE_BUCKET=my-rust-cache
export SCCACHE_REGION=us-east-1

# 查看缓存统计
sccache --show-stats
```

C++ 对照：C++ 编译加速的常用工具是 `ccache`（本地缓存）和 `distcc`（分布式编译）。Rust 的 `sccache` 功能上等价于 `ccache`，但原生支持 S3/Redis 等远程后端，且与 cargo 集成更简单（只需设置 `RUSTC_WRAPPER`）。C++ 的 `distcc` 分布式编译在 Rust 中没有直接对应，但 `codegen-units` 的并行编译和 workspace 拆分部分弥补了这一点。

## 7. 快速参考卡片

| 查询点 | 速答 |
| --- | --- |
| 快速反馈 | `cargo check`（不生成代码，最快）/ `cargo check --all-targets` |
| 自动修 | `cargo fix --allow-dirty`、`clippy --fix` 自动应用建议 |
| 静态检查 | `cargo clippy -- -D warnings`（CI 必开）；`cargo fmt` 统一风格 |

## 8. 常见坑与本节小结

### 常见坑

1. **修改代码后编译错误指向旧行号**：增量编译有时会导致错误位置偏移。运行 `cargo clean` 后重新编译可以解决，但会丢失增量缓存。
2. **`cargo fix` 误改代码**：`cargo fix` 的自动修复基于编译器建议，极少数情况下可能引入语义变化。运行后应 `git diff` 检查修改内容，不要盲目提交。
3. **release 模式下调试信息缺失**：`cargo build --release` 默认不包含调试信息，GDB 中无法看到变量值。需要在 `Cargo.toml` 中设置 `[profile.release] debug = 1` 或使用 `cargo build --profile=dev-with-opt`。
4. **异步代码单步调试混乱**：tokio 的 future 被编译器转换为状态机，GDB 单步在 `.await` 点会跳入大量生成代码。建议在 `.await` 前后加日志，或使用 `tokio-console`。
5. **`rustc --explain` 在某些安装中不可用**：部分最小化安装的 Rust 工具链不包含错误文档。运行 `rustup component add rust-docs` 安装。
6. **trait 方法未导入导致 "no method named"**：Rust 的 trait 方法需要 `use TraitName;` 才能调用。报错 `E0599 no method named 'xxx'` 时，先检查是否导入了对应的 trait。
7. **lifetime 标注过度复杂**：初学者常试图为每个引用都标注生命周期。实际上 90% 的场景满足生命周期省略规则，无需手动标注。只有编译器报错 `E0106` 时才需要添加。

### 本节小结

Rust 编译错误的核心价值是"把运行期崩溃提前到编译期"——C++ 中需要 Valgrind（可参考《../../01-C++技术体系/07-调试与测试/02-Valgrind内存检测.md》）和 TSan 花几天定位的内存问题，Rust 在编译时就拒绝了。借用检查器的四大高频报错（`cannot borrow as mutable`、`use of moved value`、`missing lifetime`、`not object safe`）都有明确的错误码和修复模式，掌握后可以快速定位。trait bound 报错（`E0277`）是泛型编程的核心，需要理解"运算符即 trait"的设计。调试工具 `rust-gdb`/`rust-lldb` 自动美化 Rust 类型显示，与 C++ GDB（可参考《../../01-C++技术体系/07-调试与测试/01-GDB程序调试.md》）用法相似但体验更好。`cargo fix` 自动修复可机械修复的警告，`rustc --explain` 提供错误码详细文档。编译时间优化通过 profile 调优、workspace 拆分、cranelift 后端、sccache 缓存四层策略逐步改善。核心心态：每个编译错误都是在避免一个生产事故，拥抱编译器而非对抗它。
