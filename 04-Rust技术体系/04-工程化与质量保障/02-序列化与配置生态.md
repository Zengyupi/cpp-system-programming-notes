## 1. serde 架构总览

### 1.1 Serialize/Deserialize 双 trait 模型

serde 是 Rust 序列化生态的事实标准，其核心设计是两个对称的 trait：`Serialize` 和 `Deserialize`。任何类型只要实现这两个 trait，就能自动支持所有 serde 兼容的数据格式（JSON、YAML、TOML、MessagePack、Bincode 等）。这种"一次实现，多格式复用"的架构与 C++ 中为每种格式单独写序列化函数的做法形成鲜明对比。

```rust
use serde::{Serialize, Deserialize};

#[derive(Serialize, Deserialize, Debug)]
pub struct User {
    pub id: u64,
    pub name: String,
    pub email: Option<String>,
    pub roles: Vec<String>,
}
```

`derive` 宏自动为结构体生成 `Serialize`/`Deserialize` 实现，无需手写任何序列化逻辑。对于枚举，serde 同样支持派生：

```rust
#[derive(Serialize, Deserialize, Debug)]
#[serde(tag = "type", content = "data")]
pub enum Event {
    Login { user_id: u64, ip: String },
    Logout { user_id: u64 },
    Message { from: u64, to: u64, text: String },
}
```

serde 的内部架构分为三层：

| 层 | 角色 | 对应 C++ 概念 |
|----|------|---------------|
| `Serialize`/`Deserialize` trait | 数据类型侧接口 | 自定义 `serialize()` 虚函数 |
| `Serializer`/`Deserializer` trait | 格式侧接口 | JSON writer/reader 抽象 |
| 数据格式 crate（serde_json 等） | 具体格式实现 | RapidJSON、yaml-cpp 等库 |

C++ 对照：C++ 中没有统一的序列化抽象。使用 RapidJSON 时需要为每个类型写 `Writer` 调用，使用 Protobuf 时需要定义 `.proto` 文件，使用 yaml-cpp 时又要写 `YAML::convert` 特化。serde 通过 trait 泛型将"类型如何序列化"与"序列化成什么格式"彻底解耦，新增一种格式只需要实现 `Serializer`/`Deserializer`，所有已有类型自动支持。

### 1.2 derive 宏与属性定制

serde 的 derive 宏支持大量 `#[serde(...)]` 属性，用于精细控制序列化行为。最常用的属性如下：

| 属性 | 作用 | 示例 |
|------|------|------|
| `rename_all` | 字段名批量转换风格 | `#[serde(rename_all = "camelCase")]` |
| `rename` | 单字段重命名 | `#[serde(rename = "userName")]` |
| `skip_serializing_if` | 条件跳过序列化 | `#[serde(skip_serializing_if = "Option::is_none")]` |
| `default` | 反序列化缺失时用默认值 | `#[serde(default)]` |
| `flatten` | 扁平化嵌套结构体 | `#[serde(flatten)]` |
| `tag`/`content` | 枚举序列化格式 | `#[serde(tag = "type")]` |
| `with` | 使用自定义模块序列化 | `#[serde(with = "chrono::serde::ts_seconds")]` |

```rust
use serde::{Serialize, Deserialize};

#[derive(Serialize, Deserialize, Debug)]
#[serde(rename_all = "camelCase")] // 所有字段转为 camelCase
pub struct ApiResponse<T> {
    pub code: i32,
    pub message: String,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub data: Option<T>,
    #[serde(default = "default_timestamp")]
    pub timestamp: i64,
}

fn default_timestamp() -> i64 {
    // 简化示例，实际应使用时间库
    1700000000
}

#[derive(Serialize, Deserialize, Debug)]
pub struct UserProfile {
    pub id: u64,
    #[serde(rename = "username")] // 单字段覆盖 rename_all
    pub name: String,
    #[serde(default)] // 缺失时用 Vec::default()
    pub tags: Vec<String>,
}
```

`skip_serializing_if = "Option::is_none"` 是最常用的属性之一，它确保 `None` 字段不出现在 JSON 输出中，减少冗余并兼容旧版本客户端。C++ 中通常需要手动判断 `if (value.has_value()) writer.Key(...)`，serde 将其声明式化。

## 2. 多格式支持：JSON/YAML/TOML

### 2.1 serde_json 用法与性能

`serde_json` 是 Rust 生态最常用的 JSON 库，提供零拷贝解析、`Value` 动态类型、流式序列化等能力。以 crates.io 最新稳定版为准。

```toml
# Cargo.toml
[dependencies]
serde = { version = "1", features = ["derive"] }
serde_json = "1"
```

```rust
use serde::{Serialize, Deserialize};
use serde_json::{json, Value};

#[derive(Serialize, Deserialize, Debug)]
struct User {
    id: u64,
    name: String,
}

fn main() -> Result<(), serde_json::Error> {
    // 序列化：结构体 -> JSON 字符串
    let user = User { id: 1, name: "Alice".to_string() };
    let json_str = serde_json::to_string(&user)?;
    println!("{}", json_str); // {"id":1,"name":"Alice"}

    // 美化输出
    let pretty = serde_json::to_string_pretty(&user)?;

    // 反序列化：JSON 字符串 -> 结构体
    let parsed: User = serde_json::from_str(&json_str)?;

    // 动态 Value：无需预定义结构体
    let v: Value = serde_json::from_str(r#"{"a":1,"b":[2,3]}"#)?;
    assert_eq!(v["a"], 1);
    assert_eq!(v["b"][0], 2);

    // json! 宏构造动态值
    let dynamic = json!({
        "code": 200,
        "data": { "items": [1, 2, 3] }
    });

    Ok(())
}
```

性能方面，serde_json 的零拷贝解析（`from_str` 配合 `#[serde(borrow)]`）可以避免字符串分配，在高频场景下显著优于 C++ RapidJSON 的 DOM 模式。对于超大 JSON 文件，使用 `serde_json::Deserializer` 的流式迭代器可以逐元素处理，无需一次性加载到内存。

### 2.2 serde_yaml 与 serde_toml

YAML 和 TOML 主要用于配置文件。`serde_yaml` 提供 YAML 1.2 支持，`toml` crate 提供 TOML 支持，两者都基于 serde 抽象，用法与 serde_json 几乎一致。

```toml
# Cargo.toml
[dependencies]
serde_yaml = "0.9"
toml = "0.8"
```

```rust
use serde::Deserialize;

#[derive(Deserialize, Debug)]
struct AppConfig {
    server: ServerConfig,
    database: DatabaseConfig,
}

#[derive(Deserialize, Debug)]
struct ServerConfig {
    host: String,
    port: u16,
}

#[derive(Deserialize, Debug)]
struct DatabaseConfig {
    url: String,
    max_connections: u32,
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // 从 YAML 字符串加载
    let yaml_str = r#"
server:
  host: 0.0.0.0
  port: 8080
database:
  url: "postgres://localhost/app"
  max_connections: 20
"#;
    let config: AppConfig = serde_yaml::from_str(yaml_str)?;

    // 从 TOML 字符串加载
    let toml_str = r#"
[server]
host = "0.0.0.0"
port = 8080

[database]
url = "postgres://localhost/app"
max_connections = 20
"#;
    let config2: AppConfig = toml::from_str(toml_str)?;

    Ok(())
}
```

格式选择建议：JSON 适合 API 通信和数据交换；YAML 适合人类编辑的复杂配置（支持注释、锚点引用）；TOML 适合简单配置（语法比 YAML 更严格，避免缩进歧义，Cargo.toml 本身就是 TOML）。

## 3. Protobuf 与 prost

### 3.1 prost 代码生成与基本用法

`prost` 是 Rust 生态最主流的 Protobuf 实现，它不使用 `protoc` 插件生成代码，而是纯 Rust 实现的 `.proto` 解析器，通过 `prost-build` 在 `build.rs` 中编译时生成 Rust 代码。以 crates.io 最新稳定版为准。

```toml
# Cargo.toml
[dependencies]
prost = "0.13"

[build-dependencies]
prost-build = "0.13"
```

```protobuf
// proto/user.proto
syntax = "proto3";

package user;

message User {
  uint64 id = 1;
  string name = 2;
  string email = 3;
  repeated string roles = 4;
}

message UserList {
  repeated User users = 1;
}
```

```rust
// build.rs
fn main() -> Result<(), Box<dyn std::error::Error>> {
    prost_build::compile_protos(&["proto/user.proto"], &["proto/"])?;
    Ok(())
}
```

```rust
// src/main.rs
pub mod user {
    include!(concat!(env!("OUT_DIR"), "/user.rs"));
}

use user::{User, UserList};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // 构造消息
    let user = User {
        id: 1,
        name: "Alice".to_string(),
        email: "alice@example.com".to_string(),
        roles: vec!["admin".to_string(), "user".to_string()],
    };

    // 序列化为二进制
    let bytes = user.encode_to_vec();
    println!("序列化后 {} 字节", bytes.len());

    // 反序列化
    let decoded = User::decode(bytes.as_slice())?;
    assert_eq!(decoded.name, "Alice");

    // 嵌套消息
    let list = UserList {
        users: vec![user],
    };
    let list_bytes = list.encode_to_vec();

    Ok(())
}
```

prost 生成的结构体是普通 Rust 结构体，字段直接公开，没有 C++ Protobuf 那种 `mutable_xxx()`/`set_xxx()` 访问器。`encode_to_vec()` 和 `decode()` 是 `prost::Message` trait 提供的方法，所有生成的消息类型都自动实现。

### 3.2 与 C++ Protobuf 对照

prost 与 C++ Protobuf 的核心差异对照（可交叉参考《../../01-C++技术体系/05-存储与序列化/03-Protobuf序列化协议.md》中 C++ 部分的详细讨论）：

| 特性 | C++ Protobuf | Rust prost |
|------|-------------|------------|
| 代码生成 | `protoc` + `grpc_cpp_plugin` | `prost-build` 纯 Rust 解析 |
| 消息类型 | 生成类，字段私有 | 生成结构体，字段公开 |
| 字段访问 | `user.name()` / `set_name()` | `user.name` 直接访问 |
|  repeated 字段 | `add_roles()` / `roles_size()` | `user.roles.push()` 直接操作 Vec |
| 序列化 | `user.SerializeToString(&s)` | `user.encode_to_vec()` |
| 反序列化 | `user.ParseFromString(s)` | `User::decode(&bytes)` |
| 未知字段 | 默认保留 | 默认丢弃（可配置） |
| 反射 | 完整反射 API | 有限反射（`prost-reflect` crate） |
| gRPC 集成 | `grpc++` 库 | `tonic` crate（基于 prost） |

prost 的设计哲学是"Rust 原生"——生成的结构体可以直接用 Rust 惯用法操作（`Vec::push`、结构体更新语法等），而不是通过 Protobuf 生成的访问器。这减少了学习成本，但也意味着 prost 不支持 Protobuf 的反射和动态消息功能（需要额外的 `prost-reflect` crate）。

对于 gRPC 服务，Rust 生态使用 `tonic` crate，它基于 prost 生成代码并提供异步 gRPC 服务端和客户端，与 C++ 的 `grpc++` 对应。

## 4. bincode 二进制序列化

### 4.1 紧凑二进制格式与配置

`bincode` 是 Rust 生态常用的紧凑二进制序列化格式，基于 serde 抽象，将数据序列化为无额外元数据的二进制流。适合网络传输、持久化存储、IPC 等对体积敏感的场景。以 crates.io 最新稳定版为准。

```toml
# Cargo.toml
[dependencies]
bincode = "1"
serde = { version = "1", features = ["derive"] }
```

```rust
use serde::{Serialize, Deserialize};
use bincode;

#[derive(Serialize, Deserialize, Debug, PartialEq)]
struct Packet {
    seq: u32,
    timestamp: u64,
    payload: Vec<u8>,
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let packet = Packet {
        seq: 42,
        timestamp: 1700000000,
        payload: vec![0xAB; 1024],
    };

    // 序列化：默认配置
    let bytes = bincode::serialize(&packet)?;
    println!("bincode: {} 字节", bytes.len()); // 4 + 8 + 8 + 1024 = 1044

    // 反序列化
    let decoded: Packet = bincode::deserialize(&bytes)?;
    assert_eq!(decoded, packet);

    // 自定义配置：使用大端序、限制最大长度（bincode 1.x DefaultOptions API）
    let config = bincode::config()
        .big_endian()
        .limit(10_000_000);
    let bytes_be = bincode::serialize_with_options(&packet, config)?;

    Ok(())
}
```

bincode 的输出格式是"结构体字段按定义顺序直接拼接"，没有字段名、没有类型标签、没有长度前缀（除了 `Vec`/`String` 等变长类型需要长度）。这使得它极其紧凑，但也意味着**不支持字段演进**——字段顺序或类型变更会导致反序列化失败。

### 4.2 适用场景与局限

| 场景 | 是否推荐 bincode | 原因 |
|------|-----------------|------|
| 同一程序内的缓存持久化 | 推荐 | 版本一致，无需兼容 |
| 同一团队内部的 RPC 通信 | 有条件推荐 | 需要严格管理版本升级 |
| 跨语言/跨团队通信 | 不推荐 | bincode 是 Rust 专属格式 |
| 需要向前/向后兼容 | 不推荐 | 无字段标识，不支持演进 |
| 存储到文件长期保存 | 不推荐 | 格式无自描述性，难以调试 |

bincode 的核心局限是**无自描述性和无版本兼容**。与 Protobuf 的字段编号机制不同，bincode 依赖字段顺序，新增字段必须追加到末尾且使用 `Option` 才能勉强兼容旧数据。对于需要长期演进的协议，应优先选择 Protobuf 或 JSON。

C++ 对照：bincode 类似于 C++ 中直接 `memcpy` 结构体到字节流，但 bincode 处理了变长类型（`Vec`、`String`）和端序问题，比裸 `memcpy` 安全。C++ 中更接近的是 Boost.Serialization 的二进制模式，但 Boost.Serialization 支持版本号，bincode 默认不支持。

## 5. 字段演进与兼容性

### 5.1 可选字段与默认值

在 JSON/YAML 等自描述格式中，字段演进的核心策略是"新增字段用 `Option` + `default`，删除字段保留为 `Option` 并忽略"。serde 的属性组合可以优雅处理：

```rust
use serde::{Serialize, Deserialize};

#[derive(Serialize, Deserialize, Debug)]
pub struct UserV2 {
    pub id: u64,
    pub name: String,

    // v2 新增字段：旧数据中不存在，用 default 填充
    #[serde(default)]
    pub age: u32,

    // v2 新增可选字段：旧数据中为 None
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub avatar_url: Option<String>,

    // v1 中有但 v2 废弃的字段：保留以兼容旧数据反序列化，
    // 但序列化时跳过，避免输出到新客户端
    #[serde(default, skip_serializing)]
    pub legacy_token: Option<String>,
}
```

这套策略的兼容矩阵：

| 操作 | 发送方 v1 | 发送方 v2 |
|------|-----------|-----------|
| 接收方 v1 | 正常 | v2 新增字段被忽略（serde 默认忽略未知字段） |
| 接收方 v2 | v2 新增字段用 default | 正常 |

serde 默认会忽略 JSON 中存在但结构体中未定义的字段（`deny_unknown_fields` 属性可以改为报错），这为向前兼容提供了基础。

### 5.2 字段重命名与版本迁移

当字段需要重命名时，使用 `#[serde(alias = "old_name")]` 可以同时接受新旧名称：

```rust
#[derive(Serialize, Deserialize, Debug)]
pub struct User {
    pub id: u64,
    // 序列化时输出 "username"，反序列化时接受 "username" 或 "name"
    #[serde(rename = "username", alias = "name")]
    pub name: String,
}
```

对于破坏性变更（类型改变、字段拆分/合并），推荐使用版本化包装结构：

```rust
#[derive(Serialize, Deserialize, Debug)]
#[serde(tag = "version")]
pub enum UserEnvelope {
    #[serde(rename = "1")]
    V1(UserV1),
    #[serde(rename = "2")]
    V2(UserV2),
}

// 读取时统一转换为最新版本
impl UserEnvelope {
    pub fn into_latest(self) -> UserV2 {
        match self {
            UserEnvelope::V1(v1) => UserV2 {
                id: v1.id,
                name: v1.name,
                age: 0,
                avatar_url: None,
                legacy_token: v1.token,
            },
            UserEnvelope::V2(v2) => v2,
        }
    }
}
```

C++ 对照：C++ 中字段演进通常靠手动写迁移函数或在 JSON 解析后做字段检查。serde 的 `alias`、`default`、`skip_serializing` 等属性将兼容策略声明式化，减少了迁移代码。Protobuf 的字段编号机制是另一种演进思路（可参考《../../01-C++技术体系/05-存储与序列化/03-Protobuf序列化协议.md》），它在二进制层面保证兼容，而 serde + JSON 的方案在文本层面更灵活。

## 6. 配置加载最佳实践

### 6.1 config crate 分层加载

`config` crate 提供分层配置加载能力，支持默认值、配置文件、环境变量、远程配置等多层合并。以 crates.io 最新稳定版为准。

```toml
# Cargo.toml
[dependencies]
config = "0.14"
serde = { version = "1", features = ["derive"] }
```

```rust
use config::{Config, File, Environment};
use serde::Deserialize;

#[derive(Debug, Deserialize, Clone)]
pub struct AppConfig {
    pub server: ServerConfig,
    pub database: DatabaseConfig,
    pub log: LogConfig,
}

#[derive(Debug, Deserialize, Clone)]
pub struct ServerConfig {
    pub host: String,
    pub port: u16,
    pub workers: usize,
}

#[derive(Debug, Deserialize, Clone)]
pub struct DatabaseConfig {
    pub url: String,
    pub max_connections: u32,
    pub timeout_secs: u64,
}

#[derive(Debug, Deserialize, Clone)]
pub struct LogConfig {
    pub level: String,
    pub file: Option<String>,
}

impl AppConfig {
    pub fn load() -> Result<Self, config::ConfigError> {
        let config = Config::builder()
            // 第 1 层：默认值
            .add_source(File::with_name("config/default").required(false))
            // 第 2 层：环境特定配置（dev/staging/prod）
            .add_source(File::with_name(&format!(
                "config/{}",
                std::env::var("RUN_ENV").unwrap_or_else(|_| "development".into())
            )).required(false))
            // 第 3 层：环境变量覆盖（前缀 APP_，分隔符 __）
            .add_source(Environment::with_prefix("APP").separator("__"))
            .build()?;

        config.try_deserialize()
    }
}
```

分层加载的优先级从低到高：默认值 < 环境配置文件 < 环境变量。环境变量 `APP_SERVER__PORT=9090` 会覆盖 `server.port`，这与 C++ 中常见的"配置文件 + 环境变量覆盖"模式一致，但 `config` crate 自动处理了类型转换和嵌套映射。

### 6.2 环境变量覆盖与校验

加载配置后，应进行运行时校验，确保配置值在合法范围内。可以在 `AppConfig` 上实现 `validate` 方法：

```rust
impl AppConfig {
    pub fn validate(&self) -> Result<(), String> {
        if self.server.port == 0 || self.server.port > 65535 {
            return Err(format!("无效端口: {}", self.server.port));
        }
        if self.server.workers == 0 {
            return Err("workers 不能为 0".into());
        }
        if self.database.max_connections == 0 {
            return Err("数据库最大连接数不能为 0".into());
        }
        if !matches!(self.log.level.as_str(),
            "trace" | "debug" | "info" | "warn" | "error")
        {
            return Err(format!("无效日志级别: {}", self.log.level));
        }
        Ok(())
    }
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let config = AppConfig::load()?;
    config.validate()?;
    println!("配置加载成功: {:?}", config);
    Ok(())
}
```

对于更复杂的校验，可以使用 `validator` crate 提供派生宏，但简单的手动 `validate` 方法通常足够且更透明。C++ 对照：C++ 中配置校验通常在读取后手动写 `if` 判断，Rust 的 `Result` 类型强制调用方处理校验失败，避免了 C++ 中常见的"校验失败但继续运行"问题。

## 7. 常见坑与本节小结

### 常见坑

1. **serde derive 忘记加 `features = ["derive"]`**：`serde` crate 的 derive 宏在默认 feature 中不启用，必须在 `Cargo.toml` 中显式声明 `serde = { version = "1", features = ["derive"] }`。
2. **bincode 跨版本不兼容**：bincode 1.x 和 2.x 的格式不兼容，且 2.x 的 API 有较大变化。长期存储的数据应锁定版本并记录格式配置。
3. **prost 生成代码找不到**：`include!(concat!(env!("OUT_DIR"), "/user.rs"))` 中的路径必须与 `prost-build` 生成的文件名一致。包名中的点会转为下划线，`user.v1` 生成 `user.v1.rs`。
4. **JSON 数字精度丢失**：`serde_json` 默认将 JSON 数字解析为 `f64` 或整数，超过 `i64` 范围的整数会丢失精度。需要大整数时使用 `serde_json::Number` 或字符串序列化。
5. **`deny_unknown_fields` 破坏向前兼容**：如果设置了 `#[serde(deny_unknown_fields)]`，发送方新增字段会导致接收方反序列化失败。除非明确需要严格校验，否则不要使用。
6. **配置文件路径问题**：`config` crate 的 `File::with_name` 是相对当前工作目录，不是相对可执行文件目录。部署时需注意工作目录设置，或使用绝对路径。

### 本节小结

Rust 序列化生态以 serde 为统一抽象层，通过 `Serialize`/`Deserialize` trait 实现"一次派生，多格式复用"。`serde_json` 用于 API 通信，`serde_yaml`/`toml` 用于配置文件，`prost` 用于 Protobuf 二进制协议（与 C++ Protobuf 对照可参考《../../01-C++技术体系/05-存储与序列化/03-Protobuf序列化协议.md》），`bincode` 用于紧凑二进制场景。字段演进通过 `Option` + `default` + `alias` + `skip_serializing` 属性组合实现，Protobuf 的字段编号机制是二进制层面的另一种演进思路。配置加载使用 `config` crate 实现默认值、环境配置文件、环境变量的分层合并，并配合手动 `validate` 方法确保配置合法性。核心原则：自描述格式（JSON/YAML）优先用于需要演进的接口，紧凑二进制（bincode）仅限同版本内部使用，跨语言协议选 Protobuf。
