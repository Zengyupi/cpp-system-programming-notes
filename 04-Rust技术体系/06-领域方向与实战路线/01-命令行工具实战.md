## 1. 为什么 Rust 适合写 CLI

### 1.1 单二进制与启动速度

Rust 编译产物是静态链接的单个 ELF/PE/Mach-O 可执行文件，无需运行时依赖。一个含 clap + regex 的 CLI 工具 release 构建后通常 3–8 MB，启动时间在毫秒级。

对照 Go 的 CLI 工具，Rust 二进制更小、冷启动更快；对照 Python 脚本，无需解释器和 venv，分发体验天差地别。

### 1.2 对照 C++：getopt 与 clap 的代差

C++ 生态中参数解析长期依赖 POSIX `getopt` / `getopt_long`，手写 switch-case 解析、手动维护 help 文本、子命令需要自己设计分发。第三方库如 `CLI11` 虽好但需要额外集成，且 C++ 的编译期反射能力有限，无法像 Rust derive 那样从结构体自动生成解析逻辑。

| 维度 | C++ getopt_long | Rust clap derive |
| --- | --- | --- |
| 定义方式 | 手写 option 数组 + switch | 结构体字段 + 派生宏 |
| help 文本 | 手动维护字符串 | 从 doc comment 自动生成 |
| 子命令 | 手动枚举分发 | enum 变体自动映射 |
| 类型转换 | atoi/strtol 手动处理 | 自动反序列化到目标类型 |
| 校验 | 手写 if-else | validator 属性声明式 |

## 2. clap derive 写参数解析

### 2.1 derive 宏与结构体定义

clap（以 crates.io 最新稳定版为准）的 derive API 让参数定义变成声明式的结构体标注。

```toml
[package]
name = "mini-cli"
version = "0.1.0"
edition = "2021"

[dependencies]
clap = { version = "4", features = ["derive"] }
```

```rust
use clap::Parser;

/// 一个示例 CLI 工具，演示 clap derive 的核心用法
#[derive(Parser, Debug)]
#[command(name = "mini-cli", version, about, long_about = None)]
struct Cli {
    /// 要搜索的模式（正则表达式）
    #[arg(short = 'p', long = "pattern", default_value = "TODO")]
    pattern: String,

    /// 搜索路径，默认为当前目录
    #[arg(default_value = ".")]
    path: String,

    /// 递归搜索子目录
    #[arg(short, long)]
    recursive: bool,

    /// 忽略大小写
    #[arg(short = 'i', long = "ignore-case")]
    ignore_case: bool,

    /// 最大并发线程数
    #[arg(short = 'j', long = "jobs", default_value_t = 4)]
    jobs: usize,
}

fn main() {
    let cli = Cli::parse();
    println!("{:?}", cli);
}
```

运行 `cargo run -- --help`，clap 会自动生成格式化的帮助文本，包括每个字段的 doc comment 作为说明。

### 2.2 子命令、枚举与默认值

子命令通过 enum + `Subcommand` 派生实现，每个变体对应一个子命令：

```rust
use clap::{Parser, Subcommand};

#[derive(Parser, Debug)]
#[command(name = "filetool", version)]
struct Cli {
    #[command(subcommand)]
    command: Commands,
}

#[derive(Subcommand, Debug)]
enum Commands {
    /// 统计文件行数
    Count {
        /// 目标文件
        file: String,
        /// 同时统计字节数
        #[arg(short, long)]
        bytes: bool,
    },
    /// 转换文件编码
    Convert {
        /// 输入文件
        input: String,
        /// 输出文件
        output: String,
        /// 目标编码
        #[arg(short, long, default_value = "utf-8")]
        encoding: String,
    },
}

fn main() {
    let cli = Cli::parse();
    match cli.command {
        Commands::Count { file, bytes } => {
            println!("counting {} (bytes={})", file, bytes);
        }
        Commands::Convert { input, output, encoding } => {
            println!("converting {} -> {} as {}", input, output, encoding);
        }
    }
}
```

### 2.3 常见坑

- **`short` 冲突**：多个字段都用 `#[arg(short)]` 时，clap 按字段首字母自动分配，可能冲突。显式写 `short = 'x'` 更安全。
- **`default_value` 与类型**：`default_value` 总是字符串，clap 会调用 `FromStr` 转换；自定义类型需实现 `FromStr`。`default_value_t` 直接传字面量，适用于原始类型。
- **位置参数顺序**：结构体中位置参数的声明顺序即解析顺序，`Vec<T>` 类型的位置参数会贪婪消费剩余参数。
- **负号参数**：以 `-` 开头的值会被误认为选项，需用 `--` 分隔，如 `grep -- -v file.txt`。

## 3. anyhow 与错误处理

### 3.1 anyhow::Result 与上下文链

CLI 工具的错误处理需要：友好的错误消息、错误链追溯、退出码。anyhow（以 crates.io 最新稳定版为准）提供 `anyhow::Result<T>` 和 `.context()` 方法，给错误附加上下文。

```toml
[dependencies]
anyhow = "1"
```

```rust
use anyhow::{Context, Result};
use std::fs;
use std::path::Path;

fn read_config(path: &str) -> Result<String> {
    let content = fs::read_to_string(path)
        .with_context(|| format!("无法读取配置文件: {}", path))?;
    Ok(content)
}

fn parse_port(content: &str) -> Result<u16> {
    content
        .trim()
        .parse::<u16>()
        .context("端口号必须是 0-65535 的整数")
}

fn main() -> Result<()> {
    let content = read_config("config.toml")?;
    let port = parse_port(&content)?;
    println!("监听端口: {}", port);
    Ok(())
}
```

错误输出示例：

```text
Error: 无法读取配置文件: config.toml

Caused by:
    No such file or directory (os error 2)
```

`.context()` 附加的消息在外层，底层错误在 `Caused by:` 链中，形成完整的错误追溯。

### 3.2 对照 C++：异常与 expected

C++ 中错误处理有三条路线：

1. **异常（try/catch）**：错误传播隐式，无法从函数签名看出是否抛异常，RAII 保证资源释放但异常安全等级需要精心维护。
2. **错误码 + errno**：C 风格，调用方容易忘记检查，无上下文信息。
3. **`std::expected<T, E>`（C++23）**：与 Rust `Result` 语义最接近，但生态尚未成熟，`?` 运算符等价物（`std::expected` 的 monadic 操作）仍在标准化中。

Rust 的 `Result<T, E>` + `?` 运算符是语言级内置的：函数签名显式声明错误类型，`?` 自动传播错误并转换类型，编译器强制处理 `Result`（不处理会有 warning）。anyhow 在标准库之上提供了动态错误类型和上下文链，适合应用层；库层面则推荐自定义错误枚举（thiserror）。

## 4. indicatif 进度条

### 4.1 基础进度条与样式

indicatif（以 crates.io 最新稳定版为准）是 Rust 生态最主流的进度条库，支持进度条、微调器（spinner）、多进度条。

```toml
[dependencies]
indicatif = "0.17"
```

```rust
use indicatif::{ProgressBar, ProgressStyle};
use std::time::Duration;

fn main() {
    let pb = ProgressBar::new(1000);
    pb.set_style(
        ProgressStyle::with_template(
            "{spinner:.green} [{elapsed_precise}] [{wide_bar:.cyan/blue}] {pos}/{len} ({eta})",
        )
        .unwrap()
        .progress_chars("#>-"),
    );

    for i in 0..1000 {
        // 模拟工作
        std::thread::sleep(Duration::from_millis(2));
        pb.inc(1);
    }
    pb.finish_with_message("处理完成");
}
```

模板字段说明：`{spinner}` 旋转图标、`{elapsed_precise}` 已用时间、`{wide_bar}` 自适应宽度进度条、`{pos}/{len}` 当前/总数、`{eta}` 预计剩余时间。

### 4.2 多进度条与异步场景

`MultiProgress` 支持在终端中同时显示多个进度条，常见于并行下载或批量处理：

```rust
use indicatif::{MultiProgress, ProgressBar, ProgressStyle};
use std::sync::Arc;
use std::thread;

fn main() {
    let m = MultiProgress::new();
    let style = ProgressStyle::with_template("{prefix:.bold.dim} {bar} {pos}/{len}")
        .unwrap();

    let mut handles = vec![];
    for i in 0..4 {
        let pb = m.add(ProgressBar::new(100));
        pb.set_style(style.clone());
        pb.set_prefix(format!("任务{}", i));
        handles.push(thread::spawn(move || {
            for _ in 0..100 {
                pb.inc(1);
                std::thread::sleep(std::time::Duration::from_millis(10));
            }
            pb.finish();
        }));
    }

    for h in handles {
        h.join().unwrap();
    }
}
```

在 async 场景中，`ProgressBar` 是 `Send + Sync` 的，可以跨 `.await` 传递，但需注意不要在持有进度条引用时阻塞 executor。

## 5. 从零实现 mini-grep

### 5.1 需求与架构

实现一个支持以下功能的 grep 工具：

- 接收正则模式和文件路径作为参数
- 支持 `-i` 忽略大小写、`-n` 显示行号、`-c` 仅统计匹配行数
- 递归搜索目录（可选）
- 错误处理友好

架构分为三层：参数解析（clap）→ 搜索逻辑（纯函数，可测试）→ 输出格式化。

### 5.2 完整代码

```toml
[package]
name = "mini-grep"
version = "0.1.0"
edition = "2021"

[dependencies]
clap = { version = "4", features = ["derive"] }
anyhow = "1"
regex = "1"
walkdir = "2"
```

```rust
use anyhow::{Context, Result};
use clap::Parser;
use regex::RegexBuilder;
use std::fs;
use std::io::{self, BufRead};
use std::path::{Path, PathBuf};
use walkdir::WalkDir;

/// 极简版 grep，支持正则、忽略大小写、行号、计数
#[derive(Parser, Debug)]
#[command(name = "mini-grep", version, about)]
struct Cli {
    /// 搜索模式（正则表达式）
    pattern: String,

    /// 文件或目录路径
    path: PathBuf,

    /// 忽略大小写
    #[arg(short = 'i', long = "ignore-case")]
    ignore_case: bool,

    /// 显示行号
    #[arg(short = 'n', long = "line-number")]
    line_number: bool,

    /// 仅输出匹配行数
    #[arg(short = 'c', long = "count")]
    count: bool,

    /// 递归搜索目录
    #[arg(short = 'r', long = "recursive")]
    recursive: bool,
}

/// 单行匹配结果
#[derive(Debug, Clone)]
struct MatchLine {
    line_number: usize,
    content: String,
}

/// 在单个文件内容中搜索，返回所有匹配行
fn search_in_content(
    content: &str,
    pattern: &str,
    ignore_case: bool,
) -> Result<Vec<MatchLine>> {
    let re = RegexBuilder::new(pattern)
        .case_insensitive(ignore_case)
        .build()
        .with_context(|| format!("无效的正则表达式: {}", pattern))?;

    let mut matches = Vec::new();
    for (idx, line) in content.lines().enumerate() {
        if re.is_match(line) {
            matches.push(MatchLine {
                line_number: idx + 1,
                content: line.to_string(),
            });
        }
    }
    Ok(matches)
}

/// 处理单个文件：读取内容并搜索
fn process_file(path: &Path, cli: &Cli) -> Result<Vec<MatchLine>> {
    let content = fs::read_to_string(path)
        .with_context(|| format!("无法读取文件: {}", path.display()))?;
    search_in_content(&content, &cli.pattern, cli.ignore_case)
}

/// 收集需要处理的文件列表
fn collect_files(path: &Path, recursive: bool) -> Vec<PathBuf> {
    let mut files = Vec::new();
    if path.is_file() {
        files.push(path.to_path_buf());
    } else if path.is_dir() {
        let walker = if recursive {
            WalkDir::new(path)
        } else {
            WalkDir::new(path).max_depth(1)
        };
        for entry in walker.into_iter().filter_map(|e| e.ok()) {
            if entry.file_type().is_file() {
                files.push(entry.path().to_path_buf());
            }
        }
    }
    files
}

fn main() -> Result<()> {
    let cli = Cli::parse();
    let files = collect_files(&cli.path, cli.recursive);

    if files.is_empty() {
        anyhow::bail!("未找到可处理的文件: {}", cli.path.display());
    }

    let mut total_count = 0usize;

    for file in &files {
        let matches = match process_file(file, &cli) {
            Ok(m) => m,
            Err(e) => {
                eprintln!("警告: {}", e);
                continue;
            }
        };

        if cli.count {
            if files.len() > 1 {
                println!("{}:{}", file.display(), matches.len());
            } else {
                println!("{}", matches.len());
            }
            total_count += matches.len();
        } else {
            for m in &matches {
                if files.len() > 1 {
                    print!("{}:", file.display());
                }
                if cli.line_number {
                    print!("{}:", m.line_number);
                }
                println!("{}", m.content);
            }
        }
    }

    if cli.count && files.len() > 1 {
        eprintln!("总计匹配: {} 行", total_count);
    }

    Ok(())
}
```

### 5.3 单元测试与集成测试

核心搜索逻辑 `search_in_content` 是纯函数，极易测试：

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn test_basic_match() {
        let content = "hello world\nfoo bar\nhello rust";
        let matches = search_in_content(content, "hello", false).unwrap();
        assert_eq!(matches.len(), 2);
        assert_eq!(matches[0].line_number, 1);
        assert_eq!(matches[1].line_number, 3);
    }

    #[test]
    fn test_ignore_case() {
        let content = "Hello\nHELLO\nhElLo";
        let matches = search_in_content(content, "hello", true).unwrap();
        assert_eq!(matches.len(), 3);
    }

    #[test]
    fn test_no_match() {
        let content = "abc\ndef";
        let matches = search_in_content(content, "xyz", false).unwrap();
        assert!(matches.is_empty());
    }

    #[test]
    fn test_regex_meta() {
        let content = "a1b\na2b\naXb";
        let matches = search_in_content(content, r"a\d+b", false).unwrap();
        assert_eq!(matches.len(), 2);
    }

    #[test]
    fn test_invalid_regex() {
        let result = search_in_content("test", "[", false);
        assert!(result.is_err());
    }

    #[test]
    fn test_empty_content() {
        let matches = search_in_content("", "anything", false).unwrap();
        assert!(matches.is_empty());
    }
}
```

## 6. 优秀 CLI 架构赏析

### 6.1 ripgrep：搜索性能的极致

ripgrep（rg）是 Rust 写的 grep 替代品，核心性能优化点：

1. **默认忽略 .gitignore**：通过 `ignore` crate 实现，自动跳过版本控制忽略的文件和隐藏文件，减少 IO。
2. **多线程并行**：使用 `crossbeam-channel` 做工作窃取，文件级并行。并行搜索的线程池设计可对照《../../01-C++技术体系/04-并发编程/05-线程池与并发实战模式.md》。
3. **regex 引擎优化**：Rust 的 `regex` crate 默认使用基于 DFA 的混合引擎，对字面量搜索有快速路径（Aho-Corasick 多模式匹配）。
4. **内存映射**：大文件使用 `memmap` 避免 read 系统调用开销。
5. **行计数优化**：`-c` 模式下不构造行字符串，直接在字节流中计数换行符。

架构分层：`cli`（参数解析）→ `searcher`（搜索核心）→ `ignore`（文件过滤）→ `printer`（输出格式化），各层独立可测试。

### 6.2 fd / bat / exa：现代 Unix 工具群

| 工具 | 替代 | 核心改进 | 关键 crate |
| --- | --- | --- | --- |
| fd | find | 智能大小写、默认忽略隐藏/.gitignore、彩色输出 | `ignore`, `regex` |
| bat | cat | 语法高亮、Git 集成、行号、自动分页 | `syntect`, `git2` |
| exa | ls | 彩色、Git 状态列、树视图、元数据 | `ansi_term`, `git2` |

共同设计模式：
- **智能默认**：忽略大小写当模式全小写时自动开启（fd）
- **尊重 .gitignore**：通过 `ignore` crate 统一处理
- **彩色输出**：检测终端是否支持颜色（`atty` / `is-terminal` crate），非 TTY 自动关闭
- **人类可读输出**：文件大小自动选择单位（`number_prefix` crate）

### 7.2 cross 交叉编译多平台

`cross`（以 crates.io 最新稳定版为准）是 cargo 的交叉编译封装，使用 Docker 容器提供各平台的工具链，无需手动安装 sysroot。

```bash
# 安装 cross
cargo install cross --git https://github.com/cross-rs/cross

# 交叉编译到常见平台
cross build --release --target x86_64-unknown-linux-gnu
cross build --release --target x86_64-pc-windows-gnu
cross build --release --target x86_64-apple-darwin
cross build --release --target aarch64-unknown-linux-gnu
cross build --release --target armv7-unknown-linux-gnueabihf
```

对照 C++ 交叉编译：C++ 需要手动安装对应平台的工具链（如 `gcc-aarch64-linux-gnu`）、设置 `CC`/`CXX` 环境变量、处理 sysroot 和依赖库路径。cross 把这些封装在 Docker 镜像中，一条命令完成。

### 7.3 GitHub Actions 自动发布

```yaml
# .github/workflows/release.yml
name: Release

on:
  push:
    tags:
      - "v*"

jobs:
  build:
    strategy:
      matrix:
        include:
          - target: x86_64-unknown-linux-gnu
            os: ubuntu-latest
          - target: x86_64-pc-windows-gnu
            os: ubuntu-latest
          - target: x86_64-apple-darwin
            os: macos-latest
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with:
          targets: ${{ matrix.target }}
      - name: Build
        run: cargo build --release --target ${{ matrix.target }}
      - name: Package
        run: |
          cd target/${{ matrix.target }}/release
          tar czf ../../../mini-grep-${{ matrix.target }}.tar.gz mini-grep*
      - uses: softprops/action-gh-release@v1
        with:
          files: mini-grep-*.tar.gz
```

## 8. 本节小结

Rust 写 CLI 工具的核心优势在于：clap derive 让参数解析声明式且零样板，anyhow 提供带上下文链的错误处理，indicatif 一行代码搞定进度反馈，编译产物是单二进制且启动极快。mini-grep 实践展示了「纯函数核心 + 薄 IO 层」的可测试架构。ripgrep/fd/bat/exa 证明了 Rust 在系统工具领域的性能与工程质量上限。发布层面，cross + GitHub Actions 让多平台二进制分发自动化。
