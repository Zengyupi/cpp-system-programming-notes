## 1. 存储引擎核心结构回顾

### 1.1 B+树：读优化的页式存储

B+树是关系型数据库（MySQL InnoDB、PostgreSQL）的核心索引结构。特点：

- **多路平衡树**：非叶子节点只存键，叶子节点存键值对并用链表串联
- **页式存储**：节点大小通常 4KB–16KB，与操作系统页对齐，一次 IO 读取一个节点
- **读放大低**：三层 B+树（扇出 1000）可索引 10 亿条数据，点查只需 3 次 IO
- **写放大**：插入/更新可能触发页分裂，随机写性能差

对照 C++ 实现：B+树节点通常用 `struct` 手动管理内存，子节点指针用 `unique_ptr<Node>` 或文件偏移量，需要自己处理页分裂、合并、锁粒度。Rust 中则用 `Vec<(K, Option<Box<Node>>)>` 或更精细的 `Arc<RwLock<Node>>`，所有权系统让节点生命周期管理更安全。

### 1.2 LSM-Tree：写优化的日志结构

LSM-Tree（Log-Structured Merge Tree）是 LevelDB/RocksDB/Cassandra 的核心结构。写入流程：

1. **WAL（Write-Ahead Log）**：先写日志文件保证崩溃恢复
2. **MemTable**：写入内存中的有序结构（跳表/B树）
3. **Immutable MemTable**：MemTable 写满后冻结，等待刷盘
4. **SSTable**：Immutable MemTable 刷到磁盘生成有序不可变文件
5. **Compaction**：后台合并多层 SSTable，清理过期数据，减少读放大

LSM 的核心权衡：**写性能极好（顺序写），但读需要查多层（读放大），Compaction 消耗 IO（写放大）**。

### 1.3 对照 C++ 存储引擎实现

C++ 实现 LSM 存储引擎的典型痛点：

- **MemTable 并发安全**：跳表实现需要手动加锁或用无锁结构，容易出现 use-after-free
- **WAL 恢复**：崩溃后扫描日志重放，需要处理部分写入（torn write），C++ 中文件操作异常安全需精心维护
- **Compaction 线程**：后台线程与前台读写的同步，C++ 中条件变量 + 原子变量组合容易出竞态
- **资源管理**：SSTable 文件句柄、内存缓存的生命周期，`shared_ptr` 循环引用风险

Rust 的所有权系统在这些场景天然有利：`Arc<RwLock<MemTable>>` 明确共享与可变性边界，`?` 运算符让 IO 错误传播简洁，`Drop` trait 保证文件句柄自动关闭，无 GC 意味着 Compaction 期间不会有 STW 停顿。更深入的存储引擎原理可对照《../../01-C++技术体系/16-基础设施与平台/01-存储引擎原理.md》。

## 2. sled：纯 Rust 嵌入式 K-V

### 2.1 核心 API 与基本操作

sled（以 crates.io 最新稳定版为准）是纯 Rust 实现的嵌入式 K-V 存储，目标是成为 Rust 生态的 "BoltDB / LevelDB"。底层使用混合 B+树（页式 + 日志结构），支持 ACID 事务。

```toml
[dependencies]
sled = "0.34"
```

```rust
use sled::Db;

fn main() -> sled::Result<()> {
    // 打开或创建数据库，目录不存在会自动创建
    let db: Db = sled::open("my_database")?;

    // 插入键值对，键和值都是 &[u8] / Vec<u8>
    db.insert("key1", "value1")?;
    db.insert(b"key2", vec![1u8, 2, 3])?;

    // 读取，返回 Option<IVec>，IVec 是 sled 的引用计数字节切片
    if let Some(value) = db.get("key1")? {
        println!("key1 = {:?}", std::str::from_utf8(&value));
    }

    // 删除
    let old = db.remove("key1")?;
    println!("删除的旧值: {:?}", old);

    // 检查是否存在
    println!("key1 存在: {}", db.contains_key("key1")?);

    // 范围扫描，返回迭代器
    db.insert("a", "1")?;
    db.insert("b", "2")?;
    db.insert("c", "3")?;
    for item in db.range("a".."c") {
        let (k, v) = item?;
        println!("{:?} -> {:?}", k, v);
    }

    // 确保数据刷到磁盘（默认后台刷盘，可手动 flush）
    db.flush()?;

    Ok(())
}
```

### 2.2 事务与批量写入

sled 支持事务（Serializable 隔离级别）和批量原子写入。事务中读取和修改多个 Tree，遇到冲突自动重试（指数退避），事务体内不应有副作用。`Batch` 用于单次原子写入多个键值对：

```rust
use sled::{Db, Transactional};

fn main() -> sled::Result<()> {
    let db = sled::open("txn_db")?;
    let tree = db.open_tree("accounts")?;

    // 事务：转账，余额不足则中止
    let result = (&tree).transaction(|t| {
        let alice: i64 = t.get("alice")?.map(|v| {
            String::from_utf8(v.to_vec()).unwrap().parse().unwrap()
        }).unwrap_or(100);
        if alice < 50 {
            return Err(sled::transaction::TransactionError::Abort("余额不足"));
        }
        t.insert("alice", (alice - 50).to_string())?;
        t.insert("bob", "150".to_string())?;
        Ok(())
    });
    println!("转账结果: {:?}", result);

    // 批量原子写入
    let mut batch = sled::Batch::default();
    batch.insert("k1", "v1");
    batch.insert("k2", "v2");
    batch.remove("old");
    db.apply_batch(batch)?;
    Ok(())
}
```

### 2.3 常见坑与调优

- **键值都是字节**：sled 不做序列化，需要自己处理 `String` ↔ `&[u8]` 转换。推荐用 `serde` + `bincode` 做结构化数据序列化。
- **IVec 不是 Vec**：`IVec` 是引用计数的字节切片，克隆是浅拷贝（增加引用计数），不需要 `to_vec()` 除非需要修改。
- **事务冲突重试**：sled 事务遇到写冲突会自动重试（指数退避），事务体内不应有副作用（如发网络请求），否则重试会重复执行。
- **内存占用**：sled 默认缓存最近使用的页，大量数据时需监控内存。可通过 `db.flush()` 主动释放。
- **多 Tree**：`db.open_tree("name")` 创建命名空间，类似 RocksDB 的 Column Family，不同 Tree 独立存储但共享 WAL。

## 3. RocksDB 绑定：rust-rocksdb

### 3.1 依赖与基本读写

rust-rocksdb（以 crates.io 最新稳定版为准）是 Facebook RocksDB 的 Rust 绑定，通过 FFI 调用 C++ 实现。适合需要成熟 LSM 存储引擎、高写入吞吐的场景。

```toml
[dependencies]
rocksdb = "0.22"
```

```rust
use rocksdb::{DB, Options};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // 配置选项
    let mut opts = Options::default();
    opts.create_if_missing(true);
    opts.set_max_open_files(1000);
    // 优化写：增大 MemTable 大小
    opts.set_write_buffer_size(64 * 1024 * 1024); // 64MB
    // 优化读：设置块缓存
    opts.set_block_cache(&rocksdb::Cache::new_lru_cache(128 * 1024 * 1024));

    // 打开数据库
    let db = DB::open(&opts, "rocksdb_data")?;

    // 写入
    db.put(b"key1", b"value1")?;

    // 读取
    match db.get(b"key1")? {
        Some(v) => println!("key1 = {:?}", std::str::from_utf8(&v)),
        None => println!("key1 不存在"),
    }

    // 删除
    db.delete(b"key1")?;

    // 范围迭代
    let iter = db.iterator(rocksdb::IteratorMode::Start);
    for item in iter {
        let (k, v) = item?;
        println!("{:?} -> {:?}", k, v);
    }

    // 前缀迭代（需要配置 prefix_extractor）
    // db.iterator(rocksdb::IteratorMode::From(b"prefix_", rocksdb::Direction::Forward));

    Ok(())
}
```

### 3.2 Column Family 与性能选项

RocksDB 的 Column Family（CF）允许在同一 DB 中创建独立配置的命名空间，类似 sled 的多 Tree。通过 `DB::open_cf_descriptors` 打开多 CF，用 `db.cf_handle("name")` 获取句柄后按 CF 读写。每个 CF 可独立配置 write_buffer_size、compaction 策略等，适合将冷热数据分离存储。

**sled vs RocksDB 选型对照**：

| 维度 | sled | rust-rocksdb |
| --- | --- | --- |
| 实现语言 | 纯 Rust | C++ 核心 + Rust FFI |
| 编译依赖 | 纯 Rust 工具链 | 需要 C++ 编译器 + clang |
| 成熟度 | 较新，API 可能变动 | 非常成熟，Facebook 生产验证 |
| 事务支持 | 原生支持多 Tree 事务 | 不支持跨行事务（需自己实现） |
| 写入性能 | 良好 | 极高（深度优化的 Compaction） |
| 适用场景 | 嵌入式、中小规模、需要事务 | 大规模写入、生产级存储后端 |

## 4. TiKV 为何选择 Rust

### 4.1 技术决策背景

TiKV 是 PingCAP 开发的分布式事务型 K-V 数据库，是 TiDB 的存储层。2016 年启动时，团队在 C++、Go、Rust 之间做了选型：

- **C++**：性能最优，但内存安全问题在分布式存储中代价极高——一个 use-after-free 可能导致整个集群数据损坏。团队规模有限，C++ 的代码审查和测试成本太高。
- **Go**：开发效率高，但 GC 停顿（STW）在低延迟存储场景不可接受。TiKV 的 P99 延迟要求在毫秒级，Go 的 GC 可能造成几十到上百毫秒的停顿。且 Go 的内存占用比 Rust 高 30%–50%，在大内存机器上成本显著。
- **Rust**：零成本抽象 + 内存安全 + 无 GC，性能与 C++ 同级，编译期消除了数据竞争和内存错误。`async/await` 生态在 2019 年后成熟，满足高并发需求。

### 4.2 Rust 在分布式存储中的优势

1. **内存安全消除整类 bug**：Raft 共识算法的实现涉及大量并发状态机，C++ 中竞态导致的状态不一致是最难调试的 bug。Rust 的 `Send/Sync` trait 在编译期保证线程安全。
2. **精确的资源控制**：TiKV 需要精细管理内存（MemTable、Block Cache、Raft Log），Rust 的所有权系统让内存占用可预测，无 GC 意味着无意外停顿。
3. **FFI 互操作**：TiKV 底层使用 RocksDB（C++），通过 rust-rocksdb 绑定调用。Rust 的 FFI 零开销，且 `unsafe` 块明确标记了需要人工审查的边界。
4. **错误处理**：分布式存储中错误处理极其重要（网络分区、磁盘故障、节点宕机），Rust 的 `Result` + `?` 让错误路径显式且不可忽略，对照 C++ 的异常或错误码，Rust 强制开发者处理每个失败点。

TiKV 的关键 crate：`raft-rs`（Raft 共识）、`engine_rocksdb`（存储引擎封装）、`grpcio`（gRPC 绑定）、`tikv_util`（通用工具）、`pd_client`（PD 调度客户端）。

## 5. 从零实现 K-V 存储骨架

### 5.1 架构设计

实现一个简化版 LSM K-V 存储，包含：

- **MemTable**：内存中的 `BTreeMap<Vec<u8>, Vec<u8>>`，有序存储
- **WAL**：写入前先追加到日志文件，保证崩溃恢复
- **SSTable**：MemTable 写满后序列化为磁盘文件
- **简单 Compaction**：合并多个 SSTable，保留最新值

### 5.2 完整代码

```toml
[package]
name = "mini-kv"
version = "0.1.0"
edition = "2021"

[dependencies]
anyhow = "1"
serde = { version = "1", features = ["derive"] }
bincode = "1"
```

```rust
use anyhow::{Context, Result};
use serde::{Deserialize, Serialize};
use std::collections::BTreeMap;
use std::fs::{self, File, OpenOptions};
use std::io::{BufReader, BufWriter, Read, Write};
use std::path::{Path, PathBuf};
use std::sync::{Arc, Mutex};

// ---------- WAL 条目 ----------

#[derive(Debug, Serialize, Deserialize)]
enum WalEntry {
    Put { key: Vec<u8>, value: Vec<u8> },
    Delete { key: Vec<u8> },
}

// ---------- SSTable ----------

#[derive(Debug, Serialize, Deserialize)]
struct SSTable {
    entries: Vec<(Vec<u8>, Option<Vec<u8>>)>, // None = 墓碑
}

impl SSTable {
    fn from_memtable(mem: &BTreeMap<Vec<u8>, Option<Vec<u8>>>) -> Self {
        SSTable { entries: mem.iter().map(|(k, v)| (k.clone(), v.clone())).collect() }
    }

    fn save(&self, path: &Path) -> Result<()> {
        let data = bincode::serialize(self).context("SSTable 序列化失败")?;
        fs::write(path, &data).with_context(|| format!("写入 SSTable 失败: {}", path.display()))?;
        Ok(())
    }

    fn load(path: &Path) -> Result<Self> {
        let data = fs::read(path).with_context(|| format!("读取 SSTable 失败: {}", path.display()))?;
        bincode::deserialize(&data).context("SSTable 反序列化失败")
    }

    fn get(&self, key: &[u8]) -> Option<Option<Vec<u8>>> {
        self.entries.binary_search_by(|(k, _)| k.as_slice().cmp(key))
            .ok().map(|idx| self.entries[idx].1.clone())
    }
}

// ---------- 存储引擎 ----------

pub struct MiniKV {
    inner: Arc<Mutex<Inner>>,
    data_dir: PathBuf,
}

struct Inner {
    memtable: BTreeMap<Vec<u8>, Option<Vec<u8>>>,
    sstables: Vec<SSTable>,
    wal_writer: BufWriter<File>,
    memtable_size: usize,
}

impl MiniKV {
    const MAX_MEMTABLE: usize = 4 * 1024 * 1024;

    pub fn open(data_dir: &Path) -> Result<Self> {
        fs::create_dir_all(data_dir).context("创建数据目录失败")?;
        let wal_path = data_dir.join("wal.log");
        let wal_file = OpenOptions::new().create(true).append(true).open(&wal_path)?;

        let mut inner = Inner {
            memtable: BTreeMap::new(),
            sstables: Vec::new(),
            wal_writer: BufWriter::new(wal_file),
            memtable_size: 0,
        };

        // 加载 SSTable
        let mut sst_files: Vec<PathBuf> = fs::read_dir(data_dir)?
            .filter_map(|e| e.ok()).map(|e| e.path())
            .filter(|p| p.extension().map(|e| e == "sst").unwrap_or(false))
            .collect();
        sst_files.sort();
        for path in &sst_files { inner.sstables.push(SSTable::load(path)?); }

        // 重放 WAL
        Self::replay_wal(&wal_path, &mut inner)?;

        Ok(MiniKV { inner: Arc::new(Mutex::new(inner)), data_dir: data_dir.to_path_buf() })
    }

    fn replay_wal(path: &Path, inner: &mut Inner) -> Result<()> {
        if !path.exists() { return Ok(()); }
        let mut reader = BufReader::new(File::open(path)?);
        loop {
            let mut len_buf = [0u8; 4];
            if reader.read_exact(&mut len_buf).is_err() { break; }
            let mut buf = vec![0u8; u32::from_le_bytes(len_buf) as usize];
            if reader.read_exact(&mut buf).is_err() { break; }
            match bincode::deserialize::<WalEntry>(&buf) {
                Ok(WalEntry::Put { key, value }) => {
                    inner.memtable_size += key.len() + value.len();
                    inner.memtable.insert(key, Some(value));
                }
                Ok(WalEntry::Delete { key }) => { inner.memtable.insert(key, None); }
                Err(_) => break,
            }
        }
        Ok(())
    }

    fn write_wal(inner: &mut Inner, entry: &WalEntry) -> Result<()> {
        let data = bincode::serialize(entry).context("WAL 序列化失败")?;
        inner.wal_writer.write_all(&(data.len() as u32).to_le_bytes())?;
        inner.wal_writer.write_all(&data)?;
        inner.wal_writer.flush()?;
        Ok(())
    }

    pub fn put(&self, key: Vec<u8>, value: Vec<u8>) -> Result<()> {
        let mut inner = self.inner.lock().unwrap();
        Self::write_wal(&mut inner, &WalEntry::Put { key: key.clone(), value: value.clone() })?;
        inner.memtable_size += key.len() + value.len();
        inner.memtable.insert(key, Some(value));
        if inner.memtable_size >= Self::MAX_MEMTABLE {
            Self::flush_memtable(&mut inner, &self.data_dir)?;
        }
        Ok(())
    }

    pub fn delete(&self, key: Vec<u8>) -> Result<()> {
        let mut inner = self.inner.lock().unwrap();
        Self::write_wal(&mut inner, &WalEntry::Delete { key: key.clone() })?;
        inner.memtable.insert(key, None);
        Ok(())
    }

    pub fn get(&self, key: &[u8]) -> Result<Option<Vec<u8>>> {
        let inner = self.inner.lock().unwrap();
        if let Some(v) = inner.memtable.get(key) { return Ok(v.clone()); }
        for sst in inner.sstables.iter().rev() {
            if let Some(v) = sst.get(key) { return Ok(v); }
        }
        Ok(None)
    }

    fn flush_memtable(inner: &mut Inner, data_dir: &Path) -> Result<()> {
        if inner.memtable.is_empty() { return Ok(()); }
        let ts = std::time::SystemTime::now().duration_since(std::time::UNIX_EPOCH).unwrap().as_nanos();
        let sst_path = data_dir.join(format!("{:020}.sst", ts));
        let sst = SSTable::from_memtable(&inner.memtable);
        sst.save(&sst_path)?;
        inner.sstables.push(sst);
        inner.memtable.clear();
        inner.memtable_size = 0;
        // 重置 WAL
        drop(std::mem::replace(&mut inner.wal_writer, BufWriter::new(
            OpenOptions::new().create(true).write(true).truncate(true).open(data_dir.join("wal.log"))?)));
        Ok(())
    }

    pub fn flush(&self) -> Result<()> {
        let mut inner = self.inner.lock().unwrap();
        Self::flush_memtable(&mut inner, &self.data_dir)
    }
}
```

        kv.put(b"hello".to_vec(), b"world".to_vec()).unwrap();
        assert_eq!(kv.get(b"hello").unwrap(), Some(b"world".to_vec()));
    }

    #[test]
    fn test_overwrite() {
        let (kv, _dir) = setup();
        kv.put(b"key".to_vec(), b"v1".to_vec()).unwrap();
        kv.put(b"key".to_vec(), b"v2".to_vec()).unwrap();
        assert_eq!(kv.get(b"key").unwrap(), Some(b"v2".to_vec()));
    }

    #[test]
    fn test_delete() {
        let (kv, _dir) = setup();
        kv.put(b"key".to_vec(), b"value".to_vec()).unwrap();
        kv.delete(b"key".to_vec()).unwrap();
        assert_eq!(kv.get(b"key").unwrap(), None);
    }

    #[test]
    fn test_persistence_after_flush() {
        let dir = TempDir::new().unwrap();
        {
            let kv = MiniKV::open(dir.path()).unwrap();
            kv.put(b"persist".to_vec(), b"data".to_vec()).unwrap();
            kv.flush().unwrap();
        }
        // 重新打开，数据应从 SSTable 恢复
        let kv2 = MiniKV::open(dir.path()).unwrap();
        assert_eq!(kv2.get(b"persist").unwrap(), Some(b"data".to_vec()));
    }

    #[test]
    fn test_wal_recovery() {
        let dir = TempDir::new().unwrap();
        {
            let kv = MiniKV::open(dir.path()).unwrap();
            kv.put(b"wal_test".to_vec(), b"recover_me".to_vec()).unwrap();
            // 不 flush，直接 drop，模拟崩溃
        }
        // 重新打开，WAL 应重放恢复数据
        let kv2 = MiniKV::open(dir.path()).unwrap();
        assert_eq!(kv2.get(b"wal_test").unwrap(), Some(b"recover_me".to_vec()));
    }

## 6. 代理/网关/负载均衡实战方向

### 6.1 反向代理与 TCP 代理

Rust 在网络代理领域有成熟生态：

- **pingora**：Cloudflare 开源的异步网络框架，是其替代 Nginx 的代理引擎核心，基于 `tokio` 实现，支持 HTTP/1、HTTP/2、gRPC 代理。
- **rpxy**：基于 pingora 的反向代理，支持 ACME 自动证书、HTTP/3。
- **tcp-proxy**：简单的 TCP 代理实现，常用于数据库连接代理、端口转发。

一个最小 TCP 代理骨架：

```rust
use anyhow::Result;
use std::sync::Arc;
use tokio::io::{self, AsyncReadExt, AsyncWriteExt};
use tokio::net::{TcpListener, TcpStream};

pub struct TcpProxy {
    listen_addr: String,
    upstream_addr: String,
}

impl TcpProxy {
    pub fn new(listen: impl Into<String>, upstream: impl Into<String>) -> Self {
        TcpProxy {
            listen_addr: listen.into(),
            upstream_addr: upstream.into(),
        }
    }

    pub async fn run(&self) -> Result<()> {
        let listener = TcpListener::bind(&self.listen_addr).await?;
        println!("TCP 代理监听 {} -> {}", self.listen_addr, self.upstream_addr);

        loop {
            let (client, addr) = listener.accept().await?;
            let upstream = self.upstream_addr.clone();
            tokio::spawn(async move {
                if let Err(e) = Self::handle(client, upstream).await {
                    eprintln!("连接 {} 处理失败: {}", addr, e);
                }
            });
        }
    }

    async fn handle(mut client: TcpStream, upstream_addr: String) -> Result<()> {
        let mut upstream = TcpStream::connect(&upstream_addr).await?;

        let (mut client_read, mut client_write) = client.split();
        let (mut upstream_read, mut upstream_write) = upstream.split();

        let client_to_upstream = io::copy(&mut client_read, &mut upstream_write);
        let upstream_to_client = io::copy(&mut upstream_read, &mut client_write);

        // 双向转发，任意一端断开则结束
        tokio::try_join!(client_to_upstream, upstream_to_client)?;
        Ok(())
    }
}
```

对照 C++ 实现：C++ 写 TCP 代理需要手动管理 epoll 事件循环、socket 缓冲区、连接超时，`boost::asio` 虽有异步支持但回调地狱明显。Rust 的 `tokio::io::copy` + `try_join!` 让双向转发仅需几行代码，`async/await` 消除了回调嵌套。

### 6.2 负载均衡算法实现

常见负载均衡算法在 Rust 中的实现：

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;

/// 后端节点
#[derive(Debug, Clone)]
pub struct Backend {
    pub addr: String,
    pub weight: u32,
}

/// 轮询（Round Robin）
pub struct RoundRobin {
    backends: Vec<Backend>,
    counter: AtomicUsize,
}

impl RoundRobin {
    pub fn new(backends: Vec<Backend>) -> Self {
        RoundRobin { backends, counter: AtomicUsize::new(0) }
    }

    pub fn next(&self) -> Option<&Backend> {
        if self.backends.is_empty() {
            return None;
        }
        let idx = self.counter.fetch_add(1, Ordering::Relaxed) % self.backends.len();
        Some(&self.backends[idx])
    }
}
```

其他常用算法：加权轮询（平滑加权，Nginx 算法，为每个后端维护当前权重，每次选权重最大者并减去总权重）、随机选择（用 `rand` crate 或时间戳取模）、一致性哈希（用 `ring` 或自建哈希环，适合会话保持场景）、最少连接数（维护每个后端活跃连接计数，选最少者）。生产级负载均衡还需配合故障转移和健康检查。

生产级负载均衡还需要：**一致性哈希**（`ring` crate 或自己实现哈希环）、**最少连接数**（需要维护每个后端的活跃连接计数）、**故障转移**（健康检查失败后自动摘除节点）。

### 6.3 服务发现与健康检查

服务发现模式：

- **静态配置**：配置文件写死后端列表，最简单但不支持动态扩缩容
- **DNS 服务发现**：通过 DNS A/SRV 记录解析后端，K8s Service 就是这种模式
- **注册中心**：Consul、etcd、Nacos，服务启动时注册，客户端 watch 变更
- **K8s API**：通过 `kube-rs` 直接 watch Endpoints 资源

健康检查实现要点：

健康检查的核心逻辑：后台任务定时（如 5 秒）对每个后端做 TCP 连接探测（`tokio::time::timeout` 包裹 `TcpStream::connect`），连续失败 3 次标记为不健康并从负载均衡池中摘除，恢复成功后自动加回。健康状态用 `Arc<RwLock<Vec<HealthyBackend>>>` 共享，负载均衡器读取时过滤掉不健康节点。关键设计：**连续失败阈值**避免网络抖动导致节点频繁摘除，**探测超时**避免阻塞检查循环。

## 7. 本节小结

存储引擎的核心是 B+树（读优化）与 LSM-Tree（写优化）的权衡。Rust 生态中 sled 提供纯 Rust 嵌入式 K-V 与原生事务，rust-rocksdb 通过 FFI 绑定成熟的 C++ RocksDB。TiKV 选择 Rust 是因为内存安全 + 无 GC + 精确资源控制在分布式存储中的不可替代性。从零实现的 K-V 存储骨架展示了 MemTable + WAL + SSTable 的完整链路，测试覆盖了持久化与崩溃恢复。代理/网关/负载均衡方向，pingora 和 tokio 生态让 Rust 成为 Nginx 替代品的有力竞争者。
