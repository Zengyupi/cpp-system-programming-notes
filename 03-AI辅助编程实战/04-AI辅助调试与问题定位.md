## 1. 调试协作总流程（先方法，后 AI）

```text
复现 → 收集第一手证据(报错/堆栈/日志/core) → 形成假设 → 最小复现
   → 让 AI 解释+补充假设 → 用实验/GDB 验证 → 定位根因 → 修复+回归测试
```

AI 插在哪：**解释证据、列可能原因清单、生成验证命令/脚本、讲解堆栈**。它不能替你在板子上复现，也不能跳过验证直接下结论。

### 1.1 给 AI 的调试信息标准包

```text
1. 现象：期望 vs 实际，是否必现/偶现，触发条件
2. 环境：OS、gcc/glibc、x86 还是 ARM 板、Debug/Release、是否多线程
3. 完整报错：编译器原文 / 运行时 stderr / dmesg / core 堆栈（从第一条 error 起）
4. 最小相关代码与数据
5. 已排查项：做过什么、排除了什么
```

## 2. 段错误 / 崩溃（SIGSEGV）

### 2.1 先用工具拿到堆栈，再问 AI

```bash
# 编译带调试信息 + 地址消毒器（最快定位越界/悬空/UAF）
g++ -g -O0 -fsanitize=address,undefined -fno-omit-frame-pointer main.cpp -o app
./app                      # ASAN 直接打印越界位置和分配/释放栈
# 或 core dump + gdb
ulimit -c unlimited
gdb ./app core -ex bt -ex "thread apply all bt"
```

把 **ASAN 报告或 `bt` 完整堆栈**贴给 AI：

```text
下面是 AddressSanitizer 完整报告（heap-use-after-free），请：
1) 逐段解释 READ/WRITE、分配栈、释放栈分别说明什么；
2) 列出导致该 UAF 的最可能调用路径（结合我贴的相关类）；
3) 给出定位它的最小 GDB 观察点方案和修复建议（用智能指针/明确生命周期）。
```

### 2.2 你要判断的点

- AI 说"加个判空就好"往往是**掩盖**而非根因；要追问"为什么会为空/被释放"；
- 多线程下的崩溃优先怀疑**数据竞争/生命周期**，让它按线程交错分析；
- Release 崩、Debug 不崩：未初始化变量、UB、优化相关，用 UBSan + `-O0/-O1` 对比。

## 3. 内存泄漏与越界（Valgrind / ASAN）

```bash
valgrind --leak-check=full --show-leak-kinds=all -s ./app        # 见《../01-C++技术体系/07-调试与测试/02-Valgrind内存检测.md》
```

```text
这是 valgrind 报告，"definitely lost" 和 "indirectly lost" 分别指什么？
结合代码指出泄漏对象的所有权应该归谁、在哪释放，给出 RAII 改法；
并说明为什么长期运行的工业网关进程即使小泄漏也必须修（fd/内存随时间耗尽）。
```

## 4. 死锁 / 多线程问题

让 AI 帮你分析，但证据要你采：

```bash
gdb -p <pid> -ex "thread apply all bt"      # 打所有线程栈，看谁在等哪把锁
# 或 helgrind / TSAN
g++ -g -fsanitize=thread ...
```

```text
下面是所有线程的 backtrace。请：
1) 标出每个线程当前持有的锁和等待的锁；2) 判断是否形成等待环（死锁）；
3) 指出锁的获取顺序应该如何统一；4) 检查是否有"持锁回调外部代码/持锁阻塞"的隐患。
```

让它对照代码找：**锁顺序不一致、重复加非递归锁、条件变量虚假唤醒没配 while、原子操作内存序错误**（原理见《../01-C++技术体系/04-并发编程/01-线程基础与生命周期.md》《../01-C++技术体系/13-并发异步与组件/07-原子操作与无锁组件.md》）。

## 5. 编译错误 vs 链接错误（AI 也会混淆，你要分清）

| 类型 | 典型关键字 | 根因方向 |
| --- | --- | --- |
| 编译错误 | `error: ...`、语法、未声明、类型不匹配、模板实例化失败 | 头文件、命名空间、模板、语法 |
| 链接错误 | `undefined reference to`、`ld returned 1` | 没链接库/源文件、符号可见性、ABI、重复定义 |

```text
请先判断这是编译期还是链接期错误，再分析：
- undefined reference：是没加 -l、没把 .cpp 加入构建、声明了没实现、还是 C/C++ 混编缺 extern "C"？
- multiple definition：是否 ODR/重复包含/全局变量定义放头文件？
给出按"最可能→次要"排序的排查清单和对应验证命令。报错：<粘贴>
```

嵌入式高频：交叉编译时链接了主机 x86 的库（架构不符）、`-static` 与 glibc、strip 后没符号——把**工具链前缀、sysroot、链接命令**一并给 AI。

## 6. 性能问题（让 AI 读 profile）

```bash
perf record -g ./app; perf report            # 见《../01-C++技术体系/07-调试与测试/03-perf性能剖析.md》
```

```text
这是 perf report / flamegraph 的热点（贴 Top 符号与占比）。
请：1) 解释热点可能的原因（缓存未命中/锁竞争/系统调用/拷贝）；
2) 给按预期收益排序的优化假设和验证方法；3) 哪些是伪热点（如自旋等待）。
```

强调：**先 profile 再优化**，别让 AI 在没有数据时给一堆"可能更快"的玄学改法。

## 7. 最小复现（Minimal Reproducible Example）

AI 最有用的技能之一是帮你把大问题**裁剪**成最小复现：

```text
帮我把这个偶发 bug 隔离成最小复现：列出需要保留/可以删掉的部分，
逐步构造一个几十行、不依赖业务库就能复现的程序。这样既能精确提问，也常能在裁剪中自己发现根因。
```

## 8. 快速参考卡片

```text
流程：复现→采证→假设→最小复现→AI解释扩假设→实验验证→根因→回归
证据包：现象/环境/完整报错/相关代码/已排查
崩溃：ASAN/UBSAN 最快；core+gdb bt；别用"判空"掩盖根因
死锁：thread apply all bt 找等待环，统一加锁顺序
链接错：缺-l/缺源文件/extern "C"/架构不符；区别于编译错
性能：先 perf 取数据再让 AI 读，拒绝无数据玄学优化
```

## 9. 常见问题与坑

| 问题 | 对策 |
| --- | --- |
| AI 看一眼就断言根因 | 要求它给"假设清单+验证方法"，用实验证伪，别信单一结论 |
| 偶现 bug 它让你"加锁试试/加 sleep" | 这是掩盖时序；用 TSAN/压力复现，找真正的竞态 |
| 只贴最后一行报错 | 从**第一条 error** 开始贴，后续常是连锁反应 |
| 板子上没法用 ASAN | 交叉编译 ASAN 运行时到目标板，或退而用 gdb/valgrind（视资源） |
| AI 给的命令没解释就让你跑 | 要求逐条解释，尤其涉及重定向、删除、改系统配置的命令 |
| 改完没回归 | 让 AI 针对该 bug 补一个会失败、修复后通过的回归测试 |
