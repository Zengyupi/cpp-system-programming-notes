## 1. 一个万能框架：RCESF

写复杂请求时按这五块组织，缺哪块补哪块：

| 要素 | 含义 | C++ 例子 |
| --- | --- | --- |
| **R**ole 角色 | 让它进入专业视角 | "你是资深 C++17 后端工程师" |
| **C**ontext 上下文 | 环境、版本、相关代码、报错原文 | gcc 11、ARM 交叉编译、贴头文件/堆栈 |
| **E**xpect 目标 | 要什么产物、格式 | "给出可编译的 .h/.cpp + 单元测试" |
| **S**teps/约束 | 分步、边界、不许做什么 | 无裸 new、异常安全、不要第三方库 |
| **F**eedback 迭代 | 用结果继续纠偏 | 贴新报错、指出不符合要求处 |

### 1.1 反例 vs 正例

```text
✗ 反例（信息缺失，只能得到正确的废话）：
  "C++ 怎么做线程池？"

✓ 正例（RCESF 齐全）：
  你是资深 C++17 工程师。我在 Linux 上写一个 Reactor 网络服务器（gcc 11，
  C++17，已有 EventLoop 和 Channel）。需要一个固定大小线程池：
  - 接口：submit(Callable&&) 返回 std::future 结果；
  - 用 condition_variable 做任务调度，线程数=硬件并发数；
  - 要求析构时优雅退出、能处理异常并通过 future 抛回；
  - 不要第三方库，给出 ThreadPool.h 和一段 main 测试，并解释为什么任务队列要加锁。
```

## 2. 给足"上下文"的六种常用材料

1. **报错原文**：编译器/链接器/运行时堆栈**完整复制**，别转述、别只截一句；
2. **相关代码**：最小相关的类/函数签名，而不是整个工程；
3. **编译与运行命令**：`g++ -std=c++17 ...`、CMake 片段、启动参数；
4. **类型与接口定义**：自定义结构体、头文件（AI 看不到你工程就靠这个）；
5. **数据样例**：输入字节流、报文 hex、期望输出（做协议解析尤其重要）；
6. **你已经试过什么**：避免它重复给你排除过的方案。

> 贴大段代码前先让它"**先说思路，确认后再写代码**"，能显著减少方向跑偏。

## 3. 让输出可控的技巧

- **限定范围**："只改这个函数，别动其它代码""用标准库，不引入 boost"。
- **要它先列计划**："先列出你会修改的文件和步骤，等我确认"。
- **要解释而非只给码**："逐行注释关键部分，并说明为什么这样设计"。
- **要多个方案对比**："给出 2 种实现，分别从性能、可读性、线程安全比较，再推荐"。
- **让它自检**："检查这段代码的生命周期、空指针、异常安全、数据竞争"。
- **小步迭代**：一次只推进一个点，比一次要一个大系统质量高得多。
- **指定输出格式**："用 Markdown 表格""只输出 diff""输出成一个 .cpp 文件"。

### 4.1 解释一段陌生源码（读 muduo/开源库时）

```text
你是 C++ 网络编程专家。下面是 muduo 中 EventLoop::loop 的实现，请：
1) 逐段解释它在做什么；2) 画出 Poller→Channel→回调的调用链（文字/ASCII）；
3) 指出为什么 one loop per thread 要用 thread_local 的 loop 指针；
4) 用更通俗的话给一个 C++ 初学者再讲一遍。代码：<粘贴>
```

```text
环境：Ubuntu22.04，gcc 11，CMake，交叉编译目标 aarch64。
我执行 <编译命令> 后出现下面完整报错：<原样粘贴，从第一条 error 开始>

```



### 4.5 协议/字节流解析（工业网关高频）

```text
你是工业协议专家。下面是一段 Modbus TCP 报文的十六进制：<hex>
请按字节标注：MBAP 头(事务id/协议id/长度/单元id)、功能码、数据、并判断是否合法。
再给一段 C++17 解析代码：输入 uint8_t* 和长度，做长度与边界校验，用 std::span，
不允许越界读取，解析结果放进结构体，错误用错误码返回。
```

### 4.6 让 AI 挑战自己的答案（非常有用）

```text
请以挑刺的 code reviewer 视角审查你刚给的代码：
重点找数据竞争、对象生命周期、整数溢出、未定义行为、异常路径泄漏，列出问题并修正。
```

## 5. 多轮协作的正确节奏

```text
描述目标+约束 → 要方案/计划 → 你确认方向 → 要代码 → 本地编译+跑测试
   → 把真实报错/结果回喂 → 修正 → 让它自审 → 你最终复核合入
```

- AI 不知道自己错了，**只有编译器、测试和人工判断能证伪**；
- 对话变长导致它"忘事"时，开新对话并把关键结论/接口重新交代一遍；
- 重要结论让它给依据（标准条款、文档、源码位置），而不是它"觉得"。

## 6. 快速参考卡片

```text
RCESF：角色 / 上下文 / 目标 / 步骤约束 / 反馈迭代
上下文六件套：完整报错、相关代码、编译命令、类型定义、数据样例、已试过的办法
可控：限范围、先计划、要解释、多方案对比、让它自检、小步走、定格式
铁律：先思路后代码；结果必须编译+测试+读懂再合；长对话会遗忘就重开并补关键信息
```

## 7. 常见问题与坑

| 问题 | 对策 |
| --- | --- |
| 它总给我用不上的泛泛答案 | 缺上下文/约束；按 RCESF 补环境、版本、代码、明确产物 |
| 一上来生成一大堆，方向就错了 | 先让它出方案和改动清单，确认后再写码 |
| 多轮后前后矛盾 | 上下文超限遗忘；开新会话，重述关键接口与已确定结论 |
| 它很自信地编了不存在的 API | 必须查头文件/官方文档验证（见第 05 篇幻觉识别） |
| 贴了整工程反而答得差 | 信息过载；只给最小相关片段和清晰问题 |
| 中文提问夹杂英文术语更准 | 技术名词用英文原文（如 RAII、SFINAE、move semantics），减少歧义 |
