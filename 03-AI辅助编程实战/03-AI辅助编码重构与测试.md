## 1. 最适合交给 AI 的编码任务（高性价比）

| 任务 | 为什么适合 | 需把关的点 |
| --- | --- | --- |
| 样板/重复代码（getter、状态机分支、序列化） | 规则明确、量大、易错 | 命名、是否漏分支 |
| 数据结构/算法初稿 | 快速得到可改的起点 | 复杂度、边界、是否符合题意 |
| C 风格 → 现代 C++ 重构 | 模式固定 | 语义是否保持、所有权是否正确 |
| 写 CMake/Makefile/Shell | 语法琐碎易忘 | 编译选项、依赖路径、交叉编译 |
| 单元测试用例 | 覆盖思路人来定，码让它写 | 是否真的断言了关键行为 |
| 注释/文档/commit message | 费时不费脑 | 别让它写出与实现不符的注释 |
| 正则、格式化、数据转换脚本 | 一次性、语法烦 | 拿真实样例验证 |
| 跨语言翻译（Python 原型→C++） | 快速落地 | 类型、内存模型、性能 |

**不适合**直接交给 AI：核心架构设计、并发正确性、安全相关、强业务规约逻辑——这些让它给参考，你主导。

## 2. 现代 C++ 重构实战（典型对话）

原始 C 风格代码：

```cpp
// 旧：裸指针 + 手工释放 + 数组
struct Buffer* buf = (struct Buffer*)malloc(sizeof(struct Buffer) + 1024);
buf->data = (char*)malloc(1024);
// ... 中途 return 会泄漏 ...
free(buf->data); free(buf);
```

提示词（套用第 02 篇框架）：

```text
重构为异常安全的 C++17：用 RAII 和智能指针管理生命周期，用 std::vector/std::array
替代手工分配，保证任何 return/异常路径都不泄漏，保持对外行为不变，列出每处改动理由。
```

需核对的**正确性清单**（AI 常在这里翻车）：

- 所有权是否唯一（该 `unique_ptr` 还是共享才用 `shared_ptr`，别滥用 shared）；
- 移动/拷贝语义、是否误拷贝大对象；
- 异常抛出时资源是否仍被 RAII 托管；
- 引用/指针是否指向已释放对象（生命周期）；
- 是否引入了不必要的虚函数/堆分配影响性能。

## 3. 跨语言迁移：Python 原型 → C++（常见路径）

先用 Python 快速验证协议解析/算法，再让 AI 辅助翻译成 C++：

```text
把下面 Python 函数翻译为 C++17，目标是嵌入式 Linux（gcc，C++17）：
- 用 std::vector<uint8_t> / std::span 表示字节缓冲；
- 显式处理大小端（用 htobe16 或手写，不依赖平台）；
- 不使用异常做普通错误返回，用 enum 错误码 + 输出参数；
- 标注每个 Python 动态特性在 C++ 里如何对应（list→vector、dict→unordered_map）。
Python：<粘贴>
```

迁移时**主动追问 AI** 这些 Python 隐藏行为在 C++ 的代价：动态 list 的扩容、dict 哈希、自动内存管理、异常即控制流——这些在资源受限的板子上都要显式处理。反向（C++→Python 做测试工具）参考《../05-Python技术体系/01-Python语言速成/07-Python脚本与自动化.md》。

## 4. 让 AI 写构建脚本与工程配置

### 4.1 CMake（最常被问，也最容易版本踩坑）

```text
用现代 CMake（target_* 风格，不要全局 include_directories）写一个 C++17 工程：
- 静态库 core + 可执行 app 链接它；-Wall -Wextra -Werror；导出 compile_commands.json；
- 可选链接 pthread 和 OpenSSL，找不到时给清晰报错；支持 aarch64 交叉编译工具链文件。
逐行注释并说明现代 CMake 为什么用 target_link_libraries 的 PRIVATE/PUBLIC/INTERFACE。
```

### 4.2 让它生成调试/分析脚手架

- 一键 GDB 脚本、Valgrind/ASAN 命令、perf 录制与火焰图步骤（配合《../01-C++技术体系/07-调试与测试/01-GDB程序调试.md》《../01-C++技术体系/07-调试与测试/02-Valgrind内存检测.md》《../01-C++技术体系/07-调试与测试/03-perf性能剖析.md》）；
- 交叉编译工具链文件、打包脚本、systemd service 模板。

> 让 AI 写命令时要求它**逐条解释作用**，避免它给出带 `rm -rf` 或危险重定向的命令而未看就跑。

## 5. AI 辅助写单元测试（投入产出最高）

流程：**人定测试点，AI 铺用例代码**。

```text
用 GoogleTest 为这个 CRC16/Modbus 校验函数补测试：
1) 标准已知向量（给出协议手册的例子）；2) 空输入/单字节/奇数字节；
3) 分片与整体结果一致；4) 表驱动方式组织。函数：<粘贴>
```

要点：

- 让它覆盖**等价类 + 边界值 + 异常路径**，而不是只测 happy path；
- 涉及并发的代码，让它写**压力/重复调度**用例（反复创建销毁、多线程跑）；
- 测试名用行为描述（`HandlesPartialFrameThenRemaining`），便于失败时定位；
- AI 生成的"期望值"要警惕：它可能编一个看似合理但错误的预期，**期望值必须来自规格/独立计算**。

## 6. 让 AI 协助读懂大型开源库（muduo / spdlog / libmodbus）

```text
我在精读这个开源库（贴目录树 + 关键文件）。请：
1) 先给整体架构和数据流；2) 按"启动→接收连接→读事件→业务回调→写回"的顺序带我走一遍；
3) 列出最值得先读的 5 个文件及阅读顺序；4) 每读完一个文件我贴给你，你帮我答疑和总结。
```

这比让它"讲讲 muduo"有效得多——**带着真实源码、按调用链推进**。对标项目清单见《../01-C++技术体系/18-面试与求职/02-简历撰写与项目表达.md》第 5.1 节。

## 7. 注释、文档与提交信息

- 让 AI 给**已经写对**的代码补注释：解释"为什么"而不是复述"做什么"；
- 生成头文件接口文档、README 初稿（需核对事实）；
- commit message：`根据以下 diff 生成符合 Conventional Commits 的中文提交信息，说明动机`；
- 反过来，也可以让它**从注释发现代码与注释不符**的地方。


## 9. 常见问题与坑

| 问题 | 对策 |
| --- | --- |
| 生成代码能编但风格和工程不一致 | 提示词里给一段你工程的现有代码当风格样例 |
| 滥用 shared_ptr/虚函数/异常 | 明确所有权策略与性能约束，要求说明每个设计选择 |
| 测试用例只测正常路径 | 明确要求边界/异常/并发，并用表驱动 |
| 期望值是 AI 编的 | 用规格或独立实现核对，别信它口算的结果 |
| CMake 给的是过时老写法 | 指定"现代 target_* 风格 + 最低 cmake 版本" |
| 一次要整个大模块，质量差 | 拆成接口→实现→测试，小步生成、逐步集成 |
