## 1. 先打底：串行通信与差分总线

### 1.1 基础概念

| 概念 | 含义 |
| --- | --- |
| 单工 / 半双工 / 全双工 | 只能一个方向 / 双方轮流收发（RS485、CAN）/ 同时收发（UART、以太网） |
| 同步 / 异步 | 同步靠独立时钟线（SPI/I2C）；异步靠约定波特率 + 起止位同步（UART/CAN） |
| 波特率 bps | 每秒比特数；收发双方必须一致，否则全是乱码 |
| 单端信号 / 差分信号 | 单端对参考地，易受干扰；差分用两根线电压差表示 0/1，共模干扰被抵消 |

**为什么工业/车载爱用差分线**：电机、继电器、发动机点火都是强干扰源，单端 TTL 电平（对 GND 的电压）很容易被干扰翻转；差分信号看 `CAN_H − CAN_L`（或 A−B），干扰同时耦合到两根线上、差值不变，所以 RS485/CAN 能在电磁恶劣环境跑几十米甚至上千米。

### 1.2 UART / RS232 / RS485 / RS422 的关系

- **UART** 是一种异步串行**协议**（单片机外设），帧格式：`起始位(0) + 5~9 数据位 + 可选校验位 + 停止位(1)`，没有时钟线，靠波特率对齐。
- **RS232 / RS485 / RS422** 是 UART 之上的**电气标准**（电平、几对线、几台设备），它们本身不规定数据含义：

| 标准 | 电平/方式 | 双工 | 节点数 | 距离/速率 | 典型用途 |
| --- | --- | --- | --- | --- | --- |
| TTL-UART | 0/3.3V 单端 | 全双工 | 点对点 | 板内、极短 | 芯片之间、调试串口 |
| RS232 | ±3~15V 单端 | 全双工 | 1 对 1 | ~15m | 老式设备、工控配置口 |
| **RS485** | 差分 A/B | **半双工** | 一主多从（最多 32/128/256） | 1200m@低速 | **Modbus RTU 的物理层**、工业仪表 |
| RS422 | 差分 | 全双工（两对线） | 1 发多收 | 较长 | 少数老设备 |

> 关键串联：你熟悉的 **Modbus RTU 就是"Modbus PDU 跑在 RS485 差分总线上"**，一主多从轮询；而 **CAN 也是差分、也是多节点，但它是多主、会自动仲裁**，这是和 RS485 最大的区别。

## 2. CAN 总线核心（本篇重点）

CAN（Controller Area Network）由 Bosch 为汽车设计，特点：**多主、广播、差分、非破坏性仲裁、强错误检测**。两根线 `CAN_H / CAN_L`，两端各接一个 **120Ω 终端电阻**（等于双绞线特性阻抗，吸收信号反射；必须在总线**两端**各一个，不是每个节点一个）。

### 2.1 物理层：显性 0 与隐性 1

| 位 | 电平 | CAN_H / CAN_L | 差分 |
| --- | --- | --- | --- |
| 显性 dominant = **0** | 主动拉 | H≈3.5V，L≈1.5V | ≈ +2V |
| 隐性 recessive = **1** | 释放 | 都≈2.5V | ≈ 0V |

总线是"**线与**"逻辑：只要有一个节点发显性 0，总线就是 0；所有节点都发 1，总线才是 1。**这个特性是仲裁的物理基础。**

### 2.2 帧类型

| 帧 | 作用 |
| --- | --- |
| 数据帧 Data Frame | 最常用，携带 0~8 字节数据（CAN FD 最多 64） |
| 远程帧 Remote Frame | 请求别的节点发某个 ID 的数据（RTR=1，现在很少用） |
| 错误帧 Error Frame | 任何节点检测到错误就发，强制大家重发 |
| 过载帧 Overload Frame | 请求延迟下一帧，少见 |

### 2.3 数据帧逐字段（标准帧 11 位 ID）

```text
┌────┬──────────────┬──────┬─────────┬──────────┬─────────┬─────┬─────┐
│SOF │ 仲裁段        │控制段│ 数据段   │ CRC 段    │ ACK 段  │EOF  │ITM  │
│1位 │11位ID+RTR+IDE │r1r0  │0~8字节  │15位+界定 │ACK+界定 │7位  │≥3位 │
│ 0  │              │+DLC4 │         │          │         │全1  │     │
└────┴──────────────┴──────┴─────────┴──────────┴─────────┴─────┴─────┘
 帧起始   决定优先级        数据长度    净荷       校验      应答    帧结束
扩展帧：ID 为 29 位（11 基 ID + SRR + IDE + 18 扩展 ID），IDE=1
```

- **ID 不是"源地址/目的地址"**：CAN 帧里没有发送者/接收者地址，ID 表示"**这条消息是什么**"（如 0x18FEEE0 表示某车速报文），所有节点都收到，靠**验收过滤器（滤波）**决定要不要。
- **标准帧 11 位 ID（CAN 2.0A）/ 扩展帧 29 位 ID（CAN 2.0B）**：J1939 用 29 位，多数工业/控制用 11 位。
- DLC 4 位表示数据长度，经典 CAN 最大 8 字节。

### 2.4 非破坏性仲裁：CAN 的灵魂（面试必问）

多个节点同时上电发送怎么办？CAN 用 **CSMA/CD + AMP（载波侦听 + 冲突检测 + 逐位仲裁）**，在 **SOF 之后的仲裁段**逐位比较：

```text
节点A 发 ID=0 1 0 ...   （二进制 ID，数值小）
节点B 发 ID=0 1 1 ...   （数值大）
总线   = 0 1 0 ...      （线与）
              ↑ 第3位：B 发了隐性1，却读到总线显性0 → B 知道自己优先级低，立刻退出发送
结果：A 毫无感知地继续发完（数据没被破坏），B 等总线空闲后自动重发
```

结论：
1. **ID 数值越小优先级越高**（因为前导 0 多）；
2. 仲裁失败的帧**不会被破坏、也不会让获胜帧出错**，所以叫"**非破坏性**"，这比以太网的 CSMA/CD（冲突后双方都退避重发，数据已损坏）高级；
3. 仲裁只在 ID 段进行，**一旦进入数据段就不允许冲突**，因此同一 ID 不能被两个节点同时发。

### 2.5 位填充、CRC 与错误处理（为什么 CAN 可靠）

- **位填充（Bit Stuffing，NRZ 编码）**：连续出现 5 个相同位后，发送方自动插入一个相反位，接收方删除，保证沿跳变足够多以恢复时钟；**填充位也算进 CRC**。
- **CRC-15**：对帧内容算校验，接收方对不上直接发错误帧。
- **ACK 槽**：发送方在 ACK 位发隐性 1，任何正确收到的节点在此位拉成显性 0 作为"我收到了"；发送方没看到显性就知道没人收到。
- **错误帧**：发现错误的节点连续发 6 个同极性位（违反位填充规则），让全网都知道这一帧坏了、一起丢弃重传。
- 节点三种错误状态，靠 TEC/REC（发送/接收错误计数器）自动管理，**坏节点会被逐步隔离，不拖垮整条总线**：

| 状态 | 条件 | 行为 |
| --- | --- | --- |
| 主动错误 Error Active | TEC/REC 均 < 128 | 正常收发，出错主动报错 |
| 被动错误 Error Passive | 计数 ≥ 128 | 能收发但报错更"温和"，要等额外间隔 |
| 总线关闭 Bus-Off | TEC > 255 | **脱离总线**，不再干扰别人，恢复后需软件/自动重连 |

### 2.6 CAN FD（Flexible Data-rate）

经典 CAN 的痛点：数据最多 8 字节、速率常被仲裁段限制在 1Mbps 内。CAN FD 改进：

| 维度 | 经典 CAN 2.0 | CAN FD |
| --- | --- | --- |
| 数据场长度 | 最多 8 字节 | **最多 64 字节** |
| 速率 | 全程同一速率 | 仲裁段低速、**数据段切换更高速率（BRS）**，常见 2/5/8Mbps |
| CRC | CRC-15 | CRC-17/21，更安全 |
| 兼容性 | — | 可向下兼容经典 CAN |

现在新车和高带宽节点（雷达、摄像头回传、OTA 刷写）普遍用 CAN FD。再往后是 **CAN XL**（数据场 2048 字节、10Mbps+）。

## 3. CAN 之上的高层协议（CAN 只到链路层）

CAN 只保证"一帧 8/64 字节可靠送达"，但**不定义数据含义、不分片、不做会话**，这些由上层协议补：

| 协议 | 领域 | 关键机制 |
| --- | --- | --- |
| **CANopen** (EN 50325-4 / CiA301) | 工业自动化、运动控制 | **对象字典 OD**（每个参数有索引）、**PDO**（过程数据，周期性、快）、**SDO**（服务数据，按需读写参数）、NMT 网络管理、SYNC 同步 |
| **SAE J1939** | 商用车/重卡/工程机械/柴油机组 | 29 位 ID 拆成优先级+PGN（参数组号）+源/目的地址；数据用 **SPN** 描述；速率 250k/500k |
| **UDS / ISO 14229（诊断）+ ISO 15765-2（ISO-TP 传输层）** | 整车诊断、刷写 OTA、故障码 DTC | ISO-TP 把长诊断报文**分包**：SF 单帧 / FF 首帧 / CF 连续帧 / FC 流控帧；服务如 0x10 会话、0x22 读数据、0x2E 写、0x31 例程、0x11 复位、0x34/36/37 刷写 |
| SAE J1939-21 / NMEA2000 | 船舶、农机 | J1939 的行业变体 |

### 3.1 ISO-TP 分包（UDS 刷写必懂）

```text
发送长报文（>8字节）：
  发送方 → SF(单帧,≤7字节直接发) 或 FF(首帧,带总长度)
  接收方 → FC(流控：告诉对方每次发几帧、间隔多久)
  发送方 → CF(连续帧,带序号 SN 1,2,3...) 直到发完
```
这和 TCP 分片/应用层分帧是同一类问题：**底层帧有长度上限，上层必须自己编号、重组**，和《08-抓包分析与手写报文解析.md》里处理粘包半包的思路一致。

## 4. 车载网络全景（为"汽车方向"铺路）

一辆车里有几十上百个 ECU，不同部位对成本/速率/确定性要求不同，于是形成分层网络：

```text
            车载以太网 100/1000BASE-T1（域控、智驾、座舱骨干，SOME/IP、DDS）
          ┌───────────────────────────────────────────────┐
   动力/底盘 CAN/CAN FD（发动机、变速箱、ESP、EPS，实时可靠）
   车身 CAN/LIN（车窗、座椅、灯光、空调：LIN 做最末端低成本节点）
   安全线控 FlexRay（线控制动/转向，时间触发、确定性冗余，渐被以太网替代）
```

| 总线 | 速率量级 | 拓扑/机制 | 确定性 | 成本 | 典型部位 |
| --- | --- | --- | --- | --- | --- |
| **LIN** | 20kbps | **单主多从**、单线、按调度表轮询 | 高（主节点定节奏） | 极低 | 车窗、雨刮、座椅、空调风门 |
| **CAN / CAN FD** | 1M / 2~8M | 多主、事件触发、优先级仲裁 | 较高（高优先级有界） | 低 | 动力总成、底盘、车身主干 |
| **FlexRay** | 2×10M | 时间触发 TDMA、双通道冗余 | **最高（时隙确定）** | 高 | 线控转向/制动等功能安全关键 |
| **车载以太网** | 100M~10G | 单对非屏蔽双绞线 100BASE-T1、交换式 | 中（可加 TSN） | 中高 | 智驾域、座舱、中央计算、OTA |

- **为什么有了 CAN 还要 LIN**：CAN 控制器贵，车窗电机这类简单节点用便宜的 LIN 从机，挂在一个"CAN-LIN 网关"下，省成本。
- **为什么线控要用 FlexRay/TSN**：刹车指令必须在**确定的微秒级时刻**到达，CAN 的事件仲裁在高负载下低优先级帧会被延迟（不确定），时间触发网络给每个报文固定时隙，最坏时延可算——这是功能安全的要求。
- **趋势**：从"分布式 ECU + CAN 主干"走向"**域控制器 / 中央计算 + 区域控制器 + 车载以太网骨干，CAN/LIN 下沉到边缘**"，上层用 **SOME/IP（面向服务 SOA）、DDS**，详见《../01-C++技术体系/17-音视频游戏与AI/01-汽车软件与智能驾驶方向.md》。

## 5. 横向对比：CAN 与工业现场总线

工业现场常见总线（Modbus/IEC104）对比：

| 总线 | 层级/物理层 | 通信模型 | 实时性 | 典型场景 |
| --- | --- | --- | --- | --- |
| Modbus RTU | RS485 差分 | 一主多从、轮询请求-响应 | 一般（毫秒级） | 仪表、PLC |
| Modbus TCP | 以太网 TCP:502 | 主从、C/S | 一般 | 工业以太网、工业网关 |
| **CANopen** | CAN 差分 | 多主 + PDO/SDO | 高 | 伺服、运动控制、医疗 |
| Profibus-DP | RS485 | 主从轮询 | 高 | 工厂自动化（西门子系） |
| **EtherCAT** | 以太网帧但**不走交换机** | 主站帧"穿过"各从站、**on the fly 逐节点读写** | **极高（微秒级）** | 多轴运动控制、机器人 |
| PROFINET | 标准/实时以太网 | C/S + RT/IRT | 高 | 工厂自动化骨干 |

> EtherCAT 快的原因值得记：一个以太网帧从主站出发**依次穿过**所有从站，每个从站在帧经过的瞬间（硬件处理，不存整帧）就把自己的数据读/写进去，最后回到主站——全程**一帧完成全网同步刷新**，避免了每站"收包→协议栈→回包"的延迟。

## 6. Linux SocketCAN：把 CAN 当 socket 写（直接复用网络编程能力）

Linux 用 **SocketCAN** 把 CAN 抽象成网络接口（`can0`），API 和 UDP socket 几乎一样，这是 C++ 工程师上手最快的路径。

### 6.1 配置与抓包

```bash
# 加载虚拟 CAN（没硬件也能在本机调试）
sudo modprobe vcan
sudo ip link add dev vcan0 type vcan
sudo ip link set vcan0 up
# 真实 CAN 卡（如 USB-CAN，比特率 500k）
sudo ip link set can0 type can bitrate 500000
sudo ip link set can0 up

candump vcan0                 # 抓帧（can-utils 包）
cansend vcan0 123#1122334455667788     # 发标准帧 ID=0x123，8 字节
cansend vcan0 18FEF100##1.00112233      # '##1' 表示 CAN FD + BRS
```
Wireshark 也能直接抓 `vcan0/can0`；行业里 Vector **CANoe / CANalyzer**、PCAN-View、Kvaser 是常用工具，DBC 文件（数据库）用来把原始 ID/字节翻译成物理量（车速、转速）。

### 6.2 C++ 收发一帧

```cpp
#include <linux/can.h>
#include <sys/socket.h>
#include <sys/ioctl.h>
#include <net/if.h>
#include <unistd.h>
#include <cstring>
#include <iostream>

int main() {
    int s = socket(PF_CAN, SOCK_RAW, CAN_RAW);      // 和 UDP socket 同套路
    ifreq ifr{}; strcpy(ifr.ifr_name, "vcan0");
    ioctl(s, SIOCGIFINDEX, &ifr);
    sockaddr_can addr{};
    addr.can_family  = AF_CAN;
    addr.can_ifindex = ifr.ifr_ifindex;
    bind(s, (sockaddr*)&addr, sizeof(addr));

    can_frame tx{};
    tx.can_id  = 0x123;          // 标准帧；扩展帧要 CAN_EFF_FLAG，即 0x80000000|id
    tx.can_dlc = 8;
    for (int i = 0; i < 8; ++i) tx.data[i] = i + 1;
    write(s, &tx, sizeof(tx));   // 发送

    can_frame rx{};
    while (read(s, &rx, sizeof(rx)) > 0) {          // 阻塞收帧
        bool ext = rx.can_id & CAN_EFF_FLAG;
        unsigned id = rx.can_id & CAN_EFF_MASK;
        std::cout << std::hex << "id=" << id << (ext ? " ext" : " std")
                  << " dlc=" << std::dec << int(rx.can_dlc) << " data=";
        for (int i = 0; i < rx.can_dlc; ++i)
            std::cout << std::hex << int(rx.data[i]) << " ";
        std::cout << std::dec << "\n";
    }
}
// g++ can_demo.cpp -o can_demo
```

### 6.3 逐字节读一帧（对着 hex 看）

```text
标准数据帧  ID=0x0A0  DLC=8  data=01 02 03 04 05 06 07 08
  仲裁段 0x0A0 → 二进制 000 1010 0000，优先级高于 0x0A1（ID 越小越高）
  DLC=0x8 → 后面正好 8 字节数据
  若收到扩展帧，ID 取 29 位（CAN_EFF_MASK=0x1FFFFFFF），其余位是标志位
```

## 7. 快速参考卡片

```text
物理层：CAN_H/CAN_L 差分，显性0(线与拉低)/隐性1，两端各一个120Ω终端电阻
仲裁：多主、逐位线与、非破坏性，ID 越小优先级越高；仲裁只在ID段，数据段不许冲突
帧：SOF|仲裁(ID+RTR+IDE)|控制(DLC)|数据0~8B|CRC15|ACK|EOF；标准11位/扩展29位
可靠：位填充(5同插反) + CRC + ACK槽 + 错误帧；TEC/REC → 主动/被动错误/Bus-Off隔离
CAN FD：数据段提速(BRS)、数据最多64B、CRC更强；CAN XL 最多2048B
上层：CANopen(OD/PDO/SDO)、J1939(PGN/SPN,29位,商用车)、UDS诊断+ISO-TP(SF/FF/CF/FC分包)
车载：LIN(便宜单主,车身末端) < CAN/CAN FD(主干) < FlexRay(时间触发,线控) < 车载以太网(骨干/SOME-IP)
工业：Modbus RTU=RS485主从轮询；EtherCAT=帧穿过从站on-the-fly，微秒级
Linux：SocketCAN 把 can0 当 UDP socket；candump/cansend 调试，DBC 翻译物理量
```

## 8. 常见问题与坑

| 问题 | 原因 / 解决 |
| --- | --- |
| 通信时好时坏、速率上不去 | 终端电阻缺失/位置错（应在**物理两端**各 120Ω）；支线（stub）过长；波特率不一致 |
| 某节点频繁 Bus-Off | 该节点发送错误计数 >255：多半是波特率不匹配、总线干扰、ACK 槽无人应答（只接了自己一个节点） |
| 两个节点发同一 ID 数据冲突 | CAN 只仲裁 ID，数据段冲突会报错；同一 ID 只能一个发送源 |
| ID 越大越优先（搞反） | 显性 0 占线，**前导 0 越多即数值越小优先级越高** |
| 把 CAN ID 当地址找"发给谁" | CAN 是广播，ID 表示"消息内容"，接收方靠滤波器按需收 |
| UDS 刷写一到多字节就失败 | 没实现 ISO-TP 分包/流控，诊断报文超过 7 字节必须走 FF/CF/FC |
| CAN FD 帧被经典 CAN 节点收到报错 | 总线上混有不支持 FD 的节点；需全网 FD 兼容或分网段 |
| RS485 总线数据乱跳 | 半双工方向切换时机不对、未接偏置/终端、A/B 接反 |
