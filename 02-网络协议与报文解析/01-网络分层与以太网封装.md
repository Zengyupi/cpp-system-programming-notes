## 1. 两种分层模型与对应关系

| OSI 七层 | TCP/IP 四层 | 典型协议/单元 | 地址/标识 |
| --- | --- | --- | --- |
| 应用/表示/会话 | 应用层 | HTTP、Modbus TCP、IEC104、DNS | 端口 + 报文 |
| 传输 | 传输层 | TCP / UDP（段 Segment / 数据报） | 端口号 |
| 网络 | 网络层 | IP / ICMP（包 Packet） | IP 地址 |
| 数据链路 | 网络接口层 | 以太网 / VLAN（帧 Frame） | MAC 地址 |
| 物理 | 物理层 | 比特流、电平、串口 | 网口/总线 |

> 记忆：**每层只认自己的首部，把上层整体当数据**。路由器看 IP（三层），交换机看 MAC（二层），应用程序看应用层。

## 2. 封装与解封装（PDU 嵌套）

发送（自上而下加首部，必要时加尾部）：

```text
应用数据
  ├ TCP 头 + 应用数据            = TCP 段
  │   ├ IP 头 + TCP段            = IP 数据报
  │   │   ├ 以太网头 + IP数据报 + FCS = 以太网帧 ──→ 网线
接收端反向逐层剥掉首部，就是解封装 / 分用(demultiplex)：
  以太网类型 0x0800→交给IP；IP头 protocol=6→交给TCP；TCP端口→交给对应socket
```

一次完整分用的判断链（抓包时 Wireshark 就是这么逐层识别的）：

```text
EtherType=0x0800(IPv4) → IP.proto=6(TCP)/17(UDP)/1(ICMP)
   → TCP/UDP 目的端口 → 应用(80 HTTP / 502 Modbus / 2404 IEC104)
```

## 3. 以太网帧结构（Ethernet II，最常见）

```text
偏移 字节            字段            说明
0    6   目的 MAC (DMAC)            广播 ff:ff:ff:ff:ff:ff
6    6   源 MAC   (SMAC)
12   2   类型 Type (EtherType)      0x0800=IPv4 0x0806=ARP 0x86DD=IPv6 0x8100=VLAN
14   46~1500  载荷 (Payload)        不足 46 字节要 padding 填充
末尾 4   FCS 帧校验(CRC32)          网卡硬件算，抓包一般看不到
```

- **MTU 1500**：以太网**载荷**最大 1500 字节（不含以太网头/FCS），IP 数据报超过就要分片（见 02 篇）；
- 最小帧 64 字节（DMAC+SMAC+Type+载荷+FCS），载荷不足 46 补 0；
- 一段真实帧 hex 示例（前 14 字节是以太网头）：

```text
目的MAC            源MAC              Type
ff ff ff ff ff ff  00 0c 29 4a 2b 9e  08 06  ...(ARP 请求)
```

### 3.1 VLAN 标签（802.1Q，电力/工业现场常见）

交换机 Trunk、变电站双网冗余常带 VLAN。插入在 SMAC 与 Type 之间，**4 字节**：

```text
... SMAC | 81 00(TPID,标识带VLAN) | TCI(2B: PCP优先级+DEI+VID 12位VLAN号) | 真正的EtherType ...
```
看到 EtherType 是 `0x8100` 就要知道：真正的上层类型在后面偏移 4 字节处。

## 4. 大小端：网络字节序 = 大端（解析一切报文的前提）

- TCP/IP 首部所有多字节整数用**大端（Big-Endian，高位在前）**，也称网络字节序；
- x86/ARM 默认多为**小端**，所以解析报文必须转，不能直接强转取值。

```c
#include <arpa/inet.h>
uint16_t v = ntohs(*(uint16_t*)p);   // network to host (short,16位)
uint32_t x = ntohl(*(uint32_t*)p);   // 32位；发送用 htons/htonl
```

```python
import struct
v = struct.unpack(">H", p[0:2])[0]   # > 表示大端；H=uint16, I=uint32, B=uint8
```

> 反例（典型 bug）：在 x86 上直接 `*(uint16_t*)p` 读端口，读出来高低字节颠倒（如 0x1F90 变 0x901F）。**工业串口规约 Modbus RTU 也是大端**，而部分规约（如某些 IEC 系列）字段字节序有特殊规定，务必查手册。

## 5. 字节对齐：报文结构体禁止直接用 #pragma 外的默认布局

C 结构体为了访问效率会**填充(padding)**，和线上字节布局不一致，**绝不能直接 `memcpy` 网络字节到带填充的结构体**：

```cpp
// ✗ 错误：编译器可能在 a 和 c 之间填充，sizeof 也不等于线上长度
struct Bad { uint8_t a; uint32_t b; uint16_t c; };

// ✓ 方案1：单字节对齐（GCC）
#pragma pack(push, 1)
struct EthHdr { uint8_t dst[6]; uint8_t src[6]; uint16_t type; };
#pragma pack(pop)

// ✓ 方案2（更推荐、可移植）：逐字节/用 ntohs 手工取，避免对齐与别名问题
uint16_t type = ntohs(*(uint16_t*)(p + 12));
```

更安全的现代写法用 `std::span<const uint8_t>` 逐字段读取并做边界校验（见 07 篇）。

## 6. 数据是怎么被抓到的（抓包点）

```text
应用 send/recv
   │  ← tcpdump/libpcap 在这层通过 AF_PACKET 复制一份（不影响原流量）
socket 层
   │
内核协议栈(IP/TCP)
   │
网卡驱动/NIC ── 网线
```

- tcpdump/Wireshark 基于 libpcap，在**内核链路层**复制报文，所以能看到以太网头；
- **本机回环 lo**、交换机**别的端口**流量默认抓不到：交换机端口隔离，要做端口镜像；
- 多网口设备注意 `-i` 指定正确网卡（见《../01-C++技术体系/08-网络与系统工具/02-tcpdump网络抓包.md》）。

## 7. 快速参考卡片

```text
封装=逐层加头，解封装=按 EtherType→IP.proto→端口 逐层分用
以太网帧：DMAC6|SMAC6|Type2|载荷46~1500|FCS4；0x0800 IP,0x0806 ARP,0x8100 VLAN
MTU=1500(载荷)，最小帧64，不足补padding
网络序=大端：ntohs/ntohl 收，htons/htonl 发；Python struct 用 ">"
报文结构：禁默认对齐，#pragma pack(1) 或逐字节+span读取，必须边界校验
抓包：libpcap 在链路层复制；抓别人流量要端口镜像；多网口注意 -i
```

## 8. 常见问题与坑

| 问题 | 原因/解决 |
| --- | --- |
| 解析端口/长度数值对不上、字节颠倒 | 忘了大小端转换，用 ntohs/struct ">" |
| 结构体 sizeof 比报文大、字段错位 | 编译器 padding；pack(1) 或逐字节解析 |
| 只抓到本端口流量 | 交换机隔离，需镜像/SPAN；或在主机本机抓 |
| 大于 1500 的数据被切成多片 | IP 分片（02 篇）或 TCP 分段 MSS，别当成丢包 |
| 看到 0x8100 不会解析 | 是 VLAN 标签，上层 EtherType 后移 4 字节 |
| 强转指针在 ARM 上崩溃 | 非对齐访问异常；用 memcpy 或逐字节拼 |
