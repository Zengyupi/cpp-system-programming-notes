## 1. 音视频基础概念

### 1.1 音频基础

| 概念 | 说明 | 典型值 |
| --- | --- | --- |
| 采样率 Sample Rate | 每秒采样次数，奈奎斯特定理需 ≥2 倍最高频率 | 44.1kHz(CD)、48kHz(视频)、16kHz(电话) |
| 采样位深 Bit Depth | 每次采样位数，决定动态范围 | 16bit(65536级)、24bit |
| 声道 Channel | 单声道/立体声/5.1环绕 | 1/2/6 |
| 码率 Bitrate | 单位时间数据量 | 128kbps(AAC)、320kbps(MP3) |
| PCM | 原始未压缩音频数据 | WAV 格式存储 |

**音频数据量计算**：采样率 × 位深 × 声道数。例如 44.1kHz/16bit/立体声 = 44100×2×2 = 176400 B/s ≈ 172KB/s，一分钟约 10MB，所以必须压缩。

### 1.2 视频基础

| 概念 | 说明 | 典型值 |
| --- | --- | --- |
| 分辨率 Resolution | 像素尺寸 | 1920×1080(1080p)、3840×2160(4K) |
| 帧率 FPS | 每秒帧数 | 24(电影)、30、60(游戏) |
| 码率 Bitrate | 单位时间数据量 | 2~8Mbps(1080p)、10~25Mbps(4K) |
| YUV | 亮度(Y) + 色度(UV) 色彩空间，人眼对亮度更敏感 | YUV420P(I420)最常用 |
| 封装格式 Container | 把音视频流打包在一起的容器 | MP4、FLV、TS、MKV、MOV |
| 编码格式 Codec | 压缩音视频数据的算法 | H.264、H.265、VP9、AV1、AAC、Opus |

### 1.3 YUV 色彩空间与采样格式

YUV 分离亮度和色度，利用人眼对色度不敏感进行色度子采样：

| 格式 | 说明 | 压缩比 |
| --- | --- | --- |
| YUV444 | Y、U、V 每个像素都有 | 无压缩，专业领域 |
| **YUV420P(I420)** | 每 4 个 Y 共享 1 个 U 和 1 个 V，平面存储 | 2:1，最常用 |
| YUV422 | 每 2 个 Y 共享 1 个 U 和 1 个 V | 4:2:2 |
| NV12 | YUV420 的交错存储（UV 交替），移动端/硬编常用 | 同 I420 |

```text
I420 平面布局（4×4 像素示例）：
Y Y Y Y    U U    V V
Y Y Y Y    U U    V V
Y Y Y Y
Y Y Y Y
总字节 = width×height(Y) + width×height/4(U) + width×height/4(V) = 1.5 × w × h
```

## 2. 音视频处理全流程

```text
采集(摄像头/麦克风/屏幕) → 预处理(美颜/降噪/回声消除) → 编码(H.264/AAC)
  → 封装(MP4/FLV/TS) → 传输(RTMP/HLS/WebRTC) → 解封装(Demux)
  → 解码(Decode) → 后处理(渲染/混音) → 播放(显示/扬声器)
```

| 环节 | 说明 | 关键技术 |
| --- | --- | --- |
| 采集 | 摄像头/麦克风/屏幕捕获 | V4L2(Linux)、AVFoundation(macOS/iOS)、MediaFoundation(Windows)、DirectShow |
| 预处理 | 视频美颜/滤镜、音频降噪/AEC/AGC | OpenGL ES 滤镜、SpeexDSP/WebRTC AEC |
| 编码 | 压缩原始数据 | H.264/x264、H.265/x265、AAC、Opus；软编/硬编 |
| 封装 | 音视频流打包 | MP4(MOOV/MDAT)、FLV(Tag)、MPEG-TS |
| 传输 | 网络分发 | RTMP、HLS、DASH、WebRTC、SRT、RIST |
| 解码 | 还原原始数据 | FFmpeg 软解、MediaCodec/VideoToolbox 硬解 |
| 渲染 | 显示/播放 | OpenGL/Metal/D3D 渲染、AudioTrack/CoreAudio 播放 |

## 3. FFmpeg 核心架构与 API

FFmpeg 是音视频开发的瑞士军刀，核心库：
- **libavformat**：封装/解封装（demuxer/muxer）
- **libavcodec**：编解码（codec）
- **libavfilter**：滤镜（filter graph）
- **libswscale**：图像缩放/格式转换
- **libswresample**：音频重采样
- **libavutil**：工具函数

### 3.1 命令行常用操作

```bash
# 转码：mp4 → HLS 切片
ffmpeg -i input.mp4 -c:v libx264 -c:a aac -f hls -hls_time 10 output.m3u8
# 推流 RTMP
ffmpeg -re -i input.mp4 -c copy -f flv rtmp://server/live/stream
# 提取音频（不重编码）
ffmpeg -i input.mp4 -vn -acodec copy output.aac
# 截取片段
ffmpeg -ss 00:01:00 -i input.mp4 -t 30 -c copy output.mp4
# 缩放 + 硬编
ffmpeg -i input.mp4 -vf scale=1280:720 -c:v h264_nvenc output.mp4
# 滤镜：画中画 + 文字
ffmpeg -i main.mp4 -i overlay.mp4 -filter_complex "[1:v]scale=200:100[ov];[0:v][ov]overlay=10:10" output.mp4
```

### 3.2 解封装+解码流程（C/C++）

```c
// 1. 打开输入
avformat_open_input(&fmt_ctx, url, NULL, NULL);
avformat_find_stream_info(fmt_ctx, NULL);

// 2. 找到音视频流
int video_idx = av_find_best_stream(fmt_ctx, AVMEDIA_TYPE_VIDEO, -1, -1, NULL, 0);
AVCodecParameters* codecpar = fmt_ctx->streams[video_idx]->codecpar;

// 3. 初始化解码器
const AVCodec* codec = avcodec_find_decoder(codecpar->codec_id);
AVCodecContext* codec_ctx = avcodec_alloc_context3(codec);
avcodec_parameters_to_context(codec_ctx, codecpar);
avcodec_open2(codec_ctx, codec, NULL);

// 4. 读包→解码→取帧
AVPacket* pkt = av_packet_alloc();
AVFrame* frame = av_frame_alloc();
while (av_read_frame(fmt_ctx, pkt) >= 0) {
    if (pkt->stream_index == video_idx) {
        avcodec_send_packet(codec_ctx, pkt);        // 送包到解码器
        while (avcodec_receive_frame(codec_ctx, frame) == 0) {
            // frame->data[0]=Y, [1]=U, [2]=V; frame->width/height/pts
            // 用 sws_scale 转 RGB 后渲染
        }
    }
    av_packet_unref(pkt);
}
```

**关键对象关系**：`AVFormatContext`（文件/流上下文）→ `AVStream`（一条音/视频流）→ `AVCodecContext`（编解码器上下文）→ `AVPacket`（编码后数据包）→ `AVFrame`（解码后原始帧）。

### 3.3 编码+封装流程要点

编码是解码的逆过程：原始 `AVFrame` → `avcodec_send_frame` → `avcodec_receive_packet` 得到 `AVPacket` → 写入输出 `AVFormatContext`。注意：
- 时间基（time_base）转换：不同容器/流的时间基不同，PTS/DTS 需用 `av_rescale_q` 转换；
- 编码器延迟：B 帧编码需要后续帧，flush 时送 NULL frame 取出缓存帧；
- 封装时需先写文件头（`avformat_write_header`），写完后写尾（`av_write_trailer`）。

## 4. 视频编码：H.264 / H.265 原理

### 4.1 帧类型

| 帧类型 | 说明 | 压缩率 |
| --- | --- | --- |
| **I 帧（Intra）** | 关键帧，完整画面，不依赖其他帧，可独立解码 | 最低（类似 JPEG） |
| **P 帧（Predictive）** | 前向预测，参考前面 I/P 帧，只存差异（运动矢量+残差） | 较高 |
| **B 帧（Bidirectional）** | 双向预测，参考前后帧，压缩率最高，但增加延迟 | 最高 |
| **IDR 帧** | 特殊 I 帧，之后的帧不能参考 IDR 之前的帧，是随机访问点 | — |

- **GOP（Group of Pictures）**：两个 I 帧之间的帧序列，GOP 越大压缩率越高但随机访问/跳转越慢；
- **SPS/PPS**：序列/图像参数集，包含解码必需参数（分辨率、Profile、量化参数等），丢失会花屏。

### 4.2 H.264 编码核心步骤

```text
原始帧 → 分块(Macroblock 16×16 / H.265 CTU 64×64)
  → 帧内预测(Intra Prediction，I帧) / 运动估计+补偿(Inter Prediction，P/B帧)
  → 残差 → 变换(DCT/整数变换) → 量化(Quantization，控制码率和质量)
  → 熵编码(CABAC/CAVLC) → NAL 单元打包
```

| 概念 | 说明 |
| --- | --- |
| 运动估计 Motion Estimation | 在参考帧中搜索最匹配块，得到运动矢量(MV) |
| 运动补偿 Motion Compensation | 用 MV 从参考帧复制预测块 |
| DCT 变换 | 空间域→频率域，能量集中在低频 |
| 量化 Quantization | 除以量化步长，高频系数归零（有损压缩的核心） |
| CABAC | 上下文自适应二进制算术编码，H.264 主流，压缩率高但计算复杂 |

### 4.3 H.264 vs H.265(HEVC) vs AV1

| 特性 | H.264(AVC) | H.265(HEVC) | AV1 |
| --- | --- | --- | --- |
| 压缩率 | 基准 | 比 H.264 高约 **50%**（同画质码率减半） | 比 H.265 再高约 20~30% |
| 编码复杂度 | 较低 | 高（软编吃力，需硬编） | 很高 |
| 专利授权 | 复杂(MPEG-LA) | 更复杂 | 免版税(AOMedia) |
| 硬件支持 | 全平台 | 主流平台 | 新一代平台 |
| 应用 | 直播、监控、视频会议、Web | 4K/8K、超高清、移动端 | 互联网视频(YouTube/Netflix) |

### 4.4 x264 编码参数调优

```bash
# 预设(preset)：ultrafast→veryslow，越慢压缩率越高
# 调优(tune)：zerolatency(低延迟直播)、film(电影)、animation(动画)
# CRF(Constant Rate Factor)：0~51，18~28 常用，越小质量越高
ffmpeg -i input.mp4 -c:v libx264 -preset medium -tune zerolatency -crf 23 output.mp4
```

## 5. 音频编码

| 编码 | 特点 | 应用 |
| --- | --- | --- |
| **AAC** | 高级音频编码，MP3 后继，LC/HE-AAC 变体 | MP4、直播、视频会议（最通用） |
| **Opus** | 低延迟、高质量，混合 SILK(语音)+CELT(音乐) | WebRTC 标配、即时通信 |
| MP3 | 老牌，兼容性好 | 音乐播放（逐渐被 AAC 取代） |
| G.711 | 未压缩 PCM μ-law/A-law，64kbps | 电话系统 |
| FLAC | 无损压缩 | 音乐存档 |

**Opus 优势**：帧长可低至 2.5ms（极低延迟），码率 6~510kbps 自适应，语音和音乐都表现好，是 WebRTC 的必选音频编码。

## 6. 流媒体协议对比

| 协议 | 传输层 | 延迟 | 封装 | 典型场景 |
| --- | --- | --- | --- | --- |
| **RTMP** | TCP | 1~3s | FLV Tag | 直播推流（主播→服务器），国内主流 |
| **RTSP** | TCP/UDP(RTP) | 低 | RTP | 监控、点播、IP Camera |
| **HLS** | HTTP(TCP) | 10s+ | TS 切片 + m3u8 | 点播、移动端直播、跨平台 |
| **DASH** | HTTP(TCP) | 10s+ | MP4/WebM 切片 | 自适应码率，YouTube/Netflix |
| **WebRTC** | UDP(SRTP) | **<1s** | RTP | 实时通信、视频会议、互动直播 |
| **SRT** | UDP(ARQ) | 低 | MPEG-TS | 低延迟可靠传输，广电/贡献源 |
| **HTTP-FLV** | HTTP(TCP) | 1~3s | FLV | 国内直播拉流（长连接流式） |

### 6.1 HLS 工作原理

```text
切片器把直播流切成 5~10s 的 TS 小文件
  → 更新 m3u8 播放列表（索引文件）
  → CDN 分发 TS 文件和 m3u8
  → 播放器按序拉取 TS 切片并播放
```
HLS 延迟 = 切片时长 × 缓存切片数（通常 3~6 片），所以延迟较高但兼容性极好（iOS 原生支持）。

### 6.2 DASH 自适应码率

DASH（Dynamic Adaptive Streaming over HTTP）类似 HLS，但支持多码率表示（Representation），播放器根据带宽动态切换清晰度，MPD（Media Presentation Description）是索引文件。

## 7. WebRTC 架构与核心技术

WebRTC（Web Real-Time Communication）实现浏览器/移动端之间的实时音视频通信，延迟 < 500ms。

### 7.1 核心组件

| 组件 | 作用 |
| --- | --- |
| **ICE** | 网络穿透框架，收集候选地址（host/srflx/relay），按优先级配对连通性检查 |
| **STUN** | 让 NAT 后的设备发现自己的公网 IP:端口 |
| **TURN** | 中继转发，P2P 打不通时用 TURN 服务器转发（有带宽成本） |
| **DTLS** | 建立加密通道，协商 SRTP 密钥 |
| **SRTP** | 加密的 RTP，媒体数据加密传输 |
| **SDP** | 会话描述协议，交换媒体能力（编码、分辨率、码率） |
| **信令 Signaling** | 交换 SDP 和 ICE 候选（WebSocket/HTTP，WebRTC 不规定信令） |

### 7.2 连接建立流程

```text
1. 信令交换 SDP（Offer/Answer）：协商编码、分辨率、加密
2. ICE 候选交换：收集 host/srflx(STUN)/relay(TURN) 地址
3. 连通性检查（STUN Binding Request）：找到可用的 P2P 路径
4. DTLS 握手：协商 SRTP 密钥
5. SRTP 媒体传输：音视频加密传输
6. 持续：NACK/PLI 丢包重传、TWCC 带宽估计、码率自适应
```

### 7.3 WebRTC 三大难点

1. **NAT 穿透**：对称型 NAT 无法 P2P，必须 TURN 中继；
2. **音视频同步**：RTCP 时间同步、抖动缓冲（Jitter Buffer）排序和缓冲；
3. **弱网对抗**：FEC（前向纠错）、NACK（负向确认重传）、码率自适应（GCC/BBR 拥塞控制）、SVC（可伸缩视频编码）。

## 8. 硬件编解码

| 方案 | 平台 | 说明 |
| --- | --- | --- |
| **NVENC/NVDEC** | NVIDIA GPU | 编码/解码，性能强，支持 H.264/H.265/AV1 |
| **QSV(Quick Sync)** | Intel 核显 | 编解码，功耗低，适合服务器 |
| **AMF** | AMD GPU | 编解码 |
| **VideoToolbox** | Apple | 硬编硬解，macOS/iOS 原生 |
| **MediaCodec** | Android | 硬编硬解，跨芯片厂商 |
| **MFC / VPU** | ARM SoC | 嵌入式/移动端，瑞芯微/海思等 |

**软硬编选择**：
- 软编（x264/x265）：画质好、参数丰富、CPU 占用高，适合离线转码；
- 硬编：速度快、CPU 占用低、画质略逊、延迟较高，适合实时直播/移动端；
- 生产环境常用：推流软编（画质优先）+ 转码硬编（并发路数多）。

## 9. 关键工程问题

### 9.1 音画同步

- PTS（Presentation Time Stamp）：显示时间戳，决定何时播放；
- DTS（Decoding Time Stamp）：解码时间戳，B 帧时 DTS ≠ PTS；
- 音频是同步基准（音频时钟更稳定），视频跟随音频，偏差大时丢帧/重复帧追赶。

### 9.2 首帧时间与延迟优化

- 首帧时间 = 连接建立 + 首片下载 + 解码 + 渲染；
- 优化：GOP 对齐（首片含 I 帧）、预加载、CDN 就近、硬解、降低起始码率；
- 直播低延迟方案：HTTP-FLV（长连接）、WebRTC、SRT、低延迟 HLS（LL-HLS，分片 1~2s + CMAF）。

### 9.3 丢包与卡顿

- 视频卡顿 = 接收端缓冲区空了，原因：网络抖动、带宽不足、解码慢；
- 对策：抖动缓冲（平滑播放）、自适应码率（ABR）、CDN 多线路、P2P 辅助。

```text
流程：采集→预处理→编码→封装→传输→解封装→解码→渲染
音频：PCM=采样率×位深×声道；AAC通用/Opus低延迟(WebRTC标配)
视频：YUV420P最常用(1.5×w×h字节)；封装≠编码(MP4是容器,H.264是编码)
H.264：I/P/B帧+GOP；SPS/PPS不能丢；DCT+量化+CABAC；H.265省50%码率
FFmpeg：avformat(封装)+avcodec(编解码)+avfilter(滤镜)+swscale(转换)
  解码：read_frame→send_packet→receive_frame；编码反向
协议：RTMP推流(1-3s) / HLS切片(10s+) / WebRTC(UDP,<1s) / HTTP-FLV拉流
WebRTC：ICE(STUN打洞+TURN中继)+DTLS+SRTP；难点=NAT穿透/同步/弱网
硬编：NVENC/QSV/VideoToolbox/MediaCodec；软编画质好，硬编速度快
同步：音频为基准，PTS控制播放，B帧DTS≠PTS
```

## 12. 常见问题与坑

1. **时间戳（PTS/DTS）未正确换算**：音画不同步，必须用 `av_rescale_q` 在不同 time_base 间转换。
2. **H.264 丢 SPS/PPS**：播放器花屏或无法解码，SPS/PPS 必须在关键帧前发送或存在容器头里。
3. **RTMP 推流未用 `-re`**：非实时速率推流导致服务器积压，`-re` 按原生帧率推送。
4. **软编 4K 卡顿**：CPU 跑满，启用硬编（h264_nvenc/h264_videotoolbox）或降分辨率/帧率。
5. **WebRTC 未做丢包重传与码率自适应**：弱网卡顿花屏，启用 NACK/FEC/GCC 拥塞控制。
6. **YUV 格式不匹配**：硬编要求 NV12，软编用 I420，用 `sws_scale` 或 `libyuv` 转换。
7. **内存泄漏**：`av_packet_alloc`/`av_frame_alloc` 必须 `av_packet_free`/`av_frame_free`，每帧 `av_packet_unref`。
8. **首帧慢**：起始分片不含 I 帧，确保 GOP 对齐和首片从 IDR 开始。
9. **B 帧导致延迟**：直播低延迟场景关闭 B 帧（`-bf 0`），用 zerolatency tune。
10. **播放器缓冲策略不当**：固定缓冲导致高延迟或频繁卡顿，用自适应缓冲（ABR + 动态缓冲水位）。
