## 1. 推理部署全景：从训练框架到线上服务

训练关注"怎么把模型学出来"，部署关注"怎么又快又省又稳地跑前向（inference）"。

```text
 训练侧（Python，离线）                部署侧（C++/引擎，在线/端侧）
 ┌──────────────┐   导出/转换   ┌──────────────┐   编译/优化   ┌─────────────┐
 │ PyTorch/TF   │ ───────────► │ 中间模型格式  │ ───────────► │ 推理引擎     │
 │ .pt/.pth     │   torch.onnx │ ONNX/gguf/...│  层融合/量化  │ Runtime/SDK │
 └──────────────┘   export     └──────────────┘   内存规划    └──────┬──────┘
                                                                     │ 加载/推理
                                                          ┌──────────▼──────────┐
                                                          │ 应用：服务/边缘设备   │
                                                          │ HTTP/gRPC、C++ 进程  │
                                                          └─────────────────────┘
```

| 阶段 | 关键动作 | 产出 |
| --- | --- | --- |
| 导出 | 把训练框架的动态图固化成静态中间表示 | `model.onnx`（通用）、`model.gguf`（LLM） |
| 编译优化 | 层融合、常量折叠、精度量化、算子选型/kernel autotune | TensorRT `engine`、NCNN `.param/.bin` |
| 运行时 | 分配输入输出、拷贝张量、执行、取结果 | C++ 进程内调用 / 独立推理服务 |
| 服务化 | 批处理、并发、扩缩容、监控 | Triton / 自研 gRPC 服务 |

> **关键认知**：训练用 Python 不代表部署也要 Python。线上高并发/端侧场景几乎都用 **C++ 推理引擎**——没有 GIL、启动快、内存可控、可交叉编译到 ARM。Python 主要用于导出转换和离线验证。

## 2. 模型格式：.pt / .onnx / .engine / .gguf 都是什么

| 格式 | 来源 | 特点 | 用途 |
| --- | --- | --- | --- |
| `.pt/.pth` | PyTorch | 训练态权重/脚本，含动态图，依赖 Python 训练代码 | 训练、继续微调 |
| **ONNX** | 开放标准（微软/FB） | 跨框架的**计算图中间表示**，算子标准化、带 opset 版本 | **部署交换格式的事实标准** |
| TensorRT `engine/plan` | NVIDIA | 针对**具体某张卡、某个 TRT 版本**编译出的二进制，换卡/换版本可能不通用 | NVIDIA GPU 生产推理 |
| `.tflite` | Google | 轻量、为移动端/微控制器优化 | Android、Coral TPU |
| NCNN `.param+.bin` | 腾讯 | 图结构与权重分离，无第三方依赖、ARM 优化好 | 移动端/嵌入式 CPU |
| `.gguf` | llama.cpp 生态 | 单文件打包 LLM 权重+元信息+分词器，支持多种量化 | **本地跑大模型** |
| OpenVINO IR | Intel | xml+bin，面向 Intel CPU/iGPU/NPU | Intel 平台 |

### 2.1 ONNX 为什么是枢纽

ONNX 用一组标准算子（Conv、MatMul、Softmax、Attention…）描述计算图，`opset` 版本决定可用算子集。PyTorch、TF、Paddle 都能导出成 ONNX，ONNX Runtime、TensorRT（通过 ONNX parser）、OpenVINO 都能吃 ONNX，于是它成了"一次导出、多端运行"的枢纽。

```python
# 导出（Python，离线做一次）
import torch
model.eval()
dummy = torch.randn(1, 3, 224, 224)
torch.onnx.export(model, dummy, "model.onnx",
                  input_names=["input"], output_names=["logits"],
                  dynamic_axes={"input": {0: "batch"},      # 批大小动态
                                "logits": {0: "batch"}},
                  opset_version=17)
# 校验：python -m onnxruntime.tools.check_onnx_model_mobile_usability ...
```

**两个高频坑**：①opset 太低不支持新算子（如某些 Attention），太高老引擎不认；②动态维度（变长 batch/序列）若导出时写死，线上只能固定形状。

## 3. 主流推理引擎选型（面试与工程都要会比）

| 引擎 | 厂商 | 主攻硬件 | 授权 | 最适合 |
| --- | --- | --- | --- | --- |
| **TensorRT** | NVIDIA | NVIDIA GPU | 闭源免费 | NVIDIA 卡上**极致延迟/吞吐**，生产首选 |
| **ONNX Runtime** | 微软 | CPU/GPU(可挂 CUDA/TensorRT EP) | MIT 开源 | **跨平台、上手快、一套代码多后端**，服务端通用首选 |
| **libtorch** | PyTorch | CPU/GPU | BSD | 不想转 ONNX、直接 C++ 加载 TorchScript |
| **NCNN** | 腾讯 | 手机/ARM CPU（部分 GPU/NPU） | MIT | 无依赖、嵌入式/移动端 CPU |
| **MNN** | 阿里 | 移动/端侧 CPU/GPU/NPU | Apache | 端侧、手淘系 |
| **TFLite** | Google | 移动/MCU | Apache | Android、微控制器（micro） |
| **OpenVINO** | Intel | Intel CPU/iGPU/VPU | Apache | Intel 平台、工业相机/工控机 |
| **llama.cpp** | 社区 | CPU 为主（CUDA/Metal/Vulkan 后端） | MIT | **CPU/边缘本地跑 LLM**，量化生态最全 |
| **DeepSpeed/FasterTransformer/vLLM** | 社区 | 多卡 GPU | 开源 | 大模型高吞吐服务（vLLM 偏 Python 服务，核心 C++/CUDA） |

> 选型决策树：**NVIDIA 服务器追性能 → TensorRT；要跨平台/快速落地 → ONNX Runtime；ARM 端侧无 GPU → NCNN/MNN 或 llama.cpp；Intel 工控机 → OpenVINO；本地大模型 → llama.cpp/gguf。**

## 4. ONNX Runtime C++ 实战（最通用的一套）

### 4.1 CMake 集成

```cmake
find_package(onnxruntime CONFIG REQUIRED)   # 或直接指定头文件/库路径
add_executable(infer_demo main.cpp)
target_link_libraries(infer_demo PRIVATE onnxruntime::onnxruntime)
```

### 4.2 最小可运行推理流程

```cpp
#include <onnxruntime_cxx_api.h>
#include <vector>
#include <iostream>

int main() {
    Ort::Env env(ORT_LOGGING_LEVEL_WARNING, "demo");
    Ort::SessionOptions opt;
    opt.SetIntraOpNumThreads(4);                 // CPU 线程数，不是越多越好
    opt.SetGraphOptimizationLevel(
        GraphOptimizationLevel::ORT_ENABLE_EXTENDED);
    // opt.AppendExecutionProvider_CUDA(0);      // 有 GPU 时挂 CUDA EP

    Ort::Session session(env, "model.onnx", opt);
    Ort::AllocatorWithDefaultOptions alloc;
    auto in_name = session.GetInputNameAllocated(0, alloc);
    auto out_name = session.GetOutputNameAllocated(0, alloc);
    const char* in_names[] = {in_name.get()};
    const char* out_names[] = {out_name.get()};

    // 输入：1x3x224x224 NCHW，这里用假数据
    std::array<int64_t, 4> shape{1, 3, 224, 224};
    std::vector<float> input(1 * 3 * 224 * 224, 0.0f);
    auto mem = Ort::MemoryInfo::CreateCpu(OrtArenaAllocator, OrtMemTypeDefault);
    Ort::Value in_tensor = Ort::Value::CreateTensor<float>(
        mem, input.data(), input.size(), shape.data(), shape.size());

    auto outputs = session.Run(
        Ort::RunOptions{nullptr}, in_names, &in_tensor, 1, out_names, 1);
    float* logits = outputs[0].GetTensorMutableData<float>();
    // 后处理：softmax / argmax ...
    std::cout << "infer ok\n";
}
```

固定五件套：**创建环境 Env → 配置 SessionOptions → 加载 Session → 构造输入 Tensor → Run 取输出**。优化点：Session 只建一次（贵）、输入输出缓冲复用（别每次 malloc）、多请求用线程池。

### 4.3 Execution Provider（EP）：同一套 API 换后端

ONNX Runtime 把硬件加速做成可插拔 EP：CPU EP（默认）、CUDA EP、TensorRT EP、OpenVINO EP、CoreML EP 等。代码几乎不变，只改 `AppendExecutionProvider_xxx`，这是它跨平台的核心。

## 5. TensorRT：NVIDIA GPU 上榨干性能

### 5.1 优化手段（面试高频）

| 优化 | 原理 | 收益 |
| --- | --- | --- |
| **层融合（layer fusion）** | Conv+BN+ReLU、多个小算子合并成一个 kernel，减少显存往返与启动次数 | 降低 kernel launch 与带宽开销 |
| **精度量化** | FP32 → FP16/INT8，用 Tensor Core、减半显存/带宽 | 吞吐常翻倍数倍 |
| **kernel auto-tuning** | 针对当前 GPU、形状从多种算法里选最快的 | 选到最优 cuDNN/cuBLAS 算法 |
| **显存复用** | 生命周期不重叠的张量共用显存 | 显著降显存占用 |
| **动态形状 profile** | 为动态 batch/尺寸预设 min/opt/max 范围 | 支持变长同时保持优化 |

### 5.2 两条构建路径

```bash
# 路径一：trtexec 命令行，最快验证
trtexec --onnx=model.onnx --saveEngine=model.engine --fp16 \
        --minShapes=input:1x3x224x224 \
        --optShapes=input:8x3x224x224 \
        --maxShapes=input:32x3x224x224

# 路径二：C++ builder API（生产可控）
# createInferBuilder -> network -> parser(ONNX) -> config(setFlag kFP16/kINT8)
# -> buildSerializedNetwork -> 反序列化 engine -> createExecutionContext -> enqueueV2/V3
```

> **engine 与硬件/版本强绑定**：在 A 卡、TRT 8.6 编译的 engine，拿到 B 卡或 TRT 8.2 可能直接加载失败。生产做法是**在目标机型上构建 engine 或按机型缓存多份**，不要指望一个 engine 走天下。底层 CUDA 线程/显存模型见《04-GPU与CUDA编程.md》。

## 6. 量化：精度、显存、速度的三角权衡

### 6.1 数值精度谱系

| 精度 | 位宽 | 特点 |
| --- | --- | --- |
| FP32 | 32 | 训练基准，精度最高、最慢最占显存 |
| **FP16** | 16 | 动态范围与 FP32 接近（有指数位），Tensor Core 加速，**几乎不掉点，首选** |
| BF16 | 16 | 指数位与 FP32 相同、动态范围大、尾数少，训练/推理都常用（A100 后） |
| **INT8** | 8 | 整数运算、省带宽，需校准，**可能掉点** |
| INT4 / 4bit | 4 | LLM 主流压缩（Q4_K_M 等），用极小精度损失换大幅提速/省内存 |

### 6.2 PTQ 与 QAT

- **PTQ（训练后量化）**：拿一小批代表性数据做**校准（calibration）**，统计各层激活分布（直方图/熵/KL 散度、最大最小、百分位），直接量化，**无需重训，工程首选**。
- **QAT（量化感知训练）**：训练时模拟量化误差，精度最好但要重训、成本高，PTQ 掉点不可接受时才上。

### 6.3 量化掉点怎么排查

```text
1. 先 FP16 跑通对比 FP32（基本不掉点，确认流程对）
2. 再 INT8 PTQ，校准集要覆盖真实输入分布（别只用一张图/一类样本）
3. 分层对比输出，定位掉点最严重的层，对该层取消量化（混合精度）
4. 敏感层（首尾层、Softmax/LayerNorm）通常保留高精度
```

### 6.4 LLM 的量化（gguf / Q4、KV Cache 量化）

大模型权重巨大，4bit 量化让 7B 模型在 16G 内存、甚至高配笔记本上可跑。`Q4_K_M` 是体积/质量的常用甜点；除权重外，**KV Cache 也可量化（Q8/Q4）**进一步降长上下文内存，代价是轻微质量下降。

## 7. CPU / 端侧优化（没有独显也要快）

### 7.1 向量化 SIMD：让一条指令算多个数

CPU 推理快不快，很大程度看有没有用上向量指令（原理呼应《../02-系统原理/03-系统架构与选型.md》的指令集章节）。

| 架构 | 向量指令集 | 单指令数据宽度演进 |
| --- | --- | --- |
| x86 | SSE → AVX → AVX2 → **AVX-512** | 128 → 256 → 512 bit |
| ARM | NEON（128bit）→ **SVE/SVE2**（可变长向量） | 128 bit 起 |

```cpp
// 朴素：一次算一个
for (int i = 0; i < n; ++i) c[i] = a[i] * b[i];
// 向量化：AVX2 一条指令处理 8 个 float；工程上一般不手写，
// 而是：①编译器自动向量化 -O3 -march=native ②用 oneDNN/Eigen/BLAS ③引擎内置
```

工程要点：**循环连续访问（别跳步）、内存对齐（`alignas(32/64)`）、用 `-march=native` 让编译器按当前 CPU 出向量指令、热点 GEMM 交给 OpenBLAS/oneDNN**。跨 x86/ARM 发布时别在老机器上用了它不支持的 AVX-512（会非法指令崩溃），要么做多版本分发，要么按目标最低支持指令集编译。

### 7.2 其他端侧优化清单

- **内存布局**：NCHW vs NHWC，匹配硬件/引擎偏好，避免反复转置。
- **算子融合 / Winograd 卷积**：引擎内置，理解原理即可。
- **线程数与绑核**：端侧小核大核（ARM big.LITTLE）别全占满，注意与业务线程争抢，必要时绑大核、关 SMT 干扰。
- **权重常驻、零拷贝**：权重 mmap 进内存（llama.cpp/NCNN 都这么做），减少加载内存与启动时间。
- **预热（warmup）**：首次推理含编译/内存分配，线上先空跑几次再计时/接流量。

## 8. 本地大模型（LLM）推理：llama.cpp 范式

### 8.1 为什么 LLM 推理和普通模型不是一回事

- **自回归生成**：一个 token 一个 token 往外吐，每步都要读一遍全部权重 → **内存带宽受限**（不是算力受限），这解释了为什么量化和带宽对 LLM 尤其关键。
- **KV Cache**：缓存历史 token 的 Key/Value 避免重算，随上下文线性增长，是长文本显存/内存大头。
- **两个性能指标要分清**：**TTFT（首 token 延迟，prefill 阶段，算力敏感）** 与 **TPOT/吞吐（每 token 耗时 / token·s，decode 阶段，带宽敏感）**。

### 8.2 llama.cpp 常用流程

```bash
# 1) 拿到 HuggingFace 上的模型，转/下载 gguf 量化版（如 Q4_K_M）
# 2) 启动本地推理服务（自带 OpenAI 兼容 HTTP 接口）
./llama-server -m qwen2.5-7b-instruct-q4_k_m.gguf \
               -c 4096 -ngl 0 -t 8 --port 8080
#   -ngl：卸载到 GPU 的层数（纯 CPU 设 0）；-c 上下文长度；-t 线程
# 3) C++ 程序像调普通 HTTP 接口一样访问，或链接 llama.h 做进程内推理
```

### 8.3 高吞吐服务化技术（了解概念，面试加分）

| 技术 | 解决什么 |
| --- | --- |
| **Continuous batching（连续批处理/动态批）** | 传统静态批等最慢的请求；动态批逐 step 进出，GPU 利用率大幅提升（vLLM 核心） |
| **PagedAttention** | 像操作系统管内存分页一样管 KV Cache，减少碎片、提升并发 |
| **Speculative Decoding** | 小模型先草拟、大模型并行校验，降延迟 |
| **张量并行/流水线并行** | 一个模型拆多卡/多机 |

## 9. 模型服务化：把推理能力变成高可用服务

### 9.1 两种形态

- **进程内嵌**：C++ 业务进程直接链接推理引擎（延迟最低，适合端侧/单体网关）。
- **独立推理服务**：模型单独成服务，业务通过 HTTP/gRPC 调用（便于独立扩缩容、多模型统一管理）。

### 9.2 Triton Inference Server（NVIDIA，生产级）

统一托管 TensorRT/ONNX/PyTorch 等多框架模型，提供：
- **dynamic batching**：攒一小段时间窗口的请求合批，提升吞吐（用可接受的微小排队延迟换高吞吐）；
- **多模型实例 / 多 GPU、模型版本管理与热更新、就绪/存活探针、Prometheus 指标**；
- 并发模型（默认单实例串行 vs 多实例并行）按延迟/吞吐目标配置。

### 9.3 自研服务要点

用《../03-网络编程/02-IO多路复用与Reactor模型.md》的 Reactor/线程池承载连接，推理任务丢进**独立推理线程池/队列**（避免阻塞 IO 线程），注意：
- 推理引擎 Session/Context 是否线程安全（通常**一个 Context 同时只能跑一次推理**，多并发要 Context 池）；
- 输入输出张量缓冲**对象池复用**，避免每请求大块 malloc；
- 批处理队列 + 超时，兼顾吞吐与尾延迟；
- 限流、超时、降级（模型超时返回兜底结果）。

## 10. 性能度量与压测（数字要能说出口）

| 指标 | 含义 | 关注点 |
| --- | --- | --- |
| **延迟 Latency**（均值/P50/**P99**） | 单次推理耗时 | 交互场景看 P99 尾延迟，别只看平均 |
| **吞吐 Throughput** | 每秒请求数 QPS / 每秒 token | 批量场景核心 |
| **TTFT / TPOT** | LLM 首 token / 后续每 token | 对话体验 |
| 显存/内存占用、功耗 | 资源成本 | 端侧看功耗与发热（嵌入式硬约束） |
| 精度指标 | 分类 acc、mAP、LLM 困惑度等 | 量化前后对比 |

工具：NVIDIA 用 `nsys`(Nsight Systems)/`nsight-compute` 看 timeline 与 kernel；CPU 用 `perf`（见《../07-调试与测试/03-perf性能剖析.md》）；压测脚本用 Python 并发打流并统计 P99（见《../06-构建与版本控制/05-Python脚本与自动化.md》5.4）。**所有优化数字必须 A/B 实测，禁止"感觉变快"。**

## 12. 快速参考卡片

```text
链路：PyTorch --导出--> ONNX --编译--> 引擎(TRT/ORT/NCNN/llama.cpp) --服务化--> C++/边缘
格式：交换用 ONNX；NVIDIA 用 engine(绑卡绑版本)；LLM 用 gguf；端侧 NCNN/TFLite/RKNN
选型：NVIDIA 追性能 TensorRT；跨平台 ONNX Runtime；ARM CPU NCNN；本地 LLM llama.cpp
量化：先 FP16(几乎不掉点) 再 INT8(PTQ校准,敏感层保高精度)；LLM 用 Q4_K_M

服务：Context 非线程安全要建池；张量缓冲复用；dynamic batching 换吞吐；P99 说话
度量：P50/P99 延迟、QPS/token-s、显存内存功耗；量化前后比精度；用 nsys/perf 实测
```

## 13. 常见问题与坑

| 问题 | 原因与解决 |
| --- | --- |
| 导出的 ONNX 在引擎里报"不支持的算子" | opset 不匹配或引擎未实现该算子。升 opset/引擎版本，或用 `onnx-simplifier` 化简、替换为等价算子 |
| 固定 batch 训练、线上想变 batch | 导出时用 `dynamic_axes`，TRT 配 min/opt/max profile |
| INT8 后精度明显下降 | 校准集不具代表性或敏感层被量化。扩大校准集、改校准算法、对首尾/归一化层保 FP16 混合精度 |
| TRT engine 换机器加载失败 | engine 绑定 GPU 型号与 TRT 版本。在目标机构建或分机型缓存 |
| CPU 推理在老 CPU 直接非法指令崩溃 | 编译用了过高 SIMD（如 AVX-512）。按最低支持指令集编译或做多版本分发 |
| 多线程并发调同一个 Context 结果错乱/崩溃 | 推理 Context 通常非线程安全。每线程一个 Context 或加 Context 池+串行执行 |
| 首帧/首请求特别慢 | 首次含图优化/内存分配。服务启动后先 warmup 再接入流量 |
| 端侧 NPU 模型反而更慢 | 数据在 CPU↔NPU 间反复拷贝抵消了加速。尽量让整网在 NPU、减少来回拷贝与格式转换 |
| LLM 上下文一长就爆内存/变慢 | KV Cache 线性增长。限制上下文、KV 量化、分页管理、必要时滑窗 |
| 只报平均延迟、上线被 P99 打爆 | 均值掩盖尾延迟。必须统计 P95/P99，配合批处理超时与限流 |
| Python 跑通但 C++ 结果对不上 | 预处理不一致（归一化均值方差、BGR/RGB、NCHW/NHWC、量化零点）。逐层对齐输入张量 |
