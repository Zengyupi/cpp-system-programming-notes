## 1. 池化思想

池化的本质是**预先分配一组资源，循环复用**，规避频繁申请/释放的开销。核心收益：减少系统调用、降低锁竞争、消除内存碎片、提升缓存局部性。

| 池类型 | 复用对象 | 规避的开销 | 典型场景 |
| --- | --- | --- | --- |
| 内存池 | 内存块 | malloc/free 系统调用、锁竞争、碎片 | 高频小块分配、消息处理 |
| 线程池 | 线程 | 线程创建/销毁（~10μs~ms 级）、栈分配 | 任务调度、异步处理 |
| 连接池 | DB/Redis/HTTP 连接 | TCP 握手、TLS 握手、认证 | 数据库访问、缓存操作 |
| 对象池 | C++ 对象实例 | 构造/析构、内存分配 | 频繁创建销毁的大对象 |
| 协程池 | 协程 | 协程创建/栈分配 | 高并发异步框架 |

**池化的代价**：预分配资源占用内存（空闲时也占着）、需要管理借出/归还的生命周期、可能出现资源耗尽等待。选型时衡量"创建开销 vs 池管理开销"——创建开销越大、使用越频繁，池化收益越大。

## 2. 内存池

### 2.1 为什么需要内存池

| 问题 | 说明 | 量化 |
| --- | --- | --- |
| 系统调用开销 | malloc 底层通过 brk/mmap 向内核申请，涉及锁和页分配 | 单次 malloc 约 50~200ns（已在用户态缓存时），首次分配更慢 |
| 多线程锁竞争 | ptmalloc 的 arena 锁，高并发下 malloc 成为瓶颈 | 线程数 > 8 时吞吐急剧下降 |
| 内存碎片 | 频繁分配释放不同大小块，产生外部碎片（空闲但无法利用） | 长期运行服务 RSS 持续上涨 |
| 缓存不友好 | malloc 返回的地址随机，对象分散在不同缓存行 | 缓存命中率低，性能差 |

内存池从一大块连续内存中切分，空闲块用链表串联，分配 O(1)，释放 O(1)，且地址连续缓存友好。

### 2.2 内存池分类

| 类型 | 原理 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 固定大小池 | 所有块大小相同，空闲链表 | 最简单、O(1)、无碎片 | 只能分配固定大小 | 对象池、消息块 |
| 可变大小池 | 按大小分级（size class），每级一个固定池 | 灵活、接近通用分配器 | 实现复杂 | 通用内存分配（jemalloc/tcmalloc） |
| Slab 分配器 | 按 2 的幂分级，每个 slab 管理一组同大小对象 | 内核采用，无外部碎片 | 内部碎片（大对象浪费） | Linux 内核、memcached |
| Arena/区域池 | 一大块内存顺序分配（bump pointer），整体释放 | 分配极快（指针++）、无需单独 free | 只能整体释放，不能单独回收 | 编译期临时分配、请求级内存 |
| Buddy 伙伴系统 | 按 2 的幂分块，分配时分裂、释放时合并 | 外部碎片少、合并高效 | 内部碎片（最大浪费近 50%） | Linux 内核物理页分配 |
| 内存池+malloc fallback | 小对象走池，大对象走 malloc | 兼顾性能与灵活性 | 两套管理 | 生产级自定义池 |

### 2.3 固定大小内存池实现

```cpp
// 固定大小内存池：空闲链表 + 大块 chunk
template <size_t BlockSize, size_t ChunkBlocks = 1024>
class FixedMemoryPool {
    struct Block { Block* next; };           // 空闲块用前几个字节存 next 指针
    Block* free_list_ = nullptr;
    std::vector<char*> chunks_;               // 所有大块，析构时统一释放
    std::mutex mtx_;                          // 多线程安全（也可做线程局部无锁）
public:
    static_assert(BlockSize >= sizeof(void*), "BlockSize too small");

    void* allocate() {
        std::lock_guard<std::mutex> lk(mtx_);
        if (free_list_) {                     // 有空闲块，O(1) 取
            Block* p = free_list_;
            free_list_ = p->next;
            return p;
        }
        // 无空闲块，分配新 chunk 并切成空闲链表
        char* chunk = new char[BlockSize * ChunkBlocks];
        chunks_.push_back(chunk);
        for (size_t i = 0; i < ChunkBlocks; ++i) {
            Block* b = reinterpret_cast<Block*>(chunk + i * BlockSize);
            b->next = free_list_;
            free_list_ = b;
        }
        Block* p = free_list_;
        free_list_ = p->next;
        return p;
    }
    void deallocate(void* p) {
        if (!p) return;
        std::lock_guard<std::mutex> lk(mtx_);
        Block* b = static_cast<Block*>(p);
        b->next = free_list_;
        free_list_ = b;
    }
    ~FixedMemoryPool() {
        for (char* c : chunks_) delete[] c;
    }
};
```

**关键设计点**：
- 空闲块的前 `sizeof(void*)` 字节复用为 next 指针（块已空闲，内容无意义）。
- `BlockSize >= sizeof(void*)` 静态断言，否则放不下指针。
- chunk 统一管理，析构时批量释放，避免小块泄漏。
- 多线程用锁保护；高性能场景用**线程局部缓存**（每个线程一个 free_list，无锁）+ 跨线程归还时加锁。

### 2.4 Arena 分配器（Bump Pointer）

```cpp
class Arena {
    char* cur_; char* end_;
    std::vector<char*> blocks_;
    static constexpr size_t kBlockSize = 4096;
public:
    void* allocate(size_t n) {
        n = (n + 7) & ~(size_t)7;             // 8 字节对齐
        if (cur_ + n > end_) {                // 当前块不够，开新块
            cur_ = new char[kBlockSize];
            end_ = cur_ + kBlockSize;
            blocks_.push_back(cur_);
        }
        void* p = cur_;
        cur_ += n;                              // 指针前移，O(1)
        return p;
    }
    // 没有单独的 deallocate！整体释放：
    void reset() {
        for (char* b : blocks_) delete[] b;
        blocks_.clear();
        cur_ = end_ = nullptr;
    }
    ~Arena() { reset(); }
};
```

Arena 分配是**最快的内存分配方式**（纯指针加法），但只能整体释放。典型用途：处理一个请求时所有临时分配都走 Arena，请求结束统一 reset，完全避免 malloc/free。

### 2.5 主流内存分配器对比

| 分配器 | 开发者 | 多线程 | 碎片控制 | 特点 |
| --- | --- | --- | --- | --- |
| ptmalloc | glibc（默认） | arena 锁 | 一般 | 稳定，多线程竞争大 |
| tcmalloc | Google | 线程缓存（ThreadCache） | 好 | 高并发快，CentralCache 跨线程 |
| jemalloc | Facebook（FreeBSD 默认） | 线程缓存（arena  per CPU） | 优秀 | 碎片控制最好，Redis 默认 |
| mi-malloc | Microsoft | 线程局部 | 好 | 轻量、高性能、可嵌入 |
| 自定义池 | 业务 | 按需求 | 可控 | 针对特定大小/生命周期优化 |

**面试高频**：tcmalloc/jemalloc 比 ptmalloc 快的核心原因——**线程局部缓存**（每个线程有自己的 free list，分配释放无锁），只有线程缓存满/空时才访问全局 CentralCache（加锁）。ptmalloc 的 arena 粒度粗，锁竞争大。

### 2.6 内存对齐

| 对齐要求 | 说明 |
| --- | --- |
| 自然对齐 | 4 字节变量地址 4 对齐，8 字节变量 8 对齐 |
| `alignas(N)` | C++11 指定对齐，如 `alignas(64)` 避免伪共享 |
| `alignof(T)` | 查询类型对齐要求 |
| `std::aligned_alloc` | C11/C++17 分配对齐内存 |
| SIMD 对齐 | SSE 需 16 对齐，AVX 需 32 对齐 |

未对齐访问在 x86 上性能下降（跨缓存行），在 ARM/PowerPC 上直接总线错误。内存池分配时必须 `(ptr + align - 1) & ~(align - 1)` 对齐。

## 3. 线程池

### 3.1 为什么需要线程池

线程创建开销：分配栈（默认 8MB 虚拟内存）、内核调度实体创建、TLS 初始化。单次创建约 10~100μs，销毁也有代价。高频任务（如每秒上万请求）每次创建线程不可接受。

### 3.2 线程池核心组件

```cpp
class ThreadPool {
    std::vector<std::thread> workers_;
    std::queue<std::function<void()>> tasks_;
    std::mutex mtx_;
    std::condition_variable cv_;
    bool stop_ = false;
public:
    explicit ThreadPool(size_t n) {
        for (size_t i = 0; i < n; ++i)
            workers_.emplace_back([this] {
                for (;;) {
                    std::function<void()> task;
                    {
                        std::unique_lock<std::mutex> lk(mtx_);
                        cv_.wait(lk, [this] { return stop_ || !tasks_.empty(); });
                        if (stop_ && tasks_.empty()) return;
                        task = std::move(tasks_.front());
                        tasks_.pop();
                    }
                    task();                              // 出锁后执行，不阻塞其他线程取任务
                }
            });
    }
    template <class F>
    auto enqueue(F&& f) -> std::future<decltype(f())> {
        using Ret = decltype(f());
        auto task = std::make_shared<std::packaged_task<Ret()>>(std::forward<F>(f));
        std::future<Ret> res = task->get_future();
        {
            std::lock_guard<std::mutex> lk(mtx_);
            if (stop_) throw std::runtime_error("enqueue on stopped pool");
            tasks_.emplace([task]() { (*task)(); });
        }
        cv_.notify_one();
        return res;
    }
    ~ThreadPool() {
        { std::lock_guard<std::mutex> lk(mtx_); stop_ = true; }
        cv_.notify_all();
        for (auto& t : workers_) t.join();
    }
};
```

**关键设计**：
- `task()` 在锁外执行——否则一个慢任务会阻塞所有线程取任务。
- 析构时先 `stop_=true` 再 `notify_all`，最后 `join`——防止线程永久阻塞在 wait 上。
- `packaged_task` + `future` 支持获取返回值和异常。

### 3.3 线程池进阶设计

| 特性 | 说明 |
| --- | --- |
| 动态扩缩容 | 任务积压时增加线程，空闲时回收（最小/最大线程数） |
| 任务优先级 | 优先队列替代普通队列，高优先级任务先执行 |
| 工作窃取（Work Stealing） | 每个线程独立队列，空闲线程从其他线程队列尾部偷任务（无锁） |
| 有界队列 | 队列满时拒绝策略（丢弃/阻塞/调用者执行） |
| 线程隔离 | 不同业务用不同线程池，避免慢任务拖垮全局 |
| 优雅关闭 | 等待正在执行的任务完成，不再接受新任务 |

**线程数设置**：
- CPU 密集型：`线程数 = CPU 核数 + 1`（避免过多上下文切换）
- IO 密集型：`线程数 = CPU 核数 × (1 + IO等待时间/计算时间)`，通常核数 × 2~10
- 最佳实践：压测确定，不要凭感觉

### 3.4 工作窃取（Work Stealing）

每个工作线程有自己的双端队列（deque），任务从本地队列头部取；本地队列空时，从其他线程队列**尾部**偷任务。好处：
- 大部分时间无锁（本地操作）
- 偷任务时只在尾部竞争，概率低
- 负载自动均衡

实现用无锁 deque（如 Chase-Lev deque），C++ 可用 `folly::WorkStealingQueue`。Go 语言调度器、Java ForkJoinPool 都用工作窃取。

## 4. 连接池

### 4.1 连接池原理

数据库连接创建开销：TCP 握手（1 RTT）+ TLS 握手（2 RTT）+ 认证（1 RTT）+ 会话初始化。单次约 1~10ms。连接池预先建立 N 个连接，请求从池中取，用完归还。

```cpp
class ConnectionPool {
    struct Conn {
        std::shared_ptr<DBConnection> conn;
        std::chrono::steady_clock::time_point last_used;
        bool alive = true;
    };
    std::queue<Conn> pool_;
    std::mutex mtx_;
    std::condition_variable cv_;
    size_t max_size_;
    size_t active_ = 0;
public:
    std::shared_ptr<DBConnection> acquire(int timeout_ms = 3000) {
        std::unique_lock<std::mutex> lk(mtx_);
        // 等待：有空闲连接 或 未达上限可新建
        if (!cv_.wait_for(lk, std::chrono::milliseconds(timeout_ms),
                [this] { return !pool_.empty() || active_ < max_size_; }))
            return nullptr;                              // 超时
        if (!pool_.empty()) {
            Conn c = std::move(pool_.front());
            pool_.pop();
            if (c.alive && is_connection_valid(c.conn)) {
                ++active_;
                return c.conn;
            }
            // 连接失效，销毁后新建（下面逻辑）
        }
        ++active_;
        return create_connection();                       // 新建连接
    }
    void release(std::shared_ptr<DBConnection> conn) {
        std::lock_guard<std::mutex> lk(mtx_);
        pool_.push({conn, std::chrono::steady_clock::now(), true});
        --active_;
        cv_.notify_one();
    }
private:
    bool is_connection_valid(std::shared_ptr<DBConnection>& c) {
        // 心跳检测：SELECT 1 或 ping，超时 1s
        return c->ping(1000);
    }
};
```

### 4.2 连接池关键参数

| 参数 | 说明 | 建议 |
| --- | --- | --- |
| 最大连接数 | 池上限 | DB 连接数 = 核心数 × 2 + 磁盘数（PostgreSQL 公式），MySQL 通常 100~500 |
| 最小空闲连接 | 常驻连接数 | 预热，避免冷启动 |
| 最大空闲时间 | 空闲超过则回收 | 60s~300s，释放资源 |
| 连接超时 | acquire 等待超时 | 3s~5s，避免无限等待 |
| 校验超时 | 心跳检测超时 | 1s，快速剔除死连接 |
| 借出超时 | 连接被持有最长时间 | 30s，防泄漏（超时强制回收+报警） |

### 4.3 连接池常见坑

| 坑 | 现象 | 规避 |
| --- | --- | --- |
| 连接泄漏 | 借出后异常路径未归还，池耗尽 | RAII 封装（析构自动 release）、借出超时报警 |
| 死连接 | 对端已关闭，池中连接失效 | 借出前校验（ping）、空闲心跳、TCP keepalive |
| 事务残留 | 归还时连接还在事务中 | 归还前 rollback/重置会话状态 |
| 池过大 | 连接数超过 DB 处理能力，DB 崩溃 | 按公式设上限，监控活跃连接数 |
| 并发获取同一连接 | 多线程共用一个连接，协议错乱 | 连接借出期间独占，归还后才能再被取 |

## 5. 对象池

### 5.1 对象池 vs 直接 new/delete

| 维度 | new/delete | 对象池 |
| --- | --- | --- |
| 分配速度 | 慢（malloc + 构造） | 快（取空闲块 + 原地构造） |
| 释放速度 | 慢（析构 + free） | 快（析构 + 归还链表） |
| 内存碎片 | 有 | 无（固定大小块） |
| 缓存友好 | 差（地址随机） | 好（连续块） |
| 适用对象 | 大对象、低频 | 小对象、高频创建销毁 |

### 5.2 对象池实现要点

```cpp
template <typename T>
class ObjectPool {
    FixedMemoryPool<sizeof(T)> mem_pool_;   // 底层用固定大小内存池
public:
    template <typename... Args>
    T* acquire(Args&&... args) {
        void* p = mem_pool_.allocate();
        return new (p) T(std::forward<Args>(args)...);  // placement new 原地构造
    }
    void release(T* obj) {
        if (!obj) return;
        obj->~T();                                       // 显式析构
        mem_pool_.deallocate(obj);
    }
};
```

**placement new**：在已分配的内存上构造对象，不分配内存。对应释放时必须显式调用析构函数 `obj->~T()`，不能直接 delete（delete 会调 free 把内存还给系统，而池需要复用）。

### 5.3 对象池 + 智能指针

用 `shared_ptr` 自定义删除器，对象离开作用域自动归还池：

```cpp
template <typename T>
std::shared_ptr<T> make_pooled(ObjectPool<T>& pool) {
    T* p = pool.acquire();
    return std::shared_ptr<T>(p, [&pool](T* obj) { pool.release(obj); });
}
```

注意：删除器捕获 pool 的引用，必须保证 pool 生命周期长于所有 shared_ptr。

## 6. 池化技术选型决策树

```text
资源创建开销大？
├─ 是 → 使用频率高？
│   ├─ 是 → 池化（必须）
│   └─ 否 → 按需创建（池化预占资源不划算）
└─ 否 → 池化收益小，按需创建即可
```

| 资源 | 创建开销 | 推荐池化 |
| --- | --- | --- |
| 线程 | 中（10~100μs） | 高频任务必须池化 |
| DB 连接 | 高（1~10ms） | 必须池化 |
| 小对象（< 64B） | 低（几十 ns） | 极高频率才池化 |
| 大对象（> 1KB） | 中 | 推荐池化 |
| 协程 | 低（栈分配） | 框架内部池化 |

## 7. 组件化设计

| 组件 | 核心职责 | 关键接口 |
| --- | --- | --- |
| 日志组件 | 分级、异步落盘、滚动、格式化 | `LOG_INFO/DEBUG/ERROR` |
| 配置组件 | 热加载、格式解析、变更通知 | `get<T>(key)`、`watch(key, cb)` |
| 定时器组件 | 定时任务、超时检测、周期执行 | `add_timer(ms, cb)`、`cancel(id)` |
| 网络组件 | 连接管理、编解码、心跳 | `start/stop`、`send/recv` |
| 线程池组件 | 任务调度、异步执行 | `enqueue(task)` |
| 监控组件 | 指标采集、告警、健康检查 | `counter/gauge/histogram` |

**组件化原则**：单一职责（一个组件只做一件事）、接口隔离（依赖抽象接口而非具体实现）、依赖注入（外部传入依赖，便于测试替换）、无环依赖（组件间不能循环依赖）。

## 8. 快速参考卡片

```text
池化核心：预分配 + 复用，O(1) 借出/归还
内存池：固定大小(空闲链表) / 可变大小(size class) / Arena(bump pointer) / Slab / Buddy
Arena：指针++分配，整体释放，请求级临时内存最快
线程池：任务队列 + condition_variable，task() 在锁外执行
线程数：CPU密集=核数+1，IO密集=核数×(1+IO/计算)
连接池：acquire/release + 心跳校验 + 借出超时 + RAII 封装
对象池：placement new 构造 + 显式析构归还，shared_ptr 自定义删除器自动归还
分配器：ptmalloc(默认) / tcmalloc(线程缓存) / jemalloc(碎片好)
对齐：(ptr + align - 1) & ~(align - 1)，SIMD 需 16/32 对齐
```

**常见坑与最佳实践：**
1. 内存池未做对齐（`alignas`/手动对齐），SIMD 或跨平台访问出错。
2. 线程池 `enqueue` 后 `notify` 放在锁内——虽然功能正确，但通知时持锁可能导致被唤醒线程立即阻塞，优化为锁外 notify。
3. 线程池析构时忘记 `join`，线程访问已销毁的成员变量导致崩溃。
4. 连接池归还后连接已失效（对端关闭/超时），未做心跳检测导致"取到死连接"。
5. 对象池 double-free：归还后指针仍被外部持有并使用（use-after-free），用 shared_ptr 自定义删除器规避。
6. 内存池固定大小无法分配超块对象，必须做 fallback 到 malloc（大对象走系统分配器）。
7. 连接池未做事务重置，归还的连接带着未提交事务，下一个使用者拿到脏状态。
8. 线程池任务队列无界，任务生产远快于消费时内存暴涨——用有界队列 + 拒绝策略。
9. Arena 分配的内存不能单独 free，混入需要单独释放的对象会导致内存泄漏。
10. 池的大小设置凭感觉——必须压测：太小导致等待，太大浪费资源且增加管理开销。
