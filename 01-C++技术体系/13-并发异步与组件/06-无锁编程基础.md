## 1. 锁的代价

### 1.1 锁的性能开销拆解

| 开销 | 说明 | 量化 |
| --- | --- | --- |
| 系统调用 | 无竞争时 futex 在用户态 CAS，不进内核；有竞争时 futex(FUTEX_WAIT) 陷入内核 | 无竞争 ~25ns，有竞争 ~1~10μs |
| 上下文切换 | 阻塞线程被换出，唤醒时换入，涉及寄存器保存/恢复、TLB 刷新 | 单次切换 ~1~5μs |
| 缓存失效 | 持锁线程被换出后，锁所在缓存行失效；唤醒后重新加载 | 跨核缓存行迁移 ~100ns+ |
| 调度延迟 | 锁释放后，等待线程不一定立即被调度（调度器时间片） | 最坏情况毫秒级 |
| 优先级反转 | 低优先级持锁，高优先级等待，中间优先级线程抢占低优先级 | 实时系统严重问题 |

**无竞争锁很快**（futex 用户态 CAS，~25ns），但**高竞争下锁成为瓶颈**：所有线程串行化，CPU 时间花在等待和切换上而非实际计算。

### 1.2 死锁四条件

| 条件 | 说明 | 破坏手段 |
| --- | --- | --- |
| 互斥 | 资源同一时刻只归一个线程 | 无法破坏（锁的本质） |
| 请求与保持 | 拿着 A 又去要 B | 一次性申请全部资源 |
| 不可剥夺 | 别人不能抢走已持有的锁 | trylock 失败就释放重来 |
| 循环等待 | 等待关系成环 | 全局锁排序（最实用） |

## 2. 无锁方案概览

| 方案 | 原理 | 适用场景 | 复杂度 |
| --- | --- | --- | --- |
| CAS 循环 | compare_exchange 自旋重试 | 临界区极短（计数器、标志位） | 低 |
| 原子变量 | std::atomic 直接操作 | 计数器、引用计数、状态标志 | 极低 |
| 无锁栈/队列 | CAS 维护链表/环形缓冲 | 生产者-消费者、任务队列 | 中 |
| RCU（读-拷贝-更新） | 读无锁，写时拷贝旧数据替换指针 | 读多写极少（路由表、配置） | 中 |
| 双缓冲 | 写备用缓冲，原子切换指针 | 读多写少、配置热更新 | 低 |
|  hazard pointer | 读者标记正在访问的指针，写者等待安全回收 | 无锁数据结构内存回收 | 高 |
| Epoch-based | 分代回收，等所有线程离开临界区再释放 | 无锁数据结构内存回收 | 高 |

**无锁（lock-free）的定义**：系统级别的无锁——保证至少一个线程在有限步内完成操作，不依赖其他线程释放锁。单个线程可能一直 CAS 失败（活锁风险），但系统整体不会因某个线程卡住而全部阻塞。

**无等待（wait-free）**：更强的保证——每个线程都在有限步内完成。实现极难，实际很少见。

## 3. CAS 与原子操作

### 3.1 CAS（Compare-And-Swap）

CAS 是无锁编程的基石：原子地比较内存值与期望值，相等则替换为新值，返回是否成功。

```cpp
// 伪代码：原子操作，CPU 指令级保证（x86: CMPXCHG，ARM: LDXR/STXR）
bool cas(T* addr, T expected, T desired) {
    if (*addr == expected) { *addr = desired; return true; }
    else { expected = *addr; return false; }  // 失败时 expected 被更新为当前值
}
```

C++ 标准库提供两种 CAS：

| 函数 | 特点 | 使用场景 |
| --- | --- | --- |
| `compare_exchange_weak` | 可能伪失败（spurious failure，即使相等也返回 false） | 必须放循环里，性能略好（ARM 上） |
| `compare_exchange_strong` | 保证真实比较一次，无伪失败 | 不需要循环时用，x86 上两者无差异 |

```cpp
std::atomic<int> counter{0};

void increment() {
    int old = counter.load(std::memory_order_relaxed);
    while (!counter.compare_exchange_weak(old, old + 1,
            std::memory_order_release,    // 成功时的内存序
            std::memory_order_acquire)) {  // 失败时的内存序
        // old 被自动更新为当前值，继续重试
    }
}
```

### 3.2 常见原子操作

| 操作 | 含义 | 典型用途 |
| --- | --- | --- |
| `load` | 原子读 | 读取状态 |
| `store` | 原子写 | 设置状态 |
| `exchange` | 原子交换（返回旧值） | 标志位翻转、取旧值 |
| `fetch_add/fetch_sub` | 原子加减（返回旧值） | 计数器、引用计数 |
| `fetch_and/fetch_or/fetch_xor` | 原子位运算 | 标志位管理 |
| `compare_exchange_weak/strong` | 原子比较交换 | 无锁数据结构核心 |

**fetch_add 的实现**：底层也是 CAS 循环（x86 有 LOCK XADD 指令直接支持，ARM 用 LL/SC 循环）。`std::atomic<int>::fetch_add(1)` 等价于 CAS 循环但编译器/CPU 可能用更高效指令。

### 3.3 CAS 的 ABA 问题【高频】

```text
线程 A: 读 head = A（准备 CAS A→B）
线程 B: pop A → push C → push A（A 的地址被复用）
线程 A: CAS(A, B) 成功（因为 head 还是 A）
  → 但链表中间已经变了！A.next 可能指向 C 而非原来的 B
```

**ABA 的危害**：CAS 只比较值是否相等，不关心"值是否被改过又改回来"。在指针场景下，内存被释放后重新分配到同一地址，CAS 误判为未变。

**解决方案**：

| 方案 | 原理 | 优缺点 |
| --- | --- | --- |
| Tagged Pointer | 指针高位存版本号，每次 CAS 版本号+1 | 简单，但受地址空间限制（64位指针只用48位，可借16位） |
| Hazard Pointer | 读者声明"我正在访问这个指针"，写者检查无 hazard 才释放 | 安全，但每线程维护 hazard 列表，开销中等 |
| Epoch-Based Reclamation | 分代（epoch），写者把待释放对象挂当前代，等所有线程进入下一代才释放 | 批量回收效率高，但延迟释放内存 |
| RCU | 读无锁，写者拷贝修改后原子替换指针，等所有读者退出临界区再释放旧数据 | 读极快，写复杂，Linux 内核大量使用 |
| 不释放（泄漏） | pop 的节点不 delete，直接泄漏 | 最简单，仅适合短生命周期程序 |

```cpp
// Tagged Pointer 示例（利用 64 位指针高 16 位存版本号）
struct TaggedPtr {
    uint64_t ptr;    // 低 48 位地址，高 16 位版本号
    static constexpr uint64_t PTR_MASK = (1ULL << 48) - 1;
    static constexpr uint64_t TAG_SHIFT = 48;
    void* get_ptr() const { return (void*)(ptr & PTR_MASK); }
    uint16_t get_tag() const { return ptr >> TAG_SHIFT; }
    TaggedPtr with_inc_tag() const { return { (ptr & PTR_MASK) | ((get_tag() + 1) << TAG_SHIFT) }; }
};
```

## 4. 无锁数据结构

### 4.1 无锁栈（Treiber Stack）

```cpp
template <typename T>
class LockFreeStack {
    struct Node { T data; Node* next; };
    std::atomic<Node*> head_{nullptr};
public:
    void push(const T& v) {
        Node* n = new Node{v, nullptr};
        n->next = head_.load(std::memory_order_relaxed);
        // CAS：head 没变则替换为 n
        while (!head_.compare_exchange_weak(n->next, n,
                std::memory_order_release,
                std::memory_order_relaxed)) {
            // n->next 被更新为当前 head，继续重试
        }
    }
    bool pop(T& out) {
        Node* old = head_.load(std::memory_order_relaxed);
        while (old && !head_.compare_exchange_weak(old, old->next,
                std::memory_order_acquire,
                std::memory_order_relaxed)) {
            // old 被更新，继续
        }
        if (!old) return false;
        out = old->data;
        // 危险：直接 delete 有 ABA + use-after-free 风险
        // 生产代码需 hazard pointer / epoch 回收
        return true;
    }
};
```

**Treiber Stack** 是最简单的无锁数据结构，push/pop 都只操作 head。但 pop 后的节点回收是难点——直接 delete 可能导致其他线程正在访问该节点（use-after-free）。

### 4.2 SPSC 无锁环形队列

单生产者单消费者（SPSC）是最实用的无锁队列，无需 CAS，只用原子 load/store：

```cpp
template <typename T, size_t N>
class SPSCQueue {
    std::array<T, N> buf_;
    alignas(64) std::atomic<size_t> head_{0};  // 消费者写，生产者读
    alignas(64) std::atomic<size_t> tail_{0};  // 生产者写，消费者读
public:
    bool push(const T& v) {
        size_t t = tail_.load(std::memory_order_relaxed);
        size_t next = (t + 1) % N;
        // 生产者读 head，需 acquire 保证看到消费者的更新
        if (next == head_.load(std::memory_order_acquire)) return false; // 满
        buf_[t] = v;
        // release：保证 buf_[t] 写入对消费者可见
        tail_.store(next, std::memory_order_release);
        return true;
    }
    bool pop(T& v) {
        size_t h = head_.load(std::memory_order_relaxed);
        // 消费者读 tail，需 acquire
        if (h == tail_.load(std::memory_order_acquire)) return false;    // 空
        v = buf_[h];
        head_.store((h + 1) % N, std::memory_order_release);
        return true;
    }
};
```

**关键设计**：
- `head_` 只有消费者写，`tail_` 只有生产者写——各自写自己的变量，无需 CAS。
- `alignas(64)` 让 head 和 tail 落在不同缓存行，避免伪共享。
- 预留一个空位：`next == head` 判满，`h == tail` 判空，不会混淆。
- 内存序：写数据用 release，读对方指针用 acquire，形成 release-acquire 同步。

### 4.3 MPMC 无锁队列（Michael-Scott Queue）

多生产者多消费者（MPMC）需要 CAS 维护 head 和 tail，实现复杂。经典实现是 Michael-Scott 队列：用 dummy 节点简化边界，enqueue 操作 tail CAS，dequeue 操作 head CAS。生产环境建议用成熟库（`boost::lockfree::queue`、`moodycamel::ConcurrentQueue`）而非手写。

## 5. 内存序（Memory Order）

### 5.1 为什么需要内存序

编译器和 CPU 都会**重排指令**（只要不影响单线程语义）。多线程下，重排可能导致一个线程看到另一个线程的操作顺序与代码顺序不同。内存序就是约束重排的契约。

### 5.2 六种内存序

| 内存序 | 含义 | 性能 | 典型用途 |
| --- | --- | --- | --- |
| `relaxed` | 仅保证原子性，无任何顺序约束 | 最快 | 计数器、引用计数（不依赖顺序的场景） |
| `consume` | 数据依赖的读不能重排到它之前 | 快（很少用，编译器常当 acquire） | _rcu_dereference |
| `acquire` | 后续读/写不能重排到它之前（load 用） | 中 | 读锁、获取共享数据 |
| `release` | 之前的读/写不能重排到它之后（store 用） | 中 | 写锁、发布共享数据 |
| `acq_rel` | acquire + release（RMW 操作用） | 较慢 | CAS、fetch_add |
| `seq_cst` | 全局顺序一致（所有线程看到相同顺序） | 最慢 | 默认值，最安全 |

### 5.3 Release-Acquire 语义

```cpp
std::atomic<int> data{0};
std::atomic<bool> ready{false};

// 线程 A（生产者）
data.store(42, std::memory_order_relaxed);
ready.store(true, std::memory_order_release);  // release：之前的写不能重排到之后

// 线程 B（消费者）
while (!ready.load(std::memory_order_acquire)) {}  // acquire：之后的读不能重排到之前
assert(data.load(std::memory_order_relaxed) == 42);  // 一定能看到 42
```

**synchronizes-with 关系**：A 的 release store 与 B 的 acquire load 同步，A 在 release 之前的所有写对 B 在 acquire 之后的所有读可见。这是无锁编程中最常用的顺序保证。

### 5.4 内存序选择原则

| 场景 | 推荐内存序 |
| --- | --- |
| 纯计数器（不依赖其他数据） | relaxed |
| 发布数据 + 标志位 | 数据 relaxed，标志 release/acquire |
| CAS 成功/失败 | 成功 acq_rel，失败 acquire（或 relaxed） |
| 不确定时 | seq_cst（安全第一，性能可接受） |

**面试高频**：x86 是强内存模型（TSO，Total Store Order），acquire/release 几乎是零开销（只有编译屏障，无 CPU 屏障）；ARM/PowerPC 是弱内存模型，需要真实的内存屏障指令（DMB/DSB）。所以"在 x86 上跑没问题的无锁代码，搬到 ARM 上可能崩"。

## 6. 伪共享（False Sharing）

### 6.1 原理

CPU 缓存以**缓存行**（cache line，通常 64 字节）为单位。两个线程写**同一缓存行的不同变量**时，缓存行在两个核心间来回失效（MESI 协议的 RFO 请求），性能急剧下降——这就是伪共享。

```text
缓存行 64 字节：[counter_a (8B)][counter_b (8B)][...]
线程 A 写 counter_a → 缓存行失效 → 线程 B 的 counter_b 也失效
线程 B 写 counter_b → 缓存行失效 → 线程 A 的 counter_a 也失效
→ 两个核心来回抢同一缓存行，性能比单线程还慢
```

### 6.2 解决方案：缓存行对齐填充

```cpp
// 方案 1：alignas 对齐到缓存行
struct alignas(64) AlignedCounter {
    std::atomic<long> value{0};
};

// 方案 2：显式填充
struct PaddedCounter {
    std::atomic<long> value{0};
    char pad[64 - sizeof(std::atomic<long>)];  // 填满 64 字节
};

// 方案 3：C++17 hardware_destructive_interference_size
struct alignas(std::hardware_destructive_interference_size) Counter {
    std::atomic<long> value{0};
};
```

**检测伪共享**：`perf c2c`（Linux 4.10+）可以精确分析缓存行竞争，找到伪共享热点。

### 6.3 MESI 缓存一致性协议

| 状态 | 含义 |
| --- | --- |
| M（Modified） | 该核心已修改，其他核心副本无效 |
| E（Exclusive） | 仅该核心有副本，未修改 |
| S（Shared） | 多个核心有相同副本 |
| I（Invalid） | 副本无效，需重新加载 |

写操作需要独占缓存行（发 RFO 请求使其他核心副本失效），这是伪共享的根源。读操作可以共享（S 状态），所以**读多写少的变量不会有伪共享问题**。

## 7. 无锁 vs 有锁：性能对比

| 维度 | 互斥锁 | 无锁 CAS |
| --- | --- | --- |
| 无竞争 | ~25ns（futex 用户态） | ~10ns（原子指令） |
| 高竞争 | 上下文切换，吞吐骤降 | CAS 自旋，CPU 100% 但吞吐也降 |
| 临界区长短 | 适合任意长度 | 只适合极短（几条指令） |
| 实现难度 | 简单 | 高（ABA、内存回收、内存序） |
| 调试难度 | 易（死锁有明确现象） | 难（竞态极难复现） |
| 优先级反转 | 有 | 无 |
| 死锁 | 可能 | 不可能（但可能活锁） |

**结论**：无锁不是银弹。临界区短、竞争极高、性能要求极致时用无锁；其他情况互斥锁更可靠、更易维护。很多"无锁更快"的结论只在特定竞争度下成立，高竞争下 CAS 自旋也会把 CPU 打满。

## 8. 什么时候不该用无锁

| 场景 | 建议 | 原因 |
| --- | --- | --- |
| 临界区复杂、耗时长 | 用互斥锁 | CAS 自旋时间过长，CPU 浪费 |
| 数据结构复杂（图、树） | 用互斥锁 | 无锁实现极难正确，几乎不可能 |
| 读多写少 | 读写锁 / RCU / 双缓冲 | 读无锁比全操作无锁更实际 |
| 性能要求不极致 | 可读性优先 | 无锁代码维护成本高 |
| 团队无无锁经验 | 用互斥锁 | 无锁 bug 极难调试，线上事故代价大 |

**无锁编程正确性验证**：ThreadSanitizer（TSan）可以检测数据竞争，但不能保证无锁算法正确；还需要模型检查（如 CDSChecker）或严格的数学证明。生产环境无锁代码必须经过充分的压力测试和长期运行验证。

## 9. 快速参考卡片

```text
无锁三要素：原子性（CAS）+ 可见性（缓存一致性）+ 顺序性（内存序）
CAS：compare_exchange_weak 必须放循环（伪失败），strong 保证一次比较
ABA：指针复用导致 CAS 误判；解法 tagged pointer / hazard pointer / epoch / RCU
SPSC 队列：head/tail 各归一个线程写，无需 CAS，release-acquire 同步
MPMC 队列：Michael-Scott，CAS 维护 head/tail，生产用成熟库
内存序：relaxed(计数器) < acquire/release(发布订阅) < seq_cst(默认最安全)
x86 强模型(TSO) acquire/release 零开销；ARM 弱模型需真实屏障
伪共享：同缓存行不同变量被多线程写，alignas(64) 隔离；perf c2c 检测
无锁不是银弹：临界区短+竞争高才用，否则互斥锁更可靠
```

**常见坑与最佳实践：**
1. `compare_exchange_weak` 没放循环里，伪失败导致丢失更新——必须 while 循环。
2. 无锁栈 pop 后直接 delete 节点，其他线程可能正在访问（use-after-free）——必须用 hazard pointer/epoch 回收。
3. 未做缓存行对齐（`alignas(64)`），多线程写相邻变量导致伪共享，性能不升反降。
4. 用 `seq_cst`（默认）时误以为没有顺序开销——x86 上开销小但 ARM 上有真实内存屏障。
5. 无锁环形队列满/空判断与 head/tail 相等冲突——必须预留一个空位（`next == head` 判满）。
6. CAS 失败后忘记更新 old 值——`compare_exchange` 会自动把 old 更新为当前值，循环里直接用即可。
7. 在无锁代码中调用可能阻塞的函数（malloc、锁）——破坏无锁保证，可能导致整个系统阻塞。
8. 忽略内存序，只在 x86 上测试——搬到 ARM/PowerPC 上出现难以复现的竞态 bug。
9. 无锁队列容量设计不当——SPSC 队列满时丢弃还是阻塞需明确，默认返回 false 可能丢数据。
10. 过度使用无锁——临界区超过几十条指令时，互斥锁的吞吐往往更高（CAS 自旋浪费 CPU）。
