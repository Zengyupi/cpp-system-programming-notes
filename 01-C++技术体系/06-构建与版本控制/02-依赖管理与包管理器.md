## 1. 概述

### 1.1 C++ 依赖管理的痛苦史

C++ 长期没有官方包管理器（直到 C++26 之前标准委员会都没有统一方案），历史上只有三条路：

| 传统方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 手动复制源码 | 把第三方源码拷进 `third_party/` | 完全可控、离线可构建 | 升级靠人肉合并，版本漂移无人知晓 |
| Git submodule | `git submodule add`（见 03-Git版本控制.md 第 9 章） | 版本由 git 锁定 | 嵌套 submodule 的递归地狱、`detached HEAD` 坑多 |
| 系统包管理器 | `apt install libfmt-dev` | 一行命令 | 版本由发行版决定，无法按项目差异化，交叉编译不友好 |

### 1.2 现状格局

```text
                C++ 依赖获取方式（2024+）
   ┌───────────────┬───────────────┬───────────────┐
   │   vcpkg       │   Conan 2.x   │  源码 vendored │
   │  微软/中央仓库 │  去中心化 recipes│  FetchContent/ │
   │  (CMake 深度) │  (多构建系统)  │  submodule     │
   └───────────────┴───────────────┴───────────────┘
            ↑ 二进制缓存/锁文件 ↑        ↑ 系统包 apt/zypper 兜底
```

| 方式 | 一句话定位 |
|---|---|
| vcpkg | 微软出品，与 CMake/VS 集成最顺滑，中央 registry（github.com/microsoft/vcpkg） |
| Conan 2.x | 去中心化，支持 CMake/Bazel/Meson 等多构建系统，可自建私有制品库 |
| FetchContent | CMake 内置（3.11+），configure 阶段直接拉源码一起编译，适合少量轻依赖 |
| 系统包 | apt/zypper/pacman，适合系统级基础库（openssl、zlib） |

## 2. vcpkg

### 2.1 安装与 bootstrap

```bash
# Linux / WSL（本知识库命令默认 Linux/WSL 环境）
git clone https://github.com/microsoft/vcpkg.git ~/vcpkg
~/vcpkg/bootstrap-vcpkg.sh            # 生成 vcpkg 可执行文件
export VCPKG_ROOT=~/vcpkg             # 建议写进 05-Shell脚本编程.md 的 ~/.bashrc
export PATH=$VCPKG_ROOT:$PATH
# Windows 对应：git clone 后运行 bootstrap-vcpkg.bat
```

### 2.2 两种模式对比（重点）

| 模式 | 依赖记录位置 | 安装范围 | 适用 | 说明 |
|---|---|---|---|---|
| 经典模式 | 无（命令行直接 `vcpkg install fmt`） | 全局 `~/vcpkg/installed/` | 临时试验、装工具 | 版本不受项目控制，多个项目互相污染 |
| **manifest 模式（推荐）** | 项目根的 `vcpkg.json` | 仅本项目构建树 | 一切正式项目 | CMake configure 时自动安装依赖，团队一致 |

> 判别方法：**当前目录存在 vcpkg.json 时，vcpkg 自动切换到 manifest 模式**，此模式下 `vcpkg install` 不带包名（读清单安装）。

### 2.3 vcpkg.json 完整示例

```json
{
  "name": "myapp",
  "version-string": "1.2.0",
  "dependencies": [
    "fmt",
    { "name": "boost-asio", "version>=": "1.83.0" },
    { "name": "gtest", "features": [] }
  ],
  "builtin-baseline": "8eb57355df4a9f3ddba68baf3b689a13d0fc3749",
  "overrides": [
    { "name": "fmt", "version": "10.1.1" }
  ]
}
```

| 字段 | 说明 | 示例 |
|---|---|---|
| `name` / `version-string` | 本项目自身标识 | `myapp` |
| `dependencies` | 直接依赖列表，字符串或对象 | `"fmt"` |
| `version>=` | 版本下限约束（配合 baseline 生效） | `"version>=": "1.83.0"` |
| `builtin-baseline` | 指向 vcpkg 仓库某次 commit 的版本基线，**必填**（不写则版本解析失败） | 40 位 commit hash |
| `overrides` | 强制锁定某包的精确版本（解决传递依赖冲突） | fmt 锁 10.1.1 |

### 2.4 CMake 集成

方式一：工具链文件（传统，命令行传参）：

```bash
cmake -B build -DCMAKE_TOOLCHAIN_FILE=$VCPKG_ROOT/scripts/buildsystems/vcpkg.cmake
```

方式二：CMakePresets.json 预设（推荐，衔接《01-构建工具GCC与CMake.md》5.9 预设文件）：

```json
{
  "version": 3,
  "configurePresets": [
    {
      "name": "vcpkg-release",
      "binaryDir": "${sourceDir}/build",
      "toolchainFile": "$env{VCPKG_ROOT}/scripts/buildsystems/vcpkg.cmake",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Release"
      }
    }
  ]
}
```

```bash
cmake --preset vcpkg-release        # configure 阶段自动按 vcpkg.json 装依赖
```

之后就是标准 CMake 写法（`find_package` + 链接目标）：

```cmake
find_package(fmt CONFIG REQUIRED)
target_link_libraries(myapp PRIVATE fmt::fmt)
```

### 2.5 常用命令表

| 命令 | 说明 | 示例 |
|---|---|---|
| `vcpkg install` | 按 vcpkg.json 安装（manifest 模式） | `vcpkg install` |
| `vcpkg install <pkg>` | 安装指定包（经典模式） | `vcpkg install fmt` |
| `vcpkg search <关键词>` | 在 registry 里搜包 | `vcpkg search json` |
| `vcpkg list` | 列出已安装的包 | `vcpkg list` |
| `vcpkg remove <pkg>` | 移除包 | `vcpkg remove fmt` |
| `vcpkg upgrade` | 列出/升级有过期版本的经典模式包 | `vcpkg upgrade --no-dry-run` |
| `vcpkg x-history <pkg>` | 查看某包的可用版本 | `vcpkg x-history fmt` |
| `vcpkg install <pkg> --triplet x64-linux` | 指定 triplet | 交叉编译见下表 |

### 2.6 triplet 与交叉编译（衔接《../09-嵌入式开发/05-嵌入式Linux系统与驱动开发.md》）

triplet 形如 `<架构>-<系统>[-后缀]`，描述"目标平台 + 链接方式"：

| triplet | 含义 | 场景 |
|---|---|---|
| `x64-linux` | Linux x64 动态库 | 桌面 Linux 默认 |
| `x64-windows` | Windows x64 动态（MD） | MSVC 默认 |
| `x64-windows-static-md` | 静态库 + 动态 CRT | 避免带一堆 dll |
| `arm64-linux` | Linux ARM64 | 树莓派/ARM 服务器（《../09-嵌入式开发/05-嵌入式Linux系统与驱动开发.md》的交叉工具链场景） |
| `arm64-android` | Android ARM64 | NDK 交叉编译 |

```bash
# 交叉编译：目标平台与宿主机不同时必须显式指定 triplet
vcpkg install --triplet arm64-linux
cmake --preset vcpkg-release -DVCPKG_TARGET_TRIPLET=arm64-linux \
      -DCMAKE_C_COMPILER=aarch64-linux-gnu-gcc   # 配合交叉工具链（《../09-嵌入式开发/05-嵌入式Linux系统与驱动开发.md》）
```

## 3. Conan 2.x

### 3.1 安装与初始化

```bash
pip install conan            # 官方推荐方式（2.x）
conan --version
conan profile detect         # 自动探测本机编译器生成默认 profile（1.x 没有这条）
```

> **Conan 1.x 与 2.x 命令差异极大**，网上大量旧教程照抄会报错：1.x 的 `cmake`/`cmake_find_package` 生成器在 2.x 已删除，替换为 `CMakeDeps` + `CMakeToolchain`；1.x 的 `conan install .. --build missing`（位置参数）在 2.x 必须写 `--build=missing`；2.x 用 `conan profile detect` 取代了 1.x 手写 default profile。

### 3.2 conanfile.txt vs conanfile.py

```ini
# conanfile.txt —— 声明式，简单项目够用
[requires]
fmt/10.1.1
gtest/1.14.0

[generators]
CMakeDeps        # 生成 find_package 可用的 xxx-config.cmake
CMakeToolchain   # 生成 conan_toolchain.cmake（含编译器/构建类型设置）

[layout]
cmake_layout     # 固定 build 目录结构，生成器路径才不会乱
```

```python
# conanfile.py —— 需要自定义逻辑（打包、条件依赖）时使用
from conan import ConanFile

class MyApp(ConanFile):
    settings = "os", "compiler", "build_type", "arch"
    generators = "CMakeDeps", "CMakeToolchain"
    requires = "fmt/10.1.1"

    def requirements(self):          # 条件依赖
        if self.settings.os == "Windows":
            self.requires("winpcap/4.1.3")
```

### 3.3 典型工作流（2.x）

```bash
conan install . --output-folder=build --build=missing
#  产出：build/conan_toolchain.cmake + 各依赖的 *-config.cmake

cmake -B build -DCMAKE_TOOLCHAIN_FILE=build/conan_toolchain.cmake -DCMAKE_BUILD_TYPE=Release
cmake --build build -j8
```

### 3.4 常用命令表（Conan 2.x）

| 命令 | 说明 | 示例 |
|---|---|---|
| `conan profile detect` | 生成默认 profile | 首次安装后必跑 |
| `conan profile show` | 查看当前生效 profile | 排查编译器配置 |
| `conan install <path>` | 解析依赖并生成集成文件 | `conan install . --build=missing` |
| `conan build <path>` | 执行 conanfile.py 的 build() | `conan build .` |
| `conan create <path>` | 打包并放入本地缓存（给库作者） | `conan create . --version=1.0.0` |
| `conan list "pkg/*"` | 查询包（含远端） | `conan list "fmt/*" -r=conancenter` |
| `conan graph info` | 打印依赖图（排查版本冲突） | `conan graph info .` |
| `conan lock create` | 生成锁文件 | `conan lock create conanfile.txt` |
| `conan cache clean` | 清理本地缓存 | 磁盘紧张时 |

### 3.5 vcpkg 与 Conan 的定位差异表

| 维度 | vcpkg | Conan 2.x |
|---|---|---|
| recipes 仓库 | 中央 registry（微软 vcpkg 仓库，PR 合入制） | 去中心化：conancenter + 任意私有 Artifactory |
| 构建系统 | 深度绑定 CMake（toolchain 一等公民） | CMake/Bazel/Meson/MSBuild 皆有生成器 |
| 版本约束 | baseline + overrides | requires 里直接写 `pkg/version`（精确版本） |
| 锁文件 | vcpkg.lock（manifest 模式自动生成） | conan.lock（`conan lock create` 生成） |
| 私有包 | 自建 registry（vcpkg-configuration.json 指向） | Artifactory/GitLab package registry 原生支持 |
| 上手成本 | 低（配好 toolchain 后无感） | 中（profile/生成器概念多） |

## 4. 五方案权衡大表与选型建议

| 方案 | 依赖获取速度 | 可复现性 | 离线构建 | 学习成本 | 团队协作 |
|---|---|---|---|---|---|
| vcpkg（manifest） | 中（首装编译，binary cache 后快） | 高（baseline + lock） | 好（缓存可迁移） | 低 | 好（提交 vcpkg.json） |
| Conan 2.x | 快（远端二进制包） | 高（精确版本 + lock） | 好 | 中 | 好（私有仓库强） |
| 系统包 apt/zypper | 快 | 差（跟发行版走） | 差 | 最低 | 一般（环境漂移） |
| FetchContent | 慢（每次 clone 源码参与编译） | 中（靠 GIT_TAG 自觉固定） | 一般（需手动 vendor） | 低 | 好 |
| Git submodule | 中 | 中（跟 commit） | 好 | 低 | 一般（嵌套地狱） |

选型建议：

| 团队情况 | 推荐 |
|---|---|
| Windows + 微软生态 / VS / 纯 CMake 项目 | vcpkg（manifest 模式） |
| 跨平台多构建系统、需要私有包仓库、库作者 | Conan 2.x |
| 只有一两个轻量头文件库依赖 | FetchContent |
| 目标是发行版打包的 Linux 软件 | 系统包 + CMake 的 find_package |
| 嵌入式目标机（无法在目标上装包） | vcpkg 自定义 triplet / Conan 交叉 profile（配合《../09-嵌入式开发/05-嵌入式Linux系统与驱动开发.md》工具链） |

## 5. CMake FetchContent 详解

```cmake
cmake_minimum_required(VERSION 3.14)
project(fetchdemo CXX)

include(FetchContent)

# 固定到具体 commit/tag：GIT_TAG 必须是不可变引用，避免"latest main"漂移
FetchContent_Declare(
  fmt
  GIT_REPOSITORY https://github.com/fmtlib/fmt.git
  GIT_TAG        10.1.1          # 用 tag；更严格可用完整 commit hash
  GIT_SHALLOW    TRUE            # 浅克隆提速
)
FetchContent_MakeAvailable(fmt)   # 3.14+：可用即不拉，拉完自动 add_subdirectory

FetchContent_Declare(
  gtest
  GIT_REPOSITORY https://github.com/google/googletest.git
  GIT_TAG        v1.14.0
)
FetchContent_MakeAvailable(gtest)
```

与 find_package 组合的"优先系统、缺失再拉源码"写法：

```cmake
find_package(fmt 10 QUIET)               # 先找系统/包管理器装的
if(NOT fmt_FOUND)
  include(FetchContent)                  # 找不到才拉源码（overlay 写法）
  FetchContent_Declare(fmt GIT_REPOSITORY https://github.com/fmtlib/fmt.git
                             GIT_TAG 10.1.1)
  FetchContent_MakeAvailable(fmt)
endif()
target_link_libraries(myapp PRIVATE fmt::fmt)   # 两种来源目标名一致，下游无感
```

| FetchContent 命令 | 说明 |
|---|---|
| `FetchContent_Declare(name ...)` | 声明来源（git/URL），不下载 |
| `FetchContent_MakeAvailable(name ...)` | 声明 + 拉取 + 自动 add_subdirectory（推荐） |
| `FetchContent_Populate(name)` | 只拉取不引入构建（自写集成时用） |
| `FETCHCONTENT_SOURCE_DIR_<name>` | 缓存变量：指定本地目录替代下载（离线/魔改依赖） |

## 6. 私有依赖与安全

### 6.1 私有 registry

| 方案 | 说明 | 适用 |
|---|---|---|
| Artifactory（Conan） | 企业级制品库，支持 Conan/vcpkg/generic 多种 repo | 中大型团队 |
| BaGet / GitHub Packages | 轻量 NuGet 风格服务器，可给 vcpkg 做二进制缓存后端 | 小团队 |
| 自建 vcpkg registry | git 仓库放自定义 recipes，项目里用 `vcpkg-configuration.json` 的 `registries` 字段指向 | 有内部私有 C++ 库 |
| GitLab/Gitea 包仓库 | Conan remote 指向即可 | 已有 GitLab 的团队 |

### 6.2 锁文件：保证团队一致

| 工具 | 锁文件 | 生成方式 | 提交到 git？ |
|---|---|---|---|
| vcpkg | `vcpkg.lock` | manifest 模式下 `vcpkg install` 自动生成 | 是（应用项目） |
| Conan | `conan.lock` | `conan lock create conanfile.txt` | 是 |
| git submodule | submodule 的 commit | `git add`（见 03-Git版本控制.md 第 9 章） | 天然锁定 |

> 与 03-Git 版本控制.md 第 10 章 .gitignore 的约定一致：**应用程序提交 lock 文件**保证可复现；库项目通常不提交，把版本选择权留给下游。

### 6.3 供应链与许可证审查

| 许可证 | 类型 | 静态链接进闭源产品 |
|---|---|---|
| MIT / BSD-2/3 / Apache-2.0 / zlib | 宽松（permissive） | 允许，保留版权声明即可 |
| MPL-2.0 | 文件级 copyleft | 修改的文件需开源，其余可闭源 |
| LGPL-2.1/3.0 | 弱传染 | 动态链接允许闭源；**静态链接须提供目标文件（.o）或源码使能重链接**——《../09-嵌入式开发/05-嵌入式Linux系统与驱动开发.md》的静态链接场景要特别注意 |
| GPL-2/3 | 强传染 | 衍生作品整体按 GPL 开源 |
| AGPL | 网络服务也传染 | 服务端使用也触发开源义务 |

```bash
# vcpkg/conan 安装时查看许可证
vcpkg install fmt            # 输出含 license: MIT
conan list "fmt/10.1.1" -r=conancenter   # 显示 license 字段
```

## 7. 与既有知识库衔接

### 7.1 CMakePresets 完整集成（衔接 01-构建工具 GCC 与 CMake.md 5.9）

```json
{
  "version": 3,
  "configurePresets": [
    {
      "name": "vcpkg",

      "toolchainFile": "build-conan/conan_toolchain.cmake"
    }

  "buildPresets": [
    { "name": "vcpkg", "configurePreset": "vcpkg" }
  ]
}
```

### 7.2 CI 中的依赖缓存策略

| 工具 | 缓存机制 | CI 做法 |
|---|---|---|
| vcpkg binary caching | 默认本地 `~/.cache/vcpkg`；可指向 GitHub Actions 缓存或 NuGet feed | CI 缓存 `~/.cache/vcpkg`，命中后跳过编译依赖 |
| Conan cache | `~/.conan2/p` 二进制包缓存 | CI 缓存 `~/.conan2` 目录，第二次流水线秒装 |
| FetchContent | `build/_deps` 目录 | 缓存整个 build 目录或 `FETCHCONTENT_BASE_DIR` |

```text
# GitHub Actions 片段：缓存 vcpkg 二进制
- uses: actions/cache@v4
  with:
    path: ~/.cache/vcpkg
    key: vcpkg-${{ runner.os }}-${{ hashFiles('vcpkg.json') }}
```

## 9. 常见问题与坑

| 问题 | 原因与解决方案 |
|---|---|
| vcpkg.json 里写了版本约束却报"version solving failed" | 缺 `builtin-baseline`。填入 vcpkg 仓库当前 commit hash（在 vcpkg 目录 `git rev-parse HEAD` 获取） |
| 经典模式与 manifest 模式混用，装了包却链接不到 | 有 vcpkg.json 时 vcpkg 只认清单。清理 `vcpkg remove` 后把依赖正式写进 vcpkg.json |
| builtin-baseline 过旧，装不上新版本包 | baseline 决定可用版本上限。`git -C $VCPKG_ROOT pull` 后更新 baseline 为新 HEAD hash |
| triplet 与目标平台不匹配，链接到 x64 库但目标是 arm64 | 交叉编译必须显式 `-DVCPKG_TARGET_TRIPLET=arm64-linux` 并匹配交叉工具链（《../09-嵌入式开发/05-嵌入式Linux系统与驱动开发.md》） |
| 照 Conan 1.x 教程执行报 "generator not found" | 1.x 的 `cmake_find_package` 等生成器已在 2.x 删除。改用 `CMakeDeps` + `CMakeToolchain`（见 3.2） |
| `conan install` 提示需要 profile | 2.x 必须先 `conan profile detect` 生成默认 profile |
| FetchContent 没固定 tag，某天构建突然失败 | 上游 main 分支变更。GIT_TAG 固定为 tag 或 commit hash，升级依赖走显式提交 |
| find_package 找不到包 | 装到非默认前缀时未设 `CMAKE_PREFIX_PATH`：`-DCMAKE_PREFIX_PATH=build`（conan 生成文件所在目录）或确保用了 toolchainFile |
| vcpkg 每次都重新编译依赖，CI 很慢 | 未启用 binary caching。CI 缓存 `~/.cache/vcpkg`（Linux）或配置 NuGet/GHA 后端 |
| Windows 下 vcpkg 装的库是静态 CRT，与主程序 MD 冲突 | 选对 triplet：动态 CRT 用 `x64-windows`，静态库 + MD 用 `x64-windows-static-md` |
| 依赖许可证不兼容（LGPL 静态链入闭源产品） | 换宽松许可的等价库，或按 6.3 履行重链接义务；嵌入式静态链接前必须过一遍许可表 |
