## 1. 低功耗与可靠性

### 1.1 低功耗模式（Cortex-M）

| 模式 | CPU | 时钟/外设 | RAM | 唤醒源 | 唤醒时间/功耗 |
| --- | --- | --- | --- | --- | --- |
| Sleep | 停 | 外设运行 | 保持 | 任意中断 | 最快/省得少 |
| Stop | 停 | 大部分时钟停，电压域保持 | 保持 | EXTI/RTC/I2C 地址匹配 | 较慢/很省电 |
| Standby | 断电核心域 | 几乎全停 | **丢失（除备份域）** | WKUP 引脚/RTC/复位 | 最慢/最省电（μA 级） |

```c
// 低功耗主循环：没事就 WFI 睡，中断唤醒处理
while (1) {
    run_due_tasks();
    if (no_pending_work()) {
        __DSB(); __WFI();     // Wait For Interrupt，睡到来中断；WFE 等事件
        __ISB();
    }
}
```

低功耗工程手段：选低频时钟、关不用外设时钟、GPIO 不用脚设为模拟输入、用 DMA 替 CPU、批量唤醒处理、RTC 定时唤醒采样后立即回睡（占空比越低越省电）。

### 1.2 看门狗（Watchdog）

| 类型 | 时钟源 | 特点 |
| --- | --- | --- |
| IWDG 独立看门狗 | 独立 LSI 时钟 | 主时钟故障也能复位，安全兜底 |
| WWDG 窗口看门狗 | APB 时钟 | 必须在"窗口"内喂狗，太早太晚都复位，能检测程序跑飞/时序异常 |

原则：**只在主循环固定一个点喂狗**，不在中断/多处喂——这样任何任务卡死都会导致喂狗超时、系统复位自恢复。配合复位原因寄存器（RCC_CSR）区分上电/看门狗/软件复位，连续异常复位可进入安全模式。

### 1.3 HardFault 定位（Cortex-M）

崩溃后进 HardFault_Handler，关键寄存器（SCB 内）：

| 寄存器 | 地址 | 看什么 |
| --- | --- | --- |
| CFSR | 0xE000ED28 | 具体原因：IACCVIOL 取指违例、DACCVIOL 数据访问违例、IBUSERR/ PRECISERR 总线错、UNDEFINSTR 非法指令、UNALIGNED 非对齐、DIVBYZERO 除零 |
| HFSR | 0xE000ED2C | FORCED（其他 fault 升级）、VECTTBL |
| BFAR/MMFAR | 0xE000ED38/34 | 出错时访问的地址 |
| EXC_RETURN(LR) | 进入异常时的 LR | bit2 区分用 MSP 还是 PSP、是否返回到线程模式 |

定位步骤：进 HardFault 时根据 EXC_RETURN 选 MSP/PSP，从栈里读出硬件自动压入的 **R0-R3、R12、LR、PC、xPSR**——其中 **PC 就是崩溃指令地址、LR 是调用者**，用 `addr2line -e app.elf <PC>` 或 map 文件直接定位到源码行。编译务必带 `-g`、保留 .elf。

### 1.4 可靠性手段清单

- 断言 `assert_param`：开发期抓非法参数，量产可重定义为"记录+安全停机"。
- 栈溢出检测：RTOS 开 `configCHECK_FOR_STACK_OVERFLOW` 钩子；栈填充 0xA5 事后看高水位线。
- 所有外部输入（串口/网络/传感器）做**长度、范围、校验**白名单，防越界与协议脏数据。
- malloc 失败有兜底；长期运行设备尽量静态分配/内存池，杜绝碎片。
- 关键参数双备份 + CRC 存 Flash，启动校验，损坏回滚默认值。

## 2. Bootloader 与 OTA 升级

### 2.1 IAP 与分区

MCU 通常用 IAP（In-Application Programming）：Flash 划分为 Bootloader 区 + App 区（+ 参数/备份区），上电先进 Bootloader，判断条件后跳转到 App。

```text
Flash 布局（示例）
0x08000000 ┌──────────────┐
           │ Bootloader    │  上电先跑：检查升级标志/固件有效性，决定跳转或升级
0x08008000 ├──────────────┤
           │ App A（运行）  │  向量表偏移到这里（SCB->VTOR），主业务
0x08040000 ├──────────────┤
           │ App B（备份）  │  下载新固件先写 B，校验通过再切换（A/B 双区）
0x08078000 ├──────────────┤
           │ 参数/标志(+CRC)│  升级标志、版本、回滚计数
0x08080000 └──────────────┘
```

### 2.2 A/B 双区安全升级流程

```text
① 运行 A；通过 UART/4G/WiFi/以太网分片下载新固件，写入 B 区（边收边写 Flash）
② 整包校验：长度 + CRC32/SHA256 +（可选）签名，防止刷入损坏/非法固件
③ 置"待切换"标志并复位
④ Bootloader 校验 B 有效 → 把 B 标记为新运行区（或拷贝覆盖 A）→ 跳转
⑤ 新固件启动成功并自检通过后，清除回滚标志；若启动失败/看门狗连续复位，
   Bootloader 自动回滚到上一可用区（保证变砖可恢复）
```

| 要点 | 说明 |
| --- | --- |
| 跳转前 | 关中断、复位外设时钟、把 MSP 设为新固件向量表第 0 项、重设 VTOR、跳到 Reset_Handler |
| 掉电安全 | 永远保留一个可启动的旧版本，新固件没确认前不覆盖它 |
| Flash 写 | 写前按扇区/页擦除（只能 1→0，擦成全 1 才能写），注意擦写寿命（万~十万次） |
| 传输 | YMODEM（串口）、HTTP/HTTPS、MQTT 下发；差分升级（bsdiff）省流量 |

## 3. 嵌入式调试技术

### 3.1 硬件调试接口

| 接口 | 引脚 | 说明 |
| --- | --- | --- |
| SWD | SWCLK+SWDIO+GND(+VCC) | ARM 主推，2 线即可下载+调试+读内存，省引脚 |
| JTAG | TCK/TMS/TDI/TDO/TRST | 传统 4/5 线，多芯片可菊花链，边界扫描 |
| ETM/ITM/SWO | 复用 SWO 单线 | 指令跟踪、实时 printf（ITM/SWO），不打断 CPU |
| UART | TX/RX/GND | 打印日志，最常用 |

### 3.2 调试手段对比

| 手段 | 适用 | 特点 |
| --- | --- | --- |
| 在线断点/单步/Watch | 开发期 | GDB/IDE 经 SWD/JTAG，可看寄存器/内存/外设位域 |
| 串口日志 | 全周期 | 带时间戳、分级日志；量产可留作诊断口 |
| SEGGER RTT | 开发期 | 经调试器直接读写内存做打印，**不占串口、几乎不耗时** |
| ITM/SWO | Cortex-M3+ | 单线跟踪输出 |
| 逻辑分析仪/示波器 | 时序问题 | 抓 I2C/SPI/UART 波形解码，验证时序与电平 |
| 仿真 QEMU/Renode | 无板调试 | 模拟 Cortex-M/外设，CI 跑固件 |
| coredump | 事后 | 崩溃把 RAM/寄存器落 Flash，离线用 GDB 还原现场 |

### 3.3 断言与现场保护

```c
// 断言：记录文件行号后停机/复位，比"乱跑"更易定位
#define MY_ASSERT(expr) do { if(!(expr)){ \
    log_fatal("ASSERT %s %s:%d", #expr, __FILE__, __LINE__); \
    fault_save_and_reset(); } } while(0)
```

## 4. 安全启动与固件加密

安全启动（Secure Boot）保证设备只运行经过授权的固件，防止攻击者刷入恶意固件。它是 OTA 安全的基础——没有安全启动的 OTA 就像没有门锁的房子。

### 4.1 Secure Boot 流程

```text
上电复位
  │
  ▼
① BootROM（芯片固化，不可修改）：内置公钥/哈希，验证第一级引导程序（SPL/Bootloader）的签名
  │   验证通过 → 执行 Bootloader；验证失败 → 拒绝启动（变砖或进入恢复模式）
  ▼
② Bootloader：用内置公钥验证应用固件（App）的签名 + 完整性（SHA256）
  │   验证通过 → 跳转 App；验证失败 → 回滚到上一版本或拒绝启动
  ▼
③ App 运行：可选验证动态加载的模块/配置文件签名
```

**信任链（Chain of Trust）**：每一级验证下一级的签名，从不可修改的 BootROM 根信任开始，逐级传递。任何一级被篡改都会导致验证失败，从而阻断启动。

### 4.2 固件签名与加密

#### 签名 vs 加密的区别

| 目的 | 机制 | 作用 |
| --- | --- | --- |
| **完整性** | SHA-256 哈希 | 固件是否被篡改（哪怕 1 bit 变化，哈希完全不同） |
| **真实性/认证** | RSA/ECDSA 数字签名 | 固件是否来自授权方（私钥签名，公钥验签） |
| **机密性** | AES 加密 | 固件内容是否可读（防止逆向工程、保护知识产权） |

> 签名和加密是两个独立维度：**签名保证"是谁发的、有没有被改"，加密保证"内容看不懂"**。安全启动至少需要签名（完整性+认证），加密可选（保护固件 IP）。

#### RSA 签名流程

```text
厂商侧（签名）：
  1. 计算固件 SHA-256 哈希：H = SHA256(firmware)
  2. 用 RSA 私钥签名：S = RSA_sign(H, private_key)
  3. 发布：firmware.bin + signature.bin（或合并成带签名头的镜像）

设备侧（验签）：
  1. 计算收到固件的 SHA-256 哈希：H' = SHA256(received_firmware)
  2. 用内置 RSA 公钥验签：RSA_verify(S, public_key) → 还原出 H
  3. 比较 H == H'：相等则通过，不等则拒绝
```

#### ECDSA vs RSA 对比

| 维度 | RSA-2048 | ECDSA P-256 |
| --- | --- | --- |
| 签名长度 | 256 字节 | 64 字节 |
| 公钥长度 | 256 字节 | 64 字节 |
| 验签速度（MCU） | 慢（大数模幂，~100ms@Cortex-M4） | 快（椭圆曲线点乘，~20ms@Cortex-M4） |
| 签名速度 | 快 | 慢（需随机数） |
| 安全性等价 | 2048 位 ≈ 112 位 | 256 位 ≈ 128 位 |
| 适用 | Bootloader 验签（验签慢但可接受） | 资源紧的 MCU、频繁验签场景 |

#### AES 加密固件

```text
厂商侧：
  1. 用 AES-256-CBC 加密固件：encrypted = AES_encrypt(firmware, key, IV)
  2. 密钥通过安全渠道注入设备（量产时烧入 OTP/安全单元）

设备侧（Bootloader 中解密）：
  1. 从加密存储区读取 IV + 加密固件
  2. 用 AES 硬件加速器（Cortex-M 多数有）解密到 RAM
  3. 验签通过后从 RAM 执行（或解密到 Flash 再执行）
```

> **常见坑**：① 密钥不能硬编码在固件里（否则逆向即可提取），应存在 OTP/安全单元/TrustZone 安全世界；② AES-CBC 需随机 IV，每次加密不同，IV 可明文存储；③ 加密+签名的顺序：**先签名后加密**（签名覆盖明文，加密后签名也被保护），或"加密后签名"（签名覆盖密文，验签在解密前）；④ MCU 上优先用硬件 AES 加速器（比软件快 10~100 倍，且不占 CPU）。

### 4.3 ARM TrustZone 概念

TrustZone 是 ARM 的硬件安全扩展，把系统资源划分为**安全世界（Secure World）**和**普通世界（Normal World）**，硬件强制隔离。

| 维度 | 安全世界（Secure） | 普通世界（Normal） |
| --- | --- | --- |
| 运行内容 | 安全启动、密钥管理、加密运算、安全存储 | 普通应用、RTOS/Linux |
| 内存访问 | 可访问安全+普通内存 | **只能访问普通内存**（安全内存不可见） |
| 外设访问 | 可访问安全+普通外设 | 只能访问标记为普通的外设 |
| 中断 | 安全中断（Group 0/1 Secure） | 普通中断（Group 1 Non-secure） |
| 切换 | 执行 SMC 指令或中断触发 | 不能直接进入安全世界（必须通过受控入口） |

**Cortex-M TrustZone-M**（M23/M33/M55）：
- 内存分区通过 SAU（安全属性单元）+ IDAU 定义哪些地址是安全的
- 函数调用通过 `sg`（Secure Gateway）指令从普通世界进入安全世界，安全世界可通过 `bxns` 返回
- 密钥、安全启动逻辑放在安全世界，普通世界的固件即使被攻破也无法提取密钥

**Cortex-A TrustZone-A**（A 系列）：
- 安全监控器（Monitor）负责世界切换
- 安全世界运行可信操作系统（TEE，如 OP-TEE、Trusty）
- 普通世界运行 Linux/Android，通过 TEE Client API 调用安全服务

> TrustZone 不是"绝对安全"，而是缩小攻击面——把最敏感的操作（密钥、签名验签）放在隔离的安全世界，普通世界被攻破不影响安全世界的密钥安全。

### 4.4 安全启动与 OTA 结合的完整流程

```text
                        厂商服务器
                       ┌────────────┐
                       │ 1. 编译固件  │
                       │ 2. SHA-256  │
                       │ 3. RSA/ECDSA 签名（私钥）│
                       │ 4. AES 加密（可选）│
                       │ 5. 发布签名+加密镜像 │
                       └─────┬──────┘
                             │ HTTPS/MQTT 下发
                             ▼
┌──────────────────────────────────────────────────────────┐
│  设备侧 OTA 流程                                            │
│                                                              │
│  ① 下载新固件到备份区（B 区），边收边写 Flash               │
│  ② 下载完成后，计算 SHA-256 哈希                            │
│  ③ Bootloader 用内置公钥验签（RSA/ECDSA verify）           │
│     ├─ 验签失败 → 丢弃固件，保持运行当前版本，上报错误       │
│     └─ 验签通过 → 置"待切换"标志，复位                       │
│  ④ 复位后 Bootloader 再次验签（防止标志被篡改）              │
│     ├─ 通过 → 解密（如加密）→ 切换运行区 → 跳转新固件       │
│     └─ 失败 → 回滚到旧版本                                   │
│  ⑤ 新固件启动后自检（外设/通信/业务逻辑）                    │
│     ├─ 成功 → 清除回滚标志，确认升级完成                     │
│     └─ 失败（看门狗复位/自检超时）→ Bootloader 自动回滚      │
└──────────────────────────────────────────────────────────┘
```

| 安全层 | 防什么攻击 | 机制 |
| --- | --- | --- |
| 传输安全 | 中间人篡改/窃听 | HTTPS/TLS、MQTT over TLS |
| 固件完整性 | 下载过程损坏、存储位翻转 | SHA-256 哈希校验 |
| 固件真实性 | 攻击者伪造恶意固件 | RSA/ECDSA 数字签名 |
| 固件机密性 | 逆向工程、IP 泄露 | AES 加密 |
| 回滚保护 | 攻击者刷入已知有漏洞的旧版本 | 版本号单调递增检查（anti-rollback） |
| 密钥保护 | 从设备提取签名私钥/加密密钥 | OTP/TrustZone 安全世界存储，私钥永不出安全区 |
| 启动信任链 | 任何一级被篡改 | BootROM→Bootloader→App 逐级验签 |

> **实现参考**：MCU 上可用 MCUboot（开源安全 Bootloader，支持签名+加密+回滚，与 Zephyr/Mynewt 集成）；嵌入式 Linux 上可用 U-Boot 的 FIT 签名（`fit-signature`）+ dm-verity（只读分区完整性校验）；量产密钥管理用 HSM（硬件安全模块）存储签名私钥，私钥永不出 HSM。

| 机密性 | AES 加密 |
| 防回滚 | 版本号单调递增 |
| 信任链 | BootROM→Bootloader→App 逐级验签 |

## 6. 常见坑

1. **多处/中断里喂狗**：喂狗点分散则任何任务卡死都检测不到；只在主循环一个点喂，配合复位原因寄存器区分异常复位。
2. **Standby 模式丢数据**：Standby 下 RAM 除备份域外全丢，唤醒后变量复位；需保留的数据放备份寄存器/EEPROM/Flash。
3. **HardFault 只在 release 版出现**：release 不带 `-g`、优化等级高，PC 反查不到源码行；量产版也应保留 .elf/map 文件用于事后 `addr2line`。
4. **OTA 升级中断在写 Flash 时掉电**：直接覆盖运行区会变砖；必须 A/B 双区，新固件写 B、校验通过再切换，启动失败自动回滚。
5. **Flash 写前未按扇区擦除**：Flash 只能把 1 写成 0，写前必须按扇区/页擦成全 1；忽略擦除导致写入失败或数据错。
6. **私钥硬编码在固件**：逆向即可提取签名私钥，安全启动形同虚设；私钥只存 OTP/安全单元/TrustZone 安全世界，永不出安全区。
7. **签名加密顺序错**：应先签名后加密（签名覆盖明文），或加密后对密文签名；对明文签名却只加密密文会导致验签对象不一致。
8. **AES-CBC 用固定 IV**：相同明文加密出相同密文，泄露模式；每次加密用随机 IV，IV 可明文随固件一起存储。
9. **混淆"签名"与"加密"**：签名保证真实性/完整性（可公开验签），加密保证机密性；安全启动至少要签名，加密是可选的 IP 保护。
10. **跳过 anti-rollback**：攻击者可刷回有已知漏洞的旧版本；Bootloader 须校验版本号单调递增，拒绝降级。
