## 1. 存储引擎分类与定位

| 类型 | 代表 | 写方式 | 读方式 | 强项 | 弱项 |
| --- | --- | --- | --- | --- | --- |
| B+ 树 | InnoDB | 原地更新（in-place） | 沿树 3~4 次 IO | 点查与范围查询均衡、事务成熟 | 随机写、写放大来自页分裂 |
| LSM 树 | LevelDB/RocksDB/HBase/Cassandra/TiKV | 顺序追加 + 后台合并 | 多层查找 | **写吞吐极高、顺序写友好** | 读放大、空间放大、compaction 抖动 |
| 哈希 | Memcached、Redis 主表 | O(1) | O(1) | 点查极快 | 不支持范围、持久化需另做 |
| 列存 | ClickHouse、Parquet、Doris | 批量列块 | 只读列、向量化 | OLAP 聚合扫描、压缩比高 | 点更新/事务弱 |

| 维度 | OLTP | OLAP |
| --- | --- | --- |
| 负载 | 短事务、点查/小范围、高并发写 | 大范围扫描、聚合、少量大查询 |
| 模型 | 行存（B+树/堆） | 列存（压缩 + 向量化 + 列式块） |
| 代表 | MySQL/PostgreSQL/Oracle | ClickHouse/Doris/Spark SQL |

## 2. B+ 树（InnoDB 的骨架）

### 2.1 为什么磁盘索引用 B+ 树而不是二叉树/哈希/红黑树

磁盘按**页/块**读取（InnoDB 默认页 16KB），一次随机 IO 约 ms 级，比内存慢几个数量级，所以索引设计目标是**降低树高、让每个节点容纳尽可能多的键（高扇出 fanout）**：

```text
            ┌──────── 根节点（一页，存很多索引键 + 子指针）────────┐
          ┌─┴───────┬──────────┬─────────┴──────────┐
       内节点     内节点       内节点       内节点      ← 内节点只存键+指针，不存数据
     ┌─┴─┬─┴─┐  ┌─┴─┬─┴─┐   ┌─┴─┬─┴─┐   ┌─┴─┬─┴─┐
    叶子 叶子 叶子 叶子 叶子 叶子 叶子 叶子  ← 数据/主键行全在叶子，叶子间双向链表
    ◄──────────── 叶子按键有序、链表串联，范围扫描顺着走，不必回上层 ───────────►
```

- 一页可放数百个键，**千万级数据树高通常只有 3~4 层**，即一次点查 3~4 次 IO；且上层节点常驻 Buffer Pool，实际常只需 1 次磁盘 IO。
- 二叉树/红黑树是二叉、树高 log₂N（千万级约 24 层），每层一次 IO，磁盘场景不可接受。

### 2.2 B+ 树 vs B 树

| 维度 | B 树 | B+ 树 |
| --- | --- | --- |
| 数据位置 | 内节点和叶子都可存数据 | **只在叶子**，内节点只放键与指针 |
| 叶子链表 | 无 | 有，范围查询/顺序扫顺着链表 |
| 扇出 | 内节点被数据占空间，扇出小、树更高 | 内节点小，扇出大、树更矮 |
| 查同一键 | 可能在任意层命中，路径长度不一 | 必到叶子，查询路径长度稳定 |
| 范围查询 | 需中序遍历回溯 | 找到起点后沿叶子链顺序扫 |

### 2.3 InnoDB 索引体系（面试核心）

| 概念 | 说明 |
| --- | --- |
| 聚簇索引（主键索引） | **叶子节点直接存整行数据**，数据按主键有序物理组织；一张表只有一个 |
| 二级索引（辅助索引） | 叶子存"索引键 + 主键值"，查到后再拿主键回聚簇索引查整行 |
| **回表** | 二级索引找到主键 → 再查聚簇索引取行，多一次 B+树查找 |
| **覆盖索引** | 查询的列恰好都在二级索引里，无需回表（EXPLAIN 里 Using index） |
| 联合索引/最左前缀 | (a,b,c) 索引可服务 a、a,b、a,b,c 的查询，不满足最左列用不上 |
| 索引下推 ICP | 在存储引擎层就用 WHERE 中可用的索引列过滤，减少回表次数 |

```sql
select name from user where city='深圳';
  若有索引 (city,name)：索引里已有 city 和 name，直接返回 = 覆盖索引，不回表
  若只有索引 (city)：先在二级索引拿到一批主键，再逐个回表取 name = 回表
```

### 2.4 页、Buffer Pool 与原地更新

- **页（page，16KB）是磁盘与内存交换的最小单位**：B+树节点即页；行存在页内，页用槽位/页目录管理。
- **Buffer Pool**：内存缓存数据页/索引页，读先查缓冲；修改先改内存页（变脏页 dirty），由后台线程按 LRU/刷盘策略异步写回，合并随机写。
- 写导致页放不下时**页分裂**（页内有序，插入新行可能劈成两页）——这是 B+树写放大的主要来源；删除产生页合并。

## 3. LSM 树（Log-Structured Merge Tree）

### 3.1 写路径与读路径

```text
写 Put(k,v)
  │ ① 顺序追加 WAL（宕机可重放）
  ▼
MemTable（内存跳表，有序；写满冻结为 Immutable MemTable）
  │ flush（顺序写新文件，不修改老文件）
  ▼
L0 SSTable（各文件键范围可能重叠）──compaction──► L1（内部不重叠）
                                          ──compaction──► L2 ... Ln（层级越大文件越大）
读 Get(k)：MemTable → Immutable → L0(逐个文件) → L1..Ln(每层二分定位)
         每层先用 Bloom Filter 判断"肯定不在"，再用稀疏索引定位 block
```

| 组件 | 说明 |
| --- | --- |
| WAL | 预写日志，MemTable 未落盘前宕机靠它恢复 |
| MemTable | 内存有序结构，多用跳表（并发读、有序遍历简单） |
| SSTable | 磁盘不可变有序文件：data block + index block + bloom + footer |
| Compaction | 把多层文件合并、去重、丢弃删除标记（tombstone），控制文件数与读放大 |
| Bloom Filter | 位数组 + 多哈希，判"一定不存在 / 可能存在"，避免无谓读盘 |

### 3.2 两种主流 compaction 策略

| 策略 | 做法 | 特点 |
| --- | --- | --- |
| Size-Tiered（STCS，Cassandra/HBase 常用） | 大小相近的若干 SSTable 合并成一个更大的 | 写放大低，但空间放大高（同层重叠多） |
| Leveled（LCS，RocksDB/LevelDB 默认风格） | 每层内部键范围不重叠，满了与下一层有序归并 | 读放大、空间放大低，但**写放大高**（数据被反复重写） |
| Tiered/Leveled 取舍 | 写多用 STCS，读/空间敏感用 LCS | RocksDB 另有 FIFO、Universal 等变体策略 |

### 3.3 三种放大（写多读少还是读多写少的分水岭）

| 放大 | 定义 | LSM | B+树 |
| --- | --- | --- | --- |
| 读放大 RA | 一次逻辑读触发的实际 IO/查找次数 | 较高（多层 + Bloom） | 低（树高固定） |
| 写放大 WA | 一次逻辑写最终写盘的字节倍数 | compaction 重写，Leveled 可达 10~30 倍 | 页分裂/redo，通常较低 |
| 空间放大 SA | 实际占用 / 有效数据 | 多版本/tombstone 未 compact 前占空间 | 接近 1 |

> LSM 用"读放大、空间放大 + 后台 compaction"换"极高顺序写吞吐"；B+树用"原地随机写"换"稳定低读放大"。RocksDB 的 level 数、block/file 大小、compaction 线程与限速都是在三者间调平衡。

## 4. WAL / Redo Log 与崩溃恢复

### 4.1 为什么要先写日志（WAL 原则）

直接改磁盘数据页是**随机写、且要改多处**，崩溃在中间会留下半新半旧的页。WAL（Write-Ahead Log）规定：**先把"做了什么修改"顺序追加到日志并 fsync，再改数据页**；数据页可以延后异步刷。

```text
写请求 → ① 写 WAL（顺序追加，fsync 落盘）→ ② 改内存页 → ③ 数据页异步刷盘
崩溃恢复：
   从最近 checkpoint 开始重放 WAL：已提交事务重做（redo/前滚），
   未提交事务撤销（undo/回滚），把数据库恢复到一致状态
```

| 要点 | 说明 |
| --- | --- |
| 顺序写 | 日志只追加，磁盘顺序写远快于随机写 |
| fsync 粒度 | 每条事务 fsync 最安全但慢；组提交（group commit）攒一批一起 fsync 摊薄开销 |
| checkpoint | 记录"此前数据页已落盘"位置，恢复时不用从头重放全部日志 |
| redo vs undo | redo 重放已提交修改（物理日志）；undo 回滚未提交、支撑 MVCC 旧版本（逻辑日志） |

### 4.2 InnoDB 的三类日志（易混）

| 日志 | 层级 | 作用 |
| --- | --- | --- |
| redo log | InnoDB 引擎层、物理日志、循环写 | 崩溃恢复（持久性），WAL |
| undo log | InnoDB 引擎层、逻辑日志 | 回滚 + MVCC 旧版本链 |
| binlog | MySQL Server 层、逻辑日志、追加写 | 主从复制、时点恢复；与 redo 用两阶段提交(2PC)保证一致 |

## 5. 事务实现：MVCC 与隔离级别

| 机制 | 说明 |
| --- | --- |
| MVCC 多版本并发控制 | 每行保留多个版本（undo 版本链），**读不加锁、读写不阻塞**：读操作通过 ReadView 看到一致性快照 |
| ReadView | 记录生成时刻的活跃事务列表；沿版本链找第一个"对本视图可见"的版本 |
| RC vs RR | RC（读已提交）**每条语句**生成新 ReadView（不可重复读）；RR（可重复读）**事务首次读**生成一次，之后复用 |
| 当前读 vs 快照读 | `select` 快照读读旧版本；`select ... for update/update/delete` 当前读读最新并加锁 |
| 间隙锁/Next-Key | RR 下在索引间隙加锁，防止插入幻影行，解决幻读 |

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 RU | 可能 | 可能 | 可能 |
| 读已提交 RC | 避免 | 可能 | 可能 |
| 可重复读 RR（InnoDB 默认） | 避免 | 避免 | 基本避免（Next-Key Lock） |
| 串行化 | 避免 | 避免 | 避免 |

## 6. 其他关键结构

| 结构 | 用途 | 要点 |
| --- | --- | --- |
| 跳表 SkipList | MemTable、Redis ZSet | 多层链表 O(logN)，概率平衡、实现比红黑树简单、范围友好 |
| 布隆过滤器 | LSM/缓存穿透防护 | 多哈希位图；判不存在 100% 准，判存在有误判率；不能删（Counting Bloom 可删） |
| 哈希索引 | 内存点查 | O(1)，无序、不支持范围；InnoDB 自适应哈希 AHI 是内部自动建 |
| LSM 稀疏索引 | SSTable 每 block 一个键 | 索引小可常驻内存，定位到 block 再在块内查 |
| 位图/跳数索引 | 列存/分析库 | 低基数列快速过滤 |

## 7. B+树 vs LSM 选型

| 维度 | B+树（InnoDB） | LSM（RocksDB 系） |
| --- | --- | --- |
| 写吞吐 | 中（随机写 + 页分裂） | **高（顺序写）** |
| 读延迟 | 稳定、低 | 波动（多层/compaction），靠 Bloom/缓存 |
| 范围扫描 | 叶子链，强 | 需跨多文件归并 |
| 空间放大 | 低 | 中高（compaction 前） |
| 后台开销 | 刷脏页 | compaction 占 CPU/IO，可能抖动 |
| 事务/生态 | 成熟（MVCC/锁/外键） | 多为 KV，事务需额外实现 |
| 适合 | 通用 OLTP、读写均衡、强事务 | 写多读少、时序/日志/海量 KV、KV 分离场景 |

## 8. 快速参考卡片

```text
B+树：数据只在叶子+叶子双向链表；高扇出低树高(千万级3~4层IO)；InnoDB 页16K
聚簇索引叶子=整行；二级索引叶子=主键；回表=再查聚簇；覆盖索引不回表；最左前缀
Buffer Pool 缓存页，脏页异步刷；页分裂是 B+ 写放大来源
LSM：WAL→MemTable(跳表)→SSTable(L0..Ln)，读=内存+多层，Bloom 判不存在
compaction：STCS 写放大低/空间放大高；Leveled 反之；RA/WA/SA 三放大权衡
WAL：先顺序写日志并fsync，再改数据页；崩溃 redo 前滚 + undo 回滚 + checkpoint
InnoDB 三日志：redo(物理/持久) undo(回滚/MVCC) binlog(复制/2PC)
MVCC：undo 版本链 + ReadView；RC 每语句新视图，RR 事务级视图
选型：读写均衡强事务→B+树；写多读少海量KV→LSM；分析聚合→列存
```

## 9. 常见问题与坑

1. 只说"LSM 写快"讲不清代价：读放大、空间放大、compaction 抢占 IO 导致写停顿，必须一起答。
2. 混淆 redo log 与 binlog：前者引擎层物理循环写，后者 Server 层逻辑追加写，靠 2PC 一致。
3. 以为索引建了就走：不满足最左前缀、索引列上用函数/隐式类型转换、`like '%x'` 都会让索引失效。
4. 二级索引忘了回表代价：大表高频查询尽量做成覆盖索引。
5. Bloom Filter 说反：它只能保证"不存在一定准"，说"存在"是可能误判。
6. 把 B 树当 B+树：B 树内节点也存数据、无叶子链表，范围查询弱。
7. WAL 每条都 fsync 导致吞吐崩：用组提交批量 fsync，在持久性与性能间取舍。
8. 忽略 compaction 策略：写极多用 Size-Tiered，读/空间敏感用 Leveled，配错会放大问题。
9. MVCC 下以为 RR 完全无锁：快照读无锁，当前读/写仍要行锁与 Next-Key Lock。
