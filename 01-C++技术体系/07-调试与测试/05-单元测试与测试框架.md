## 1. 概述

### 1.1 为什么 C++ 比其他语言更需要单元测试

| C++ 的特殊性 | 后果 | 测试如何缓解 |
|---|---|---|
| 编译-链接周期长（见《../06-构建与版本控制/01-构建工具GCC与CMake.md》） | 手动"改一下再跑一遍"成本极高 | 测试一次编译，反复运行 |
| 内存错误多（越界、泄漏、悬垂指针） | 隐蔽且复现困难 | 测试配合 ASan（衔接《../06-构建与版本控制/01-构建工具GCC与CMake.md》2.4 的 `-fsanitize=address`） |
| 无运行时反射、无 GC | 回归全靠人肉 | 断言自动判定，失败即报告 |
| 未定义行为（UB）多 | "在我机器上是好的" | 参数化测试覆盖大量输入组合 |

### 1.2 测试金字塔

```text
        /  端到端(E2E)  \      数量少、慢、贵、贴近真实环境
       /   集成测试      \     中等数量、验证模块间协作
      /    单元测试       \    数量大、毫秒级、隔离（本篇重点）
```

| 层级 | 对象 | 速度 | 占比建议 | 典型工具 |
|---|---|---|---|---|
| 单元测试 | 单个函数/类，依赖被替身替换 | 毫秒级 | 约 70% | GoogleTest、Catch2、doctest |
| 集成测试 | 多模块组合、真实文件/数据库 | 秒级 | 约 20% | 同上 + 测试夹具 |
| 端到端 | 整个程序对外接口 | 分钟级 | 约 10% | 脚本 + 05-Shell脚本编程.md 的命令组合 |

### 1.3 FIRST 原则

| 原则 | 含义 | 反例 |
|---|---|---|
| Fast 快 | 单个用例毫秒级，整套秒级 | 用例里 sleep(5)、连真实网络 |
| Independent 独立 | 用例顺序无关，可单独运行 | 用例 A 依赖 B 先写入的全局变量 |
| Repeatable 可重复 | 任何环境结果一致 | 依赖当前时间、随机数、剩余磁盘 |
| Self-validating 自判定 | 通过/失败自动报告 | 用例里只 printf 不断言 |
| Timely 及时 | 与生产代码同步编写 | 上线前补测试 |

## 2. 框架选型对比

| 框架 | 当前版本 | 形态 | 编译速度 | 学习成本 | 适用场景 |
|---|---|---|---|---|---|
| GoogleTest + gmock | v1.14+（v1.13 起 要求 C++14） | 需编译的库（子模块/FetchContent/vcpkg） | 中等 | 中等 | 工业事实标准；需要 mock 的大中型项目；资料最多 |
| Catch2 | v3.x（v2.x 已停止新增特性） | v3 必须编译库（不再是单头文件）；v2 才是单头 `catch.hpp` | v3 相比 v2 明显改善 | 低 | 中小项目；喜欢 `REQUIRE(a == b)` 自然断言 |
| doctest | v2.4.x | 真正的单头文件 | 三者中最快 | 最低 | 编译时间敏感、教学、快速原型 |
| Boost.Test | 随 Boost 发行（1.8x） | 需编译或 header-only 模式 | 较慢 | 较高 | 项目已深度依赖 Boost 时顺带使用 |

选型建议：**新项目默认 GoogleTest**（配套 gmock、CI 生态、招聘熟悉度），个人小工具可用 doctest/Catch2 v3。

## 3. GoogleTest 入门

### 3.1 源码集成（FetchContent 完整示例，可直接复制）

```cmake
cmake_minimum_required(VERSION 3.14)   # FetchContent_MakeAvailable 需 3.14+
project(demo LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# ---------- 被测代码 ----------
add_library(mylib STATIC src/parser.cpp)
target_include_directories(mylib PUBLIC include)

# ---------- 拉取 GoogleTest（版本固定，保证可复现，详见 02-依赖管理与包管理器.md 第 5 章） ----------
include(FetchContent)
FetchContent_Declare(
  googletest
  GIT_REPOSITORY https://github.com/google/googletest.git
  GIT_TAG        v1.14.0
)
# Windows/MSVC 必设：让 gtest 使用与主项目一致的动态 CRT，否则链接报错
set(gtest_force_shared_crt ON CACHE BOOL "" FORCE)
FetchContent_MakeAvailable(googletest)

# ---------- 测试目标 ----------
enable_testing()
add_executable(unit_tests tests/test_parser.cpp tests/test_math.cpp)
# gtest_main 自带 main()，无需手写；若链接 GTest::gtest 则需要自己写 main
target_link_libraries(unit_tests PRIVATE mylib GTest::gtest_main)

# 自动把每个 TEST_* 注册为独立的 ctest 条目
include(GoogleTest)
gtest_discover_tests(unit_tests)
```

```bash
cmake -B build && cmake --build build -j8   # 配置 + 编译
ctest --test-dir build --output-on-failure  # 运行全部测试
```

### 3.2 最简单的用例：TEST 宏

```cpp
#include <gtest/gtest.h>
#include "mylib/parser.hpp"

// TEST(测试套件名, 用例名)：两个名字都会出现在失败输出里
TEST(ParserTest, ParsesSimpleKeyValue) {
  Parser p;
  auto result = p.Parse("key=value");
  EXPECT_TRUE(result.ok);          // 失败后本用例继续执行后面的断言
  EXPECT_EQ(result.value, "value");
}

int main(int argc, char** argv) {  // 仅当链接 GTest::gtest 而非 gtest_main 时需要
  ::testing::InitGoogleTest(&argc, argv);
  return RUN_ALL_TESTS();
}
```

### 3.3 夹具：TEST_F 复用 SetUp/TearDown

```cpp
// 夹具类必须继承 ::testing::Test
class QueueTest : public ::testing::Test {
 protected:
  void SetUp() override {     // 每个 TEST_F 运行前调用（构造之后的准备工作）
    q_.Enqueue(1);
    q_.Enqueue(2);
  }
  void TearDown() override {} // 每个 TEST_F 运行后调用（可不写，析构函数也可承担）
  Queue<int> q_;              // 每个用例拿到的是全新的对象——天然隔离
};

TEST_F(QueueTest, DequeueReturnsFifoOrder) {   // 必须用 TEST_F 而不是 TEST
  EXPECT_EQ(q_.Dequeue(), 1);
  EXPECT_EQ(q_.Dequeue(), 2);
}
```

| 夹具机制 | 时机 | 典型用途 |
|---|---|---|
| 构造函数 | 每个用例前 | 初始化成员 |
| SetUp() | 每个用例前（构造之后） | 需要访问 this 的初始化、可能抛异常的准备 |
| TearDown() | 每个用例后 | 释放构造函数无法可靠释放的资源 |
| 析构函数 | 每个用例后 | 默认资源回收 |
| SetUpTestSuite() | 整个套件仅一次 | 极重的公共资源（注意：会被所有用例共享，慎用） |

## 4. 断言大全

### 4.1 EXPECT 与 ASSERT 的区别

| 类别 | 失败后行为 | 适用场景 |
|---|---|---|
| EXPECT_* | 记录失败，**继续执行**本用例后续断言 | 一般校验，能一次看到多个问题 |
| ASSERT_* | **立即中止**本用例（通过 return） | 后续代码依赖该值时，如 `ASSERT_NE(p, nullptr)` 后解引用 p |

### 4.2 常用断言分类表

| 分类 | 断言 | 说明 | 示例 |
|---|---|---|---|
| 布尔 | EXPECT_TRUE / EXPECT_FALSE | 真/假判定 | `EXPECT_TRUE(ok)` |
| 相等 | EXPECT_EQ / EXPECT_NE | 需可 `==` 比较（自定义类型须提供 operator==） | `EXPECT_EQ(v.size(), 3)` |
| 大小 | EXPECT_LT / EXPECT_LE / EXPECT_GT / EXPECT_GE | 小于/小于等于/大于/大于等于 | `EXPECT_LT(latency_ms, 100)` |
| 字符串 | EXPECT_STREQ / EXPECT_STRNE / EXPECT_STRCASEEQ | C 风格 `const char*` 专用 | `EXPECT_STREQ(name, "root")` |
| 浮点 | EXPECT_NEAR / EXPECT_DOUBLE_EQ / EXPECT_FLOAT_EQ | **浮点必须用专用断言**：NEAR 指定绝对误差，DOUBLE_EQ/FLOAT_EQ 允许 4 个 ULP | `EXPECT_NEAR(0.1+0.2, 0.3, 1e-9)` |
| 异常 | EXPECT_THROW / EXPECT_NO_THROW / EXPECT_ANY_THROW | 断言语句抛出/不抛异常 | `EXPECT_THROW(v.at(9), std::out_of_range)` |
| 死亡 | EXPECT_EXIT / EXPECT_DEATH / EXPECT_DEATH_TEST | 见第 5.3 节 | `EXPECT_EXIT(f(), ExitedWithCode(0), "")` |
| 显式 | SUCCEED() / FAIL() / ADD_FAILURE() | 手工标记结果 | `FAIL() << "未实现"` |

```text
// 反例：浮点直接 EXPECT_EQ 会因二进制表示失败
EXPECT_EQ(0.1 + 0.2, 0.3);              // FAIL：0.30000000000000004 != 0.3
// 正解：绝对误差容忍
EXPECT_NEAR(0.1 + 0.2, 0.3, 1e-9);      // PASS
```

## 5. 进阶用法

### 5.1 值参数化：TEST_P + INSTANTIATE_TEST_SUITE_P

同一个函数吃多组输入，避免复制粘贴用例：

```cpp
bool IsPrime(int n);   // 被测函数

// 1) 夹具继承 TestWithParam<T>，T 是参数类型
class IsPrimeTest : public ::testing::TestWithParam<int> {};

// 2) 用 TEST_P 取参数
TEST_P(IsPrimeTest, ReturnsTrueForPrimes) {
  EXPECT_TRUE(IsPrime(GetParam()));
}

// 3) 一次性实例化多组输入（旧版叫 INSTANTIATE_TEST_CASE_P，已废弃）
INSTANTIATE_TEST_SUITE_P(PrimeValues, IsPrimeTest,
                         ::testing::Values(2, 3, 5, 7, 11, 13));
```

生成的用例名形如 `PrimeValues/IsPrimeTest.ReturnsTrueForPrimes/2`，可用 `--gtest_filter` 精确筛选。

### 5.2 类型参数化：TYPED_TEST

对模板容器用同一套断言跑多种类型：

```cpp
template <typename T>
class StackTest : public ::testing::Test {};   // 模板夹具

using MyTypes = ::testing::Types<int, double, std::string>;
TYPED_TEST_SUITE(StackTest, MyTypes);          // 旧名 TYPED_TEST_CASE 已废弃

TYPED_TEST(StackTest, PushIncreasesSize) {
  Stack<TypeParam> s;                          // TypeParam 即当前类型
  s.Push(TypeParam{});
  EXPECT_EQ(s.Size(), 1u);
}
```

### 5.3 死亡测试（Death Test）

原理：GoogleTest **fork 出子进程**执行危险语句，父进程 waitpid 检查退出码/信号——进程崩溃不会拖垮整个测试程序。用途：测试 `assert()`、`abort()`、致命错误分支。

```cpp
TEST(CrashTest, NegativeSizeAborts) {
  EXPECT_DEATH(Buffer(-1), "size must be positive");  // 第二参数：stderr 中的正则
}

TEST(ExitTest, NormalExitCodeZero) {
  EXPECT_EXIT(RunMainWithHelp(), ::testing::ExitedWithCode(0), "Usage:");
}
```

注意：死亡测试内不要开多线程（fork 只复制调用线程）。

## 6. gmock 打桩

### 6.1 MOCK_METHOD 语法

```cpp
// 新语法（gtest v1.10+，当前推荐）：
// MOCK_METHOD(返回类型, 方法名, (参数列表), (限定符))
class MockDb : public Db {
 public:
  MOCK_METHOD(bool, Connect, (const std::string& dsn), (override));
  MOCK_METHOD(int,  Query,  (const std::string& sql),  (const, override));  // 多个限定符逗号分隔
};
// 旧语法 MOCK_METHOD2(Connect, bool(const std::string&)) 已废弃，见到旧教程要转换
```

### 6.2 依赖注入 + EXPECT_CALL 三段式

```cpp
// ---- 接口（被测代码只依赖抽象）----
class WeatherService {
 public:
  virtual ~WeatherService() = default;
  virtual int GetTemperature(const std::string& city) = 0;
};

// ---- 被测类：构造注入 ----
class WeatherReport {
 public:
  explicit WeatherReport(WeatherService* svc) : svc_(svc) {}
  bool NeedsCoat() const { return svc_->GetTemperature("beijing") < 5; }
 private:
  WeatherService* svc_;
};

// ---- 测试 ----
TEST(WeatherReportTest, ColdCityNeedsCoat) {
  MockWeather mock;                 // class MockWeather : public WeatherService { MOCK_METHOD... }
  WeatherReport report(&mock);

  EXPECT_CALL(mock, GetTemperature(::testing::_))  // ① 匹配器：任意城市
      .Times(1)                                    // ② 次数：恰好一次
      .WillOnce(::testing::Return(-5));            // ③ 动作：返回 -5

  EXPECT_TRUE(report.NeedsCoat());  // 断言业务逻辑，gmock 在 TearDown 时核对调用次数
}
```

| 三段式组成 | 常用写法 | 说明 |
|---|---|---|
| 匹配器 | `_`（任意）/ `Eq(v)` / `Lt(n)` / `StrEq(s)` / `AllOf(...)` | 约定"哪些调用算数" |
| 次数 Times | `Times(2)` / `Times(AtLeast(1))` / `Times(Between(1,3))` / `Times(AnyNumber())` | 用例结束时核对，不符则报错 |
| 动作 | `WillOnce(Return(x))` / `WillRepeatedly(Return(y))` / `WillOnce(Invoke(f))` | 决定桩的返回/副作用 |

默认动作问题：未被 `EXPECT_CALL` 覆盖的调用，返回值是零值/垃圾。用 `ON_CALL` 兜底：

```text
ON_CALL(mock, GetTemperature(_)).WillByDefault(Return(20));  // 兜底默认值
```

### 6.3 何时该 mock、何时不该

| 情况 | 做法 |
|---|---|
| 依赖网络/数据库/时钟等慢或外部资源 | mock |
| 被测逻辑需要验证"是否调用了回调" | mock（spy 用法） |
| **被测类本身** | 绝不 mock 自己——那等于没测 |
| 简单纯函数依赖（如 std::string） | 不 mock，直接用真实现 |
| 依赖行为本身就是被测语义（如自定义分配器） | 用 fake 实现，不用 mock |

## 7. 测试组织与工程实践

### 7.1 目录结构建议

```text
project/
├── CMakeLists.txt
├── include/            # 对外头文件
├── src/                # 实现代码
└── tests/              # 与 src 平行，镜像源码结构
    ├── CMakeLists.txt
    ├── test_parser.cpp     # 对应 src/parser.cpp
    ├── test_math.cpp
    └── mocks/
        └── mock_db.h       # 公共 mock 放这里，避免重复定义
```

### 7.2 命名规范：被测函数_场景_期望结果

```cpp
// 好的命名：失败输出本身就是文档
TEST(Divide, PositiveOperands_ReturnsQuotient)   { EXPECT_EQ(Divide(6,3), 2); }
TEST(Divide, ZeroDividend_ReturnsZero)           { EXPECT_EQ(Divide(0,3), 0); }
TEST(Divide, ZeroDivisor_ThrowsInvalidArgument)  { EXPECT_THROW(Divide(6,0), std::invalid_argument); }

// 坏的命名：失败后无法定位
TEST(Divide, Test1) { EXPECT_EQ(Divide(6,3), 2); }
```

### 7.3 三段式好测试（正常 + 边界 + 异常）

| 用例类别 | 覆盖点 | 示例输入 |
|---|---|---|
| 正常路径 | 典型合法输入 | `Parse("key=value")` |
| 边界 | 空输入、单元素、极值、首尾下标 | `Parse("")`、`v[v.size()-1]` |
| 异常/错误 | 非法输入、资源不足 | `Parse("===not-kv===")` |

### 7.4 TDD 简介与务实策略

TDD 循环：**写失败的测试（红）→ 写最小实现让其通过（绿）→ 重构（重构）**。个人项目务实做法：

| 策略 | 说明 |
|---|---|
| 核心算法 TDD | 解析器、数学库这类纯逻辑，先写测试很划算 |
| 胶水代码事后补 | main、配置加载等低价值路径不必严格 TDD |
| 修 bug 先写复现用例 | 每个 bug 沉淀一个回归测试，防止复发 |
| 不追求覆盖率数字 | 覆盖率是手段不是目的，80% 的有意义分支好过 100% 的空跑 |

## 8. CMake/ctest 集成与 CI

### 8.1 ctest 常用命令表

| 命令 | 说明 | 示例 |
|---|---|---|
| `ctest --test-dir build` | 指定构建目录（CMake 3.20+，免 cd） | `ctest --test-dir build` |
| `ctest -R <正则>` | 只跑名称匹配的测试 | `ctest -R "Parser.*"` |
| `ctest -E <正则>` | 排除匹配的测试 | `ctest -E "Slow.*"` |
| `ctest --output-on-failure` | 失败才打印输出（CI 必加） | `ctest --output-on-failure` |
| `ctest -j N` | 并行运行 | `ctest -j8` |
| `ctest -L <label>` | 按标签筛选（用 set_tests_properties 设 LABELS） | `ctest -L slow` |
| `ctest --repeat until-fail:100` | 重复运行找不稳定测试 | `ctest --repeat until-fail:100` |
| `ctest --verbose` | 打印全部输出 | 调试测试本身时用 |

### 8.2 测试二进制的常用参数

|---|---|---|

## 9. 可测试性设计

### 9.1 依赖注入改造示例

```cpp
// ---------- 改造前：硬编码全局依赖，无法替换 ----------
class PriceService {
 public:
  double GetPrice(const std::string& sku) {
    return db_.Query("SELECT price FROM t WHERE sku='" + sku + "'");  // 真连数据库
  }
 private:
  SqliteDatabase db_;   // 具体类型，测试时没法换
};

// ---------- 改造后：接口 + 构造注入 ----------
struct PriceSource {                                   // 抽象接口
  virtual ~PriceSource() = default;
  virtual double GetPrice(const std::string& sku) = 0;
};

class PriceService {
 public:
  explicit PriceService(PriceSource& src) : src_(src) {}   // 注入
  double GetPrice(const std::string& sku) { return src_.GetPrice(sku); }
 private:
  PriceSource& src_;
};
// 生产代码注入 SqlPriceSource，测试注入 MockPriceSource
```

### 9.2 测试替身四兄弟

| 替身 | 定义 | 返回值 | 记录交互 | C++ 示例 |
|---|---|---|---|---|
| dummy | 只为凑齐参数签名，从不使用 | 否 | 否 | 传 `nullptr` 占位 |
| stub | 针对调用返回预设值 | 是 | 否 | `FakeClock` 返回固定时间 |
| spy | stub + 记录"被怎么调用过" | 是 | 是 | gmock 的 EXPECT_CALL 核对 |
| mock | 预设期望并验证交互契约 | 可 | 是 | `MOCK_METHOD` 生成的类 |
| fake | 可工作的简化实现 | 是 | — | 内存版 kv 存储代替 Redis |

### 9.3 不确定源的注入处理

| 不确定源 | 危害 | 注入方案 |
|---|---|---|
| 当前时间 | 测试结果随运行时刻变化 | 抽 `Clock` 接口，测试用 `FakeClock{now_value}` |
| 随机数 | 无法复现失败 | 随机数引擎由构造传入，测试注入固定种子（如 `std::mt19937 seed(42)`） |
| 环境变量/工作目录 | 换台机器就挂 | 启动时集中读取成配置结构体，测试直接构造结构体 |
| 线程调度 | 用例偶发失败 | 逻辑与线程分离：纯函数部分单测，并发部分进集成层 |

## 10. 快速参考卡片

### 10.1 "我要测 XX → 用什么机制"

| 需求 | 机制 | 关键语法 |
|---|---|---|
| 普通函数一次校验 | TEST | `TEST(Suite, Case)` |
| 多用例共享准备代码 | TEST_F 夹具 | `class X : public ::testing::Test` + SetUp |
| 同一函数多组输入 | 值参数化 | `TestWithParam<T>` + `TEST_P` + `INSTANTIATE_TEST_SUITE_P` |
| 模板类多类型验证 | 类型参数化 | `TYPED_TEST_SUITE` + `TYPED_TEST` |
| 验证"是否调用了依赖" | gmock | `EXPECT_CALL(...).Times(...)` |
| 替换慢/外部依赖 | gmock 打桩 | `MOCK_METHOD(Ret, Name, (Args), (override))` |
| 测 assert/abort 分支 | 死亡测试 | `EXPECT_DEATH(stmt, "regex")` |
| 整套测试统一调度 | CTest | `enable_testing()` + `gtest_discover_tests` |
| 防止低级错误漏网 | 编译期 | 测试目标也开 `-Wall -Wextra -fsanitize=address`（见《../06-构建与版本控制/01-构建工具GCC与CMake.md》） |
| 崩溃现场深挖 | gdb | 测试失败二进制直接交给 08-GDB程序调试.md 的手段调试 |

## 11. 常见问题与坑

| 问题 | 原因与解决方案 |
|---|---|
| 用例单独跑通过、整套跑失败 | 测试间共享静态/全局状态。改用夹具成员保存状态，每用例独立构造；用 `--gtest_shuffle` 暴露顺序依赖 |
| 浮点断言随机失败 | 用了 `EXPECT_EQ`。换 `EXPECT_NEAR(a, b, tol)` 或 `EXPECT_DOUBLE_EQ`（4 ULP 容差） |
| mock 方法返回垃圾值/随机数 | 未设期望的调用走默认动作。用 `ON_CALL(...).WillByDefault(Return(x))` 兜底，或确保每条路径都有 EXPECT_CALL |
| 静态函数/自由函数没法 mock | 静态绑定无法运行时替换。重构为类成员函数 + 接口，或把可变逻辑作为 `std::function` 参数传入 |
| 测试越跑越慢，最后没人跑 | 用例里做了真实 IO/sleep。慢测试打 `LABELS slow` 标签剥离，pre-push 只跑快集，CI 全量 |
| TEST_F 编译报 static_assert 失败 | 夹具忘了继承 `::testing::Test`（或参数化忘了继承 `TestWithParam<T>`）。检查基类 |
| INSTANTIATE_TEST_SUITE_P 放头文件被两个目标包含 | 链接期重复定义。实例化代码放 .cpp；公共 mock 头只放类定义不放 EXPECT_CALL |
| MSVC 下 gtest 链接 LNK2038 CRT 冲突 | 未设 `gtest_force_shared_crt=ON`。见 3.1 注释，或改用 vcpkg 安装（见 02-依赖管理与包管理器.md） |
| 死亡测试偶发卡死 | 子进程 fork 时存在多线程。死亡测试所在用例避免开线程，或把多线程逻辑移到普通用例 |
| Catch2 v3 按 v2 单头方式编译失败 | v3 不再提供单头。CMake 用 `find_package(Catch2 3 REQUIRED)` 链接 `Catch2::Catch2WithMain`（版本差异见第 2 章） |
| ctest 找不到测试 | 忘了 `enable_testing()`（需在顶层 CMakeLists），或只写了 add_test 没写目标。用 `ctest -N` 列出已注册测试排查 |
