## 1. 概述

### 1.1 优化总纲

> "过早优化是万恶之源" —— Donald Knuth（原话语境：97% 的时间花在 3% 的代码上，先找到那 3%）。

| 反模式 | 后果 |
|---|---|
| 凭直觉优化 | 常常改错地方，白费工还引入 bug |
| 先写"灵活"的抽象再优化 | 抽象泄漏性能，重构成本高 |
| 用 -O0 调试版测量 | 结论完全失真（见 1.3） |
| 正确姿势 | **先测量 → 定位热点 → 改 → 再测量对比**（第 2 章方法论） |

### 1.3 测量黄金法则

```text
# 分析用的构建：Release 优化 + 调试符号（两者不冲突）
g++ -O2 -g -std=c++17 -o myapp main.cpp
```

| 配置 | 问题 |
|---|---|
| -O0 + 测量 | 无内联、变量强制进内存、循环不展开——测的是"翻译"不是"程序"，结论全错 |
| -O2 无 -g | 有热点排名但看不到函数名/行号（perf 显示十六进制地址） |
| -O2 -g | **标准分析配置**：符号齐全，优化真实 |
| sanitizer 开着测量 | ASan/MSan 有 2-20 倍开销，只能测正确性不能测性能 |

## 2. 方法论

### 2.1 热点 80/20 与流程

经验上约 80% 的时间消耗在 20%（常常更少）的代码上。标准流程（PEP 风格：测量→定位→假设→修改→再测量）：

```text
 测量(基线) → 定位热点 → 提出假设("是 vector 重复分配") → 修改
     ↑                                                      │
     └────────── 再测量对比(无提升则回滚) ←──────────────────┘
```

| 步骤 | 工具/产物 | 关键纪律 |
|---|---|---|
| 1 建立基线 | perf stat / 计时脚本 | 基线数据要存档，供前后对比 |
| 2 定位 | perf record + report / 火焰图 | 看全局（含 libc/内核），别只盯自己写的函数 |
| 3 假设 → 4 修改 | 写下预期收益 | 一次只改一个变量 |
| 5 再测量 | 同环境同参数对比 | 无提升即回滚 |

### 2.2 profile 噪声源表

| 噪声源 | 表现 | 对策 |
|---|---|---|
| 环境抖动（其他进程） | 两次结果差 >10% | 多次运行取中位数；taskset 绑核 |
| CPU 频率漂移（睿频/温控） | 时间测量不稳定 | `cpupower frequency-set -g performance` 固定频率 |
| 页错误冷热差 | 首次运行显著慢 | 先跑一遍预热，或丢弃首次数据 |
| 采样与周期任务共振 | 某函数假热点 | 采样率避开 100 整数倍（如 -F 99），多轮交叉验证 |
| 虚拟机/云主机超分 | 结果不可复现 | 重要测量用物理机或独占 vCPU |

## 3. gprof（入门教学工具）

### 3.1 三步流程

```text
# 1) 编译时插桩（-pg）
g++ -pg -O2 -g -o myapp main.cpp
# 2) 正常运行，退出后在当前目录生成 gmon.out
./myapp
# 3) 解析报告
gprof myapp gmon.out > flat.txt     # 平坦报告
gprof myapp gmon.out --graph > graph.txt   # 含调用图
```

### 3.2 flat profile 输出解读

```text
 %   cumulative   self              self     total
time   seconds   seconds    calls  Ts/call  Ts/call  name
 45.2      2.10     2.10     1000     0.00     0.01  ParseJson(...)
```

| 列 | 含义 | 用法 |
|---|---|---|
| % time | 本函数自身时间占总时间百分比 | 排序找头部 |
| cumulative seconds | 累计时间（含排在其上函数） | 找到覆盖 80% 的截断点 |
| self seconds | 自身耗时（不含子调用） | 纯自身热点 |
| calls | 调用次数（插桩函数才有；库函数/未插桩显示为空） | 区分"单次慢"vs"次数多" |
| self Ts/call | 单次调用自身耗时 | 高→算法问题 |
| total Ts/call | 单次调用含子函数耗时 | 高→深挖其调用树 |

### 3.3 局限表（为什么生产用 perf）

| 局限 | 说明 |
|---|---|
| 需要重新编译 | -pg 插桩，改造成本高 |
| 看不到库内时间 | 未插桩的 libc/系统调用时间被摊派，定位失真；也无内核态视角（页错误/IO 不可见） |
| 采样精度低 | 依赖 profil() 定时器，多线程支持差 |
| 定位 | 入门理解"函数级时间分布"的最佳教具；实际项目直接用 perf |

## 4. perf（重点）

### 4.1 前提条件

```bash
# 权限检查：perf_event_paranoid 值决定可用范围
cat /proc/sys/kernel/perf_event_paranoid
#   4/3 = 禁止所有用户态采样；2 = 仅允许进程级用户态（内核态剖析被拒）；1 = 禁止系统级全机会话（进程级内核态仍可用）；0 = CPU事件含系统级但不含raw tracepoint；-1 = 全开
sudo sysctl kernel.perf_event_paranoid=-1          # 临时放开（需 root）
echo 'kernel.perf_event_paranoid=-1' | sudo tee /etc/sysctl.d/perf.conf   # 永久
# 容器内：需要容器被授予 PERFMON 权限或 --privileged，否则 perf record 报 "Permission denied"
# 无 PMU 的环境（部分虚拟机）：软件事件 cpu-clock 仍可用（见 4.3）
```

### 4.2 命令大表

| 命令 | 说明 | 示例 |
|---|---|---|
| `perf stat <cmd>` | 不采样，直接统计硬件计数器 | `perf stat ./myapp` |
| `perf stat -p <pid>` | 统计已运行进程 | `perf stat -p 1234 sleep 10` |
| `perf record <cmd>` | 采样记录到 perf.data | `perf record -F 99 -g ./myapp` |
| `perf record -p <pid>` | 附着到运行中进程 | 排查线上进程 |
| `perf report` | 交互式查看 perf.data | `perf report --sort=dso` |
| `perf top` | 实时热点（类 top 但到函数级） | `perf top -p 1234` |
| `perf list` | 列出本机可用事件 | `perf list \| grep cache` |
| `perf annotate` | 热点下钻到汇编/源码行 | `perf annotate` |
| `perf script` | 导出原始采样（喂给火焰图） | `perf script > out.perf` |

其余常用参数：`-F 99` 采样频率、`-e <event>` 指定事件、`--call-graph dwarf` 栈回溯方式（4.5）、`-d` 更多 stat 细节。

### 4.3 perf stat 指标解读表

```text
 Performance counter stats for './myapp':
       2345.67 msec task-clock        #    0.995 CPUs utilized
           1285      context-switches #    0.548 K/sec
          10234      page-faults      #    4.364 M/sec
    15,234,567,890      cycles        #    6.497 GHz
    18,765,432,109      instructions  #    1.23  insn per cycle
         7,654,321      branch-misses #    0.77% of all branches
```

| 指标 | 含义 | 异常信号 |
|---|---|---|
| task-clock | 占用 CPU 时间 | 与墙钟比看并行度 |
| context-switches | 上下文切换 | 突高 → 线程过多/锁竞争/IO 阻塞 |
| cpu-migrations | 进程在核间迁移 | 高 → 缓存反复失效，考虑 taskset 绑核 |
| page-faults | 缺页次数 | 高 → 分配模式差/工作集超内存 |
| cycles / instructions | 周期数与指令数 | 基础量 |
| IPC（insn per cycle） | 指令级并行度 | **<0.5 通常意味着停顿**：内存等待或分支失败；>1 才算健康 |
| branch-misses | 分支预测失败 | 占比高 → 数据排序/重组条件判断 |
| cache-misses | 缓存缺失 | 高 → 布局不友好（见第 6、9 章） |

### 4.4 常用事件表

| 事件 | 类型 | 说明 |
|---|---|---|
| `cpu-clock` | 软件事件 | **无 PMU 也可用**，虚拟机/受限环境首选 |
| `task-clock` | 软件事件 | 仅统计在 CPU 上的时间 |
| `page-faults` | 软件事件 | 缺页统计 |
| `context-switches` | 软件事件 | 切换统计 |
| `cycles` / `instructions` | 硬件 | IPC 计算 |
| `cache-misses` / `L1-dcache-load-misses` | 硬件 | 缓存行为（对布局优化敏感） |
| `branch-misses` | 硬件 | 分支预测 |

```bash
# 无 PMU 环境（部分虚拟机）用软件事件采样
perf record -e cpu-clock -F 99 -g ./myapp
```

### 4.5 输出解读与调用栈

perf report 每行：`Overhead | Command | Shared Object(Dso) | Symbol`。**Dso 列告诉你时间花在哪个二进制/库**（libc、libstdc++、驱动 vs 自己的模块）——只看自己代码是常见错误。

| `--call-graph` 方式 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| `fp`（帧指针） | 沿 rbp 链回溯 | 快、数据小 | 需要编译加 `-fno-omit-frame-pointer`，默认 -O2 会省略帧指针导致栈残缺 |
| `dwarf` | 借助 DWARF 调试信息 + libunwind | 不用改编译选项，栈完整 | perf.data 大（每采样几 KB），需 -g |
| `lbr` | Intel 硬件栈（Skylake+） | 开销最小 | 仅新 Intel CPU |

```bash
perf record --call-graph dwarf -F 99 ./myapp   # 最常用组合
perf report --sort=dso                          # 按库聚合看全局分布
perf annotate                                   # 进入热点函数看每条指令/源码行的采样占比
```

## 5. 火焰图

### 5.1 原理

把成千上万个采样点按**调用栈聚合**：相同栈合并为一个矩形，纵向是调用深度（栈底在下），横向宽度 = 该栈出现的采样数占比 = CPU 时间占比。宽的"平台"就是热点。

```text
 ┌───────────────────────────────────────────────┐
 │           ▁▁▁▁▁▁▁  parse()  42%                │ ← 最宽平台 = 最大热点
 │      ▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁              │
 │ main ── run() ── handle() ── io()             │ ← 栈底
 └───────────────────────────────────────────────┘
```

### 5.2 工具链完整命令

```bash
git clone https://github.com/brendangregg/FlameGraph
cd FlameGraph

# 1) 采样（99Hz 质数频率 + dwarf 栈）
perf record -F 99 --call-graph dwarf -o perf.data ./myapp

# 2) 导出原始采样并折叠调用栈
perf script -i perf.data > out.perf
./stackcollapse-perf.pl out.perf > out.folded

# 3) 生成可交互 SVG（浏览器打开，可点击下钻、Ctrl+F 搜索高亮）
./flamegraph.pl out.folded > flame.svg
```

### 5.3 on-CPU 与 off-CPU

| 视角 | 回答的问题 | 工具 |
|---|---|---|
| on-CPU 火焰图 | CPU 时间花在哪些函数 | perf record（本篇默认） |
| off-CPU 分析 | 线程阻塞时卡在哪个栈（IO/锁/睡眠） | BCC 的 `offcputime`（eBPF）、`pidstat -w` 辅助 |
| 全局 pid 视角 | 某进程整体 CPU 占用率 | top / pidstat（linux高级命令） |

判断：CPU 使用率高 → on-CPU 火焰图；CPU 低但延迟高 → off-CPU 分析（问题在等待不在计算）。

### 5.4 解读技巧表

| 技巧 | 说明 |
|---|---|
| 先找最宽平台 | 自上而下扫顶部的大矩形 |
| 顶部宽 vs 底部宽 | 顶部宽 = 该函数自身；底部宽 = 子树总和大，需逐层下钻找"贡献者" |
| 搜索高亮 | SVG 里 Ctrl+F 输入函数名，快速定位所有出现位置 |
| 看 Dso 颜色 | 火焰图按库着色，先确认时间在自家代码还是 libc/驱动 |
| 对比图 | 优化前后各生成一张，diff 形态（Brendan Gregg 的 flamegraphdiff） |

## 6. 内存性能

### 6.1 valgrind --tool=massif（衔接 09-Valgrind 内存检测.md 第 7 章）

```bash
# 采样堆内存曲线（开销约 10-20 倍，慢任务慎用）
valgrind --tool=massif --stacks=yes ./myapp
# 生成 massif.out.<pid>，文本化查看
ms_print massif.out.12345 | less
```

输出关键内容：随时间的堆/栈峰值曲线、峰值时刻的**分配栈归属**（哪个函数分配了最多字节）——定位"谁吃掉了内存"。

### 6.2 heaptrack（更低开销）

```bash
sudo apt install heaptrack heaptrack-gui
heaptrack ./myapp                      # 1) 记录，生成 heaptrack.myapp.<pid>.gz
heaptrack_print heaptrack.myapp.12345.gz > report.txt   # 2) 文本报告
heaptrack_gui heaptrack.myapp.12345.gz # 3) GUI 交互分析（火焰图式内存视图）
```

| 维度 | massif | heaptrack |
|---|---|---|
| 开销 | 10-20 倍（Valgrind 虚拟机） | 明显更低（拦截分配器） |
| 界面 | ms_print 文本（GUI 需 massif-visualizer） | 自带 heaptrack_gui（火焰图式视图） |
| 建议 | 已有 09-Valgrind内存检测.md 工作流时顺用 | 大程序/需要快速迭代时首选 |

### 6.3 内存优化清单表

| 手法 | 说明 | 适用 |
|---|---|---|
| 容器 reserve | vector/map 预留避免反复扩容搬移 | 已知规模上限时 |
| 小对象池/arena | 一次性分配大块自管理，替代高频 new | 大量短命小对象（见《../09-嵌入式开发/01-嵌入式开发导论与硬件基础.md》资源受限场景） |
| string SSO 认知 | 短字符串（libstdc++ 15 字节内）已免堆分配；长串共享要留心 | 字符串密集代码 |
| 结构体字段重排 | 消除对齐 padding | 海量结构数组 |
| 惰性加载/分页 | 大文件 mmap 而非全量读入 | 大数据集 |

```cpp
// 字段重排消 padding：按对齐要求从大到小排
struct BadLayout {          // char(1)+pad(7) + double(8) + int(4)+pad(4) = 24 字节
  char   type;
  double value;
  int    count;
};
struct GoodLayout {         // double(8) + int(4) + char(1)+pad(3) = 16 字节
  double value;
  int    count;
  char   type;
};
static_assert(sizeof(BadLayout) == 24, "布局检查");
static_assert(sizeof(GoodLayout) == 16, "布局检查");
static_assert(offsetof(GoodLayout, type) == 12, "offset 静态验证");
// 需要对齐控制时：alignas(64) 让缓存行独占（避免伪共享）
struct alignas(64) PaddedCounter { std::atomic<int> v; };
```

## 7. gperftools

```bash
sudo apt install libgoogle-perftools-dev   # 提供 libprofiler、libtcmalloc、pprof
```

### 7.1 CPU Profiler

```text
# 链接 -lprofiler（或 LD_PRELOAD=libprofiler.so 免重链）
g++ -O2 -g -o myapp main.cpp -lprofiler

CPUPROFILE=/tmp/myapp.prof ./myapp      # 运行结束生成采样文件
pprof --text myapp /tmp/myapp.prof       # 文本热点排名
pprof --web myapp /tmp/myapp.prof        # 调用图（需 graphviz）
pprof --pdf myapp /tmp/myapp.prof > cpu.pdf
```

### 7.2 tcmalloc：替换系统分配器

```text
# 方式一：链接期替换
g++ -O2 -o myapp main.cpp -ltcmalloc
# 方式二：运行期免重编译
LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libtcmalloc.so ./myapp
```

| 收益场景 | 原理 | 何时无效 |
|---|---|---|
| 多线程高频小对象分配 | 线程本地缓存避免锁竞争 | 单线程场景收益小 |
| 高分配率服务（解析、请求对象） | 更快的 size-class 分配 | 大块分配为主的程序 |
| 需要内存峰值控制 | 有 `ReleaseFreeMemory` 等调优接口 | 内嵌 glibc 假设的代码（《../09-嵌入式开发/01-嵌入式开发导论与硬件基础.md》场景需评估） |

### 7.3 Heap Profiler（查泄漏的替代方案）

```text
HEAPPROFILE=/tmp/myapp.hprof ./myapp    # 按增长阈值自动落盘多个快照
pprof --text myapp /tmp/myapp.hprof.0001.heap
```

与 09-Valgrind 内存检测.md Memcheck 的分工：Memcheck 精确报告"绝对丢失"的块；gperftools heap profiler 适合**持续增长型**问题（不泄漏但越用越多）的采样追踪。

## 8. Google Benchmark 微基准测试

### 8.1 为什么不用手写 for 计时

| 手写计时的坑 | 后果 | benchmark 的对策 |
|---|---|---|
| 编译器死码消除（DCE）删掉被测代码 | 测了个寂寞 | `benchmark::DoNotOptimize` |
| CPU 频率漂移/睿频、时钟粒度不够 | 数字随机跳动、短操作测不准 | 高精度计时 + 多轮统计 + 自动迭代次数 |
| 首次冷缓存 | 首个样本偏慢 | 多次迭代自动求稳态 |
| 报告无结构 | 没法对比回归 | 机器可读输出 + compare.py |

### 8.2 完整示例

```cpp
// bench_string.cpp —— 当前版本 v1.8.x；v1.1+ 用 range-for 风格循环
#include <benchmark/benchmark.h>
#include <algorithm>
#include <numeric>
#include <random>
#include <string>
#include <vector>

// 基本微基准
static void BM_StringCreation(benchmark::State& state) {
  for (auto _ : state) {                 // 旧 API 是 while (state.KeepRunning())
    std::string created("hello");
    benchmark::DoNotOptimize(created);   // 把对象"暴露"给优化器，防 DCE
    benchmark::ClobberMemory();          // 强制写回内存，防重排
  }
}
BENCHMARK(BM_StringCreation);

// 参数化：state.range(0) 取参数（测试不同长度字符串）
static void BM_StringCopy(benchmark::State& state) {
  std::string src(state.range(0), 'x');
  for (auto _ : state) {
    std::string copy(src);
    benchmark::DoNotOptimize(copy);
  }
  state.SetItemsProcessed(state.iterations() * state.range(0));  // 吞吐量（字节/秒）
}
BENCHMARK(BM_StringCopy)->Arg(8)->Arg(64)->Arg(512);

// 夹具：SetUp 阶段不计入测量时间
class SortBench : public benchmark::Fixture {
 protected:
  void SetUp(const benchmark::State&) override {
    data.resize(10000);
    std::iota(data.begin(), data.end(), 0);
    std::shuffle(data.begin(), data.end(), std::mt19937{42});  // 固定种子，可复现
  }
  std::vector<int> data;
};
BENCHMARK_F(SortBench, StdSort)(benchmark::State& state) {
  for (auto _ : state) {
    auto copy = data;                    // 每轮都从同一份乱序数据出发
    std::sort(copy.begin(), copy.end());
    benchmark::DoNotOptimize(copy);
  }
}

BENCHMARK_MAIN();                        // 取代自己的 main
```

```cmake
# CMake 集成（vcpkg/conan 安装 benchmark 后；FetchContent 固定 tag 见 02-依赖管理与包管理器.md 第 5 章）
find_package(benchmark REQUIRED)
add_executable(bench_string bench_string.cpp)
target_link_libraries(bench_string PRIVATE benchmark::benchmark)
```

```bash
./bench_string --benchmark_filter=BM_StringCopy   # 筛选
# 对比两个构建产物（基准库自带工具，路径为 benchmark 源码树 tools/ 目录）
python benchmark/tools/compare.py benchmarks ./bench_old --benchmark_filter=BM_ ./bench_new --benchmark_filter=BM_
```

| 常用选项 | 说明 |
|---|---|
| `--benchmark_filter=<re>` | 只跑匹配的基准 |
| `--benchmark_min_time=2s` | 每个基准至少跑 2 秒（默认 0.5s） |
| `--benchmark_repetitions=10` | 重复次数（报告均值与离散度） |
| `->Threads(4)` / `->Arg()` / `->ArgPairs()` | 多线程/多参数注册 |
| `state.SetBytesProcessed(n)` | 声明吞吐量口径 |

## 9. C++ 常见性能手法清单（按典型收益排序）

| 排序 | 手法 | 何时适用 | 反例（别瞎优化） |
|---|---|---|---|
| 1 | 算法复杂度降级（O(n²)→O(n log n)，如冒泡→std::sort、嵌套查找→哈希） | 有 profile 证据的热点 | 小 n（<32）时常数可能反超 |
| 2 | 减少拷贝：传 `const&`、`std::move`、返回值依赖 RVO、`reserve` | 大对象频繁传递/容器增长 | 小 POD（int/point）按值传更快 |
| 3 | 缓存友好布局：SoA 替代 AoS、字段重排、`alignas(64)` 防伪共享 | 遍历海量数据的循环 | 指针跳转为主的链式结构（先改数据结构） |
| 4 | 避免热路径重复构造：string 拼接预 reserve、把不变计算提出循环 | 字符串/对象在循环内构造 | 循环只跑几次的冷路径 |
| 5 | 数据结构选型：vector 而非 list（缓存局部性碾压）、`unordered_map` vs `map` | 顺序遍历为主、查找为主 | 需要稳定迭代器/有序遍历时别硬换 |
| 6 | 分支预测友好：排序数据、`[[likely]]`（C++20）标注主干 | 分支 miss 率高（perf stat 可见） | 分支占比很小时收益可忽略 |
| 7 | 内联热路径小函数（定义在头文件/`inline`） | 跨翻译单元的超热小函数 | 大函数内联膨胀反而伤 icache |
| 8 | 异步/并行：线程池拆分独立任务 | 各部分无共享数据 | 共享状态多时锁开销吃掉收益（先测） |

## 12. 常见问题与坑

| 问题 | 原因与解决方案 |
|---|---|
| 在 -O0 调试版上 profile，优化后毫无收益 | -O0 无内联、变量驻内存，热点分布与 Release 完全不同。永远用 `-O2 -g`（RelWithDebInfo）测量 |
| 微基准明明提升 30%，全局却没变化 | 微环境里缓存/分支行为与真实负载不同。以 perf stat 全局指标与端到端耗时为最终裁判 |
| 火焰图里只找自己写的函数，忽略 libc/驱动 | 时间常在 memcpy/strlen/内核态。看 Dso 维度聚合（`--sort=dso`）再定位 |
| perf record 报 Operation not permitted | perf_event_paranoid 限制或容器无 PERFMON 权限。sysctl 放开（4.1）或给容器加权限；退路是 `-e cpu-clock` 软件事件 |
| 虚拟机/云主机上采样结果漂移 | 超分与频率漂移。绑核（taskset）、固定性能模式、多次取中位数，关键测量用物理机 |
| perf report 全是十六进制地址，没有函数名 | 忘了 `-g` 调试符号。重编 `-O2 -g`；剥离过符号的二进制可先 `file myapp` 检查 |
| 调用栈只有零星几帧 | 帧指针被优化省略（-fomit-frame-pointer）。用 `--call-graph dwarf`，或编译加 `-fno-omit-frame-pointer` 用 fp 模式 |
| gprof 报告里库函数时间归零/归错 | 未插桩代码不计入，gprof 无内核态视角。换 perf（第 4 章） |
| massif 慢到跑不完真实负载 | Valgrind 10-20 倍开销。缩输入规模、降低 `--sample-period`，或换 heaptrack |
| benchmark 结果不可信（被优化没了/单次运行波动大） | 死码消除用 `benchmark::DoNotOptimize` 接住结果 + `ClobberMemory`；单次结论不可靠，用 `--benchmark_repetitions=10`、`--benchmark_min_time=2s` 看离散度 |
| 加了线程反而变慢 | 伪共享（多核争同缓存行）或锁竞争。`alignas(64)` 隔离热点计数器；perf stat 看 context-switches 突增 |
