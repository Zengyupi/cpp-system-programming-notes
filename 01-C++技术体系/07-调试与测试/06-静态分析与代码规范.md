## 1. 概述

### 1.1 防 bug 三道防线

```text
   写代码 ──→ 【防线1】编译期警告 ──→ 【防线2】静态分析 ──→ 【防线3】动态检测/测试
              -Wall -Wextra          clang-tidy/cppcheck     sanitizer + 单元测试
              （01-构建工具GCC与CMake.md    （本篇重点）            （01-构建工具GCC与CMake.md 2.4
               2.4 调试与警告选项）                           的 -fsanitize=address，
                                                       配合 15-单元测试与测试框架.md / 09-Valgrind内存检测.md）
        越靠左：发现越早、修复成本越低、覆盖面越广（不需要跑起来）
```

| 防线 | 检查时机 | 能查出 | 成本 |
|---|---|---|---|
| 编译器警告 | 编译时 | 未初始化、签名不匹配、可疑转换 | 几乎为零（第 6 章） |
| 静态分析 | 编译前后、提交前、CI | 使用后移动、拷贝浪费、坏味道、规范违反 | 秒到分钟 |
| 动态检测 | 运行时 | 越界、泄漏、数据竞争、逻辑断言失败 | 需要测试用例驱动 |

### 1.2 左移工具链

```text
   编辑器(LSP: clangd) ──实时红线──→ 你敲代码的那一刻
        │
   git pre-commit hook ──本地拦截──→ 提交那一刻（本篇第 8 章，衔接 03-Git版本控制.md 11.3）
        │
   CI 流水线 ──强制门禁──→ 合入主干前（-Werror / --dry-run -Werror）
```

## 2. clang-format：格式统一

### 2.1 安装

```bash
# Ubuntu/Debian（本知识库命令以 Linux/WSL 为准；Windows 可用 winget install LLVM.LLVM）
sudo apt install clang-format            # 版本随发行版，建议 14+
clang-format --version                   # 确认版本
```

### 2.2 .clang-format 常用配置项

放在仓库根目录，随 git 提交（团队唯一的格式事实来源）：

```text
---
# 基础风格：Google（也可 LLVM / Mozilla / WebKit / Chromium）
BasedOnStyle: Google
IndentWidth: 4          # 缩进 4 空格
TabWidth: 4             # Tab 宽度
UseTab: Never           # 永不用制表符（避免各编辑器显示不一）
ColumnLimit: 100        # 每行最大列数，0 表示不限制
PointerAlignment: Left  # 指针贴左：int* p（Right 则 int *p）
AllowShortFunctionsOnASingleLine: Inline  # 只允许类内联函数写一行
SortIncludes: CaseSensitive              # 对 #include 排序（14+ 新枚举值；旧版写 true/false）
AccessModifierOffset: -4                 # public/private 相对缩进
IncludeBlocks: Preserve                  # 保持 include 分组之间的空行
BreakBeforeBraces: Attach                # 大括号跟随行尾（Linux 风格则 Stroustrup/Allman）
```

| 配置项 | 推荐值 | 说明 |
|---|---|---|
| `BasedOnStyle` | Google / LLVM | 起点风格，其余项覆盖它 |
| `IndentWidth` / `TabWidth` / `UseTab` | 4 / 4 / Never | 缩进策略，最常吵架的一项 |
| `ColumnLimit` | 100（或 80） | 0 = 不限；限宽保证双栏 diff 可读 |
| `PointerAlignment` | Left | `int* p` vs `int *p` 之争一键终结 |
| `AllowShortFunctionsOnASingleLine` | Inline | 一行函数是否允许折叠 |
| `SortIncludes` | CaseSensitive | include 排序；注意 14 版起枚举值变更 |
| `AccessModifierOffset` | -4（配 IndentWidth 4） | 访问修饰符缩进 |
| `AlignAfterOpenBracket` | Align | 换行续排对齐方式 |
| `DerivePointerAlignment` | false | 关闭"按文件现状推断"，保证一致 |

### 2.3 常用命令表

| 命令 | 说明 | 示例 |
|---|---|---|
| `clang-format -i <files>` | 原地格式化 | `clang-format -i src/*.cpp include/*.h` |
| `clang-format --dry-run -Werror <files>` | 只校验不改写，违规即报错退出 | CI / hook 用 |
| `clang-format --style=file` | 从文件向上查找 .clang-format（默认行为） | 建议显式写在命令里 |
| `clang-format --dump-config` | 打印最终生效配置 | 排查某项被 BasedOnStyle 覆盖 |
| `git clang-format` | **只格式化本次改动涉及的行** | 大存量代码库渐进治理神器 |
| `git clang-format --diff` | 只显示改动行的格式差异 | hook 里做拦截 |

```bash
# 校验不修改（CI 门禁标准写法）
clang-format --dry-run -Werror $(git ls-files '*.cpp' '*.h')
# 存量仓库渐进治理：只动本次提交碰过的行
git clang-format -f
```

### 2.4 与 .editorconfig 的分工

| 工具 | 管什么 | 管不了什么 |
|---|---|---|
| .editorconfig | 编辑器通用基础：缩进风格、字符集、末尾换行、去尾随空格 | C++ 语法级排版 |
| .clang-format | C++ 的换行/对齐/空格/括号/排序 | 非 C++ 文件 |
| 结论 | 两者共存：.editorconfig 兜底所有语言，C++ 细节交给 clang-format | |

### 2.5 团队落地步骤

| 步骤 | 操作 |
|---|---|
| 1 | 技术负责人定稿 .clang-format 提交到仓库根 |
| 2 | 一次性全量格式化，**独立提交**（只含格式变更，方便 review 与 blame 忽略） |
| 3 | 编辑器装 clangd 扩展（保存即格式化，见01-构建工具GCC与CMake.md 5.7） |
| 4 | pre-commit hook 拦截（第 8 章） |
| 5 | CI 加 `--dry-run -Werror` 兜底 |

## 3. clang-tidy：深度静态检查

### 3.1 check 分组大表

| 分组 | 代表 check | 能查出什么 |
|---|---|---|
| `bugprone-*` | bugprone-use-after-move、bugprone-sizeof-expression、bugprone-dangling-handle | 易错模式：移动后使用、sizeof 算错、句柄悬垂 |
| `modernize-*` | modernize-use-nullptr、modernize-use-override、modernize-use-emplace、modernize-avoid-c-arrays | 旧写法现代化：NULL→nullptr、缺 override、C 数组 |
| `performance-*` | performance-unnecessary-copy-initialization、performance-for-range-copy、performance-move-const-arg | 不必要的拷贝、按值遍历、无效 move |
| `readability-*` | readability-function-size、readability-implicit-bool-conversion、readability-magic-numbers | 可读性：超长函数、隐式布尔转换、魔法数字 |
| `cppcoreguidelines-*` | cppcoreguidelines-init-variables、cppcoreguidelines-narrowing-conversions、cppcoreguidelines-pro-type-member-init | C++ Core Guidelines：未初始化、窄化转换、成员漏初始化 |
| `misc-*` | misc-unused-parameters、misc-non-private-member-variables-in-classes | 杂项：无用参数、类公开成员 |
| `clang-analyzer-*` | clang-analyzer-cplusplus.NewDeleteLeaks、clang-analyzer-deadcode.DeadStores | 流敏感分析：泄漏、死赋值 |

### 3.2 .clang-tidy 配置文件示例

```bash
# 放仓库根目录，同样随 git 提交
Checks: >
  -*,
  bugprone-*,
  modernize-*,
  performance-*,
  readability-*,
  cppcoreguidelines-*,
  misc-*,
  clang-analyzer-*,
  -modernize-use-trailing-return-type,
  -modernize-avoid-c-arrays,
  -readability-magic-numbers,
  -readability-identifier-naming,
  -cppcoreguidelines-avoid-magic-numbers
WarningsAsErrors: ''            # 哪些 check 升级为错误；空 = 只警告
HeaderFilterRegex: 'src/.*|include/.*'   # 只检查自己代码的头（跳过系统/三方头）
FormatStyle: file               # 自动修复时遵循 .clang-format
```

语法要点：`-*` 关掉全部再白名单打开；`-check-name` 表示排除；顺序敏感（后面的覆盖前面）。

### 3.3 与 compile_commands.json 配合

clang-tidy 必须知道每个文件的编译参数（-I、-std、宏），否则头文件路径全对不上：

```bash
# CMake 生成编译数据库（衔接 01-构建工具GCC与CMake.md 5.7）
cmake -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON

# 检查单个文件（-p 指向 compile_commands.json 所在目录）
clang-tidy -p build src/parser.cpp

# 列出当前配置启用的所有 check
clang-tidy --list-checks

# 并行全仓扫描（readme 自带脚本，Linux 用 run-clang-tidy）
run-clang-tidy -p build src/

# 自动修复（务必先看 diff）
clang-tidy -p build --fix src/parser.cpp
run-clang-tidy -p build -fix src/
```

| 命令 | 说明 |
|---|---|
| `clang-tidy -p build <file>` | 检查单文件 |
| `clang-tidy --list-checks` | 查看启用清单 |
| `run-clang-tidy -p build src/` | 按 CPU 核数并行全仓 |
| `clang-tidy --fix -p build <file>` | 应用 fixit |
| `clang-tidy --fix-errors` | 连编译错误也尝试修（危险，少用） |

### 3.4 --fix 的纪律

自动修复会真实改动代码，必须：先在独立分支跑 → `git diff` 逐文件审查 → 与功能提交分离。详见第 10 章坑表。

## 4. cppcheck：轻量快速

### 4.1 定位

不依赖编译数据库也能跑（自己解析语法），单线程全仓也很轻，适合 CI 全量兜底与没有完整构建环境的场景。与 clang-tidy 互补：

| 维度 | cppcheck | clang-tidy |
|---|---|---|
| 依赖 | 无（可独立运行） | 需要 compile_commands.json 才准 |
| 速度 | 快 | 慢（含语义分析） |
| 规则丰富度 | 中 | 高（几百个 check） |
| 误报率 | 中（配合 --inconclusive 标注） | 中 |
| 定位 | CI 全量兜底、快速扫描 | 深度检查、自动修复 |

### 4.2 常用命令与选项表

```text
# 全量：警告+风格+性能+可移植性，指定标准
cppcheck --enable=all --std=c++17 --inconclusive src/

# 复用 CMake 编译数据库，路径与宏更准确
cppcheck --project=build/compile_commands.json --enable=warning,style

# CI 输出 XML
cppcheck --xml --output-file=cppcheck.xml src/

# 嵌入式 MISRA 检查（衔接《../09-嵌入式开发/07-嵌入式工程实践与设计模式.md》，需 addons 目录随源码安装）
cppcheck --addon=misra src/

# 行内压制误报
cppcheck --inline-suppr src/    # 配合代码中 // cppcheck-suppress memo
```

| 选项 | 说明 | 示例 |
|---|---|---|
| `--enable=all` | 打开 warning/style/performance/portability/information | 最常用 |
| `--enable=warning,style` | 只开部分级别 | CI 折中 |
| `--std=c++17` | 按 C++17 规则解析 | 与项目 -std 一致 |
| `--project=<db>` | 读取 compile_commands.json | 精确路径 |
| `--inconclusive` | 连不确定的也报（更多误报） | 本地深查 |
| `--xml --output-file` | XML 报告 | CI 展示 |
| `--addon=misra.py` | MISRA C 规则 addon | 嵌入式合规 |
| `--suppressions-list=file` | 批量压制清单 | 存量代码治理 |

## 5. include-what-you-use 与头文件卫生

### 5.1 未用 include 的代价

| 代价 | 说明 |
|---|---|
| 编译时间 | 每个多余 include 都是一棵要展开的子树（大型项目头文件占大头） |
| 传递依赖伪装 | 依赖别人"顺带"包含的头，上游一重构就碎 |
| 重编译风暴 | 无关头文件被改，大量 .cpp 无辜重编（配合 make 的依赖追踪，见01-构建工具GCC与CMake.md 4.3） |

### 5.2 用法

```bash
sudo apt install iwyu            # 或从 github/include-what-you-use 源码编译
# 单文件（需编译参数，-Xiwyu 传 IWYU 自身选项）
include-what-you-use -Xiwyu --no_comments -std=c++17 -Iinclude src/parser.cpp
# 并行批量（读编译数据库）
iwyu_tool -p build src/
# CMake 一键集成：编译时对所有文件跑 IWYU
cmake -B build -DCMAKE_CXX_INCLUDE_WHAT_YOU_USE="include-what-you-use;-Xiwyu;--no_comments"
```

### 5.3 前向声明 vs include 的取舍

| 手段 | 优点 | 代价 | 适用 |
|---|---|---|---|
| include | 完整类型可用（创建、继承、访问成员） | 编译时间、耦合 | 需要完整类型时 |
| 前向声明 `class Foo;` | 零成本、解耦 | 只能用于指针/引用/声明参数 | 头文件里的成员指针、函数参数 |

```cpp
// widget.h —— 头文件里只用到指针/引用，前向声明足够
class Renderer;                    // 前向声明：不动 renderer.h
class Widget {
 public:
  void Draw(Renderer& r) const;    // 引用，无需完整类型
 private:
  Renderer* renderer_ = nullptr;   // 指针，同样无需完整类型
};
```

## 6. 编译警告纪律

### 6.1 必开组合（GCC/Clang）

```text
g++ -std=c++17 -Wall -Wextra -Wshadow -Wconversion -Wpedantic -c foo.cpp
```

| 警告 | 抓什么 | 强度建议 |
|---|---|---|
| `-Wall -Wextra` | 基础大礼包（未用参数、有符号比较等） | 必开 |
| `-Wshadow` | 局部变量遮蔽外层/成员变量（改错对象的经典来源） | 强烈建议 |
| `-Wconversion` | 隐式窄化转换（int→char、size_t→int） | 建议开，老代码可能吵 |
| `-Wold-style-cast` | C 风格强制转换 `(int)x` | 团队可选（Google 风格禁用 C 转） |
| `-Wnon-virtual-dtor` | 基类有虚函数但析构非虚 | 必开（UB 级问题） |
| `-Woverloaded-virtual` | 子类隐藏了父类虚函数重载 | 建议 |
| `-Werror` | 警告当错误 | **只在 CI 用**（见坑表） |

### 6.2 MSVC 对照表（跨平台团队）

| GCC/Clang | MSVC 等价 | 说明 |
|---|---|---|
| `-Wall -Wextra` | `/W4` | MSVC 的 /Wall 比 /W4 吵得多，通常取 /W4 |
| `-Wshadow` | C4456/C4457/C4458/C4459 | /W4 下默认不报，需 `/w4456` 显式提级 |
| `-Wconversion` | C4244/C4267/C4245 | /W4 下部分覆盖 |
| `-Werror` | `/WX` | 同样仅 CI |
| `-Wpedantic` | `/permissive-` | MSVC 用严格一致性模式替代 |

CMake 写法（衔接 01-构建工具 GCC 与 CMake.md 5.4）：

```cmake
if(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
  add_compile_options(-Wall -Wextra -Wshadow -Wconversion)
elseif(MSVC)
  add_compile_options(/W4 /permissive-)
endif()
```

## 7. 代码规范要点（以 Google C++ Style 为纲的速览）

> 各家规范（Google/LLVM/其他公司内规）差异多为风格无对错，**关键是全仓库统一**。机械部分交给 .clang-format + .clang-tidy（第 2、3 章）即可执行 80%。

### 7.1 头文件纪律

| 规则 | 说明 |
|---|---|
| 自包含 | 每个 .h 单独编译通过（include 自己需要的全部依赖，不依赖包含顺序） |
| 守卫命名 | `#define PROJECT_PATH_FILE_H_`（全路径 + 尾下划线，避免冲突） |
| include 顺序 | 对应头 → C 系统 → C++ 标准库 → 三方库 → 项目内（clang-format SortIncludes 自动保证组内有序） |

### 7.2 命名约定表

| 实体 | Google 风格 | 示例 |
|---|---|---|
| 类/结构/枚举/类型别名 | 大驼峰 CamelCase | `class UrlTable` |
| 普通函数/成员函数 | 大驼峰（首单词可小写的旧风格已弃） | `AddTableEntry()` |
| 局部变量/函数参数 | 下划线 snake_case | `loop_counter` |
| 类私有数据成员 | snake_case + 尾下划线 | `table_entries_` |
| 结构体公开成员 | snake_case 无尾缀 | `struct Point { int x; }` |
| 编译期常量 | k + 大驼峰 | `constexpr int kDaysInWeek = 7;` |
| 枚举值 | k + 大驼峰 | `enum class Color { kRed, kGreen }` |
| 宏 | 全大写下划线 | `#define LOG_ERROR(...)` |
| 文件名 | 小写下划线 | `url_table.cpp` / `url_table_test.cpp`（配合15-单元测试与测试框架.md 命名） |

### 7.3 所有权与设计约定

```cpp
// 所有权转移用注释显式声明（配合智能指针使用处的可读性）
// 返回的指针所有权转移给调用者（C++ 里裸指针默认不管理所有权）
std::unique_ptr<Connection> CreateConnection();

class Consumer {
 public:
  // consumer 不拥有 source（借用，生命周期由调用方保证）
  explicit Consumer(PriceSource& source);
};
```

| 约定 | 建议 |
|---|---|
| 裸指针语义 | 默认"不管理所有权"；转移用 `std::unique_ptr` + 注释 |
| 单参构造函数 | 加 `explicit` 防隐式转换 |
| 异常/RTTI | 视项目定：嵌入式常禁用（见《../09-嵌入式开发/02-MCU启动流程与嵌入式C关键技术.md》g++ -fno-exceptions）；业务后端可用 |
| 隐式转换 | 禁用双参以上的转换构造，operator 转换慎用 |
| 输出参数 | 避免裸 out 指针，优先返回结构体/std::optional |

## 8. 流程集成：从编辑器到 CI

### 8.1 git pre-commit hook 完整脚本（衔接 03-Git 版本控制.md 11.3）

```bash
#!/bin/sh
# 文件：.git/hooks/pre-commit（chmod +x），hook 机制见 03-Git版本控制.md 第 11.3 节
# 目标：只拦截"本次提交的 C++ 文件"的格式问题，控制在秒级

# 1. 取暂存区中新增/修改的 C++ 文件
changed=$(git diff --cached --name-only --diff-filter=ACM \
          | grep -E '\.(c|h|cpp|hpp|cc|cxx)$' || true)
[ -z "$changed" ] && exit 0          # 没碰 C++ 文件直接放行

# 2. 只校验改动行（存量代码不受影响）—— git clang-format 随 clang-format 附带
if ! git clang-format --diff --extensions c,h,cpp,hpp,cc,cxx; then
  echo ""
  echo "[pre-commit] 格式不符合 .clang-format，请运行: git clang-format -f"
  exit 1
fi

# 3. 快速警告门禁（不做深度分析，保持 hook 秒级）
if ! echo "$changed" | xargs clang-format --dry-run -Werror 2>/dev/null; then
  echo "[pre-commit] 存在格式违规（整文件检查）"
  exit 1
fi
exit 0
```

### 8.2 pre-commit 框架（团队一键安装 hooks）

```bash
# .pre-commit-config.yaml —— 提交到仓库，成员执行 pre-commit install 即生效
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.5.0
    hooks:
      - id: check-merge-conflict      # 拦截未解决的冲突标记
      - id: end-of-file-fixer         # 文件末尾换行
      - id: trailing-whitespace       # 去尾随空格
  - repo: https://github.com/pre-commit/mirrors-clang-format
    rev: v17.0.6                      # 固定版本，保证全队输出一致
    hooks:
      - id: clang-format
        types_or: [c++, c]
  - repo: https://github.com/pocc/pre-commit-hooks
    rev: v1.3.5
    hooks:
      - id: cppcheck
        args: ["--enable=warning,style", "--std=c++17"]
```

## 10. 常见问题与坑

| 问题 | 原因与解决方案 |
|---|---|
| clang-tidy 报一堆头文件找不到 | 没有编译数据库或没传 `-p build`。`cmake -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON` 后重跑（衔接01-构建工具GCC与CMake.md 5.7） |
| `--fix` 自动修复后代码坏了 | fixit 并非总正确（尤其宏展开处）。独立分支跑、`git diff` 逐块审查、与功能提交分离 |
| 规范讨论浪费大量会议时间 | 风格无对错。用 .clang-format 生成即终局，讨论预算留给架构设计 |
| `modernize-*` 全量开，警告刷屏 | 白名单制：排除不认同的（如 trailing-return-type）；新规则先本地试运行一周再进 CI |
| 一次性全仓 format 后 blame 全断 | 格式化单独成提交，并用 `git blame -w -C`（忽略空白、跨移动追踪）查历史 |
| 本地开 `-Werror` 后换编译器版本全员编不过 | 警告集随版本变化。`-Werror` 只放 CI 固定版本镜像，本地默认不启用 |
| clang-tidy 全仓跑太慢没人等 | `run-clang-tidy` 并行 + CI 只对 PR 改动文件跑；hook 里只放 clang-format |
| 不同成员 clang-format 版本不同，格式抖动 | .clang-format 部分选项值随版本演进（如 SortIncludes 枚举化）。团队锁定同一版本（pre-commit 框架的 rev 固定就是为此） |
| cppcheck 误报太多渐渐没人看 | 用 `--inline-suppr` + `// cppcheck-suppress <id>` 精准压制；CI 只开 warning 级别 |
| IWYU 删头后其他翻译单元编不过 | 该头此前被"传递包含"掩盖了真实依赖。IWYU 逐文件跑并全量编译验证，别一把梭 |
| hook 里跑 clang-tidy 太慢，开发者直接绕过 | hook 只做秒级检查（clang-format），重量级放 CI；提供 `--no-verify` 之外的正道：慢检查改 pre-push（03-Git版本控制.md 11.3） |
