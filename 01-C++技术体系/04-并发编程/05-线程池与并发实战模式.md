## 1. 线程池基础

### 1.1 线程池（任务队列 + 条件变量 + 原子停止位）

```cpp
#include <condition_variable>
#include <functional>
#include <mutex>
#include <queue>
#include <thread>
#include <vector>

class ThreadPool {
public:
    explicit ThreadPool(std::size_t n) : stop_(false) {
        for (std::size_t i = 0; i < n; ++i)
            workers_.emplace_back([this] {
                for (;;) {
                    std::unique_lock<std::mutex> lk(m_);
                    cv_.wait(lk, [this] { return stop_ || !tasks_.empty(); });  // 等任务或停止
                    if (stop_ && tasks_.empty()) return;        // 排空任务后才退出
                    auto task = std::move(tasks_.front());
                    tasks_.pop();
                    lk.unlock();                                // 执行期间放锁
                    task();                                     // 真正干活（可能抛异常，见注释）
                    lk.lock();
                }
            });
    }
    ~ThreadPool() {
        { std::lock_guard<std::mutex> lk(m_); stop_ = true; }   // 先置停止位（持锁修改共享状态）
        cv_.notify_all();                                       // 再广播唤醒
        for (auto& t : workers_) t.join();                      // 等全部 worker 退出
    }
    template <typename F>
    void submit(F&& f) {
        { std::lock_guard<std::mutex> lk(m_); tasks_.emplace(std::forward<F>(f)); }
        cv_.notify_one();
    }
private:
    std::vector<std::thread> workers_;
    std::queue<std::function<void()>> tasks_;
    std::mutex m_;
    std::condition_variable cv_;
    bool stop_;                                                 // 仅在持锁时读写
};
// 注：生产实现还应有：任务里 try/catch 防止异常杀线程、submit 返回 future、
//     线程数按 CPU 密集/IO 密集选择、动态扩缩容等。
```

## 2. 线程池进阶

基础线程池在高并发场景下有几个瓶颈：所有 worker 竞争同一个全局队列（锁竞争）、无法区分任务优先级、线程数固定不能适应负载波动、队列无界可能 OOM。本节逐一解决。

### 2.1 Work-Stealing 工作窃取算法

**核心思想**：每个 worker 线程有自己的本地任务队列（deque），worker 优先从自己的队列取任务；当本地队列为空时，去**窃取**其他 worker 队列末尾的任务。

```text
线程布局：
  Worker 0: [本地 deque 0] ← 自己从头部取（push/pop 头部，无竞争）
  Worker 1: [本地 deque 1] ← 空闲时从 Worker 0 的尾部偷（pop 尾部，有竞争用 CAS）
  Worker 2: [本地 deque 2]
  Worker 3: [本地 deque 3]

任务提交：
  submit() → 随机选一个 worker 的本地队列 push，或用全局队列分发

工作流程：
  1. Worker 从自己 deque 头部 pop（LIFO，缓存友好：刚提交的任务数据还在缓存）
  2. 自己队列为空 → 随机选一个 victim，从其 deque 尾部 pop（FIFO 窃取）
  3. 所有队列都空 → 条件变量等待新任务
```

Work-stealing 的关键优势：

| 维度 | 全局单队列 | Work-stealing |
| --- | --- | --- |
| 锁竞争 | 所有 worker 竞争同一把锁 | 本地操作无锁，仅窃取时有 CAS 竞争 |
| 缓存亲和性 | 任务随机分配到任意核 | LIFO 取任务，刚提交的任务数据仍在本核缓存 |
| 负载均衡 | 依赖调度器 | 自动窃取均衡（空闲线程偷忙线程的任务） |
| 实现复杂度 | 简单 | 复杂（需要无锁 deque + 窃取协议） |

C++17 work-stealing 线程池核心代码（简化版）：

```cpp
#include <atomic>
#include <deque>
#include <functional>
#include <mutex>
#include <random>
#include <thread>
#include <vector>
#include <condition_variable>

class WorkStealingPool {
public:
    explicit WorkStealingPool(std::size_t n) : stop_(false) {
        for (std::size_t i = 0; i < n; ++i)
            local_queues_.emplace_back(std::make_unique<LocalQueue>());
        for (std::size_t i = 0; i < n; ++i)
            workers_.emplace_back([this, i] { worker_loop(i); });
    }

    ~WorkStealingPool() {
        { std::lock_guard<std::mutex> lk(m_); stop_ = true; }
        cv_.notify_all();
        for (auto& t : workers_) t.join();
    }

    void submit(std::function<void()> task) {
        std::size_t idx = rng_() % workers_.size();  // 随机选一个本地队列
        local_queues_[idx]->push(std::move(task));
        cv_.notify_one();
    }

private:
    struct LocalQueue {
        std::deque<std::function<void()>> dq;
        std::mutex mtx;
        void push(std::function<void()> f) {
            std::lock_guard<std::mutex> lk(mtx);
            dq.push_front(std::move(f));  // 头部 push
        }
        bool pop_local(std::function<void()>& out) {
            std::lock_guard<std::mutex> lk(mtx);
            if (dq.empty()) return false;
            out = std::move(dq.front()); dq.pop_front();  // 头部 pop（LIFO）
            return true;
        }
        bool steal(std::function<void()>& out) {
            std::lock_guard<std::mutex> lk(mtx);
            if (dq.empty()) return false;
            out = std::move(dq.back()); dq.pop_back();    // 尾部 pop（FIFO 窃取）
            return true;
        }
    };

    void worker_loop(std::size_t my_idx) {
        std::function<void()> task;
        while (true) {
            // 1. 优先从自己的本地队列取
            if (local_queues_[my_idx]->pop_local(task)) {
                task();
                continue;
            }
            // 2. 随机窃取其他 worker
            bool stole = false;
            for (std::size_t attempt = 0; attempt < workers_.size(); ++attempt) {
                std::size_t victim = (my_idx + attempt + 1) % workers_.size();
                if (local_queues_[victim]->steal(task)) { stole = true; break; }
            }
            if (stole) { task(); continue; }
            // 3. 都没有，等待
            std::unique_lock<std::mutex> lk(m_);
            cv_.wait(lk, [this] { return stop_ || has_any_task(); });
            if (stop_ && !has_any_task()) return;
        }
    }

    bool has_any_task() {
        for (auto& q : local_queues_)
            if (!q->dq.empty()) return true;  // 注意：此处未加锁，仅作快速检查
        return false;
    }

    std::vector<std::thread> workers_;
    std::vector<std::unique_ptr<LocalQueue>> local_queues_;
    std::mutex m_;
    std::condition_variable cv_;
    bool stop_;
    std::mt19937 rng_{std::random_device{}()};
};
```

> 生产级 work-stealing（如 Intel TBB、Go runtime、Java ForkJoinPool）使用**无锁的 Chase-Lev deque**：本地 push/pop 用原子操作无锁，窃取端用 CAS。上面的简化版用 mutex 保护每个 deque，逻辑正确但性能不是最优。完整无锁实现参见 09 模块。

### 2.2 优先级任务队列

基础线程池的任务是 FIFO 的，无法区分紧急程度。优先级队列让高优先级任务先执行。

```cpp
#include <queue>
#include <functional>
#include <mutex>

// 带优先级的任务包装
struct PriorityTask {
    int priority;                        // 数字越大优先级越高
    std::function<void()> func;
    std::uint64_t seq;                  // 同优先级按提交顺序（FIFO）
    bool operator>(const PriorityTask& other) const {
        if (priority != other.priority) return priority < other.priority;  // 大顶堆
        return seq > other.seq;                                              // 同优先级先来先执行
    }
};

class PriorityThreadPool {
public:
    explicit PriorityThreadPool(std::size_t n) : stop_(false), seq_counter_(0) {
        for (std::size_t i = 0; i < n; ++i)
            workers_.emplace_back([this] {
                for (;;) {
                    std::unique_lock<std::mutex> lk(m_);
                    cv_.wait(lk, [this] { return stop_ || !pq_.empty(); });
                    if (stop_ && pq_.empty()) return;
                    auto task = std::move(const_cast<PriorityTask&>(pq_.top()));
                    pq_.pop();
                    lk.unlock();
                    task.func();
                }
            });
    }

    void submit(std::function<void()> f, int priority = 0) {
        {
            std::lock_guard<std::mutex> lk(m_);
            pq_.push(PriorityTask{priority, std::move(f), seq_counter_++});
        }
        cv_.notify_one();
    }

    ~PriorityThreadPool() {
        { std::lock_guard<std::mutex> lk(m_); stop_ = true; }
        cv_.notify_all();
        for (auto& t : workers_) t.join();
    }

private:
    std::vector<std::thread> workers_;
    std::priority_queue<PriorityTask, std::vector<PriorityTask>, std::greater<PriorityTask>> pq_;
    std::mutex m_;
    std::condition_variable cv_;
    bool stop_;
    std::uint64_t seq_counter_;
};
```

| 特性 | FIFO 队列 | 优先级队列 |
| --- | --- | --- |
| 执行顺序 | 提交顺序 | 优先级 + 提交顺序 |
| 数据结构 | `std::queue`（环形缓冲） | `std::priority_queue`（二叉堆） |
| push/pop 复杂度 | O(1) | O(log n) |
| 饥饿风险 | 无 | 低优先级任务可能永远不执行（需老化机制） |
| 适用场景 | 通用任务调度 | 紧急任务优先、QoS 分级 |

> 优先级队列的经典坑：**低优先级饥饿**。如果持续有高优先级任务提交，低优先级任务永远排不到。解决方案：老化（aging）——任务等待时间越长，动态提升其优先级；或设置最低执行率（每执行 N 个高优先级任务，必须执行 1 个低优先级）。

### 2.3 动态扩缩容策略

固定线程数在负载波动时效率不高：负载低时空闲线程浪费资源，负载高时线程不够用。动态扩缩容根据队列长度和任务等待时间调整线程数。

```cpp
#include <atomic>
#include <chrono>
#include <condition_variable>
#include <functional>
#include <mutex>
#include <queue>
#include <thread>
#include <vector>

class DynamicThreadPool {
public:
    DynamicThreadPool(std::size_t min_threads, std::size_t max_threads)
        : min_threads_(min_threads), max_threads_(max_threads),
          active_threads_(0), stop_(false) {
        for (std::size_t i = 0; i < min_threads_; ++i) spawn_worker();
        // 管理线程：定期检查负载，决定扩缩容
        manager_ = std::thread([this] { manage_loop(); });
    }

    ~DynamicThreadPool() {
        { std::lock_guard<std::mutex> lk(m_); stop_ = true; }
        cv_.notify_all();
        manager_.join();
        for (auto& t : workers_) if (t.joinable()) t.join();
    }

    void submit(std::function<void()> f) {
        { std::lock_guard<std::mutex> lk(m_); tasks_.push(std::move(f)); }
        cv_.notify_one();
    }

private:
    void spawn_worker() {
        workers_.emplace_back([this] {
            while (true) {
                std::function<void()> task;
                {
                    std::unique_lock<std::mutex> lk(m_);
                    cv_.wait(lk, [this] { return stop_ || !tasks_.empty(); });
                    if (stop_ && tasks_.empty()) return;
                    // 缩容：如果当前线程数超过需要，且自己是"多余"的，则退出
                    if (should_exit()) return;
                    task = std::move(tasks_.front());
                    tasks_.pop();
                    ++active_threads_;
                }
                task();
                --active_threads_;
            }
        });
    }

    bool should_exit() {
        // 简化：如果队列空且线程数 > min_threads_，允许退出
        // 实际实现需要更精细的空闲超时机制
        return tasks_.empty() && workers_.size() > min_threads_;
    }

    void manage_loop() {
        while (!stop_) {
            std::this_thread::sleep_for(std::chrono::milliseconds(500));
            std::lock_guard<std::mutex> lk(m_);
            if (stop_) return;

            std::size_t pending = tasks_.size();
            std::size_t current = workers_.size();

            // 扩容：队列积压 > 线程数的 2 倍，且未达上限
            if (pending > current * 2 && current < max_threads_) {
                spawn_worker();
            }
            // 缩容：队列空且活跃线程少，且超过最小线程数
            // （实际缩容由 worker 在 should_exit 时自然退出）
        }
    }

    std::size_t min_threads_;
    std::size_t max_threads_;
    std::atomic<std::size_t> active_threads_;
    std::vector<std::thread> workers_;
    std::thread manager_;
    std::queue<std::function<void()>> tasks_;
    std::mutex m_;
    std::condition_variable cv_;
    bool stop_;
};
```

| 策略 | 触发条件 | 操作 | 风险 |
| --- | --- | --- | --- |
| 扩容 | 队列积压 > 阈值 | 创建新 worker | 创建开销、瞬时过载 |
| 缩容 | 空闲超时（如 60s 无任务） | worker 自然退出 | 频繁扩缩容（抖动） |
| 预热 | 启动时 | 先创建 min_threads 个 | 低负载时浪费 |
| 防抖动 | 扩容后冷却期（如 10s 内不缩容） | 延迟缩容决策 | 响应变慢 |

### 2.4 有界队列与拒绝策略

无界队列在生产者远快于消费者时会无限增长，最终 OOM。有界队列限制最大长度，满时执行拒绝策略。

```cpp
#include <condition_variable>
#include <functional>
#include <mutex>
#include <queue>
#include <thread>
#include <vector>
#include <stdexcept>

enum class RejectPolicy {
    Abort,          // 抛异常
    Discard,        // 静默丢弃新任务
    DiscardOldest,  // 丢弃队列中最老的任务，腾出空间
    CallerRuns,     // 由提交线程自己执行（反压）
    Block           // 阻塞等待队列有空位
};

class BoundedThreadPool {
public:
    BoundedThreadPool(std::size_t n, std::size_t max_queue,
                      RejectPolicy policy = RejectPolicy::Abort)
        : max_queue_(max_queue), policy_(policy), stop_(false) {
        for (std::size_t i = 0; i < n; ++i)
            workers_.emplace_back([this] {
                for (;;) {
                    std::unique_lock<std::mutex> lk(m_);
                    cv_.wait(lk, [this] { return stop_ || !tasks_.empty(); });
                    if (stop_ && tasks_.empty()) return;
                    auto task = std::move(tasks_.front());
                    tasks_.pop();
                    lk.unlock();
                    not_full_.notify_one();  // 队列有空位了，通知阻塞的提交者
                    task();
                }
            });
    }

    void submit(std::function<void()> f) {
        std::unique_lock<std::mutex> lk(m_);
        if (tasks_.size() >= max_queue_) {
            switch (policy_) {
                case RejectPolicy::Abort:
                    throw std::runtime_error("线程池队列已满");
                case RejectPolicy::Discard:
                    return;  // 静默丢弃
                case RejectPolicy::DiscardOldest:
                    tasks_.pop();  // 丢最老的
                    break;          // 继续 push 新的
                case RejectPolicy::CallerRuns:
                    lk.unlock();
                    f();  // 提交者自己执行（反压：降低提交速度）
                    return;
                case RejectPolicy::Block:
                    not_full_.wait(lk, [this] { return tasks_.size() < max_queue_; });
                    break;
            }
        }
        tasks_.push(std::move(f));
        lk.unlock();
        cv_.notify_one();
    }

    ~BoundedThreadPool() {
        { std::lock_guard<std::mutex> lk(m_); stop_ = true; }
        cv_.notify_all();
        not_full_.notify_all();
        for (auto& t : workers_) t.join();
    }

private:
    std::size_t max_queue_;
    RejectPolicy policy_;
    std::vector<std::thread> workers_;
    std::queue<std::function<void()>> tasks_;
    std::mutex m_;
    std::condition_variable cv_;
    std::condition_variable not_full_;
    bool stop_;
};
```

| 拒绝策略 | 行为 | 适用场景 |
| --- | --- | --- |
| Abort | 抛异常，让调用者处理 | 关键任务，不能丢也不能阻塞 |
| Discard | 静默丢弃 | 非关键日志、监控数据 |
| DiscardOldest | 丢最老的任务 | 最新数据最重要（如实时行情） |
| CallerRuns | 提交者自己执行 | 反压（自然降低提交速率），最安全 |
| Block | 阻塞等待 | 不能丢任务，且提交者可以等待 |

## 3. 无锁 SPSC 环形队列

单生产者单消费者时，两个索引分别只被一端写入，可用 acquire/release 精确同步：

```cpp
#include <atomic>
#include <cstddef>

template <typename T, std::size_t N>       // N 必须是 2 的幂：用 & (N-1) 代替 %
class SpscQueue {
    static_assert((N & (N - 1)) == 0, "N 必须是 2 的幂");
public:
    bool push(const T& v) {                       // 仅生产者线程调用
        auto t = tail_.load(std::memory_order_relaxed);
        auto h = head_.load(std::memory_order_acquire);   // 看消费者释放了多少空间
        if (t - h == N) return false;                     // 满
        buf_[t & (N - 1)] = v;
        tail_.store(t + 1, std::memory_order_release);    // 发布：写数据在更新索引之前
        return true;
    }
    bool pop(T& v) {                              // 仅消费者线程调用
        auto h = head_.load(std::memory_order_relaxed);
        auto t = tail_.load(std::memory_order_acquire);   // 同步生产者已发布的数据
        if (h == t) return false;                         // 空
        v = buf_[h & (N - 1)];
        head_.store(h + 1, std::memory_order_release);    // 释放空间
        return true;
    }
private:
    T buf_[N];
    alignas(64) std::atomic<std::size_t> head_{0};  // 伪共享处理：两个索引分缓存行
    alignas(64) std::atomic<std::size_t> tail_{0};
};
// MPMC（多生产者多消费者）复杂得多，需要 CAS 索引分配，建议直接用成熟库。
```

## 4. 无锁进阶

### 4.1 ABA 问题与 tagged pointer

**ABA 问题**：CAS 操作只比较"值是否相等"，但值从 A 变成 B 又变回 A 时，CAS 会误认为"没变过"，导致逻辑错误。

```text
经典 ABA 场景（无锁栈 push/pop）：
  栈: top → A → B → C
  线程 1: pop() 准备 CAS(top, A, B)  —— 读到 top=A，next=B
  线程 2: pop() → 返回 A
          pop() → 返回 B
          push(A) → 栈变为 top → A → C  （A 被重新插入！）
  线程 1: CAS(top, A, B) 成功！
          但 B 已经被 pop 并可能被释放/重用 → top→B 是悬垂指针！
```

**解决方案：tagged pointer（标记指针）**

把指针和一个版本号（tag/counter）打包成一个原子变量，每次修改时版本号递增。ABA 时即使指针相同，版本号也不同，CAS 失败。

```cpp
#include <atomic>
#include <cstdint>

// 利用 64 位指针高 16 位未使用（x86_64 只用低 48 位），存版本号
struct TaggedPtr {
    std::uint64_t raw;
    static constexpr std::uint64_t PTR_MASK = 0x0000FFFFFFFFFFFF;
    static constexpr std::uint64_t TAG_SHIFT = 48;

    void* ptr() const { return reinterpret_cast<void*>(raw & PTR_MASK); }
    std::uint16_t tag() const { return static_cast<std::uint16_t>(raw >> TAG_SHIFT); }

    static TaggedPtr make(void* p, std::uint16_t t) {
        return { (reinterpret_cast<std::uint64_t>(p) & PTR_MASK)
               | (static_cast<std::uint64_t>(t) << TAG_SHIFT) };
    }
};

// 无锁栈的 pop（带 tag 防 ABA）
struct Node { int data; Node* next; };

class LockFreeStack {
    std::atomic<TaggedPtr> top_;
public:
    LockFreeStack() : top_(TaggedPtr::make(nullptr, 0)) {}

    void push(int v) {
        Node* node = new Node{v, nullptr};
        TaggedPtr old_top = top_.load(std::memory_order_relaxed);
        do {
            node->next = static_cast<Node*>(old_top.ptr());
            TaggedPtr new_top = TaggedPtr::make(node, old_top.tag() + 1);  // tag 递增
        } while (!top_.compare_exchange_weak(old_top, new_top,
                    std::memory_order_release, std::memory_order_relaxed));
    }

    bool pop(int& out) {
        TaggedPtr old_top = top_.load(std::memory_order_acquire);
        while (old_top.ptr()) {
            Node* node = static_cast<Node*>(old_top.ptr());
            TaggedPtr new_top = TaggedPtr::make(node->next, old_top.tag() + 1);
            if (top_.compare_exchange_weak(old_top, new_top,
                    std::memory_order_acq_rel, std::memory_order_acquire)) {
                out = node->data;
                // 注意：此处不能直接 delete node！可能有其他线程正在访问
                // 需要 hazard pointer 或延迟回收（见 4.3）
                return true;
            }
            // CAS 失败：old_top 被刷新为最新值（含最新 tag），重试
        }
        return false;  // 栈空
    }
};
```

| 方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| tagged pointer | 指针 + 版本号打包 | 简单，性能好 | 依赖指针高位未用（64 位限定），tag 可能溢出回绕 |
| 双重 CAS (DCAS) | 同时 CAS 指针和版本号两个变量 | 不依赖指针布局 | 大多数硬件不支持 DCAS，需用 CAS2 模拟 |
|  hazard pointer | 记录正在访问的指针，回收前检查 | 不依赖指针布局，安全 | 实现复杂，有内存延迟回收开销 |
| RCU | 读端无锁，写端复制修改 + 延迟释放 | 读端极快，适合读多写少 | 写端复杂，需要 grace period 机制 |

### 4.2 MPMC 无锁队列设计思路

MPMC（Multi-Producer Multi-Consumer）无锁队列比 SPSC 复杂得多，因为多个生产者同时写 tail、多个消费者同时读 head，都需要 CAS 竞争。

**经典设计：基于数组的 MPMC 队列（Dmitry Vyukov 风格）**

```text
核心思想：每个槽位有一个 sequence 号，生产者/消费者通过 sequence 协调

数组 buf[N]，每个元素带 seq[i]（原子计数器）：
  初始：seq[i] = i

生产者 enqueue(v):
  pos = tail.load(relaxed)
  cell = pos % N
  seq = seq[cell].load(acquire)
  diff = seq - pos
  if diff == 0:        // 该槽位可写
      if CAS(tail, pos, pos+1):  // 抢占这个位置
          buf[cell] = v
          seq[cell].store(pos+1, release)  // 标记已写入
          return true
  elif diff < 0: return false  // 队列满
  else: retry  // 其他生产者正在写，重试

消费者 dequeue(&v):
  pos = head.load(relaxed)
  cell = pos % N
  seq = seq[cell].load(acquire)
  diff = seq - (pos+1)
  if diff == 0:        // 该槽位有数据
      if CAS(head, pos, pos+1):
          *v = buf[cell]
          seq[cell].store(pos+N, release)  // 标记已读取，可被下一轮生产者写
          return true
  elif diff < 0: return false  // 队列空
  else: retry
```

| 维度 | SPSC 队列 | MPMC 队列 |
| --- | --- | --- |
| 生产者数 | 1 | 多 |
| 消费者数 | 1 | 多 |
| 索引更新 | 直接 store（无竞争） | CAS 循环（有竞争） |
| 内存序 | acquire/release 即可 | acquire/release + CAS acq_rel |
| 性能 | 极高（接近无开销） | 较高（CAS 竞争） |
| 实现难度 | 简单 | 复杂 |
| 典型用途 | 单线程生产 + 单线程消费的流水线 | 线程池任务队列、通用消息队列 |

> MPMC 无锁队列的完整实现（含内存回收、缓存行对齐、批量操作）参见 09 模块《../13-并发异步与组件/07-原子操作与无锁组件.md》。生产环境建议直接使用成熟库：`boost::lockfree::queue`、`moodycamel::ConcurrentQueue`、Intel TBB `concurrent_queue`。

### 4.3 Hazard Pointer 与 RCU

无锁数据结构的核心难题之一是**内存安全回收**：一个线程刚从链表中摘下节点准备 delete，另一个线程可能正在读取该节点——直接 delete 会导致 use-after-free。

**Hazard Pointer（危险指针）**

```text
原理：
  1. 每个线程有一个 hazard pointer 列表，记录"我正在访问的指针"
  2. 读节点前：把节点指针存入自己的 hazard list
  3. 删节点前：把节点加入"待回收列表"，不立即 delete
  4. 定期扫描：遍历所有线程的 hazard list，如果待回收节点不在任何 hazard list 中，才安全 delete

回收流程：
  线程 A: pop 节点 X → X 加入 retire_list
  线程 B: 读 X 前 → hp[B] = X（标记危险）
  扫描: X 在 hp[B] 中 → 不回收，等下一轮
  线程 B: 读完 X → hp[B] = nullptr
  扫描: X 不在任何 hazard list 中 → delete X ✓
```

```cpp
#include <atomic>
#include <vector>
#include <unordered_set>

// 简化版 hazard pointer 框架
class HazardPointer {
public:
    static HazardPointer& instance() {
        static HazardPointer hp;
        return hp;
    }

    // 线程声明正在访问 ptr
    void protect(void* ptr) {
        auto& my_hazards = hazards_[std::this_thread::get_id()];
        my_hazards.insert(ptr);
    }

    // 线程取消保护
    void unprotect(void* ptr) {
        auto& my_hazards = hazards_[std::this_thread::get_id()];
        my_hazards.erase(ptr);
    }

    // 延迟回收：加入待删列表
    void retire(void* ptr) {
        retire_list_.push_back(ptr);
        try_reclaim();
    }

private:
    void try_reclaim() {
        // 收集所有 hazard 指针
        std::unordered_set<void*> all_hazards;
        for (auto& [tid, hz] : hazards_)
            for (void* p : hz) all_hazards.insert(p);

        // 回收不在 hazard 列表中的节点
        std::vector<void*> remaining;
        for (void* p : retire_list_) {
            if (all_hazards.count(p))
                remaining.push_back(p);  // 还在被访问，留到下一轮
            else
                delete p;  // 安全回收
        }
        retire_list_.swap(remaining);
    }

    std::unordered_map<std::thread::id, std::unordered_set<void*>> hazards_;
    std::vector<void*> retire_list_;
};
```

**RCU（Read-Copy-Update）**

```text
核心思想（读多写极少的场景）：
  读端：完全无锁，直接读指针（RCU read-side critical section）
  写端：
    1. 复制要修改的数据结构（Copy）
    2. 修改副本
    3. 原子地替换旧指针为新指针（rcu_assign_pointer）
    4. 等待一个 grace period（所有已开始的读端都结束）
    5. 释放旧数据结构

为什么读端可以无锁？
  写端不修改旧数据，只替换指针。正在读旧数据的线程继续读旧的（一致的快照），
  新的读线程看到新指针。旧数据在 grace period 后才释放，保证没有线程正在读它。

grace period：
  所有线程都经历过一次"静止点"（quiescent state，即不在 RCU 读端临界区中）。
  之后可以确定没有线程还持有旧数据的引用。
```

| 特性 | Hazard Pointer | RCU |
| --- | --- | --- |
| 读端开销 | 存 hazard pointer（一次写） | 几乎为零（rcu_read_lock 通常是编译器屏障） |
| 写端开销 | 加入 retire list + 定期扫描 | 复制数据 + 等待 grace period |
| 回收延迟 | 不确定（取决于扫描频率） | 一个 grace period（通常几毫秒） |
| 适用场景 | 通用无锁数据结构 | 读极多写极少（路由表、配置热更新） |
| 标准支持 | 无（需自行实现或用库） | Linux 内核有完整实现；用户态有 liburcu |

## 5. 并发模式

### 5.1 Active Object 模式

Active Object 将"方法调用"和"方法执行"解耦：调用者提交请求到队列，专用线程串行执行请求，从而**无需显式加锁**就能保证线程安全。

```cpp
#include <functional>
#include <future>
#include <mutex>
#include <queue>
#include <thread>
#include <condition_variable>

class ActiveObject {
public:
    ActiveObject() : stop_(false) {
        worker_ = std::thread([this] { run(); });
    }

    ~ActiveObject() {
        { std::lock_guard<std::mutex> lk(m_); stop_ = true; }
        cv_.notify_one();
        worker_.join();
    }

    // 提交任务，返回 future（调用者可以异步取结果）
    template <typename F>
    auto submit(F&& f) -> std::future<decltype(f())> {
        using Ret = decltype(f());
        auto task = std::make_shared<std::packaged_task<Ret()>>(std::forward<F>(f));
        auto fut = task->get_future();
        {
            std::lock_guard<std::mutex> lk(m_);
            tasks_.push([task]() { (*task)(); });
        }
        cv_.notify_one();
        return fut;
    }

private:
    void run() {
        while (true) {
            std::function<void()> task;
            {
                std::unique_lock<std::mutex> lk(m_);
                cv_.wait(lk, [this] { return stop_ || !tasks_.empty(); });
                if (stop_ && tasks_.empty()) return;
                task = std::move(tasks_.front());
                tasks_.pop();
            }
            task();  // 单线程串行执行，内部数据无需加锁
        }
    }

    std::thread worker_;
    std::queue<std::function<void()>> tasks_;
    std::mutex m_;
    std::condition_variable cv_;
    bool stop_;
};

// 使用示例：一个线程安全的计数器，内部无需 mutex
class SafeCounter {
    ActiveObject ao_;
    int value_ = 0;  // 只在 ao_ 的 worker 线程中被访问，无需锁
public:
    std::future<int> increment() {
        return ao_.submit([this] { return ++value_; });
    }
    std::future<int> get() {
        return ao_.submit([this] { return value_; });
    }
};
```

| 维度 | 互斥锁保护 | Active Object |
| --- | --- | --- |
| 线程安全机制 | 锁（互斥） | 单线程串行执行（避免共享） |
| 调用方式 | 同步（直接调用，可能阻塞等锁） | 异步（提交到队列，返回 future） |
| 死锁风险 | 有（多把锁、回调中加锁） | 无（单线程无锁） |
| 性能 | 高（多线程并行） | 低（单线程串行，适合低并发） |
| 适用场景 | 高并发、短临界区 | 低并发、复杂状态机、避免锁复杂度 |

### 5.2 Monitor Object 模式

Monitor Object 是"共享资源 + 一把锁 + 条件变量"的封装：所有公共方法自动加锁，内部用条件变量等待/通知。这是最经典的线程安全类设计模式。

```cpp
#include <condition_variable>
#include <mutex>
#include <queue>

template <typename T>
class MonitorQueue {
public:
    void push(const T& v) {
        std::lock_guard<std::mutex> lk(m_);  // 自动加锁
        q_.push(v);
        cv_.notify_one();                       // 自动通知
    }                                            // 自动解锁（析构）

    T pop() {
        std::unique_lock<std::mutex> lk(m_);
        cv_.wait(lk, [this] { return !q_.empty(); });  // 谓词等待
        T v = q_.front(); q_.pop();
        return v;
    }

    bool try_pop(T& v) {
        std::lock_guard<std::mutex> lk(m_);
        if (q_.empty()) return false;
        v = q_.front(); q_.pop();
        return true;
    }

    std::size_t size() const {
        std::lock_guard<std::mutex> lk(m_);
        return q_.size();
    }

private:
    mutable std::mutex m_;
    std::condition_variable cv_;
    std::queue<T> q_;
};
```

Monitor Object 的关键规则：
- **所有公共方法都在持锁状态下执行**（封装锁，用户无需手动加锁）
- **条件变量等待必须用谓词**（防虚假唤醒）
- **不要在持锁时调用外部回调**（可能导致死锁，回调中可能反过来调用 monitor 的方法）
- **返回引用/指针时要小心**（引用的对象在锁释放后可能被其他线程修改）

### 5.3 双重检查锁（DCLP）单例的正确写法

DCLP（Double-Checked Locking Pattern）是单例模式的经典优化：先无锁检查，再加锁检查，避免每次获取单例都加锁。但在 C++11 之前，DCLP 因内存序问题是不安全的。

```cpp
// ========== 错误写法（C++03 及以前，UB）==========
class SingletonBad {
    static SingletonBad* instance_;
    static std::mutex mtx_;
public:
    static SingletonBad* get() {
        if (!instance_) {                    // ① 无锁检查（可能看到半构造对象）
            std::lock_guard<std::mutex> lk(mtx_);
            if (!instance_)                  // ② 加锁后再检查
                instance_ = new SingletonBad();  // ③ new 的写序可能重排！
        }
        return instance_;
    }
};
// 问题：new 分三步——分配内存、构造对象、赋值给 instance_。
// 编译器/CPU 可能重排为：分配内存 → 赋值 instance_ → 构造对象。
// 线程 A 执行到"赋值 instance_"但还没构造完，线程 B 看到 instance_ 非空，
// 直接返回半构造对象 → UB。

// ========== 正确写法 1：C++11 magic statics（最推荐）==========
class SingletonMagic {
public:
    static SingletonMagic& get() {
        static SingletonMagic instance;  // C++11 起：局部 static 初始化线程安全
        return instance;
    }
    SingletonMagic(const SingletonMagic&) = delete;
    SingletonMagic& operator=(const SingletonMagic&) = delete;
private:
    SingletonMagic() = default;
};
// 原理：C++11 标准规定局部 static 的初始化是线程安全的。
// 编译器内部生成类似 DCLP 的代码，但用正确的内存序（atomic + acquire/release）。
// 如果初始化抛异常，下次调用会重新尝试。

// ========== 正确写法 2：atomic + acquire/release（显式 DCLP）==========
#include <atomic>

class SingletonAtomic {
    static std::atomic<SingletonAtomic*> instance_;
    static std::mutex mtx_;
public:
    static SingletonAtomic* get() {
        SingletonAtomic* p = instance_.load(std::memory_order_acquire);  // ① acquire 读
        if (!p) {
            std::lock_guard<std::mutex> lk(mtx_);
            p = instance_.load(std::memory_order_relaxed);  // ② 已持锁，relaxed 足够
            if (!p) {
                p = new SingletonAtomic();
                instance_.store(p, std::memory_order_release);  // ③ release 写：构造完成后才发布
            }
        }
        return p;
    }
};
// 原理：
//   - ③ release store 保证：new 的构造（在 release 之前）对 acquire 读可见
//   - ① acquire load 保证：看到 release 写的指针时，构造已完成
//   - ② 持锁后用 relaxed 读：因为锁已经建立了 happens-before
```

| 写法 | 线程安全 | 性能 | 推荐度 |
| --- | --- | --- | --- |
| C++03 裸 DCLP（无 atomic） | ❌ UB | 高 | 禁止 |
| 每次加锁（无 DCLP） | ✅ | 低（每次都加锁） | 不推荐 |
| C++11 magic static | ✅ | 高（首次初始化后无锁） | **最推荐** |
| atomic + acquire/release DCLP | ✅ | 高 | 需要控制生命周期时用 |

### 5.4 信号丢失（Spurious Wakeup）与唤醒丢失（Lost Wakeup）

这两个是条件变量最经典的问题，名字相似但完全不同。

**Spurious Wakeup（虚假唤醒）**：线程被唤醒，但谓词条件并未满足。

```text
原因：
  - OS 底层 futex 允许无通知唤醒（性能优化，避免某些竞态）
  - C++ 标准明确允许 condition_variable 出现虚假唤醒
  - 多消费者场景下，notify_one 唤醒一个，但另一个消费者抢先拿走了任务

后果：
  - 如果用裸 wait(lk) 而不检查条件，被虚假唤醒后以为条件满足，实际队列为空 → 取到空任务/崩溃

防范：
  - 永远用 wait(lk, pred) 谓词版本，或手写 while 循环
  - 谓词在 wait 返回后重新检查，不满足则继续等待
```

```cpp
// 错误：裸 wait，不检查条件
void bad_consumer() {
    std::unique_lock<std::mutex> lk(m);
    cv.wait(lk);                // 可能被虚假唤醒！
    int v = q.front(); q.pop();  // 队列可能为空 → 未定义行为
}

// 正确：谓词 wait
void good_consumer() {
    std::unique_lock<std::mutex> lk(m);
    cv.wait(lk, [] { return !q.empty(); });  // 谓词自动重试，虚假唤醒后继续等
    int v = q.front(); q.pop();
}
```

**Lost Wakeup（唤醒丢失）**：notify 发生时，对方还没进入 wait，通知被"漏掉"了。

```text
场景：
  线程 A（消费者）：检查队列空 → 准备调用 wait（但还没调用）
  线程 B（生产者）：push 任务 → notify_one（此时 A 还没在等，通知丢失）
  线程 A（消费者）：调用 wait → 永久阻塞（因为通知已经发过了，不会再发）

根因：
  检查条件和进入 wait 之间有时间窗口，notify 可能落在这个窗口里

防范：
  - 检查条件和 wait 必须在**同一把锁的保护下**进行
  - notify 前必须**持锁修改共享状态**（谓词依赖的变量）
  - 这样消费者持锁检查条件时，生产者无法同时修改条件并 notify
  - 即使 notify 先于 wait 发生，谓词已经变了，wait 会立即返回（不阻塞）
```

```cpp
// 错误：检查和 wait 不在同一把锁里
void bad_pattern() {
    if (q.empty()) {              // 无锁检查
        // 时间窗口：生产者可能在这里 push + notify
        std::unique_lock<std::mutex> lk(m);
        cv.wait(lk);               // 通知已丢失，永久阻塞
    }
}

// 正确：持锁检查 + 谓词 wait
void good_pattern() {
    std::unique_lock<std::mutex> lk(m);  // 先拿锁
    cv.wait(lk, [] { return !q.empty(); });  // 持锁检查谓词，生产者无法在检查和 wait 之间插入 notify
    // 即使 notify 先发生，谓词 !q.empty() 已为 true，wait 立即返回
}
```

| 问题 | 现象 | 根因 | 防范 |
| --- | --- | --- | --- |
| Spurious Wakeup | 被唤醒但条件不满足 | OS 允许无通知唤醒 | 谓词 wait / while 循环 |
| Lost Wakeup | notify 后对方仍永久睡死 | notify 落在检查与 wait 的窗口 | 持锁检查 + 持锁改状态 + 谓词 |

### 6.1 gdb 多线程命令

gdb 多线程命令（详见《../07-调试与测试/01-GDB程序调试.md》）：

| 命令 | 作用 |
| --- | --- |
| `info threads` | 列出所有线程及当前停在哪 |
| `thread 3` | 切到 3 号线程 |
| `thread apply all bt` | 所有线程都打印调用栈（死锁排查第一步） |
| `break work.cpp:42 thread 3` | 断点只对 3 号线程生效 |
| `set scheduler-locking on` | 单步时不让其他线程乱跑 |
| `p (int)pthread_mutex_trylock(&m)` | 死锁现场试探某把锁是否被持有（技巧） |

### 6.2 ThreadSanitizer（TSan）深度使用

ThreadSanitizer 是基于编译期插桩的数据竞争检测器，是查找并发 bug 的首选工具。

**编译与运行**：

```bash
# 编译：必须加 -fsanitize=thread，建议 -g -O1（-O0 太慢，-O2 可能优化掉竞争）
g++ -std=c++17 -fsanitize=thread -g -O1 -pthread main.cpp -o app

# 运行：直接执行，TSan 会在检测到竞争时打印报告
./app

# 常用环境变量
TSAN_OPTIONS="halt_on_error=1:report_batches=0:history_size=7" ./app
#   halt_on_error=1   首次检测到错误即退出（默认继续运行）
#   report_batches=0  不合并相似报告（每个竞争都完整打印）
#   history_size=7    记录更多栈帧历史（默认 4，最大 7）
```

**典型报告解读**：

```text
==================
WARNING: ThreadSanitizer: data race (pid=12345)
  Write of size 4 at 0x7f8a1c000010 by thread T2:
    #0 increment() main.cpp:10:5   ← 线程 2 在第 10 行写
    #1 worker() main.cpp:20:3

  Previous write of size 4 at 0x7f8a1c000010 by thread T1:
    #0 increment() main.cpp:10:5   ← 线程 1 也在第 10 行写
    #1 worker() main.cpp:20:3

  Location is global 'counter' at 0x7f8a1c000010 (main.exe+0x000000409010)
  ← 竞争的变量是全局 counter

  Thread T2 (tid=12347, running) created by main thread at:
    #0 pthread_create ...
    #1 std::thread::_M_start_thread ...
    #2 main main.cpp:30:10

  Thread T1 (tid=12346, finished) created by main thread at:
    ...
==================
```

报告三要素：
1. **竞争位置**：哪个变量、哪个内存地址（`Location is global 'counter'`）
2. **两个访问点**：分别是哪个线程、哪行代码、读还是写（`Write` / `Read`）
3. **线程创建栈**：这两个线程是在哪里创建的（帮助定位）

**TSan 能检测的问题**：

| 问题类型 | 报告关键词 | 说明 |
| --- | --- | --- |
| 数据竞争 | `data race` | 最常见，两个线程无同步访问同一内存 |
| 锁顺序倒置 | `lock-order-inversion` | 可能死锁：线程 A 锁 X 后锁 Y，线程 B 锁 Y 后锁 X |
| 误用 mutex | `mutex...wrong thread` | 在非加锁线程 unlock，或重复 unlock |
| 信号不安全 | `signal-unsafe-call` | 信号处理函数中调用了非异步信号安全的函数 |
| 内存泄漏 | 可选 | TSan 也能检测泄漏（但精度不如 ASan） |

**TSan 的局限**：

| 局限 | 说明 |
| --- | --- |
| 性能开销 | 运行慢 5~15 倍，内存多 5~10 倍 |
| 只检测运行到的路径 | 没执行到的代码路径不会报竞争（需要好的测试覆盖） |
| 不检测原子操作内部 | `std::atomic` 的操作被认为是安全的（即使内存序选错也不报） |
| 不能与其他 sanitizer 同时用 | TSan 和 ASan/MSan 互斥（一次只能用一个） |
| 不支持 detach 线程的完整跟踪 | detach 线程的栈可能不完整 |

> TSan 与 ASan 的区别：TSan 查**数据竞争**（多线程并发问题），ASan 查**内存错误**（use-after-free、buffer overflow 等）。两者不能同时启用，需要分开编译运行。

### 6.3 Valgrind helgrind / DRD

Valgrind 提供两个线程错误检测器，无需重新编译（但需要带调试信息）。

**helgrind**：

```bash
# 编译（不需要特殊 flag，但需要 -g）
g++ -std=c++17 -g -pthread main.cpp -o app

# 运行 helgrind
valgrind --tool=helgrind ./app

# 常用选项
valgrind --tool=helgrind --history-level=full --track-lockorders=yes ./app
#   --history-level=full     记录完整的访问历史（更详细但更慢）
#   --track-lockorders=yes   检测锁顺序倒置（死锁风险）
```

**DRD（Data Race Detector）**：

```bash
valgrind --tool=drd ./app

# 常用选项
valgrind --tool=drd --check-stack-var=yes --exclusive-threshold=100 ./app
#   --check-stack-var=yes     也检查栈上变量的竞争（默认只查堆和全局）
#   --exclusive-threshold=100  持锁超过 100ms 时警告（可能的锁竞争热点）
```

**helgrind vs DRD 对比**：

| 维度 | helgrind | DRD |
| --- | --- | --- |
| 算法 | 基于 happens-before 向量时钟 | 基于 happens-before + 段（segment） |
| 数据竞争检测 | ✅ | ✅ |
| 锁顺序倒置检测 | ✅（`--track-lockorders`） | ❌（不检测） |
| 内存开销 | 较高（每个字节跟踪） | 较低 |
| 速度 | 慢 30~50 倍 | 慢 20~40 倍（比 helgrind 快） |
| 递归锁支持 | 有限 | 较好 |
| 典型用途 | 查数据竞争 + 死锁风险 | 快速筛查数据竞争 |

**helgrind 典型报告**：

```text
==12345== Possible data race during read of size 4 at 0x601040 by thread #2
==12345==    at 0x40095A: worker() (main.cpp:15)
==12345==  This conflicts with a previous write of size 4 by thread #1
==12345==    at 0x40095A: worker() (main.cpp:15)
==12345==  Address 0x601040 is 0 bytes inside data symbol "counter"
```

| 工具 | 编译要求 | 速度 | 竞争检测 | 死锁检测 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| TSan | `-fsanitize=thread` | 慢 5~15x | ✅ 精确 | ✅ 锁序倒置 | 首选，CI 集成 |
| helgrind | 仅 `-g` | 慢 30~50x | ✅ | ✅ 锁序倒置 | 不能重编译时 |
| DRD | 仅 `-g` | 慢 20~40x | ✅ | ❌ | 快速筛查 |

> Valgrind 工具链的详细使用（memcheck/helgrind/callgrind 等）详见《../07-调试与测试/02-Valgrind内存检测.md》。编译选项与 sanitizer 集成详见《../06-构建与版本控制/01-构建工具GCC与CMake.md》。

## 7. 快速参考卡片

按"我要实现 XX → 选什么工具"：

| 需求 | 推荐 |
| --- | --- |
| 后台跑一段活，结束拿结果 | `std::async(std::launch::async, ...)`（注意 future 析构阻塞） |
| 长期后台线程、RAII 自动 join | `std::jthread`（C++20）；C++11 手动 join |
| 多任务队列消费 | 线程池（第 1 节） |
| 一次性全局初始化 | 函数局部 `static`（C++11 线程安全）> `call_once` |
| 生产者-消费者同步 | `mutex` + `condition_variable` + 谓词 wait |
| 读多写少的缓存 | `shared_mutex` + `shared_lock`（读）/`unique_lock`（写） |
| 一次锁多把锁 | `std::scoped_lock`（C++17） |
| 简单计数器 | `std::atomic<int>` + relaxed |
| 标志位发布数据 | `atomic<bool>` + release/acquire 配对 |
| 精确控制线程数 | `std::thread::hardware_concurrency()` 兜底默认值 |
| 线程独立状态 | `thread_local` |
| 查数据竞争 | TSan `-fsanitize=thread` |
| 单生产者单消费者高频队列 | 无锁 SPSC 环形队列（acquire/release） |
| 限制并发资源数 | `std::counting_semaphore`（C++20） |
| 等待 N 个任务完成 | `std::latch`（C++20） |
| 多轮迭代同步 | `std::barrier`（C++20） |

内存序速查：

| 场景 | 内存序 |
| --- | --- |
| 不携带其他数据的纯计数 | `relaxed` |
| 发布/读取共享数据（标志位、锁） | `release` 写 + `acquire` 读 |
| CAS 循环里改共享数据 | `acq_rel` |
| 多变量间需要全序（默认） | `seq_cst` |

## 8. 常见问题与坑

| 问题 | 原因与解决方案 |
| --- | --- |
| `std::thread` 对象析构时程序直接 terminate | 未调用 join/detach 就析构。解决：join；或用 C++20 `jthread` 自动 join |
| detach 后访问局部对象崩溃 | 线程比对象活得久 → 悬垂引用。解决：按值拷贝数据进线程、或用 `shared_ptr` 延长生命周期 |
| 条件变量 wait 用了 `lock_guard` 编译不过 | `wait` 内部要解锁/重锁，必须 `std::unique_lock` |
| notify 后消费者永远睡死 | 通知先于 wait 发生且谓词未变（丢失唤醒）。解决：先持锁修改共享状态再 notify，且 wait 必带谓词 |
| 用裸 `wait(lk)` 不带谓词，偶发取到空任务 | 虚假唤醒。解决：`wait(lk, pred)` 或 while 循环重判条件 |
| `std::async` 一行调用反而变串行 | 默认策略返回的临时 future 析构即阻塞。解决：保存返回值、显式 `launch::async`、或改线程池 |
| 递归加锁自己死锁 | 同线程对 `std::mutex` 重复 lock 是 UB。解决：理清调用链；确需重入用 `recursive_mutex`（说明设计有问题） |
| atomic 全 relaxed，但其他线程读到旧数据 | relaxed 只保证单变量原子，不建 happens-before。解决：携带数据的标志用 acquire/release，别把 relaxed 当同步用 |
| `volatile` 当多线程同步 | volatile 不是内存屏障，CPU 乱序依旧。解决：用 `std::atomic` 或锁 |
| 双重检查锁定（DCLP）不加 atomic 崩溃 | `if (!p) { lock; if (!p) p = new T; }` 中 new 的写序可能重排。解决：C++11 起用局部 static；或 `std::atomic<T*>` + acquire/release |
| 线程数开太多反而变慢 | 上下文切换 + 缓存失效 + 锁竞争。解决：CPU 密集 ≈ 核数；IO 密集适度超额 |
| 线程里抛异常没人接 → terminate | 异常逃出线程函数即 terminate。解决：线程函数顶层 try/catch，或用 `std::promise::set_exception` 传回 |
| 无锁队列 ABA 导致崩溃 | CAS 只比较值，A→B→A 后误认为没变。解决：tagged pointer（指针+版本号）或 hazard pointer |
| 伪共享导致多线程比单线程还慢 | 不同变量在同一缓存行，一个核写使其他核缓存失效。解决：`alignas(64)` 隔离或 padding |
| 优先级队列低优先级任务永远不执行 | 持续高优先级任务导致饥饿。解决：老化机制（等待越久优先级越高）或最低执行率保证 |
