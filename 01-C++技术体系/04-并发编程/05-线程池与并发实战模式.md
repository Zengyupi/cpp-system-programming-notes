## 1. 线程池基础

### 1.1 线程池（任务队列 + 条件变量 + 原子停止位）

```cpp
#include <condition_variable>
#include <functional>
#include <mutex>
#include <queue>
#include <thread>
#include <vector>

class ThreadPool {
public:
    explicit ThreadPool(std::size_t n) : stop_(false) {
        for (std::size_t i = 0; i < n; ++i)
            workers_.emplace_back([this] {
                for (;;) {
                    std::unique_lock<std::mutex> lk(m_);
                    cv_.wait(lk, [this] { return stop_ || !tasks_.empty(); });  // 等任务或停止
                    if (stop_ && tasks_.empty()) return;        // 排空任务后才退出
                    auto task = std::move(tasks_.front());
                    tasks_.pop();
                    lk.unlock();                                // 执行期间放锁
                    task();                                     // 真正干活（可能抛异常，见注释）
                    lk.lock();
                }
            });
    }
    ~ThreadPool() {
        { std::lock_guard<std::mutex> lk(m_); stop_ = true; }   // 先置停止位（持锁修改共享状态）
        cv_.notify_all();                                       // 再广播唤醒
        for (auto& t : workers_) t.join();                      // 等全部 worker 退出
    }
    template <typename F>
    void submit(F&& f) {
        { std::lock_guard<std::mutex> lk(m_); tasks_.emplace(std::forward<F>(f)); }
        cv_.notify_one();
    }
private:
    std::vector<std::thread> workers_;
    std::queue<std::function<void()>> tasks_;
    std::mutex m_;
    std::condition_variable cv_;
    bool stop_;                                                 // 仅在持锁时读写
};
// 注：生产实现还应有：任务里 try/catch 防止异常杀线程、submit 返回 future、
//     线程数按 CPU 密集/IO 密集选择、动态扩缩容等。
```

## 2. 线程池进阶

基础线程池在高并发场景下有几个瓶颈：所有 worker 竞争同一个全局队列（锁竞争）、无法区分任务优先级、线程数固定不能适应负载波动、队列无界可能 OOM。本节逐一解决。

### 2.1 Work-Stealing 工作窃取算法

**核心思想**：每个 worker 线程有自己的本地任务队列（deque），worker 优先从自己的队列取任务；当本地队列为空时，去**窃取**其他 worker 队列末尾的任务。

```text
线程布局：
  Worker 0: [本地 deque 0] ← 自己从头部取（push/pop 头部，无竞争）
  Worker 1: [本地 deque 1] ← 空闲时从 Worker 0 的尾部偷（pop 尾部，有竞争用 CAS）
  Worker 2: [本地 deque 2]
  Worker 3: [本地 deque 3]

任务提交：
  submit() → 随机选一个 worker 的本地队列 push，或用全局队列分发

工作流程：
  1. Worker 从自己 deque 头部 pop（LIFO，缓存友好：刚提交的任务数据还在缓存）
  2. 自己队列为空 → 随机选一个 victim，从其 deque 尾部 pop（FIFO 窃取）
  3. 所有队列都空 → 条件变量等待新任务
```

Work-stealing 的关键优势：

| 维度 | 全局单队列 | Work-stealing |
| --- | --- | --- |
| 锁竞争 | 所有 worker 竞争同一把锁 | 本地操作无锁，仅窃取时有 CAS 竞争 |
| 缓存亲和性 | 任务随机分配到任意核 | LIFO 取任务，刚提交的任务数据仍在本核缓存 |
| 负载均衡 | 依赖调度器 | 自动窃取均衡（空闲线程偷忙线程的任务） |
| 实现复杂度 | 简单 | 复杂（需要无锁 deque + 窃取协议） |

C++17 work-stealing 线程池核心代码（简化版）：

```cpp
#include <atomic>
#include <deque>
#include <functional>
#include <mutex>
#include <random>
#include <thread>
#include <vector>
#include <condition_variable>

class WorkStealingPool {
public:
    explicit WorkStealingPool(std::size_t n) : stop_(false) {
        for (std::size_t i = 0; i < n; ++i)
            local_queues_.emplace_back(std::make_unique<LocalQueue>());
        for (std::size_t i = 0; i < n; ++i)
            workers_.emplace_back([this, i] { worker_loop(i); });
    }

    ~WorkStealingPool() {
        { std::lock_guard<std::mutex> lk(m_); stop_ = true; }
        cv_.notify_all();
        for (auto& t : workers_) t.join();
    }

    void submit(std::function<void()> task) {
        std::size_t idx = rng_() % workers_.size();  // 随机选一个本地队列
        local_queues_[idx]->push(std::move(task));
        cv_.notify_one();
    }

private:
    struct LocalQueue {
        std::deque<std::function<void()>> dq;
        std::mutex mtx;
        void push(std::function<void()> f) {
            std::lock_guard<std::mutex> lk(mtx);
            dq.push_front(std::move(f));  // 头部 push
        }
        bool pop_local(std::function<void()>& out) {
            std::lock_guard<std::mutex> lk(mtx);
            if (dq.empty()) return false;
            out = std::move(dq.front()); dq.pop_front();  // 头部 pop（LIFO）
            return true;
        }
        bool steal(std::function<void()>& out) {
            std::lock_guard<std::mutex> lk(mtx);
            if (dq.empty()) return false;
            out = std::move(dq.back()); dq.pop_back();    // 尾部 pop（FIFO 窃取）
            return true;
        }
    };

    void worker_loop(std::size_t my_idx) {
        std::function<void()> task;
        while (true) {
            // 1. 优先从自己的本地队列取
            if (local_queues_[my_idx]->pop_local(task)) {
                task();
                continue;
            }
            // 2. 随机窃取其他 worker
            bool stole = false;
            for (std::size_t attempt = 0; attempt < workers_.size(); ++attempt) {
                std::size_t victim = (my_idx + attempt + 1) % workers_.size();
                if (local_queues_[victim]->steal(task)) { stole = true; break; }
            }
            if (stole) { task(); continue; }
            // 3. 都没有，等待
            std::unique_lock<std::mutex> lk(m_);
            cv_.wait(lk, [this] { return stop_ || has_any_task(); });
            if (stop_ && !has_any_task()) return;
        }
    }

    bool has_any_task() {
        for (auto& q : local_queues_)
            if (!q->dq.empty()) return true;  // 注意：此处未加锁，仅作快速检查
        return false;
    }

    std::vector<std::thread> workers_;
    std::vector<std::unique_ptr<LocalQueue>> local_queues_;
    std::mutex m_;
    std::condition_variable cv_;
    bool stop_;
    std::mt19937 rng_{std::random_device{}()};
};
```

> 生产级 work-stealing（如 Intel TBB、Go runtime、Java ForkJoinPool）使用**无锁的 Chase-Lev deque**：本地 push/pop 用原子操作无锁，窃取端用 CAS。上面的简化版用 mutex 保护每个 deque，逻辑正确但性能不是最优。无锁队列专题见《06-无锁进阶：SPSC队列与ABA防护.md》，完整实现见《../13-并发异步与组件/07-原子操作与无锁组件.md》。

### 2.2 优先级任务队列

基础线程池的任务是 FIFO 的，无法区分紧急程度。优先级队列让高优先级任务先执行。

```cpp
#include <queue>
#include <functional>
#include <mutex>

// 带优先级的任务包装
struct PriorityTask {
    int priority;                        // 数字越大优先级越高
    std::function<void()> func;
    std::uint64_t seq;                  // 同优先级按提交顺序（FIFO）
    bool operator>(const PriorityTask& other) const {
        if (priority != other.priority) return priority < other.priority;  // 大顶堆
        return seq > other.seq;                                              // 同优先级先来先执行
    }
};

class PriorityThreadPool {
public:
    explicit PriorityThreadPool(std::size_t n) : stop_(false), seq_counter_(0) {
        for (std::size_t i = 0; i < n; ++i)
            workers_.emplace_back([this] {
                for (;;) {
                    std::unique_lock<std::mutex> lk(m_);
                    cv_.wait(lk, [this] { return stop_ || !pq_.empty(); });
                    if (stop_ && pq_.empty()) return;
                    auto task = std::move(const_cast<PriorityTask&>(pq_.top()));
                    pq_.pop();
                    lk.unlock();
                    task.func();
                }
            });
    }

    void submit(std::function<void()> f, int priority = 0) {
        {
            std::lock_guard<std::mutex> lk(m_);
            pq_.push(PriorityTask{priority, std::move(f), seq_counter_++});
        }
        cv_.notify_one();
    }

    ~PriorityThreadPool() {
        { std::lock_guard<std::mutex> lk(m_); stop_ = true; }
        cv_.notify_all();
        for (auto& t : workers_) t.join();
    }

private:
    std::vector<std::thread> workers_;
    std::priority_queue<PriorityTask, std::vector<PriorityTask>, std::greater<PriorityTask>> pq_;
    std::mutex m_;
    std::condition_variable cv_;
    bool stop_;
    std::uint64_t seq_counter_;
};
```

| 特性 | FIFO 队列 | 优先级队列 |
| --- | --- | --- |
| 执行顺序 | 提交顺序 | 优先级 + 提交顺序 |
| 数据结构 | `std::queue`（环形缓冲） | `std::priority_queue`（二叉堆） |
| push/pop 复杂度 | O(1) | O(log n) |
| 饥饿风险 | 无 | 低优先级任务可能永远不执行（需老化机制） |
| 适用场景 | 通用任务调度 | 紧急任务优先、QoS 分级 |

> 优先级队列的经典坑：**低优先级饥饿**。如果持续有高优先级任务提交，低优先级任务永远排不到。解决方案：老化（aging）——任务等待时间越长，动态提升其优先级；或设置最低执行率（每执行 N 个高优先级任务，必须执行 1 个低优先级）。

### 2.3 动态扩缩容策略

固定线程数在负载波动时效率不高：负载低时空闲线程浪费资源，负载高时线程不够用。动态扩缩容根据队列长度和任务等待时间调整线程数。

```cpp
#include <atomic>
#include <chrono>
#include <condition_variable>
#include <functional>
#include <mutex>
#include <queue>
#include <thread>
#include <vector>

class DynamicThreadPool {
public:
    DynamicThreadPool(std::size_t min_threads, std::size_t max_threads)
        : min_threads_(min_threads), max_threads_(max_threads),
          active_threads_(0), stop_(false) {
        for (std::size_t i = 0; i < min_threads_; ++i) spawn_worker();
        // 管理线程：定期检查负载，决定扩缩容
        manager_ = std::thread([this] { manage_loop(); });
    }

    ~DynamicThreadPool() {
        { std::lock_guard<std::mutex> lk(m_); stop_ = true; }
        cv_.notify_all();
        manager_.join();
        for (auto& t : workers_) if (t.joinable()) t.join();
    }

    void submit(std::function<void()> f) {
        { std::lock_guard<std::mutex> lk(m_); tasks_.push(std::move(f)); }
        cv_.notify_one();
    }

private:
    void spawn_worker() {
        workers_.emplace_back([this] {
            while (true) {
                std::function<void()> task;
                {
                    std::unique_lock<std::mutex> lk(m_);
                    cv_.wait(lk, [this] { return stop_ || !tasks_.empty(); });
                    if (stop_ && tasks_.empty()) return;
                    // 缩容：如果当前线程数超过需要，且自己是"多余"的，则退出
                    if (should_exit()) return;
                    task = std::move(tasks_.front());
                    tasks_.pop();
                    ++active_threads_;
                }
                task();
                --active_threads_;
            }
        });
    }

    bool should_exit() {
        // 简化：如果队列空且线程数 > min_threads_，允许退出
        // 实际实现需要更精细的空闲超时机制
        return tasks_.empty() && workers_.size() > min_threads_;
    }

    void manage_loop() {
        while (!stop_) {
            std::this_thread::sleep_for(std::chrono::milliseconds(500));
            std::lock_guard<std::mutex> lk(m_);
            if (stop_) return;

            std::size_t pending = tasks_.size();
            std::size_t current = workers_.size();

            // 扩容：队列积压 > 线程数的 2 倍，且未达上限
            if (pending > current * 2 && current < max_threads_) {
                spawn_worker();
            }
            // 缩容：队列空且活跃线程少，且超过最小线程数
            // （实际缩容由 worker 在 should_exit 时自然退出）
        }
    }

    std::size_t min_threads_;
    std::size_t max_threads_;
    std::atomic<std::size_t> active_threads_;
    std::vector<std::thread> workers_;
    std::thread manager_;
    std::queue<std::function<void()>> tasks_;
    std::mutex m_;
    std::condition_variable cv_;
    bool stop_;
};
```

| 策略 | 触发条件 | 操作 | 风险 |
| --- | --- | --- | --- |
| 扩容 | 队列积压 > 阈值 | 创建新 worker | 创建开销、瞬时过载 |
| 缩容 | 空闲超时（如 60s 无任务） | worker 自然退出 | 频繁扩缩容（抖动） |
| 预热 | 启动时 | 先创建 min_threads 个 | 低负载时浪费 |
| 防抖动 | 扩容后冷却期（如 10s 内不缩容） | 延迟缩容决策 | 响应变慢 |

### 2.4 有界队列与拒绝策略

无界队列在生产者远快于消费者时会无限增长，最终 OOM。有界队列限制最大长度，满时执行拒绝策略。

```cpp
#include <condition_variable>
#include <functional>
#include <mutex>
#include <queue>
#include <thread>
#include <vector>
#include <stdexcept>

enum class RejectPolicy {
    Abort,          // 抛异常
    Discard,        // 静默丢弃新任务
    DiscardOldest,  // 丢弃队列中最老的任务，腾出空间
    CallerRuns,     // 由提交线程自己执行（反压）
    Block           // 阻塞等待队列有空位
};

class BoundedThreadPool {
public:
    BoundedThreadPool(std::size_t n, std::size_t max_queue,
                      RejectPolicy policy = RejectPolicy::Abort)
        : max_queue_(max_queue), policy_(policy), stop_(false) {
        for (std::size_t i = 0; i < n; ++i)
            workers_.emplace_back([this] {
                for (;;) {
                    std::unique_lock<std::mutex> lk(m_);
                    cv_.wait(lk, [this] { return stop_ || !tasks_.empty(); });
                    if (stop_ && tasks_.empty()) return;
                    auto task = std::move(tasks_.front());
                    tasks_.pop();
                    lk.unlock();
                    not_full_.notify_one();  // 队列有空位了，通知阻塞的提交者
                    task();
                }
            });
    }

    void submit(std::function<void()> f) {
        std::unique_lock<std::mutex> lk(m_);
        if (tasks_.size() >= max_queue_) {
            switch (policy_) {
                case RejectPolicy::Abort:
                    throw std::runtime_error("线程池队列已满");
                case RejectPolicy::Discard:
                    return;  // 静默丢弃
                case RejectPolicy::DiscardOldest:
                    tasks_.pop();  // 丢最老的
                    break;          // 继续 push 新的
                case RejectPolicy::CallerRuns:
                    lk.unlock();
                    f();  // 提交者自己执行（反压：降低提交速度）
                    return;
                case RejectPolicy::Block:
                    not_full_.wait(lk, [this] { return tasks_.size() < max_queue_; });
                    break;
            }
        }
        tasks_.push(std::move(f));
        lk.unlock();
        cv_.notify_one();
    }

    ~BoundedThreadPool() {
        { std::lock_guard<std::mutex> lk(m_); stop_ = true; }
        cv_.notify_all();
        not_full_.notify_all();
        for (auto& t : workers_) t.join();
    }

private:
    std::size_t max_queue_;
    RejectPolicy policy_;
    std::vector<std::thread> workers_;
    std::queue<std::function<void()>> tasks_;
    std::mutex m_;
    std::condition_variable cv_;
    std::condition_variable not_full_;
    bool stop_;
};
```

| 拒绝策略 | 行为 | 适用场景 |
| --- | --- | --- |
| Abort | 抛异常，让调用者处理 | 关键任务，不能丢也不能阻塞 |
| Discard | 静默丢弃 | 非关键日志、监控数据 |
| DiscardOldest | 丢最老的任务 | 最新数据最重要（如实时行情） |
| CallerRuns | 提交者自己执行 | 反压（自然降低提交速率），最安全 |
| Block | 阻塞等待 | 不能丢任务，且提交者可以等待 |

## 3. 并发模式

### 3.1 Active Object 模式

Active Object 将"方法调用"和"方法执行"解耦：调用者提交请求到队列，专用线程串行执行请求，从而**无需显式加锁**就能保证线程安全。

```cpp
#include <functional>
#include <future>
#include <mutex>
#include <queue>
#include <thread>
#include <condition_variable>

class ActiveObject {
public:
    ActiveObject() : stop_(false) {
        worker_ = std::thread([this] { run(); });
    }

    ~ActiveObject() {
        { std::lock_guard<std::mutex> lk(m_); stop_ = true; }
        cv_.notify_one();
        worker_.join();
    }

    // 提交任务，返回 future（调用者可以异步取结果）
    template <typename F>
    auto submit(F&& f) -> std::future<decltype(f())> {
        using Ret = decltype(f());
        auto task = std::make_shared<std::packaged_task<Ret()>>(std::forward<F>(f));
        auto fut = task->get_future();
        {
            std::lock_guard<std::mutex> lk(m_);
            tasks_.push([task]() { (*task)(); });
        }
        cv_.notify_one();
        return fut;
    }

private:
    void run() {
        while (true) {
            std::function<void()> task;
            {
                std::unique_lock<std::mutex> lk(m_);
                cv_.wait(lk, [this] { return stop_ || !tasks_.empty(); });
                if (stop_ && tasks_.empty()) return;
                task = std::move(tasks_.front());
                tasks_.pop();
            }
            task();  // 单线程串行执行，内部数据无需加锁
        }
    }

    std::thread worker_;
    std::queue<std::function<void()>> tasks_;
    std::mutex m_;
    std::condition_variable cv_;
    bool stop_;
};

// 使用示例：一个线程安全的计数器，内部无需 mutex
class SafeCounter {
    ActiveObject ao_;
    int value_ = 0;  // 只在 ao_ 的 worker 线程中被访问，无需锁
public:
    std::future<int> increment() {
        return ao_.submit([this] { return ++value_; });
    }
    std::future<int> get() {
        return ao_.submit([this] { return value_; });
    }
};
```

| 维度 | 互斥锁保护 | Active Object |
| --- | --- | --- |
| 线程安全机制 | 锁（互斥） | 单线程串行执行（避免共享） |
| 调用方式 | 同步（直接调用，可能阻塞等锁） | 异步（提交到队列，返回 future） |
| 死锁风险 | 有（多把锁、回调中加锁） | 无（单线程无锁） |
| 性能 | 高（多线程并行） | 低（单线程串行，适合低并发） |
| 适用场景 | 高并发、短临界区 | 低并发、复杂状态机、避免锁复杂度 |

### 3.2 Monitor Object 模式

Monitor Object 是"共享资源 + 一把锁 + 条件变量"的封装：所有公共方法自动加锁，内部用条件变量等待/通知。这是最经典的线程安全类设计模式。

```cpp
#include <condition_variable>
#include <mutex>
#include <queue>

template <typename T>
class MonitorQueue {
public:
    void push(const T& v) {
        std::lock_guard<std::mutex> lk(m_);  // 自动加锁
        q_.push(v);
        cv_.notify_one();                       // 自动通知
    }                                            // 自动解锁（析构）

    T pop() {
        std::unique_lock<std::mutex> lk(m_);
        cv_.wait(lk, [this] { return !q_.empty(); });  // 谓词等待
        T v = q_.front(); q_.pop();
        return v;
    }

    bool try_pop(T& v) {
        std::lock_guard<std::mutex> lk(m_);
        if (q_.empty()) return false;
        v = q_.front(); q_.pop();
        return true;
    }

    std::size_t size() const {
        std::lock_guard<std::mutex> lk(m_);
        return q_.size();
    }

private:
    mutable std::mutex m_;
    std::condition_variable cv_;
    std::queue<T> q_;
};
```

Monitor Object 的关键规则：
- **所有公共方法都在持锁状态下执行**（封装锁，用户无需手动加锁）
- **条件变量等待必须用谓词**（防虚假唤醒）
- **不要在持锁时调用外部回调**（可能导致死锁，回调中可能反过来调用 monitor 的方法）
- **返回引用/指针时要小心**（引用的对象在锁释放后可能被其他线程修改）

### 3.3 双重检查锁（DCLP）单例的正确写法

DCLP（Double-Checked Locking Pattern）是单例模式的经典优化：先无锁检查，再加锁检查，避免每次获取单例都加锁。但在 C++11 之前，DCLP 因内存序问题是不安全的。

```cpp
// ========== 错误写法（C++03 及以前，UB）==========
class SingletonBad {
    static SingletonBad* instance_;
    static std::mutex mtx_;
public:
    static SingletonBad* get() {
        if (!instance_) {                    // ① 无锁检查（可能看到半构造对象）
            std::lock_guard<std::mutex> lk(mtx_);
            if (!instance_)                  // ② 加锁后再检查
                instance_ = new SingletonBad();  // ③ new 的写序可能重排！
        }
        return instance_;
    }
};
// 问题：new 分三步——分配内存、构造对象、赋值给 instance_。
// 编译器/CPU 可能重排为：分配内存 → 赋值 instance_ → 构造对象。
// 线程 A 执行到"赋值 instance_"但还没构造完，线程 B 看到 instance_ 非空，
// 直接返回半构造对象 → UB。

// ========== 正确写法 1：C++11 magic statics（最推荐）==========
class SingletonMagic {
public:
    static SingletonMagic& get() {
        static SingletonMagic instance;  // C++11 起：局部 static 初始化线程安全
        return instance;
    }
    SingletonMagic(const SingletonMagic&) = delete;
    SingletonMagic& operator=(const SingletonMagic&) = delete;
private:
    SingletonMagic() = default;
};
// 原理：C++11 标准规定局部 static 的初始化是线程安全的。
// 编译器内部生成类似 DCLP 的代码，但用正确的内存序（atomic + acquire/release）。
// 如果初始化抛异常，下次调用会重新尝试。

// ========== 正确写法 2：atomic + acquire/release（显式 DCLP）==========
#include <atomic>

class SingletonAtomic {
    static std::atomic<SingletonAtomic*> instance_;
    static std::mutex mtx_;
public:
    static SingletonAtomic* get() {
        SingletonAtomic* p = instance_.load(std::memory_order_acquire);  // ① acquire 读
        if (!p) {
            std::lock_guard<std::mutex> lk(mtx_);
            p = instance_.load(std::memory_order_relaxed);  // ② 已持锁，relaxed 足够
            if (!p) {
                p = new SingletonAtomic();
                instance_.store(p, std::memory_order_release);  // ③ release 写：构造完成后才发布
            }
        }
        return p;
    }
};
// 原理：
//   - ③ release store 保证：new 的构造（在 release 之前）对 acquire 读可见
//   - ① acquire load 保证：看到 release 写的指针时，构造已完成
//   - ② 持锁后用 relaxed 读：因为锁已经建立了 happens-before
```

| 写法 | 线程安全 | 性能 | 推荐度 |
| --- | --- | --- | --- |
| C++03 裸 DCLP（无 atomic） | ❌ UB | 高 | 禁止 |
| 每次加锁（无 DCLP） | ✅ | 低（每次都加锁） | 不推荐 |
| C++11 magic static | ✅ | 高（首次初始化后无锁） | **最推荐** |
| atomic + acquire/release DCLP | ✅ | 高 | 需要控制生命周期时用 |

### 3.4 信号丢失（Spurious Wakeup）与唤醒丢失（Lost Wakeup）

这两个是条件变量最经典的问题，名字相似但完全不同。

**Spurious Wakeup（虚假唤醒）**：线程被唤醒，但谓词条件并未满足。

```text
原因：
  - OS 底层 futex 允许无通知唤醒（性能优化，避免某些竞态）
  - C++ 标准明确允许 condition_variable 出现虚假唤醒
  - 多消费者场景下，notify_one 唤醒一个，但另一个消费者抢先拿走了任务

后果：
  - 如果用裸 wait(lk) 而不检查条件，被虚假唤醒后以为条件满足，实际队列为空 → 取到空任务/崩溃

防范：
  - 永远用 wait(lk, pred) 谓词版本，或手写 while 循环
  - 谓词在 wait 返回后重新检查，不满足则继续等待
```

```cpp
// 错误：裸 wait，不检查条件
void bad_consumer() {
    std::unique_lock<std::mutex> lk(m);
    cv.wait(lk);                // 可能被虚假唤醒！
    int v = q.front(); q.pop();  // 队列可能为空 → 未定义行为
}

// 正确：谓词 wait
void good_consumer() {
    std::unique_lock<std::mutex> lk(m);
    cv.wait(lk, [] { return !q.empty(); });  // 谓词自动重试，虚假唤醒后继续等
    int v = q.front(); q.pop();
}
```

**Lost Wakeup（唤醒丢失）**：notify 发生时，对方还没进入 wait，通知被"漏掉"了。

```text
场景：
  线程 A（消费者）：检查队列空 → 准备调用 wait（但还没调用）
  线程 B（生产者）：push 任务 → notify_one（此时 A 还没在等，通知丢失）
  线程 A（消费者）：调用 wait → 永久阻塞（因为通知已经发过了，不会再发）

根因：
  检查条件和进入 wait 之间有时间窗口，notify 可能落在这个窗口里

防范：
  - 检查条件和 wait 必须在**同一把锁的保护下**进行
  - notify 前必须**持锁修改共享状态**（谓词依赖的变量）
  - 这样消费者持锁检查条件时，生产者无法同时修改条件并 notify
  - 即使 notify 先于 wait 发生，谓词已经变了，wait 会立即返回（不阻塞）
```

```cpp
// 错误：检查和 wait 不在同一把锁里
void bad_pattern() {
    if (q.empty()) {              // 无锁检查
        // 时间窗口：生产者可能在这里 push + notify
        std::unique_lock<std::mutex> lk(m);
        cv.wait(lk);               // 通知已丢失，永久阻塞
    }
}

// 正确：持锁检查 + 谓词 wait
void good_pattern() {
    std::unique_lock<std::mutex> lk(m);  // 先拿锁
    cv.wait(lk, [] { return !q.empty(); });  // 持锁检查谓词，生产者无法在检查和 wait 之间插入 notify
    // 即使 notify 先发生，谓词 !q.empty() 已为 true，wait 立即返回
}
```

| 问题 | 现象 | 根因 | 防范 |
| --- | --- | --- | --- |
| Spurious Wakeup | 被唤醒但条件不满足 | OS 允许无通知唤醒 | 谓词 wait / while 循环 |
| Lost Wakeup | notify 后对方仍永久睡死 | notify 落在检查与 wait 的窗口 | 持锁检查 + 持锁改状态 + 谓词 |

## 5. 常见问题与坑

| 问题 | 原因与解决方案 |
| --- | --- |
| `std::thread` 对象析构时程序直接 terminate | 未调用 join/detach 就析构。解决：join；或用 C++20 `jthread` 自动 join |
| detach 后访问局部对象崩溃 | 线程比对象活得久 → 悬垂引用。解决：按值拷贝数据进线程、或用 `shared_ptr` 延长生命周期 |
| 条件变量 wait 用了 `lock_guard` 编译不过 | `wait` 内部要解锁/重锁，必须 `std::unique_lock` |
| notify 后消费者永远睡死 | 通知先于 wait 发生且谓词未变（丢失唤醒）。解决：先持锁修改共享状态再 notify，且 wait 必带谓词 |
| 用裸 `wait(lk)` 不带谓词，偶发取到空任务 | 虚假唤醒。解决：`wait(lk, pred)` 或 while 循环重判条件 |
| `std::async` 一行调用反而变串行 | 默认策略返回的临时 future 析构即阻塞。解决：保存返回值、显式 `launch::async`、或改线程池 |
| 递归加锁自己死锁 | 同线程对 `std::mutex` 重复 lock 是 UB。解决：理清调用链；确需重入用 `recursive_mutex`（说明设计有问题） |
| 线程数开太多反而变慢 | 上下文切换 + 缓存失效 + 锁竞争。解决：CPU 密集 ≈ 核数；IO 密集适度超额 |
| 线程里抛异常没人接 → terminate | 异常逃出线程函数即 terminate。解决：线程函数顶层 try/catch，或用 `std::promise::set_exception` 传回 |
| 优先级队列低优先级任务永远不执行 | 持续高优先级任务导致饥饿。解决：老化机制（等待越久优先级越高）或最低执行率保证 |

> 无锁相关坑（relaxed 读旧值、volatile 同步、ABA、伪共享、DCLP）见《06-无锁进阶：SPSC队列与ABA防护.md》第 4 节。
