## 1. condition_variable（C++11）

### 1.1 生产者-消费者完整示例

```cpp
#include <condition_variable>
#include <mutex>
#include <optional>
#include <queue>

std::queue<int> q;
std::mutex m;
std::condition_variable cv;
bool done = false;

void producer() {
    for (int i = 0; i < 100; ++i) {
        { std::lock_guard<std::mutex> lk(m); q.push(i); }
        cv.notify_one();                       // 修改共享状态后再通知
    }
    { std::lock_guard<std::mutex> lk(m); done = true; }
    cv.notify_all();                           // 唤醒所有消费者让它们退出
}

void consumer() {
    for (;;) {
        std::unique_lock<std::mutex> lk(m);    // 必须 unique_lock（wait 内部要解锁/重锁）
        cv.wait(lk, [] { return !q.empty() || done; });   // 谓词版本 = while 循环防虚假唤醒
        while (!q.empty()) {
            int v = q.front(); q.pop();
            lk.unlock();                       // 处理期间放锁，别占着临界区干活
            /* 消费 v */
            lk.lock();
        }
        if (done && q.empty()) return;
    }
}
```

### 1.2 为什么必须用谓词（虚假唤醒）

| 现象 | 原因 | 对策 |
| --- | --- | --- |
| 虚假唤醒 spurious wakeup | OS 底层 `futex`/条件变量允许无通知唤醒（性能权衡），标准明确允许 | `wait(lk, pred)` 或手写 `while (!pred()) cv.wait(lk);` |
| 丢失唤醒 | notify 时对方没在等待 | 通知前先改共享状态并持锁更新，谓词自然兜底 |
| 惊群 | notify_all 唤醒 N 个只有 1 个能干活 | 只在"状态影响所有等待者"（如退出）时用 notify_all |

### 1.3 wait 内部三步

```text
cv.wait(lk, pred) 的内部逻辑：
        ┌──────────────────────────────┐
        │ while (!pred()) {            │
        │   ① lk.unlock()   ──────────── 必须先解锁，否则生产者进不了临界区改状态
        │   ② 线程阻塞挂起（不占 CPU） │
        │   ③ lk.lock()     ──────────── 被唤醒后重新加锁，返回前必须重新持有
        │ }                            │
        └──────────────────────────────┘
```

| notify 函数 | 语义 | 用法 |
| --- | --- | --- |
| `notify_one` | 唤醒一个等待者 | 队列新增一个任务 |
| `notify_all` | 唤醒所有等待者 | 状态变化影响多个等待者/退出广播 |

> 注意：通知本身不需要持锁，但**修改谓词依赖的共享状态必须持锁**；`notify` 在持锁内还是外是性能权衡（外可避免唤醒后立刻阻塞），先保证正确性。

## 2. 异步工具（C++11）

### 2.1 三兄弟对比

| 工具 | 角色 | 取结果方式 | 备注 |
| --- | --- | --- | --- |
| `std::promise<T>` | 手工设置结果的一端 | 配对的 `future.get()` | `set_value` 只能一次；可传异常 `set_exception` |
| `std::packaged_task<F>` | 包装可调用对象，执行结果自动进 future | `future.get()` | 把"任务"与"结果通道"绑定，适合塞进线程池 |
| `std::async(F, args...)` | 最高层：自动起线程 + 返回 future | `future.get()` | 策略见下表 |
| `std::shared_future<T>` | 可拷贝、多次 `get` | 广播同一结果 | future 只能 `get` 一次 |
| `std::future<T>` | 结果占位 | `get()` 阻塞、`wait_for` 探测 | **不可续接**（见 2.3） |

### 2.2 async 启动策略

| 策略 | 行为 | 坑 |
| --- | --- | --- |
| `std::launch::async` | 新线程立即执行 | **future 析构会阻塞**等任务结束（临时对象被丢弃时最容易踩：`std::async(...);` 一行直接变同步） |
| `std::launch::deferred` | 惰性：首次 `get()` 才在当前线程执行 | 从不 `get` 就**从不执行** |
| 默认（`async|deferred`） | 实现自选 | 行为不可移植，常见实现偏向新线程但不能依赖 |

```cpp
#include <future>

int slow_computation() { /* ... */ return 42; }

int main() {
    std::future<int> f = std::async(std::launch::async, slow_computation);
    // 主线程先干别的 ...
    int v = f.get();              // 阻塞取结果（只能 get 一次）
}
```

### 2.3 future 的局限与替代

| 局限 | 说明 |
| --- | --- |
| 不可续接 | 没有 `.then()`：拿结果必须阻塞 get |
| 不可组合 | 没有 `when_all / when_any` |
| 单次 | `get` 后 future 失效（`shared_future` 才能多次） |

第三方延续回调模型：`folly::Future`（`.then()` 链式）、`boost::future`（`then`/`when_all`，Continuation 语义）、以及 C++20 协程 `co_await`（语言级方案，见后续协程篇）。

## 3. once_flag / call_once 与 thread_local

| 工具 | 用途 | 示例 |
| --- | --- | --- |
| `std::call_once` + `std::once_flag`（C++11） | 全局初始化只执行一次（含异常安全） | 单例、全局配置加载 |
| 函数局部 `static` 初始化 | C++11 起线程安全（"magic statics"），**优先用它** | 单例惯用法 |
| `thread_local`（C++11） | 每线程一份变量 | 每线程缓冲、错误码、随机数引擎 |

```cpp
#include <mutex>

std::once_flag g_once;
void init_globals() { std::call_once(g_once, [] { /* 只跑一次 */ }); }

// 更简洁的等价物：C++11 起局部 static 初始化线程安全
Widget& instance() { static Widget w; return w; }

thread_local int tls_error_code = 0;    // 每个线程独立一份，互不干扰
```

> `thread_local` 的底层实现原理（`fs` 段寄存器、TLS 区域布局）详见《01-线程基础与生命周期.md》第 3.5 节。

## 4. C++20 同步原语

C++20 在 `<semaphore>`、`<latch>`、`<barrier>`、`<atomic>` 中新增了一批高层同步原语，填补了 C++11/17 只有 mutex/condition_variable 的空白。它们的共同特点是**语义更明确、误用空间更小**。

### 4.1 counting_semaphore 与 binary_semaphore

信号量维护一个非负计数器，`acquire()` 递减（到 0 则阻塞），`release()` 递增（唤醒等待者）。与 mutex 的关键区别：**信号量可以由不同线程 release**（mutex 必须同一线程 unlock），且初始计数可以大于 1。

```cpp
#include <semaphore>
#include <thread>
#include <vector>
#include <cstdio>

// 计数信号量：限制同时访问资源的线程数（如连接池上限）
std::counting_semaphore<10> pool_sem{10};  // 初始计数 10，最多 10 个线程同时进入

void worker(int id) {
    pool_sem.acquire();        // 计数 -1，满了则阻塞等待
    std::printf("线程 %d 获得资源\n", id);
    // 使用受限资源
    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    pool_sem.release();        // 计数 +1，唤醒一个等待者
    std::printf("线程 %d 释放资源\n", id);
}

// 二元信号量：计数最大为 1，等价于 mutex 但可跨线程 release
std::binary_semaphore ready{0};  // 初始 0：用于"事件通知"模式

void sender() {
    // 准备数据...
    ready.release();  // 发信号：计数 0→1，唤醒等待者
}

void receiver() {
    ready.acquire();  // 等信号：计数 1→0，若为 0 则阻塞
    // 数据已就绪，处理
}
```

| 特性 | `std::counting_semaphore<N>` | `std::binary_semaphore` | `std::mutex` |
| --- | --- | --- | --- |
| 计数范围 | 0 ~ N（模板参数指定上限） | 0 ~ 1 | 0/1（隐含） |
| acquire/release 线程 | 可不同线程 | 可不同线程 | **必须同一线程** |
| 初始计数 | 构造时指定 | 构造时指定 | 0（未锁定） |
| 典型用途 | 资源池限流、生产者-消费者 | 事件通知、一次性信号 | 临界区互斥 |
| 超时版本 | `try_acquire_for/until` | 同左 | `timed_mutex` 才有 |

> 信号量 vs condition_variable：信号量是**自包含**的（计数器 + 等待队列），不需要额外 mutex 保护状态；condition_variable 需要配合 mutex + 共享谓词变量。简单的"事件通知/资源计数"用信号量更简洁，复杂的"等待任意条件"用 condition_variable。

### 4.2 latch

latch 是一个**一次性**的倒计时门闩：初始计数为 N，`count_down()` 递减，`wait()` 阻塞直到计数归零。**计数只能递减不能递增，归零后永久打开**（latch 不可复用）。

```cpp
#include <latch>
#include <thread>
#include <vector>
#include <cstdio>

int main() {
    const int N = 5;
    std::latch work_done(N);  // 5 个 worker 都完成后打开

    std::vector<std::jthread> workers;
    for (int i = 0; i < N; ++i) {
        workers.emplace_back([&work_done, i] {
            std::printf("worker %d 开始工作\n", i);
            std::this_thread::sleep_for(std::chrono::milliseconds(50 * i));
            std::printf("worker %d 完成\n", i);
            work_done.count_down();  // 递减计数，不阻塞
        });
    }

    work_done.wait();  // 阻塞直到所有 worker 都 count_down
    std::printf("全部 worker 完成，主线程继续\n");

    // latch 归零后永久打开，再次 wait 立即返回
    work_done.wait();  // 不阻塞
    return 0;
}
```

latch 的典型模式：

| 模式 | 用法 |
| --- | --- |
| 等待 N 个任务完成 | `latch(N)`，每个任务结束 `count_down()`，主线程 `wait()` |
| 让 N 个线程同时启动 | `latch(1)`，所有线程 `wait()` 等发令枪，主线程 `count_down()` |
| 嵌套等待 | 多个 latch 串联：完成阶段 A → 打开 latch A → 开始阶段 B |

### 4.3 barrier

barrier 与 latch 类似也是倒计时，但**可复用**：N 个线程到达 `arrive_and_wait()` 后全部阻塞，直到第 N 个到达，然后**全部释放并自动重置计数**，进入下一轮。barrier 还支持在每轮结束时执行一个 completion 函数。

```cpp
#include <barrier>
#include <thread>
#include <vector>
#include <cstdio>

int main() {
    const int N = 3;
    int round = 0;

    // completion 函数：每轮所有线程到达后、释放前执行（由最后一个到达的线程调用）
    std::barrier sync_point(N, [&round]() noexcept {
        ++round;
        std::printf("=== 第 %d 轮同步完成 ===\n", round);
    });

    std::vector<std::jthread> workers;
    for (int i = 0; i < N; ++i) {
        workers.emplace_back([&sync_point, i] {
            for (int phase = 0; phase < 3; ++phase) {
                std::printf("线程 %d 进入阶段 %d\n", i, phase);
                std::this_thread::sleep_for(std::chrono::milliseconds(30 * (i + 1)));
                std::printf("线程 %d 完成阶段 %d，等待同步\n", i, phase);
                sync_point.arrive_and_wait();  // 到达并等待；全部到达后一起释放
            }
        });
    }
    return 0;
}
```

| 特性 | `std::latch` | `std::barrier` |
| --- | --- | --- |
| 可复用 | 否（一次性，归零后永久打开） | 是（每轮自动重置） |
| 计数变化 | 只能递减 | 递减到 0 后自动恢复为 N |
| completion 回调 | 无 | 有（每轮结束时执行） |
| 灵活到达 | `count_down(n)` 可一次减多个 | `arrive(n)` 可一次到达多个 |
| 典型用途 | 一次性等待/发令 | 迭代式并行计算（BSP 模型）、多阶段流水线同步 |

> BSP（Bulk Synchronous Parallel）模型：计算 → 屏障同步 → 计算 → 屏障同步……barrier 是 BSP 的核心原语。典型场景：并行矩阵乘法中，每轮计算完所有分块后 barrier 同步，再交换边界数据进入下一轮。

### 4.4 atomic_ref

`std::atomic_ref<T>`（C++20）允许对**已存在的普通对象**进行原子访问，而不需要把对象本身声明为 `std::atomic<T>`。这在以下场景特别有用：
- 对象大部分时间单线程访问，偶尔需要多线程原子访问
- 第三方库返回的普通对象需要原子操作
- 数组元素需要原子访问（`std::atomic<T>` 数组不可拷贝，`atomic_ref` 无此问题）

```cpp
#include <atomic>
#include <thread>
#include <vector>
#include <cstdio>

struct Config {
    int timeout = 1000;
    int retries = 3;
    // 普通 int，不是 atomic
};

Config g_config;  // 全局配置，大部分时间只读

void update_config() {
    // 对普通 int 创建原子引用，进行原子写
    std::atomic_ref<int> atomic_timeout(g_config.timeout);
    atomic_timeout.store(5000, std::memory_order_release);
}

void read_config() {
    std::atomic_ref<int> atomic_timeout(g_config.timeout);
    int t = atomic_timeout.load(std::memory_order_acquire);
    std::printf("timeout = %d\n", t);
}

// 数组元素的原子操作：计数器数组
int counters[8] = {0};

void increment(int idx) {
    std::atomic_ref<int> c(counters[idx]);
    c.fetch_add(1, std::memory_order_relaxed);
}
```

| 特性 | `std::atomic<T>` | `std::atomic_ref<T>` |
| --- | --- | --- |
| 对象类型 | 原子包装类型，独占存储 | 引用外部已有对象，不占额外存储 |
| 生命周期 | 与 atomic 对象绑定 | 引用的对象必须比 atomic_ref 活得久 |
| 拷贝/移动 | 不可拷贝不可移动 | 可拷贝（浅拷贝引用） |
| 数组使用 | `std::atomic<T> arr[N]` 元素不可拷贝 | `T arr[N]` + `atomic_ref` 逐个引用，更灵活 |
| 对齐要求 | atomic 自身保证对齐 | **引用的对象必须满足对齐要求**（`atomic_ref<T>::required_alignment`） |

> 重要约束：`atomic_ref` 引用的对象必须满足 `required_alignment` 对齐要求，否则是 UB。对于 `int` 通常天然满足，但对于自定义结构体可能需要 `alignas`。另外，对同一对象不能混用原子和非原子访问——要么全部通过 atomic_ref，要么全部普通访问，否则数据竞争。

### 4.5 C++20 同步原语适用场景对比

| 场景 | 推荐原语 | 理由 |
| --- | --- | --- |
| 限制并发访问资源数（连接池/线程池） | `counting_semaphore` | 计数天然表达"剩余资源数" |
| 一次性事件通知（数据就绪） | `binary_semaphore` 或 `latch(1)` | 比 condition_variable + mutex + bool 更简洁 |
| 等待 N 个任务全部完成（一次性） | `latch(N)` | 语义明确，count_down 不阻塞调用者 |
| 多轮迭代同步（BSP/并行计算） | `barrier` | 可复用 + completion 回调 |
| 让 N 个线程同时开始（发令枪） | `latch(1)` | 所有线程 wait，主线程 count_down |
| 对已有普通对象做原子访问 | `atomic_ref` | 不需要改对象类型，灵活 |
| 临界区互斥 | `mutex`（C++11） | 信号量可替代但 mutex 语义更严格（同线程 unlock） |
| 等待复杂条件（队列非空/状态变化） | `condition_variable` | 谓词可表达任意条件 |
