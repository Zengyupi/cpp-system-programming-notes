## 1. 互斥与锁

### 1.1 mutex 家族

| 类型 | 标准 | 特点 | 适用 |
| --- | --- | --- | --- |
| `std::mutex` | C++11 | 基本互斥 | 默认选择 |
| `std::recursive_mutex` | C++11 | 同线程可重复加锁 | **掩盖设计问题**，尽量别用 |
| `std::timed_mutex` | C++11 | `try_lock_for/try_lock_until` | 可放弃的获取 |
| `std::shared_mutex` | C++17 | 读写锁（读共享写独占） | 读多写少 |
| `std::shared_timed_mutex` | C++14 | 读写锁 + 超时 | C++17 前的替代 |

读写锁的标准用法——读端 `shared_lock` 共享、写端 `unique_lock` 独占：

```cpp
#include <shared_mutex>
#include <unordered_map>

std::shared_mutex rw_mtx;
std::unordered_map<int, std::string> cache;

std::string read_cache(int key) {
    std::shared_lock<std::shared_mutex> lk(rw_mtx);   // 多个读线程可同时进入
    auto it = cache.find(key);
    return it == cache.end() ? std::string{} : it->second;
}

void write_cache(int key, std::string value) {
    std::unique_lock<std::shared_mutex> lk(rw_mtx);   // 写线程独占，阻塞一切新读
    cache[key] = std::move(value);
}
```

读写锁的两个代价必须清楚：

1. **写饥饿**：若读请求源源不断，写者可能长期排队拿不到锁。glibc/STL 实现通常带"读者排队到写者之后"的偏好策略，但业务层仍应保证写操作不会被无限延后；
2. **读写锁并不一定更快**：shared_mutex 内部要维护读者计数，原子操作比 mutex 更重。只有"读占绝大多数（如 9:1 以上）且读临界区有一定长度"时才划算，否则普通 mutex 反而更快——先测量再选型。

关于 `recursive_mutex`：它内部用计数器允许同一线程重复加锁、对应次数解锁。但"一个函数持锁后又调用另一个也要拿同一把锁的函数"几乎总是**锁边界设计不清**的信号。正确重构方式是拆成"不加锁的私有实现 + 加锁的公有外壳"：

```cpp
class Foo {
    std::mutex mtx;
    void do_a_locked();   // 内部方法，约定调用者已持锁，不再加锁
public:
    void a() { std::lock_guard<std::mutex> lk(mtx); do_a_locked(); }
    void b() {
        std::lock_guard<std::mutex> lk(mtx);
        do_a_locked();    // 直接调用不加锁版本，无需递归锁
    }
};
```

### 1.2 RAII 锁具对比大表

| 锁具 | 标准 | 开销/体积 | 可延迟/手动解锁 | 可移动 | 多锁一次拿 | 典型用途 |
| --- | --- | --- | --- | --- | --- | --- |
| `std::lock_guard` | C++11 | 最小（一个锁引用） | 否 | 否 | 否 | **作用域临界区（默认首选）** |
| `std::unique_lock` | C++11 | 较大（带状态标志） | 是（`defer_lock` 后手动） | 是 | 否 | 条件变量、需要中途解锁的复杂流 |
| `std::scoped_lock` | C++17 | 可变参 | 否 | 否 | **是**（免死锁算法） | 一次锁多把互斥量 |
| `std::shared_lock` | C++14 | 同 unique_lock | 是 | 是 | 否 | `shared_mutex` 的读端 |

```cpp
#include <mutex>

std::mutex m1, m2;

void locked_scope() {
    std::lock_guard<std::mutex> lk(m1);      // 构造即加锁，析构自动解锁（异常安全）
    // 临界区
}                                            // 自动解锁

void two_locks() {
    std::scoped_lock lk(m1, m2);             // C++17：内部用免死锁算法同时锁两把
}

void manual() {                              // std::lock + adopt_lock 两段式（C++11 写法）
    std::unique_lock<std::mutex> lk1(m1, std::defer_lock);
    std::unique_lock<std::mutex> lk2(m2, std::defer_lock);
    std::lock(lk1, lk2);                     // 一次性加锁，失败则全部释放重试
    // ...
}
```

记忆要点：**默认 lock_guard；要配合 condition_variable、要中途 unlock/try_lock 才升级 unique_lock；同时拿多把锁一律 scoped_lock。**

### 1.3 锁粒度原则

| 原则 | 说明 |
| --- | --- |
| 临界区尽量短 | 只锁共享数据访问，慢操作（I/O、内存分配、回调）移出锁外 |
| 不要在持锁时调用未知代码 | 回调/虚函数可能反过来加锁 → 死锁 |
| 一把粗锁 vs 多把细锁 | 先用粗锁保证正确，profile 证明竞争后再拆 |
| 锁与数据绑定 | 一把锁明确保护哪几份数据，写进注释；避免"一把全局锁保护一切" |
| 避免锁中锁 | 临界区内再加锁是死锁温床；确有需要时纳入全局加锁顺序（见 2.2） |

### 1.4 互斥锁的底层原理：futex 与自旋

`std::mutex` 在 Linux 上封装的是 `pthread_mutex`，而 pthread_mutex 的核心是 **futex（fast userspace mutex）**——一套"用户态快路径 + 内核态慢路径"的混合机制：

```text
加锁 lock：
  ① 用户态原子指令 CAS（cmpxchg）尝试把锁状态 0(空闲) → 1(持有)
  ② 成功（无竞争）：直接返回，全程不进内核，约 10~20ns
  ③ 失败（已被持有）：执行 futex(FUTEX_WAIT) 系统调用，线程挂入等待队列、让出 CPU
解锁 unlock：
  ① 原子地把状态改回 0
  ② futex(FUTEX_WAKE) 唤醒等待队列中的一个（或多个）线程
```

关键推论：**无竞争时 mutex 只是一条原子指令，非常便宜；真正昂贵的是竞争失败后的系统调用与上下文切换（约 1~5μs 量级）。** 这决定了三种等待策略的取舍：

| 策略 | 机制 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 自旋等待 | while CAS 不空出让 CPU | 无上下文切换，唤醒延迟极低 | 空耗 CPU、单核下等于死等 | 临界区极短（几十 ns）、多核 |
| 让出执行 | `sched_yield()`/短暂 pause | 比阻塞轻 | 仍参与调度，竞争激烈时抖动 | 短暂重试 |
| 阻塞等待 | futex_wait 睡眠 | 不耗 CPU | 切换开销大、唤醒有延迟 | 临界区较长（μs 级以上） |

glibc 的 pthread_mutex 默认实现**自适应自旋（adaptive spin）**：竞争时先自旋很短一段时间，若锁仍未释放再真正睡入内核，兼顾两种场景。内核里的 `spinlock`、无锁队列里的 `while(!cas())` 则是纯自旋的代表——它们成立的前提是"持锁者一定在其他核上运行且很快释放"。

> 对比记忆：用户态原子（~ns）＜ 自旋（空转）＜ futex 阻塞/唤醒（~μs）＜ 线程创建（~数十 μs）。这也是线程池存在的根本原因之一，见《05-线程池与并发实战模式.md》。

### 1.5 加锁的常见陷阱

**陷阱 1：最令人头疼的语法解析（Most Vexing Parse）**

```cpp
void bad() {
    std::lock_guard<std::mutex>(mtx);   // 看起来加了锁，实际被 C++ 语法解析为
}                                       // 「一个名为 mtx 的形参的函数声明」！什么都没锁

void good() {
    std::lock_guard<std::mutex> lk(mtx);  // 给锁对象起名字，才是真正的变量定义
    std::lock_guard<std::mutex> lk2{mtx}; // 或 C++11 统一初始化花括号，彻底规避歧义
}
```

**陷阱 2：mutex 不可拷贝/移动**。`std::mutex` 既不可拷贝也不可移动，因此包含 mutex 的类默认拷贝构造会被删除；需要拷贝语义时要自行实现（通常先锁源对象再复制数据成员，mutex 本身不复制）。

**陷阱 3：const 成员函数里加锁**。const 方法不能修改普通成员，而加锁会修改 mutex 内部状态——必须把 mutex 声明为 `mutable`：

```cpp
class ThreadSafeCounter {
    mutable std::mutex mtx;   // const 读接口也要加锁
    int value = 0;
public:
    int get() const {
        std::lock_guard<std::mutex> lk(mtx);
        return value;
    }
};
```

**陷阱 4：锁了个寂寞——局部锁**。在函数内定义局部 mutex，等于每个线程进来各拿一把新锁，对共享数据毫无保护。锁对象的生命周期必须**覆盖且长于**被保护数据的所有访问路径（通常是类成员或全局静态对象）。

**陷阱 5：持锁期间做危险动作**：`new`/`malloc`（可能触发分配器慢路径甚至自己的锁）、调用虚函数或外部回调（可能反向加锁）、阻塞 IO、`join()` 等待另一个需要本锁的线程——都可能造成长时间持锁或死锁。

**陷阱 6：裸 lock/unlock 的异常泄漏**。`mtx.lock(); do_something_that_may_throw(); mtx.unlock();` 一旦中间抛异常，锁永远不释放。**永远使用 RAII 锁具**，这是 C++ 并发编程的铁律。

## 2. 死锁

### 2.1 四个必要条件

| 条件 | 含义 | 破坏方法 |
| --- | --- | --- |
| 互斥 | 资源同一时刻只能一个线程持有 | 不可破坏（锁的本质） |
| 持有并等待 | 拿着 A 等 B | 一次性申请全部锁（`std::scoped_lock`） |
| 不可剥夺 | 拿到的锁不能被强抢 | `try_lock_for` + 失败全部释放重试 |
| 循环等待 | A→B→C→A 环 | **固定全局加锁顺序**（最实用） |

四个条件同时成立才会死锁，因此破坏任意一个即可；工程上最可行的是破坏"循环等待"。

### 2.2 经典 ABBA 死锁

```cpp
// 线程 1                                   线程 2
std::lock_guard<std::mutex> a(mA);          std::lock_guard<std::mutex> b(mB);
std::lock_guard<std::mutex> b(mB);          std::lock_guard<std::mutex> a(mA);
//         线程1拿A等B，线程2拿B等A → 互相永久等待
```

避免策略表：

| 策略 | 写法 | 备注 |
| --- | --- | --- |
| 固定加锁顺序 | 约定"永远先锁 mA 再锁 mB"，或按 mutex 地址排序 | 简单可靠，团队约定要落到 code review |
| `std::scoped_lock` | `std::scoped_lock lk(mA, mB);` | 库内部用 try-lock + 退避算法规避顺序问题 |
| `std::lock` + defer | 见 1.2 `manual()` | C++11 下的等价物 |
| try_lock + 退避 | 拿不到第二把就释放第一把，随机延时后重试 | 破坏不可剥夺，注意避免活锁（见 2.4） |
| 缩小临界区 | 只在真正需要两把锁的窗口内持有 | 减小相遇概率，不根除 |

固定顺序在大型系统中的落地方式：给每把锁编号并画出**锁顺序图（lock ordering graph）**，代码评审时核对任何"锁中锁"路径都沿编号递增方向加锁，保证等待关系是一个偏序、不可能成环。

### 2.3 其他死锁形态

| 形态 | 说明 | 规避 |
| --- | --- | --- |
| **自死锁** | 同一线程对普通 mutex 连续 lock 两次，默认类型（PTHREAD_MUTEX_NORMAL）直接永久阻塞 | 重构锁边界（见 1.1），不要依赖 recursive_mutex |
| **锁顺序环** | A→B→C→A 的多线程多锁环，ABBA 的一般化 | 全局锁顺序 |
| **读写锁升级死锁** | 线程持读锁后想"升级"为写锁，而其他读者尚未释放，写锁要等所有读者释放——自己等自己 | C++ 标准库不支持锁升级；先显式释放 shared_lock，再重新取 unique_lock |
| **锁与 join 环** | 线程 A 持锁并 `join(B)`，B 恰好阻塞在同一把锁上 | join 前先释放锁 |
| **条件变量误用** | wait 时没持锁、或通知状态与锁不匹配导致永久等待 | 固定"同一把 mutex + 谓词 wait"范式，见《03-条件变量与异步任务.md》 |
| **遗忘解锁** | 异常路径或复杂分支漏掉 unlock | RAII 自动杜绝 |

### 2.4 活锁与饥饿

死锁不是并发停滞的唯一形态，三者要能区分：

| 概念 | 现象 | CPU 占用 | 本质 |
| --- | --- | --- | --- |
| **死锁 Deadlock** | 线程互相阻塞，全部睡死不动 | 接近 0 | 等待关系成环 |
| **活锁 Livelock** | 线程都在运行、不断重试，但状态来回横跳无法推进 | 可能很高 | 谦让/退避策略同步化 |
| **饥饿 Starvation** | 个别线程长期抢不到资源，其他线程正常 | 低 | 调度/排队不公平 |

活锁的经典例子：两个线程都用"try_lock 失败→全部释放→立刻重试"，且节奏完全一致，就会反复同时放弃、同时重试。破解手段是**随机退避（jitter/指数退避）**打破同步节奏，这与网络冲突退避是同一思想。

饥饿的典型场景：读写锁中读者不断到来导致写者无限延后；以及**优先级反转**——低优先级线程持锁，高优先级线程等锁，而中优先级线程长期抢占低优先级 CPU，导致高优先级被间接拖死。解法是**优先级继承（Priority Inheritance）**与**优先级天花板协议（Priority Ceiling）**，实时系统与 FreeRTOS 中的实现见《../09-嵌入式开发/04-中断系统与RTOS原理.md》。

### 2.5 死锁排查手段

线上进程"卡死不退出、CPU 却不高"时，按下面路径定位：

1. `gdb -p <pid>` attach 上去，`thread apply all bt` 打印全部线程栈；
2. 找到多个卡在 `__lll_lock_wait` / `futex` / `pthread_mutex_lock` 的线程，沿调用栈看它们各自**已经持有**、**正在等待**哪把锁；
3. 持锁线程的栈停在哪里——若它也卡在另一把锁上，即构成锁等待链，画出链条即可找到环的起点；
4. 无 GDB 时可用 `pstack <pid>` 或遍历 `/proc/<pid>/task/<tid>/stack` 快速看内核栈；
5. **预防优于救火**：开发期用 ThreadSanitizer、Valgrind helgrind/DRD 自动报告锁序环，用法见《05-线程池与并发实战模式.md》与 06-工程化与工具链对应篇目。

### 2.6 面试高频问题

1. **死锁的四个必要条件？如何破坏？**——互斥/持有并等待/不可剥夺/循环等待；工程上用固定加锁顺序破坏循环等待。
2. **lock_guard、unique_lock、scoped_lock 的区别？**——见 1.2 对比表，关键词：能否手动控制、能否移动、能否一次多锁。
3. **读写锁适用什么场景？有什么坑？**——读远多于写；写饥饿、读者计数开销，别滥用。
4. **mutex 可以拷贝吗？const 成员函数如何加锁？**——不可拷贝移动；`mutable std::mutex`。
5. **自旋锁和互斥锁的区别与选型？**——自旋不睡眠无切换开销但空耗 CPU，适合极短临界区与多核；互斥阻塞睡眠适合较长临界区；futex 是"先自旋后阻塞"的折中。
6. **无竞争时加解锁的代价？**——一条原子 CAS，约十几 ns；竞争失败才陷入内核。
7. **什么是活锁、饥饿、优先级反转？**——见 2.4。
