## 1. atomic 基本用法

| 操作 | 说明 |
| --- | --- |
| `a.load()` / `a.store(v)` | 原子读/写 |
| `a.exchange(v)` | 原子交换，返回旧值 |
| `a.fetch_add(1)` / `fetch_sub` 等 | 原子加减（还有 and/or/xor） |
| `a.compare_exchange_weak(expected, desired)` | CAS：相等则写入 desired 返回 true；不相等把当前值写回 expected 返回 false。**可能伪失败**（值相等也返回 false），必须放循环里 |
| `a.compare_exchange_strong(...)` | CAS 但不伪失败，一次性使用场景用它 |
| `a.is_lock_free()` | 是否真无锁（大于机器字长的类型可能退化为内部加锁） |

```cpp
#include <atomic>

std::atomic<int> counter{0};
counter.fetch_add(1, std::memory_order_relaxed);   // 纯计数器：relaxed 足够

// 自旋锁：acquire/release 配对（经典用法）
std::atomic<bool> locked{false};
void spin_lock() {
    while (locked.exchange(true, std::memory_order_acq_rel)) {  // 抢锁：成功拿到旧值 false
        while (locked.load(std::memory_order_relaxed)) { /* 自旋等对方放锁 */ }
    }
}
void spin_unlock() {
    locked.store(false, std::memory_order_release);  // 释放：临界区内的写全部"发布"出去
}

// CAS 循环：把 x 原子地乘 2（weak 可能伪失败，必须放循环里）
std::atomic<int> x{1};
int expected = x.load();          // 期望的当前值
int desired  = expected * 2;      // 想写入的新值
while (!x.compare_exchange_weak(expected, desired)) {   // 失败时 expected 被刷新为最新值
    desired = expected * 2;       // 基于最新值重算，继续重试
}
```

## 2. 六大内存序

| 内存序 | 保证什么 | 典型用途 |
| --- | --- | --- |
| `memory_order_relaxed` | 只保证本操作原子，**无任何顺序约束** | 统计计数器、事件计数 |
| `memory_order_consume` | 依赖顺序（标准实际按 acquire 处理，已不推荐） | 极少用，避免 |
| `memory_order_acquire` | 本操作**之后**的读写不能重排到它之前；能看到 release 之前的写 | 加锁端、读"已发布"数据 |
| `memory_order_release` | 本操作**之前**的读写不能重排到它之后 | 解锁端、发布数据 |
| `memory_order_acq_rel` | 读改写操作同时具有 acquire + release | CAS 循环中的比较交换 |
| `memory_order_seq_cst`（默认） | 以上全部 + 所有 seq_cst 操作存在**全局单一全序** | 默认；多变量一致性场景 |

## 3. Acquire-Release 配对

```text
线程 A（生产者）                                线程 B（消费者）
─────────────────────                          ─────────────────────
data = 42;              // ① 普通写
flag.store(true,        // ② release：①不许重排到②之后
          memory_order_release);
                                               while (!flag.load(memory_order_acquire));  // ③
                                               assert(data == 42);   // ④ 必然成立！

happens-before 链：① →(程序序) ② →(synchronizes-with) ③ →(程序序) ④
                   release 写 与 acquire 读 配对，建立起跨线程的可见性
```

| 组合 | 结果 |
| --- | --- |
| store(release) ↔ load(acquire) | 建立 synchronizes-with，release 前的写在 acquire 后可见 |
| store(relaxed) ↔ load(acquire) 等 | 无配对关系，不建 happens-before |
| 全用 relaxed | 只保证单个变量自身原子，其他变量的写入对读线程**不可见或乱序** |

## 4. 硬件内存模型与缓存一致性

> C++ 内存序不是抽象的语言游戏——它最终映射到 CPU 的内存屏障指令和缓存一致性协议。理解硬件能解释"为什么 acquire/release 在 x86 上几乎免费，在 ARM 上却有开销"。

### 4.1 MESI 缓存一致性协议

多核 CPU 每个核有私有 L1/L2 缓存，共享 L3 和主存。如果两个核同时缓存了同一缓存行（cache line，通常 64 字节），必须保证一致性——这就是 MESI 协议的职责。

MESI 是缓存行的四种状态首字母：

| 状态 | 含义 | 该核能否写 | 其他核副本 |
| --- | --- | --- | --- |
| **M**odified（已修改） | 该缓存行被本核修改，与主存不一致，本核是唯一拥有者 | 可直接写 | 其他核无有效副本（为 I） |
| **E**xclusive（独占） | 该缓存行与主存一致，且只有本核拥有 | 写前先变 M（无需通知其他核） | 其他核无副本 |
| **S**hared（共享） | 该缓存行与主存一致，可能多个核同时拥有 | 写前需发 Invalidate 让其他核副本失效 | 其他核可能有 S 副本 |
| **I**nvalid（无效） | 该缓存行内容无效，需要时重新从主存/其他核加载 | 必须先获取最新副本 | 无意义 |

状态转换的核心操作：

```text
核 A 读 X（X 不在 A 的缓存）：
  → 发 Read 请求到总线
  → 若其他核有 M 状态的 X：该核先写回主存，然后双方变 S
  → 若其他核有 E/S 状态的 X：双方变 S
  → 若无其他核有 X：A 获得 E 状态

核 A 写 X（X 当前为 S 状态）：
  → 发 Read-Invalidate（或 Invalidate）请求
  → 所有其他核的 X 副本变 I（无效）
  → A 的 X 变 M，然后写入
  → 这就是"伪共享"的根源：一个核写导致其他核的缓存行全部失效

核 A 写 X（X 当前为 E 状态）：
  → 无需总线事务，直接变 M 写入（最快路径）
```

> MESI 保证的是**缓存一致性**（cache coherence），即同一地址的多副本最终一致；它**不保证内存顺序**（memory consistency），即不同地址的操作在多核间的可见顺序。后者由内存模型（TSO/弱内存序）和内存屏障决定。

### 4.2 False Sharing 与 alignas(64) 优化

False sharing（伪共享）是 MESI 协议带来的最经典性能陷阱：**两个线程访问不同变量，但这些变量恰好在同一个 64 字节缓存行中**。一个线程的写会导致整个缓存行在其他核上失效，即使其他线程访问的是完全不同的变量——性能退化堪比锁竞争。

```cpp
#include <atomic>
#include <thread>
#include <vector>
#include <chrono>
#include <cstdio>

// ========== 反例：伪共享 ==========
struct BadCounters {
    std::atomic<int> a{0};   // 线程 1 只写 a
    std::atomic<int> b{0};   // 线程 2 只写 b
    // a 和 b 很可能在同一个 64 字节缓存行中！
    // 线程 1 写 a → 使线程 2 核上的缓存行失效 → 线程 2 写 b 时需重新加载
};

// ========== 正解：缓存行对齐隔离 ==========
struct alignas(64) GoodCounters {
    std::atomic<int> a{0};
    // 填充到 64 字节边界，确保 a 独占一个缓存行
    char padding[64 - sizeof(std::atomic<int>)];
    std::atomic<int> b{0};
    // b 也在下一个缓存行起始位置
};

// 更简洁的 C++17 写法：每个变量单独 alignas
struct AlignedCounters {
    alignas(64) std::atomic<int> a{0};
    alignas(64) std::atomic<int> b{0};
};

// 性能对比测试
template <typename Counters>
double benchmark() {
    Counters c;
    auto start = std::chrono::high_resolution_clock::now();
    std::jthread t1([&] { for (int i = 0; i < 10'000'000; ++i) c.a.fetch_add(1, std::memory_order_relaxed); });
    std::jthread t2([&] { for (int i = 0; i < 10'000'000; ++i) c.b.fetch_add(1, std::memory_order_relaxed); });
    // jthread 自动 join
    auto end = std::chrono::high_resolution_clock::now();
    return std::chrono::duration<double, std::milli>(end - start).count();
}

int main() {
    std::printf("伪共享版本: %.1f ms\n", benchmark<BadCounters>());
    std::printf("缓存行隔离: %.1f ms\n", benchmark<GoodCounters>());
    // 典型结果：伪共享比隔离慢 3~10 倍
    return 0;
}
```

| 优化手段 | 做法 | 适用场景 |
| --- | --- | --- |
| `alignas(64)` | 变量声明时指定 64 字节对齐 | 已知会被不同核频繁写的变量 |
| 显式 padding | 在变量间插入 `char pad[64]` | 需要精确控制布局的结构体 |
| 合并写 | 把频繁写的变量集中到一个核 | 生产者-消费者模式中索引分离 |
| 每线程副本 + 定期合并 | `thread_local` 计数器，结束时汇总 | 统计计数器（读多写少的最终汇总） |

> 检测伪共享：Linux `perf stat -e cache-misses,cache-references` 观察缓存失效率；或 Intel VTune 的 "False Sharing" 分析。经验法则：被不同核频繁写的原子变量，默认加 `alignas(64)`。

### 4.3 x86 TSO vs ARM 弱内存序

CPU 内存模型决定了**一个核的内存操作以什么顺序对其他核可见**。这是 C++ 内存序在硬件层面的映射基础。

**x86/x86_64 — TSO（Total Store Order）**：

x86 是强内存模型，规则近似：
- 存储操作（store）按程序顺序对其他核可见（Store→Store 不重排）
- 加载操作（load）按程序顺序执行（Load→Load 不重排）
- **Store 可以被后面的 Load 重排**（Store→Load 重排，这是 TSO 唯一允许的重排）
- 存储有 Store Buffer：写先进 store buffer，异步刷到缓存，读可以绕过 store buffer 读自己刚写的值

这意味着在 x86 上：
- `acquire` 和 `release` 几乎是**零开销**的（不需要额外屏障指令，CPU 硬件已保证大部分顺序）
- `seq_cst` 的 store 需要 `MFENCE` 或 `LOCK XCHG`（有开销）
- `relaxed` 和 `acquire/release` 生成的指令几乎一样

**ARM/RISC-V — 弱内存序（Weak Memory Ordering）**：

ARM 是弱内存模型，允许几乎所有重排：
- Load→Load 可重排
- Load→Store 可重排
- Store→Store 可重排
- Store→Load 可重排
- 多核间可见性完全由内存屏障指令（`DMB`/`DSB`/`ISB`）控制

这意味着在 ARM 上：
- `acquire` 需要 `LDAR`（load-acquire 指令）
- `release` 需要 `STLR`（store-release 指令）
- `seq_cst` 需要 `DMB ISH` 全屏障
- 每个内存序都有**真实的指令开销**

| 维度 | x86 TSO | ARM 弱内存序 |
| --- | --- | --- |
| Load→Load 重排 | 禁止 | 允许 |
| Store→Store 重排 | 禁止 | 允许 |
| Load→Store 重排 | 禁止 | 允许 |
| Store→Load 重排 | **允许**（唯一） | 允许 |
| acquire 开销 | ~0（硬件保证） | `LDAR` 指令 |
| release 开销 | ~0（硬件保证） | `STLR` 指令 |
| seq_cst 开销 | `MFENCE`/`LOCK XCHG` | `DMB ISH` 全屏障 |
| 典型平台 | 桌面/服务器 | 手机/嵌入式/苹果 Silicon |

> 实践启示：在 x86 上开发时，`relaxed` 和 `acquire/release` 性能差异不明显，容易写出"碰巧能跑"的代码；但同样的代码移植到 ARM（如苹果 M 系列、服务器 ARM）上可能出现微妙的可见性 bug。**正确做法是按语义选择内存序，而不是按当前平台的性能表现**——代码的可移植性比几个纳秒的优化更重要。

## 5. happens-before 形式化定义

C++ 内存模型的核心是 **happens-before** 关系：如果操作 A happens-before 操作 B，那么 A 的效果对 B 可见。这是一个**严格偏序**（传递、反对称、不自反）。

### 5.1 三条基本规则

**规则 1：程序序（Sequenced-before）**

同一线程内，按程序顺序，前面的操作 sequenced-before 后面的操作，因而也 happens-before。

```text
线程 A：
  data = 42;        // ①
  flag = true;      // ②
  ① sequenced-before ② ⟹ ① happens-before ②
```

**规则 2：同步（Synchronizes-with）**

一个线程的 release 操作 synchronizes-with 另一个线程对同一原子变量的 acquire 操作。

```text
线程 A（生产者）                          线程 B（消费者）
flag.store(true, release);   // ②       while (!flag.load(acquire));  // ③
                                          ② synchronizes-with ③
```

**规则 3：传递闭包（Transitive closure）**

如果 A happens-before B，且 B happens-before C，则 A happens-before C。

```text
完整链：
  ① (data=42) →(程序序) ② (flag store release) →(同步) ③ (flag load acquire) →(程序序) ④ (assert data==42)
  ⟹ ① happens-before ④
  ⟹ 线程 B 必然看到 data == 42
```

### 5.2 形式化定义

```text
定义（happens-before）：
  设 → 为 happens-before 关系，则 → 是满足以下条件的最小关系：

  (1) 若 A sequenced-before B，则 A → B
  (2) 若 A synchronizes-with B，则 A → B
  (3) 若 A → B 且 B → C，则 A → C

  即：→ = (sequenced-before ∪ synchronizes-with) 的传递闭包

定义（数据竞争）：
  两个操作 A 和 B 构成数据竞争，当且仅当：
  (1) A 和 B 作用于同一内存位置
  (2) 至少一个是写操作
  (3) A 和 B 来自不同线程
  (4) 既不存在 A → B，也不存在 B → A（没有 happens-before 关系）

  数据竞争 ⟹ 未定义行为（UB）
```

### 5.3 常见同步关系建立方式

| 操作对 | 建立 synchronizes-with 的条件 |
| --- | --- |
| `store(release)` → `load(acquire)` | load 读到了 store 写入的值（或后续 release 写入的值） |
| `mutex::unlock()` → `mutex::lock()` | lock 成功获取了 unlock 释放的锁 |
| `thread` 构造 → 线程函数首条操作 | 线程启动建立同步 |
| `thread::join()` 返回 → join 后的操作 | 线程结束建立同步 |
| `promise::set_value()` → `future::get()` 返回 | get 读到了 set_value 的结果 |
| `atomic::fetch_add(acq_rel)` | 读端 acquire + 写端 release，同时建立两个方向 |

> 关键直觉：happens-before 不是"时间上先发生"，而是"可见性保证"。两个操作可以在物理时间上 A 先于 B，但如果没有 happens-before 关系，B 仍然可能看不到 A 的效果——因为 CPU 缓存、store buffer、编译器重排都可能导致延迟可见。

## 6. 数据竞争与 UB

**定义**：两个以上线程访问**同一内存位置**，至少一个是写，且二者之间没有 happens-before 同步关系 → **数据竞争 → 未定义行为**。

| 常见误解 | 事实 |
| --- | --- |
| "没加锁顶多读到旧值" | 错。数据竞争是 **UB**：编译器可以假设无竞争做激进优化（寄存器缓存、重排、甚至删掉"不可能"的读），读到撕裂值、死循环、任意错乱都可能 |
| "volatile 能当同步用" | 错。`volatile` 只禁编译器缓存/重排该变量访问，**不生成内存屏障**，CPU 乱序照样发生。同步用 atomic/锁 |
| "int 赋值是原子的所以没竞争" | 错。即使单条指令原子，UB 来自**缺乏顺序保证**，不来自撕裂 |

检测工具（衔接《../06-构建与版本控制/01-构建工具GCC与CMake.md》的 sanitizer 与《../07-调试与测试/02-Valgrind内存检测.md》）：

| 工具 | 命令 | 说明 |
| --- | --- | --- |
| ThreadSanitizer (TSan) | `g++ -fsanitize=thread -g -O1 main.cpp && ./a.out` | 报告 "data race" 并给出两个线程的栈 |
| Helgrind | `valgrind --tool=helgrind ./a.out` | 详见《../07-调试与测试/02-Valgrind内存检测.md》 |

> 调试工具的深度使用（TSan 报告解读、helgrind/DRD 对比）详见《05-线程池与并发实战模式.md》调试节。

## 7. 快速参考卡片

### 7.1 内存序选型决策

| 场景 | 内存序 |
| --- | --- |
| 不知道选什么 | `memory_order_seq_cst`（默认，最安全） |
| 纯统计计数器（单变量、无跨变量依赖） | `memory_order_relaxed` |
| 读端"拿到已发布数据" | `memory_order_acquire` |
| 写端"发布数据" | `memory_order_release` |
| 读改写（CAS） | `memory_order_acq_rel` 或 `seq_cst` |
| 需要多变量全局一致顺序 | `seq_cst` |

### 7.2 必背范式

```cpp
// CAS 循环（weak 会伪失败，必须放 while）
int expected = a.load(std::memory_order_relaxed);
while (!a.compare_exchange_weak(expected, expected + 1,
                               std::memory_order_acq_rel));
```

```cpp
// 跨线程发布-消费（acquire/release 配对）
data = 42;                                   // ① 普通写
flag.store(true, std::memory_order_release); // ②
// 对端：while(!flag.load(std::memory_order_acquire)); 必见 data==42
```

### 7.3 工程要点

| 要点 | 做法 |
| --- | --- |
| 检测伪共享 | 频繁写的原子变量 `alignas(64)` 或 `thread_local` 计数后合并 |
| 找数据竞争 | `g++ -fsanitize=thread -g -O1` 跑 ThreadSanitizer |
| 缓存行大小 | x86/ARM 多为 64 字节 |

## 8. 常见坑

| 现象 | 根因 | 对策 |
| --- | --- | --- |
| CAS 偶尔不生效 | `compare_exchange_weak` 允许伪失败 | 必须放进 `while` 循环，失败时 expected 已被刷新为最新值 |
| 多线程读到旧值 | 以为 `relaxed` 能同步其他变量 | `relaxed` 只保单变量原子，跨变量可见性要用 acquire/release 配对 |
| 用 `volatile` 做同步 | 误以为 volatile 禁止 CPU 乱序 | volatile 只禁编译器重排，不发内存屏障；同步用 atomic/锁 |
| 单变量原子但还是 UB | 数据竞争的 UB 来自缺 happens-before，不是撕裂 | 访问共享变量一律加锁或建立 acquire/release 关系 |
| 两核各写一个计数器却很慢 | 两变量落在同一缓存行（false sharing） | `alignas(64)` 隔离或 `thread_local` 聚合 |
| x86 上好好的，ARM/M 系列上偶发崩溃 | x86 TSO 下乱序少，"碰巧能跑" | 按语义选内存序，别依赖当前平台；移植前用 TSan/ARM 复测 |
| 用了 `consume` | 该序实际实现退化为 acquire，且语义晦涩 | 用 acquire，别碰 consume |
| 大原子变量变慢/锁警告 | 超过机器字长的 atomic 内部退化为加锁 | 用 `is_lock_free()` 检查，必要时改用对齐的普通变量 + 锁 |
