## 1. 并发概述

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| 并发（concurrency） | 任务在时间段内交替推进，单核也可并发 | 单核跑 OS 多任务 |
| 并行（parallelism） | 任务在同一时刻物理同时执行，必须多核 | 8 核同时算矩阵分块 |

C++11 内存线程模型的意义：

| 时代 | 做法 | 问题 |
| --- | --- | --- |
| C++98/03 | 无语言级线程；用 pthread/Win32 API | 不跨平台；连 `int` 是否原子都没有语言保证 |
| C++11 起 | `std::thread` + `std::atomic` + **内存模型** | 标准首次定义了多线程下"什么行为有定义"（happens-before） |

并发适用场景：

| 场景 | 是否适合多线程 | 说明 |
| --- | --- | --- |
| CPU 密集计算（编解码、数值） | 适合（并行） | 核数上限收益 |
| I/O 密集（网络、磁盘） | 适合（并发掩盖延迟） | 线程数可大于核数 |
| 强依赖共享可变状态的逻辑 | 不适合 | 锁竞争吃掉收益，考虑重构 |
| 低频小任务 | 不适合 | 线程创建/切换开销占比过高 |

## 2. std::thread 基础（C++11）

### 2.1 创建线程的四种方式

```cpp
#include <thread>
#include <string>

void free_func(int n) {}

struct Task {
    void run(int n) {}
};

int main() {
    std::thread t1(free_func, 42);            // ① 普通函数 + 参数（参数被拷贝进线程内部存储）
    Task obj;
    std::thread t2(&Task::run, &obj, 42);     // ② 成员函数指针 + 对象指针
    std::thread t3([] { /* ... */ });         // ③ lambda（最常用）
    int captured = 1;
    std::thread t4([&captured] { captured = 2; });  // ④ 按引用捕获——见下方生命周期坑
    t1.join(); t2.join(); t3.join(); t4.join();
}
```

### 2.2 join vs detach

| 维度 | `join()` | `detach()` |
| --- | --- | --- |
| 语义 | 等待线程结束并回收 | 放手不管，线程变"守护"状态 |
| 对象状态 | join 后 thread 可复用（move 赋值） | detach 后 thread 不再代表任何线程 |
| 不调用任何一者的后果 | 析构时 `std::terminate()` 直接崩 | 同左 |
| 风险 | 忘 join 卡死主线程 | **对象生命周期**：线程还在跑，引用的局部对象已析构 → 悬垂 UB |

```cpp
void bad_detach() {
    int local = 42;
    std::thread t([&] { std::this_thread::sleep_for(std::chrono::seconds(1));
                        /* 用 local —— 此刻 local 已析构，UB */ });
    t.detach();          // 函数返回，local 消亡，线程仍在运行
}
```

> 准则：**优先 join；必须 detach 时，线程只能访问全局/静态或自持有（拷贝）的数据**。

### 2.3 jthread（C++20）

| 特性 | `std::thread` | `std::jthread`（C++20） |
| --- | --- | --- |
| 析构行为 | 未 join/detach → terminate | **自动 join**（RAII） |
| 取消机制 | 无 | 携带 `std::stop_token`，析构时先 `request_stop()` |

```cpp
#include <thread>

void worker(std::stop_token st) {
    while (!st.stop_requested()) {          // 协作式取消检查
        // 干活
    }
}
int main() {
    std::jthread jt(worker);                // 自动把内部 stop_token 传给 worker
    // ...
}                                           // jt 析构：request_stop() + join()
```

### 2.4 传参与杂项

| 要点 | 说明 |
| --- | --- |
| 参数默认按值拷贝 | 想传引用必须 `std::thread t(f, std::ref(x))`；想转移用 `std::move(obj)` |
| 传裸指针不转移所有权 | 指向的对象生命周期仍由你负责（最大坑） |
| `std::thread` 不可拷贝 | 只能 move；容器 `std::vector<std::thread>` 用 move 塞入 |
| `hardware_concurrency()` | 返回硬件并发数提示；**可能返回 0**（不可得），要兜底 |
| `std::this_thread::` | `get_id()` / `sleep_for()` / `sleep_until()` / `yield()` |

## 3. Linux 线程底层实现

> 本节聚焦 Linux 平台。`std::thread` 在 glibc/Linux 上底层就是 pthread + NPTL，理解底层能解释很多"为什么"：为什么 `std::mutex` 无竞争时不进内核、为什么线程创建有 ~10MB 虚拟地址开销、为什么 `thread_local` 访问几乎零成本。

### 3.1 clone 系统调用与 NPTL 线程实现

Linux 没有独立的"线程"系统调用，线程本质上是**与父进程共享地址空间的进程**，通过 `clone(2)` 创建：

```c
// clone 关键标志位（简化）
clone(CLONE_VM       // 共享地址空间（页表）
    | CLONE_FS       // 共享文件系统信息（cwd、umask）
    | CLONE_FILES    // 共享文件描述符表
    | CLONE_SIGHAND  // 共享信号处理表
    | CLONE_THREAD   // 放入同一线程组（共享 TGID，即 getpid() 返回值）
    | CLONE_SETTLS   // 设置 TLS 段基址
    , child_stack, ...);
```

| 维度 | 传统 fork 进程 | NPTL 线程（clone + CLONE_THREAD） |
| --- | --- | --- |
| 地址空间 | 独立（写时复制） | 共享（CLONE_VM） |
| PID/TGID | 各自独立 PID | 共享 TGID（`getpid()` 相同），各自有 TID（`gettid()`） |
| 信号 | 各自独立信号处理 | 共享信号处理，但信号可定向到具体线程 |
| 栈 | 独立分配 | 独立分配（默认 8MB，通过 `pthread_attr_setstacksize` 调整） |
| 调度实体 | 独立 task_struct | 独立 task_struct（内核不区分进程/线程，统一调度） |

NPTL（Native POSIX Threads Library）是 glibc 的现代线程实现，取代了历史上的 LinuxThreads。它的核心特征：

- **1:1 模型**：每个用户态线程对应一个内核 task_struct，调度由内核完成
- **线程组**：同组线程共享 TGID，`getpid()` 返回 TGID，`gettid()` 返回内核线程 ID
- **TLS 支持**：通过 `CLONE_SETTLS` 设置 `fs` 段寄存器基址（x86_64），实现高效线程局部存储

线程创建的开销来源：

| 开销项 | 典型值 | 说明 |
| --- | --- | --- |
| 栈虚拟地址预留 | 8MB | 仅预留 VA，不实际分配物理页（按需缺页） |
| 栈守护页 | 4KB | 栈底的不可访问页，用于栈溢出检测 |
| TCB（线程控制块） | ~数 KB | pthread 内部结构，含 TID、errno、TLS 等 |
| clone 系统调用 | ~数 μs | 进入内核创建 task_struct |
| 总计 | ~10-50 μs | 远大于线程池任务调度开销，故高频小任务用线程池 |

### 3.2 futex 原理与系统调用路径

futex（Fast Userspace muTEX）是 Linux 同步原语的基石。`std::mutex`、`std::condition_variable`、`std::semaphore` 在无竞争时完全在用户态完成，只有竞争时才陷入内核——这就是 futex 的核心设计。

**核心思想**：用一个用户态的 `int` 作为锁状态，原子操作修改它；只有当需要等待/唤醒时才调用 `futex(2)` 系统调用，让内核把等待线程挂起在该地址上。

```text
无竞争路径（纯用户态，纳秒级）：
  mutex::lock()
    → atomic 交换锁状态 0→1（成功）
    → 直接进入临界区（不进内核！）

有竞争路径（陷入内核，微秒级）：
  mutex::lock()
    → atomic 交换失败（锁已被持有）
    → futex(WAIT, &lock_state, 1)   // 内核检查值仍为1则挂起
    → （被唤醒后）重试 atomic 交换

mutex::unlock()：
  → atomic 置锁状态为 0
  → 若有等待者：futex(WAKE, &lock_state, 1)  // 唤醒一个
  → 若无等待者：直接返回（不进内核！）
```

futex 系统调用的关键操作：

| 操作 | 语义 |
| --- | --- |
| `FUTEX_WAIT` | 原子检查 `*addr == val`，相等则挂起当前线程在该 futex 上；不等则立即返回 `EAGAIN`（避免丢失唤醒） |
| `FUTEX_WAKE` | 唤醒最多 `val` 个等待在该 futex 上的线程 |
| `FUTEX_REQUEUE` | 把等待者从一个 futex 转移到另一个（用于条件变量优化） |
| `FUTEX_CMP_REQUEUE` | 带条件检查的 requeue |

> 关键细节：`FUTEX_WAIT` 的"检查值+挂起"是**原子**的——这是防止丢失唤醒的根本保证。如果先检查值再挂起（非原子），检查后挂起前对方发了 WAKE，就会永久睡死。

`std::condition_variable::wait` 的底层路径：

```text
cv.wait(lk, pred):
  while (!pred()) {
    lk.unlock()                        // 先放锁
    futex(WAIT, &cv_futex, ...)       // 挂起在条件变量的 futex 上
    lk.lock()                          // 被唤醒后重新拿锁
  }

cv.notify_one():
  futex(WAKE, &cv_futex, 1)           // 唤醒一个等待者
```

### 3.3 调度策略与优先级

Linux 线程调度由内核 `scheduler` 负责，主要有三类策略：

| 策略 | 类别 | 优先级范围 | 调度方式 | 典型用途 |
| --- | --- | --- | --- | --- |
| `SCHED_OTHER`（默认） | 普通（CFS） | 静态优先级 0，nice 值 -20~19 | 完全公平调度器，按权重分配 CPU 时间 | 绝大多数普通线程 |
| `SCHED_FIFO` | 实时 | 1~99（数字越大优先级越高） | 先入先出：高优先级抢占，同优先级按排队顺序，直到主动 yield/阻塞/被更高优先级抢占 | 硬实时任务、中断处理线程 |
| `SCHED_RR` | 实时 | 1~99 | 轮转：同 FIFO，但同优先级线程有时间片轮转 | 需要公平性的实时任务 |

```cpp
#include <pthread.h>
#include <sched.h>
#include <cstdio>

void set_realtime(pthread_t tid, int policy, int prio) {
    struct sched_param param;
    param.sched_priority = prio;
    int ret = pthread_setschedparam(tid, policy, &param);
    if (ret != 0) {
        // 常见失败：EPERM（无 CAP_SYS_NICE 权限）
        std::perror("pthread_setschedparam");
    }
}

// 查询当前线程调度属性
void print_sched() {
    int policy;
    struct sched_param param;
    pthread_getschedparam(pthread_self(), &policy, &param);
    std::printf("policy=%d (%s), prio=%d\n",
                policy,
                policy == SCHED_OTHER ? "OTHER" :
                policy == SCHED_FIFO  ? "FIFO"  :
                policy == SCHED_RR    ? "RR"    : "?",
                param.sched_priority);
}
```

> 注意：设置实时调度策略需要 `CAP_SYS_NICE` 能力（通常需要 root 或 `/etc/security/limits.conf` 配置）。实时线程如果写了死循环且不阻塞，会**独占 CPU 饿死所有普通线程**，包括 SSH 登录——使用时务必确保实时线程有阻塞点或 `sched_yield()`。

### 3.4 CPU 亲和性（pthread_setaffinity_np）

CPU 亲和性（affinity）控制线程允许在哪些 CPU 核上运行。绑定线程到特定核可以：
- 提高缓存命中率（减少线程迁移导致的缓存失效）
- 隔离关键任务（避免与其他进程争抢）
- 配合 NUMA 架构优化内存访问

```cpp
#include <pthread.h>
#include <sched.h>
#include <cstdio>
#include <unistd.h>

// 把当前线程绑定到指定 CPU 核
void pin_to_cpu(int cpu_id) {
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(cpu_id, &cpuset);
    int ret = pthread_setaffinity_np(pthread_self(), sizeof(cpu_set_t), &cpuset);
    if (ret != 0) std::perror("pthread_setaffinity_np");
}

// 把线程绑定到一组 CPU 核
void pin_to_cpus(const std::vector<int>& cpus) {
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    for (int c : cpus) CPU_SET(c, &cpuset);
    pthread_setaffinity_np(pthread_self(), sizeof(cpu_set_t), &cpuset);
}

// 查询当前线程运行在哪个核上
int current_cpu() {
    return sched_getcpu();  // 注意：返回值可能因调度立即变化
}

// 常见模式：主线程绑定到 CPU 0，worker 线程分别绑定到 CPU 1..N
int main() {
    pin_to_cpu(0);  // 主线程固定在 0 号核
    int n = std::thread::hardware_concurrency();
    std::vector<std::jthread> workers;
    for (int i = 1; i < n; ++i) {
        workers.emplace_back([i] {
            pin_to_cpu(i);
            // ... 工作负载
        });
    }
    return 0;
}
```

| 亲和性策略 | 适用场景 | 风险 |
| --- | --- | --- |
| 不绑定（默认） | 通用负载，内核自动平衡 | 线程迁移导致缓存失效 |
| 每线程绑定固定核 | CPU 密集、低延迟、性能敏感 | 负载不均时某核过载，其他核空闲 |
| 绑定到 NUMA 节点内的核 | 大内存访问、NUMA 架构 | 跨节点内存访问延迟高 |

> `pthread_setaffinity_np` 的 `_np` 后缀表示 "non-portable"，是 Linux 扩展。C++ 标准库没有亲和性接口，需要直接用 pthread（`std::thread::native_handle()` 可获取 pthread_t）。

### 3.5 TLS（线程局部存储）实现原理

线程局部存储让每个线程拥有独立的变量副本。C++ 提供了三种方式：

| 方式 | 标准/平台 | 作用域 | 特点 |
| --- | --- | --- | --- |
| `__thread` | GCC/Clang 扩展（非标准） | 全局/静态变量 | 只能用于 POD 类型，不能有构造/析构；访问最快 |
| `thread_local` | C++11 标准 | 全局/命名空间/类静态/局部静态 | 支持非 POD 类型，有构造/析构；首次访问时初始化 |
| `pthread_key_create` | POSIX | 运行时动态创建 | 最灵活，可注册 destructor；通过 `pthread_getspecific/setspecific` 访问 |

**x86_64 上的 TLS 实现——`fs` 段寄存器**：

Linux x86_64 用 `fs` 段寄存器指向当前线程的 TLS 区域。线程创建时，`clone(CLONE_SETTLS)` 设置 `fs.base`，之后 TLS 变量的访问通过段寄存器偏移完成，**不需要函数调用，是单条指令**：

```text
TLS 变量的内存地址 = fs.base + 变量在 TLS 块中的偏移量

汇编层面（x86_64）：
  mov %fs:0x28, %rax    // 读取 TLS 偏移 0x28 处的变量（典型为 stack canary）
  mov %eax, %fs:0x30    // 写入 TLS 偏移 0x30 处的变量
```

TLS 区域的布局（x86_64，简化）：

```text
高地址
  ┌─────────────────────┐
  │ 线程私有变量区       │  ← __thread / thread_local 变量
  │ (编译时确定偏移)     │
  ├─────────────────────┤
  │ TCB (pthread 内部)  │  ← fs.base 指向这里
  │   - tid             │
  │   - errno           │  ← errno 本质就是 TLS 变量！
  │   - stack_guard     │
  │   - ...             │
  └─────────────────────┘
低地址
```

> `errno` 为什么是线程安全的？因为它本质上就是一个 `__thread int`，每个线程独立一份。早期单线程时代 `errno` 是全局变量，多线程后改为 TLS。

`thread_local` 的延迟初始化：

```cpp
// 非 POD 类型的 thread_local：首次访问时才构造
thread_local std::string tls_str = "hello";  // 每个线程首次访问时构造自己的副本

// 函数内的 thread_local static：同样每线程一份，首次调用该线程时初始化
void func() {
    thread_local int counter = 0;  // 每个线程独立计数
    ++counter;
}
```

| 特性 | `__thread` | `thread_local` |
| --- | --- | --- |
| 支持非 POD 类型 | 否（编译错误） | 是 |
| 构造/析构 | 无 | 有（线程退出时析构） |
| 初始化时机 | 程序加载时（零初始化） | 首次访问时（动态初始化） |
| 访问开销 | 单条指令（最快） | 首次访问有初始化检查，之后同 `__thread` |
| 可移植性 | GCC/Clang 扩展 | C++11 标准 |
