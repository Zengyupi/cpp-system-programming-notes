## 1. 并发模型为什么这样演进（理解主线，别死记）

核心矛盾：**连接数越来越多，但绝大多数连接大部分时间在 "等"**（等网络、等对端），CPU 真正要算的时间很少。模型演进就是在不断降低 "等待一个连接" 所占用的资源。

| 模型            | 做法                           | 解决了什么             | 新的瓶颈                                                         |
| ------------- | ---------------------------- | ----------------- | ------------------------------------------------------------ |
| 多进程（每连接 fork） | accept 到连接就 fork 一个进程处理      | 隔离性强，一个进程崩了不影响别的  | 进程创建 / 切换重、地址空间独立难共享、上万连接扛不住                                 |
| 多线程（每连接一线程）   | 每连接一个线程，共享地址空间               | 比进程轻、共享数据方便       | 线程仍占栈内存（默认 8MB / 线程），上千线程切换与锁竞争严重                            |
| 线程池           | 固定数量线程复用                     | 控制线程数、避免无限创建      | 一个线程同时只能阻塞在一个连接上，连接数 ≫ 线程数时不够用                               |
| **IO 多路复用**   | 一个线程用 epoll 同时监听上万 fd，谁就绪处理谁 | 等待不占线程，单线程即可管海量连接 | 单线程用满一个核，业务计算重时需要配合多线程                                       |
| **Reactor**   | IO 多路复用 + 事件回调 + 线程池的标准化模式   | 高并发 IO 与多核业务的平衡   | 编程模型是异步回调，需要工程化封装                                            |
| Proactor      | 内核把 IO 做完再通知（异步 IO 完成事件）     | 连 "读写" 都不阻塞       | Linux 原生 aio 对网络支持弱，io\_uring 在补齐（见《../13-并发异步与组件/02-io_uring与异步IO.md》） |

> 关键认知：
>
> **epoll 让 "等待" 这件事从 "每连接一个线程" 变成 "一个线程统一等一批"**
>
> ，这是 C10K 的答案。但它只解决 IO 等待，业务该多线程还是多线程 —— 于是有了 "Reactor IO 线程 + 业务线程池" 的组合。

### 同步 / 异步、阻塞 / 非阻塞别混

* 阻塞 / 非阻塞描述 "**调用方在等结果时能不能干别的**"；同步 / 异步描述"**结果是谁把数据搬好的**"（自己 read 搬 = 同步，内核搬完通知应用 = 异步）。

* Reactor = **非阻塞 + 同步**（epoll 告知可读，应用自行 read）；Proactor/IOCP = **异步**（内核读完把完成事件丢给应用）。

## 2. Reactor 的三种形态与取舍

```text
事件源(fd) ──→ EventDispatcher(epoll_wait) ──→ 分发到对应 Handler 回调

                                                  │

                          单线程全做 / 丢给线程池 / 多个 Reactor 各管一组
```

| 形态                 | 结构                                                                    | 适用 / 代表                 |
| ------------------ | --------------------------------------------------------------------- | ----------------------- |
| 单 Reactor 单线程      | 一个线程完成 accept + 读写 + 业务                                               | 业务极快、无阻塞调用；Redis 6 之前   |
| 单 Reactor 多线程      | 一个 IO 线程收事件，业务丢线程池                                                    | IO 轻、业务有计算；中小并发         |
| **主从 Reactor 多线程** | mainReactor 只 accept，连接分给多个 subReactor，每个 subReactor 一个 IO 线程 + 可选线程池 | 高并发主流；Nginx/Netty/muduo |

**为什么要主从分离**：accept 是极低频操作，而已有连接的读写是高频；让一个主 Reactor 专门负责接入，多个 subReactor 平摊海量连接的读写，既避免单点成为瓶颈，又能让连接数随核数水平扩展。新连接接入后按轮询 / 最少负载分配给某个 subReactor，**此后该连接始终在同一个 IO 线程上处理，避免加锁**。

## 3. 事件循环（EventLoop）的关键机制

```cpp
class EventLoop {

    int epfd_;

    std::vector<struct epoll_event> events_;

    std::vector<Task> pending_;           // 其它线程投递来的任务

public:

    void loop() {

        while (running_) {

            int n = epoll_wait(epfd_, events_.data(), events_.size(), timeout_);

            for (int i = 0; i < n; ++i) handleEvent(events_[i]); // IO 回调

            doPendingTasks();             // 执行跨线程任务

            handleExpiredTimers();         // 处理到期定时器

        }

    }

};
```

三个必懂机制：

1. **one loop per thread**：每个 EventLoop 绑定一个线程，fd 的所有操作都在所属 IO 线程做，从而**无锁**；别的线程要操作这个连接，就把任务 "投递" 进它的队列。

2. **跨线程唤醒为什么用 eventfd**：IO 线程正阻塞在 `epoll_wait`，另一线程投递任务后必须把它 "叫醒"。早期用 socketpair 自管道，Linux 现在用 `eventfd`（一个 8 字节计数器，更轻、无方向问题），把它也注册进 epoll，写一字节即唤醒。

3. **事件循环里绝不能阻塞**：一次同步磁盘写、一次同步 DNS、一把拿不到的锁，都会卡住这个线程上的**所有**连接。阻塞操作必须丢业务线程池或改异步。

## 4. 定时器：服务器为什么离不开它

| 用途        | 说明                                     |
| --------- | -------------------------------------- |
| 心跳 / 空闲超时 | 连接对端掉电不发 FIN，靠定时器判定 "多久没数据就关闭"，防 fd 泄漏 |
| 协议超时      | 请求多久没响应则重传 / 断开                        |
| 定时任务      | 周期上报、统计、连接保活                           |

| 数据结构                  | 增 / 删 / 取最近到期       | 适用                           |
| --------------------- | ------------------- | ---------------------------- |
| 最小堆（priority\_queue）  | 增 O (logn)、取顶 O (1) | 连接数适中、实现简单，muduo 采用          |
| 红黑树（std::map/set）     | O(logn)             | 通用，内核定时器用它                   |
| **时间轮（Timing Wheel）** | 增 / 删 O (1)         | **海量连接的空闲检测**，每格一个链表，指针扫过即到期 |

时间轮思想：环形数组每格代表一个时间单位，任务挂在 "到期那格" 的链表上，指针每 tick 走一格，扫到的格子全部到期 ——**不用排序，所以 O (1)**。海量长连接踢死连接用它最合适。

## 5. 协议解析：本质是 "字节流分帧"

TCP 是无边界字节流（没有 "消息" 概念），服务器必须自己确定一条完整消息的边界，这就是半包 / 粘包问题的根源（原理与代码见 `02-网络协议与报文解析/08-抓包分析与手写报文解析.md`）。

### 5.1 三种定界方式

| 定界       | 例子                                        | 解析                         |
| -------- | ----------------------------------------- | -------------------------- |
| 固定长度     | 老式私有协议                                    | 收满 N 字节即一条                 |
| 分隔符      | HTTP 头以 `\r\n\r\n` 结束、Redis RESP 以 `\r\n` | 找分隔符                       |
| **长度字段** | Modbus TCP、Protobuf、自定义二进制                | 先读固定头拿 length，再收满 body（主流） |

### 5.2 HTTP 解析状态机

```text
REQUEST_LINE → HEADERS（逐行读，遇空行结束）→ BODY（按 Content-Length/chunked 读够）→ DONE
```

每次 recv 到数据追加到接收缓冲区，驱动状态机向前推进；不够一条就保留残包等下次，一次收到多条就循环切出。绝不能假设 "一次 recv 就是一条消息"。

### 5.3 设计自定义二进制协议（长连接网关常用）

```cpp
struct MsgHeader {        // 定长头，字段全部网络字节序（大端），结构体 #pragma pack(1)

    uint32_t magic;       // 魔数：快速识别是不是本协议/对齐错位

    uint16_t version;     // 版本：兼容演进

    uint16_t type;        // 消息类型（请求/响应/心跳）

    uint32_t length;      // body 长度，用于分帧

};
```

设计要点：**定长头 + 长度字段**最通用；魔数用于错位自检；版本号为了前后兼容；心跳包只有头没有 body。解析时先校验 "剩余字节 ≥ 头长"，再按 length 校验整包，任何越界都断开连接而不是崩溃。

## 6. 高性能手段的原理（知其所以然）

| 手段                        | 解决的问题 / 原理                                                                                     |
| ------------------------- | ---------------------------------------------------------------------------------------------- |
| 零拷贝 sendfile/mmap/splice  | 传统读文件再发送要 "磁盘→内核页缓存→用户态→内核 socket→网卡"4 次拷贝、多次上下文切换；sendfile 让数据在内核里直接从页缓存到 socket，省掉用户态来回拷贝与切换 |
| writev 聚合发送（gather write） | 包头和包体是两块内存，用一次 writev 拼着发出，避免先 memcpy 成一块、减少系统调用                                               |
| 池化（内存 / 线程 / 连接池）         | 复用资源，省掉反复 malloc、线程创建、TCP 握手的开销，见《../13-并发异步与组件/04-内存池与池化技术.md》                                            |
| CPU 亲和性绑核                 | 线程固定在某核，减少跨核迁移导致的 CPU cache 失效；主从 Reactor 各绑一个核                                                |
| 批量 / 捎带                   | 多个响应合并发送、ACK 捎带，降低系统调用与包数量                                                                     |
| 调内核参数                     | backlog/somaxconn、fd 上限、端口范围、tcp\_tw\_reuse，见《02-百万并发与TCP栈优化.md》                           |

### 一次响应的完整数据流（把全章串起来）

```cpp
网卡收包(DMA) → 内核协议栈 → socket 接收队列 → epoll_wait 返回可读

   → IO 线程 read 到接收缓冲 → 状态机切出完整消息

   → 丢业务线程池处理 → 结果投回 IO 线程

   → write 到发送缓冲（必要时 writev/零拷贝）→ 内核 → 网卡发出
```

## 7. 压测与性能指标

| 指标         | 含义 / 注意                                       |
| ---------- | --------------------------------------------- |
| QPS / TPS  | 每秒请求数 / 事务数；注意是否长连接、是否带业务逻辑，否则数字没有可比性         |
| 延迟分位       | **P50/P95/P99**，别只看平均 —— 长尾（GC、调度抖动、缺页）才是体验杀手 |
| 并发连接数      | 同时保持的连接数（C10K/C100K），区别于 QPS                  |
| 错误率 / 资源水位 | CPU、内存、fd、上下文切换（vmstat）、网卡是否打满                |

```bash
wrk -t8 -c1000 -d30s --latency http://127.0.0.1:8080/   # 多线程1000连接压30秒，输出分位延迟

ab -n 100000 -c 1000 http://127.0.0.1:8080/

# 压测要点：压测机和被测机分开、关掉无用日志、长连接、逐步加压找拐点而非一上来打满
```

## 8. 快速参考卡片

```cpp
演进主线：连接大多在等 → epoll 统一等待 → Reactor=非阻塞同步事件驱动 → +线程池用多核

形态：单Reactor单线程(Redis) / +线程池 / 主从(main只accept,sub管读写,连接绑定单线程免锁)

EventLoop：one loop per thread；跨线程用 eventfd 唤醒；循环内禁止阻塞

定时器：最小堆(通用)/时间轮(O(1),海量踢死连接)

分帧：固定长/分隔符/长度字段(主流)；接收缓冲+状态机，处理半包粘包

零拷贝：sendfile 省用户态拷贝与切换；writev 聚合；绑核减 cache 失效

压测：看 P99 不看平均，找拐点，长连接，压测机分离
```

## 9. 常见问题与坑

| 问题                             | 原因与解决                                           |
| ------------------------------ | ----------------------------------------------- |
| EventLoop 里做同步日志 / 同步 DNS，整体卡顿 | 阻塞操作丢线程池或改异步，保证 IO 线程非阻塞                        |
| 半包被当成完整消息解析                    | 按长度字段 / 分隔符切分，残包保留，禁止按 recv 次数定界                |
| 忽略 chunked 只认 Content-Length   | HTTP 两种定界都要支持                                   |
| 连接关闭没从 epoll 注销、没清定时器          | 统一的连接清理出口，避免野指针 / 泄漏                            |
| 多线程操作同一连接不加区分                  | 连接固定到所属 IO 线程，跨线程投递任务                           |
| 零拷贝用错场景                        | sendfile 只适合 "文件→socket" 且不需用户态改数据；要加工内容仍需 read |
| 压测 QPS 很高但线上延迟差                | 压测是短连接 / 空业务 / 同机；关注 P99、真实业务与网络                |
