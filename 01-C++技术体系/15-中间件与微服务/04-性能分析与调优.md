## 1. 性能分析方法论

### 1.1 五步法

```text
1. 明确目标（QPS / P99延迟 / 吞吐 / 资源占用 / 成本）
2. 建立基线（压测得到当前指标，记录环境与配置）
3. 定位瓶颈（CPU / 内存 / IO / 网络 / 锁，用工具测量而非猜测）
4. 针对性优化（先优化最大瓶颈，每次只改一个变量）
5. 验证效果（对比优化前后指标，回归测试确保无功能退化）
```

**黄金法则**：先测量，再优化。无数据支撑的优化多是盲目——"过早优化是万恶之源"（Knuth），但"不测量就优化"更糟。

### 1.2 性能指标

| 指标 | 含义 | 关注点 |
| --- | --- | --- |
| QPS/TPS | 每秒请求/事务数 | 吞吐量 |
| 延迟（Latency） | 请求响应时间 | P50/P90/P99/P999，**不要只看平均** |
| 吞吐（Throughput） | 单位时间处理的数据量 | MB/s、消息/s |
| CPU 使用率 | 用户态/内核态/IO等待 | user%高=计算密集，iowait%高=IO瓶颈 |
| 内存使用 | RSS/虚拟内存/swap | 内存泄漏、OOM |
| 并发数 | 同时处理的请求数 | 连接数、线程数 |

**为什么看 P99 而不是平均**：平均延迟可能很好（10ms），但 P99 可能很差（500ms）——用户体验由慢请求决定。优化目标通常是"P99 < 50ms"而非"平均 < 10ms"。

### 1.3 压测方法

| 要点 | 说明 |
| --- | --- |
| 压测环境 | 与生产一致（硬件、内核参数、数据量） |
| 渐进加压 | 从低负载开始，逐步增加，找到拐点 |
| 持续时间 | 至少 5~10 分钟，观察稳定性（内存泄漏、GC） |
| 记录配置 | 压测命令、参数、环境配置，保证可复现 |
| 客户端瓶颈 | 压测客户端本身可能成为瓶颈（CPU/端口/连接数） |

```text
# wrk HTTP 压测示例
wrk -t 16 -c 1000 -d 60s --latency http://localhost:8080/api
# -t 线程数 -c 并发连接数 -d 持续时间 --latency 打印延迟分布
```

## 2. 瓶颈定位

### 2.1 五大瓶颈类型

| 瓶颈 | 表现 | 定位工具 | 优化方向 |
| --- | --- | --- | --- |
| CPU | 单核/多核跑满，用户态高 | `perf top`、`top`、`htop` | 算法优化、减少拷贝、SIMD、并行 |
| 内存 | 内存持续上涨、swap、OOM | `valgrind`、`heaptrack`、`pmap` | 内存池、预分配、减少泄漏、大页 |
| 磁盘 IO | iowait 高、D 状态进程 | `iostat -x`、`iotop`、`dstat` | 异步 IO、批量写、SSD、零拷贝 |
| 网络 | 连接满、带宽打满、延迟高 | `ss`、`tcpdump`、`iftop` | 连接池、批量发送、压缩、协议优化 |
| 锁竞争 | 线程大量等待、sys%高 | `perf lock`、`pstack`、TSan | 缩小临界区、读写锁、无锁、分片 |

### 2.2 常用命令速查

```bash
top -H                    # 整体资源 + 线程视图
perf top -g               # CPU 热点函数（实时）
perf record -g ./server   # 采样 CPU 调用栈
perf report               # 查看采样结果
iostat -x 1               # 磁盘 IO（%util、await、r/s、w/s）
iotop                     # 进程级 IO
ss -s                     # 网络连接统计
ss -tanp                  # TCP 连接详情
free -h                   # 内存使用
vmstat 1                  # 系统整体（r、b、si、so、us、sy、wa）
pidstat 1                 # 进程级 CPU/内存/IO/上下文切换
```

### 2.3 瓶颈判断决策树

```text
CPU 高？
├─ user% 高 → 计算密集 → perf top 找热点函数 → 算法/拷贝/SIMD
├─ sys% 高 → 系统调用多 → strace/perf trace → 减少 syscall/批量
└─ iowait% 高 → IO 等待 → iostat → 磁盘/网络 IO 优化

内存高？
├─ RSS 持续涨 → 可能泄漏 → valgrind/heaptrack → 找泄漏点
├─ swap 使用 → 内存不足 → 加内存/优化内存占用
└─ 缓存命中率低 → 数据结构/访问模式 → 缓存友好优化

锁竞争？
├─ 线程状态多为 S(等待) → perf lock/pstack → 缩小临界区/读写锁/无锁
└─ 上下文切换频繁 → pidstat -w → 减少线程数/锁竞争
```

## 3. CPU 优化

### 3.1 优化手段

| 手段 | 说明 | 效果 |
| --- | --- | --- |
| 算法优化 | 降低时间复杂度（O(n²)→O(n log n)） | 数量级提升 |
| 减少拷贝 | 零拷贝、引用传递、移动语义 | 减少内存带宽占用 |
| 内联 | 热路径函数 `inline`/LTO | 消除函数调用开销 |
| 缓存友好 | 连续内存访问、按行遍历、数据结构紧凑 | 提升缓存命中率 |
| 分支预测 | 热路径减少分支、`[[likely]]`/`[[unlikely]]` | 减少分支预测失败 |
| SIMD | 向量化（SSE/AVX/NEON） | 数据并行，数倍提升 |
| 多线程 | 任务并行拆分 | 利用多核 |
| 编译优化 | `-O2/-O3`、`-march=native`、LTO/PGO | 编译器自动优化 |

### 3.2 缓存友好优化

CPU 缓存层次：L1（~1ns，32KB/核）→ L2（~4ns，256KB/核）→ L3（~10ns，共享几 MB）→ 内存（~100ns）。**缓存未命中的代价是命中的 100 倍**。

```cpp
// 反例：按列遍历二维数组（缓存不友好，每次跳一行）
for (int j = 0; j < n; ++j)
    for (int i = 0; i < n; ++i)
        a[i][j] = 0;      // 每次访问跳 n*sizeof(int) 字节，缓存行失效

// 正例：按行遍历（缓存友好，连续访问）
for (int i = 0; i < n; ++i)
    for (int j = 0; j < n; ++j)
        a[i][j] = 0;      // 连续内存，预取有效，缓存命中
```

**结构体对齐与填充**：热数据放在同一缓存行，冷数据分开；多线程写的变量用 `alignas(64)` 避免伪共享（详见《../13-并发异步与组件/06-无锁编程基础.md》）。

### 3.3 分支预测

现代 CPU 有分支预测器，预测失败时流水线清空（~15~20 周期惩罚）。

```cpp
// 热路径减少分支（C++20 属性语法）
if (condition) [[likely]] { ... }    // 告诉编译器这个分支更可能
if (error) [[unlikely]] { ... }      // 错误分支冷路径

// 用查表替代分支
int sign = (x > 0) - (x < 0);     // 无分支计算符号
```

### 3.4 SIMD 向量化

```cpp
// 编译器自动向量化（-O3 或 -O2 -ftree-vectorize）
void add_arrays(float* a, const float* b, int n) {
    for (int i = 0; i < n; ++i)
        a[i] += b[i];    // 编译器自动用 AVX 一次算 8 个 float
}

// 手动 SIMD（AVX2，一次处理 8 个 float）
#include <immintrin.h>
void add_avx(float* a, const float* b, int n) {
    for (int i = 0; i + 8 <= n; i += 8) {
        __m256 va = _mm256_loadu_ps(a + i);
        __m256 vb = _mm256_loadu_ps(b + i);
        _mm256_storeu_ps(a + i, _mm256_add_ps(va, vb));
    }
}
```

## 4. 内存优化

### 4.1 优化手段

| 手段 | 说明 |
| --- | --- |
| 内存池 | 预分配+复用，减少 malloc/free 开销和碎片（详见《../13-并发异步与组件/04-内存池与池化技术.md》） |
| 预分配 | `vector::reserve`、`string::reserve`，避免多次扩容拷贝 |
| 移动语义 | `std::move`、右值引用，减少深拷贝 |
| `string_view` | 只读字符串用 `std::string_view`，零拷贝 |
| 避免泄漏 | valgrind/ASan 定期检测，RAII 管理资源 |
| 大页（HugePage） | 2MB/1GB 页，减少 TLB miss，提升地址翻译速度 |
| 对象紧凑 | 减少结构体 padding，热字段放前面，用 `[[no_unique_address]]` |
| 减少临时对象 | 表达式模板、返回值优化（RVO/NRVO） |

```cpp
// 预分配避免扩容
std::vector<int> v;
v.reserve(10000);      // 预分配，避免多次扩容（每次扩容拷贝全部元素）

// string_view 零拷贝
void process(std::string_view sv) {  // 不拷贝字符串
    // 只读操作
}

// 移动语义
std::vector<int> get_large_vector() {
    std::vector<int> v(1000000);
    return v;    // NRVO 或 move，不拷贝
}
```

### 4.2 大页（HugePage）

TLB（Translation Lookaside Buffer）缓存虚拟地址→物理地址映射。默认 4KB 页，大内存工作集下 TLB miss 多。用 2MB 大页可减少 TLB miss。

```bash
# 查看大页配置
cat /proc/meminfo | grep Huge
# 配置大页数量
echo 1024 > /proc/sys/vm/nr_hugepages    # 1024 个 2MB 大页 = 2GB
# 应用通过 mmap(MAP_HUGETLB) 或 libhugetlbfs 使用
```

## 5. IO 优化

### 5.1 磁盘 IO

| 手段 | 说明 |
| --- | --- |
| 异步 IO | io_uring/libaio，不阻塞线程（详见《../13-并发异步与组件/02-io_uring与异步IO.md》） |
| 批量写 | 攒批后一次 write，减少系统调用 |
| 顺序写 | 追加写（append-only），磁盘顺序写比随机写快 1000 倍 |
| 零拷贝 | `sendfile`/`splice`，数据不经过用户态 |
| SSD | 替换机械盘，随机 IO 性能数量级提升 |
| 页缓存 | 利用内核页缓存，热数据读不打磁盘 |
| direct IO | 绕过页缓存，数据库等自管理缓存场景用 |

### 5.2 网络 IO

| 手段 | 说明 |
| --- | --- |
| 连接池 | 复用 TCP 连接，避免握手开销 |
| 批量发送 | 攒批（Nagle/应用层 batch），减少小包 |
| 压缩 | snappy/lz4/zstd 压缩，减少带宽 |
| 协议优化 | 二进制协议（Protobuf）替代文本（JSON） |
| 多路复用 | HTTP2/QUIC，一个连接多路并发 |
| 内核旁路 | DPDK/用户态协议栈，极致性能（详见《../13-并发异步与组件/03-用户态协议栈与DPDK.md》） |

### 5.3 零拷贝

传统 `read+write`：磁盘→内核缓冲区→用户缓冲区→内核 socket 缓冲区→网卡，4 次拷贝+4 次上下文切换。

`sendfile`：磁盘→内核缓冲区→socket 缓冲区→网卡，2 次拷贝（DMA），0 次用户态拷贝。

```cpp
// sendfile 零拷贝（文件→socket）
#include <sys/sendfile.h>
int fd = open("file.dat", O_RDONLY);
off_t offset = 0;
sendfile(sock_fd, fd, &offset, file_size);  // 内核直接拷贝，不进用户态
```

## 6. 锁优化

### 6.1 优化手段

| 手段 | 说明 |
| --- | --- |
| 缩小临界区 | 只保护必要的共享数据，IO/计算移出锁外 |
| 读写锁 | 读多写少用 `shared_mutex`，读并发 |
| 锁分片 | 把一把大锁拆成多把（如 16 把锁，按 key 哈希） |
| 无锁数据结构 | CAS 实现无锁队列/栈（详见《../13-并发异步与组件/06-无锁编程基础.md》） |
| 线程局部存储 | `thread_local`，避免共享 |
| 消息传递 | 用 SPSC 队列替代共享内存+锁（Actor 模型） |
| 乐观锁 | 版本号/CAS，读不加锁，写时校验 |

```cpp
// 锁分片：16 把锁，按 key 哈希分散
class ShardedMap {
    static constexpr int N = 16;
    std::unordered_map<int, std::string> maps_[N];
    std::mutex mtx_[N];
public:
    void set(int key, const std::string& val) {
        int idx = key % N;
        std::lock_guard<std::mutex> lk(mtx_[idx]);  // 只锁 1/16
        maps_[idx][key] = val;
    }
};
```

## 7. 火焰图分析

### 7.1 生成火焰图

```bash
# 1. 采样（99Hz 采样，避免与周期性任务锁频）
perf record -F 99 -g -p $(pidof server) -- sleep 30
# 2. 生成折叠栈
perf script | stackcollapse-perf.pl > out.folded
# 3. 生成火焰图 SVG
flamegraph.pl out.folded > flame.svg
# 4. 浏览器打开 flame.svg，点击可放大
```

### 7.2 怎么看火焰图

| 视觉特征 | 含义 |
| --- | --- |
| 横轴宽度 | 函数占用 CPU 时间比例（越宽越热） |
| 纵向 | 调用栈深度（底部是调用者，顶部是被调用者） |
| 平顶（plateau） | 函数本身消耗 CPU（不是子函数），是优化重点 |
| 宽底窄顶 | 调用开销大（函数调用本身耗时） |
| 颜色 | 随机（无特殊含义），有些工具按用户态/内核态/锁区分 |

**优化目标**：找最宽的平顶——那是真正消耗 CPU 的地方。优化后重新生成火焰图对比，看热点是否下降。

### 7.3 其他可视化

| 图类型 | 用途 |
| --- | --- |
| CPU 火焰图 | CPU 热点分析 |
| 内存火焰图 | 内存分配热点（heaptrack/massif） |
| 离线火焰图（off-CPU） | 阻塞/等待分析（线程不在 CPU 上的时间） |
| 差分火焰图 | 对比优化前后，红色=新增，蓝色=减少 |

## 10. 快速参考卡片

```text
方法论：定目标 → 建基线 → 定位瓶颈 → 优化 → 验证（每次只改一个变量）
看 P99 不看平均：用户体验由慢请求决定
CPU：perf top/火焰图找热点 → 算法/拷贝/缓存友好/SIMD/编译优化
内存：valgrind/heaptrack → 池/预分配/移动/大页/TLB
IO：iostat → 异步/批量/顺序/零拷贝/SSD
锁：perf lock/pstack → 缩小临界区/读写锁/分片/无锁
火焰图：看最宽的平顶（函数本身耗 CPU），不是看调用栈深度
零拷贝：sendfile 2次DMA拷贝，read+write 4次拷贝+4次切换
缓存层次：L1(1ns) → L2(4ns) → L3(10ns) → 内存(100ns)，未命中惩罚100倍
```

**常见坑与最佳实践：**
1. 未建立基线就优化，无法量化效果——先压测记录当前指标。
2. 只盯 CPU 忽略内存泄漏和 IO 等待——`vmstat` 看 wa%，`iostat` 看 %util。
3. 过度优化：局部微优化（如把 `i++` 改 `++i`）忽略架构级问题（如同步 IO 阻塞）。
4. 压测客户端本身成为瓶颈（端口耗尽、CPU 打满），结论失真——压测机与被压机分离，监控压测机资源。
5. 优化后未回归测试，引入新 bug（如无锁改造引入竞态）——每次优化后跑完整测试。
6. 只看平均延迟忽略 P99——平均 10ms 但 P99 500ms，用户体验很差。
7. 火焰图看错地方——看平顶（函数自身耗时），不是看宽底（调用开销）。
8. 用 `O0` 编译做性能测试——必须用 `-O2/-O3`，否则结论无意义。
9. 忽略编译器优化选项——`-march=native`、LTO、PGO 可能带来 20~50% 提升。
10. 优化后不记录对比——形成调优手册，下次遇到类似问题直接复用。
