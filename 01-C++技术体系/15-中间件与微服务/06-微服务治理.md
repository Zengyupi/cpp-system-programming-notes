## 1. 微服务架构

### 1.1 单体 vs 微服务

| 维度 | 单体架构 | 微服务架构 |
| --- | --- | --- |
| 部署 | 一个应用包 | 多个服务独立部署 |
| 扩展 | 整体扩展 | 按服务独立扩展 |
| 技术栈 | 统一 | 可异构（不同服务不同语言） |
| 故障影响 | 全局 | 隔离（一个服务挂不影响其他） |
| 开发协作 | 耦合高 | 团队独立，并行开发 |
| 运维复杂度 | 低 | 高（服务发现、配置、链路、监控） |
| 数据 | 共享数据库 | 每服务独立数据库 |
| 适用 | 小型项目、初期 | 中大型、团队多、业务复杂 |

### 1.2 微服务治理全景

```text
客户端 → API 网关（路由/鉴权/限流/熔断）
  → 服务 A（注册到注册中心）
    ├─ RPC/HTTP → 服务 B（从注册中心发现）
    ├─ MQ → 异步解耦
    ├─ 缓存（Redis）
    └─ DB（每服务独立）
横切关注点：
  注册中心（服务发现）、配置中心（动态配置）
  链路追踪（TraceId 串联）、监控告警（指标/日志）
  服务容错（限流/熔断/降级/隔离）
  分布式事务（最终一致）、幂等控制
```

| 治理能力 | 核心组件 | 解决的问题 |
| --- | --- | --- |
| 服务注册与发现 | Nacos/etcd/ZooKeeper/Consul/Eureka | 服务动态上下线，客户端找到服务端 |
| 配置管理 | Nacos/Apollo/Spring Cloud Config | 配置集中管理、动态刷新、环境隔离 |
| API 网关 | APISIX/Kong/Envoy/Spring Cloud Gateway | 统一入口、路由、鉴权、限流 |
| 服务容错 | Sentinel/Hystrix/Resilience4j | 限流、熔断、降级、隔离，防雪崩 |
| 链路追踪 | SkyWalking/Zipkin/Jaeger/OpenTelemetry | 调用链可视化，定位慢调用/故障 |
| 监控告警 | Prometheus+Grafana/ELK | 指标采集、日志聚合、告警 |
| 分布式事务 | Seata/TCC/可靠消息 | 跨服务数据一致性 |

## 2. 注册中心

### 2.1 核心机制

```text
服务提供者启动 → 注册到注册中心（IP+端口+元数据）
服务消费者启动 → 从注册中心拉取服务列表（缓存到本地）
注册中心 → 心跳检测提供者存活，下线不健康实例
服务列表变化 → 注册中心推送/消费者定时拉取更新
```

| 机制 | 说明 |
| --- | --- |
| 服务注册 | 提供者启动时注册，关闭时注销 |
| 心跳保活 | 提供者定期发心跳，超时未收到则下线 |
| 服务发现 | 消费者拉取/订阅服务列表 |
| 变更通知 | 服务列表变化时通知消费者（push 或 pull） |
| 健康检查 | 主动探测（TCP/HTTP）或被动心跳 |

### 2.2 主流注册中心对比

| 组件 | CAP 取向 | 一致性 | 健康检查 | 配置管理 | 语言 | 特点 |
| --- | --- | --- | --- | --- | --- | --- |
| ZooKeeper | CP | 强一致（ZAB） | 临时节点（会话断开自动删除） | 不支持 | Java | 老牌，Dubbo 默认，强一致但不可用时无法注册 |
| etcd | CP | 强一致（Raft） | 租约（lease）+ keepalive | 支持（KV） | Go | 轻量，K8s 原生，云原生首选 |
| Consul | CP | 强一致（Raft） | 主动探测（HTTP/TCP/gRPC） | 支持（KV） | Go | 多数据中心，DNS 接口 |
| Nacos | AP/CP 可切换 | 灵活（AP 临时实例/CP 持久实例） | 心跳+主动探测 | 支持（配置中心一体） | Java | 阿里开源，注册+配置一体，国内主流 |
| Eureka | AP | 最终一致 | 客户端心跳（自我保护机制） | 不支持 | Java | Netflix 开源，AP 高可用，已停更 |

**CP vs AP 选择**：
- CP（ZooKeeper/etcd）：注册中心不可用时，无法注册/发现新服务，但已有缓存可用。适合强一致要求高的场景。
- AP（Eureka/Nacos AP）：注册中心不可用时，仍可用本地缓存继续服务，可能拿到已下线实例。适合高可用要求高的场景。
- **生产推荐**：Nacos（国内生态好，注册+配置一体）或 etcd（云原生，K8s 集成好）。

### 2.3 服务发现模式

| 模式 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 客户端发现 | 消费者从注册中心拉列表，自己负载均衡选节点 | 灵活，可定制负载均衡策略 | 客户端逻辑重，多语言需各自实现 |
| 服务端发现 | 消费者请求负载均衡器（如 Nginx），由它转发 | 客户端简单 | 多一跳，负载均衡器可能成为瓶颈 |

Dubbo/gRPC 用客户端发现；K8s Service + kube-proxy 用服务端发现。

## 3. 配置中心

### 3.1 为什么需要配置中心

- 配置分散在各服务的配置文件中，修改需重启服务。
- 多环境（dev/test/prod）配置管理混乱。
- 配置变更无审计、无版本回滚。
- 敏感配置（密码、密钥）明文存储不安全。

### 3.2 主流配置中心

| 组件 | 特点 | 配置推送 | 版本管理 | 灰度发布 |
| --- | --- | --- | --- | --- |
| Nacos | 注册+配置一体，国内主流 | 长轮询推送 | 有 | 支持（按 IP/标签） |
| Apollo | 携程开源，功能最全，权限管理细 | 实时推送（HTTP 长轮询） | 有（版本+审计） | 支持（灰度+回滚） |
| Spring Cloud Config | Git 存储，Spring 生态 | 需配合 Bus（MQ）推送 | Git 自带 | 需自己实现 |
| etcd | KV 存储，轻量 | watch 机制实时通知 | 有（revision） | 需自己实现 |

**动态刷新**：配置变更后推送通知，服务热更新配置（如日志级别、限流阈值、开关），无需重启。C++ 服务可通过 etcd watch 或 Nacos 长轮询实现。

## 4. API 网关

### 4.1 网关职责

| 功能 | 说明 |
| --- | --- |
| 路由转发 | 按路径/域名/规则分发到后端服务 |
| 鉴权认证 | 统一 token/JWT/OAuth2 校验，后端无需重复实现 |
| 限流 | 令牌桶/漏桶/滑动窗口，保护后端 |
| 熔断降级 | 下游故障时快速失败，返回兜底结果 |
| 灰度发布 | 按比例/用户标签分流到新版本 |
| 日志监控 | 统一访问日志、指标采集、TraceId 注入 |
| 协议转换 | HTTP↔gRPC、WebSocket |
| CORS | 统一跨域处理 |

### 4.2 网关选型

| 网关 | 语言 | 性能 | 特点 |
| --- | --- | --- | --- |
| APISIX | Lua（OpenResty） | 极高 | 热更新、插件丰富、云原生、国产 |
| Kong | Lua（OpenResty） | 高 | 插件生态成熟、企业版功能全 |
| Envoy | C++ | 高 | 云原生、Service Mesh 数据平面、xDS 动态配置 |
| Nginx + Lua | C/Lua | 极高 | 灵活但需自己开发 |
| Spring Cloud Gateway | Java | 中 | Spring 生态集成好 |

## 5. 服务容错【高频】

### 5.1 服务雪崩

```text
服务 A 调用 B，B 调用 C
C 故障 → B 超时等待 → B 线程池被占满 → B 不可用
→ A 也超时等待 → A 线程池被占满 → A 不可用
→ 故障沿调用链扩散，整个系统崩溃（雪崩）
```

**容错四板斧**：限流、熔断、降级、隔离。

### 5.2 限流

| 算法 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 固定窗口 | 固定时间计数，超了拒绝 | 简单 | 边界突刺（窗口切换前后各打满） |
| 滑动窗口 | 窗口细化成小格，滚动计数 | 无突刺 | 需存储小格计数 |
| 漏桶 | 请求进桶，恒定速率流出 | 输出平滑 | 无法应对突发 |
| 令牌桶 | 恒定速率放令牌，请求取令牌 | 允许突发 | 实现稍复杂 |

**多级限流**：网关层限流（全局限流）→ 服务层限流（单服务限流）→ 资源层限流（DB 连接池/线程池）。

### 5.3 熔断（Circuit Breaker）

熔断器三态模型（类似电路保险丝）：

| 状态 | 说明 | 转换条件 |
| --- | --- | --- |
| Closed（关闭） | 正常调用，统计失败率 | 失败率超阈值 → Open |
| Open（打开） | 直接快速失败，不调用下游 | 超时时间到 → Half-Open |
| Half-Open（半开） | 放行少量请求试探 | 成功 → Closed；失败 → Open |

```text
请求进来 → 熔断器 Closed？
  ├─ 是 → 调用下游 → 成功/失败计数
  │         └─ 失败率 > 50% 且请求数 > 20 → 打开熔断器（Open）
  ├─ Open → 直接返回降级结果，不调用下游
  │         └─ 5 秒后 → Half-Open
  └─ Half-Open → 放行 1 个请求试探
            ├─ 成功 → Closed（恢复）
            └─ 失败 → Open（继续熔断）
```

**主流熔断器**：Sentinel（阿里，功能全）、Hystrix（Netflix，已停更）、Resilience4j（轻量，Java）、C++ 可自己实现或用 `folly::AsyncTimeout`。

### 5.4 降级（Degradation）

下游不可用时，返回兜底结果而非报错：

| 降级策略 | 说明 | 示例 |
| --- | --- | --- |
| 返回默认值 | 返回静态默认值 | 推荐接口故障时返回空列表 |
| 返回缓存 | 返回缓存的旧数据 | 商品详情故障时返回 Redis 缓存 |
| 简化逻辑 | 跳过非核心功能 | 下单时跳过积分计算，保证主流程 |
| 批量处理 | 同步改异步 | 写操作失败时写 MQ 异步重试 |

### 5.5 隔离（Bulkhead，舱壁模式）

| 隔离方式 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 线程池隔离 | 每个下游依赖独立线程池 | 故障隔离，一个依赖慢不影响其他 | 线程数多，上下文切换开销 |
| 信号量隔离 | 限制并发数（计数） | 轻量，无线程切换 | 无法排队，超限直接拒绝 |
| 资源隔离 | 独立部署/独立连接池 | 物理隔离最彻底 | 资源浪费 |

## 6. 链路追踪

### 6.1 核心概念

| 概念 | 说明 |
| --- | --- |
| Trace | 一次完整请求链路，唯一 TraceId |
| Span | 一次服务调用/方法调用，有 parent-child 关系 |
| Annotation | 事件标记（cs/sr/ss/cr：客户端发送/服务端接收/服务端发送/客户端接收） |
| Sampling | 采样，高并发下只记录部分请求（1%~100%） |

```text
TraceId: abc123
├─ Span1: 网关 → 订单服务 (10ms)
│   ├─ Span2: 订单服务 → 库存服务 (5ms)
│   └─ Span3: 订单服务 → 支付服务 (8ms)
│       └─ Span4: 支付服务 → 银行接口 (20ms)
```

### 6.2 主流链路追踪

| 组件 | 特点 | 语言 | 侵入性 |
| --- | --- | --- | --- |
| SkyWalking | APM 全链路，无侵入（Java agent），功能全 | Java 为主 | 低（agent 字节码增强） |
| Zipkin | Twitter 开源，轻量，专注链路 | 多语言 | 中（需埋点） |
| Jaeger | CNCF 项目，Uber 开源，云原生 | 多语言 | 中 |
| OpenTelemetry | CNCF 标准，统一埋点 SDK+采集器 | 多语言 | 中（标准化埋点） |

**C++ 服务接入**：用 OpenTelemetry C++ SDK 埋点，或在 RPC 框架中自动注入 TraceId（brpc 内置 trace）。TraceId 通过 HTTP header / RPC metadata 跨服务传递。

### 6.3 日志与 TraceId 关联

在日志中打印 TraceId，通过 TraceId 串联一次请求的所有服务日志——出问题时用 TraceId 搜日志，快速定位故障点。

```cpp
// C++ 日志中注入 TraceId
LOG_INFO("trace_id={} order_id={} process start", trace_id, order_id);
// 跨服务传递：HTTP header "X-Trace-Id" 或 RPC metadata
```

## 7. 幂等与分布式事务

### 7.1 幂等设计

微服务间调用因网络重试、超时重发、MQ 重复投递等，同一请求可能执行多次。**所有写操作必须幂等**。

| 幂等方案 | 说明 | 适用 |
| --- | --- | --- |
| 唯一 ID + 去重表 | 请求带唯一 ID，处理前查去重表 | 通用 |
| 数据库唯一索引 | 利用唯一约束，重复插入报错即跳过 | 插入操作 |
| 乐观锁版本号 | UPDATE ... WHERE version=N，影响行数=0 即重复 | 更新操作 |
| 状态机 | 状态单向流转（待支付→已支付），重复请求不改变 | 订单/流程 |
| token 机制 | 先申请 token，处理时校验并删除 token | 防表单重复提交 |

### 7.2 分布式事务

| 方案 | 一致性 | 性能 | 业务侵入 | 适用 |
| --- | --- | --- | --- | --- |
| 2PC/XA | 强一致 | 低（阻塞） | 低 | 数据库层面，传统企业 |
| TCC | 最终一致 | 中 | 高（Try/Confirm/Cancel 三接口） | 资金、库存 |
| SAGA | 最终一致 | 高 | 中（补偿事务） | 长流程业务 |
| 本地消息表 | 最终一致 | 高 | 中 | 已有 DB，异步场景 |
| 事务消息（RocketMQ） | 最终一致 | 高 | 低 | 已有 RocketMQ |
| Seata AT | 最终一致 | 中 | 低（自动补偿） | Java 生态，阿里开源 |

深入原理见《../14-内核云原生与分布式/04-分布式系统与一致性.md》。

## 8. Service Mesh（服务网格）

### 8.1 理念

把服务治理（服务发现、负载均衡、熔断、限流、链路追踪、安全）从应用代码中**剥离**到 Sidecar 代理（Envoy），应用无感知。

```text
Pod 内：
  应用容器（业务代码，无治理逻辑）
    ↑↓ localhost
  Sidecar 代理（Envoy，处理所有治理逻辑）
    ↑↓ 网络
控制平面（Istio Pilot）：下发配置（服务列表、路由规则、限流策略）
```

### 8.2 优缺点

| 优点 | 缺点 |
| --- | --- |
| 业务代码无侵入，治理逻辑统一 | 多一跳（Sidecar），延迟增加 1~5ms |
| 多语言统一治理（C++/Go/Java 一致） | 资源开销（每个 Pod 多一个 Sidecar 容器） |
| 动态配置，运行时调整策略 | 运维复杂度高（需懂 Istio/Envoy） |
| 安全（mTLS 自动加密） | 调试困难（流量经过 Sidecar） |

**适用场景**：多语言微服务、大规模集群、对治理一致性要求高。小团队/单语言可先用 SDK 模式（Sentinel/Dubbo）。

### 8.3 主流 Service Mesh

| 项目 | 数据平面 | 控制平面 | 特点 |
| --- | --- | --- | --- |
| Istio | Envoy | Istiod | 功能最全，行业标准，复杂 |
| Linkerd | linkerd2-proxy（Rust） | 自带 | 轻量，简单，CNCF 毕业 |
| Kuma | Envoy | 自带 | 多网格，Kong 出品 |

## 9. 快速参考卡片

```text
微服务治理：注册中心 + 配置中心 + 网关 + 容错 + 链路追踪 + 分布式事务
注册中心：CP(ZooKeeper/etcd/Consul) vs AP(Eureka/Nacos)，Nacos 国内主流
配置中心：Nacos/Apollo，动态刷新无需重启
网关：APISIX/Kong/Envoy，路由+鉴权+限流+熔断+灰度
容错四板斧：限流(令牌桶) + 熔断(三态Closed/Open/HalfOpen) + 降级(兜底) + 隔离(线程池/信号量)
熔断：失败率超阈值→Open快速失败→超时后HalfOpen试探→成功恢复
链路追踪：Trace(一次请求) → Span(一次调用)，TraceId 串联日志
幂等：唯一ID+去重表 / 唯一索引 / 乐观锁版本号 / 状态机
Service Mesh：Sidecar(Envoy) 剥离治理逻辑，多语言统一，Istio 主流
```

**常见坑与最佳实践：**
1. 熔断阈值设置过严（失败率 30% 就熔断），正常网络抖动误触发——阈值设 50%+，最小请求数 20+，熔断时间 5~30 秒。
2. 未做幂等，重试导致重复扣款/下单——所有写操作必须幂等（唯一 ID+去重表或乐观锁）。
3. 服务下线未从注册中心注销（kill -9），消费者调用失败——注册中心心跳超时自动下线，客户端有失败重试+剔除机制。
4. 配置中心动态刷新未处理好，配置不一致（部分实例更新了部分没更新）——配置推送有确认机制，灰度发布按比例。
5. 限流算法选错（固定窗口），边界瞬间 2 倍流量打垮下游——用滑动窗口或令牌桶。
6. 链路追踪采样率设太高（100%），高并发下存储和网络压力大——生产用 1%~10% 采样，出错时动态调高。
7. 分布式事务用 2PC 导致长时间锁表，性能极差——互联网场景用最终一致（TCC/SAGA/消息），只在资金核心用强一致。
8. 网关层做了太多业务逻辑，变成"上帝服务"和单点——网关只做横切关注点，业务逻辑放后端服务。
9. 服务间同步调用链路过长（A→B→C→D），一个慢服务拖垮全链路——异步化（MQ）+ 超时+熔断+降级。
10. 忽略可观测性（监控/日志/链路），出问题只能靠猜——上线前必须接入监控（Prometheus）、日志（ELK）、链路（SkyWalking/Jaeger），设置告警。
