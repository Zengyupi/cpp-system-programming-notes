## 1. 消息队列（MQ）

### 1.1 为什么用 MQ

| 作用 | 说明 | 典型场景 |
| --- | --- | --- |
| 解耦 | 生产消费异步，系统松耦合 | 订单创建后通知库存/物流/积分，新增消费方不改订单代码 |
| 削峰填谷 | 缓冲瞬时高峰流量 | 秒杀 10 万 QPS 打进来，下游按 1 万 QPS 匀速消费 |
| 异步 | 非关键路径异步处理 | 用户注册后发欢迎邮件/送积分，接口立即返回 |
| 广播 | 一对多通知 | 配置变更广播到所有服务实例 |
| 可追溯 | 消息持久化，可重放 | 数据同步、事件溯源 |

### 1.2 主流 MQ 对比

| 维度 | RabbitMQ | Kafka | RocketMQ | Pulsar |
| --- | --- | --- | --- | --- |
| 吞吐 | 万级（~1-5万/s） | 百万级（~100万+/s） | 十万级（~10万+/s） | 百万级 |
| 延迟 | 亚毫秒~毫秒 | 毫秒级（攒批） | 毫秒级 | 毫秒级 |
| 消息模型 | 队列（消费即删）+ 交换机路由 | 日志（可重复消费，pull） | 日志（pull）+ 事务消息 | 分层存储（计算/存储分离） |
| 顺序性 | 单队列单消费者 | 单分区内有序 | 单队列有序 | 单分区有序 |
| 事务消息 | 不支持 | 支持（Kafka 事务） | 原生支持（半消息+回查） | 支持 |
| 延迟消息 | 插件支持 | 不原生支持 | 原生支持（18个级别） | 支持 |
| 协议 | AMQP | 自定义二进制 | 自定义 | 多协议兼容 |
| 适用 | 业务消息、复杂路由、RPC | 日志、埋点、流处理、大数据 | 电商交易、金融、事务 | 云原生多租户、存算分离 |

**选型一句话**：业务消息+复杂路由选 RabbitMQ；日志/流处理/高吞吐选 Kafka；电商事务/延迟消息选 RocketMQ；云原生多租户选 Pulsar。

### 1.3 核心概念

| 概念 | 说明 |
| --- | --- |
| Producer | 生产者，发送消息 |
| Consumer | 消费者，消费消息 |
| Broker | MQ 服务节点 |
| Topic/Queue | 消息主题/队列，逻辑分类 |
| Partition | 分区（Kafka），并行消费单位，分区内有序 |
| Consumer Group | 消费组，组内分摊消息（竞争消费），组间各自独立消费 |
| Offset | 消息在分区内的位置（Kafka） |
| ACK | 确认，消费者处理完后通知 Broker |

### 1.4 消息可靠性三环节【高频】

| 环节 | 丢失风险 | 解决方案 |
| --- | --- | --- |
| 生产端 | 发出去没到 Broker（网络抖动） | 确认机制（Kafka acks=all、RabbitMQ Publisher Confirm）、重试 |
| 存储端 | Broker 收到未落盘就宕机 | 持久化（队列+消息持久化）、多副本（Kafka replication.factor≥3） |
| 消费端 | 收到但处理失败/崩溃 | 手动 ack（处理完再确认）、失败重试、死信队列 |

**端到端不丢配置（Kafka 示例）**：
- 生产端：`acks=all` + `retries=Integer.MAX_VALUE` + `enable.idempotence=true`
- Broker：`replication.factor=3` + `min.insync.replicas=2` + `unclean.leader.election.enable=false`
- 消费端：`enable.auto.commit=false`，处理成功后手动 `commitSync`

### 1.5 重复消费与幂等

MQ 通常保证 at-least-once（至少一次），消息可能重复。消费者必须**幂等**：同一消息处理多次结果一致。

| 幂等方案 | 说明 | 适用 |
| --- | --- | --- |
| 唯一 ID + 去重表 | 消息带唯一 ID，处理前查去重表，已存在则跳过 | 数据库操作 |
| 数据库唯一索引 | 利用唯一约束，重复插入报错即跳过 | 插入操作 |
| 乐观锁版本号 | UPDATE ... WHERE version=N，影响行数=0 即重复 | 更新操作 |
| 状态机 | 状态只能单向流转（待支付→已支付），重复请求不改变状态 | 订单/流程 |
| Redis SETNX | 用消息 ID 做 key，SETNX 成功才处理 | 轻量去重 |

### 1.6 消息顺序性

- **全局有序**：只能单分区+单消费者，吞吐极低，很少需要。
- **局部有序**：同一业务 key 的消息进同一分区（Kafka 按 key 路由），单消费者消费该分区——同 key 有序，不同 key 并行。
- **乱序容忍**：大多数业务可容忍乱序，用版本号/时间戳去重即可。

## 2. 缓存（Redis）

### 2.1 缓存三大问题【高频】

| 问题 | 现象 | 原因 | 解决方案 |
| --- | --- | --- | --- |
| 缓存穿透 | 查询不存在的数据，请求直达 DB | 缓存中没有，每次都查 DB | 布隆过滤器（拦截不存在的 key）、空值缓存（短 TTL） |
| 缓存击穿 | 热点 key 过期瞬间，大量请求直达 DB | 热点 key 过期，重建缓存期间并发打 DB | 互斥锁（只让一个线程重建）、逻辑过期（不设 TTL，异步更新） |
| 缓存雪崩 | 大量 key 同时过期，或 Redis 宕机，DB 压力骤增 | 批量 key 同时间过期 / 缓存服务不可用 | 过期时间加随机值、多级缓存、Redis 高可用（哨兵/集群）、限流降级 |

```cpp
// 缓存击穿：互斥锁重建（简化版）
std::string get_with_lock(const std::string& key) {
    std::string val = redis_get(key);
    if (!val.empty()) return val;
    // 缓存未命中，尝试加锁
    std::string lock_key = "lock:" + key;
    if (redis_set(lock_key, "1", "NX", "EX", 10)) {  // SET NX EX 加锁
        val = db_query(key);          // 只有一个线程查 DB
        redis_set(key, val, "EX", 300);
        redis_del(lock_key);
    } else {
        std::this_thread::sleep_for(std::chrono::milliseconds(50));
        return get_with_lock(key);    // 等待后重试读缓存
    }
    return val;
}
```

### 2.2 缓存一致性

缓存与数据库双写时，如何保证一致性？

| 方案 | 流程 | 一致性 | 说明 |
| --- | --- | --- | --- |
| 先删缓存再更库 | 删缓存 → 更 DB | 有并发风险 | 删缓存后、更 DB 前，有读请求把旧值写回缓存 |
| 先更库再删缓存 | 更 DB → 删缓存 | 推荐，最终一致 | 并发窗口极小（读旧缓存+写新DB+删缓存同时发生概率极低） |
| 延迟双删 | 删缓存 → 更 DB → 延迟再删缓存 | 更可靠 | 解决先删缓存方案的并发问题，延迟时间=读业务逻辑耗时 |
| 订阅 binlog | 更 DB → Canal 监听 binlog → 删缓存 | 最终一致 | 业务代码无侵入，可靠但引入组件 |

**推荐方案**：先更库再删缓存（Cache Aside Pattern），配合延迟双删兜底。

```text
推荐流程：
1. 读：先读缓存，命中返回；未命中查 DB，写入缓存，返回
2. 写：先更新 DB，再删除缓存（不是更新缓存）
3. 为什么删而不是更：并发写时更新缓存可能被旧值覆盖，删更简单安全
```

### 2.3 缓存模式

| 模式 | 说明 | 适用 |
| --- | --- | --- |
| Cache Aside（旁路缓存） | 应用同时管理缓存和 DB，读缓存未命中查 DB 并回填 | 最常用，读多写少 |
| Read Through | 应用只读缓存，缓存层负责从 DB 加载 | 缓存层封装好 |
| Write Through | 应用写缓存，缓存层同步写 DB | 写性能要求一般 |
| Write Behind（异步写） | 应用写缓存，缓存层异步批量写 DB | 写多、可容忍短暂不一致 |

## 3. API 网关

### 3.1 网关职责

| 职责 | 说明 |
| --- | --- |
| 路由转发 | 按路径/域名/规则分发到后端服务 |
| 鉴权认证 | 统一 token/JWT/OAuth2 校验，后端无需重复实现 |
| 限流 | 令牌桶/漏桶/滑动窗口，保护后端 |
| 熔断降级 | 下游故障时快速失败，返回兜底结果 |
| 日志监控 | 统一访问日志、指标采集、链路追踪（TraceId） |
| 灰度发布 | 按比例/用户标签分流到新版本 |
| 协议转换 | HTTP↔gRPC、WebSocket 等 |
| CORS/跨域 | 统一处理跨域请求 |

### 3.2 限流算法

| 算法 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 固定窗口 | 固定时间内计数，超了拒绝 | 简单 | 边界突刺（窗口切换前后各打满） |
| 滑动窗口 | 把窗口细化成小格，滚动计数 | 无边界突刺 | 实现稍复杂，需存储小格计数 |
| 漏桶 | 请求进桶，恒定速率流出 | 输出平滑 | 无法应对突发（桶满即拒绝） |
| 令牌桶 | 恒定速率往桶里放令牌，请求取令牌 | 允许突发（桶里有令牌就能发） | 实现稍复杂 |

**令牌桶 vs 漏桶**：令牌桶允许突发流量（桶里攒了令牌可以一次性用），漏桶输出速率恒定（不允许突发）。API 网关通常用令牌桶（允许合理突发）。

```cpp
// 令牌桶简化实现
class TokenBucket {
    std::mutex mtx_;
    double tokens_;           // 当前令牌数
    double capacity_;         // 桶容量
    double rate_;             // 每秒生成速率
    std::chrono::steady_clock::time_point last_;
public:
    TokenBucket(double cap, double rate) : tokens_(cap), capacity_(cap), rate_(rate),
        last_(std::chrono::steady_clock::now()) {}
    bool try_acquire(double need = 1.0) {
        std::lock_guard<std::mutex> lk(mtx_);
        auto now = std::chrono::steady_clock::now();
        double elapsed = std::chrono::duration<double>(now - last_).count();
        tokens_ = std::min(capacity_, tokens_ + elapsed * rate_);  // 补充令牌
        last_ = now;
        if (tokens_ >= need) { tokens_ -= need; return true; }
        return false;
    }
};
```

## 4. RPC 框架

### 4.1 RPC vs HTTP

| 维度 | RPC | HTTP/REST |
| --- | --- | --- |
| 协议 | 自定义二进制（TCP/HTTP2） | 文本（JSON over HTTP） |
| 序列化 | Protobuf/Thrift/msgpack | JSON |
| 性能 | 高（二进制紧凑、HTTP2 多路复用） | 较低（文本冗余、TCP 连接开销） |
| 接口定义 | IDL（.proto/.thrift） | 无强制（OpenAPI/Swagger） |
| 服务发现 | 内置（注册中心） | 需额外实现 |
| 适用 | 内部微服务间调用 | 对外 API、浏览器端 |

### 4.2 RPC 核心流程

```text
客户端 Stub（本地代理，看起来像调本地函数）
  ↓ 序列化请求（Protobuf/Thrift）
  ↓ 服务发现（注册中心取服务端地址列表）
  ↓ 负载均衡（选一个节点）
  ↓ 连接管理（连接池/HTTP2 多路复用）
网络传输 ────────────────────────> 服务端
                                      ↓ 反序列化
                                      ↓ 路由到具体方法
                                      ↓ 执行业务逻辑
                                      ↓ 序列化响应
客户端 Stub <──────────────────────── 网络传输
  ↓ 反序列化响应
  ↓ 返回给调用方（看起来像本地函数返回）
```

### 4.3 主流 RPC 框架

| 框架 | 语言 | 序列化 | 特点 |
| --- | --- | --- | --- |
| gRPC | 多语言 | Protobuf | Google 开源，HTTP2，流式通信，云原生主流 |
| Apache Thrift | 多语言 | Thrift | Facebook 开源，轻量，跨语言 |
| Dubbo | Java | Hessian2/Protobuf | 阿里开源，Java 生态，服务治理完善 |
| brpc | C++ | Protobuf | 百度开源，C++ 高性能，工业级 |
| Tars | C++ | Tars | 腾讯开源，多语言，一体化框架 |

**C++ 后端推荐**：brpc（百度开源，工业级，性能极佳）或 gRPC（云原生主流，多语言互通好）。

### 4.4 RPC 关键组件

| 组件 | 说明 |
| --- | --- |
| 序列化 | Protobuf（推荐，紧凑高效）、Thrift、msgpack、FlatBuffers |
| 传输 | TCP（自定义协议）、HTTP2（gRPC，多路复用+头部压缩） |
| 注册中心 | 服务注册与发现（etcd/Nacos/ZooKeeper/Consul） |
| 负载均衡 | 客户端负载均衡（轮询/随机/一致性哈希/最少连接） |
| 超时重试 | 调用超时、失败重试（注意幂等）、熔断 |
| 连接池 | 复用 TCP 连接，避免握手开销 |
| 拦截器 | 鉴权、日志、监控、链路追踪（AOP 思想） |

## 5. 中间件协作架构

```text
客户端 → API网关（鉴权/限流/路由）
  → 服务A（业务逻辑）
    ├─ RPC → 服务B
    ├─ MQ → 异步任务（发邮件/通知）
    ├─ 缓存（Redis）→ 热点数据
    └─ DB（MySQL）→ 持久化
  → 服务C
    └─ 搜索引擎（ES）→ 复杂查询
横切：配置中心、注册中心、链路追踪、监控告警、日志收集
```

## 6. 快速参考卡片

```text
MQ：解耦+削峰+异步；RabbitMQ(业务路由) / Kafka(高吞吐日志) / RocketMQ(事务)
MQ可靠性：生产confirm + Broker持久化多副本 + 消费手动ack
重复消费：必须幂等（唯一ID+去重表 / 唯一索引 / 乐观锁 / 状态机）
缓存三问题：穿透(布隆/空值) 击穿(互斥锁/逻辑过期) 雪崩(随机TTL/多级缓存)
缓存一致：先更库再删缓存（Cache Aside）+ 延迟双删兜底
网关：路由+鉴权+限流(令牌桶)+熔断+日志+灰度
RPC：序列化(Protobuf)+传输(HTTP2/TCP)+注册中心+负载均衡+超时重试
C++ RPC：brpc(工业级高性能) / gRPC(云原生多语言)
```

**常见坑与最佳实践：**
1. 消费者自动 ack，业务处理失败消息仍被确认导致丢失——关自动提交，处理成功后手动 ack。
2. 未做幂等，消息重复消费产生脏数据（重复扣款/下单）——所有消费端必须幂等。
3. 缓存删除与数据库更新非原子，出现不一致窗口——用先更库再删缓存+延迟双删。
4. 固定窗口限流边界瞬间突刺（窗口切换前后各打满 2 倍流量）——用滑动窗口或令牌桶。
5. RPC 未设置超时与重试上限，下游慢时线程池被占满导致雪崩——设置合理超时（P99×2），重试上限 2~3 次，配合熔断。
6. 缓存 key 设计不合理（大 key、热 key）——大 key 拆分，热 key 本地缓存+多副本。
7. MQ 消费者处理逻辑阻塞 poll 线程（Kafka），导致 rebalance——处理逻辑放线程池，poll 线程只负责拉取。
8. 网关层做了太多业务逻辑，变成"上帝服务"——网关只做横切关注点（鉴权/限流/路由），业务逻辑放后端服务。
9. RPC 调用用同步阻塞，高并发下线程数爆炸——用异步调用（Future/回调）或协程。
10. 中间件版本不兼容（Protobuf 字段编号复用、Kafka 客户端版本不匹配 Broker）——字段编号用 reserved 保护，客户端版本与 Broker 配套。
