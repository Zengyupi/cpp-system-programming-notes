测试样例（后续复用）：

```cpp
// demo.c
#include <stdio.h>
int g_counter = 42;
static int helper(int x){ return x * 2; }
int add(int a, int b){ return helper(a + b); }
int main(void){ printf("sum=%d\n", add(1, 2)); return 0; }
```
```bash
gcc -g -O0 -c demo.c -o demo.o      # 编译为可重定位目标文件（未链接）
gcc demo.o -o demo_app              # 链接为可执行文件
```

## 0. 分析路线图：什么时候用哪个选项

```text
拿到一个 ELF（.o / 可执行 / .so / .a）
│  先看是什么平台、有没有符号     -f（file 格式/架构） file 命令
│  看有哪些段、各多大             -h（section 表）
├─ 想看代码怎么编译的 ────────── -d -M intel（反汇编） + -S -l（混源码，需 -g）
├─ 想看符号/函数在哪 ────────── -t（普通符号） -T（动态符号） -C（C++ 还原）
├─ 想看链接怎么填地址 ───────── -r（.o 重定位） -R（GOT 动态重定位）
├─ 想看某段原始字节 ─────────── -s -j 段名
└─ 崩溃地址翻译到源码行 ─────── addr2line -e app -f -C 地址
```

## 1. 基本调用与选项总表

```bash
objdump [选项] 目标文件(.o / 可执行文件 / .so / .a 静态库)
```

| 选项 | 作用 | 常用度 |
| --- | --- | --- |
| `-f` | **文件头**（架构、标志、入口地址） | ★★★ |
| `-h` | **段表**（各 section 大小/VMA/偏移/标志） | ★★★ |
| `-x` | 全部头信息（≈ `-f -h -t -r` 合集） | ★★ |
| `-p` | 程序头/动态段（看 NEEDED 依赖库） | ★★ |
| `-d` | **反汇编**所有含机器码的段（.text） | ★★★★★ |
| `-D` | 反汇编**所有**段（含 .data/.rodata） | ★★ |
| `-M intel` | **Intel 语法**（默认 AT&T） | ★★★★★ |
| `-S` | 反汇编与 **C/C++ 源码混排**（需 `-g`） | ★★★★ |
| `-l` | 插入**源码文件:行号**（需 `-g`） | ★★★ |
| `-j 段名` | 只处理指定段（`.text`/`.plt`/`.rodata`） | ★★★ |
| `-t` / `-T` | 普通符号表 / **动态**符号表 | ★★★ |
| `-r` / `-R` | 静态重定位表 / 动态重定位(GOT) | ★★★ |
| `-s` | 十六进制 **dump 段完整内容** | ★★★ |
| `-C` | **demangle**，还原 C++ 修饰名 | ★★★★ |
| `-a` | 静态库(.a)归档成员 | ★★ |
| `-g` / `--dwarf=` | DWARF 调试信息 | ★ |

> 选项可叠加：`objdump -d -M intel -S -l demo.o`（Intel + 源码 + 行号）。

## 2. 前置：ELF 常见段

| 段 | 内容 |
| --- | --- |
| `.text` | 机器指令 |
| `.rodata` | 只读数据（字符串字面量、const，`"sum=%d\n"` 在这） |
| `.data` | 初值非 0 的全局/静态变量（`g_counter=42`） |
| `.bss` | 未初始化/零初始化的全局静态变量，不占文件、加载清零 |
| `.plt`/`.got(.plt)` | 动态链接过程链接表/全局偏移表（调 printf 走这里） |
| `.symtab`/`.strtab` | 符号表/字符串表（strip 后删除） |
| `.dynsym`/`.dynstr` | 动态符号表（运行时需要，strip 也保留） |
| `.rela.*` | 重定位表（.o 里记录待填地址的位置） |
| `.debug_*` | 加 `-g` 才有的 DWARF 调试信息 |

## 3. 看头部信息

### 3.1 `-f` 文件头

```bash
$ objdump -f demo.o
demo.o:     file format elf64-x86-64
architecture: i386:x86-64, flags 0x00000011:
HAS_RELOC, HAS_SYMS
start address 0x0000000000000000
```

- `file format elf64-x86-64`：格式与架构。**交叉编译后用它确认是否目标平台**（ARM64 应是 `elf64-littleaarch64`，若仍是 x86-64 说明工具链用错）。
- `.o` 未链接故 `HAS_RELOC`、入口为 0；可执行文件这里是真正的 `_start` 入口。

### 3.2 `-h` 段表

```bash
$ objdump -h demo.o
Idx Name          Size      VMA               LMA               File off  Algn
  0 .text         00000069  0000000000000000  0000000000000000  00000040  2**0
                  CONTENTS, ALLOC, LOAD, RELOC, READONLY, CODE
  1 .data         00000004  0000000000000000  0000000000000000  000000ac  2**2
                  CONTENTS, ALLOC, LOAD, DATA
```

| 列/标志 | 含义 |
| --- | --- |
| Size | 段字节数（`.data`=4 正好一个 int） |
| VMA/LMA | 运行虚拟地址/加载地址；`.o` 未重定位全 0，链接后才有真实地址 |
| File off / Algn | 文件内偏移 / 对齐（`2**2`=4 字节） |
| CODE/DATA/READONLY/RELOC/ALLOC | 代码/数据/只读/含重定位/需加载进内存 |

### 3.3 `-p` 看动态依赖

```bash
objdump -p demo_app | grep NEEDED     # NEEDED libc.so.6，等价 ldd / readelf -d
```

## 4. 反汇编（最高频）

### 4.1 `-d -M intel`

```bash
$ objdump -d -M intel demo.o
0000000000000012 <add>:
  12:	f3 0f 1e fa          	endbr64
  16:	55                   	push   rbp
  17:	48 89 e5             	mov    rbp,rsp
  1a:	48 83 ec 08          	sub    rsp,0x8
  1e:	89 7d fc             	mov    DWORD PTR [rbp-0x4],edi   # a 入栈（System V: a=edi,b=esi）
  21:	89 75 f8             	mov    DWORD PTR [rbp-0x8],esi
  24:	8b 55 fc             	mov    edx,DWORD PTR [rbp-0x4]
  27:	8b 45 f8             	mov    eax,DWORD PTR [rbp-0x8]
  2a:	01 d0                	add    eax,edx                   # a+b
  2c:	89 c7                	mov    edi,eax                   # 结果作 helper 参数放 edi
  2e:	e8 cd ff ff ff       	call   0 <helper>                # 未链接，先占位，靠重定位修正
  33:	c9                   	leave
  34:	c3                   	ret
```

三列分别是：**文件内偏移 ｜ 机器码原始字节 ｜ 汇编助记符**。

> 这段同时印证了 x86-64 System V 调用约定：整型参数依次走 `rdi,rsi,rdx,rcx,r8,r9`（这里 `add(a,b)` 的 a 在 edi、b 在 esi），返回值在 eax。更多约定见《../02-系统原理/03-系统架构与选型.md》。

### 4.2 AT&T vs Intel 语法

objdump 默认 AT&T，和 Intel 语法操作数顺序、符号写法相反：

| 维度 | AT&T（默认） | Intel（`-M intel`，推荐） |
| --- | --- | --- |
| 操作数顺序 | 源在前目的在后：`mov %edi,%eax` | 目的在前源在后：`mov eax,edi` |
| 寄存器/立即数 | `%rbp`、`$0x8` | `rbp`、`0x8` |
| 内存 | `-4(%rbp)` | `[rbp-4]` |
| 宽度 | 指令后缀 `movl/movq` | `DWORD PTR/QWORD PTR` |

> Linux 内核/GCC 原生输出多为 AT&T；Intel 手册、Windows/逆向资料多为 Intel。固定 `-M intel` 更顺手。

### 4.3 `-S/-l` 源码混排、`-j` 限定段

```bash
gcc -g -O0 demo.c -c -o demo.o          # 需 -g；学习对照用 -O0（-O2 会重排/内联导致错位）
objdump -d -M intel -S -l demo.o
objdump -d -M intel -j .text demo.o                       # 只看 .text
objdump -d -M intel demo_app | sed -n '/<add>:/,/ret/p'   # 只抠 add 函数
```

## 5. 符号表：`-t` / `-T` / `-C`

### 5.1 `-t` 普通符号

```bash
$ objdump -t demo.o
0000000000000000 l    df *ABS*  0000000000000000 demo.c
0000000000000000 l     F .text  0000000000000012 helper      # l=local(static), F=函数
0000000000000000 g     O .data  0000000000000004 g_counter   # g=global, O=数据对象, 大小4
0000000000000012 g     F .text  0000000000000023 add
0000000000000035 g     F .text  0000000000000034 main
0000000000000000         *UND*  0000000000000000 printf      # UND=未定义，外部库提供
```

| 标志 | 含义 |
| --- | --- |
| `l`/`g` | local（static 内部链接）/ global（外部可见） |
| `F`/`O`/`d` | 函数 / 数据对象 / section 符号 |
| `*UND*` | **未定义**：本文件引用但不定义，链接时从别的 .o/.so 解析（printf） |

### 5.2 `-T` 动态符号与符号版本

```bash
$ objdump -T demo_app | grep -E 'printf|GLIBC'
0000..  DF *UND*  .. (GLIBC_2.2.5)  printf
0000..  DF *UND*  .. (GLIBC_2.34)  __libc_start_main
```

> 看 `.so` 导出接口、程序依赖的外部符号及 **GLIBC 版本**。"高版本编译、低版本运行报 `version GLIBC_2.34 not found`"的根因就在这。

### 5.3 `-C` 还原 C++ 修饰名

```cpp
$ g++ -c cpp.cpp -o cpp.o       # namespace ns { class Widget { void run(int); } }
$ objdump -t cpp.o | grep run
... _ZN2ns6Widget3runEi                       # name mangling，难读
$ objdump -t -C cpp.o | grep run
... ns::Widget::run(int)                      # -C 直接 demangle
```

> 链接报 `undefined reference to _ZN...` 时，用 `-C` 或 `c++filt` 还原，立刻看出是哪个类、哪个签名没实现或不匹配。

## 6. 重定位与动态链接

### 6.1 `-r`：.o 的静态重定位

```bash
$ objdump -r demo.o
RELOCATION RECORDS FOR [.text]:
OFFSET           TYPE              VALUE
0000000000000048 R_X86_64_PLT32    add-0x4       # 调 add，PLT 相对寻址
0000000000000051 R_X86_64_PC32     .rodata-0x4   # 引用字符串字面量（PC 相对）
000000000000005e R_X86_64_PLT32    printf-0x4    # 调外部 printf
# （-g 时还有大量 .debug_* 重定位，分析代码可忽略）
```

这解释了 4.1 里 `call 0 <helper>` 为何是占位：**链接前地址未知，重定位表记录"在哪个偏移、用什么方式、填哪个符号"，链接器据此回填**。

| 常见类型(x86-64) | 含义 |
| --- | --- |
| `R_X86_64_PC32` | 相对 PC 的 32 位偏移（同模块数据/函数） |
| `R_X86_64_PLT32` | 相对 PC、经 PLT 调用（常为外部函数） |
| `R_X86_64_32/_64` | 绝对 32/64 位地址 |
| `R_X86_64_GOTPCREL` | 经 GOT 间接访问全局数据 |

### 6.2 PLT/GOT 延迟绑定流程（理解动态链接）

第一次调用外部函数 `printf` 的过程：

```text
call printf@plt
   │
   ▼
.plt 桩 ──首次──► 跳到 .got.plt 里存放的地址（首调指向解析器 resolver）
   │                                        │
   │                                  动态链接器用符号名查到 printf 真实地址
   │                                        │ ① 回填 .got.plt[n] = printf 真地址
   │◄───────────────────────────────────────┘ ② 跳转过去执行
   ▼ 第二次调用：.plt 桩直接从已回填的 GOT 取地址，一步到位，不再解析
```

```bash
objdump -d -M intel -j .plt demo_app   # 看 PLT 桩
objdump -R demo_app                    # GOT 待解析/已解析的外部符号
```

> 好处：① 延迟绑定，启动时不解析全部符号，加快启动；② 支持共享库位置无关（PIC），GOT 集中存放可重定位地址。

## 7. `-s` dump 段字节（验证字节序/初值）

```bash
$ objdump -s -j .data demo.o
Contents of section .data:
 0000 2a000000                             *...
```

- `g_counter = 42 = 0x2a`，`.data` 里按**小端**存为 `2a 00 00 00`，与《03-二进制查看工具.md》看到的内存字节互证：objdump 告诉你"哪个变量"，hexdump 给你"原始字节"。
- `-s -j .rodata` 可看到字符串字面量 `"sum=%d\n"` 的 ASCII 存储与结尾 `00`。

## 8. 静态库与交叉编译

### 8.1 `-a` 静态库

```bash
$ ar rcs libdemo.a demo.o
$ objdump -a libdemo.a
In archive libdemo.a:
demo.o:     file format elf64-x86-64
rw-r--r-- 0/0 4328 Jan 1 08:00 1970 demo.o
```

`.a` 是多个 `.o` 的归档，`objdump -d libdemo.a` 逐个成员反汇编。

### 8.2 交叉编译：objdump 跟架构绑定

分析 ARM/RISC-V 目标必须用对应交叉版，否则架构识别/反汇编错误：

```text
aarch64-linux-gnu-objdump -f board.elf        # ARM64，先 -f 确认 elf64-littleaarch64
arm-linux-gnueabihf-objdump -d firmware.elf   # ARM32（elf32-littlearm）
riscv64-linux-gnu-objdump -d app.elf          # RISC-V
```

> 嵌入式/工业网关开发第一步：`xxx-objdump -f` 核对架构与大小端，避免"x86 程序误拷到 ARM 板、exec format error"。

## 9. binutils 家族分工

| 工具 | 最擅长 | 典型命令 |
| --- | --- | --- |
| `objdump` | **反汇编**、综合查看 | `objdump -d -M intel a.o` |
| `readelf` | 专解 **ELF**，比 objdump 更原始权威（不经 BFD），详见《05-readelf工具.md》 | `readelf -h/-l/-S/-d a.out` |
| `nm` | 轻量列符号（地址+类型 U/T/B/D） | `nm -C a.out \| grep func` |
| `strings` | 提取可打印字符串 | `strings -a bin \| grep -i ver` |
| `size` | 快速看 text/data/bss 大小 | `size a.out` |
| `addr2line` | **地址→源码文件:行号**（崩溃定位） | `addr2line -e a.out -f -C 0x4012ab` |
| `c++filt` | 单独 demangle | `echo _ZN2ns6Widget3runEi \| c++filt` |
| `strip` | 删符号/调试信息瘦身 | `strip --strip-unneeded lib.so` |
| `ar` | 管理静态库 | `ar t lib.a`（列成员） |
| `ldd` | 查动态依赖（glibc） | `ldd ./app` |
| `file` | 一眼看格式/架构/是否 stripped | `file a.out` |

> 口诀：**反汇编用 objdump，ELF 装载/动态细节用 readelf，崩溃地址翻译用 addr2line，找符号用 nm**。

## 10. 实战工作流

```bash
# 1) 崩溃地址定位（日志 PC=0x4011a7）
addr2line -e ./app -f -C 0x4011a7
objdump -d -M intel -S app | grep -B2 -A20 '4011a7:'

# 2) 函数是否被优化/内联掉
objdump -t -C app | grep -i MyFunc       # 没符号 → 被 static+优化内联/删除

# 3) undefined reference / GLIBC 版本
objdump -T app | grep GLIBC_2.34         # 依赖的最高 glibc，目标机须 ≥ 它
nm -C libxxx.a | grep ' U '              # U = 该库还缺哪些符号

# 4) 全局变量初值/字节序
objdump -s -j .data app                  # 与 hexdump 互证
```

## 12. 常见问题与坑

1. **默认 AT&T 看着别扭**：固定 `-M intel`，两者操作数顺序相反，别混读。
2. **`-S` 对不上源码**：没加 `-g`，或开了 `-O2` 重排/内联；对照学习用 `-g -O0`。
3. **`.o` 里 call 目标是 0/假地址**：正常，未链接，由 `-r` 重定位项在链接时回填。
4. **分析 ARM/RISC-V 用错 x86 的 objdump**：用交叉版并先 `-f` 核对架构大小端。
5. **strip 后 `-t` 没符号**：`.symtab` 被删只剩 `-T`；保留带符号版用于调试，另发 strip 版。
6. **C++ 符号看不懂**：`-C` 或 `c++filt` demangle，定位真实类与签名。
7. **`-d` 不反汇编数据段**：看数据字节用 `-s`，强制全部用 `-D`。
8. **GLIBC 版本报错**：`objdump -T` 看符号版本，换老基线编译或静态/容器化分发。
9. **objdump 与 readelf "不一致"**：objdump 经 BFD 规整过；看 ELF 原始结构以 `readelf` 为准。
10. **大文件直接 -d 刷屏**：`-j` 限段或管道 `less`/`sed -n` 抠函数。
