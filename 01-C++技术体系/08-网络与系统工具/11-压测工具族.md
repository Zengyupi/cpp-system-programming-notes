## 0. 压测方法论

### 0.1 压测的核心问题

压测不是"跑个工具看 QPS"，而是回答三个问题：

1. **系统能扛多少？**——最大吞吐量（QPS/TPS）和响应时间（P50/P99/P999）。
2. **瓶颈在哪？**——CPU、内存、磁盘 IO、网络、应用代码、数据库，哪个先到上限。
3. **拐点在哪？**——并发量增加到多少时，吞吐量不再增长甚至下降、响应时间急剧恶化。

### 0.2 标准流程：梯度加压

```text
并发量
  ↑
  │        ┌────── 拐点：吞吐量不再增长，延迟飙升
  │       ╱
  │      ╱  ← 线性增长区：并发↑ → 吞吐↑，延迟平稳
  │     ╱
  │    ╱
  │   ╱
  └──────────────────→ 并发量
```

1. **从低并发开始**：1 并发跑 30 秒，确认基线延迟和 QPS。
2. **逐步加压**：每次并发翻倍（1→2→4→8→16→32→64→128→256），每档跑 60 秒以上。
3. **记录每档数据**：QPS、P50/P99/P999 延迟、错误率、CPU/内存/IO/网络水位。
4. **找到拐点**：QPS 不再增长或 P99 延迟超过 SLA 的那档。
5. **定位瓶颈**：拐点时看资源监控——CPU 满了？IO await 高了？网络带宽满了？连接数到上限了？

### 0.3 压测环境要求

- **环境隔离**：压测机和被测机分开，避免压测工具本身消耗被测机资源。
- **网络隔离**：压测流量不要和业务流量混跑，避免互相影响。
- **数据预热**：数据库/缓存要有真实量级的数据，空库压出来的 QPS 没有参考价值。
- **多次取平均**：每档至少跑 3 次取平均，排除偶发抖动。
- **压测机资源足够**：压测机本身不能成为瓶颈（CPU、端口数、fd 数要够）。

## 1. HTTP 压测

### 1.1 wrk — 多线程事件驱动，首选

`wrk` 是 HTTP 压测的首选工具：多线程 + 事件驱动（epoll），单机就能打出高并发，支持 Lua 脚本扩展复杂场景。

```bash
apt install wrk          # Ubuntu
wrk -t4 -c100 -d30s http://localhost:8080/api/test
```

参数：

| 参数 | 含义 |
| --- | --- |
| `-t` | 线程数（一般 = CPU 核数） |
| `-c` | 并发连接数 |
| `-d` | 持续时间（如 `30s`、`2m`） |
| `-s` | Lua 脚本文件 |
| `-H` | 请求头（可多次） |
| `--latency` | 打印延迟分布 |
| `--timeout` | 超时时间 |

实跑输出：

```text
Running 30s test @ http://localhost:8080/api/test
  4 threads and 100 connections
  Thread Stats   Avg      Stdev     Max   +/- Stdev
    Latency     5.23ms    3.12ms  89.45ms   78.34%
    Req/Sec     4.82k   312.45    5.67k    72.00%
  Latency Distribution
     50%    4.56ms
     75%    6.12ms
     90%    8.34ms
     99%   18.56ms
  576842 requests in 30.02s, 145.32MB read
Requests/sec:  19214.56
Transfer/sec:      4.84MB
```

- `Latency Avg/Stdev/Max`：平均延迟、标准差、最大值；**标准差大说明延迟不稳定**。
- `Req/Sec`：每个线程的每秒请求数。
- `Latency Distribution`：P50/P75/P90/P99 延迟分布，**P99 是 SLA 关键指标**。
- `Requests/sec`：总 QPS。

**Lua 脚本扩展**（POST 请求、动态参数、复杂流程）：

```lua
-- post.lua
wrk.method = "POST"
wrk.body   = '{"user_id": 123, "action": "click"}'
wrk.headers["Content-Type"] = "application/json"

-- 动态参数：每个请求带递增 id
local counter = 0
request = function()
   counter = counter + 1
   path = "/api/item?id=" .. counter
   return wrk.format(nil, path)
end
```

```bash
wrk -t4 -c100 -d30s -s post.lua http://localhost:8080
```

### 1.2 ab — Apache Bench，简单够用

`ab` 是 Apache 自带的压测工具，优点是简单、随处可用，缺点是单线程、不支持 HTTP/1.1 keepalive（默认）、高并发下自身容易成为瓶颈。

```bash
apt install apache2-utils
ab -n 10000 -c 100 http://localhost:8080/api/test
ab -n 10000 -c 100 -k http://localhost:8080/api/test    # -k 开启 keepalive
ab -n 1000 -c 50 -p post_data.txt -T "application/json" http://localhost:8080/api  # POST
```

参数：`-n` 总请求数、`-c` 并发数、`-k` keepalive、`-p` POST 数据文件、`-T` Content-Type。

输出关键字段：

```text
Requests per second:    5234.12 [#/sec] (mean)       ← QPS
Time per request:       19.104 [ms] (mean)            ← 平均延迟（含并发分摊）
Time per request:       0.191 [ms] (mean, across all concurrent requests)
Transfer rate:          1234.56 [Kbytes/sec] received

Connection Times (ms)
              min  mean[+/-sd] median   max
Connect:        0    0.1   0.3      0       5
Processing:     2   18.5  12.3     15     120
Waiting:        2   18.4  12.3     15     120
Total:          2   18.6  12.4     15     125

Percentage of the requests served within a certain time (ms)
  50%     15
  66%     20
  75%     24
  80%     28
  90%     38
  95%     48
  98%     65
  99%     82
 100%    125 (longest request)
```

> `ab` 的 `Time per request` 第一行是"并发分摊后的平均时间"（= 并发数 / QPS），不是单个请求的真实延迟；真实平均延迟看 `Connection Times Total mean`。

### 1.3 wrk2 — 固定吞吐量压测

`wrk2` 是 wrk 的改进版，核心差异是**固定吞吐量（constant throughput）**：wrk 是"尽可能快地发请求"，wrk2 是"按指定速率发请求"，更适合测试系统在给定负载下的延迟表现（而非极限吞吐）。

```bash
# wrk2 需从源码编译
git clone https://github.com/giltene/wrk2.git
cd wrk2 && make
./wrk -t4 -c100 -d30s -R2000 http://localhost:8080/api/test
```

- `-R2000`：固定每秒 2000 请求（全局速率）。
- 输出增加了 `Correct` 列（修正后的延迟统计，排除协调遗漏）。
- 适用场景：已知系统峰值 QPS 是 5000，想测在 5000 QPS 下 P99 延迟是否达标。

## 2. MySQL 压测

### 2.1 mysqlslap — MySQL 自带

`mysqlslap` 随 MySQL 客户端安装，适合快速验证 MySQL 性能，不需要额外装工具。

```bash
mysqlslap --user=root --password=xxx --host=localhost \
  --concurrency=50,100,200 \
  --iterations=3 \
  --number-of-queries=1000 \
  --create-schema=testdb \
  --query="SELECT * FROM users WHERE id = 1"
```

| 参数 | 含义 |
| --- | --- |
| `--concurrency` | 并发数（可逗号分隔多档） |
| `--iterations` | 每档运行次数 |
| `--number-of-queries` | 总查询数（每并发分摊） |
| `--create-schema` | 测试用的数据库名 |
| `--query` | 要执行的 SQL |
| `--auto-generate-sql` | 自动生成 SQL（不需要手写） |

输出：

```text
Benchmark
        Average number of seconds to run all queries: 0.856 seconds
        Minimum number of seconds to run all queries: 0.823 seconds
        Maximum number of seconds to run all queries: 0.901 seconds
        Number of clients running queries: 50
        Average number of queries per client: 20
```

### 2.2 sysbench — OLTP 基准测试，行业标准

`sysbench` 是最常用的 MySQL 基准测试工具，支持 OLTP 读写混合、只读、只写等多种场景，结果可复现、可对比。

```bash
apt install sysbench

# 1. 准备数据（创建表 + 插入测试数据）
sysbench oltp_read_write \
  --mysql-host=localhost --mysql-port=3306 \
  --mysql-user=root --mysql-password=xxx \
  --mysql-db=sbtest \
  --tables=10 --table-size=1000000 \
  prepare

# 2. 运行压测
sysbench oltp_read_write \
  --mysql-host=localhost --mysql-port=3306 \
  --mysql-user=root --mysql-password=xxx \
  --mysql-db=sbtest \
  --tables=10 --table-size=1000000 \
  --threads=16 --time=60 --report-interval=10 \
  run

# 3. 清理数据
sysbench oltp_read_write --mysql-host=localhost --mysql-user=root --mysql-db=sbtest cleanup
```

常用测试场景：

| 场景 | 命令 | 用途 |
| --- | --- | --- |
| 读写混合 | `oltp_read_write` | 模拟典型 OLTP 负载（默认 70% 读 + 30% 写） |
| 只读 | `oltp_read_only` | 测读性能（查询缓存、索引效率） |
| 只写 | `oltp_write_only` | 测写性能（insert/update/delete、redo log、binlog） |
| 点查 | `oltp_point_select` | 测主键查询性能 |
| 更新索引 | `oltp_update_index` | 测带索引更新的性能 |

输出关键字段：

```text
SQL statistics:
    queries performed:
        read:                            112345      ← 读查询数
        write:                           48123       ← 写查询数
        other:                           16046       ← 其他（BEGIN/COMMIT）
        total:                           176514
    transactions:                        8025   (133.75 per sec.)   ← TPS
    queries:                             176514 (2942.50 per sec.)   ← QPS
    ignored errors:                      0      (0.00 per sec.)
    reconnects:                          0      (0.00 per sec.)

General statistics:
    total time:                          60.0012s
    total number of events:              8025

Latency (ms):
         min:                                    2.34
         avg:                                   11.95
         max:                                  156.78
         95th percentile:                       28.45    ← P95 延迟
         sum:                                95892.12

Threads fairness:
    events (avg/stddev):           501.5625/12.34
    execution time (avg/stddev):   59.9326/0.01
```

- **TPS**：每秒事务数，OLTP 场景的核心指标。
- **QPS**：每秒查询数（含读写）。
- **P95 延迟**：95% 请求在多少毫秒内完成。
- `--report-interval=10`：每 10 秒打印一次中间结果，便于观察性能是否随时间衰减（如缓存失效、连接泄漏）。

## 3. Redis 压测

### 3.1 redis-benchmark — Redis 自带

`redis-benchmark` 随 Redis 安装，支持各种命令的 QPS 测试，是 Redis 性能验证的标准工具。

```bash
apt install redis-tools

# 默认测试：50 并发、100000 请求、测试一组默认命令
redis-benchmark -h localhost -p 6379 -c 50 -n 100000

# 只测试特定命令
redis-benchmark -h localhost -p 6379 -c 50 -n 100000 -t set,get

# 测试 Pipelining（管道）
redis-benchmark -h localhost -p 6379 -c 50 -n 100000 -P 10

# 测试指定 key 空间大小（模拟真实缓存命中率）
redis-benchmark -h localhost -p 6379 -c 50 -n 100000 -r 1000000
```

| 参数 | 含义 |
| --- | --- |
| `-c` | 并发连接数（默认 50） |
| `-n` | 总请求数（默认 100000） |
| `-t` | 只测试指定命令（逗号分隔） |
| `-P` | Pipelining 管道大小（一次发多少请求） |
| `-r` | key 空间大小（随机 key 的范围，模拟缓存） |
| `-d` | value 数据大小（字节，默认 3） |
| `-k` | 是否使用 keepalive（默认 1） |
| `--csv` | CSV 格式输出 |

实跑输出：

```text
====== SET ======
  100000 requests completed in 0.89 seconds
  50 parallel clients
  3 bytes payload
  keep alive: 1
  host configuration "save": 3600 1 300 100 60 10000
  host configuration "appendonly": no
  multi-thread: no

0.00% <= 0.2 milliseconds
50.00% <= 0.3 milliseconds
95.00% <= 0.5 milliseconds
99.00% <= 0.7 milliseconds
99.90% <= 1.1 milliseconds
100.00% <= 2.5 milliseconds
112359.55 requests per second    ← SET QPS

====== GET ======
  100000 requests completed in 0.85 seconds
...
117647.06 requests per second    ← GET QPS
```

**Pipelining 对 QPS 的影响**（实跑对比，WSL Ubuntu 24.04 + Redis 7.0.15）：

```text
-P 1  (无管道):  SET ~112k QPS, GET ~118k QPS
-P 10 (10管道):  SET ~450k QPS, GET ~520k QPS
-P 50 (50管道):  SET ~680k QPS, GET ~750k QPS
```

> Pipelining 把多个请求打包一次发送，减少网络往返次数，QPS 可提升数倍。但管道大小不是越大越好：过大的管道会增加单请求延迟（要等一批凑齐），且受服务端处理能力限制。实际业务中常用 10-50 的管道。

**不同命令的 QPS 差异**（同环境，50 并发，100k 请求）：

| 命令 | QPS | 说明 |
| --- | --- | --- |
| `GET` | ~118k | 最简单的读 |
| `SET` | ~112k | 最简单的写 |
| `INCR` | ~105k | 读+写原子操作 |
| `LPUSH` | ~100k | 列表操作 |
| `SADD` | ~98k | 集合操作 |
| `HSET` | ~95k | 哈希操作 |
| `ZADD` | ~88k | 有序集合（跳表，开销最大） |
| `MGET` (10 key) | ~90k | 批量读（单次返回多值） |

## 4. TCP 与网络带宽压测

### 4.1 iperf3 — 网络带宽测试标准

`iperf3` 是测试网络带宽、延迟抖动、丢包率的标准工具，C/S 架构：一端做服务端，一端做客户端。

```bash
apt install iperf3

# 服务端（被测机器或对端）
iperf3 -s -p 5201

# 客户端（压测端）
iperf3 -c 192.168.1.100 -p 5201 -t 30 -P 4
```

| 参数 | 含义 |
| --- | --- |
| `-s` | 服务端模式 |
| `-c` | 客户端模式，后跟服务端 IP |
| `-p` | 端口（默认 5201） |
| `-t` | 测试时长（秒，默认 10） |
| `-P` | 并行流数（多线程打满带宽） |
| `-R` | 反向测试（服务端→客户端，测下行带宽） |
| `-u` | UDP 模式（可测丢包和抖动） |
| `-b` | 目标带宽（UDP 模式下指定，如 `1G`） |
| `-i` | 报告间隔（秒） |

TCP 模式输出：

```text
Connecting to host 192.168.1.100, port 5201
[  5] local 192.168.1.200 port 54321 connected to 192.168.1.100 port 5201
[ ID] Interval           Transfer     Bitrate         Retr  Cwnd
[  5]   0.00-1.00   sec   112 MBytes   940 Mbits/sec    0    320 KBytes
[  5]   1.00-2.00   sec   113 MBytes   948 Mbits/sec    0    320 KBytes
...
[  5]  29.00-30.00  sec   112 MBytes   940 Mbits/sec    0    320 KBytes
- - - - - - - - - - - - - - - - - - - - - - - - -
[ ID] Interval           Transfer     Bitrate         Retr
[  5]   0.00-30.00  sec  3.30 GBytes   944 Mbits/sec    0             sender
[  5]   0.00-30.00  sec  3.29 GBytes   942 Mbits/sec                  receiver
```

- `Bitrate`：实际带宽，**接近网卡速率（如 940 Mbps ≈ 千兆网卡上限）说明网络打满了**。
- `Retr`：重传次数，**持续 > 0 说明网络有丢包或拥塞**。
- `Cwnd`：拥塞窗口大小。

UDP 模式输出（增加丢包和抖动）：

```text
[  5]   0.00-10.00  sec  1.10 GBytes   945 Mbits/sec  0.000 ms  0/137500 (0%)
```

- 末尾 `0/137500 (0%)`：丢包数/总包数（丢包率）。
- `0.000 ms`：抖动（Jitter），UDP 包到达时间的方差。

> **测带宽要用 `-P` 多流**：单流 TCP 受单连接拥塞窗口限制，可能打不满带宽；`-P 4` 或 `-P 8` 多并行流才能测出真实带宽上限。

### 4.2 TCP 应用层压测

对于自定义 TCP 协议的服务，没有现成的压测工具，常见方案：

| 方案 | 适用场景 | 特点 |
| --- | --- | --- |
| `wrk` + Lua 脚本 | HTTP over TCP | 只能压 HTTP |
| 自研压测客户端 | 私有协议 | 最灵活，但要写代码 |
| `tcpkali` | 通用 TCP | 支持多连接、消息速率控制、响应延迟统计 |
| `masscan` / `nmap` | 端口扫描/连通性 | 不是真正的压测 |

`tcpkali` 示例：

```bash
apt install tcpkali
# 1000 连接，每秒每连接发 10 条消息，消息内容从文件读取
tcpkali -c 1000 -r 10 -m "PING\r\n" -T 30s 192.168.1.100:6379
```

### 5.2 结果解读关键字段

```text
wrk:
  Requests/sec    → QPS
  Latency 99%     → P99 延迟（SLA 关键）
  Latency Stdev   → 延迟稳定性（大=抖动严重）
  Non-2xx/3xx     → 错误率（必须为 0）

ab:
  Requests per second → QPS
  Connection Times Total mean → 真实平均延迟
  99% 行           → P99 延迟
  Failed requests   → 失败请求数

sysbench:
  transactions per sec → TPS
  queries per sec      → QPS
  95th percentile      → P95 延迟
  ignored errors       → 错误数

redis-benchmark:
  requests per second  → QPS
  <= 99% 行            → P99 延迟

iperf3:
  Bitrate              → 实际带宽
  Retr                 → 重传次数（>0=丢包/拥塞）
  UDP: Jitter / lost  → 抖动 / 丢包率
```

### 5.3 压测前检查清单

```bash
# 压测机 fd 数（高并发需要）
ulimit -n
# 临时调大
ulimit -n 65535

# 压测机本地端口范围（大量出站连接需要）
sysctl net.ipv4.ip_local_port_range
# 调大
sysctl -w net.ipv4.ip_local_port_range="1024 65535"

# TIME_WAIT 复用（大量短连接场景）
sysctl -w net.ipv4.tcp_tw_reuse=1

# 确认压测机 CPU 核数（wrk 线程数 = 核数）
nproc

# 被测机监控（另开终端）
vmstat 1
iostat -xz 1
mpstat -P ALL 1
```

## 6. 常见问题与坑

1. **压测机本身成为瓶颈**：压测工具也吃 CPU 和网络，高并发下先确认压测机 CPU 没满、带宽没占满；否则测出来的是压测机的上限而非被测系统的上限。
2. **`ab` 单线程打不满高并发**：ab 是单线程模型，并发超过几百后自身 CPU 就满了；高并发 HTTP 压测用 wrk。
3. **wrk 的 `-c` 不是越大越好**：并发连接数超过系统处理能力后，QPS 不再增长但延迟飙升；要通过梯度加压找到最优并发。
4. **sysbench 数据量太小导致结果偏高**：`--table-size=1000000`（100 万行）是基准，数据量太小全在内存里，测不出磁盘 IO 和真实查询性能。
5. **redis-benchmark 默认 value 只有 3 字节**：`-d` 参数指定 value 大小，真实业务 value 可能几百到几千字节，QPS 会低很多。
6. **Pipelining 提升 QPS 但不提升单请求延迟**：管道是"批量发"，总吞吐上去了，但单个请求的端到端延迟反而可能增加（要等凑批）；对延迟敏感的业务不能盲目用大管道。
7. **iperf3 单流打不满带宽**：TCP 单连接受拥塞窗口和 RTT 限制，`-P 4` 或 `-P 8` 多流才能测满；测出来带宽远低于网卡速率时先加 `-P`。
8. **压测结果不可复现**：每次压测前清理缓存（`echo 3 > /proc/sys/vm/drop_caches`）、确认没有其他进程干扰、数据量一致、跑 3 次取平均。
9. **只看 QPS 不看延迟**：QPS 高但 P99 延迟超标一样不达标；SLA 通常是"QPS ≥ X 且 P99 ≤ Yms"，两个指标都要满足。
10. **压测环境和生产环境差异大**：CPU 核数、内存、磁盘类型（SSD vs HDD）、网络带宽、数据量都影响结果；压测结论要注明环境配置，不能直接套用到生产。
11. **HTTP 压测没加 keepalive**：`ab` 默认不开 keepalive（`-k` 才开），每次请求都新建 TCP 连接，QPS 会低很多且测的是连接建立性能而非应用性能；wrk 默认开 keepalive。
12. **压测时不监控资源**：只看压测工具输出不知道瓶颈在哪；必须同时监控被测机的 CPU/内存/IO/网络（《10-Linux系统监控命令族.md》），拐点时哪个资源先满就是瓶颈。
