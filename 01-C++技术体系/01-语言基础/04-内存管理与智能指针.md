## 1. 概述

### 1.1 C++ 内存管理的核心哲学

| 原则 | 含义 |
|---|---|
| RAII（Resource Acquisition Is Initialization） | 资源获取即初始化：构造函数拿资源，析构函数放资源，栈展开自动清理 |
| 所有权（ownership）明确 | 每块资源在任一时刻有且只有一个明确的"拥有者"（或明确记录共享） |
| 谁获取谁释放 | 分配与释放在同一抽象层级成对出现，最理想是同一个类里 |
| 异常安全 | 任何退出路径（return/异常/break）都不能跳过释放——只有 RAII 能做到 |
| 零开销 | 不用的智能指针不付费：unique_ptr 与裸指针同尺寸（无状态删除器时） |

与托管语言的本质差异：Java/Go 的对象在堆上、由 GC 回收，代价是不确定时延与停顿；C++ 允许完全避开堆与 GC，这是它在嵌入式/实时/游戏领域不可替代的原因（相关实践见《../09-嵌入式开发/05-嵌入式Linux系统与驱动开发.md》）。

## 2. 进程内存布局

### 2.1 地址空间总览

```text
高地址
+----------------------------+
| 命令行参数 / 环境变量         |
+----------------------------+
| 栈 stack                    | 自动存储期
| |  局部变量、函数调用帧        | 向低地址增长，速度快（移动栈指针）
| v  每帧随函数返回自动回收      | 大小受限（Linux 默认 8MB）
|                            |
| ^  堆 heap                  | 动态存储期（new/malloc）
| |  生存期由程序员控制          | 向高地址增长，分配慢、有碎片
+----------------------------+
| .bss   未初始化的全局/静态变量 | 程序加载时清零，不占可执行文件体积
| .data  已初始化的全局/静态变量 | 初值存于可执行文件
+----------------------------+
| .rodata 字符串字面量、const 数据| 只读，写入触发段错误
| .text   机器码               | 只读+可执行
+----------------------------+
低地址
```

（用 `size a.out` 可查看各段大小；用 `cat /proc/<pid>/maps` 可看运行时布局，详见「04-Linux命令行速查.md」。）

### 2.2 栈 vs 堆

| 维度 | 栈 | 堆 |
|---|---|---|
| 分配速度 | 一次寄存器加减法（~1ns 级） | 涉及分配器查找/加锁（几十~上百 ns） |
| 大小限制 | 小（Linux 默认 8MB，可 ulimit 调整） | 大（受限于虚拟内存） |
| 生命周期 | 作用域绑定，自动回收 | 手工控制（new/delete） |
| 内存碎片 | 无 | 有（频繁变长分配产生外部碎片） |
| 局部性 | 极好（连续、缓存命中率高） | 差（地址分散） |
| 安全性 | 越界/过深递归 → stack overflow | 忘释放→泄漏；早释放→悬垂 |
| 典型用途 | 局部变量、函数参数、返回小对象 | 大对象、生存期跨越作用域、多态容器 |

**实践含义：能用栈就不用堆；必须堆时优先容器/智能指针而不是裸 new。**

## 3. new / delete 深入

### 3.1 new 表达式到底做了什么

`new T(args)` 不是一条"分配指令"，它是**三个步骤**的语法糖：

```cpp
Widget* w = new Widget(42);
// 编译器实际做的：
// 1) void* mem = operator new(sizeof(Widget));   分配原始内存
// 2) mem 转换为 Widget*
// 3) 在 mem 上调用 Widget::Widget(42)             构造对象
```

`delete w` 则是两步：

```text
delete w;
// 1) w->~Widget();          析构对象
// 2) operator delete(w);    释放内存
```

**推论：malloc 只完成第 1 步——拿到的是没有构造的原始内存；new = malloc + 构造。** 这就是 C 和 C++ 不可混用分配函数的原因。

如果第 3 步构造函数抛异常，运行时会自动调用匹配的 `operator delete` 释放第 1 步的内存（保证不泄漏）——这也是 `new` 比"malloc + placement new"安全的原因。

### 3.2 new[] 与 delete[] 必须配对

```text
Widget* arr = new Widget[10];   // 分配 10 个对象 + 可能的 cookie（记录个数，视实现而定）
delete[] arr;                   // 正确：按 cookie 逐个析构再释放
// delete arr;                  // UB！只析构第一个对象，其余 9 个的资源全部泄漏
```

`delete[]` 需要知道"要析构几个"，这个个数信息由实现自行存放（常用 cookie）。对"平凡可析构"类型编译器可能省略 cookie（视实现而定）——但**你的代码永远不该依赖这种实现细节**：new[] 配 delete[]，new 配 delete，一次配错就是 UB。

### 3.3 placement new 与手动析构义务

placement new 在**已存在的内存**上构造对象，不分配：

```cpp
#include <new>                       // placement new 的声明在这里

alignas(Widget) unsigned char buf[sizeof(Widget)];   // 栈上内存，注意对齐
Widget* w = new (buf) Widget(42);    // 在 buf 上构造
w->doSomething();
w->~Widget();                        // 必须手动调用析构！
// buf 是栈内存，绝不能 delete buf
```

| 义务 | 说明 |
|---|---|
| 内存由你提供 | 栈、静态区、内存池均可 |
| 对齐由你保证 | `alignas(T)` 或分配器保证 |
| **析构由你手动调用** | 编译器无从知晓该对象的析构时机 |
| 释放方式跟随内存来源 | 栈内存不释放；池内存还给池 |

placement new 是内存池、`std::vector` 内部实现、以及嵌入式"静态构造"技术的基石。标准库还有一个带参形式 `new (std::nothrow) T`（见 3.6）。

### 3.4 operator new 可重载

`operator new` 是普通函数，可全局替换或按类重载——这是自定义内存池的入口：

```cpp
#include <cstdio>
#include <cstdlib>
#include <new>

// 全局替换（影响整个程序，慎用；一般用于统计/调试）
void* operator new(std::size_t sz) {
    std::printf("alloc %zu bytes\n", sz);
    if (void* p = std::malloc(sz)) return p;
    throw std::bad_alloc{};
}
void operator delete(void* p) noexcept { std::free(p); }

// 按类重载（只影响该类）：把对象放进内存池
struct Pool { static void* alloc(std::size_t); static void free(void*); };
struct FastNode {
    static void* operator new(std::size_t sz) { return Pool::alloc(sz); }
    static void operator delete(void* p) { Pool::free(p); }
};
```

### 3.5 new 失败的行为

```cpp
Widget* p1 = new Widget;                  // 失败：抛 std::bad_alloc
Widget* p2 = new (std::nothrow) Widget;   // 失败：返回 nullptr（不抛）
if (!p2) { /* 内存不足的处理路径 */ }
```

传统 C 程序员习惯检查返回值——注意默认 new **不返回 nullptr 而是抛异常**，`if (p)` 检查是死代码；要么捕获 `std::bad_alloc`，要么显式用 nothrow 形式。

## 4. RAII：资源管理的正确姿势

### 4.1 手工管理的三宗罪

```cpp
// 反例：裸 FILE* 手工管理
void saveConfig(const Config& cfg) {
    FILE* f = fopen("config.ini", "w");
    if (!f) return;
    if (!cfg.valid()) { fclose(f); return; }     // 罪1：每条退出路径都要记得清理
    fprintf(f, "%s", cfg.dump().c_str());
    if (diskFull()) throw std::runtime_error("disk");  // 罪2：异常直接跳过 fclose → 泄漏
    fclose(f);
}   // 罪3：以后新增 return 的人一定会忘记 fclose
```

### 4.2 RAII 封装

```cpp
class FilePtr {                            // 最小 RAII 包装
public:
    explicit FilePtr(FILE* f) : f_(f) {}
    ~FilePtr() { if (f_) fclose(f_); }     // 唯一的释放点：析构函数

    FilePtr(const FilePtr&) = delete;              // 裸资源不可拷贝
    FilePtr& operator=(const FilePtr&) = delete;

    FilePtr(FilePtr&& o) noexcept : f_(o.f_) { o.f_ = nullptr; }   // 可移动=可转移所有权
    FilePtr& operator=(FilePtr&& o) noexcept {
        if (this != &o) { if (f_) fclose(f_); f_ = std::exchange(o.f_, nullptr); }
        return *this;
    }
    FILE* get() const { return f_; }
private:
    FILE* f_;
};

void saveConfig(const Config& cfg) {
    FilePtr f(fopen("config.ini", "w"));
    if (!f.get()) return;
    fprintf(f.get(), "%s", cfg.dump().c_str());
    if (diskFull()) throw std::runtime_error("disk");   // 异常 → 栈展开 → ~FilePtr 仍然执行
}   // 所有退出路径自动 fclose，无泄漏
```

### 4.3 为什么 RAII 是异常安全的基础

异常发生时，栈展开（stack unwinding）会**自动调用已构造完成对象的析构函数**。这意味着：只要资源被 RAII 对象持有，任何退出路径（return/异常/break/goto）都必然释放——这是 try/catch 手工清理永远做不到的（catch 位置与 throw 位置可能相隔多层）。

| 标准库现成的 RAII 设施 | 资源 |
|---|---|
| `std::fstream` | 文件句柄 |
| `std::lock_guard` / `std::unique_lock` | 互斥锁 |
| `std::unique_ptr` / `std::shared_ptr` | 堆内存与任意资源 |
| `std::thread` / `std::jthread`(C++20) | 线程（jthread 析构自动 join） |
| `std::vector` 等容器 | 元素数组的内存 |

**口诀：先找现成 RAII 类，找不到再写一个小包装类，永远不让裸资源跨函数边界。**

## 5. 智能指针总览

| 智能指针 | 所有权语义 | 可拷贝 | 可移动 | 开销 | 头文件 |
|---|---|---|---|---|---|
| `unique_ptr<T>` | **独占**：同一时刻只有一个拥有者 | 否（编译错） | 是 | 几乎为零（无状态删除器时 sizeof == 裸指针） | `<memory>` |
| `shared_ptr<T>` | **共享**：引用计数归零才释放 | 是（计数 +1） | 是（计数不变） | 控制块 + 原子计数（拷贝有原子开销） | `<memory>` |
| `weak_ptr<T>` | **不拥有**：观察 shared 管理的对象 | 是 | 是 | 与控制块同住，不参与强计数 | `<memory>` |
| 裸指针 / 引用 | **不拥有**：仅观察 | — | — | 零 | — |

**裸指针没有被废除，它的新角色是"非拥有观察"**：参数传递、遍历、缓存索引。判断标准只有一个：**"谁负责 delete"必须能一眼看出**——智能指针的名字就是答案。

## 6. unique_ptr 详解

### 6.1 基本用法与 make_unique（C++14）

```cpp
#include <memory>

auto p = std::make_unique<Widget>(42);     // 推荐：C++14 起才有 make_unique
std::unique_ptr<Widget> q(new Widget(42)); // C++11 只能直接 new

p->run();                                  // 像裸指针一样使用
if (p) { }                                 // 判空
Widget* raw = p.get();                     // 借出裸指针（观察用，不能 delete）
Widget& obj = *p;                          // 解引用

p.reset();                                 // 立即释放
p.reset(new Widget(7));                    // 释放旧的、接管新的
auto w = p.release();                      // 放弃所有权，返回裸指针（此后由你负责 delete）
```

`make_unique` 的三个理由：代码里不出现裸 new；异常安全（C++11 的 `foo(unique_ptr<T>(new T), bar())` 求值顺序陷阱）；与 `make_shared` 风格统一。

### 6.2 数组

```cpp
auto arr = std::make_unique<int[]>(128);   // 数组特化：自动 delete[]
arr[0] = 1;
// 但更优先：std::vector<int>（可增长、有 size、可拷贝）
```

### 6.3 自定义删除器：接管一切"裸资源"

unique_ptr 不只管内存，它管**任何需要成对调用 open/close 的东西**：

```cpp
// FILE*：functor 删除器（零大小开销）
struct FileCloser {
    void operator()(FILE* f) const noexcept { if (f) fclose(f); }
};
std::unique_ptr<FILE, FileCloser> fp(fopen("data.bin", "rb"));
if (!fp) { /* 打开失败 */ }

// Windows 句柄 / POSIX fd 同理
struct FdCloser { void operator()(int fd) const noexcept { ::close(fd); } };
std::unique_ptr<int, FdCloser> fdsock(open("log", O_WRONLY));
```

| 删除器写法 | sizeof(unique_ptr) | 备注 |
|---|---|---|
| 默认 `default_delete<T>` | = 裸指针 | 调 delete |
| 无状态 functor（如上 FileCloser） | = 裸指针 | **零开销**，推荐 |
| 函数指针 `void(*)(FILE*)` | 裸指针 + 8 字节 | 多存一个函数指针 |
| 捕获了状态的 lambda | 视捕获大小而定 | 灵活但增加体积 |

C++20 起 lambda 可以直接出现在模板实参里：`std::unique_ptr<FILE, decltype([](FILE* f){ fclose(f); })>`（无捕获 lambda 仍是零大小）。

### 6.4 所有权转移必须 std::move

```cpp
auto p = std::make_unique<Widget>();
auto q = p;                 // 编译错误！拷贝构造被删除——独占语义的编译期保证
auto r = std::move(p);      // OK：移动=所有权转移，p 变为 nullptr
consume(std::move(r));      // 传值移交所有权，调用方明确知道"我给出去了"
```

函数签名即文档：

| 签名 | 语义 |
|---|---|
| `void f(Widget&)` | 我借用，不改变所有权 |
| `void f(std::unique_ptr<Widget> w)` | **我把你的对象拿走了**（调用方必须 move） |
| `void f(const std::unique_ptr<Widget>& w)` | 我只是间接用一下，别这么写——直接传 `Widget&` 更清晰 |
| `std::unique_ptr<Widget> f()` | 我是生产者，产出的所有权交给你 |

### 6.5 零开销抽象

无状态删除器的 `unique_ptr` 与裸指针同大小，析构内联后等价于一条 delete，生成的机器码与手工管理相同。"零开销"不是口号：用 `../06-工程化与工具链/08-GDB程序调试.md` 中的 disassemble 或 `-S` 汇编输出即可验证。**没有理由再手写 new/delete。**

## 7. shared_ptr 详解

### 7.1 引用计数与控制块

```text
直接构造（两次分配）：
   sp ──────> ┌───────────┐
              │  Widget 对象 │        独立的一块堆内存
              └───────────┘
   sp ──────> ┌────────────────────────┐
              │ 控制块（独立堆内存）        │
              │  strong count（强计数）    │  归零 → 析构对象
              │  weak count（弱计数）      │  归零 → 释放控制块+对象内存
              │  deleter / allocator     │
              └────────────────────────┘

make_shared（一次分配）：
   sp ──────> ┌────────────┬───────────┐
              │  控制块      │ Widget 对象 │   同一块内存，缓存友好
              └────────────┴───────────┘
```

### 7.2 make_shared 的优缺点

| | `make_shared<T>()` | `shared_ptr<T>(new T)` |
|---|---|---|
| 堆分配次数 | **1 次**（控制块+对象合并） | 2 次 |
| 缓存局部性 | 好 | 差 |
| 异常安全 | 好 | C++17 前有求值顺序坑 |
| 对象内存释放时机 | **所有 weak_ptr 消亡后**才整块释放 | 强计数归零即释放对象 |
| 自定义删除器 | 不支持 | 支持 |
| 私有构造函数 | 不可用 | 可用 |

**重点理解那个"缺点"**：make_shared 把对象和控制在同一块内存里，`~Widget()` 在强计数归零时照常执行（对象生命周期正常结束），但**内存本身要等最后一个 weak_ptr 消失才能 free**。对象很大且存在长期 weak_ptr（如缓存场景）时，这是真实的内存滞留——此时应改用 `shared_ptr<T>(new T)` 的两次分配形式。

### 7.3 拷贝/移动对计数的影响

```cpp
auto a = std::make_shared<Widget>();   // strong = 1
auto b = a;                            // 拷贝：strong = 2（一次原子递增）
auto c = std::move(a);                 // 移动：strong 仍 = 2（a 变 null，无原子操作）
b.reset();                             // strong = 1
c.reset();                             // strong = 0 → ~Widget() → 释放内存
```

### 7.4 线程安全性（精确表述，必考）

| 操作 | 线程安全吗 |
|---|---|
| 不同线程操作**各自的 shared_ptr 副本**（指向同一对象） | **安全**：控制块计数是原子操作 |
| 不同线程**读写同一个 shared_ptr 变量**（如一个线程 reset，另一个读它） | **不安全**：需要外部加锁或 `std::atomic<std::shared_ptr>`（C++20，视实现可用性而定） |
| 不同线程调用**同一个被指对象**的成员 | **不安全**：shared_ptr 只管计数，不管对象本身 |

一句话：**shared_ptr 的计数是线程安全的，它指向的对象不是。**

### 7.5 enable_shared_from_this

场景：对象已被 shared_ptr 管理，成员函数内部想再拿一个 shared_ptr（典型是异步回调中保活自身）。

```cpp
#include <memory>

struct Task : std::enable_shared_from_this<Task> {
    void asyncRun() {
        // 错误示范：Task* this 是裸指针，无法直接变 shared_ptr
        // 若写 shared_ptr<Task>(this) → 产生第二个控制块 → 双重释放！
        post([self = shared_from_this()] {     // 正确：从基类拿同源的 shared_ptr
            self->run();
        });                                     // 回调执行期间 Task 保证存活
    }
    void run();
};
```

| 用法 | 结果 |
|---|---|
| 成员函数中 `shared_from_this()` | 正确，与外部 shared_ptr 共享同一控制块 |
| **构造函数中**调用 `shared_from_this()` | **抛 std::bad_weak_ptr**：weak_this 在 shared_ptr 接管时才初始化，构造期间尚不存在 |
| 直接 `shared_ptr<T>(this)` | 灾难：第二个控制块 → 双重释放 |

构造期需要 shared_ptr 的正确姿势：用静态工厂函数 `static std::shared_ptr<Task> create(...)` 返回 `make_shared<Task>(...)`。

## 8. weak_ptr：打破循环引用

### 8.1 循环引用导致泄漏的完整反例

```cpp
#include <cstdio>
#include <memory>

struct Node {
    std::shared_ptr<Node> next;   // 双向链表两个方向都用强引用
    std::shared_ptr<Node> prev;
    ~Node() { std::puts("~Node"); }          // 这个析构永远不会被调用
};

int main() {
    auto a = std::make_shared<Node>();       // a: strong=1
    auto b = std::make_shared<Node>();       // b: strong=1
    a->next = b;                             // b: strong=2
    b->prev = a;                             // a: strong=2
}   // 离开作用域：局部 a、b 各自减 1 → 两对象计数仍为 1 → 互相抱团永不释放 → 泄漏
    // valgrind 会报告 "definitely lost"（详见《../07-调试与测试/02-Valgrind内存检测.md》）
```

### 8.2 weak_ptr 修复版

```cpp
struct Node {
    std::shared_ptr<Node> next;   // 主方向保持强引用（决定链表生命）
    std::weak_ptr<Node>   prev;   // 回指方向降级为弱引用（不参与生命周期）
};

// 使用时必须"提升"回 shared_ptr 才能访问：
if (auto prev = n->prev.lock()) {   // lock()：原子地检查存活并提升
    prev->data();
}
```

**建模原则：所有权方向（父→子）用 shared_ptr，回指方向（子→父、观察者→被观察者、缓存→对象）一律 weak_ptr。**

### 8.3 lock() 与 expired() 的正确用法

```cpp
std::weak_ptr<Widget> w = sp;

// 正确：lock() 原子地"检查+提升"，成功即持有强引用，期间对象保证存活
if (auto s = w.lock()) { s->run(); }

// 错误：expired() 与后续使用之间存在竞态窗口（TOCTOU）
if (!w.expired()) { w.lock()->run(); }   // 检查后、使用前对象可能恰好被释放
```

## 9. 内存错误类型与检测

| 错误类型 | 典型成因 | 检测手段 |
|---|---|---|
| 内存泄漏 | 忘记 delete、异常路径跳过释放、shared_ptr 循环引用 | valgrind（`--leak-check=full`）、`-fsanitize=leak` |
| 悬垂指针（use-after-free） | delete 后继续用、返回局部变量地址/引用、容器扩容后旧迭代器 | ASan（`-fsanitize=address`）、valgrind |
| 重复释放 | 同一指针 delete 两次、`delete p.get()` | ASan（double-free 直接报错） |
| 堆越界 | new T[n] 后访问 a[n]、strcpy 溢出 | ASan、valgrind |
| 栈越界 | 数组下标越界、过深递归 | ASan（`detect_stack_use_after_return`）、gdb 看栈帧 |
| 未初始化读 | 局部变量裸用 | MSan（`-fsanitize=memory`，Clang）、valgrind 部分覆盖 |
| new[]/delete 错配 | delete 了 new[] 的内存 | ASan、valgrind（报 mismatch） |

```text
# 编译时插桩（详见《../06-构建与版本控制/01-构建工具GCC与CMake.md》）
g++ -g -fsanitize=address,undefined -fno-omit-frame-pointer main.cpp -o main
./main                          # 错误当场报，带调用栈

# 无需重编译的运行时检查（详见《../07-调试与测试/02-Valgrind内存检测.md》）
valgrind --leak-check=full --show-leak-kinds=all ./main

# 崩溃后看现场（详见《../07-调试与测试/01-GDB程序调试.md》）
gdb ./main core
```

**经验法则：开发期常开 ASan + UBSan（开销约 2 倍），CI 里跑 valgrind，发布版关闭。**

## 10. 选择决策与实践准则

### 10.1 决策树

```text
              需要一个对象，生命周期怎么管？
                          |
        +-----------------+------------------+
        |                                    |
   栈/成员/容器放得下？                 必须动态分配？
   （值语义：自动、零成本）                    |
        | 是                                 |
        v                                    v
   直接用值（默认选择）            所有权属于几个人？
                                             |
                          +------------------+-------------------+
                          | 1 个（唯一）       |  多个共享            |
                          v                  v                     v
                     unique_ptr          shared_ptr          只是观察不拥有？
                          |                  |                     v
                  接管 C 资源?          有回指/循环?          裸指针 或 引用
                          v                  v
                   自定义删除器          weak_ptr 打破环
```

### 10.2 实践准则清单

1. **默认值语义**：栈对象、成员对象、`std::vector<T>` 存值。对象不大（<几百字节）时这是最优解。
2. **必须多态才用指针**：`std::vector<std::unique_ptr<Base>>` 是标准的多态容器形态。
3. **动态分配的默认答案是 unique_ptr**，需要共享再升级 shared_ptr（单向不可逆心智负担最小）。
4. **裸指针只做观察**：函数参数传 `T*`/`T&` 表示"借用"，永远不 delete 参数。
5. **new/delete 只允许出现在类的内部**（封装资源的那一层）或智能指针构造处。
6. **优先 make_unique/make_shared**；需要自定义删除器或延迟释放时再直接 new。
7. **所有回指关系用 weak_ptr**（父子的子方向、观察者、缓存）。
8. **内存池/arena 用 placement new + 手动析构**，封装成 RAII 类对外暴露。

## 12. 常见问题与坑

| 问题 | 原因与解决方案 |
|---|---|
| shared_ptr 互相引用，析构永远不执行 | 循环引用使强计数无法归零。回指方向改 weak_ptr；怀疑时用 valgrind 验证 |
| `delete p.get()` 之后程序崩溃 | get() 只是借出裸指针，智能指针稍后还会再 delete 一次 → 双重释放。get() 只用于观察 |
| unique_ptr 按值传参编译报错"deleted copy constructor" | 独占语义禁止拷贝。传 `std::move(p)` 移交所有权，或传 `const T&`/`T*` 表示借用 |
| 保存了 `p.get()` 的裸指针，智能指针提前释放 → 悬垂 | 裸指针不延长生命周期。需要长期持有就保存 shared_ptr/weak_ptr 本身 |
| make_shared + 常驻 weak_ptr 导致大对象内存迟迟不还 | 合并分配使对象内存与控制块同生共死（析构照常，free 延迟）。大对象+长期 weak 场景改用 `shared_ptr<T>(new T)` |
| 构造函数里调 shared_from_this() 抛 bad_weak_ptr | weak_this 在 shared_ptr 接管时才初始化。改用静态工厂函数或两段式 init |
| 以为 shared_ptr 是线程安全的，多线程同时写对象成员崩了 | 计数原子安全 ≠ 对象本身线程安全。对象访问仍需锁；同一 shared_ptr 变量的并发读写也需保护 |
| new[] 配了 delete（或反之） | UB，多数实现对非平凡析构类型直接崩溃。数组一律 `make_unique<T[]>` 或 vector |
| placement new 的对象忘了手动调析构 | 对象内的资源（如 string 成员）泄漏。每处 placement new 配对一次显式 `~T()`，最好封装成 RAII |
| 智能指针与 C API 混用（`legacy(c_str(), p.get())` 之后对象被释放） | 裸指针跨过了智能指针的边界。自定义删除器让 unique_ptr 直接管理 C 资源 |
| `if (new Widget)` 判空是死代码 | 默认 new 失败抛 bad_alloc 而非返回 nullptr。需要判空用 nothrow 形式或捕获异常 |
| lambda 捕获 unique_ptr 捕不了（编译错） | unique_ptr 不可拷贝。用初始化捕获 `[p = std::move(p)]`（C++14）按移动捕获 |
| 多线程共享同一个 shared_ptr 变量（一读一写）不加锁 | shared_ptr 变量本身非原子。加锁，或 C++20 `std::atomic<shared_ptr>`（支持情况视实现而定） |
