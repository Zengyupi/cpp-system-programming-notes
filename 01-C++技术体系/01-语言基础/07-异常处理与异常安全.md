## 1. 异常机制底层原理

### 1.1 异常处理的完整流程

C++ 异常处理不是简单的 `goto`，它涉及**异常对象的构造、栈展开（stack unwinding）、handler 匹配、异常对象的销毁**四个阶段。

```cpp
#include <stdexcept>
#include <iostream>

void level3() {
    throw std::runtime_error("something broke");
    // 1. 构造异常对象（在编译器管理的特殊内存中，不在栈上）
    // 2. 立即停止当前函数后续执行，开始栈展开
}
void level2() {
    std::string local = "resource";   // 栈展开时自动析构
    level3();                          // 异常从这里向上传播
}
void level1() {
    try {
        level2();
    } catch (const std::runtime_error& e) {
        // 3. handler 匹配成功：异常对象绑定到 e
        std::cerr << "caught: " << e.what() << '\n';
    }
    // 4. 离开 catch 块：异常对象自动销毁
}
```

| 阶段 | 发生了什么 | 关键细节 |
|---|---|---|
| throw | 构造异常对象 | 对象存放在编译器管理的异常存储区（不是栈、不是堆，实现相关）；throw 之后的代码永不执行 |
| 栈展开 | 沿调用链向上找 handler | 每离开一个作用域，已构造的局部对象按构造逆序析构；找到 handler 后停止展开 |
| handler 匹配 | 按 catch 子句顺序匹配 | 精确匹配 > 公有基类匹配 > `...` 兜底；catch by reference 避免切片 |
| 异常销毁 | 离开 catch 块 | 异常对象自动销毁；若 catch 中重新 throw（`throw;`）则对象继续存活 |

### 1.2 栈展开的精确语义

栈展开是异常安全的基石。标准规定 [except.ctor]/2：**栈展开期间，每个已构造完成的自动存储期对象都按构造的逆序调用析构函数**。

```cpp
struct A { A() { std::puts("A ctor"); } ~A() { std::puts("A dtor"); } };
struct B { B() { std::puts("B ctor"); } ~B() { std::puts("B dtor"); } };

void f() {
    A a;        // 先构造 A
    B b;        // 再构造 B
    throw 1;    // 栈展开：先析构 b，再析构 a（逆序）
}
// 输出：A ctor → B ctor → B dtor → A dtor
```

**关键推论**：如果一个对象的构造函数抛异常，那么**该对象本身的析构函数不会被调用**（因为它没有构造完成），但它的成员和基类子对象（已构造的部分）会被逆序析构。这就是"构造函数中抛异常需要 RAII 成员"的根本原因——见第 3.4 节。

### 1.3 异常对象的生命周期

| 场景 | 异常对象行为 |
|---|---|
| `throw T(args);` | 在异常存储区构造 T 对象 |
| `catch (T e)` 按值捕获 | **拷贝构造**一个副本（切片风险！），原异常对象在 catch 块结束时销毁 |
| `catch (const T& e)` 按引用捕获 | 直接绑定原异常对象，零拷贝，**推荐** |
| `catch (...)` | 捕获任何异常，但无法访问异常对象内容 |
| `throw;`（重新抛出） | 继续传播当前异常对象，不构造新对象 |
| `throw e;`（抛出捕获的异常） | **拷贝构造**新异常对象（可能切片！），应改用 `throw;` |

```cpp
catch (const std::exception& e) {
    // 正确：重新抛出原异常（保留派生类型）
    throw;
    // 错误：拷贝构造新的 std::exception（切片！丢失派生信息）
    // throw e;
}
```

## 2. 异常安全三级保证（核心考点）

异常安全保证描述的是：**当操作抛出异常时，程序状态保持在什么程度**。这是面试高频考点，必须能准确区分三级并举例。

### 2.1 三级保证定义

| 保证级别 | 英文 | 语义 | 失败后状态 | 典型实现 |
|---|---|---|---|---|
| 不抛保证 | No-throw / No-fail | 操作**绝不**抛出异常 | 操作必然成功 | 析构函数、swap、移动构造（标 noexcept） |
| 强保证 | Strong | 失败则**状态完全不变**（事务语义：要么全做，要么全不做） | 回滚到操作前状态 | copy-and-swap 惯用法 |
| 基本保证 | Basic | 失败后对象仍**有效**（不变量成立）、**不泄漏资源**，但状态可能已改变 | 有效但未知的中间状态 | 大多数 STL 容器操作 |
| 无保证 | — | 失败后可能泄漏资源、对象不变量被破坏 | 不可用 | 裸 new/delete 手工管理 |

> 记忆口诀：**不抛 > 强 > 基本 > 无**。级别越高，失败后的状态越确定，但实现成本也越高。

### 2.2 基本保证示例

```cpp
class Widget {
    std::vector<int> data_;
public:
    // push_back 提供基本保证：若分配失败抛 bad_alloc，
    // vector 自身不变量仍成立（size 不变、无泄漏），但 data_ 可能已部分修改
    void add(int x) {
        data_.push_back(x);   // 若抛异常，data_ 仍有效
    }
};
```

基本保证是"最低可接受标准"：对象不会崩溃、不会泄漏，但调用者不能假设操作完全没发生。

### 2.3 强保证：copy-and-swap 惯用法

强保证的核心思想：**先在副本上做所有可能抛异常的操作，全部成功后再用不抛的 swap 提交**。

```cpp
#include <utility>
#include <string>

class Widget {
    std::string name_;
    std::vector<int> data_;
public:
    Widget() = default;
    Widget(const Widget&) = default;
    Widget& operator=(const Widget& rhs) {
        // 第一步：拷贝 rhs 到临时对象（可能抛异常，但 *this 完全不受影响）
        Widget tmp(rhs);
        // 第二步：用不抛的 swap 把 tmp 的内容换进 *this
        swap(tmp);
        return *this;
    }   // 若第一步抛异常，*this 完好无损 → 强保证
        // 若第二步抛异常... swap 不抛，所以不会发生

    void swap(Widget& other) noexcept {
        using std::swap;
        swap(name_, other.name_);
        swap(data_, other.data_);
    }
};

// 友元 swap（ADL 会优先找到它）
void swap(Widget& a, Widget& b) noexcept { a.swap(b); }
```

| copy-and-swap 的优点 | copy-and-swap 的代价 |
|---|---|
| 自动获得强异常安全保证 | 每次赋值多一次拷贝（即使是自赋值也拷贝） |
| 代码简洁，无需手工处理自赋值 | 大对象拷贝成本高 |
| 同时处理了自赋值（拷贝自己再 swap 自己） | 无法复用 rhs 的资源（移动赋值可以） |

> **自赋值安全**：copy-and-swap 天然处理自赋值——`Widget tmp(*this)` 拷贝自己，然后 swap 自己，结果不变。传统写法需要 `if (this != &rhs)` 检查。

### 2.4 不抛保证：哪些函数必须不抛

| 函数类别 | 为什么必须不抛 | 违反后果 |
|---|---|---|
| 析构函数 | 栈展开期间若析构再抛异常 → `std::terminate` | 程序直接终止 |
| swap | 强保证的提交操作必须不抛 | 强保证失效 |
| 移动构造/赋值 | 容器扩容依赖移动不抛来选择移动而非拷贝 | 退化为拷贝，性能暴跌 |
| `operator delete` | 资源释放失败无法恢复 | 泄漏或终止 |

C++11 起，**析构函数默认是 noexcept 的**（除非类的成员或基类的析构函数显式标了 `noexcept(false)`）。在析构函数中抛异常是未定义行为级别的严重错误。

```cpp
struct Bad {
    ~Bad() noexcept(false) { throw std::runtime_error("dtor threw"); }
};
// 栈展开期间 Bad 的析构抛异常 → std::terminate 直接终止程序
```

## 3. RAII 与异常安全

### 3.1 为什么 RAII 是异常安全的基础

异常的核心问题是：**函数可能在任意语句处提前退出**（throw 导致栈展开），而手工的资源释放在 `try` 块末尾，无法覆盖所有退出路径。RAII 把释放绑定到析构函数，而析构函数在栈展开时**必然**被调用——这是唯一能覆盖所有退出路径的机制。

```cpp
// 反例：裸指针手工管理，异常路径泄漏
void bad() {
    int* p = new int[1000];
    doSomething();          // 若这里抛异常 → p 永远不会被 delete → 泄漏
    delete[] p;             // 这行执行不到
}

// 正例：RAII 自动管理，任何退出路径都释放
void good() {
    auto p = std::make_unique<int[]>(1000);
    doSomething();          // 若抛异常 → 栈展开 → p 的析构自动释放 → 无泄漏
}                           // 正常返回也释放
```

### 3.2 标准库中的 RAII 设施

| RAII 类 | 管理的资源 | 头文件 |
|---|---|---|
| `std::unique_ptr` / `std::shared_ptr` | 堆内存 | `<memory>` |
| `std::lock_guard` / `std::unique_lock` | 互斥锁 | `<mutex>` |
| `std::fstream` / `std::ifstream` | 文件句柄 | `<fstream>` |
| `std::vector` / `std::string` | 动态数组/字符串内存 | `<vector>` / `<string>` |
| `std::jthread`（C++20） | 线程（析构自动 join） | `<thread>` |
| `std::scoped_lock`（C++17） | 多把锁（避免死锁） | `<mutex>` |

### 3.3 自定义 RAII 包装的完整示例

当标准库没有现成的 RAII 类时（如 C 库的 FILE*、POSIX fd、Windows 句柄），应当自己写一个小包装类：

```cpp
#include <cstdio>
#include <utility>

class FilePtr {
public:
    FilePtr() = default;
    explicit FilePtr(FILE* f) : f_(f) {}

    // 禁止拷贝（裸资源不可共享所有权）
    FilePtr(const FilePtr&) = delete;
    FilePtr& operator=(const FilePtr&) = delete;

    // 支持移动（转移所有权）
    FilePtr(FilePtr&& o) noexcept : f_(o.f_) { o.f_ = nullptr; }
    FilePtr& operator=(FilePtr&& o) noexcept {
        if (this != &o) {
            close();
            f_ = std::exchange(o.f_, nullptr);
        }
        return *this;
    }

    ~FilePtr() { close(); }

    FILE* get() const { return f_; }
    explicit operator bool() const { return f_ != nullptr; }

private:
    void close() noexcept {
        if (f_) {
            std::fclose(f_);
            f_ = nullptr;
        }
    }
    FILE* f_ = nullptr;
};

// 使用：任何退出路径都自动 fclose
void processFile(const char* path) {
    FilePtr fp(std::fopen(path, "rb"));
    if (!fp) return;
    // ... 读取、处理，即使抛异常也会自动关闭
}
```

### 3.4 构造函数中抛异常的安全处理

构造函数抛异常时，**对象本身的析构不会被调用**（因为对象未构造完成），但已构造的成员和基类子对象会被逆序析构。这意味着：如果成员是 RAII 类型，它们的资源会被正确释放；如果成员是裸指针，就会泄漏。

```cpp
class BadWidget {
    int* buf1_;
    int* buf2_;
public:
    BadWidget() : buf1_(new int[100]), buf2_(new int[100]) {
        // 若 buf2_ 的 new 抛 bad_alloc：
        // buf1_ 已构造（是指针，析构什么都不做）→ buf1_ 泄漏！
        throw std::runtime_error("init failed");
    }
    ~BadWidget() { delete[] buf1_; delete[] buf2_; }  // 构造失败时不会调用
};

class GoodWidget {
    std::unique_ptr<int[]> buf1_;   // RAII 成员
    std::unique_ptr<int[]> buf2_;
public:
    GoodWidget() : buf1_(std::make_unique<int[]>(100)),
                   buf2_(std::make_unique<int[]>(100)) {
        // 若 buf2_ 抛异常：buf1_ 的析构（unique_ptr）自动执行 → 无泄漏
        throw std::runtime_error("init failed");
    }
    // 无需手写析构
};
```

> **准则**：类的资源成员一律用 RAII 类型（智能指针、容器、锁守卫），不要用裸指针。这样构造函数抛异常时资源自动释放，且不需要手写析构函数（rule of zero）。

## 4. noexcept 深度解析

### 4.1 noexcept 的两种形态

| 形态 | 含义 | 示例 |
|---|---|---|
| `noexcept` / `noexcept(true)` | 承诺不抛异常；若实际抛出 → `std::terminate` | `void f() noexcept;` |
| `noexcept(false)` | 可能抛异常（默认状态） | `void f() noexcept(false);` |
| `noexcept(表达式)` | 条件式 noexcept：表达式为 true 则不抛 | `void f() noexcept(std::is_nothrow_move_constructible_v<T>);` |

### 4.2 noexcept 不是"禁止抛异常"，而是"抛了就 terminate"

```cpp
void f() noexcept {
    throw std::runtime_error("oops");   // 编译通过！运行时直接 std::terminate
}
```

noexcept 是**对调用者的承诺**，不是对编译器的强制约束。编译器不会阻止 noexcept 函数内部抛异常，但运行时如果真的抛了，程序直接终止（不栈展开、不 catch）。

### 4.3 noexcept 与移动语义：vector 扩容的关键

这是面试最高频的考点之一。vector 扩容时需要把旧元素搬移到新内存。搬移有两个选择：

| 选择 | 操作 | 异常安全 |
|---|---|---|
| 移动构造 | 窃取资源（快） | 若移动构造抛异常，旧元素已被破坏、新元素未完成 → 无法回滚 → **违反基本保证** |
| 拷贝构造 | 深拷贝（慢） | 若拷贝抛异常，旧元素完好 → 回滚释放新内存 → **强保证** |

标准库的选择是 `std::move_if_noexcept`：**只有当移动构造标了 noexcept 时才用移动，否则退化为拷贝**。

```cpp
#include <vector>
#include <utility>

class Fast {
public:
    Fast() = default;
    Fast(const Fast&) { /* 深拷贝，慢 */ }
    Fast(Fast&&) noexcept { /* 窃取资源，快 */ }  // 标了 noexcept
};

class Slow {
public:
    Slow() = default;
    Slow(const Slow&) { /* 深拷贝 */ }
    Slow(Slow&&) { /* 窃取资源，但没标 noexcept */ }  // 没标 noexcept
};

std::vector<Fast> vf;  // 扩容用移动 → 快
std::vector<Slow> vs;  // 扩容退化为拷贝 → 慢一个数量级，且无任何告警
```

> **准则**：移动构造函数和移动赋值运算符**一律标 `noexcept`**。这是 Modern C++ 最容易被忽略但影响最大的规则之一。忘标 noexcept 的后果是性能静默下降，没有编译错误、没有运行时告警。

### 4.4 noexcept 运算符：编译期查询

`noexcept(表达式)` 可以在编译期判断一个表达式是否承诺不抛异常，常用于条件式 noexcept：

```cpp
#include <type_traits>

template <typename T>
void swap(T& a, T& b) noexcept(noexcept(a.swap(b))) {
    a.swap(b);
}
// 含义：如果 T::swap 不抛异常，那么这个 swap 也不抛异常

// 标准库提供了便捷的 type trait：
static_assert(std::is_nothrow_move_constructible_v<std::vector<int>>);
static_assert(!std::is_nothrow_copy_constructible_v<std::vector<int>>);
// vector 的移动构造是 noexcept 的，拷贝构造不是（可能分配失败）
```

### 4.5 何时该标 noexcept

| 函数 | 是否标 noexcept | 原因 |
|---|---|---|
| 析构函数 | 默认就是 | C++11 起默认 noexcept |
| 移动构造/赋值 | **必须标** | vector 扩容优化依赖 |
| swap | **应该标** | 强保证的提交操作 |
| `operator delete` | 应该标 | 释放不应失败 |
| 简单的 getter / 纯计算函数 | 可以标 | 确实不抛 |
| 可能分配内存的函数 | **不要标** | `new` 可能抛 bad_alloc |
| 可能调用用户回调的函数 | **不要标** | 回调可能抛任何异常 |
| 虚函数 | 谨慎 | 派生类重写时 noexcept 规格必须兼容（更严格可以，更宽松不行） |

## 5. 异常 vs 错误码：选型决策

### 5.1 全面对比

| 维度 | 异常（exception） | 错误码（error code） |
|---|---|---|
| 正常路径性能 | 零开销（不进入 catch 时无运行时代价，现代编译器零成本异常模型） | 每次调用都要检查返回值 |
| 错误路径性能 | 有开销（栈展开、异常表查找，通常比正常返回慢） | 与正常返回相同 |
| 可读性 | 主逻辑与错误处理分离，代码清晰 | 错误检查侵入主逻辑，`if (rc) return rc;` 层层嵌套 |
| 遗漏风险 | 低：未捕获的异常向上传播直至 terminate，不会被静默忽略 | 高：忘记检查返回值是最常见的 bug 之一 |
| 无法忽略 | 是：异常必须被处理或传播 | 否：调用者可以完全忽略返回值 |
| 携带信息 | 丰富：异常对象可带错误消息、错误码、堆栈等 | 有限：通常只是一个整数 |
| 适用场景 | 应用层、业务逻辑、库的公共 API | 性能敏感的热路径、嵌入式、内核、C 兼容接口 |
| 资源安全 | 配合 RAII 自动安全 | 需要手工确保每个错误路径都释放资源 |

### 5.2 混合策略：C++23 std::expected

现代 C++ 趋势是**异常用于真正的异常情况，expected 用于可预期的失败**：

```cpp
#include <expected>
#include <string>

enum class ParseError { InvalidFormat, OutOfRange };

std::expected<int, ParseError> parseNumber(std::string_view s) {
    if (s.empty()) return std::unexpected(ParseError::InvalidFormat);
    // ... 解析
    return 42;   // 成功
}

void demo() {
    auto result = parseNumber("123");
    if (result) {
        use(*result);
    } else {
        log_error(result.error());
    }
}
```

`std::expected<T, E>` 的价值：**编译期强制调用者处理错误**（不检查就用 `*result` 是 UB），同时不破坏主流程的可读性。它是异常和错误码之间的中间道路。

### 5.3 决策树

```text
                    这个失败是"异常"还是"预期"？
                           |
              +------------+------------+
              |                         |
         真正的异常                 可预期的失败
    （内存不足、逻辑错误）       （文件不存在、输入格式错）
              |                         |
       用 throw + try/catch      用 expected / optional / 错误码
              |
       配合 RAII 保证资源安全
```

## 6. 标准异常体系

### 6.1 异常继承层次

```cpp
std::exception (根，<exception>)
├── std::bad_alloc (<new>)              — new 失败
├── std::bad_cast (<typeinfo>)          — dynamic_cast 引用转换失败
├── std::bad_typeid (<typeinfo>)        — typeid 解引用空指针
├── std::bad_exception (<exception>)     — 异常规格违规（C++17 前）
├── std::logic_error (<stdexcept>)       — 逻辑错误（可在运行前检测）
│   ├── std::invalid_argument            — 非法参数
│   ├── std::domain_error                — 定义域错误
│   ├── std::length_error                — 长度超限
│   ├── std::out_of_range                — 越界（at()、vector::at）
│   └── std::future_error (C++11)       — future 操作错误
└── std::runtime_error (<stdexcept>)     — 运行时错误（仅运行时可检测）
    ├── std::range_error                 — 范围错误
    ├── std::overflow_error              — 算术上溢
    ├── std::underflow_error             — 算术下溢
    ├── std::regex_error (C++11)         — 正则表达式错误
    ├── std::system_error (C++11)        — 系统调用错误（带 error_code）
    │   └── std::ios_base::failure       — IO 错误
    └── std::filesystem::filesystem_error (C++17) — 文件系统错误
```

### 6.2 logic_error vs runtime_error

| 维度 | `std::logic_error` | `std::runtime_error` |
|---|---|---|
| 语义 | 程序逻辑错误，理论上可在运行前通过代码审查避免 | 运行时环境导致的错误，无法在运行前预测 |
| 典型例子 | 传了空指针、越界访问、非法枚举值 | 内存不足、文件打不开、网络断开 |
| 可否预防 | 可以（修正代码逻辑） | 不可完全预防（环境因素） |
| 面试区分 | "程序员的错" | "世界的错" |

### 6.3 自定义异常的最佳实践

```cpp
#include <stdexcept>
#include <string>

// 准则1：继承自标准异常体系（通常是 runtime_error 或 logic_error）
// 准则2：提供 what() 消息
// 准则3：支持错误码（可选但推荐）
class NetworkError : public std::runtime_error {
public:
    enum class Code { Timeout, ConnectionRefused, DnsFailure };

    NetworkError(Code code, const std::string& msg)
        : std::runtime_error(msg), code_(code) {}

    Code code() const noexcept { return code_; }

private:
    Code code_;
};

// 使用
void connect() {
    throw NetworkError(NetworkError::Code::Timeout, "connect timed out after 30s");
}

try {
    connect();
} catch (const NetworkError& e) {
    log("network error: code={}, msg={}", static_cast<int>(e.code()), e.what());
} catch (const std::exception& e) {
    log("other error: {}", e.what());
}
```

| 自定义异常准则 | 说明 |
|---|---|
| 继承标准异常 | 让 `catch (const std::exception&)` 能捕获你的异常 |
| 用 `what()` 带消息 | 标准接口，日志和调试都依赖它 |
| 附加错误码 | 便于程序化处理（不同错误码走不同恢复路径） |
| 不要继承多个异常基类 | 菱形继承、切片风险 |
| 异常类型要具体 | `NetworkError` 比 `std::runtime_error` 更利于精确 catch |
| 按引用捕获 | `catch (const NetworkError& e)` 避免切片 |

## 7. 异常处理的常见坑与最佳实践

### 7.1 常见坑汇总

| 坑 | 现象 | 解决方案 |
|---|---|---|
| 裸 new 后抛异常 | 内存泄漏 | 用 `make_unique` / `make_shared` |
| 移动构造忘标 noexcept | vector 扩容退化为拷贝，性能暴跌 | 移动构造/赋值一律 `noexcept` |
| 析构函数抛异常 | 栈展开期间二次异常 → `std::terminate` | 析构函数绝不抛异常，内部 try/catch 吞掉 |
| `catch (...)` 吞异常 | 掩盖 bug，调试困难 | 至少记录日志后重新抛出，或只在最顶层用 |
| 按值 catch 异常 | 异常对象切片（派生类信息丢失） | 一律 `catch (const T& e)` |
| `throw e;` 重新抛出 | 拷贝构造新异常（切片） | 用 `throw;`（无操作数）重新抛出原异常 |
| 异常规格 `throw(T)` | C++17 已移除，动态异常规格被废弃 | 用 `noexcept` 替代 |
| 在 `noexcept` 函数中抛异常 | 运行时 `std::terminate` | 确保 noexcept 函数内部真的不抛，或内部 catch |
| 构造函数中做复杂初始化 | 部分成员构造失败 → 泄漏 | 成员用 RAII 类型，或用工厂函数 + 两段式 init |
| `catch` 中修改全局状态后不重抛 | 异常被静默处理，调用者不知道失败了 | 要么完全处理，要么记录后重新抛出 |
| 异常对象中携带指针 | 指针指向的内存可能已释放 | 异常对象用值语义（string、vector），不要带裸指针 |

### 7.2 最佳实践清单

1. **默认用异常**：现代 C++ 应用层代码默认使用异常处理错误，配合 RAII 保证资源安全。
2. **资源一律 RAII**：不要在函数中出现裸 `new`/`fopen`/`lock`，全部交给智能指针、fstream、lock_guard。
3. **移动构造标 noexcept**：这是性能优化的硬性要求，不是可选建议。
4. **析构函数绝不抛异常**：如果析构中调用可能抛的操作，内部 `try/catch` 吞掉并记录日志。
5. **按引用捕获异常**：`catch (const std::exception& e)` 是标准写法。
6. **catch 顺序从具体到宽泛**：先 catch 派生类，最后 catch 基类和 `...`。
7. **不要用异常做控制流**：异常用于"错误"，不要用 throw/catch 模拟 goto 或循环 break。
8. **强保证用 copy-and-swap**：需要事务语义的赋值运算符，copy-and-swap 是标准解法。
9. **自定义异常继承标准体系**：让通用 catch 能捕获你的异常，同时提供 what() 消息。
10. **顶层兜底 catch**：在 `main` 或线程入口处放 `catch (const std::exception&)` + `catch (...)` 兜底，防止未捕获异常直接 terminate 时连日志都没有。

```cpp
// 顶层兜底的标准写法
int main() {
    try {
        return runApp();
    } catch (const std::exception& e) {
        std::fprintf(stderr, "fatal error: %s\n", e.what());
        return 1;
    } catch (...) {
        std::fprintf(stderr, "fatal error: unknown exception\n");
        return 1;
    }
}
```

## 8. 面试高频考点速查

| 考点 | 一句话答案 |
|---|---|
| 异常安全三保证 | 不抛（绝不抛）、强（失败状态不变）、基本（失败仍有效不泄漏） |
| 为什么移动构造要 noexcept | vector 扩容用 move_if_noexcept，非 noexcept 退化为拷贝 |
| 析构函数能抛异常吗 | 不能，栈展开期间二次异常 → terminate；C++11 起析构默认 noexcept |
| RAII 为什么是异常安全基础 | 析构在栈展开时必然调用，覆盖所有退出路径 |
| copy-and-swap 为什么提供强保证 | 先在副本上操作（失败不影响原对象），再用不抛 swap 提交 |
| 按值 catch 的问题 | 异常对象切片，派生类信息丢失 |
| `throw;` vs `throw e;` | `throw;` 重新抛出原异常（保留类型）；`throw e;` 拷贝构造新异常（切片） |
| noexcept 函数抛了会怎样 | 运行时 std::terminate，不栈展开 |
| 构造函数抛异常时析构会调用吗 | 对象本身的析构不调用（未构造完成），但已构造的成员/基类逆序析构 |
| logic_error vs runtime_error | logic_error 是逻辑错误（可预防）；runtime_error 是运行时环境错误（不可完全预防） |
