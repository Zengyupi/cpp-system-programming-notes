## 1. 概述

### 1.1 三大类总览

| 类别 | 关注点 | 模式（一句话意图） |
|---|---|---|
| 创建型 | 对象**怎么来** | 单例（全局唯一实例）、工厂方法（子类决定造什么）、抽象工厂（造一族相关对象）、建造者（分步构造复杂对象）、原型（克隆已有实例） |
| 结构型 | 对象**怎么组装** | 适配器（转换接口）、装饰器（动态叠加职责）、代理（控制访问）、外观（简化子系统入口）、组合（树形结构统一处理）、桥接（抽象与实现分离）、享元（共享细粒度对象） |
| 行为型 | 对象**怎么协作** | 观察者（一对多通知）、策略（可替换算法）、状态（状态驱动行为）、命令（封装请求）、模板方法（固定流程留定制点）、迭代器（统一遍历）、访问者（双分派操作）、中介者、备忘录、职责链、解释器 |

### 1.2 SOLID 原则

| 原则 | 含义 | 违反的信号 |
|---|---|---|
| S 单一职责 | 一个类只有一个变化的理由 | 类名里出现 And/Manager/Helper |
| O 开闭 | 对扩展开放，对修改关闭 | 加功能要改一串 if/else 或既有类 |
| L 里氏替换 | 子类必须能无感替换父类 | 子类偷偷抛异常/收窄前置条件 |
| I 接口隔离 | 不强迫依赖用不到的方法 | 实现类一堆空方法 |
| D 依赖倒置 | 依赖抽象而非具体实现 | 高层模块直接 new 低层类 |

**模式与原则的关系**：模式是实现原则的具体手法。策略模式服务于开闭与依赖倒置；代理与装饰器服务于单一职责的分离。

### 1.3 模式是手段不是目的

| 提醒 | 说明 |
|---|---|
| 先有痛点再上模式 | "两次法则"：同样的重复出现第三次，再抽象 |
| 模式有成本 | 类数量膨胀、间接层增加、调试跳转变深 |
| 现代语言内置了很多模式 | 范围 for 内置迭代器；lambda 替代命令/策略；variant 替代访问者 |
| 一切以可测性为检验 | 模式用得好，单元测试（见「15-单元测试与测试框架.md」）就好写 |

## 2. 创建型模式

### 2.1 单例（Singleton）

**Meyers' Singleton——C++11 后的唯一正确写法：**

```cpp
class Logger {
public:
    static Logger& instance() {
        static Logger logger;    // C++11 起标准保证：局部静态变量初始化线程安全
        return logger;           // （magic statics，见「01-语言基础与类型系统.md」7.3）
    }

    Logger(const Logger&) = delete;             // 禁拷贝
    Logger& operator=(const Logger&) = delete;

    void log(const std::string& msg);

private:
    Logger() = default;          // 构造私有：禁止外部创建
    ~Logger() = default;
    FILE* out_ = stderr;
};

// 用法：Logger::instance().log("started");
```

| 实现方式 | 初始化时机 | 线程安全 | 问题 |
|---|---|---|---|
| Meyers（函数内 static） | 首次调用（懒汉） | C++11 起**由标准保证** | — |
| 饿汉（namespace 级 static 成员） | 程序启动（静态初始化） | 是 | 可能初始化顺序惨案；启动即付出代价 |
| 手写双检锁（DCLP） | 首次调用 | C++11 前**无正确写法**（指令重排） | 历史包袱，删掉 |
| `std::call_once` | 首次调用 | 是 | 比 Meyers 啰嗦，无优势 |

**单例的固有缺陷**：全局可变状态 → 单元测试难以隔离（无法注入 mock）、隐藏依赖（调用 Logger 的代码与 Logger 硬绑定）、多线程下时序难推理。因此工程实践是：**进程内天然唯一的东西（日志器、配置中心）用单例；业务对象即使"现在只有一个"也走依赖注入**。

### 2.2 工厂方法与抽象工厂

```cpp
// 产品
struct Button { virtual void draw() const = 0; virtual ~Button() = default; };
struct WinButton : Button { void draw() const override { /* Windows 风格 */ } };
struct MacButton : Button { void draw() const override { /* macOS 风格 */ } };

// 工厂方法：把"造哪个"延迟到子类
struct ButtonFactory {
    virtual std::unique_ptr<Button> create() const = 0;
    virtual ~ButtonFactory() = default;
};
struct WinFactory : ButtonFactory {
    std::unique_ptr<Button> create() const override { return std::make_unique<WinButton>(); }
};
struct MacFactory : ButtonFactory {
    std::unique_ptr<Button> create() const override { return std::make_unique<MacButton>(); }
};

void buildUi(const ButtonFactory& factory) {          // 客户端只认抽象
    auto btn = factory.create();
    btn->draw();
}
```

```cpp
// 抽象工厂：一次造"一族"相关产品
struct UiKit {
    virtual std::unique_ptr<Button> makeButton() const = 0;
    virtual std::unique_ptr<Menu>  makeMenu() const = 0;
    virtual ~UiKit() = default;
};
```

| 对比 | 工厂方法 | 抽象工厂 |
|---|---|---|
| 造什么 | 单个产品 | 一族相关产品 |
| 扩展新产品 | 加一个工厂子类即可（开闭） | 要改抽象接口（违反开闭） |
| 典型场景 | 序列化器、连接器 | 跨平台 UI 套件、主题换肤 |

**工厂返回值必须是 `std::unique_ptr`**——返回裸指针的时代结束了（泄漏责任不清）。简单场景不必写工厂类：一个返回 `unique_ptr` 的普通函数就是轻量工厂（见第 5 章）。

### 2.3 建造者（Builder）

```cpp
class HttpRequest {
public:
    HttpRequest& setUrl(std::string url)   { url_ = std::move(url); return *this; }
    HttpRequest& setMethod(std::string m)  { method_ = std::move(m); return *this; }
    HttpRequest& setTimeout(int ms)        { timeout_ms_ = ms; return *this; }
    HttpRequest& addHeader(std::string k, std::string v) {
        headers_.emplace_back(std::move(k), std::move(v));
        return *this;
    }
    void send();

private:
    std::string url_, method_ = "GET";
    int timeout_ms_ = 3000;
    std::vector<std::pair<std::string, std::string>> headers_;
};

// 链式调用：可读、参数可选、字段有默认值
auto req = HttpRequest{}
    .setUrl("https://api.example.com/v1/data")
    .setMethod("POST")
    .addHeader("Content-Type", "application/json");
req.send();
```

适用信号：构造参数多（>4 个）、大量可选参数、希望调用代码自文档化。C++20 后，简单的参数聚合还可以用指定初始化器 `Config{.retries = 3, .timeout = 1000}` 达成同样效果。

### 2.4 原型（Prototype）

```cpp
struct Enemy {
    int hp{}, speed{};
    std::vector<std::string> skills;
    virtual std::unique_ptr<Enemy> clone() const = 0;     // "复制我"
    virtual ~Enemy() = default;
};

struct Goblin : Enemy {
    std::unique_ptr<Enemy> clone() const override {
        return std::make_unique<Goblin>(*this);          // 拷贝构造即克隆
    }
};

Goblin template_goblin;             // 从配置加载、调好参数
auto e1 = template_goblin.clone();  // 每次出场：克隆而不再手工配置
```

适用：创建成本高（解析配置/加载资源）但差异小、运行期才知道具体类型。本质是"以拷贝构造为虚函数"。

## 3. 结构型模式

### 3.1 适配器（Adapter）

```cpp
// 目标接口（我们想要的）
struct Logger { virtual void write(std::string_view msg) = 0; virtual ~Logger() = default; };

// 遗留实现（接口不兼容）
struct LegacyPrinter {
    void print_line(const char* s);                     // 只接受 NUL 结尾、自带换行
};

// 对象适配器：组合 + 转发（优先用组合）
struct LegacyAdapter : Logger {
    explicit LegacyAdapter(LegacyPrinter& p) : printer_(p) {}
    void write(std::string_view msg) override {
        std::string line(msg);                          // string_view 不保证 NUL 结尾
        printer_.print_line(line.c_str());
    }
private:
    LegacyPrinter& printer_;
};
```

| 形式 | 实现 | 评价 |
|---|---|---|
| 对象适配器 | 组合被适配者 | 灵活，可适配一族（推荐） |
| 类适配器 | 多继承目标接口 + 被适配者 | 能暴露被适配者保护成员，但耦合死 |

注意区分：**适配器改变接口（让不兼容的双方合作），装饰器保持接口（增强同一接口的行为）**。标准库中 `stack`/`queue` 就是容器适配器（把 deque 的接口改造成栈语义）。

### 3.2 装饰器（Decorator）

```cpp
struct Stream {                                   // 统一接口
    virtual void write(std::string_view d) = 0;
    virtual ~Stream() = default;
};
struct FileSink : Stream {
    void write(std::string_view d) override;      // 真正落盘
};

struct Decorator : Stream {                      // 装饰器基类：持有一个内部流并转发
    explicit Decorator(std::shared_ptr<Stream> s) : inner_(std::move(s)) {}
    void write(std::string_view d) override { inner_->write(d); }
protected:
    std::shared_ptr<Stream> inner_;
};

struct Buffered : Decorator {                    // 职责1：加缓冲
    using Decorator::Decorator;
    void write(std::string_view d) override {
        buf_ += d;
        if (buf_.size() >= 4096) flush();
    }
    void flush() { inner_->write(buf_); buf_.clear(); }
private:
    std::string buf_;
};
struct Timestamped : Decorator {                 // 职责2：加时间戳前缀
    using Decorator::Decorator;
    void write(std::string_view d) override {
        inner_->write(now() + " " + std::string(d));
    }
    static std::string now();
};

// 运行期自由叠加：
auto sink = std::make_shared<Timestamped>(
              std::make_shared<Buffered>(
                std::make_shared<FileSink>()));
sink->write("hello");
```

这是"**组合优于继承**"的教科书案例：想要"带缓冲+带时间戳的文件流"，继承需要 2×2 组合爆炸，组合只需像洋葱一样包两层。iostream 的 streambuf 链、Java IO 流都是此模式。缺点：层层包装后调用栈变深，调试需要追踪多层（见第 8 章坑表）。

### 3.3 代理（Proxy）

```cpp
class BigImage {                       // 加载昂贵的大图
public:
    explicit BigImage(std::string path);
    void draw() const;
};

class ImageProxy {                     // 与本体同接口，按需加载 + 计数控制
public:
    explicit ImageProxy(std::string path) : path_(std::move(path)) {}
    void draw() const {
        if (!image_) image_ = std::make_unique<BigImage>(path_);   // 懒加载
        image_->draw();
    }
private:
    std::string path_;
    mutable std::unique_ptr<BigImage> image_;   // mutable：draw 是 const 也能改缓存
};
```

| 代理 vs 装饰器 | 代理 | 装饰器 |
|---|---|---|
| 意图 | **控制访问**（懒加载、权限、远程） | **增强行为** |
| 对象生命周期 | 常代替本体存在 | 一定包裹本体 |
| 与智能指针的联系 | unique_ptr 是"资源所有权的代理"：客户端经它操作对象、由它决定释放时机 | — |

### 3.4 外观（Facade）

```cpp
class Compiler {                        // 一 个门面，挡住五个子系统
public:
    bool compile(const std::string& src) {
        auto tokens = lexer_.tokenize(src);
        auto ast    = parser_.parse(tokens);
        if (!optimizer_.run(ast)) return false;
        return codegen_.emit(ast, output_);
    }
private:
    Lexer lexer_; Parser parser_; Optimizer optimizer_; CodeGen codegen_; Output output_;
};
// 客户端从"调 5 个类、按正确顺序"变成"调 1 个方法"
```

价值：给复杂子系统一个高层入口、减少客户端耦合。它**不禁止**绕过门面直接用子系统（与代理的强制控制不同）。

### 3.5 组合（Composite）

```cpp
struct Node {                                        // 叶子与容器统一接口
    virtual ~Node() = default;
    virtual int size() const = 0;
};
struct File : Node {
    int sz;
    explicit File(int s) : sz(s) {}
    int size() const override { return sz; }
};
struct Dir : Node {
    std::vector<std::shared_ptr<Node>> children;     // 容器持有孩子（可以既有叶又有容器）
    int size() const override {
        int total = 0;
        for (auto& c : children) total += c->size(); // 递归：统一处理，无需判型
        return total;
    }
    void add(std::shared_ptr<Node> n) { children.push_back(std::move(n)); }
};

Dir root;
root.add(std::make_shared<File>(100));
auto sub = std::make_shared<Dir>();
sub->add(std::make_shared<File>(50));
root.add(sub);
root.size();          // 150：客户端完全不区分文件/目录
```

适用：树形结构（文件系统、UI 控件树、组织架构、场景图）。与访问者联用可对整棵树做类型分派操作。

### 3.6 桥接（Bridge）

```cpp
struct Renderer {                                    // 实现维度
    virtual std::string renderCircle() const = 0;
    virtual std::string renderSquare() const = 0;
    virtual ~Renderer() = default;
};
struct VectorRenderer : Renderer {
    std::string renderCircle() const override;
    std::string renderSquare() const override;
};
struct RasterRenderer : Renderer {
    std::string renderCircle() const override;
    std::string renderSquare() const override;
};

struct Shape {                                       // 抽象维度
    explicit Shape(const Renderer& r) : r_(r) {}
    virtual std::string draw() const = 0;
    virtual ~Shape() = default;
protected:
    const Renderer& r_;
};
struct Circle : Shape {
    using Shape::Shape;
    std::string draw() const override { return r_.renderCircle(); }
};
struct Square : Shape {
    using Shape::Shape;
    std::string draw() const override { return r_.renderSquare(); }
};

// 2 种渲染器 × N 种形状：继承法需要 2N 个类且每加一个维度翻倍；
// 桥接法：抽象持有一个实现引用，两维度独立扩展。
```

适用信号：类型存在两个独立变化的维度（形状×渲染、平台×协议），继承类数呈笛卡尔积爆炸。

## 4. 行为型模式

### 4.1 观察者（Observer）：完整可运行示例

```cpp
#include <algorithm>
#include <cstdint>
#include <functional>
#include <iostream>
#include <utility>
#include <vector>

class TemperatureSensor {                             // Subject（被观察者）
public:
    using Callback = std::function<void(double)>;
    using ConnectionId = std::uint64_t;

    ConnectionId subscribe(Callback cb) {             // 订阅：返回连接号
        ConnectionId id = next_id_++;
        observers_.push_back({id, std::move(cb)});
        return id;
    }
    void unsubscribe(ConnectionId id) {               // 退订
        observers_.erase(
            std::remove_if(observers_.begin(), observers_.end(),
                           [id](const Observer& o) { return o.id == id; }),
            observers_.end());
        // C++20 起可以直接：std::erase_if(observers_, ...);
    }
    void update(double value) {
        value_ = value;
        for (auto& o : observers_) o.cb(value);       // 广播（回调中退订的坑见第 8 章）
    }
private:
    struct Observer { ConnectionId id; Callback cb; };
    std::vector<Observer> observers_;
    ConnectionId next_id_ = 0;
    double value_ = 0.0;
};

// RAII 连接对象：作用域结束自动退订——防止"观察者已死、回调还挂着"
class ScopedSubscription {
public:
    ScopedSubscription(TemperatureSensor& s, TemperatureSensor::Callback cb)
        : sensor_(&s), id_(s.subscribe(std::move(cb))) {}
    ~ScopedSubscription() { if (sensor_) sensor_->unsubscribe(id_); }

    ScopedSubscription(const ScopedSubscription&) = delete;
    ScopedSubscription& operator=(const ScopedSubscription&) = delete;
    ScopedSubscription(ScopedSubscription&& o) noexcept : sensor_(o.sensor_), id_(o.id_) {
        o.sensor_ = nullptr;
    }
private:
    TemperatureSensor* sensor_;
    TemperatureSensor::ConnectionId id_;
};

int main() {
    TemperatureSensor sensor;
    {
        ScopedSubscription display(sensor, [](double t) {
            std::cout << "[display] " << t << " C\n";
        });
        ScopedSubscription alarm(sensor, [](double t) {
            if (t > 30.0) std::cout << "[alarm] too hot!\n";
        });
        sensor.update(23.5);      // 两条回调都触发
        sensor.update(35.0);      // display + alarm
    }                              // 离开作用域：自动退订
    sensor.update(40.0);          // 无任何输出：悬垂回调已被 RAII 拆除
}
```

要点：现代实现用 `std::function` 注册（不再强制继承 Observer 抽象类）；**RAII 订阅对象是 C++ 观察者区别于 Java 的关键**——它把"忘记退订导致悬垂回调"这个模式级头号 bug 变成了编译器自动处理的事。GUI 信号槽、事件总线、发布订阅中间件都是此模式。

### 4.2 策略（Strategy）：传统 vs 现代两版

```cpp
// ---- 传统实现：继承 ----
struct SortStrategy {
    virtual void sort(std::vector<int>& v) const = 0;
    virtual ~SortStrategy() = default;
};
struct StdQuickSort : SortStrategy {
    void sort(std::vector<int>& v) const override { std::sort(v.begin(), v.end()); }
};
class Sorter {                                   // 上下文：持有一个策略
public:
    explicit Sorter(std::unique_ptr<SortStrategy> s) : strategy_(std::move(s)) {}
    void run(std::vector<int>& v) const { strategy_->sort(v); }
private:
    std::unique_ptr<SortStrategy> strategy_;
};

// ---- 现代实现：直接注入可调用对象 ----
class Sorter2 {
public:
    using Strategy = std::function<void(std::vector<int>&)>;
    explicit Sorter2(Strategy s) : strategy_(std::move(s)) {}
    void run(std::vector<int>& v) const { strategy_(v); }
private:
    Strategy strategy_;
};

Sorter2 s([](std::vector<int>& v) {              // lambda 即策略，零类定义
    std::sort(v.begin(), v.end(), std::greater<int>{});
});
```

| 维度 | 继承版 | std::function 版 |
|---|---|---|
| 定义一个策略的成本 | 一个类 | 一个 lambda |
| 运行期换策略 | 支持 | 支持 |
| 状态携带 | 成员变量 | lambda 捕获 |
| 热路径性能 | 虚调用（可内联，视实现） | 类型擦除调用（同样间接） |
| 更快的选择 | — | 模板参数注入（编译期单态，零间接） |

```cpp
template <typename S>                       // 第三种：编译期策略，零开销
void run(std::vector<int>& v, S s) { s(v); }
```

STL 到处是策略：`std::sort` 的比较器、`unordered_map` 的 hash/equal、`priority_queue` 的比较器——全是策略模式的函数化。

### 4.3 状态（State）

```cpp
// ---- 版本1：枚举 + switch（状态少、行为简单时首选，嵌入式常用）----
class TrafficLight {
public:
    enum class State { Green, Yellow, Red };
    void next() {
        switch (state_) {
        case State::Green:  state_ = State::Yellow; break;
        case State::Yellow: state_ = State::Red;    break;
        case State::Red:    state_ = State::Green;  break;
        }
    }
    const char* name() const {
        switch (state_) {
        case State::Green:  return "绿";
        case State::Yellow: return "黄";
        case State::Red:    return "红";
        }
        return "?";
    }
private:
    State state_ = State::Red;
};

// ---- 版本2：State 模式（每个状态一个类，行为复杂/状态多时用）----
struct LightState {
    virtual const char* name() const = 0;
    virtual std::unique_ptr<LightState> next() const = 0;   // 状态自己决定下一个状态
    virtual ~LightState() = default;
};
struct Green; struct Red;
struct Yellow : LightState {
    const char* name() const override { return "黄"; }
    std::unique_ptr<LightState> next() const override;
};
struct Green : LightState {
    const char* name() const override { return "绿"; }
    std::unique_ptr<LightState> next() const override { return std::make_unique<Yellow>(); }
};
struct Red : LightState {
    const char* name() const override { return "红"; }
    std::unique_ptr<LightState> next() const override { return std::make_unique<Green>(); }
};
std::unique_ptr<LightState> Yellow::next() const { return std::make_unique<Red>(); }

class TrafficLight2 {                       // 上下文：只转发给当前状态对象
public:
    TrafficLight2() : state_(std::make_unique<Red>()) {}
    void next() { state_ = state_->next(); }
    const char* name() const { return state_->name(); }
private:
    std::unique_ptr<LightState> state_;
};
```

**与 if/else 的本质区别**：状态转换规则分散在各状态类内部（每个状态自己知道自己去哪），新增状态不改旧状态的 switch。与《../09-嵌入式开发/07-嵌入式工程实践与设计模式.md》中状态机模式的呼应：资源受限平台常用**状态表（二维数组：当前状态 × 事件 → 次态 + 动作函数指针）**替代类层次，查表 O(1)、RAM 占用可预算。

### 4.4 命令（Command）：与 lambda 等价的现代写法

```cpp
// ---- 传统：命令类层次 ----
struct Light {                       // 接收者（Receiver）
    void on();
    void off();
};
struct Command {
    virtual void execute() = 0;
    virtual ~Command() = default;
};
struct LightOnCmd : Command {        // 具体命令：绑定一个接收者与一个动作
    explicit LightOnCmd(Light& l) : light_(l) {}
    void execute() override { light_.on(); }
private:
    Light& light_;
};

// ---- 现代：std::function<void()> 就是命令对象 ----
using Cmd = std::function<void()>;

class RemoteControl {                      // 按钮绑定命令 + 撤销栈
public:
    void bind(int slot, Cmd on) { slots_[slot] = std::move(on); }
    void press(int slot) {
        if (slots_[slot]) {
            history_.push_back(slots_[slot]);    // 记录以支持撤销/重放
            slots_[slot]();
        }
    }
    // 撤销：绑定"逆操作"命令即可
    void bindUndo(int slot, Cmd undo) { undos_[slot] = std::move(undo); }
private:
    std::map<int, Cmd> slots_, undos_;
    std::vector<Cmd> history_;                   // 命令队列：日志、重放、宏录制的基础
};

Light light;                                  // 接收者
RemoteControl remote;
remote.bind(1, [&light] { light.on(); });     // lambda 捕获接收者，就地成命令
remote.bindUndo(1, [&light] { light.off(); });
remote.press(1);                              // 执行 + 进入历史记录
```

命令模式的价值在"命令成为一等公民"之后才显现：排队、延迟执行、撤销/重做、日志回放、宏录制、线程池任务。而这些恰好是 `std::function`/lambda 的主场——**命令模式在 C++ 里已经"溶解"进了语言**。

### 4.5 模板方法（Template Method）与 NVI 惯用法

```cpp
class DataPipeline {                     // 模板方法：run() 固定流程
public:
    void run() {                         // 公有非虚：流程骨架不可被改写
        load();
        if (validate()) transform();     // 定制点藏在私有虚函数里
        save();
    }
private:
    virtual void load() = 0;             // 子类只填空
    virtual bool validate() { return true; }      // 有默认实现的钩子
    virtual void transform() = 0;
    virtual void save() = 0;
protected:
    ~DataPipeline() = default;           // NVI：基类析构不必 public virtual
};
```

**NVI（Non-Virtual Interface）**：公有函数非虚（定流程、做校验和日志），虚函数设为 private（纯定制点）。好处：基类牢牢控制"怎么调"，子类只决定"做什么"。这是对"所有可重写函数都该 public virtual"直觉的修正。

### 4.6 迭代器（Iterator）

STL 已把迭代器做成了语言级基础设施：容器提供 `begin()/end()`，范围 for 与百个算法消费它。自定义容器的标准姿势：

```cpp
class FixedStack {                       // 使自己可被范围 for 与 STL 算法使用
    int data_[64];
    std::size_t n_ = 0;
public:
    int* begin() { return data_; }               // 正向迭代
    int* end()   { return data_ + n_; }
    const int* begin() const { return data_; }
    const int* end()   const { return data_ + n_; }
    void push(int v) { data_[n_++] = v; }
};

FixedStack s; s.push(3); s.push(1);
for (int x : s) { }                              // 直接可用
std::sort(s.begin(), s.end());                   // 算法也能用
```

**结论：不要手写 Iterator 类**——除非容器不是线性存储（此时参考 std::list 源码）。C++20 ranges 进一步泛化了它。

### 4.7 访问者（Visitor）：double dispatch 简述

```cpp
struct Circle; struct Square;
struct ShapeVisitor {                          // 访问者：对每种具体类型一个重载
    virtual void visit(const Circle&) = 0;
    virtual void visit(const Square&) = 0;
    virtual ~ShapeVisitor() = default;
};
struct Shape {
    virtual void accept(ShapeVisitor& v) const = 0;   // 第一次分派：虚调用
    virtual ~Shape() = default;
};
struct Circle : Shape {
    void accept(ShapeVisitor& v) const override { v.visit(*this); }  // 第二次：按静态类型选重载
};
struct Square : Shape {
    void accept(ShapeVisitor& v) const override { v.visit(*this); }
};

struct AreaCalculator : ShapeVisitor {         // 新操作=新访问者，不改类型层次（开闭）
    double total = 0;
    void visit(const Circle& c) override { total += 3.14159 * c.r * c.r; }
    void visit(const Square& s) override { total += s.side * s.side; }
};

AreaCalculator calc;
for (auto& s : shapes) s->accept(calc);
```

难点是 double dispatch：C++ 虚函数只按**一个**对象的动态类型分派；`accept` 里再调 `visit(*this)` 时 `*this` 的静态类型已是具体类型，于是两个动态类型都确定了。**代价**：加新形状要改所有访问者。**现代替代**：`std::variant<Circle, Square>` + `std::visit`（见「06-现代C++新特性.md」5.5），同样是封闭类型集合+开放操作集合，但不需要侵入形状类。

## 5. 现代 C++ 对传统模式的替代表

| 模式 | 传统实现 | 现代替代 | 备注 |
|---|---|---|---|
| 策略 | 抽象基类 + 继承 | `std::function` / lambda 参数 / 模板参数 | STL 算法比较器即此 |
| 命令 | Command 类层次 | `std::function<void()>` + lambda | 撤销栈=存逆 lambda |
| 单例 | Singleton 类（含 getInstance） | 函数内 `static` 局部变量 | Meyers 版 |
| 观察者 | 抽象 Observer 基类 | `std::function` 注册表 + RAII 连接 | 本篇 4.1 |
| 建造者 | Builder 类 | 链式 setter / C++20 指定初始化器 | `Config{.x=1}` |
| 访问者 | double dispatch | `std::variant` + `std::visit` | 类型集合封闭时 |
| 工厂 | 工厂类 | 返回 `unique_ptr` 的函数 / `make_unique` | 简单场景免类 |
| 模板方法 | 继承 + 虚函数 | `std::function` 钩子 / std::execution 风格 | 视需要组合化 |
| 装饰器 | 继承 Decorator 基类 | 范围/视图组合（C++20 ranges） | 数据处理场景 |
| 状态 | 状态类层次 | `enum class` + 函数表 / variant | 视复杂度分层 |

**判断标准**：需要运行期多态/状态携带 → 类版本；只是"传一段行为" → 函数版本。别用类表达"一个函数就能表达的事"。

## 6. 嵌入式场景的模式应用

（硬件细节见《../09-嵌入式开发/05-嵌入式Linux系统与驱动开发.md》，此处只谈模式取舍。）

| 场景 | 推荐做法 | 注意事项 |
|---|---|---|
| 状态机（协议、控制流程） | **状态表**：二维数组「当前状态 × 事件 → {次态, 动作函数指针}」 | RAM/ROM 占用可精确预算；比 switch 更适合工具生成 |
| 中断回调解耦（观察者） | ISR 只置标志/入队，主循环消费 | 回调在 ISR 上下文执行时**不可**加锁/分配/printf；用 `volatile`/`std::atomic` 传递事件 |
| 硬件外设封装（单例） | 外设对象全局唯一，构造函数做寄存器初始化 | 静态初始化顺序与上电时序：别在全局对象构造里依赖其他全局对象（用 constinit 或显式 init()）；避免动态内存 |
| 资源管理（RAII） | GPIO/总线句柄 RAII 包装 | unique_ptr + 静态内存池替代堆 |
| 装饰器/代理 | 慎用多层动态分发 | 实时路径上的虚调用与堆分配要经预算；ROM 空间紧张时模板膨胀也计入成本 |
| 驱动多实例 | 模板参数传基址（编译期单态）优于运行期虚表 | `template <uintptr_t Base> class Uart` 零间接调用 |

## 8. 常见问题与坑

| 问题 | 原因与解决方案 |
|---|---|
| 过度设计：三个类的小工具用了五个模式 | 模式是手段不是目的。遵循"三次法则"，先写直白的代码，重复出现再抽象 |
| 单例让单元测试一团糟 | 全局状态无法替换 mock。把单例限制在进程级天然唯一物；业务对象走构造函数注入（见「15-单元测试与测试框架.md」） |
| 观察者悬垂回调：监听对象析构后通知仍调用它 | 注册方死亡但没退订。用 RAII 订阅对象（ScopedSubscription）自动退订；或观察者持有 weak_ptr |
| 在构造函数里注册 this（把自己交给回调/观察者） | 此时对象尚未构造完成，回调若立即触发将访问半成品；多线程下更危险。注册动作放到单独的 `init()`/工厂函数中完成 |
| 广播回调的过程中有订阅者退订，程序崩溃 | 遍历 observers_ 时 erase 使迭代器失效。退订先入延迟队列、广播结束后统一处理，或遍历副本 |
| 装饰器层层包装，断点要跳七八层 | 间接层的固有成本。控制层数（最多两三层）；关键路径给装饰器加日志；必要时退回直接组合 |
| 工厂返回裸指针，调用方忘记 delete | 所有权不清。工厂一律返回 `std::unique_ptr`（转 shared 是调用方一行的事） |
| 每个工厂/策略/命令都写一个类，文件爆炸 | 现代 C++ 里函数即对象：lambda + std::function 覆盖大部分轻量场景（见第 5 章替代表） |
| 单例在 main 结束后析构时访问了已销毁的其他全局对象 | 静态对象销毁顺序与构造相反且跨编译单元不确定。析构里别依赖别的全局/单例；或用"不死单例"（new 出来永不 delete，交 OS 回收） |
| 装饰器与适配器分不清，用错 | 适配器**改接口**（鸭子接口不匹配）；装饰器**保接口加行为**。问自己：客户端调用的是不是同一个接口？ |
| 状态机用类层次实现，但状态对象频繁 new/delete | 转换高频时分配开销大。状态对象无状态化（单例/flyweight），或退回枚举+switch/状态表 |
| 虚函数做"策略"导致热路径虚调用开销 | 性能敏感路径改模板参数注入（编译期多态零间接）或函数指针表 |
| 访问者加一个新形状要改所有访问者类 | 访问者牺牲"类型可扩展"换"操作可扩展"。类型经常加就别用访问者，改 variant 或普通虚函数 |
