## 1. CPU 指令集架构：RISC 与 CISC

### 1.1 ARM 与 x86 的底层逻辑

| 对比维度 | ARM 架构 | x86 架构 |
| :--- | :--- | :--- |
| **指令集类型** | RISC（精简指令集） | CISC（复杂指令集，但内部解码为类 RISC 微指令 μops） |
| **指令长度** | AArch64 定长 4 字节（Thumb/Thumb-2 为 2/4 混合） | 变长 1~15 字节，解码复杂 |
| **通用寄存器** | AArch64 有 31 个通用寄存器（x0~x30） | x86-64 有 16 个（rax…r15），历史包袱重 |
| **设计哲学** | 单条指令简单、硬件精简、能效优先，复杂操作靠指令序列 | 单条指令功能强、向后兼容几十年、硬件复杂、峰值性能强 |
| **内存模型** | **弱序（weak ordering）**：硬件允许更多乱序，需内存屏障（DMB/DSB/ISB）保证顺序 | **强序（TSO，总存储序）**：默认"写按程序序可见"，编程心智更简单 |
| **功耗与散热** | 功耗低、发热小，SoC 常可无风扇 | 功耗高、通常需主动散热 |
| **典型应用** | 手机、IoT、树莓派、云服务器（AWS Graviton、Ampere、鲲鹏）、Apple Silicon | 传统 PC、高性能服务器、多数笔记本 |
| **特权级** | EL0（用户）/EL1（内核）/EL2（Hypervisor）/EL3（安全监控） | Ring3（用户）/Ring0（内核）（虚拟化用 VMX root/non-root） |
| **Linux 支持** | 主流发行版均有 `arm64/aarch64` 版本 | 最成熟，所有发行版原生支持 |

> **关键纠偏**："x86 性能一定比 ARM 强"是过时印象。同制程同功耗下 ARM 核心数/能效常占优，苹果 M 系列、AWS Graviton、华为鲲鹏已在桌面与服务器市场证明自己；而"x86 是纯 CISC"也不准确——现代 x86 CPU 前端把复杂指令拆成 μops 交给类 RISC 乱序核心执行。

### 1.2 三大指令集对比（含 RISC-V）

| 维度 | x86-64 | ARM64(AArch64) | RISC-V |
| --- | --- | --- | --- |
| 归属 | Intel/AMD | ARM 公司（授权 IP） | 开源（免授权费） |
| 指令设计 | 变长 CISC | 定长 RISC | 模块化：基础 RV32I/64I + 可选 M(乘除)/A(原子)/F/D(浮点)/C(压缩) 等扩展 |
| 内存模型 | TSO 强序 | 弱序（RCsc） | RVWMO 弱序（可配 TSO 扩展 Ztso） |
| 生态 | PC/服务器垄断 | 移动+服务器+嵌入式全覆盖 | 嵌入式爆发中，服务器/高性能进行中 |
| 典型 | 酷睿/霄龙 |  Cortex-A、苹果、鲲鹏 | 平头哥、赛昉、ESP32-C 系列 |

### 1.3 调用约定（Calling Convention）——函数参数怎么传

| 平台 | 整型/指针参数寄存器（前 N 个） | 其余参数 | 系统调用号 |
| --- | --- | --- | --- |
| x86-64 System V（Linux/macOS） | `rdi, rsi, rdx, rcx, r8, r9`（第 7 个起压栈） | 栈（从右向左） | `rax`，参数 `rdi,rsi,rdx,r10,r8,r9`（注意是 r10 不是 rcx） |
| AArch64（ARM64） | `x0~x7`（前 8 个） | 栈 | `x8`，参数 `x0~x5` |
| 32 位 x86 cdecl | 全部压栈 | 栈 | `eax`，栈传参 |

> 返回值：整型/指针放 `rax`（x86-64）或 `x0`（ARM64）。这套约定决定了 gdb 反汇编、内联汇编、跨语言 FFI 时去哪里取参数。

### 1.4 ARM 常见术语辨析（易混淆）

| 术语 | 含义 |
| --- | --- |
| `ARMv7` / `ARMv8` / `ARMv9` | **指令集架构版本**（v8 起引入 64 位 AArch64 执行态） |
| `Cortex-A` / `Cortex-R` / `Cortex-M` | **内核产品线**：A=应用处理器（跑 Linux）、R=实时、M=单片机（跑 RTOS） |
| `aarch64` / `arm64` | 64 位执行状态/架构名（同一概念，Linux/GCC 常用 aarch64，Apple/部分语境用 arm64） |
| `armhf` / `armv7` | 32 位硬浮点 ABI，常见于老树莓派、Cortex-A7/A9 |
| `x86_64` / `AMD64` | x86 的 64 位扩展（AMD 率先设计，故得名 AMD64；与 Intel 64 基本兼容） |

## 2. 微架构与存储层次（性能问题的物理根源）

### 2.1 缓存层次

```text
                容量递增、速度递减、单价递减
  寄存器 ──► L1(I/D,每核私有,~32K) ──► L2(每核私有,256K~1M)
     │                                      │
     │                                      ▼
     │                              L3(所有核共享,几 MB~几十 MB)
     │                                      │
     ▼                                      ▼
  0 周期                              主内存 DDR（~百 ns 级）
```

| 层级 | 归属 | 典型延迟量级 | 说明 |
| --- | --- | --- | --- |
| 寄存器 | 核内 | 0 | 编译期分配 |
| L1 | 每核私有（分指令 i-cache/数据 d-cache） | ~1ns / 4 周期 | 最快缓存 |
| L2 | 每核私有 | ~3-5ns / 12 周期 | |
| L3/LLC | 多核共享 | ~10-20ns / 40 周期 | 跨核通信用它 |
| 内存 DDR | 所有核 | ~60-100ns | 缓存未命中（cache miss）的代价 |

- **缓存行（cache line）= 64 字节**：缓存与内存按行搬运，不是按字节。这解释了两个高频现象：
  - **伪共享（false sharing）**：两个线程各改各的变量，但变量落在同一缓存行，缓存行在核间反复弹跳，性能骤降。解法是 `alignas(64)` 填充隔离（见《../04-并发编程/04-原子操作与C++内存模型.md》SPSC 队列）。
  - **顺序局部性**：连续访问数组比链表快得多——硬件预取器能预测顺序访问。

### 2.2 NUMA：多路服务器的"远近内存"

```text
单路(UMA)：所有核经同一内存控制器，访问任何内存等距
多路(NUMA)：
   Node0: CPU0(核0..N) ──本地总线──► 本地内存(快)
      │ 跨节点互连带(UPI / Infinity Fabric)
   Node1: CPU1(核0..N) ──本地总线──► 本地内存(快)
   CPU0 访问 Node1 的内存 = 远端访问，慢 1.5~2 倍
```

| 实践点 | 说明 |
| --- | --- |
| 查看拓扑 | `lscpu`、`numactl -H`、`numastat` |
| 绑定 | `numactl --cpunodebind=0 --membind=0 ./app` 让进程只用本地内存 |
| 部署原则 | 线程/进程尽量固定在一个 NUMA 节点，避免跨节点访存；Redis/数据库尤其敏感 |

### 2.3 超线程/SMT、大页

| 概念 | 本质 | 注意 |
| --- | --- | --- |
| 超线程（Intel HT）/SMT（ARM/AMD） | 一个物理核模拟两个逻辑核，**共享执行单元与缓存**，一个线程等内存时另一个用执行单元 | 对缓存缺失多的负载提速明显；计算密集且都打满时收益小甚至互相干扰；`lscpu` 里 Core/Thread 可区分 |
| 标准页 4KB | 虚拟→物理映射项多，TLB（页表缓存）易 miss | 一般场景 |
| **大页 2MB/1GB** | 一页覆盖更大内存，显著减少 TLB miss | 数据库、DPDK、大堆 JVM/Redis 提速；`/proc/meminfo` 看 HugePages；透明大页 THP 对低延迟程序可能引入抖动，常建议关闭 |

## 3. Linux 系统整体架构

### 3.1 用户态与内核态

```cpp
┌──────────────────────── 用户态（EL0 / Ring3）────────────────────────┐
│  应用程序  bash / nginx / redis / 你的 C++ 进程                        │
│  标准库 glibc（malloc/printf 是用户态封装，本身不是内核）               │
└───────────────▲───────────────────────────────────┬──────────────────┘
                │ 系统调用 syscall（软中断/专用指令陷入，切换特权级）      │
                │ read/write/fork/mmap/futex/epoll_wait ...             │
┌───────────────┴───────────────────────────────────▼──────────────────┐
│                          内核态（EL1 / Ring0）  Linux Kernel           │
│  进程调度 │ 内存管理(mm/vmalloc/页表) │ VFS 文件抽象 │ 网络协议栈(TCP/IP)│
│  系统调用接口(syscall)        中断/异常处理        设备驱动            │
└───────────────▲──────────────────────────────────────────────────────┘
                │ 驱动通过总线/寄存器访问
┌───────────────┴──────────────────────────────────────────────────────┐
│  硬件：CPU / 内存 / 磁盘 / 网卡 / 外设                                  │
└───────────────────────────────────────────────────────────────────────┘
```

| 概念 | 说明 |
| --- | --- |
| 用户态/内核态 | 用户程序不能直接操作硬件，必须通过**系统调用**陷入内核；切换有开销（保存寄存器、切栈、特权级、可能的页表/缓存影响），所以要减少无谓 syscall（如 `readv/writev`、`sendmmsg` 批量、用户态栈 DPDK） |
| 系统调用 | 用户态进入内核的唯一正规入口；`strace -c ./app` 统计调用次数与耗时 |
| 内核子系统 | 进程/调度、内存管理、VFS（统一文件抽象）、网络栈、设备驱动模型、IPC |
| 伪文件系统 | `/proc`（进程与内核状态）、`/sys`（设备/驱动模型），不是真文件，读它实时由内核生成 |

### 3.2 从一次"读文件"看全栈协作

```text
fread() [glibc 用户态缓冲]
  → 不够则 read() 系统调用，陷入内核
  → VFS 找到文件系统（ext4/xfs...）
  → 页缓存 page cache 命中？命中直接拷回；未命中 → 块层 I/O 调度 → 磁盘驱动 → DMA 读盘
  → 数据经内核页缓存再 copy_to_user 到用户缓冲区
（网络同理：数据→网卡 DMA→内核协议栈→copy 到用户；零拷贝 sendfile/mmap 减少拷贝，见《../03-网络编程/02-IO多路复用与Reactor模型.md》）
```

## 4. 位数、数据模型、字节序与 ABI

| 概念 | 要点 |
| --- | --- |
| 32 位 vs 64 位 | 指针宽度 4→8 字节，虚拟地址空间从 ~3GB 扩到 128TB（x86-64 当前 48/57 位）；64 位才能用大内存与更多寄存器 |
| 数据模型 | Linux/macOS 64 位用 **LP64**（long=8、指针=8），Windows 用 **LLP64**（long=4、指针=8）——跨平台别用 `long` 存宽度敏感值，用 `<cstdint>`（详见《../01-语言基础/01-语言基础与类型系统.md》2.2） |
| 字节序 | x86、ARM 默认**小端**（低字节在低地址）；网络字节序为**大端**，跨主机协议要 `htonl/ntohl`；RISC-V 小端为主 |
| ABI | 应用二进制接口：调用约定、类型大小、对齐、名字修饰、系统调用方式的约定；ABI 不兼容则二进制不能直接链接运行（如 hard-float 的 armhf 与 soft-float 不能混用） |
| 目标三元组 | `架构-厂商-系统-库`，如 `x86_64-pc-linux-gnu`、`aarch64-linux-gnu`、`arm-none-eabi`（裸机），决定交叉工具链命名（见《../09-嵌入式开发/07-嵌入式工程实践与设计模式.md》13.1） |

## 5. Linux 发行版对决：四大主流家族

它们共享同一个 Linux 内核，但软件集合、包管理、更新策略、支持周期不同。

| 特性 | Debian / Ubuntu 系 | Red Hat 系 (RHEL/CentOS/Rocky/Alma) | Arch Linux | Fedora | openSUSE |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **定位** | 新手友好、开发者首选，桌面服务器兼顾 | 企业生产金标准，极致稳定 | 极客 DIY，高度可定制、追新 | RHEL 的上游试验田 | 企业与社区并重，管理工具强 |
| **包管理** | `apt`/`dpkg` | `dnf`(新)/`yum`(旧)/`rpm` | `pacman` | `dnf`/`rpm` | `zypper`/`rpm` |
| **更新策略** | 定期发布，有 LTS，稳定 | 稳定版支持周期极长（可达 10 年） | 滚动更新，软件最新 | 6 个月快发，生命周期短 | 常规版 Leap + 滚动版 Tumbleweed |
| **上手难度** | ★★（Ubuntu）~★★★（Debian） | ★★★ | ★★★★★ | ★★★ | ★★★ |
| **生态** | 社区最庞大、资料最多 | 企业认证软件多 | Arch Wiki 极其详尽 | 推动前沿 | YaST 图形化管理见长 |
| **适用** | 入门、开发、云服务器、桌面；Ubuntu LTS 也是流行服务器系统 | 关键业务、生产服务器、长期稳定；Rocky/Alma 是 CentOS 停更后的首选替代 | 追新、深度定制、理解系统内部 | 桌面尝鲜、为 RHEL 铺路 | 需要强大图形管理工具的管理员 |

> 其他常见：**Alpine**（musl libc + busybox，体积极小，容器镜像首选）、**Debian-slim**、国产 **openEuler / 麒麟 / openKylin / Anolis（龙蜥）/ TencentOS**。

## 6. 选型建议速查表

### 6.1 按场景选发行版

- **新手入门 & 日常开发**：**Ubuntu LTS**，社区大、问题好搜、WSL 体验最好。
- **生产服务器 & 企业**：**RHEL** 或免费兼容克隆 **Rocky / AlmaLinux / openEuler / Anolis**；求稳可选 **Debian Stable**。
- **极简容器镜像**：**Alpine**（注意 musl 与 glibc 的偶发差异，如 DNS、二进制兼容性）。
- **极客 / 深度玩家**：**Arch**，滚动更新、AUR 丰富，代价是要自己维护。
- **尝鲜**：**Fedora**，较早用上新内核/新特性。
- **嵌入式目标板**：开发主机任选（Ubuntu 最常见）；目标根文件系统用 **Buildroot/Yocto** 自己裁（见《../09-嵌入式开发/05-嵌入式Linux系统与驱动开发.md》第 10 章），树莓派官方 Raspberry Pi OS 基于 Debian。
- **国内/信创服务器**：关注 **openEuler / openKylin / Anolis**，对鲲鹏（aarch64）等国产 ARM 平台适配好。

### 6.2 按负载选硬件（后台开发视角）

| 负载类型 | CPU | 内存 | 磁盘 | 网络 |
| --- | --- | --- | --- | --- |
| 计算密集（编解码、AI 推理） | 核数/主频/向量指令（AVX/NEON）优先 | 带宽 | 一般 | 一般 |
| 内存型（Redis/缓存/内存计算） | 中等 | **越大越好、高频率、注意 NUMA** | NVMe 落盘 | 中等 |
| I/O 型（网关/数据库/消息） | 核数（并发连接） | 充足 | **NVMe SSD、关注 IOPS 与写放大** | **多队列网卡、带宽、offload** |
| 低延迟（高频交易/DPDK） | 高主频、关 SMT、核隔离 | 大页、NUMA 绑定 | 尽量避免 | 内核旁路、SR-IOV |

## 7. 查看当前系统的架构与环境

```bash
uname -a                  # 内核版本与架构全貌
uname -m                  # x86_64 / aarch64 / armv7l
arch                      # 同上
lscpu                     # 架构、字节序、核数/线程/插槽、缓存、NUMA、虚拟化
cat /proc/cpuinfo         # 每核详细信息（型号、标志位 flags：看是否支持 avx2/neon 等）
free -h                   # 内存与缓存/可用量
lsblk                     # 块设备拓扑
lspci / lsusb             # PCIe/USB 设备（网卡、显卡型号）
numactl -H                # NUMA 拓扑（多路服务器）
cat /etc/os-release       # 通用发行版信息（所有系统都有）
lsb_release -a            # 发行版信息（精简系统可能无此命令）
dpkg --print-architecture # Debian 系：软件包架构（amd64/arm64）
getconf LONG_BIT          # 32 还是 64
ldd --version | head -1   # glibc 版本（决定二进制能否在老系统跑）
```

> **部署黄金原则**：编译机的 glibc/内核不要比目标运行机新，否则会出现 `GLIBC_2.xx not found`（排查见《02-编译链接与加载原理.md》第 9 章）。

```text
架构：x86-64(CISC/TSO/16寄存器) | ARM64(RISC/弱序/31寄存器/EL0-3) | RISC-V(模块化/开源)
调用约定：x86-64 参数 rdi rsi rdx rcx r8 r9；ARM64 x0-x7；返回 rax / x0
缓存：L1 私有~1ns → L2 私有 → L3 共享~十几 ns → 内存~百 ns；缓存行 64B，警惕伪共享
NUMA：多路服务器优先本地内存，numactl 绑定；SMT 两逻辑核共享物理核
大页：2M/1G 减 TLB miss，数据库/DPDK 受益；低延迟场景警惕 THP 抖动
分层：用户态—syscall—内核态(调度/mm/VFS/网络栈/驱动)—硬件；strace 看系统调用
位数：指针 8 字节；LP64(Linux long=8) vs LLP64(Win long=4)；x86/ARM 小端、网络大端
发行版：开发 Ubuntu LTS；生产 RHEL/Rocky/openEuler；容器 Alpine；追新 Fedora/Arch
三元组：x86_64-pc-linux-gnu / aarch64-linux-gnu / arm-none-eabi(裸机)
环境：uname -m、lscpu、/etc/os-release、/proc/cpuinfo、numactl -H
```

## 9. 常见问题与坑

| 问题 | 原因与解决 |
| --- | --- |
| 程序在 x86 正常、ARM 上结果乱 | 弱内存模型暴露了缺失的同步/屏障；或依赖了小端、未对齐访问。用 `std::atomic`/显式屏障，对齐数据，别假设字节序 |
| 多线程统计数据吞吐上不去 | 检查伪共享（perf c2c），热点计数 `alignas(64)` 隔离或用每线程计数最后汇总 |
| 多路服务器内存带宽异常低 | 跨 NUMA 访问。`numastat` 看分布，进程与内存绑定同一节点 |
| 大内存应用偶发延迟尖刺 | TLB miss 或 THP 同步合并。预分配大页或关闭 THP（`echo never > .../enabled`） |
| 二进制拷到别的机器 `GLIBC_2.xx not found` | 编译机 glibc 太新。在更老的系统/容器里编译，或静态/带 sysroot 交叉构建 |
| 以为"核数"越多线性越快 | `lscpu` 区分物理核/逻辑核（SMT）；内存带宽、锁竞争、Amdahl 定律才是瓶颈 |
| Alpine 容器跑某二进制报 not found | musl 与 glibc 不兼容；换 glibc 基础镜像（debian-slim）或静态编译 |
| 容器里看到的是宿主机核数/内存 | /proc、lscpu 默认反映宿主；用 cgroup 限制并让程序读 cgroup（注意 K8s requests/limits） |
