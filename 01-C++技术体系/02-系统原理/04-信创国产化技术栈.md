## 1. 信创是什么、为什么需要

**信创 = 信息技术应用创新**，核心是在关键行业用自主可控的 IT 底座替代境外技术栈，解决"卡脖子"与供应链安全问题。

### 1.1 推进节奏："2 + 8 + N"

```text
2（最先、最彻底）：党政机关
8（重点行业）：金融、电力、电信、石油、交通、教育、医疗、航空航天
N（全面铺开）：消费、中小企业等全行业
```

### 1.2 技术栈分层（自下而上，每层都有国产替代）

```text
┌────────────────────────────────────────────────────────┐
│ 应用软件  ：电力 SCADA/工业网关、ERP、OA、行业业务系统    │
├────────────────────────────────────────────────────────┤
│ 中间件    ：应用服务器(TongWeb/BES)、消息、缓存、API 网关   │
├────────────────────────────────────────────────────────┤
│ 数据库    ：达梦/人大金仓/openGauss/GaussDB/TiDB/OceanBase │
├────────────────────────────────────────────────────────┤
│ 操作系统  ：银河麒麟/统信UOS/openEuler/龙蜥/openKylin      │
├────────────────────────────────────────────────────────┤
│ 芯片/固件 ：CPU(鲲鹏/飞腾/海光/龙芯)、BIOS/ BMC、整机、GPU  │
├────────────────────────────────────────────────────────┤
│ 基础设施  ：服务器、存储、交换机、云（华为云/天翼云等）       │
└────────────────────────────────────────────────────────┘
   横向贯穿：安全（等保、商密 SM2/3/4，见《../03-网络编程/03-网络安全与加密编程.md》）
```

> 对 C++ 后台/嵌入式工程师，信创改造的实际工作 90% 集中在三件事：**①把程序从 x86 重新编译/适配到国产 CPU（多为 ARM）；②把 MySQL/Oracle 换成国产数据库并改 SQL/驱动；③在国产 OS 上做兼容性认证。**

## 2. 国产 CPU：四条技术路线（选型第一关）

国产 CPU 最大的区别是**指令集架构路线**，这直接决定你的 C++ 程序要不要改、怎么编译（指令集基础见《03-系统架构与选型.md》第 1 章）。

| 厂商/品牌 | 指令集路线 | 架构来源 | 典型型号 | 特点与适用 |
| --- | --- | --- | --- | --- |
| **华为鲲鹏 Kunpeng** | ARMv8（AArch64） | 自研核（购买 ARMv8 永久授权 + 自研微架构） | 鲲鹏 920（服务器） | 服务器/云计算主力，多核高并发，生态最成熟，openEuler 配套 |
| **飞腾 Phytium** | ARMv8（AArch64） | ARM 授权 | 腾云 S 系列（服务器）、腾锐 D（桌面）、腾珑 E（嵌入式） | 党政/电力/工控份额大，**嵌入式与工业场景常见** |
| **海光 Hygon** | x86-64 | AMD Zen 授权合资 | 海光 C86 系列 | **x86 生态无缝兼容**，迁移成本最低，金融/算力中心多 |
| **兆核心 Zhaoxin** | x86-64 | 威盛 VIA x86 授权 | 开胜 KX、开先 KX-U | 桌面/工控，x86 兼容，单核性能一般 |
| **龙芯 Loongson** | **LoongArch（自主指令集）** | 完全自研，不再用 MIPS | 3A6000（桌面）、3C5000（服务器） | **自主化程度最高**，但生态需重新移植，软件要专门编译 |
| **申威 Sunway** | 自主 SW64 | 源自 DEC Alpha 自研 | 申威 26010（神威·太湖之光） | 超算/特种领域，生态封闭，民用少 |

### 2.1 按"迁移成本"给 C++ 程序排序

```text
海光/兆芯(x86)        ：二进制/源码几乎直接跑，成本最低（注意 glibc/内核版本）
鲲鹏/飞腾(ARM64)      ：源码重新编译 + 修少量平台相关代码，主流路径（绝大多数信创项目）
龙芯(LoongArch)       ：需 LoongArch 工具链重新移植，第三方库要有 LoongArch 版，成本最高
申威(SW64)            ：基本只在特种/超算圈，普通业务很少接触
```

### 2.2 关键认知：ARM 授权 ≠ 受制于人

鲲鹏/飞腾拿到的是 **ARMv8 指令集授权（架构授权）**，微架构核自研，可自主迭代；指令集只是"语言规范"，真正的 CPU 设计能力在自己手里。而海光走 x86 兼容路线、龙芯走完全自主路线，是不同的产业权衡（生态成熟度 vs 自主彻底性），面试能讲清这层区别是加分项。

## 3. 国产操作系统：都是 Linux，但要分清关系

国产 OS 几乎都基于 Linux 内核，区别在上层定制、包管理、商业支持与合规认证。

| 系统 | 厂商/背景 | 基础 | 包管理 | 定位 |
| --- | --- | --- | --- | --- |
| **银河麒麟 Kylin V10** | 麒麟软件（中标软件+天津麒麟合并） | Ubuntu/Debian 与自研内核线 | `apt/dpkg`（服务器版也有 rpm 线） | 党政/电力/军工市占高，信创招标最常见 |
| **统信 UOS** | 统信软件（深度 Deepin 团队） | Debian | `apt/dpkg` | 桌面体验最好，党政桌面+服务器 |
| **openEuler（欧拉）** | 华为开源、开放原子基金会 | 独立社区发行版 | `dnf/rpm` | **开源底座**，麒麟/统信/华为 EulerOS 等多个商业版基于它，服务器主流 |
| **龙蜥 Anolis OS** | 阿里/龙蜥社区（兼容 RHEL） | RHEL/CentOS 替代 | `dnf/rpm` | 云上 CentOS 替代，服务器 |
| **openKylin（开放麒麟）** | 社区 | 桌面 | `apt` | 桌面开源生态 |
| 华为 EulerOS / 麒麟信安 / 普华 / 凝思 | 各厂商 | 多基于 RHEL/openEuler | rpm 为主 | 电力/工控行业定制（凝思在电力常见） |

> **别被名字绕晕**：判断一个国产系统"怎么用"，最快方式是 `cat /etc/os-release` 看它基于 Debian 还是 RHEL 系，决定用 `apt` 还是 `yum/dnf`；看 `uname -m` 是 `x86_64` 还是 `aarch64/loongarch64`，决定架构。命令见《03-系统架构与选型.md》第 7 章。

### 3.1 国产 OS 上的开发心智

- 内核、glibc、gcc、systemd 都是熟悉的那套，**POSIX 编程、epoll、多线程代码无需改**；
- 差异主要在：软件源里的库版本可能较老、部分闭源第三方只提供 x86 版需找 ARM 版或自编译、安全加固策略（默认防火墙、SELinux/强制访问控制）更严；
- 商业版提供长期支持与等保/商密认证，这是招标硬门槛，不是纯技术问题。

## 4. 国产数据库（C++ 后台适配的重头戏）

### 4.1 分类与代表产品

| 类别 | 产品 | 出身/兼容 | 典型场景 |
| --- | --- | --- | --- |
| **传统关系型（集中式）** | **达梦 DM8** | 自研、高度兼容 Oracle 语法 | 党政/电力/金融去 O（Oracle）首选之一 |
| | **人大金仓 KingbaseES（KES）** | 基于 PostgreSQL 内核 | 党政/能源，PG 兼容、迁移工具成熟 |
| | 神舟通用、南大通用 GBase 8s | 自研/Informix 线 | 政务、专项 |
| **开源关系型** | **openGauss** | 华为开源（PG 血统、已深度自研） | 国采开源底座，很多商业库基于它 |
| | GaussDB | 华为商业版（集中式+分布式） | 金融/电信 |
| **NewSQL/分布式** | **OceanBase**（蚂蚁）、**TiDB**（PingCAP） | MySQL 协议兼容、原生分布式 | 金融级高并发、水平扩展、去 IOE |
| 分析型/HTAP | GaussDB(DWS)、ClickHouse 国产发行、StarRocks/Doris | 列存 | 数仓、实时分析 |

### 4.2 兼容性：两条主线

```text
去 Oracle 路线：Oracle ──► 达梦 DM8（PL/SQL、序列、存储过程兼容度高）/ 人大金仓(Oracle 兼容模式)
去 MySQL  路线：MySQL  ──► TiDB / OceanBase（MySQL 协议与方言，应用改动小）
去 PG 路线 ：PostgreSQL ─► openGauss / 人大金仓(PG 模式)
```

### 4.3 C++ 程序如何连国产数据库

| 接口 | 说明 |
| --- | --- |
| **ODBC** | 最通用：各国产库都提供 ODBC 驱动，unixODBC + DSN，跨库可换，**信创项目最保险的选择** |
| 达梦 DPI / DM CI | 达梦原生 C 接口（类似 OCI），性能高、绑定 DM |
| 金仓/openGauss `libpq` | PG 系用 libpq C 接口，原 PostgreSQL 代码几乎不动 |
| MySQL C API / 连接池 | TiDB/OB 走 MySQL 协议，原 MySQL 客户端代码直接连 |
| 商用连接池/中间件 | 如提供读写分离、分库分表代理 |

```c
// ODBC 通用流程（达梦/金仓都走这套，换库只换驱动名与 DSN）
SQLAllocHandle(SQL_HANDLE_ENV, ...);                 // 环境
SQLSetEnvAttr(..., SQL_ATTR_ODBC_VERSION, SQL_OV_ODBC3);
SQLAllocHandle(SQL_HANDLE_DBC, env, &dbc);
SQLDriverConnect(dbc, 0, (SQLCHAR*)"DSN=DM8;UID=SYSDBA;PWD=xxx;", ...);
SQLExecDirect(stmt, (SQLCHAR*)"SELECT id,name FROM device WHERE id=?", SQL_NTS);
// 参数绑定 SQLBindParameter、列绑定 SQLBindCol，与具体数据库解耦
```

### 4.4 SQL 适配常见坑

- **分页**：MySQL `LIMIT`、Oracle/达梦 `ROWNUM`、PG/openGauss `LIMIT/OFFSET`，用 ORM/中间层屏蔽或按库写方言；
- **自增**：MySQL `AUTO_INCREMENT` vs Oracle/达梦**序列 sequence + 触发器**、PG 的 serial/identity；
- **数据类型/函数差异**：字符串拼接（`CONCAT` vs `||`）、日期函数、`IFNULL/NVL/COALESCE`、隐式类型转换规则不同；
- **关键字冲突、大小写敏感、保留字**：达梦默认大写标识符、MySQL 小写不敏感，表名/字段名要统一规范；
- **存储过程/PL-SQL**：去 O 项目里最重的一块，达梦兼容度最高但仍需逐个调试；
- **迁移工具**：各厂自带 DTS/迁移助手（达梦 DTS、金仓 KCSQL/KDTS）做结构+数据迁移，但**存储过程、触发器、特殊函数必须人工回归**。

## 6. C++ 程序迁移到国产 ARM（鲲鹏/飞腾）实战

这是信创里 C++ 工程师的核心技能。好消息：**只要代码标准、可移植，绝大多数情况"重新编译 + 修几处平台假设"即可。**

### 6.1 迁移流程

```text
1. 盘点：收集源码 + 全部第三方依赖（有没有只提供 x86 .so 的闭源库？这是最大风险）
2. 搭环境：aarch64 国产机/鲲鹏云服务器/openEuler，装 gcc、cmake
3. 重新编译：先编依赖库（ARM 版），再编业务，逐个解决编译错误
4. 修平台问题：char 符号、对齐、字节序、弱内存序、内联汇编、SIMD（见 6.2）
5. 功能回归 + 性能对比（x86 vs ARM），用 perf 重新调优
6. 兼容性认证测试，拿互认证证书
```

### 6.2 必查的可移植性问题（高频踩坑）

| 问题 | x86 上"碰巧没事"，ARM 上爆雷 | 正确写法 |
| --- | --- | --- |
| **`char` 有无符号** | x86 Linux 默认 `char` 有符号；ARM 默认**无符号** | 明确写 `signed char`/`unsigned char`，别裸用 `char` 存数值 |
| **非对齐访问** | x86 容忍非对齐（慢）；ARM 可能**直接总线错误 SIGBUS** | 结构体对齐、`memcpy` 取多字节值、`__attribute__((packed))` 后别用裸指针强转 |
| **弱内存序** | x86 是 TSO 强序，缺屏障也"看起来对"；ARM 弱序会乱序 | 用 `std::atomic`/内存屏障，别靠"默认顺序"（原理见《03-系统架构与选型.md》1.1） |
| **数据模型/字宽** | 假设 `long==8`、指针转 int | 用 `<cstdint>` 的 `int32_t/int64_t`、`uintptr_t`（见《../01-语言基础/01-语言基础与类型系统.md》） |
| **内联汇编** | x86 汇编在 ARM 编不过 | 用编译器 builtin/可移植库替代，或写 ARM/NEON 版本 |
| **SIMD** | SSE/AVX  intrinsics 不可用 | 换 NEON/SVE，或让编译器自动向量化、用跨平台库（详见《../17-音视频游戏与AI/03-端侧AI推理部署.md》7.1） |
| **硬编码 x86 路径/so 名** | 写死 `libxxx_x86.so`、`/usr/lib64` | 用构建系统按架构选择，`/usr/lib/aarch64-linux-gnu` |
| **编译平台宏** | `#ifdef __x86_64__` 分支 | 增加 `__aarch64__`/`__loongarch__` 分支 |

### 6.3 编译方式：原生 vs 交叉编译

- **原生编译（推荐，最省事）**：直接在鲲鹏/飞腾 ARM 机器或 openEuler 虚拟机上 `cmake .. && make -j`，目标和编译机同架构，问题最少。
- **交叉编译**：x86 开发机上用 `aarch64-linux-gnu-g++` 编出 ARM 二进制（嵌入式/资源受限场景），需要 ARM 版 sysroot 和全部依赖的 ARM 版，方法见《../09-嵌入式开发/07-嵌入式工程实践与设计模式.md》交叉编译章节。

```text
# ARM 机上原生编译，开启可移植优化
g++ -O2 -std=c++17 -Wall main.cpp -o app
# -march 选择：按目标 CPU（鲲鹏 920 支持 -march=armv8-a 及特定扩展），
# 通用分发用 armv8-a 基线，别为了优化用目标机不支持的扩展
file app          # 确认是 ELF 64-bit LSB ... ARM aarch64
uname -m          # aarch64
```

### 6.4 性能调优差异

- ARM 核多、单核频率相对低：**高并发靠多核横向扩展**，线程/进程并行度匹配物理核，注意 NUMA（多路鲲鹏同样有 NUMA，见《03-系统架构与选型.md》2.2）；
- 用 `perf`（ARM  PMU）重新找热点，别照搬 x86 优化结论；
- 内存带宽、缓存行伪共享问题在多核 ARM 上同样存在，`alignas(64)` 依然有效；
- 编译器版本对 ARM 代码质量影响大，尽量用较新 gcc，开启 `-O2/-O3`。

| 事项 | 说明 |
| --- | --- |
| **兼容性互认证** | 应用软件要和国产 OS/CPU/数据库分别做适配测试，出具"兼容性认证证书"，进采购名录/生态兼容性清单 |

| **选型建议** | 求稳、迁移成本低 → 海光(x86)+达梦；走主流自主生态、长期投入 → 鲲鹏/飞腾(ARM)+openEuler/麒麟+openGauss/达梦；桌面 → 统信/麒麟 |

### 7.1 电力/工业方向的典型信创组合

电力与工业自动化领域的信创改造中，工业网关（规约转换网关）是核心设备类型之一，其典型技术栈组合为：**飞腾/鲲鹏 ARM + 银河麒麟（或凝思）+ 达梦/人大金仓 + 东方通 + 国密 + IEC104/61850 规约**。对于从事工业通信领域的开发者，将"**C++ 规约网关在 ARM 国产平台交叉编译运行 + 采集数据写入达梦 + 国密加密上送**"完整跑通一遍，是非常对口且具有差异化竞争力的项目实践方向。

## 9. 常见问题与坑

| 问题 | 原因与解决 |
| --- | --- |
| 程序在 x86 正常、移植 ARM 后数值异常/死循环 | 多为 `char` 符号不同或非对齐访问。显式 signed/unsigned、memcpy 取值、排查 packed 结构体 |
| ARM 上偶发 SIGBUS（总线错误） | 非对齐内存访问。对齐数据，禁止把 `char*` 强转 `int*` 直接解引用 |
| 多线程在 ARM 上偶发乱序、x86 从不复现 | 弱内存序。用 `std::atomic` 与正确内存序/屏障，不依赖 x86 TSO（见《../04-并发编程/04-原子操作与C++内存模型.md》） |
| 闭源第三方库只有 x86 的 .so | 迁移最大风险。找厂商要 ARM/LoongArch 版、找开源替代，或在隔离层用进程/服务替代 |
| 换达梦后 SQL 报错/结果不符 | 方言差异：序列、分页、字符串函数、大小写敏感、保留字。用迁移工具后逐句回归，存储过程人工调 |
| 应用连不上国产库 | 驱动架构不对（装了 x86 驱动）、端口/实例名、ODBC DSN 配置。优先 ODBC 统一抽象 |
| 二进制在老国产 OS 报 `GLIBC_2.xx not found` | 编译机 glibc 太新。在更老系统/容器编译，或静态链接（见《02-编译链接与加载原理.md》） |
| 用了 SSE/AVX intrinsics 编不过 | x86 SIMD。换 NEON/SVE 或自动向量化/跨平台库（见《../17-音视频游戏与AI/03-端侧AI推理部署.md》） |
| 以为"国产 OS 是另一套系统"要重学 | 都是 Linux 内核，POSIX/epoll/多线程照用；差异在包管理、库版本、安全加固、合规认证 |
| 性能不如预期就怀疑国产 CPU 不行 | 多为没按多核/NUMA 并行、编译没开优化、照搬 x86 调优。用 perf 重新定位，按 ARM 特性调 |
