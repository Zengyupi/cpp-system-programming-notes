## 1. 概述：从 .cpp 到可执行文件

```text
 main.cpp  libmath.h
    │  gcc -E   预处理（展开 #include / 宏 / 条件编译）
    ▼
 main.i    （纯 C++ 文本，所有头文件已并入）
    │  gcc -S   编译（语法/语义分析、优化、生成汇编）
    ▼
 main.s    （x86-64 汇编文本）
    │  gcc -c   汇编（汇编器 as 翻译成机器码）
    ▼
 main.o    （ELF 目标文件：机器码 + 符号表 + 重定位信息）
    │  gcc main.o -lmath -o app   链接（ld：符号解析 + 重定位 + 合并段）
    ▼
  app      （可执行 ELF；若链接了 .so 则运行时还需动态加载器）
```

| 阶段 | gcc 选项 | 产物 | 工具本体 | 中间产物是否文本 |
| --- | --- | --- | --- | --- |
| 预处理 | `gcc -E main.cpp -o main.i` | `.i` | cpp 预处理器 | 是（可直接读） |
| 编译 | `gcc -S main.i -o main.s` | `.s` | cc1plus | 是（汇编文本） |
| 汇编 | `gcc -c main.s -o main.o` | `.o` | as | 否（ELF 二进制） |
| 链接 | `gcc main.o libmath.a -o app` | 可执行 | ld | 否 |

> 记忆法：`-E`xpand、`-S`ource（出汇编）、`-c`ompile（只到目标文件）。`g++` 等价于 `gcc` + 按 C++ 处理 + 链接 C++ 运行时库。

## 2. 预处理

### 2.1 #include 的两种形式

| 形式 | 查找规则 | 用途 |
| --- | --- | --- |
| `#include <foo>` | 只搜 `-I`/系统目录列表 | 系统头、第三方安装的头 |
| `#include "foo"` | 先搜当前文件所在目录，找不到再按 `<>` 规则 | 项目内部头文件 |

`-I` 与系统默认目录查看：

```cpp
g++ -E -x c++ - -v < /dev/null     # 打印搜索路径列表（#include <...> 与 #include "..." 段）
g++ -I/home/me/proj/include -c main.cpp
```

### 2.2 宏、条件编译与预定义宏

```cpp
#define MAX(a, b) ((a) > (b) ? (a) : (b))    // 带参宏：参数与整体都要括号
#define LOG_LEVEL 2
#if LOG_LEVEL >= 2
  #define LOG(msg) std::cerr << msg << '\n'
#else
  #define LOG(msg)                            // 编译期裁剪：零开销
#endif
```

| 常用预定义宏 | 含义 | 示例值 |
| --- | --- | --- |
| `__FILE__` / `__LINE__` | 当前文件名 / 行号 | `"main.cpp"` / `42` |
| `__FUNCTION__` / `__func__` | 当前函数名 | `"main"` |
| `__DATE__` / `__TIME__` | 编译日期/时间 | |
| `__cplusplus` | C++ 标准版本号 | `201103L`(11) `201402L`(14) `201703L`(17) `202002L`(20) |
| `__x86_64__` 等 | 目标平台宏 | 判别架构/编译器 |

### 2.3 头文件守卫 vs #pragma once

| 方式 | 写法 | 特点 |
| --- | --- | --- |
| 宏守卫 | `#ifndef X_H` `#define X_H` … `#endif` | 标准保证；全平台通用 |
| `#pragma once` | 文件首行一句 | 非标准但所有主流编译器支持；不怕宏名撞车；对"同文件多路径挂载"（符号链接等）可能误判 |

## 3. 编译阶段

### 3.1 编译器内部流水线

| 步骤 | 做什么 |
| --- | --- |
| 词法/语法分析 | 源码 → AST |
| 语义分析 | 类型检查、重载决议、模板实例化 |
| 优化 | 中间表示（GIMPLE/LLVM IR）上做内联、常量折叠、循环优化、死代码消除…… |
| 代码生成 | 产出汇编（`-S` 可见），寄存器分配、指令选择 |

### 3.2 优化等级

| 等级 | 内容 | 适用场景 |
| --- | --- | --- |
| `-O0` | 不优化，变量都在栈上 | 调试（gdb 单步与源码一一对应） |
| `-O1` | 基础优化，无重量级 pass | 想调试又嫌 O0 慢 |
| `-O2` | 内联、向量化、循环优化全家桶 | **发布版默认** |
| `-O3` | 更激进的内联/循环展开 | CPU 密集热点（代码膨胀换取速度） |
| `-Os` | 在 O2 基础上以体积优先 | 嵌入式、体积敏感 |
| `-Og` | 只做不妨碍调试的优化 | 调试期推荐 |

> 陷阱：`-O2` 下"未初始化变量""未定义行为"常直接表现为崩溃或结果错乱，O0 却"碰巧正常"——不是编译器 bug，是 UB 被优化放大。配合 `-fsanitize=undefined,address`（见《../06-构建与版本控制/01-构建工具GCC与CMake.md》）。

### 3.3 警告与单文件反查

```bash
g++ -std=c++17 -Wall -Wextra -c main.cpp        # 日常最低配置
g++ -S -O2 -masm=intel main.cpp -o main.s       # 看某函数的汇编（验证内联/虚调用）
objdump -d -M intel main.o | less                # 反汇编目标文件
objdump -d app | grep -A20 '<func>:'             # 定位某函数机器码
```

## 4. 目标文件与 ELF

### 4.1 ELF 结构

```text
+-----------------------+  低地址
| ELF Header            |  魔数 \x7fELF、架构、入口地址
+-----------------------+
| .text                 |  代码（机器指令）
| .rodata               |  只读数据：字符串字面量、const 数组、（vtable 常放这里）
| .data                 |  已初始化的可写全局/静态变量
| .bss                  |  未初始化（或零初始化）变量：只记录大小，文件里不占空间
+-----------------------+
| .symtab / .strtab     |  符号表与符号名字符串表
| .rela.text            |  .text 中需要重定位的位置清单
| .rela.data            |  .data 的重定位项
+-----------------------+
| .debug_*（-g 时）     |  调试信息（DWARF）
| .comment 等           |  编译器版本注释
+-----------------------+  高地址（可执行文件还含 program headers 指导装载）
```

### 4.2 各段内容对照表

| 段 | 存放内容 | 对应 C++ 概念 |
| --- | --- | --- |
| `.text` | 机器指令 | 函数体、模板实例化后的代码 |
| `.rodata` | 只读数据 | 字符串字面量、`constexpr` 数组、vtable（Itanium ABI 下） |
| `.data` | 已初始化可写数据 | `int g = 5;`、静态成员 `inline int X::v = 1;` |
| `.bss` | 零初始化数据（不占文件体积） | `int g;`、`static int s;`、静态成员定义 |
| `.symtab` | 符号表（名字→地址/类型） | 函数名、全局变量名（mangling 后） |
| `.rela.text` | 代码中待补地址的位置 | `call printf` 时先占位再重定位 |
| `.debug_info` | DWARF 调试信息 | `-g` 生成，gdb 依赖 |
| `.plt/.got` | 动态链接跳板与全局偏移表 | 调用共享库函数 |
| `.init/.fini` | 构造/析构回调段 | 全局对象构造（`__libc_csu_init` 一类机制） |

### 4.3 符号表与查看命令

```bash
nm main.o                 # 列符号：类型字母 + 名字
readelf -a main.o         # ELF 全量信息（段、符号、重定位）
objdump -t main.o         # 符号表（带段归属）
```

`nm` 类型字母速查（大小写=全局/局部）：

| 字母 | 含义 | 例子 |
| --- | --- | --- |
| `T` / `t` | 定义在 .text（全局/局部） | 普通函数 |
| `D` / `d` | 已初始化数据 | `int g = 5;` |
| `B` / `b` | .bss | 未初始化全局 |
| `R` / `r` | 只读数据 | const 数组 |
| `U` | **未定义引用：本文件用了但没定义** | `printf`、其他 TU 的函数 |
| `W` / `w` | 弱符号 | 默认模板实例、`__attribute__((weak))` |
| `V` / `v` | 弱定义的对象 | |
| `u` | 仅 C++ 的"独一无二的"符号（如内联函数局部静态） | |

## 5. 符号与重定位

### 5.1 强符号与弱符号

| 概念 | 定义 | 规则 |
| --- | --- | --- |
| 强符号 | 普通函数定义、已初始化全局变量 | **多个强符号同名 → "multiple definition" 链接错误** |
| 弱符号 | `__attribute__((weak))` 声明、未初始化全局（旧规则下的 tentative definition） | 强弱共存选强；只有弱选任意一个 |
| 常见来源 | 头文件里定义了函数/变量且被多个 .cpp include | 修复：函数加 `inline`，变量加 `inline`（C++17）或声明放头、定义放 .cpp |

> GCC 10 起默认 `-fno-common`：未初始化全局变量不再是 common 符号，重复定义直接报错（老代码升级常见踩雷）。

### 5.2 C++ name mangling

C++ 支持重载与命名空间，必须把签名编进符号名（Itanium ABI）：

```bash
$ echo 'int add(int, double) { return 0; }' | g++ -c -x c++ - -o /tmp/a.o
$ nm /tmp/a.o
0000000000000000 T _Z3addid
$ c++filt _Z3addid
add(int, double)
```

| 场景 | 处理 |
| --- | --- |
| C 库头文件在 C++ 里用 | 包 `extern "C" { #include <c_header.h> }`：按 C 规则不 mangling |
| 自己写的动态库导出 C 接口 | 函数声明 `extern "C"`，符号名保持干净（也可配合 `-Wl,--version-script`） |
| 链接报错只给 mangled 名 | `c++filt _ZN3foo3barEv` 解码后再查 |

### 5.3 重定位如何补齐地址

```text
main.o 中：  call  <占位 0>        ← .rela.text 记录："此处调用符号 add"
链接时：      ld 查 .symtab 得到 add 的最终地址
             把地址回填到 call 指令的位移字段
运行期(动态)： call printf@plt → PLT 跳 GOT → 运行时解析（惰性绑定）
```

## 6. 静态库 vs 动态库

| 维度 | 静态库 `.a` | 动态库 `.so` |
| --- | --- | --- |
| 链接时机 | 链接期复制进可执行文件 | 链接期只记录依赖，运行期装载 |
| 文件本质 | 一堆 `.o` 的归档（`ar`） | 特殊 ELF（含 .dynsym/.plt/.got） |
| 可执行文件体积 | 变大 | 小 |
| 库更新 | 必须重新链接 | 替换 .so 即生效（接口兼容时） |
| 加载方式 | 无额外加载 | 加载器 `ld.so` 映射、多进程共享一份代码页 |
| 符号解析 | 链接期全部落定 | 运行期还需重定位（启动开销） |
| 部署 | 单文件即可跑 | 目标机必须存在 .so 及其依赖 |
| 创建 | `ar rcs libfoo.a foo.o bar.o` | `g++ -shared -fPIC -o libfoo.so foo.o bar.o` |
| 使用 | `g++ main.o -L. -lfoo` | 同左（优先找 .so，见 7.3） |

`-fPIC`（Position Independent Code）必要性：

| 选项 | 含义 | 用于 |
| --- | --- | --- |
| `-fPIC` | 生成位置无关代码：地址全部走 GOT/PLT 间接访问 | **.so 必须加**（否则装载到任意基址时指令里写死的地址全错） |
| `-fPIE` + `-pie` | 可执行文件位置无关（ASLR 默认开启的根因） | 现代发行版默认 |
| 不加 | 写死绝对地址 | 只适合静态库/非 PIE 可执行 |

完整示例：

```bash
# 静态库
g++ -c mathlib.cpp -o mathlib.o
ar rcs libmath.a mathlib.o              # r=插入 c=创建 s=写索引
g++ main.cpp -L. -lmath -o app_static

# 动态库
g++ -fPIC -c mathlib.cpp -o mathlib_pic.o
g++ -shared -fPIC -o libmath.so mathlib_pic.o
g++ main.cpp -L. -lmath -Wl,-rpath,'$ORIGIN' -o app_shared
./app_shared                            # rpath 用 $ORIGIN 使其找同目录的 .so
```

## 7. 链接器行为

### 7.1 从左到右解析：undefined reference 的头号原因

ld 按命令行**从左到右**扫描：见到 `.o` 就把其中符号全部登记；见到库（`.a/.so`）只提取"当前还缺的符号"对应的成员，**之后**才声明的依赖它看不见。

```text
g++ -lmath main.cpp -o app      # 错：扫 -lmath 时 main.cpp 还没贡献任何符号，啥也不提取
g++ main.cpp -lmath -o app      # 对：main.o 先产生 U 符号，再由 libmath 解析
```

| 场景 | 正确写法 |
| --- | --- |
| 普通依赖 | `g++ main.o -lfoo -lbar`（foo 依赖 bar 则 foo 在前） |
| 循环依赖（A↔B） | `g++ main.o -Wl,--start-group -lA -lB -Wl,--end-group`（或重复写两遍 `-lA -lB -lA`） |
| 静态库互相拆着用 | group 最省事，但有少量性能成本 |

### 7.2 -l 与文件名映射

| 命令 | 查找结果 |
| --- | --- |
| `-lfoo` | 在各搜索目录依次找 `libfoo.so` → `libfoo.a`（动态优先） |
| `-l:libfoo.a` | 强制指定文件名（绕过 lib 前缀规则，强制静态） |
| `-static` | 只用 `.a`，把 libc/libstdc++ 也静态打入 |
| `-Wl,-Bstatic -lfoo -Wl,-Bdynamic` | 仅对 foo 用静态，其余恢复动态 |
| `-L<dir>` | 追加库搜索目录（编译期） |

### 7.3 同名 .so/.a 的选择规则

| 条件 | 选择 |
| --- | --- |
| 目录中两者并存、无特殊选项 | `.so` 优先 |
| 需要 `.a` | `-l:libfoo.a` 或 `-Wl,-Bstatic` 或 `-static` |
| `-L` 多目录 | 先给的目录先搜 |

## 8. 动态库运行期

### 8.1 加载地址与查找顺序

可执行文件（PIE）与 .so 装载基址由 ASLR 随机化，代码靠 GOT/PLT 与相对寻址工作。

运行时 `.so` 查找顺序（Linux/ld.so）：

| 顺序 | 来源 | 设置方式 |
| --- | --- | --- |
| 1 | `DT_RPATH`（旧） | 链接时 `-Wl,-rpath,/path`（不带 new-dtags） |
| 2 | `LD_LIBRARY_PATH` 环境变量 | 运行前 export |
| 3 | `DT_RUNPATH`（新默认） | 链接时 `-Wl,-rpath` + `--enable-new-dtags`（多数发行版默认） |
| 4 | `/etc/ld.so.cache` | `ldconfig` 扫描 `/etc/ld.so.conf.d/` 生成 |
| 5 | 兜底目录 `/lib`、`/usr/lib`（及 64 位的 lib64） | 系统库 |

`rpath` 与 `RUNPATH` 的区别：

| 维度 | DT_RPATH | DT_RUNPATH |
| --- | --- | --- |
| 优先级 | 高于 `LD_LIBRARY_PATH` | **低于** `LD_LIBRARY_PATH` |
| 作用范围 | 传递给整个依赖树（所有间接依赖也用它找） | 只对**本模块直接依赖**生效 |
| 现状 | 旧；新链接器默认产出 RUNPATH | 当前默认（`--enable-new-dtags`） |
| 查看 | `readelf -d app | grep -i path` | 同左 |

### 8.2 诊断命令

| 命令 | 用途 |
| --- | --- |
| `ldd ./app` | 列出全部动态依赖及是否能找到（"not found" 即启动失败原因） |
| `ldd -r ./app` | 额外检查符号重定位缺失（未定义符号运行期才会炸的提前暴露） |
| `LD_DEBUG=libs ./app` | 打印加载器搜库全过程 |
| `LD_LIBRARY_PATH=/opt/x/lib ./app` | 临时指定搜索路径（调试用，别写进生产脚本） |
| `readelf -d app` | 看 NEEDED/RPATH/RUNPATH |
| `objdump -p app` | 同上的另一种视图 |

> 安全提示：`ldd` 在部分老系统上会执行目标文件本身，不要对不可信二进制运行。

### 8.3 dlopen 手动装载

```cpp
#include <dlfcn.h>
#include <iostream>

int main() {
    void* h = dlopen("./libplugin.so", RTLD_NOW);   // RTLD_NOW：立即解析全部符号
    if (!h) { std::cerr << dlerror() << '\n'; return 1; }
    using Fn = int (*)(int);
    auto fn = reinterpret_cast<Fn>(dlsym(h, "plugin_entry"));   // 按名字取符号
    if (!fn) { std::cerr << dlerror() << '\n'; return 1; }
    std::cout << fn(42) << '\n';
    dlclose(h);                                     // 引用计数归零才真正卸载
}
// 编译：g++ main.cpp -ldl -o loader（glibc 2.34+ 已并入 libc，-ldl 可省）
```

| API | 作用 |
| --- | --- |
| `dlopen(path, flags)` | 装载库；`RTLD_LAZY` 惰性绑定 / `RTLD_NOW` 立即 / `RTLD_GLOBAL` 符号可见于后续装载 |
| `dlsym(handle, name)` | 取函数/变量地址；失败返回 NULL |
| `dlerror()` | 取最近一次错误描述（用完即清） |
| `dlclose(handle)` | 减引用计数 |

## 9. 常见错误速查表

| 错误 | 典型原因 | 最小复现与修复 |
| --- | --- | --- |
| `undefined reference to 'foo(int)'`（链接期） | ① 没实现/没链库 ② 库顺序错 ③ C++ 调 C 忘 `extern "C"` ④ 模板成员函数定义在 .cpp | 逐条排查：`nm libfoo.a \| grep foo` 看符号在不在；调整命令行顺序；补 `extern "C"`；模板挪回头文件 |
| `multiple definition of 'x'` | 头文件里定义了非 inline 变量/函数被多 TU 包含；GCC10 起 -fno-common 收紧 | 函数加 `inline`；变量加 `inline`（C++17）或声明放头文件、定义放 .cpp |
| `cannot find -lfoo` | 没有该名字的库文件或路径没加 | 确认 `libfoo.so/.a` 存在；补 `-L<path>` |
| `error while loading shared libraries: libfoo.so: cannot open shared object file` | 运行期找不到 .so | `ldd ./app` 看哪个 not found；装到系统目录 `ldconfig`，或链接时 `-Wl,-rpath,'$ORIGIN'` |
| `GLIBCXX_version not found` | 编译用的 libstdc++ 比运行环境新（ABI 版本不匹配） | `strings /usr/lib/.../libstdc++.so.6 \| grep GLIBCXX` 看支持的版本；升级运行环境或用旧工具链/静态链接标准库 |
| `GLIBC_x.y not found` | 同上但发生在 libc | 同上思路；目标是让"编译机不比运行机新" |
| `undefined symbol: _ZN...`（运行期/dlopen） | .so 内引用了但未定义且未导出的符号；或插件用 `dlopen` 缺 `-Wl,--export-dynamic` 找主程序符号 | `nm -D libx.so \| grep 名字`；主程序链接加 `-rdynamic`；或把公共依赖独立成 .so |
| `relocation R_X86_64_32 ... recompile with -fPIC` | 生成 .so 时混入了非 PIC 的 .o | 所有进 .so 的目标统一 `-fPIC` 重编 |

## 10. 与构建系统衔接

make/cmake 最终都只是生成上一节的 gcc/ld 命令行（详见《../06-构建与版本控制/01-构建工具GCC与CMake.md》）：

| CMake 写法 | 生成的链接行为 |
| --- | --- |
| `target_link_libraries(app PRIVATE foo)` | 命令行追加 `-lfoo`；PRIVATE 只链自己 |
| `target_link_libraries(app PUBLIC bar)` | 依赖 bar 的**接口**同时传给依赖 app 的目标（头文件路径、编译定义一并传播） |
| `target_link_libraries(app PRIVATE a b)` | **顺序即书写顺序**：a 依赖 b 时必须 a 在前，同 7.1 规则 |
| `set(CMAKE_BUILD_RPATH ...) / BUILD_RPATH_USE_ORIGIN` | 控制 rpath（跨机器部署常用 `$ORIGIN`） |
| `target_include_directories(app PRIVATE inc)` | 生成 `-I inc`（预处理阶段） |

排查思路：构建失败时先看真实命令行（`make VERBOSE=1` 或 cmake `--build . -- VERBOSE=1`），把它抄下来手工执行，问题立刻具体化。

## 11. 快速参考卡片

按"我想看 XX"组织诊断命令：

| 我想看…… | 命令 |
| --- | --- |
| 预处理后的完整源码 | `g++ -E main.cpp -o main.i` |
| 某函数生成的汇编 | `g++ -S -O2 main.cpp && less main.s` |
| 目标文件有哪些段 | `readelf -S main.o` |
| 目标文件定义/引用了哪些符号 | `nm main.o`（`U` = 用了没定义） |
| 一个 mangled 名是什么 | `c++filt _ZN3foo3barEv` |
| 反汇编某个函数 | `objdump -d app \| grep -A30 '<foo'` |
| 可执行文件依赖哪些 .so | `ldd ./app`；`readelf -d app \| grep NEEDED` |
| 运行时找不到库的详细过程 | `LD_DEBUG=libs ./app` |
| 库是静态还是动态、含哪些成员 | `ar t libfoo.a`（列成员）；`file libfoo.so` |
| rpath/RUNPATH 设置 | `readelf -d app \| grep -i path` |
| 符号是否真的导出 | `nm -D libfoo.so` |
| 重定位项 | `readelf -r main.o` |

流程速记：

```text
-E 预处理出 .i → -S 出 .s → -c 出 .o → 链接出可执行
.o 里有 U 符号 → 必须有人提供定义（别的 .o 或 -lxxx）
-l 从左到右解析 → 被依赖的库放右边
.so 运行期再找 → RPATH → LD_LIBRARY_PATH → RUNPATH → ldconfig → /lib
```

## 12. 常见问题与坑

| 问题 | 原因与解决方案 |
| --- | --- |
| 模板类成员函数写在 .cpp，链接报 undefined reference | 调用方实例化时看不到定义。解决：实现放头文件；或 .cpp 末尾显式实例化 `template class Stack<int>;` |
| `-lmath` 放在 `main.cpp` 前面，符号没被解析 | ld 从左到右、库只解决"已出现"的未定义符号。解决：调整顺序，`main.cpp -lmath` |
| 两个静态库互相依赖，怎么排都缺符号 | 循环依赖。解决：`-Wl,--start-group -lA -lB -Wl,--end-group`，或合并两库 |
| 程序在开发机正常、拷到别的机器 "cannot open shared object file" | 运行期找不到 .so。解决：`ldd` 找出缺失项；部署用 `-Wl,-rpath,'$ORIGIN'` 把库放可执行文件同目录 |
| rpath 写了相对路径 `./lib` 却失效 | rpath 相对的是**进程工作目录**而非可执行文件位置。解决：用 `$ORIGIN`（注意 shell 转义：`'-Wl,-rpath,$ORIGIN'`） |
| 用 `gcc` 链接 C++ 程序，报一堆 `undefined reference to std::...` | `gcc` 不自动链 libstdc++。解决：用 `g++` 链接，或手动 `-lstdc++` |
| 头文件里 `int count;` 定义全局变量，多 TU include 后 multiple definition | 每个包含它的 .o 都有强定义。解决：头文件 `extern int count;` + 一个 .cpp 定义；或 C++17 `inline int count;` |
| dlopen 的插件调用主程序函数失败 undefined symbol | 主程序符号默认不导出给插件。解决：主程序链接加 `-Wl,--export-dynamic`（`-rdynamic`） |
| 升级 GCC 后老程序报 GLIBCXX not found | 编译机 libstdc++ 比运行机新。解决：运行机升级 libstdc++，或使用老工具链重编，或静态链标准库 |
| 编译 .so 忘加 `-fPIC` 报 relocation 错误 | so 装载基址不固定，绝对地址无效。解决：全部源文件 `-fPIC` |
| `-O2` 一开程序行为就变 | 多半是 UB（未初始化/越界/数据竞争）被优化放大。解决：`-fsanitize=address,undefined` 复现修复，别关优化了事 |
| 增量编译改了头文件但没重编依赖它的 .cpp | 依赖关系缺失（make 没写依赖、cmake 正常会生成）。解决：`make -B` 强制全量验证；补头文件依赖规则 |
