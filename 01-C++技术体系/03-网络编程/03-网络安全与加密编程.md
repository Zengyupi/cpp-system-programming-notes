## 1. 安全目标与密码学全家福

### 1.1 四大安全目标（CIA + 抗抵赖）

| 目标 | 含义 | 由谁保证 |
| --- | --- | --- |
| 机密性 Confidentiality | 内容不被第三方看懂 | 对称/非对称**加密** |
| 完整性 Integrity | 传输中没被篡改 | **哈希/MAC/签名** |
| 可用性 Availability | 服务随时可用 | 限流、防 DDoS、冗余（运维侧） |
| 认证 Authentication | 确认对方是谁 | 证书、签名、HMAC、口令 |
| 抗抵赖 Non-repudiation | 发过不能否认 | **数字签名**（私钥签、公钥验） |

### 1.2 三类原语一张图理清

```text
                       密码学原语
        ┌──────────────────┼────────────────────┐
     对称加密            非对称加密              哈希/摘要
   一把密钥加解密      公钥/私钥一对          单向定长指纹
   AES/ChaCha20       RSA / ECC(ECDH/ECDSA)   SHA-256/SM3
   快、加密大数据      慢、传密钥/签名          不可逆、抗碰撞
        └──────────────┬────────────────────┘
                       ▼
        MAC/HMAC（对称密钥+摘要 → 防篡改+认证）
        数字签名（私钥对摘要加密 → 认证+抗抵赖）
        证书 PKI（公钥绑身份，CA 签名背书）
```

### 1.3 常见算法对照（别再用过时的）

| 类别 | 推荐 | 了解/兼容 | **禁用/过时** |
| --- | --- | --- | --- |
| 对称 | **AES-128/256-GCM**、ChaCha20-Poly1305 | AES-CBC（须配 HMAC） | DES、3DES、RC4、AES-ECB |
| 非对称 | RSA-2048+、**ECC P-256**、X25519 | RSA-1024（已不够） | RSA-512、自定义 |
| 摘要 | **SHA-256/384**、SHA-3、SM3 | SHA-1（仅兼容） | MD5（抗碰撞已破，不能用于安全） |
| 密钥交换 | ECDHE（X25519/P-256） | DH | 静态 RSA 密钥交换（无前向保密） |
| 国密 | SM2(非对称)、SM4(对称)、SM3(摘要) | 电力/政务国产化要求 | — |

## 2. 对称加密：分组模式与 AES-GCM

### 2.1 分组密码模式（面试高频，ECB 为什么不能用）

| 模式 | 是否需要 IV | 并行 | 完整性 | 说明 |
| --- | --- | --- | --- | --- |
| ECB | 否 | 可 | 无 | **相同明文块→相同密文，泄露模式（经典企鹅图），禁用** |
| CBC | 需要 IV | 加密串行 | 无（要另配 HMAC） | 每块与前一块异或；IV 必须随机不可预测 |
| CTR | 需要 nonce（计数器） | 可并行 | 无 | 把分组密码变流密码，nonce 绝不能复用 |
| **GCM** | 需要 nonce | 可 | **自带认证标签 AEAD** | **行业首选**：加密+完整性+认证一体 |
| ChaCha20-Poly1305 | nonce | 可 | AEAD | 无 AES 硬件加速的移动/嵌入式平台更快 |

**AEAD（认证加密）**：GCM/ChaCha20-Poly1305 在解密时同时校验认证标签（Tag），密文被改一个字节就解密失败，**不需要再单独算 HMAC**，避免"CBC + 自行拼 MAC"的各种实现漏洞。

### 2.2 IV/nonce/密钥的铁律

- **密钥**：长度固定（AES-128=16B、AES-256=32B），必须来自安全随机源，绝不能硬编码进代码。
- **IV/nonce**：GCM 推荐 12 字节；**同一把密钥下 nonce 绝不能重复**（GCM nonce 复用是灾难性的，可泄露密钥）。每次加密随机生成并和密文一起发送（IV 不需要保密）。
- GCM 单密钥下加密数据量有上限（约 64GB/分组），超长流量要轮换密钥。

### 2.3 OpenSSL 3.x EVP 做 AES-256-GCM（加解密）

> OpenSSL 3.0 起推荐 **EVP 高层接口**，老的 `AES_encrypt` 等低级接口已废弃。编译：`g++ gcm.cpp -lcrypto -o gcm`。

```cpp
#include <openssl/evp.h>
#include <openssl/rand.h>
#include <vector>
#include <cstring>

// 输出 = nonce(12) || ciphertext || tag(16)
bool aes_gcm_seal(const std::vector<unsigned char>& key,   // 32B
                  const std::vector<unsigned char>& plain,
                  const std::vector<unsigned char>& aad,   // 附加认证数据(可不加密但要防改)
                  std::vector<unsigned char>& out) {
    unsigned char nonce[12], tag[16];
    RAND_bytes(nonce, sizeof nonce);                 // 安全随机 nonce
    EVP_CIPHER_CTX* ctx = EVP_CIPHER_CTX_new();
    int len = 0, outlen = 0;
    std::vector<unsigned char> ct(plain.size());

    EVP_EncryptInit_ex(ctx, EVP_aes_256_gcm(), nullptr, nullptr, nullptr);
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_SET_IVLEN, 12, nullptr);
    EVP_EncryptInit_ex(ctx, nullptr, nullptr, key.data(), nonce);
    EVP_EncryptUpdate(ctx, nullptr, &len, aad.data(), (int)aad.size()); // AAD
    EVP_EncryptUpdate(ctx, ct.data(), &len, plain.data(), (int)plain.size());
    outlen = len;
    EVP_EncryptFinal_ex(ctx, ct.data() + len, &len);
    outlen += len;
    EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_GCM_GET_TAG, 16, tag);            // 取 tag
    EVP_CIPHER_CTX_free(ctx);

    out.insert(out.end(), nonce, nonce + 12);
    out.insert(out.end(), ct.begin(), ct.begin() + outlen);
    out.insert(out.end(), tag, tag + 16);
    return true;
}
// 解密时顺序对称：EVP_DecryptInit → SET_IVLEN → 传入 nonce/key →
//   DecryptUpdate(AAD) → DecryptUpdate(密文) → 先 EVP_CTRL_GCM_SET_TAG 再
//   DecryptFinal；Final 返回 0 表示标签校验失败（密文被篡改），必须丢弃。
```

> 嵌入式若要求国密，把 `EVP_aes_256_gcm()` 换成 `EVP_sm4_gcm()`/`EVP_sm4_cbc()`（OpenSSL 1.1.1+ 或 GmSSL），摘要用 SM3、非对称用 SM2，接口范式一致。

## 3. 非对称加密与密钥交换

### 3.1 为什么要混合加密

非对称算法（RSA/ECC）**慢几个数量级**，不能直接加密大量数据。真实系统（TLS）用**混合加密**：

```text
1. 非对称/密钥协商(ECDH) 安全地协商出一把"会话密钥"（只传几个字节）
2. 之后用这把对称密钥(AES-GCM) 加密海量业务数据（快）
```

### 3.2 RSA vs ECC

| 维度 | RSA | ECC（椭圆曲线） |
| --- | --- | --- |
| 安全基础 | 大整数分解难题 | 椭圆曲线离散对数难题 |
| 同等安全强度密钥长度 | 3072 位 | 256 位（**短得多**） |
| 运算/存储/带宽 | 大、慢 | 小、快，适合嵌入式/TLS 握手提速 |
| 典型用途 | 加密/签名/证书 | ECDH 密钥交换、ECDSA/Ed25519 签名 |
| 选型 | 兼容性最广 | 新系统优先（X25519/P-256） |

### 3.3 ECDH 与前向保密（PFS）

- **DH/ECDH**：双方公钥互换，各自用私钥+对方公钥算出**同一个共享密钥**，窃听者只看到公钥也算不出来。
- **DHE/ECDHE（E=ephemeral 临时）**：每次会话临时生成密钥对，会话结束私钥即销毁。即使服务器长期私钥将来泄露，也解不开历史会话——这就是**前向保密**，TLS1.3 只保留这类交换。

## 4. 哈希、HMAC、数字签名

### 4.1 哈希的性质与正确用途

性质：单向不可逆、定长输出、抗碰撞（找两条不同输入得到相同摘要在计算上不可行）。用途：完整性校验、指纹、口令存储（**必须加盐+慢哈希**，见 4.4）、Merkle 树、签名前先对消息取摘要。

```cpp
// OpenSSL EVP 算 SHA-256（一次性接口）
unsigned char digest[EVP_MAX_MD_SIZE]; unsigned int dlen = 0;
EVP_Digest(data, data_len, digest, &dlen, EVP_sha256(), nullptr); // 国密换 EVP_sm3()
```

### 4.2 单纯哈希为什么不能做消息认证

哈希是公开的，攻击者改了消息可以**重算哈希**。**HMAC = 密钥 + 消息**一起算摘要，没有密钥就伪造不出，用于接口签名、Webhook 校验、令牌：

```text
HMAC(K, m) = H( (K ⊕ opad) || H( (K ⊕ ipad) || m ) )
```

```text
// HMAC-SHA256
unsigned char mac[EVP_MAX_MD_SIZE]; unsigned int mlen = 0;
HMAC(EVP_sha256(), key, key_len, data, data_len, mac, &mlen);
// 校验时用恒定时间比较 CRYPTO_memcmp，不要用 memcmp/==（防时序攻击）
```

### 4.3 数字签名 = 私钥签、公钥验

| 步骤 | 动作 |
| --- | --- |
| 签名方 | 对消息算摘要 → **用私钥**对摘要签名（RSA-PSS / ECDSA / Ed25519） |
| 验证方 | **用公钥**验证签名与摘要是否一致 |

它同时提供**认证（确实是私钥持有者发的）、完整性、抗抵赖**。注意和"加密"方向相反：加密是公钥加密私钥解，签名是私钥签公钥验。

### 4.4 口令存储（最容易写错的地方）

- **绝不能明文存口令，也不能直接 MD5/SHA-256 一遍**（彩虹表/撞库秒破）。
- 正确：**每个用户随机盐 salt + 慢哈希/专用算法 bcrypt / scrypt / Argon2（首选）**，通过"故意算得慢、耗内存"提高暴力破解成本。
- 校验用恒定时间比较；登录加限速/锁定防在线爆破。

## 5. 编码不是加密：Hex / Base64

Base64/Hex 只是**把二进制换成可打印字符**，没有密钥、任何人都能还原，**不提供任何安全性**。证书、密钥常用 PEM（Base64 包裹 DER）格式。抓包/二进制分析见《../08-网络与系统工具/03-二进制查看工具.md》。

```text
// OpenSSL Base64 编码
BIO* b64 = BIO_new(BIO_f_base64());
BIO* mem = BIO_new(BIO_s_mem());
b64 = BIO_push(b64, mem);
BIO_write(b64, raw, raw_len); BIO_flush(b64);
// 解码反向；注意 Base64 后体积约增大 1/3
```

## 6. 证书与 PKI：公钥怎么绑定到"人"

### 6.1 X.509 证书里有什么

证书把"**公钥**"和"**身份（域名/组织）**"绑定，并由可信第三方 **CA（证书机构）用私钥签名**背书。核心字段：主体、主体公钥、签发者 CA、有效期 `notBefore/notAfter`、**SAN（Subject Alternative Name，现代浏览器认的域名列表）**、签名算法、序列号。

```text
信任链：根 CA（自签，预装在系统/浏览器信任库）
   └─ 中间 CA（由根签）
        └─ 站点叶子证书（由中间 CA 签，部署在服务器）
验证：逐级验签名 + 校验有效期 + 校验域名匹配 + 检查是否被吊销(CRL/OCSP)
```

### 6.2 openssl 命令行高频操作（必会）

```text
# 1) 生成私钥
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out key.pem
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out ec.key
# 2) 生成 CSR（证书签名请求，拿去找 CA 签）
openssl req -new -key key.pem -out server.csr -subj "/CN=gw.example.com"
# 3) 自签证书（内网/测试用，生产找受信 CA 或 Let's Encrypt）
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 365 -nodes
# 4) 查看证书内容（明文）
openssl x509 -in cert.pem -text -noout
# 5) 验证证书链 / 看远端服务证书与握手
openssl verify -CAfile ca.pem cert.pem
openssl s_client -connect host:443 -servername host -showcerts
# 6) 私钥/证书格式转换（PEM<->DER、导出 PKCS#12 给 Windows/IIS）
openssl pkcs12 -export -inkey key.pem -in cert.pem -out bundle.p12
# 7) 用密钥对文件做签名/验签、加解密
openssl dgst -sha256 -sign key.pem -out data.sig data.bin
openssl dgst -sha256 -verify pub.pem -signature data.sig data.bin
```

## 7. TLS：密码学怎么拼成安全连接

### 7.1 TLS 握手解决的三件事

1. **协商**：客户端/服务器挑出双方都支持的密码套件、TLS 版本；
2. **认证**：客户端验证服务器证书（可选双向认证 mTLS：服务器也验客户端证书）；
3. **密钥交换**：ECDHE 协商出会话密钥 → 之后全部用对称加密（AES-GCM/ChaCha20）传输。

### 7.2 TLS1.2 与 TLS1.3 对比

| 维度 | TLS1.2 | TLS1.3（2018，现推荐） |
| --- | --- | --- |
| 握手 RTT | 2-RTT | **1-RTT**，可 0-RTT 恢复（有重放风险，慎用） |
| 密钥交换 | 支持静态 RSA（无 PFS） | **只留 (EC)DHE 临时交换，强制前向保密** |
| 密码套件 | 混杂、大量老旧套件可配错 | 大幅精简，只留 AEAD |
| 已废弃算法 | 可配出 RC4/3DES/CBC 弱套件 | 全部移除 |

### 7.3 OpenSSL 写 TLS 服务端骨架（在普通 TCP 上套 SSL）

编译：`g++ tls_server.cpp -lssl -lcrypto -o tls_server`。它与普通 socket 的差别只在 `accept` 后把 fd 包一层 `SSL`。

```cpp
#include <openssl/ssl.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <unistd.h>

int main() {
    SSL_library_init();
    SSL_CTX* ctx = SSL_CTX_new(TLS_server_method());
    SSL_CTX_set_min_proto_version(ctx, TLS1_2_VERSION);   // 禁用 SSLv3/TLS1.0/1.1
    SSL_CTX_use_certificate_file(ctx, "cert.pem", SSL_FILETYPE_PEM);
    SSL_CTX_use_PrivateKey_file(ctx, "key.pem", SSL_FILETYPE_PEM);
    if (SSL_CTX_check_private_key(ctx) != 1) return 1;   // 证书与私钥是否匹配

    int lfd = socket(AF_INET, SOCK_STREAM, 0);
    sockaddr_in addr{}; addr.sin_family = AF_INET;
    addr.sin_port = htons(4433); addr.sin_addr.s_addr = htonl(INADDR_ANY);
    bind(lfd, (sockaddr*)&addr, sizeof addr); listen(lfd, 16);

    for (;;) {
        int cfd = accept(lfd, nullptr, nullptr);
        SSL* ssl = SSL_new(ctx);
        SSL_set_fd(ssl, cfd);
        if (SSL_accept(ssl) <= 0) { SSL_free(ssl); close(cfd); continue; }
        char buf[1024];
        int n = SSL_read(ssl, buf, sizeof buf);          // 等价 read，但走加密通道
        SSL_write(ssl, "ok\n", 3);                        // 等价 write
        SSL_shutdown(ssl); SSL_free(ssl); close(cfd);
    }
}
```

客户端用 `TLS_client_method()` + `SSL_connect`，**生产环境必须加载 CA 并验证证书**（见下，最常见的漏洞就是关掉校验）。

### 7.4 证书验证绝不能关（最高频的安全漏洞）

很多调试代码写 `SSL_CTX_set_verify(ctx, SSL_VERIFY_NONE, ...)` 或 `verify=0`、`InsecureSkipVerify`（Go）然后忘了改回来——这等于**没有 TLS**，中间人可随意冒充服务器。正确做法：加载信任 CA、`SSL_VERIFY_PEER`、校验返回值，并校验连接的主机名（`X509_check_host`，防"证书是真的但不是这个域名"）。

## 8. 安全工程实践（C++ 通讯/后台）

| 主题 | 正确做法 |
| --- | --- |
| 随机数 | 密码学随机用 `RAND_bytes`/`getrandom`/`arc4random`，**绝不用 `rand()`/`srand(time)`**（可预测） |
| 密钥管理 | 不硬编码、不进 git；用环境变量/配置中心/KMS/HSM；日志脱敏；支持密钥轮换 |
| 比较敏感值 | MAC/令牌比较用 `CRYPTO_memcmp` 恒定时间，防**时序攻击**（逐字节短路泄露信息） |
| 栈/堆缓冲 | 长度先校验再拷贝，用 `std::vector/string`，禁用 `strcpy/sprintf/gets`（见第 10 章） |
| 最小权限 | 进程不跑 root，能力下放；网络默认 deny；输入"外部的都是恶意的" |
| TLS 配置 | 最低 TLS1.2、优先 1.3；AEAD 套件；开 HSTS；证书到期监控 |
| 依赖安全 | 定期升级 OpenSSL（Heartbleed 类 CVE）、`pip-audit`/依赖扫描；静态扫描见《../07-调试与测试/06-静态分析与代码规范.md》 |
| 纵深防御 | 校验+认证+最小权限+审计日志多层，不把安全押在单一措施上 |

## 9. 工业 / 电力通讯安全

### 9.1 传统工业规约天生"裸奔"

**Modbus RTU/TCP、IEC 60870-5-104、DNP3 早期版本设计时默认在封闭可信内网，没有认证、没有加密**：Modbus TCP 甚至没有身份校验，谁能连上 502 端口就能写线圈、遥控断路器。联网化后这成为重大风险，需要靠**网络隔离 + 边界防护 + 安全增强规约**补。

### 9.2 电力监控系统安全分区（"安全分区、网络专用、横向隔离、纵向认证"）

```text
 生产控制大区                        管理信息大区
 ┌───────────────┐  正向(单向)隔离   ┌───────────────┐
 │ 安全区 I (实时) │ ═══════════════► │ 安全区 III     │
 │ 调度自动化/继电  │  反向必须摆渡+审计 │ 生产管理/MIS    │
 ├───────────────┤  电力专用横向隔离   ├───────────────┤
 │ 安全区 II(非实时)│   装置(不同防火墙) │ 安全区 IV(办公) │
 │ 变电站监控/配网  │                   │ 互联网/邮件     │
 └───────────────┘                   └───────────────┘
   区 I↔II 之间：逻辑隔离(防火墙)
   上下级调度之间(纵向)：纵向加密认证装置 / 认证网关 + 电力数字证书
```

| 概念 | 要点 |
| --- | --- |
| 安全区 I/II/III/IV | 按实时性与重要性分区，I 区最核心（控制类） |
| 横向隔离 | 生产大区→信息大区用**电力专用单向隔离装置**（不是普通防火墙），正向只出不进 |
| 纵向认证 | 调度主站↔厂站之间用**纵向加密认证装置**，对 104 等报文做隧道加密/签名 |
| 电力数字证书 | 基于国家 PKI 的设备/应用证书，做身份认证 |

### 9.3 安全增强规约与标准

| 标准/规约 | 作用 |
| --- | --- |
| **IEC 62351** | 电力系统信息安全系列标准，定义 TLS 用于 TCP 规约、加密/认证/证书在 104、GOOSE/SV 上的应用 |
| Modbus/TCP Security（端口 802） | Modbus 组织出的 **TLS 版 Modbus**，带 X.509 认证 |
| DNP3 Secure Authentication v5 | DNP3 的挑战-响应认证、HMAC、加密 |
| OPC UA | 自带 **Sign&Encrypt**、证书与安全策略，比经典 OPC DA（DCOM，弱）安全得多 |
| 等保 2.0（网络安全等级保护） | 国内合规要求，工业控制系统需定级备案、测评整改 |

> 工程落地：嵌入式网关侧常用 **mbedTLS/wolfSSL/OpenSSL**（体积比桌面 OpenSSL 小，适合交叉编译），在 104/Modbus TCP 外建立 TLS 隧道或对接纵向加密装置；证书烧录、设备身份、固件签名校验（OTA 防刷，见《../09-嵌入式开发/06-低功耗可靠性与OTA升级.md》）要在产品设计阶段就考虑，不能事后补。

## 10. C/C++ 常见安全漏洞速查

| 漏洞 | 成因 | 防御 |
| --- | --- | --- |
| 缓冲区溢出（栈/堆） | 拷贝不检查长度 | 有界拷贝、容器、FORTIFY_SOURCE、ASLR+栈保护/PIE 编译选项 |
| 格式化字符串 | `printf(用户输入)` | 固定格式串 `printf("%s", x)` |
| 整数溢出/下溢 | 长度计算回绕导致小 buffer | 用宽类型、做范围检查 |
| Use-After-Free / Double Free | 生命周期错误 | RAII/智能指针（见《../01-语言基础/04-内存管理与智能指针.md》）、ASan 检测 |
| 命令/SQL 注入 | 拼接外部输入 | 参数化、白名单、绝不用 `system(strcat)` |
| 硬编码密钥/后门口令 | 图省事写死 | 密钥外置、代码审计、禁入库 |
| 关闭证书校验 | 调试代码残留 | 强制验证链+主机名，CI 检查 |
| 弱随机 | `rand()` 生成 token/密钥 | 密码学安全随机源 |

编译期加固选项（GCC/Clang）：`-fstack-protector-strong -D_FORTIFY_SOURCE=2 -fPIE -pie -Wl,-z,relro,-z,now`，运行期靠 ASLR、编译器 sanitizer 与 Valgrind（见《../07-调试与测试/02-Valgrind内存检测.md》）提前发现内存问题。

## 11. 快速参考卡片

```text
目标：机密(加密) 完整(摘要/MAC) 认证(证书/签名) 抗抵赖(数字签名)
选型：对称 AES-256-GCM(AEAD首选)；非对称 ECC/X25519；摘要 SHA-256；国密 SM2/3/4
铁律：不发明算法；nonce 同密钥不重复；密钥不硬编码；随机用 RAND_bytes
混合：ECDHE 协商会话密钥(前向保密) → AES-GCM 传数据；非对称不加密大数据
HMAC=带密钥摘要(接口签名)；签名=私钥签摘要/公钥验；口令用 Argon2/bcrypt+盐
编码：Base64/Hex 不是加密；PEM=Base64(DER)
TLS：最低1.2优先1.3；只留 ECDHE+AEAD；客户端必须验证书链+主机名，绝不 VERIFY_NONE
OpenSSL：高层 EVP 接口；编译 -lssl -lcrypto；命令行 req/x509/s_client/verify
工业：104/Modbus 原生无安全；分区 I/II/III/IV + 横向单向隔离 + 纵向加密认证；IEC62351/OPC UA
```

## 12. 常见问题与坑

| 问题 | 原因与解决 |
| --- | --- |
| 用了 AES-ECB，相同明文得到相同密文 | ECB 不安全。换 GCM/CTR，配合随机 nonce |
| GCM 解密"偶发"失败/被破 | 同一密钥复用了 nonce。每次加密随机生成 nonce 并随密文传输 |
| 自己拼 CBC+HMAC 出漏洞 | 直接用 AEAD（GCM/ChaCha20-Poly1305），让库同时保证加密与认证 |
| 客户端连任何证书都通过 | 关了校验。加载 CA、VERIFY_PEER、X509_check_host，失败即断连 |
| token/签名比较用 `==`/memcmp | 时序攻击。用 `CRYPTO_memcmp` 恒定时间比较 |
| 用 `rand()` 生成密钥/会话 id | 可预测。密码学场景必须 `RAND_bytes`/`getrandom` |
| MD5 做口令或签名 | 碰撞已破。完整性用 SHA-256，口令用 Argon2/bcrypt+盐 |
| 私钥/证书对不上，SSL_accept 失败 | 启动时 `SSL_CTX_check_private_key` 校验；确认证书 SAN 覆盖域名 |
| 嵌入式 OpenSSL 体积太大 | 用 mbedTLS/wolfSSL 裁剪交叉编译，只编译需要的套件 |
| 以为内网工业协议不用安全 | 104/Modbus 无认证，联网即风险。靠分区隔离+纵向加密+IEC62351/TLS 加固 |
| OpenSSL 版本老触发 CVE（如 Heartbleed） | 建立依赖升级机制，编译期加固选项+依赖扫描+关注 CVE 公告 |
