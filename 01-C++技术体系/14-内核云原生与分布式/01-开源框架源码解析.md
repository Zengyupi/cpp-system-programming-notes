## 1. Nginx

### 1.1 架构特点

| 特点 | 说明 |
| --- | --- |
| 多进程模型 | 1 个 master + N 个 worker（一般等于 CPU 核数）；master 负责读配置、fork/监控 worker，worker 处理真实请求 |
| 事件驱动 | 每个 worker 一个 epoll（/kqueue），全异步非阻塞，单线程扛海量连接 |
| 模块化 | 核心极小，功能全在模块：event/handler/filter/upstream/load-balancer 等 |
| 内存池 | 连接级、请求级内存池，请求结束统一销毁，几乎不逐块 free |
| 热升级/平滑重载 | `reload` 不中断服务：master 起新 worker、老 worker 处理完存量再退出 |

```text
master（管理进程，不处理请求，root 启动后降权）
  ├── worker 0  ── 自己的 epoll 事件循环 ── 处理分到的连接
  ├── worker 1  ── 自己的 epoll
  └── worker N  ── 自己的 epoll
  （cache manager / loader 等辅助进程按需）
```

### 1.2 为什么用多进程而非多线程

- 多进程天然共享代码、隔离数据：一个 worker 段错误只死自己，master 拉起新的，整体不挂。
- 单 worker 内单线程，**无锁**，没有数据竞争，省去同步开销。
- 多核靠多进程横向扩展；`SO_REUSEPORT`（1.9.1+）让多 worker 绑同一端口由内核做连接负载均衡，替代早期的 `accept_mutex` 惊群锁。

### 1.3 一个 HTTP 请求的处理流水线（11 阶段）

```text
读请求 post_read → server_rewrite → 找配置 find_config → rewrite
→ post_rewrite → 访问控制 preaccess/access → post_access
→ 生成内容 try_files/content → log
每个阶段挂载一串模块 handler，按顺序执行；content 阶段产出内容，
再经 header filter 链、body filter 链（gzip/chunked/headers）加工后发出
```

- **handler 模块**生成内容（如静态文件、fastcgi 代理）；**filter 模块**加工响应头/体；**upstream 模块**做反向代理与负载均衡。
- 反向代理是"全双工"两条连接：client↔nginx、nginx↔upstream，各自挂事件，互不阻塞。

### 1.4 关键数据结构：内存池 ngx_pool_t

```c
// 小块：从池的 current 块按对齐边界切，不够就再挂一块；大块(>max)直接 malloc、单独可释放
struct ngx_pool_s {
    ngx_pool_data_t      d;        // 当前块：已用指针 last、块尾 end、失败计数 failed
    size_t               max;      // 小块上限：超过走大块
    ngx_pool_t          *current;  // 下一次分配从哪块开始找
    ngx_chain_t         *chain;
    ngx_pool_large_t    *large;    // 大块链表（可单独 free）
    ngx_pool_cleanup_t  *cleanup;  // 析构回调链（如关闭 fd、释放外部资源）
};
// 请求结束 ngx_destroy_pool(r->pool)：调 cleanup 回调、释放所有块，杜绝泄漏
```

设计精髓：**生命周期与请求/连接绑定，统一回收**，把"配对 free"的负担从每个函数上拿掉——这是 C 语言下对抗内存泄漏的经典工程范式。

## 2. Redis

### 2.1 核心设计

| 点 | 说明 |
| --- | --- |
| 单线程命令执行 | 命令在**主线程串行执行**，天然无锁、无数据竞争；6.0 起把 socket 读写、协议解析交给多 IO 线程，**命令执行仍单线程** |
| 事件驱动 | 自研 ae 事件库（封装 epoll/kqueue/select），文件事件 + 时间事件（定时任务）同一循环 |
| 纯内存 | 数据在内存，瓶颈多在网络与内存带宽而非 CPU |
| 持久化 | RDB 快照（fork + COW）+ AOF 追加日志（AOF rewrite 压缩） |

### 2.2 单线程为何还快

1. 纯内存操作，单次命令在纳秒~微秒级。
2. IO 多路复用 + 非阻塞，单连接等待不阻塞全局。
3. 命令串行，**无锁、无上下文切换、无缓存行弹跳**。
4. 高效底层数据结构（跳表、压缩列表、哈希表）。
5. 协议简单（RESP），解析开销小。

> 单线程的代价：单条**慢命令**（`keys *`、大 `hgetall`、大集合 `sort`）会阻塞所有客户端。生产要禁用危险命令、分页扫描（`scan/hscan`）、控制单个 key 规模。

### 2.3 核心数据结构

| 对象 | 底层编码（随数据量/参数自动转换） |
| --- | --- |
| String | 整数 / embstr / raw（SDS） |
| Hash | listpack（小）↔ hashtable（大） |
| List | quicklist（双向链表 + listpack 节点） |
| Set | intset（纯整数且小）↔ hashtable |
| ZSet | listpack（小）↔ **skiplist + dict**（大）：跳表按分值有序遍历，dict 存 member→score 实现 O(1) 取分 |

```c
// SDS（老版本示意；新版本按长度细分为 sdshdr5/8/16/32/64，更省内存）
struct sdshdr {
    int len;        // 已用长度 → strlen O(1)
    int free;       // 剩余空间 → 预分配，减少扩容次数
    char buf[];     // 柔性数组，二进制安全（可存 \0）
};
```

| 机制 | 要点 |
| --- | --- |
| SDS 相比 C 字符串 | O(1) 长度、二进制安全、预留空间减少重分配、惰性释放 |
| dict 渐进式 rehash | 扩容时挂**两张哈希表**，每次增删改查顺带迁移一小批，避免一次性 rehash 卡顿 |
| 跳表 skiplist | 多层有序链表实现 O(logN) 查找/范围查询，实现比平衡树简单、无旋转、范围友好 |
| ziplist→listpack | 7.0 用 listpack 取代 ziplist，消除连锁更新风险 |

### 2.4 持久化、过期与淘汰

| 主题 | 机制 |
| --- | --- |
| RDB | `bgsave` fork 子进程借 COW 生成二进制快照，体积小、恢复快，可能丢最后一次快照后的数据 |
| AOF | 每条写命令追加；`appendfsync always/everysec(默认)/no`；日志膨胀用 rewrite 重写压缩；7.0 支持 multi-part AOF |
| 过期删除 | 惰性删除（访问时查）+ 定期删除（抽样扫描）双策略 |
| 内存淘汰 | 内存达 `maxmemory`：noeviction、allkeys/volatile-lru、-lfu、-random、-ttl；LRU 是**采样近似**而非精确 LRU |

## 3. muduo（C++ 高性能网络库，Reactor 范本）

muduo 是学习 C++ 网络编程的最佳源码之一，线程模型即 **one loop per thread + thread pool**：

```text
mainReactor(主线程 EventLoop)            只负责 accept 新连接
      │ 按轮询把新连接分发
      ├── subReactor 0 (EventLoop 线程0，一个 epoll)  ── 持有若干 TcpConnection
      ├── subReactor 1 (EventLoop 线程1)
      └── subReactor N ...
线程间不靠锁共享数据，而用 EventLoop::runInLoop/queueInLoop 把任务"投递"到所属线程执行
```

| 组件 | 职责 |
| --- | --- |
| EventLoop | 一个线程一个，封装"epoll_wait + 执行待办回调"的循环；`loop->runInLoop(cb)` 实现跨线程调度 |
| Channel | 不拥有 fd，只负责一个 fd 的**可读/可写/关闭事件分发**与回调绑定 |
| Poller/EPollPoller | epoll 的封装，返回活跃 Channel 列表 |
| EventLoopThreadPool | 一组 sub loop，main loop accept 后按负载分配连接 |
| TcpConnection | 一条连接的全部状态：输入/输出 Buffer、socket、Channel；用 `shared_ptr` 管理生命周期 |

关键工程技巧：

- **跨线程唤醒用 eventfd**：sub loop 平时阻塞在 epoll_wait，别的线程往它的待办队列塞任务后写 eventfd 把它唤醒，避免用锁+条件变量。
- **生命周期防竞态**：回调里 `shared_from_this`/`tie` 弱引用保证执行回调期间对象不被析构（与《../01-语言基础/04-内存管理与智能指针.md》7.5 同源）。
- **应用层输出缓冲**：写不完先存 `output buffer`，等 EPOLLOUT 再继续发，做到非阻塞且不丢数据。

> 对照阅读：Reactor 五角色、one loop per thread、eventfd 唤醒的原理见《../12-网络与服务器架构/04-Reactor与高性能网络库.md》第 6 章。

## 4. LevelDB / RocksDB（LSM 存储引擎）

| 层 | 内容 |
| --- | --- |
| 写入路径 | 先顺序写 **WAL 日志**（宕机可恢复），再写内存 **MemTable（跳表，有序）** |
| Flush | MemTable 写满 → 冻结为 Immutable → 后台落盘成 **SSTable**（有序、不可变文件） |
| 分层 | L0 文件可能键重叠，L1 往下每层内部有序、层间有序；后台 **compaction** 合并、去重、删除 tombstone |
| 读取路径 | MemTable → Immutable → L0 各文件 → L1…Ln，配 **Bloom Filter** 快速判断 key 不在某文件、block cache 加速 |
| 优势/代价 | 顺序写极快、写放大低；代价是**读放大、空间放大**与 compaction 占用 IO |

RocksDB（Facebook  fork 自 LevelDB）增强：多线程 compaction、列族、分层/分层级压缩、更多压缩算法与限流，是 MyRocks、TiKV、CockroachDB 等的底座。细节配合《../16-基础设施与平台/01-存储引擎原理.md》。

## 5. memcached

| 点 | 说明 |
| --- | --- |
| 线程模型 | 多线程：main 线程 accept，worker 线程各自事件循环（与 muduo 思路一致），用任务队列分发连接 |
| 内存管理 | **slab 分配器**：按固定尺寸分 slab class，item 放进最接近的块，**避免频繁 malloc 与外部碎片**，代价是内部碎片 |
| 分布式 | 服务器本身**不分片**，由客户端用**一致性哈希**把 key 分散到多个实例 |
| 淘汰 | 每个 class 内 LRU |
| 与 Redis 区别 | 纯 KV、value 不透明、无丰富数据结构、单线程模型不同（memcached 多线程） |

## 6. Skynet（游戏服务器框架）

| 特点 | 说明 |
| --- | --- |
| Actor 模型 | 每个 service 一个独立执行环境（默认独立 Lua VM，也可 C），**状态不共享** |
| 消息通信 | 服务间只靠消息队列异步通信，天然避免锁 |
| 多线程 | 少量 worker 线程从全局/次级消息队列取消息，派发给对应 Actor 串行执行 |
| 调度 | 每条消息处理是一次 Actor 执行，Actor 内部不会并发，编程模型简单 |

```text
服务 A ──消息──► 全局队列 ──► worker 取出 ──► 目标服务 B（在 B 的 VM 里串行处理）
```

Actor 模型精髓：**用消息传递代替共享内存，用每 Actor 串行代替加锁**，与多线程共享状态形成对照。

## 7. DPDK（高性能数据平面）

| 技术 | 说明 |
| --- | --- |
| 用户态驱动 | 网卡经 UIO/VFIO 绑定到用户态，**绕过内核协议栈与系统调用**，自己轮询收包 |
| 大页内存 | 2M/1G hugepage 降低 TLB miss |
| PMD 轮询 | 不靠中断，忙等轮询收发包，延迟稳定（代价是占满 CPU） |
| CPU 亲和 | 独占核心、绑 NUMA 本地内存，避免迁移与跨节点访存 |
| 无锁结构 | `rte_ring`（多生产者多消费者无锁环形队列）、`rte_mempool`（固定块对象池） |
| 适用 | 网关、防火墙、负载均衡、软路由等超高吞吐/极低延迟数据面；**不适合**复杂业务逻辑 |

> 与内核协议栈的取舍、用户态收包原理配合《../13-并发异步与组件/03-用户态协议栈与DPDK.md》《../02-系统原理/03-系统架构与选型.md》第 2 章。

## 9. 阅读源码方法论

```text
1. README + 目录结构 + 官方架构文档，建立全局观
2. 从 main/初始化流程入手：谁创建谁、谁持有谁（画对象关系图）
3. 抓五条主线：
   ① 线程/进程模型  ② 事件循环/调度  ③ 核心数据结构
   ④ 内存怎么来怎么走  ⑤ 连接/请求/对象的完整生命周期
4. 顺着一条典型路径走到底（如 Nginx：收到一个字节→发出响应；Redis：一条命令进→出）
5. 小改动 + 编译运行 + 加日志/gdb 断点，验证自己的理解
```

| 想搞清的问题 | 去读哪里 |
| --- | --- |
| 内存如何管理 | 内存池/slab/arena/对象池的创建与销毁点 |
| 事件如何驱动 | epoll 封装、事件循环主函数、回调注册表 |
| 连接/请求生命周期 | 结构体在哪 new/accept、在哪 close/free |
| 多线程怎么协作 | 任务队列、wakeup 机制、锁与无锁结构 |
| 配置如何生效 | 解析模块 → 内部结构体 → 运行时读取点 |

## 10. 快速参考卡片

```text
Nginx：master+多worker(单线程epoll) + 请求级内存池 + 11阶段流水线 + filter链
Redis：命令单线程(6.0 IO多线程) + ae事件 + SDS/dict渐进rehash/跳表 + RDB/AOF
muduo：one loop per thread，main reactor accept，sub reactor IO，eventfd 跨线程唤醒
LSM：WAL→MemTable(skiplist)→SSTable 分层 compaction，Bloom 加速读
memcached：多线程 + slab 定长块 + 客户端一致性哈希分片
Skynet：Actor 状态隔离 + 消息队列，串行代替锁
DPDK：用户态驱动绕过内核 + 大页 + PMD 轮询 + rte_ring 无锁
读源码五主线：线程模型/事件/数据结构/内存/生命周期；顺一条典型路径走到底
```

**常见坑（面试易被追问）：**
1. 说 Redis 单线程却不知道 6.0 后 IO 多线程、命令执行仍单线程，以及异步删除（unlink/惰性释放）。
2. 说 Nginx 高性能却讲不清 worker 模型、内存池与 `SO_REUSEPORT`/惊群。
3. 把 LSM 只说成"写内存刷盘"，讲不清 compaction、读放大与 Bloom filter。
4. 读源码只看不跑，答不出"改哪里、加什么日志能验证理解"。
5. 混淆多进程/多线程/协程/Actor 的适用边界与共享方式。
6. 把 DPDK 当通用方案，忽略其独占 CPU、不适合复杂业务的代价。
7. 不知道 muduo 为何用 eventfd 唤醒、为何 TcpConnection 要 shared_ptr 管生命周期。
