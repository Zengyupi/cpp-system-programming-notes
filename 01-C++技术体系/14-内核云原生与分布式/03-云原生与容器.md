## 1. 容器 vs 虚拟机

```text
┌─────────────────────────────────────────────┐
│ 虚拟机：每个 VM 完整 Guest OS                │
│ App | App | App                            │
│ Bins/Libs | Bins/Libs | Bins/Libs          │
│ Guest OS | Guest OS | Guest OS             │
│ Hypervisor (KVM/Xen)                       │
│ Host OS                                   │
│ 硬件                                       │
└─────────────────────────────────────────────┘

┌─────────────────────────────────────────────┐
│ 容器：共享 Host 内核，进程级隔离             │
│ App | App | App                            │
│ Bins/Libs | Bins/Libs | Bins/Libs          │
│ Container Engine (Docker/containerd)       │
│ Host OS（共享内核）                         │
│ 硬件                                       │
└─────────────────────────────────────────────┘
```

| 维度 | 虚拟机 | 容器 |
| --- | --- | --- |
| 隔离级别 | 硬件虚拟化（完整 OS） | 进程级（共享内核） |
| 启动速度 | 分钟级 | 秒级（~100ms） |
| 资源开销 | 高（每 VM 一个完整 OS，GB 级内存） | 低（进程级，MB 级） |
| 镜像大小 | GB 级 | MB 级（基础镜像 ~5MB） |
| 安全性 | 强隔离（Hypervisor 层） | 弱（共享内核，容器逃逸风险） |
| 密度 | 单机几十台 | 单机几百个 |
| 适用 | 异构 OS、强隔离需求 | 微服务、弹性伸缩、CI/CD |

**容器不是轻量级虚拟机**：容器共享宿主机内核，没有自己的内核；容器内的"root"在宿主机上可能是普通用户（User Namespace）。容器逃逸（CVE-2019-5736 等）是真实安全风险，生产环境用非 root 用户 + seccomp + AppArmor 加固。

## 2. 容器三大底层技术

### 2.1 Namespace（命名空间——隔离什么能看到）

Namespace 是 Linux 内核提供的**全局资源隔离**机制：每个 Namespace 有独立的资源视图，进程在 Namespace 内看到的是隔离后的资源。

| Namespace | 隔离内容 | 系统调用 flag | 说明 |
| --- | --- | --- | --- |
| PID | 进程号 | `CLONE_NEWPID` | 容器内 PID=1，看不到宿主机进程 |
| Mount | 文件系统挂载点 | `CLONE_NEWNS` | 容器有独立的根文件系统 |
| NET | 网络栈 | `CLONE_NEWNET` | 独立网卡、端口、路由表、iptables |
| UTS | 主机名/域名 | `CLONE_NEWUTS` | 容器有独立 hostname |
| IPC | 信号量、消息队列、共享内存 | `CLONE_NEWIPC` | 独立的 System V IPC |
| User | 用户和组 ID | `CLONE_NEWUSER` | 容器内 root 映射到宿主机普通用户 |
| Cgroup | cgroup 根目录 | `CLONE_NEWCGROUP` | 独立的 cgroup 视图（Linux 4.6+） |
| Time | 系统时间 | `CLONE_NEWTIME` | 独立的时间视图（Linux 5.6+） |

```c
// 创建新进程并加入多个新 Namespace（容器创建的核心）
#define _GNU_SOURCE
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

static char child_stack[1024 * 1024];

int child_main(void* arg) {
    // 子进程在新 Namespace 中：独立 PID、网络、挂载、主机名、IPC
    printf("Container: pid=%d, hostname=", getpid());
    execlp("bash", "bash", NULL);  // 启动 shell
    return 0;
}

int main() {
    int flags = CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWNS |
                CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWUSER;
    pid_t pid = clone(child_main, child_stack + sizeof(child_stack),
                      flags | SIGCHLD, NULL);
    waitpid(pid, NULL, 0);
    return 0;
}
```

**User Namespace 的安全意义**：容器内的 UID 0（root）映射到宿主机的非特权 UID（如 100000），即使容器内进程"以 root 运行"，在宿主机上也只是普通用户权限，大幅降低逃逸危害。

### 2.2 Cgroups（控制组——限制能用多少）

Cgroups 是 Linux 内核提供的**资源限制与统计**机制，限制进程组的 CPU、内存、IO 等资源使用。

| 子系统 | 限制内容 | 关键参数 |
| --- | --- | --- |
| cpu | CPU 时间片 | `cpu.cfs_quota_us` / `cpu.cfs_period_us`（如 50000/100000 = 0.5 核） |
| cpuacct | CPU 使用统计 | 统计 CPU 用量 |
| cpuset | 绑定 CPU 核和内存节点 | `cpuset.cpus`、`cpuset.mems`（NUMA 亲和） |
| memory | 内存限制 | `memory.limit_in_bytes`（硬限制）、`memory.memsw.limit_in_bytes`（含 swap） |
| blkio | 块设备 IO | 读写速率限制（BPS/IOPS） |
| devices | 设备访问白名单 | 允许/禁止访问特定设备 |
| freezer | 冻结/恢复进程组 | 挂起容器所有进程 |
| net_cls | 网络流量标记 | 配合 tc 做流量控制 |
| pids | 进程数限制 | `pids.max`（防 fork bomb） |

**Cgroups v1 vs v2**：

| 维度 | v1 | v2 |
| --- | --- | --- |
| 架构 | 每个子系统独立层级树 | 统一层级树（所有子系统一棵树） |
| 接口 | 每个子系统一个目录 | 统一目录，文件带子系统前缀 |
| 进程归属 | 一个进程可属多个层级 | 一个进程只属一个 cgroup（inner node 不能有进程） |
| 内存管理 | memory + memsw 分开 | memory.max 统一（含 swap） |
| 采用状态 | 老系统默认 | 新系统默认（systemd 240+） |

```text
# Docker 限制资源的本质就是写 cgroup 文件
docker run --cpus=2 --memory=512m --pids-limit=100 nginx
# 等价于在 cgroup 中设置：
# cpu.max = 200000 100000（2 核）
# memory.max = 512M
# pids.max = 100
```

**OOM Killer**：容器内存超过 `memory.limit_in_bytes` 时，内核 OOM killer 会杀掉容器内进程（通常是 PID 1）。C++ 服务要处理好内存，避免被 OOM kill 导致数据丢失。

### 2.3 UnionFS（联合文件系统——镜像分层）

UnionFS 把多个目录（层）**联合挂载**到同一个挂载点，上层覆盖下层。镜像就是一组只读层的联合，容器运行时在最上层加一个可写层。

```text
容器可写层（Container R/W）   ← 运行时修改写在这里（COW）
├─ 应用层（COPY app /app）    只读
├─ 依赖层（RUN apt install）  只读
├─ 基础层（FROM ubuntu）      只读
└─ 内核（共享宿主机）
```

**写时复制（COW）**：修改下层文件时，先把文件复制到可写层再修改，下层保持不变。删除文件时在可写层创建"whiteout"文件标记删除。好处：多个容器共享基础层，节省磁盘和内存（页缓存共享）。

**OverlayFS**（Docker 默认存储驱动）：
- `lowerdir`：只读层（可以多个，用冒号分隔）
- `upperdir`：可写层
- `merged`：联合挂载后的视图
- `workdir`：内部工作目录

```text
# Docker 镜像分层查看
docker history nginx:latest
# 每行对应一层，IMAGE 列是层 ID，CREATED BY 是创建该层的指令
```

## 3. Docker 架构与核心

### 3.1 Docker 组件

```text
客户端(docker CLI) ──REST API──► dockerd(Docker守护进程)
                                     ├─ containerd(容器生命周期管理)
                                     │   └─ containerd-shim
                                     │       └─ runc(OCI运行时，真正创建容器)
                                     ├─ 镜像管理(拉取/存储/分层)
                                     ├─ 网络管理(bridge/overlay)
                                     └─ 卷管理(volume)
```

| 组件 | 职责 |
| --- | --- |
| `dockerd` | Docker 守护进程，监听 REST API，管理镜像/容器/网络/卷 |
| `containerd` | 行业标准容器运行时，管理容器生命周期（启动/停止/删除） |
| `runc` | OCI 运行时，真正调用 Linux 系统调用（clone/namespace/cgroups）创建容器 |
| `docker CLI` | 命令行客户端，与 dockerd 通信 |

### 3.2 Dockerfile 最佳实践

| 原则 | 说明 |
| --- | --- |
| 多阶段构建 | 编译环境和运行环境分离，最终镜像不含编译工具链 |
| 最小基础镜像 | 用 `alpine`/`distroless`/`scratch` 替代 `ubuntu`，减小攻击面 |
| 层缓存利用 | 变化少的指令放前面（依赖安装），变化多的放后面（代码复制） |
| 合并 RUN 指令 | 减少层数，`apt-get install && rm -rf /var/lib/apt/lists/*` 同层清理 |
| 非 root 用户 | `USER appuser`，避免容器内 root |
| .dockerignore | 排除无关文件，加快构建、减小上下文 |
| 固定版本标签 | `FROM ubuntu:22.04` 而非 `ubuntu:latest`，保证可复现 |

```dockerfile
# C++ 服务多阶段构建示例
FROM gcc:12 AS builder
WORKDIR /src
COPY CMakeLists.txt .
COPY src/ ./src/
RUN cmake -B build -DCMAKE_BUILD_TYPE=Release && \
    cmake --build build -j$(nproc)

FROM ubuntu:22.04
RUN apt-get update && apt-get install -y --no-install-recommends \
    libstdc++6 ca-certificates && \
    rm -rf /var/lib/apt/lists/*                    # 同层清理，减小镜像
RUN useradd -m appuser
USER appuser
COPY --from=builder /src/build/server /app/server
WORKDIR /app
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s \
    CMD curl -f http://localhost:8080/health || exit 1
CMD ["/app/server"]
```

### 3.3 常用命令速查

| 命令 | 说明 |
| --- | --- |
| `docker build -t name:tag .` | 构建镜像 |
| `docker run -d --name c -p 8080:80 -v /data:/data name` | 后台运行、端口映射、挂载卷 |
| `docker ps -a` | 查看所有容器（含已停止） |
| `docker images` | 查看本地镜像 |
| `docker exec -it cid bash` | 进入运行中容器 |
| `docker logs -f cid` | 查看并跟随日志 |
| `docker stop cid && docker rm cid` | 停止并删除容器 |
| `docker rmi image` | 删除镜像 |
| `docker compose up -d` | 编排启动多容器 |
| `docker system prune -a` | 清理未使用的镜像/容器/网络 |

## 4. Kubernetes 核心

### 4.1 K8s 架构

```text
                    ┌─────────────────────────────┐
                    │      Master（控制平面）       │
                    │  API Server ← 所有操作入口    │
                    │  etcd ← 集群状态存储          │
                    │  Scheduler ← Pod 调度        │
                    │  Controller Manager ← 控制器  │
                    └──────────┬──────────────────┘
                               │
          ┌────────────────────┼────────────────────┐
          ▼                    ▼                    ▼
   ┌────────────┐      ┌────────────┐      ┌────────────┐
   │   Node 1   │      │   Node 2   │      │   Node 3   │
   │ kubelet    │      │ kubelet    │      │ kubelet    │
   │ kube-proxy │      │ kube-proxy │      │ kube-proxy │
   │ Pod(容器)  │      │ Pod(容器)  │      │ Pod(容器)  │
   └────────────┘      └────────────┘      └────────────┘
```

| 组件 | 职责 |
| --- | --- |
| API Server | 所有操作的唯一入口，REST API，认证授权，etcd 交互 |
| etcd | 分布式 KV 存储，保存集群所有状态（Raft 共识） |
| Scheduler | 监听未调度的 Pod，根据资源/亲和性/污点选择 Node |
| Controller Manager | 运行各种控制器（Deployment/ReplicaSet/Node 等），调谐到期望状态 |
| kubelet | Node 上的代理，管理 Pod 生命周期（创建/监控/重启） |
| kube-proxy | Node 上的网络代理，维护 Service 的负载均衡规则（iptables/IPVS） |

### 4.2 核心对象

| 对象 | 职责 | 关键属性 |
| --- | --- | --- |
| Pod | 最小调度单元，1 或多个容器共享网络/存储 | `containers`、`restartPolicy` |
| Deployment | 无状态应用管理，副本数 + 滚动更新 | `replicas`、`strategy`、`selector` |
| StatefulSet | 有状态应用，稳定网络标识+有序部署 | `serviceName`、`volumeClaimTemplates` |
| Service | 稳定访问入口 + 负载均衡 | `type`(ClusterIP/NodePort/LoadBalancer)、`selector` |
| ConfigMap | 配置数据（非敏感） | `data`、挂载为文件或环境变量 |
| Secret | 敏感数据（base64 编码） | `data`、`type` |
| Ingress | 七层路由（域名/路径转发） | `rules`、`tls` |
| Namespace | 逻辑隔离（多团队/多环境） | `default`、`kube-system` |
| PersistentVolume | 持久化存储 | `storageClassName`、`accessModes` |

```yaml
# Deployment 示例
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-server
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-server
  template:
    metadata:
      labels:
        app: my-server
    spec:
      containers:
      - name: server
        image: my-server:1.0
        ports:
        - containerPort: 8080
        resources:
          requests: { cpu: "100m", memory: "128Mi" }
          limits:   { cpu: "500m", memory: "512Mi" }
        livenessProbe:
          httpGet: { path: /health, port: 8080 }
          initialDelaySeconds: 10
        readinessProbe:
          httpGet: { path: /ready, port: 8080 }
```

### 4.3 服务发现与负载均衡

```text
客户端 → Service(ClusterIP) → kube-proxy(iptables/IPVS 规则) → Pod IP 列表
                                                              （按 label selector 动态更新）
```

Service 通过 `label selector` 匹配 Pod，kube-proxy 在每个 Node 上维护 iptables/IPVS 规则实现负载均衡。Pod IP 变化时 Service 自动更新，客户端只需访问稳定的 Service DNS（`my-server.default.svc.cluster.local`）。

## 5. 容器网络

| 网络模式 | 说明 | 适用 |
| --- | --- | --- |
| bridge | 默认，容器连到 docker0 网桥，NAT 出网 | 单机容器互通 |
| host | 共享宿主机网络命名空间 | 高性能网络（如 DPDK、压测） |
| none | 无网络 | 安全隔离、批处理 |
| overlay | 跨主机容器网络（VXLAN） | 多机集群（Docker Swarm/K8s） |

**K8s 网络模型**：所有 Pod 间可直接通信（NAT 不修改源/目的 IP），通过 CNI 插件（Calico/Flannel/Cilium）实现跨 Node 网络。

## 6. 容器化 C++ 服务要点

### 6.1 PID 1 与信号处理

容器内的应用通常是 PID 1。Linux 中 PID 1 有特殊语义：**不会被默认信号处理器终止**——如果应用不处理 SIGTERM，`docker stop` 发的 SIGTERM 会被忽略，10 秒后被 SIGKILL 强杀（可能丢数据）。

```cpp
#include <atomic>
#include <csignal>
#include <iostream>
#include <thread>

std::atomic<bool> g_running{true};

void signal_handler(int sig) {
    std::cout << "Received signal " << sig << ", shutting down gracefully...\n";
    g_running = false;
}

int main() {
    std::signal(SIGTERM, signal_handler);  // docker stop / k8s 优雅终止
    std::signal(SIGINT, signal_handler);   // Ctrl+C

    while (g_running) {
        // 处理请求...
        std::this_thread::sleep_for(std::chrono::milliseconds(100));
    }

    // 优雅退出：停止接受新连接、等待在途请求完成、刷新日志、释放资源
    std::cout << "Cleanup done, exiting.\n";
    return 0;
}
```

### 6.2 健康检查

| 探针 | 作用 | 失败后果 |
| --- | --- | --- |
| livenessProbe | 检测进程是否存活 | 失败 → 重启容器 |
| readinessProbe | 检测是否可接受流量 | 失败 → 从 Service 摘除（不重启） |
| startupProbe | 检测启动是否完成 | 失败 → 重启（慢启动应用用） |

C++ 服务应实现 `/health`（进程存活）和 `/ready`（依赖就绪+可接受流量）两个 HTTP 端点。

### 6.3 资源限制与 OOM

```yaml
resources:
  requests: { cpu: "100m", memory: "128Mi" }  # 调度依据，保证最低资源
  limits:   { cpu: "500m", memory: "512Mi" }  # 硬上限，超过内存被 OOM kill
```

C++ 服务注意：
- `memory.limit` 是 cgroup 限制，超过直接 OOM kill（不会抛异常）
- 内存池/缓存大小要根据 limit 设置，不要用"宿主机内存"做判断
- `std::vector` 扩容可能瞬间翻倍，预留足够 headroom

### 6.4 日志约定

容器化应用日志应输出到 **stdout/stderr**，由容器运行时收集（`docker logs`、K8s logging driver）。不要写文件到容器内（容器销毁即丢失），需要持久化用 Volume 挂载。

## 7. 快速参考卡片

```text
容器 = Namespace(隔离视图) + Cgroups(资源限制) + UnionFS(分层镜像)
Namespace 7种：PID/Mount/NET/UTS/IPC/User/Cgroup
Cgroups：cpu/memory/blkio/cpuset/pids，v2 统一层级
UnionFS：lowerdir(只读层) + upperdir(可写层) + merged(联合视图)，COW
Docker：dockerd → containerd → runc(真正调 clone 创建容器)
Dockerfile：多阶段构建 + 最小基础镜像 + 非root + 层缓存
K8s：Pod(最小单元) → Deployment(副本+滚动更新) → Service(稳定入口)
K8s Master：API Server + etcd + Scheduler + Controller Manager
K8s Node：kubelet + kube-proxy + Pod
健康检查：liveness(重启) / readiness(摘流量) / startup(慢启动)
C++容器化：PID1处理SIGTERM + 日志stdout + 内存按limit设置 + /health端点
```

**常见坑与最佳实践：**
1. 容器内 C++ 服务以 PID=1 运行，未处理 SIGTERM 导致无法优雅退出——必须注册信号处理器。
2. 未设置 `--memory` 限制，容器内内存泄漏拖垮宿主机——必须设 memory limit。
3. 单层镜像过大（一条 RUN 装所有依赖且不清理），无法复用缓存且镜像臃肿——合并 RUN 并同层清理。
4. 日志写文件而非 stdout，容器日志系统采集不到——统一输出到 stdout/stderr。
5. 容器内服务绑定 `127.0.0.1`，外部无法访问——绑定 `0.0.0.0` 或容器 IP。
6. 用 `latest` 标签，构建不可复现——固定版本标签（`ubuntu:22.04`）。
7. 容器内以 root 运行，安全风险高——`USER` 切换到非特权用户。
8. 健康检查只检查进程存活不检查依赖就绪——readinessProbe 应检查 DB/缓存连接。
9. 多阶段构建忘记拷贝运行时依赖（libstdc++ 等），容器启动报 `error while loading shared libraries`——运行镜像装必要的运行库。
10. K8s 中 Pod 被驱逐但未处理优雅终止——`terminationGracePeriodSeconds` 给足时间，应用处理 SIGTERM。
