## 1. 分布式基础理论

### 1.1 CAP 定理

CAP 定理（Brewer 定理）：分布式系统中，**一致性（Consistency）、可用性（Availability）、分区容错性（Partition tolerance）三者不可兼得**，最多同时满足两个。

| 字母 | 含义 | 说明 |
| --- | --- | --- |
| C（Consistency） | 一致性 | 所有节点同一时刻看到相同数据（线性一致） |
| A（Availability） | 可用性 | 每个请求都能在有限时间内收到非错误响应 |
| P（Partition tolerance） | 分区容错 | 网络分区（节点间消息丢失/延迟）时系统仍能运行 |

**为什么必须选 P？** 分布式系统跨网络部署，网络分区是必然事件（光纤被挖、交换机故障、机房断网），不选 P 意味着分区时系统不可用，违背分布式初衷。因此实际选择是 **CP 或 AP**：

| 选择 | 取舍 | 代表系统 |
| --- | --- | --- |
| CP | 保证一致性，牺牲可用性（分区时拒绝服务） | ZooKeeper、etcd、HBase、MongoDB(强一致模式) |
| AP | 保证可用性，牺牲强一致（分区时返回可能旧数据） | Eureka、Cassandra、DynamoDB、CouchDB |

**CAP 的常见误解**：
- CAP 不是"三个里选两个"那么简单——C 和 A 不是非黑即白，有多种一致性级别和可用性降级策略。
- CAP 只在**网络分区发生时**才需要取舍，正常情况下 C 和 A 可以同时满足。
- "选了 AP 就不要一致性"是错的——AP 系统通常提供最终一致性，只是不保证强一致。

### 1.2 BASE 理论

BASE 是对 CAP 中 AP 方案的实践总结，放弃强一致换取高可用：

| 缩写 | 全称 | 含义 |
| --- | --- | --- |
| BA | Basically Available | 基本可用：允许响应时间增加或功能降级，但不拒绝服务 |
| S | Soft state | 软状态：允许系统存在中间状态（数据同步中），不影响整体可用 |
| E | Eventually consistent | 最终一致性：经过一段时间后，所有节点数据收敛一致 |

**ACID vs BASE**：

| 维度 | ACID（传统数据库） | BASE（分布式系统） |
| --- | --- | --- |
| 一致性 | 强一致 | 最终一致 |
| 可用性 | 事务期间可能阻塞 | 基本可用，允许降级 |
| 设计思想 | 保守、先保证正确 | 激进、先保证可用 |
| 适用 | 金融、账务 | 互联网高并发场景 |

## 2. 一致性模型

| 模型 | 说明 | 强度 |
| --- | --- | --- |
| 线性一致（Linearizability） | 写入后任何读立即读到最新值，且操作有全局时序 | 最强（CAP 的 C） |
| 顺序一致（Sequential） | 所有进程看到相同操作顺序，但不保证实时 | 强 |
| 因果一致（Causal） | 有因果关系的操作顺序一致，无因果的可乱序 | 中 |
| 最终一致（Eventual） | 无新写入后，经过一段时间收敛一致 | 弱 |
| 读己之写（Read-your-writes） | 写入后自己能读到，别人不一定 | 弱（特定保证） |

**最终一致的变种**：
- **读己之写一致**：用户写完后刷新页面能看到自己的写（同会话内）。
- **单调读一致**：用户读到某个值后，不会读到更旧的值。
- **因果一致**：如果操作 B 依赖操作 A 的结果，则所有节点先看到 A 再看到 B。

## 3. 共识算法

### 3.1 Paxos

Paxos 是分布式共识的经典算法，由 Lamport 提出，**难理解、难实现**，但被证明是正确的。

| 角色 | 职责 |
| --- | --- |
| Proposer（提议者） | 提出提案（编号+值） |
| Acceptor（接受者） | 投票接受/拒绝提案 |
| Learner（学习者） | 学习已达成共识的值 |

**两阶段提交**：
1. **Prepare 阶段**：Proposer 发 Prepare(n)，Acceptor 承诺不接受编号 < n 的提案，并返回已接受的最大编号提案。
2. **Accept 阶段**：Proposer 收到多数派响应后，发 Accept(n, value)，Acceptor 接受（若未承诺更高编号）。

**核心保证**：通过"多数派"和"编号递增"保证只有一个值被选中，且后续提案只能选已选中的值。Paxos 太复杂，工程上多用 Raft。

### 3.2 Raft【高频】

Raft 是 Paxos 的**易理解替代**，核心是"强领导者"模型，分解为三个子问题：

| 子问题 | 机制 |
| --- | --- |
| 领导者选举（Leader Election） | 任期（term）+ 随机超时 + 多数派投票 |
| 日志复制（Log Replication） | Leader 向 Follower 同步日志，多数派确认后提交 |
| 安全性（Safety） | 只有包含所有已提交日志的节点才能当选 Leader |

```text
状态流转：
Follower ──超时没收到心跳──> Candidate ──获多数票──> Leader
                              │
                       未获多数票/发现更高term ──> 退回 Follower
```

**领导者选举**：
- 每个 Follower 有随机选举超时（150~300ms），超时未收到 Leader 心跳则转为 Candidate，term+1，给自己投票并发 RequestVote。
- 获得多数派票的 Candidate 成为 Leader，发心跳（AppendEntries 空日志）维持权威。
- 一个 term 内最多一个 Leader（多数派保证）。

**日志复制**：
```text
客户端 → Leader: 写请求
Leader → 本地追加日志(term, index, command)
Leader → Follower: AppendEntries(prevLogIndex, prevLogTerm, entries[])
Follower → 校验连续性 → 追加日志 → 返回成功
Leader → 收到多数派成功 → 提交日志(commitIndex++) → 应用到状态机
Leader → 下次心跳通知 Follower 提交
```

**安全性保证**：
- Candidate 的 RequestVote 包含自己最后一条日志的 (term, index)。
- Follower 只投票给日志**至少和自己一样新**的 Candidate（最后日志 term 大的更新，term 相同则 index 大的更新）。
- 因此 Leader 一定包含所有已提交日志，不会丢数据。

**Raft 代表实现**：etcd（分布式 KV）、TiKV（分布式存储）、Consul、CockroachDB。

### 3.3 ZAB（ZooKeeper Atomic Broadcast）

ZooKeeper 使用的共识协议，与 Raft 类似但有差异：
- ZAB 支持**恢复模式**（Leader 崩溃后重新选举+数据同步）和**广播模式**（正常运行）。
- ZAB 的 Leader 选举用 epoch（类似 term）+ zxid（类似日志索引）。
- ZAB 保证**全局有序**（所有事务有全局递增 zxid）；Raft 用 (term, index) 全局排序，日志索引跨任期连续递增。

## 4. 分布式锁

### 4.1 为什么需要分布式锁

单机锁（`std::mutex`）只管一个进程内的线程。多实例部署时，每个进程各有一把锁，全部加锁成功 → 共享资源被并发修改（如库存超卖）。锁必须放到所有进程都能访问的共享存储上。

### 4.2 三种实现对比

| 方案 | 原理 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| Redis | `SET NX PX` + Lua 释放 | 性能高（10w QPS） | 主从切换可能丢锁（脑裂） | 高并发短临界区 |
| MySQL | 唯一索引/行锁/乐观锁 | 强一致、无需新组件 | 性能差（百 QPS） | 低频任务防重 |
| ZooKeeper/etcd | 临时节点+watch / 租约 | 强一致(CP)、会话断开自动释放 | 性能中等（千 QPS） | 选主、绝不双写 |

### 4.3 Redis 分布式锁【核心】

三条军规：

| 军规 | 命令/做法 | 原因 |
| --- | --- | --- |
| 加锁必须原子 | `SET key uuid NX PX 30000` | SETNX + EXPIRE 两条命令间宕机 → 死锁 |
| 解锁必须校验+原子 | Lua：GET 比对 uuid 相等才 DEL | 先 GET 后 DEL 两步间锁易主 → 误删他人锁 |
| 长任务要续期 | 看门狗每 TTL/3 执行 PEXPIRE | 业务没完成锁先过期 → 并发进入临界区 |

```lua
-- 加锁（一条命令原子）
SET lock_key unique_value NX PX 30000

-- 解锁（Lua 保证原子性，校验 value 防止误删）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**Redlock（红锁）**：在 N 个独立 Redis 实例上同时加锁，获得超过 N/2+1 个才算成功。解决单实例主从切换丢锁问题，但有争议（Martin Kleppmann 与 antirez 的辩论），重要场景建议用 etcd/ZooKeeper。

### 4.4 etcd 分布式锁

etcd 基于 Raft 强一致，分布式锁用**租约（lease）+ 事务（txn）**实现：
1. 创建 lease（TTL），keepalive 续期。
2. `txn` 中 `put key with lease` 带 `create_revision=0` 条件（不存在才创建）。
3. 创建成功即获得锁；失败则 watch 锁的删除事件，等待后重试。
4. 释放：删除 key 或 lease 过期自动释放。

比 Redis 锁更可靠（CP 系统，无主从切换丢锁问题），但性能略低。

## 5. 分布式事务

### 5.1 分布式事务的挑战

单体应用中一个事务操作多个表，用本地事务即可。微服务后，一个业务操作跨多个服务/多个数据库，本地事务管不了——需要分布式事务。

### 5.2 方案对比

| 方案 | 原理 | 一致性 | 性能 | 业务侵入 | 适用 |
| --- | --- | --- | --- | --- | --- |
| 2PC（两阶段提交） | prepare → commit/rollback | 强一致 | 低（阻塞） | 低（资源管理器支持） | 数据库层面、传统企业 |
| 3PC | canCommit → preCommit → doCommit | 强一致 | 低 | 低 | 理论为主，很少用 |
| TCC | Try / Confirm / Cancel | 最终一致 | 中 | 高（每个服务写三个接口） | 资金、库存等强业务语义 |
| SAGA | 长事务拆成多个本地事务+补偿 | 最终一致 | 高 | 中 | 长流程业务（订单→支付→物流） |
| 本地消息表 | 本地事务+消息表+定时投递 | 最终一致 | 高 | 中 | 已有 DB、异步场景 |
| 事务消息 | RocketMQ 半消息+回查 | 最终一致 | 高 | 低 | 已有 RocketMQ |
| 最大努力通知 | 反复通知+对账 | 最终一致（弱） | 高 | 低 | 支付结果通知 |

### 5.3 2PC 流程

```text
协调者 → 所有参与者: prepare（准备提交，锁资源）
参与者 → 协调者: ready / no / abort
协调者决策:
  全部 ready → 发 commit
  有一个 no/超时 → 发 rollback
参与者 → 执行 commit/rollback → 释放锁 → 返回 ack
```

**2PC 的问题**：
- **同步阻塞**：prepare 后所有参与者锁资源等待协调者指令，性能差。
- **单点故障**：协调者挂了，参与者一直阻塞（锁不释放）。
- **数据不一致**：commit 阶段部分参与者收到 commit、部分没收到（协调者宕机），数据不一致。

3PC 增加 canCommit 阶段和超时机制，减少阻塞但仍不完美，实际很少用。

### 5.4 TCC 模式

| 阶段 | 动作 | 说明 |
| --- | --- | --- |
| Try | 资源预留/冻结 | 如冻结库存（不扣减）、冻结金额 |
| Confirm | 确认执行 | 扣减冻结的库存/金额 |
| Cancel | 回滚释放 | 解冻库存/金额 |

每个服务必须实现 Try/Confirm/Cancel 三个接口，且 Confirm/Cancel 必须**幂等**（可能被重试调用）。TCC 业务侵入大但一致性好，适合资金类场景。

### 5.5 本地消息表

```text
1. 业务操作 + 插入消息表（同一个本地事务，原子）
2. 后台线程定时扫描消息表，投递到 MQ
3. 消费者处理消息，处理成功后标记已完成
4. 失败则重试（指数退避），超过阈值告警人工介入
```

优点：简单可靠，不依赖特殊 MQ；缺点：消息表与业务表耦合，需要定时任务。

## 6. 负载均衡与高可用

### 6.1 负载均衡策略

| 策略 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 轮询（Round Robin） | 依次分发 | 简单 | 不考虑节点性能差异 |
| 加权轮询 | 按权重分发 | 适配异构节点 | 权重配置需调优 |
| 最小连接数 | 分发到当前连接最少的节点 | 动态适配负载 | 需要维护连接计数 |
| 一致性哈希 | 哈希环+虚拟节点 | 节点增减影响最小 | 实现稍复杂 |
| 随机 | 随机分发 | 简单 | 可能不均 |
| 源 IP 哈希 | 同一客户端固定到同一节点 | 会话保持 | 节点变化时会话丢失 |

### 6.2 一致性哈希【高频】

**问题**：普通取模哈希 `hash(key) % N`，节点数 N 变化时几乎所有 key 重新映射（缓存雪崩）。

**一致性哈希**：key 和节点都映射到 0~2³² 哈希环上，key 顺时针找第一个节点。节点增减只影响相邻节点的 key。

```text
哈希环（0 ~ 2^32-1）：
  Node A ← key1, key2
  Node B ← key3
  Node C ← key4, key5
新增 Node D 在 B、C 之间：只有 B~D 之间的 key 迁移到 D，其余不变
```

**虚拟节点**：节点少时分布不均（一个节点可能占环的大半），每个物理节点映射 100~200 个虚拟节点，让 key 分布更均匀。

```cpp
// 一致性哈希简化实现
class ConsistentHash {
    std::map<uint32_t, std::string> ring_;  // 哈希值 -> 节点名
    int virtual_nodes_;
public:
    ConsistentHash(int vn = 150) : virtual_nodes_(vn) {}
    void addNode(const std::string& node) {
        for (int i = 0; i < virtual_nodes_; ++i) {
            std::string key = node + "#" + std::to_string(i);
            uint32_t h = std::hash<std::string>{}(key);
            ring_[h] = node;
        }
    }
    std::string getNode(const std::string& key) {
        if (ring_.empty()) return "";
        uint32_t h = std::hash<std::string>{}(key);
        auto it = ring_.lower_bound(h);  // 顺时针找第一个 >= h 的节点
        if (it == ring_.end()) it = ring_.begin();
        return it->second;
    }
};
```

### 6.3 高可用设计

| 手段 | 说明 |
| --- | --- |
| 多副本 | 无状态服务多实例部署，负载均衡分发 |
| 主从切换 | 有状态服务主从复制，主挂了从提升（Raft/哨兵） |
| 熔断降级 | 下游故障时快速失败，返回兜底结果，防止雪崩 |
| 限流 | 保护系统不被突增流量打垮（令牌桶/漏桶） |
| 超时重试 | 设置合理超时，失败重试（注意幂等） |
| 异地多活 | 多机房部署，单机房故障不影响整体 |

## 7. 快速参考卡片

```text
CAP：三者不可兼得，必保 P → CP(etcd/ZK) 或 AP(Eureka/Cassandra)
BASE：基本可用 + 软状态 + 最终一致
一致性分级：线性一致 > 顺序一致 > 因果一致 > 最终一致
Raft：选举(term+随机超时+多数派) + 日志复制(AppendEntries) + 安全(Leader日志最全)
Paxos：Prepare + Accept 两阶段，多数派，难理解难实现
分布式锁：Redis(SET NX PX + Lua + 看门狗) / MySQL(唯一索引) / etcd(租约+txn)
分布式事务：2PC强一致但阻塞；TCC/SAGA/本地消息表最终一致
一致性哈希：哈希环+虚拟节点，节点增减只影响相邻key
高可用：多副本+主从切换+熔断降级+限流+超时重试
```

**常见坑与最佳实践：**
1. 分布式锁未设超时时间，进程崩溃导致死锁——必须带 TTL。
2. Redis 锁释放未校验 value，误删他人锁——Lua 脚本 GET+DEL 原子化。
3. 2PC 协调者单点故障，参与者长期阻塞——用 TCC/SAGA 等最终一致方案替代。
4. 一致性哈希未加虚拟节点，节点少时分布严重不均——每节点 100~200 个虚拟节点。
5. 混淆"强一致"与"最终一致"，在资金场景用了最终一致导致资损——按业务对一致性的要求选型。
6. 分布式事务中 Confirm/Cancel 未做幂等，重试导致重复扣减——所有补偿操作必须幂等。
7. Redis 主从异步复制，主写锁未同步到从即宕机，从提升为主后锁丢失——重要场景用 Redlock 或 etcd。
8. 负载均衡用源 IP 哈希，节点扩缩容时大量会话丢失——用粘性会话+会话共享（Redis 存 session）。
9. 只考虑正常情况不考虑网络分区——CAP 取舍必须在设计阶段明确，不能出问题才想。
10. 把"最终一致"当成"不用管一致性"——最终一致需要监控收敛时间，数据不一致窗口要有对账和补偿机制。
