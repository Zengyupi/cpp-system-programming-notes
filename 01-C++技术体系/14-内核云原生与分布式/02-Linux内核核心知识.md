## 1. 进程、线程与协程的本质及切换成本

### 1.1 Linux 里没有本质区别的进程与线程

* 进程是**资源容器**（独立地址空间、fd 表、信号处理），线程是**调度实体**；

* Linux 不单独实现线程，线程本质是和同组进程**共享地址空间的 task\_struct**（通过 `clone` 带 `CLONE_VM | CLONE_FILES` 等标志创建），所以线程也叫轻量级进程；

* 协程则完全在**用户态**切换寄存器和栈，不进内核，操作系统根本感知不到。

### 1.2 上下文切换到底切什么、谁更贵

| 切换   | 保存 / 恢复内容                            | 是否进内核、换地址空间 | 相对成本        |
| ---- | ------------------------------------ | ----------- | ----------- |
| 进程切换 | 寄存器、栈、**页表基址**、刷部分 TLB、CPU cache 受影响 | 是，换 mm      | 最重（数千～上万周期） |
| 线程切换 | 寄存器、栈；**地址空间不变**，TLB 保留              | 进内核但同 mm    | 较轻          |
| 协程切换 | 少量寄存器 + 栈指针，用户态几十～几百条指令              | 否           | 最轻          |

这解释了两个高频结论：**为什么线程切换比进程轻（共享地址空间不用切页表 / TLB）**、**为什么高并发用协程（把上万连接的调度从内核线程切换变成用户态协作切换）**。

### 1.3 进程状态与两个经典坑

```text
R 运行/就绪 ──时间片到──> 就绪队列

S 可中断睡眠（等事件，能被信号唤醒）

D 不可中断睡眠（等磁盘IO等，杀不掉，kill -9 也无效）

T 停止(trace/stop)    Z 僵尸(已退出但父进程没回收)
```

* **D 状态**：进程在内核态等待 IO 返回，此时任何信号都不处理；大量 D 状态 = 磁盘 / 网络存储 IO 卡死，不是程序 bug，查存储链路。

* **僵尸进程 Z**：子进程退出后残留一个 task\_struct 等父进程取退出码；父进程不 `wait` 就一直占 PID，堆积会耗尽进程号。解法：父进程处理 `SIGCHLD` 调 `waitpid`、或被 init/systemd 托管、或 `double fork` 让孤儿进程被 1 号进程收养。

```bash
ps -eLf                       # 看线程（LWP）

top -H -p <pid>               # 看某进程各线程 CPU

ps -eo state,pid,comm | sort | uniq -c   # 统计各状态进程数

cat /proc/<pid>/status        # 线程数 Threads、状态、内存
```

## 2. 进程调度 CFS

* Linux 默认 **CFS（完全公平调度器）**：用红黑树按 **vruntime（虚拟运行时间）** 排序，永远挑 vruntime 最小的运行；nice 值决定权重，nice 越低权重越大、vruntime 涨得越慢、分到 CPU 越多。

* 实时调度类 `SCHED_FIFO/SCHED_RR` 优先级高于 CFS，工业网关等硬实时场景才用，滥用会饿死系统进程。

```bash
nice -n 10 ./app          # 以低权重启动（nice 越大优先级越低）

taskset -c 0,1 ./app      # 绑核运行，减少迁移导致的 cache 失效

chrt -f 50 ./rt_app       # 以 SCHED_FIFO 实时策略运行
```

后台开发实践：线程池 / Reactor 线程**绑核**能减少跨核迁移和缓存失效；但不要随便用实时优先级。

## 3. 虚拟内存（后台性能的核心，务必理解）

### 3.1 为什么要有虚拟内存

每个进程都以为自己独占连续的 0\~ 全部地址空间，由 **MMU + 多级页表**映射到物理内存。带来三大好处：进程隔离（一个进程崩了不踩别人）、内存 "看起来" 连续（物理页可分散）、按需分配与超卖。

```text
虚拟地址 ──MMU(查多级页表,TLB缓存映射)──> 物理地址

缺页(page fault)：页表里没映射 → 陷入内核 → 分配物理页/从磁盘读入 → 返回继续
```

### 3.2 TLB、大页与缺页

* 每次地址转换都查页表很慢，**TLB** 缓存最近的虚拟→物理映射；页越小，同样内存需要的映射项越多、越容易 TLB miss（一次 miss 要走多级页表，几十～上百周期）。

* **大页（HugePage 2MB/1GB）**：一条映射覆盖更大内存，显著减少 TLB miss，这就是 Redis/DPDK/ 数据库吃大内存时开大页变快的原因。

* **缺页分两种**：minor（minor fault，物理页还在 / 刚分配，软中断代价小）和 major（major fault，要从磁盘读回，毫秒级，性能杀手）。进程刚启动、访问新申请内存时的 minor fault 是正常的；运行中频繁 major fault 说明内存不够在换入换出。

### 3.3 malloc/free 背后到底发生什么

```cpp
小内存：glibc(ptmalloc) 从堆(brk)的 arena 空闲块里切，free 后通常留着复用、不立刻还 OS

大内存(默认>128KB)：直接 mmap 匿名页，free 时 munmap 归还
```

* `free` 不等于物理内存立刻下降：小块回到分配器空闲链表供复用；这也是为什么进程 RSS 只涨不降（内存池 / 分配器缓存），不一定是泄漏。

* 多线程下 ptmalloc 每个 arena 带锁，高并发分配有竞争 —— 这是 **tcmalloc/jemalloc 更快**、以及业务用**内存池**的根本原因，见《../13-并发异步与组件/04-内存池与池化技术.md》。

* **写时复制 COW**：`fork` 后父子共享同一物理页并标只读，谁写才复制一页。Redis 做 RDB 快照就是 fork 子进程、靠 COW 遍历内存，理解这点才知道 fork 期间大量写入会放大内存。

### 3.4 内存回收与 OOM

内存紧张时内核先回收（丢弃干净文件页、把匿名页 swap 到磁盘），实在不够触发 **OOM Killer** 按 `oom_score`（占用越大、越 "该死" 得分越高）杀进程 —— 被杀的未必是占内存最多的那个。

```bash
free -h                      # available 才是真正还能用的（含可回收缓存）

cat /proc/meminfo            # 详细：Cached/Swap/Slab/AnonPages

cat /proc/<pid>/smaps        # 进程各段内存、缺页统计

vmstat 1                     # si/so 列非0说明在 swap，major fault 列 bo

dmesg | grep -i "killed process"   # 查是否被 OOM
```

## 4. 文件系统与 IO

### 4.1 VFS 与 "一切皆文件"

VFS 是一层统一抽象，ext4/xfs/tmpfs/procfs/socket 都实现同一套 open/read/write 接口，所以应用能用统一方式操作普通文件、设备、管道、socket。

```text
用户态 read/write ──系统调用──> VFS ──> 具体文件系统(ext4/xfs) ──> 页缓存 ──> 块层 ──> 磁盘
```

### 4.2 Page Cache：为什么 "写成功" 不等于 "落盘"

* **读**：先查页缓存，命中就直接从内存返回（不碰磁盘），所以重复读文件很快。

* **写**：`write()` 默认只写到**页缓存**就返回（writeback，延迟刷盘），由内核后台异步落盘。**掉电会丢**。要数据可靠必须 `fsync/fdatasync` 强制刷到物理介质 —— 这正是数据库 WAL/redo log 必须 fsync 的原因。

* `echo 3 > /proc/sys/vm/drop_caches` 只是丢弃可重建的干净缓存（测试用），不影响数据安全。

### 4.3 五种 IO 模型（和网络编程一脉相承）

阻塞 IO → 非阻塞轮询 → IO 多路复用 (select/poll/epoll) → 信号驱动 → 异步 IO (AIO/io\_uring)。演进逻辑和第 1 章并发模型一致：**让等待不阻塞线程**。网络上最终落到 epoll/Reactor，新方案是 io\_uring，见《../13-并发异步与组件/02-io_uring与异步IO.md》。

### 4.4 零拷贝到底省了什么

传统 "读文件再发给网络"：磁盘→内核页缓存→**拷贝到用户态**→再**拷回内核** socket 缓冲→网卡，共 4 次拷贝、4 次上下文切换。`sendfile` 让数据在内核内直接从页缓存到 socket，省掉两次用户态拷贝和两次切换；`mmap` 把页缓存直接映射到用户空间省一次拷贝。前提是数据**不需要在用户态加工**。

## 5. 网络栈：一个包的内核之旅

```cpp
收包：网卡 DMA 写入内存 → 硬中断通知 → 软中断(NAPI 轮询批量收) → 协议栈(IP/TCP 处理)

        → 放入对应 socket 接收队列 → 唤醒 epoll_wait/阻塞的 read

发包：write 到发送缓冲 → 协议栈加首部 → 排队(qdisc) → 网卡驱动 → DMA 发出
```

理解这条路径就能解释一堆现象：

* 为什么要调 `somaxconn`/ 接收缓冲：协议栈收到了但应用来不及取，队列会满、丢包 / 重传；

* 为什么软中断 si CPU 高：收包都在软中断处理，单核扛不住时要开 RPS/RFS 分散到多核；

* **DPDK 为什么快**：绕过整个内核协议栈，用户态轮询 + 大页 + 独占 CPU + UIO 直接收发包，省掉中断、拷贝和上下文切换，代价是自己实现协议栈，见《../13-并发异步与组件/03-用户态协议栈与DPDK.md》。

## 6. 用户态 / 内核态与系统调用开销

* 程序平时跑在用户态（受限），调 `read/write/epoll_wait/futex/mmap` 等会经 `syscall` 指令**陷入内核态**执行，再返回；切换要保存现场、做权限检查、且现代 CPU 的 Meltdown/Spectre 缓解（KPTI）还会刷 TLB，单次开销纳秒～微秒级，高频累积很可观。

* 高性能框架的很多设计本质都在**减少系统调用次数**：epoll 一次等一批 fd（而非每连接一个阻塞调用）、`writev` 合并写、io\_uring 一次提交一批 IO（SQE/CQE 批量收割）。

## 8. 快速参考卡片

```cpp
进程=资源容器，线程=共享地址空间的调度实体，协程=用户态自切（不进内核、最轻）

切换成本：进程(切页表/TLB) > 线程(同地址空间) > 协程(用户态)

D 状态=不可中断IO(杀不掉,查存储)；Z 僵尸=父进程没 wait

CFS：红黑树按 vruntime 选最小，nice 定权重；绑核减迁移

虚拟内存：MMU+多级页表+TLB；大页减 TLB miss；major fault 要读盘(慢)

malloc 小走 brk 复用、大走 mmap；free 不一定还 OS；COW 支撑 fork 快照

write 只到 Page Cache，可靠落盘要 fsync；零拷贝省用户态来回拷贝

收包：DMA→硬中断→软中断→协议栈→socket队列→唤醒epoll；DPDK 绕过内核

syscall 有陷入开销，epoll/writev/io_uring 的价值=减少 syscall 次数
```

## 9. 常见问题与坑

| 现象                           | 根因方向                                               |
| ---------------------------- | -------------------------------------------------- |
| 一堆进程 D 状态、负载很高但 CPU 不忙       | 磁盘 / 网络存储 IO 阻塞，查 iostat await、存储链路                |
| 僵尸进程越来越多、无法新建进程              | 父进程没回收子进程，处理 SIGCHLD/waitpid                       |
| RSS 只涨不降就断定内存泄漏              | 先分清分配器缓存 / 页缓存；用 valgrind/heaptrack、smaps 确认是否真泄漏  |
| 程序偶发卡几十～几百毫秒                 | major fault、swap（si/so）、调度被抢占、THP 规整；查 vmstat/perf |
| free 显示 available 和 free 差很多 | 可回收的页缓存算在 available，是正常的，别误判内存不足                   |
| 高并发单核 si（软中断）跑满              | 网络收包集中在一个核，开 RPS/RFS 或多队列网卡分散                      |
| 写文件返回成功却丢数据                  | 只写了 Page Cache，关键数据必须 fsync                        |
| 线程开越多反而越慢                    | 切换与锁竞争、cache 弹跳；考虑线程数匹配核数或协程化                      |
