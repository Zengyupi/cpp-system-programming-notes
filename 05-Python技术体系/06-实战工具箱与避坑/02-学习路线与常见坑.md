## 1. 系统程序员学Python最小路径

C++/Rust程序员学Python最大的误区是按Python就业教程从头学起，花大量时间在Web框架、ORM、前端模板上。系统程序员需要的是**脚本与工具链能力**，核心路径可以压缩到20小时。

### 1.1 必须掌握（20小时）

| 主题 | 关键内容 | 对应C++/Rust概念 | 学习时间 |
| --- | --- | --- | --- |
| 语法基础 | 变量、缩进、条件、循环、函数、类 | 与C++差异主要在语法形式 | 3h |
| 数据结构 | list/dict/set/tuple、切片、推导式 | vector/map/unordered_set/pair | 3h |
| 文件与IO | open/read/write、上下文管理器、pathlib | fstream/文件操作 | 2h |
| 子进程与系统 | subprocess、os、sys、argparse | system/popen/命令行解析 | 3h |
| 文本处理 | 正则re、字符串方法、编码bytes/str | string/regex/编码转换 | 3h |
| 异常与错误 | try/except/finally、自定义异常、EAFP模式 | try/catch/RAII | 1h |
| 模块与包 | import、__init__.py、虚拟环境venv | #include/命名空间/Cargo | 2h |
| 常用标准库 | json/csv/struct/hashlib/logging/itertools | 对应各类第三方库 | 3h |

**核心原则**：标准库优先。系统程序员的Python脚本90%的需求只用标准库就能解决，不要一上来就装第三方包。`subprocess`跑编译、`struct`拼报文、`re`分析日志、`argparse`做CLI、`pathlib`管路径、`json`读配置——这些是日常最高频的组合。

### 1.2 按需学习（用到再看）

| 主题 | 触发场景 | 推荐资源 |
| --- | --- | --- |
| threading/multiprocessing | 需要并行跑编译或数据处理 | 标准库文档 + concurrent.futures |
| asyncio | 写高并发mock服务端或爬虫 | 先理解事件循环，再学async/await |
| ctypes/cffi | Python调用C动态库做混合编程 | 对照《../../04-Rust技术体系/02-Rust进阶机制/02-Unsafe裸指针与FFI互操作.md》理解ABI |
| matplotlib | 监控数据可视化、性能图表 | 只学pyplot接口，5分钟上手 |
| pytest | Python代码本身需要单元测试 | 比unittest简洁，fixture是核心 |
| requests | 调用REST API做自动化 | 比urllib简洁，一个get/post就够 |
| numpy/pandas | 大规模日志数据分析 | 只学DataFrame基本操作，别学全 |

### 1.3 可以跳过（系统程序员场景用不到）

- **Django/Flask/FastAPI**：除非要写内部管理后台，否则不需要。系统程序员的Python是工具脚本，不是Web服务。
- **ORM（SQLAlchemy等）**：直接用`sqlite3`标准库或裸SQL足够，脚本场景不需要对象关系映射。
- **前端模板（Jinja2等）**：生成HTML报告时内联字符串模板即可，不需要完整模板引擎。
- **装饰器高级用法**：理解`@staticmethod`/`@classmethod`即可，元编程级别的装饰器对脚本写作无增益。
- **元类（metaclass）**：99%的脚本永远不需要，属于Python框架开发者的知识。
- **WSGI/ASGI**：Web部署概念，与工具脚本无关。
- **pipenv/poetry高级用法**：`venv` + `pip`足够，复杂依赖管理是Python项目的需求，不是脚本的需求。

## 2. Pythonic惯用法对照

"Pythonic"不是玄学，而是**在正确场景用正确写法**。C++/Rust程序员容易把C++的写法直接翻译成Python，结果既不简洁也不高效。以下是最高频的惯用法对照与适用边界。

### 2.1 推导式 vs 循环

**什么时候用推导式**：简单的转换/过滤，一行能写完，逻辑清晰。

```python
# Pythonic：推导式
squares = [x * x for x in range(100) if x % 2 == 0]
names = {user.id: user.name for user in users if user.active}
```

**什么时候用普通循环**：逻辑复杂（多步处理、异常处理、副作用）、需要提前break、推导式嵌套超过两层。

```python
# 不要这样写：嵌套推导式可读性差
result = [(x, y) for x in range(10) if x > 3 for y in range(5) if y < x]

# 用循环更清晰
result = []
for x in range(10):
    if x <= 3:
        continue
    for y in range(5):
        if y < x:
            result.append((x, y))
```

**对照C++**：推导式类似C++20的`std::views::filter | transform`，但Python推导式是立即求值（列表），不是惰性的。

### 2.2 生成器 vs 列表

**什么时候用生成器**：数据量大、不需要随机访问、只遍历一次、可能提前终止。

```python
# 生成器：逐行读取大文件，不占内存
def read_lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.strip()

# 消费时可以用for，也可以用next
for line in read_lines("huge.log"):
    if "ERROR" in line:
        process(line)
        break  # 提前终止，不会读完整个文件
```

**什么时候用列表**：需要多次遍历、需要随机访问（索引）、需要len()、数据量小。

```python
# 列表：需要排序/索引/多次遍历
errors = [line for line in read_lines("app.log") if "ERROR" in line]
errors.sort()
print(f"共{len(errors)}条错误，第一条: {errors[0]}")
```

**常见错误**：把生成器当列表用——`len(generator)`会报`TypeError`，索引访问也不行。需要列表时用`list(generator)`转换，但注意这会消耗整个生成器。

### 2.3 with语句 vs 手动close

**什么时候必须用with**：文件、socket、数据库连接、锁、任何需要确保释放的资源。

```python
# Pythonic：with自动关闭，即使异常也会释放
with open("data.bin", "rb") as f:
    data = f.read()

# 等价于（但更安全）：
f = open("data.bin", "rb")
try:
    data = f.read()
finally:
    f.close()
```

**with的本质**是上下文管理器协议（`__enter__`/`__exit__`），类似C++的RAII。区别在于C++RAII在对象析构时自动释放，Python的with是显式的作用域。自定义上下文管理器：

```python
from contextlib import contextmanager

@contextmanager
def timed_block(name):
    import time
    start = time.time()
    try:
        yield  # with块的代码在这里执行
    finally:
        print(f"{name} 耗时 {time.time() - start:.3f}s")

with timed_block("编译"):
    subprocess.run(["make", "-j8"], check=True)
```

### 2.4 EAFP vs LBYL

**EAFP**（Easier to Ask for Forgiveness than Permission）：先做，出错再处理。是Python的推荐风格。

**LBYL**（Look Before You Leap）：先检查条件，再执行。是C++的常见风格。

```python
# EAFP（Pythonic）
try:
    value = config["timeout"]
except KeyError:
    value = 30

# LBYL（C++风格，Python中不推荐）
if "timeout" in config:
    value = config["timeout"]
else:
    value = 30
```

**EAFP的优势**：避免竞态条件（检查和操作之间状态可能变化）、代码更直接、性能在正常路径上更好（不用每次检查）。

**什么时候用LBYL**：异常开销不可接受的高频路径、检查本身很廉价且逻辑更清晰、需要区分多种缺失情况。

```python
# 高频循环中，LBYL可能更快（避免异常栈展开）
result = []
for item in large_list:
    if item in cache:        # LBYL
        result.append(cache[item])
    else:
        val = expensive_compute(item)
        cache[item] = val
        result.append(val)
```

### 2.5 其他惯用法

**解包赋值**：

```python
# 交换变量（不需要临时变量）
a, b = b, a

# 函数返回多值
def get_status():
    return 200, "OK", {"data": 1}
code, msg, body = get_status()

# 用_忽略不需要的值
_, _, body = get_status()

# 用*收集剩余
first, *rest, last = [1, 2, 3, 4, 5]  # first=1, rest=[2,3,4], last=5
```

**enumerate vs range(len)**：

```python
# Pythonic
for i, item in enumerate(items):
    print(f"{i}: {item}")

# 不要这样
for i in range(len(items)):
    print(f"{i}: {items[i]}")
```

**zip并行遍历**：

```python
for name, score in zip(names, scores):
    print(f"{name}: {score}")
```

## 3. 高频坑总表

以下是C++/Rust程序员写Python时最容易踩的坑，按出现频率排序。每个坑都给出现象、原因、正确写法。

### 3.1 编码与字符串

**现象**：`UnicodeDecodeError: 'utf-8' codec can't decode byte 0xc4 in position 0`，或中文乱码。

**原因**：Python 3中`str`是Unicode字符串，`bytes`是字节序列，二者不能隐式转换。从文件/网络读取的是`bytes`，需要显式`.decode()`；`open()`默认用系统编码（Windows上是GBK/cp936，Linux上是UTF-8），跨平台会出问题。

**正确写法**：

```python
# 始终指定encoding
with open("file.txt", encoding="utf-8") as f:
    text = f.read()

# 二进制文件用bytes模式
with open("packet.bin", "rb") as f:
    data = f.read()  # bytes

# bytes <-> str 显式转换
text = data.decode("utf-8")     # bytes -> str
data = text.encode("utf-8")     # str -> bytes

# 不确定编码时，用errors参数容错
text = data.decode("utf-8", errors="replace")  # 非法字节替换为U+FFFD
```

**对照C++**：C++的`std::string`就是字节序列，没有编码概念，编码处理需要手动做。Python把编码问题暴露在类型系统层面，反而更安全——前提是理解`str`/`bytes`的区别。

### 3.2 GIL与并发

**现象**：用`threading`开多线程跑CPU密集型计算，速度没有提升甚至更慢。

**原因**：CPython有全局解释器锁（GIL），同一时刻只有一个线程执行Python字节码。CPU密集型任务多线程无法并行，但IO密集型任务（网络请求、文件读写、sleep）可以，因为IO操作会释放GIL。

**正确写法**：

```python
# CPU密集型：用multiprocessing（多进程，每个进程有独立GIL）
from multiprocessing import Pool

def process_file(path):
    # CPU密集的解析/计算
    return result

with Pool(8) as pool:
    results = pool.map(process_file, file_list)

# IO密集型：用threading或asyncio
import concurrent.futures
with concurrent.futures.ThreadPoolExecutor(max_workers=16) as executor:
    futures = [executor.submit(fetch_url, url) for url in urls]
    results = [f.result() for f in concurrent.futures.as_completed(futures)]
```

**注意**：`subprocess`调用的外部程序（如C++编译器）不受GIL限制，多线程并行跑编译是有效的。

### 3.3 可变默认参数

**现象**：函数默认参数是列表/字典，多次调用后数据累积，出现"幽灵数据"。

```python
# 错误写法
def add_item(item, lst=[]):
    lst.append(item)
    return lst

add_item(1)  # 返回 [1]
add_item(2)  # 返回 [1, 2] —— 不是预期的 [2]！
```

**原因**：默认参数在函数**定义时**求值一次，不是每次调用时求值。可变对象（list/dict/set）的修改会保留下来。

**正确写法**：

```python
def add_item(item, lst=None):
    if lst is None:
        lst = []
    lst.append(item)
    return lst
```

**对照C++**：C++的默认参数也是在调用点求值，但C++默认参数通常是值类型（int/string），不会出现这个问题。Python的`None`是不可变的，用它做哨兵是标准做法。

### 3.4 闭包延迟绑定

**现象**：循环中创建lambda或闭包，所有闭包都引用循环变量的最终值。

```python
# 错误写法
funcs = []
for i in range(5):
    funcs.append(lambda: i)  # 所有lambda都引用同一个i

for f in funcs:
    print(f())  # 输出 4 4 4 4 4，不是 0 1 2 3 4
```

**原因**：Python闭包捕获的是变量名（引用），不是变量值。循环结束后`i`的值是4，所有闭包调用时都查找当前的`i`。

**正确写法**：

```python
# 方法1：默认参数捕获当前值（默认参数在定义时求值）
funcs = []
for i in range(5):
    funcs.append(lambda i=i: i)

# 方法2：用生成器函数或functools.partial
from functools import partial
funcs = [partial(lambda x: x, i) for i in range(5)]
```

**对照Rust**：Rust闭包默认move语义，捕获的是值，不会有这个问题。Python需要显式处理。

### 3.5 浮点精度

**现象**：`0.1 + 0.2 == 0.3`返回`False`，金额计算出现微小误差。

**原因**：与C++一样，Python的`float`是IEEE 754双精度浮点数，0.1和0.2在二进制中是无限循环小数，无法精确表示。

**正确写法**：

```python
# 比较用容差
abs(a - b) < 1e-9

# 精确十进制计算用decimal
from decimal import Decimal, getcontext
getcontext().prec = 20
a = Decimal("0.1")
b = Decimal("0.2")
print(a + b == Decimal("0.3"))  # True

# 整数计算（金额用分）
total_cents = 10 + 20  # 0.10元 + 0.20元 = 30分
```

### 3.6 相对导入

**现象**：`from .utils import helper`报`ImportError: attempted relative import with no known parent package`，或脚本直接运行时导入失败。

**原因**：相对导入（带点的import）只能在包内部使用，且模块必须作为包的一部分被导入（`python -m package.module`），不能直接运行脚本（`python module.py`）。直接运行时`__name__`是`"__main__"`，Python不知道它属于哪个包。

**正确写法**：

```text
project/
├── main.py              # 入口脚本
└── mypackage/
    ├── __init__.py
    ├── utils.py
    └── core.py          # 内部用相对导入
```

```python
# core.py 内部：相对导入
from .utils import helper

# 运行方式：从项目根目录用 -m 运行
python -m mypackage.core

# 或者在 main.py 中用绝对导入
from mypackage.core import run
```

**脚本写作建议**：单文件脚本不要用相对导入，直接用绝对导入或把脚本所在目录加入`sys.path`。多文件工具建议打包成包，用`python -m`运行。

### 3.7 路径跨平台

**现象**：Windows下写的路径`"data\\config.json"`在Linux下找不到，或用字符串拼接路径导致分隔符错误。

**原因**：Windows用`\`，Linux/macOS用`/`。硬编码分隔符不可移植。

**正确写法**：

```python
# 用pathlib（Python 3.4+，推荐）
from pathlib import Path

config_path = Path("data") / "config.json"  # 自动用正确分隔符
print(config_path)  # Windows: data\config.json, Linux: data/config.json

# 常用操作
Path("output").mkdir(parents=True, exist_ok=True)  # 创建目录，存在不报错
for p in Path("logs").glob("*.log"):               # 遍历文件
    print(p.name)

# 旧代码用os.path
import os
config_path = os.path.join("data", "config.json")
```

**注意**：`Path`对象可以直接传给`open()`、`subprocess.run()`等大多数标准库函数，不需要转成字符串。

### 3.8 内置名遮蔽

**现象**：定义了名为`list`/`dict`/`id`/`type`/`min`/`max`/`sum`的变量，后续调用内置函数时报`TypeError: 'list' object is not callable`。

```python
# 错误写法
list = [1, 2, 3]       # 遮蔽了内置list()
result = list("abc")    # TypeError: 'list' object is not callable
```

**原因**：Python允许变量名与内置函数同名，局部作用域的定义会遮蔽（shadow）内置名。这在C++中也可能发生，但C++编译器通常会警告。

**正确写法**：避免使用内置名做变量名，用`lst`/`items`/`data`/`obj_id`等替代。

```python
# 常见需要避开的内置名
# list, dict, set, tuple, str, int, float, bool, bytes
# id, type, len, min, max, sum, sorted, reversed, enumerate, zip, map, filter
# open, file, input, print, format, range, slice, object, property
# all, any, abs, round, divmod, pow, complex, chr, ord, bin, oct, hex
```

**快速检查**：写完代码后`python -W all script.py`，或用`pylint`/`flake8`检查，会报告`redefined-builtin`警告。

## 4. 什么时候坚决不用Python

Python是优秀的工具语言，但不是万能的。以下场景**坚决不要用Python**，用C++/Rust或其他更合适的语言：

1. **性能敏感的核心路径**：高频交易、实时信号处理、数据包转发线速处理。Python的解释器开销和GIL使其无法达到微秒级延迟。即使PyPy也无法与C++/Rust的裸金属性能相比。

2. **硬实时系统**：嵌入式实时控制、工业控制闭环。Python的GC停顿、解释器延迟不可预测，无法满足硬实时要求。用C/Rust。

3. **内存受限环境**：MCU（几KB~几百KB RAM）、极小容器。Python解释器本身需要几MB内存，无法运行。用C/Rust（no_std）。

4. **需要精细内存布局的场景**：网络协议栈、驱动程序、共享内存结构。Python对象有复杂的内存布局和开销，无法控制字节对齐。用C++的`#pragma pack`或Rust的`#[repr(C)]`。

5. **发布为二进制交付的桌面应用**：虽然有PyInstaller等工具，但打包体积大（几十MB）、启动慢、易被杀毒软件误报。用C++/Qt或Rust/Tauri。

6. **需要长期运行且内存不能泄漏的守护进程**：Python的循环引用GC不是确定性的，某些C扩展可能泄漏内存。虽然可以用`gc`模块调试，但核心守护进程建议用Rust（所有权保证无泄漏）或C++（RAII）。

7. **多线程CPU密集并行**：GIL限制。用C++/Rust的原生线程，或Python的`multiprocessing`（但进程间通信开销大）。

8. **需要调用大量特定平台API且无成熟绑定**：虽然`ctypes`/`cffi`可以调用C库，但复杂C++ API（模板、重载、RAII）的绑定很痛苦。直接用C++写。

**Python的甜蜜点**：一次性脚本、自动化工具、数据处理与分析、原型验证、测试脚手架、构建编排、文档生成、混合编程中的胶水层。这些场景下Python的开发效率远超C++/Rust，且性能通常不是瓶颈。

## 5. 工作中常见Python问题简答

以下是系统程序员在工作中（代码审查、技术讨论、面试）可能被问到的Python问题，给出精准简答。

**Q1: Python的GIL是什么？对多线程有什么影响？**

GIL（Global Interpreter Lock）是CPython中的全局互斥锁，确保同一时刻只有一个线程执行Python字节码。影响：CPU密集型任务多线程无法并行加速；IO密集型任务（网络/文件/sleep）可以并行，因为IO操作会释放GIL。绕过方案：`multiprocessing`多进程、C扩展中释放GIL（如numpy）、用`asyncio`单线程并发。

**Q2: `list`和`tuple`有什么区别？什么时候用哪个？**

`list`可变（可增删改），`tuple`不可变。`list`用`[]`，`tuple`用`()`。性能上`tuple`创建更快、内存更小、可哈希（能做dict的key）。选择：内容会变化用`list`，固定不变的结构化数据用`tuple`（如函数返回多值、坐标点）。需要字典key时必须用`tuple`。

**Q3: `__init__`和`__new__`有什么区别？**

`__new__`是静态方法，负责创建并返回实例对象（在`__init__`之前调用），通常不需要重写，除非要控制实例创建（如单例、不可变类子类化）。`__init__`是实例方法，负责初始化实例属性，在`__new__`返回实例后调用。日常写类只需要`__init__`。

**Q4: Python的深浅拷贝有什么区别？**

`copy.copy()`（浅拷贝）：创建新对象，但内部元素是引用。嵌套的可变对象（如list of list）修改会影响原对象。`copy.deepcopy()`（深拷贝）：递归复制所有嵌套对象，完全独立。注意：不可变对象（int/str/tuple）深浅拷贝无区别；自定义类需要实现`__copy__`/`__deepcopy__`才能正确拷贝。

**Q5: `*args`和`**kwargs`是什么？**

`*args`收集任意数量的位置参数为一个tuple，`**kwargs`收集任意数量的关键字参数为一个dict。用于函数参数数量不确定的场景（如装饰器、转发调用）。调用时`*`和`**`也可以解包：`func(*list_args, **dict_kwargs)`。命名不强制叫args/kwargs，但这是惯例。

**Q6: Python的垃圾回收机制是什么？**

主要是**引用计数**：每个对象维护引用计数，归零时立即释放。辅以**分代垃圾回收**（generational GC）处理循环引用（A引用B、B引用A，计数都不为零但已不可达）。`gc`模块可以手动触发回收、调试泄漏。与C++RAII的区别：Python的对象释放时机在引用归零时（确定性），但循环引用需要GC扫描（非确定性）。

**Q7: `is`和`==`有什么区别？**

`==`比较值是否相等（调用`__eq__`），`is`比较是否是同一个对象（比较`id()`，即内存地址）。`a == b`为True不代表`a is b`为True。常见坑：用`is`比较整数/字符串——小整数（-5~256）和某些字符串被Python缓存，`is`可能返回True，但这是实现细节，不应依赖。比较值永远用`==`，比较None用`is None`（因为None是单例）。

**Q8: Python的装饰器是什么？**

装饰器是接收函数/类作为参数、返回新函数/类的可调用对象，用`@decorator`语法糖应用。本质是`func = decorator(func)`。用于在不修改原函数代码的情况下增加功能（日志、计时、权限检查、缓存）。带参数的装饰器需要三层嵌套：`@decorator(args)`等价于`func = decorator(args)(func)`。`functools.wraps`用于保留原函数的元信息（名称、文档字符串）。

**Q9: `__name__ == "__main__"`是什么意思？**

Python文件被直接运行时，解释器把`__name__`变量设为`"__main__"`；被import时，`__name__`是模块名。这个判断让文件既可以作为脚本直接运行（执行main逻辑），也可以作为模块被导入（不执行main逻辑）。是Python脚本的标准入口写法。

**Q10: Python中怎么处理大文件？**

不要用`read()`或`readlines()`一次性加载到内存。用迭代器逐行读取：`for line in open("big.txt", encoding="utf-8")`，这是惰性的，每次只读一行。二进制文件用`f.read(chunk_size)`分块读取。需要随机访问时用`f.seek()`定位。处理CSV用`csv.reader`（也是迭代器），处理JSON大文件用`ijson`（第三方，流式解析）。

## 6. 本节小结

- **学习路径**：系统程序员学Python只需20小时掌握核心（语法、数据结构、文件IO、子进程、文本处理、异常、模块包、标准库），按需学习threading/asyncio/ctypes/pytest等，跳过Web框架、ORM、元类等与工具脚本无关的内容。
- **Pythonic惯用法**：推导式vs循环、生成器vs列表、with vs手动close、EAFP vs LBYL——关键是在正确场景用正确写法，不是为了"Pythonic"而牺牲可读性。
- **高频坑总表**：编码与字符串、GIL与并发、可变默认参数、闭包延迟绑定、浮点精度、相对导入、路径跨平台、内置名遮蔽——这8类坑是C++/Rust工程师写Python最常踩的，遇到时先查此表。
- **不适用场景**：CPU密集高性能、硬实时、底层驱动、内存受限、需要大量平台API且无成熟绑定——这些场景用C++/Rust，Python做胶水层和工具层。
- **工作问答**：GIL、list/tuple、__init__/__new__、深浅拷贝、*args/**kwargs、垃圾回收、is/==、装饰器、__name__、大文件处理——这10个问题是代码审查和技术讨论中最高频的，精准简答有助于团队沟通。
